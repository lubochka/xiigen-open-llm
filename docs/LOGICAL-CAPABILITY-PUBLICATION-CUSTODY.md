# Опека файлов при публикации обученной способности

Этот документ описывает защиту, которая нужна, когда локальный тренер создаёт файлы новой способности: checkpoint политики, tokenizer, manifest и служебные метрики.

## Зачем это нужно

Тренер сначала пишет файлы во временную область, а потом публикует их как готовую способность. В этот момент нельзя доверять одной строке пути: между проверкой и удалением путь может стать символической ссылкой, hardlink-алиасом или чужим файлом с теми же байтами.

Поэтому публикация доверяет не имени файла, а его физической личности:

- в Windows — идентификатору тома и FileId из удержанного handle;
- в Linux x64 — паре device/inode из `fstat` удержанного дескриптора;
- в обеих системах — размеру, числу ссылок и SHA-256 содержимого.

Если любой признак меняется, операция останавливается fail-closed: тренер не принимает файл как свой и не удаляет чужую замену.

## Контракт тренера

Перед допуском к обучению тренер проверяет, что текущая платформа умеет безопасную файловую опеку. Отказ происходит до допуска, обучения, реестра и создания каталогов. Старый публичный код ошибки сохранён для совместимости отчётов и тестов, но смысл теперь шире: требуется не Windows как ОС, а безопасная опека файловой личности на текущей платформе.

Новые низкоуровневые POSIX-операции собраны в `18.CapabilityTraining/LogicalCapabilityFileCustody.*.cs`. Продуктовый код выше этого слоя не вызывает `open`, `openat`, `unlinkat` или `renameat2` напрямую. Для старой Windows-ветки состояния domain-classifier сохранены прежние Win32 error constants, а Linux/WSL путь той же логики идёт через общий custody helper.

## Windows

Windows-поведение сохранено: файл открывается через handle с нужными правами, личность читается из `GetFileInformationByHandle` и `GetFileInformationByHandleEx`, а удаление ставит delete-disposition на проверенный handle.

Это важно для старых тестов, которые доказывают, что byte-identical подмена не принимается как свой файл.

## Linux / WSL

Linux x64 использует отдельную POSIX-ветку:

- leaf-файл открывается с запретом перехода по символической ссылке;
- путь к custody-каталогу проходится descriptor-walk'ом от доверенного корня `/`: каждый segment открывается через `openat(O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC)`, а отсутствующие segment'ы создаются только через `mkdirat` относительно уже удержанного родительского fd;
- существующие предки не считаются owned-артефактами: root-owned/read-only каталоги и sticky temp-каталоги вроде `/tmp` допустимы как удержанные предки, но финальный custody-каталог обязан принадлежать текущему пользователю и не быть writable для group/other;
- hardlink с числом ссылок больше одного не принимается как owned-файл;
- временный manifest создаётся эксклюзивно;
- публикация manifest использует удержанный дескриптор родительского каталога, advisory-lock и переименование без перезаписи существующего имени;
- состояние domain-classifier переносится active → backup → active только после сверки retained file identity; Linux-переименование использует `renameat2(RENAME_NOREPLACE)`, поэтому чужая замена destination не перезаписывается;
- служебный DPO reservation-lock вида `.dpo_step_000001.lock` принимается в transient-инвентарь только для точного ожидаемого шага и только после повторного захвата identity, `flock`, проверки размера и числа ссылок;
- если DPO возвращает отказ после создания финальных transient-файлов, rollback дополнительно подбирает только точные expected reservation-lock имена текущих шагов; wildcard `*.lock` и чужая замена не удаляются;
- откат перед `unlinkat` заново открывает leaf через удержанный родительский fd и сравнивает inode с удержанным дескриптором; после `unlinkat` retained fd обязан показать тот же inode и `LinkCount == 0`, иначе гонка hardlink считается cleanup-failure;
- file sync и directory sync выполняются там, где файловая система их поддерживает.

Если нужный Linux-примитив недоступен, результат считается узким fail-closed отказом, а не зелёной публикацией. Тренер не игнорирует `*.lock` по маске: чужой lock, lookalike с другим шагом или замена ожидаемого lock-файла между проверкой и cleanup сохраняются и останавливают публикацию.

## Что проверяют тесты

`Tests/DefaultLogicalCapabilityTrainerTests.cs` содержит новые проверки:

- символическая ссылка не открывается как owned-файл;
- hardlink не проходит доказательство единственной файловой личности;
- откат не удаляет чужой файл, если путь был заменён после захвата;
- manifest не публикуется через symlink-предка и не уходит в новый путь, если ancestor заменили после descriptor-proof;
- hardlink, созданный прямо перед `unlinkat`, превращает cleanup в fail-closed и сохраняет alias;
- manifest сохраняется через безопасную публикацию и не перезаписывает уже существующий manifest.
- собственный DPO reservation-lock в Linux не считается foreign inventory, но неожиданный lock и замена expected lock перед cleanup остаются fail-closed.

Отдельный тест в `Tests/TeachingRegistryPersistenceTests.cs` проверяет контракт публикации manifest по реальной способности платформы: он спрашивает `LogicalCapabilityFileCustody.IsCurrentPlatformSupported`, на Windows и Linux x64 доказывает успешную публикацию и чтение inventory, а на неподдерживаемых платформах ждёт прежний стабильный код отказа до создания каталога.

Полная цель среза — чтобы семейство тестов тренера способностей проходило в WSL без отключения защит и без подгонки ожидаемых результатов под старую Windows-only ветку.
