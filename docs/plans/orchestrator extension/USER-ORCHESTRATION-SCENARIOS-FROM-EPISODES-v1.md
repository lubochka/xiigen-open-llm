## 1. Бизнес-идея -> архитектура системы

### Промпт пользователя

```text
У меня есть описание продукта, бизнес-требования и несколько диаграмм. Помоги превратить это в систему, которую можно реально построить.
```

### Ожидаемая оркестрация

1. Понять бизнес-цель продукта и кто им пользуется.
2. Прочитать все приложенные документы и диаграммы.
3. Выделить основные роли, действия пользователей и события системы.
4. Построить первый architecture map: клиент, сервер, данные, внешние сервисы.
5. Определить главный архитектурный принцип проекта.
6. Разложить систему на flows, modules и buildable parts.
7. Отметить, чего не хватает для реализации: данные, экраны, API, роли, правила безопасности.
8. Сформировать первый план работы для архитектора и исполнителя.

## 2. Дизайн или diagram -> buildable plan

### Промпт пользователя

```text
У меня есть диаграммы того, как пользователи проходят через систему. Скажи, как из этого получить план проекта и код.
```

### Ожидаемая оркестрация

1. Разобрать каждую диаграмму как источник требований.
2. Найти actors, actions, decisions, events и data objects.
3. Сопоставить элементы диаграммы с известными архитектурными patterns.
4. Построить flows: что запускается, что вызывает что, где меняется состояние.
5. Перевести flows в проектные части: UI, API, services, storage, integrations.
6. Определить, какие элементы можно строить generic, а какие зависят от конкретного домена.
7. Сформировать build plan по слоям.

## 3. Инструмент генерирует визуальный результат, но результат выглядит неправильно

### Промпт пользователя

```text
Инструмент технически работает, но визуальный результат постоянно неправильный. Нужно понять, как исправлять это раунд за раундом.
```

### Ожидаемая оркестрация

1. Зафиксировать expected visual result и actual visual result.
2. Сравнить их как человек, а не только тестами.
3. Разделить проблемы на классы: layout, spacing, sizing, positioning, styles, responsiveness.
4. Для каждого класса найти root cause.
5. Исправлять по одному классу проблемы за раз.
6. После каждого исправления снова показать результат человеку.
7. Вести state: что было исправлено, что сломалось, что осталось.
8. Не объявлять done без визуального review.

## 4. Несколько fix-ов применили одновременно и всё стало хуже

### Промпт пользователя

```text
Мы пытались исправить несколько связанных проблем сразу, и система стала хуже. Нужно понять, как безопасно продолжить.
```

### Ожидаемая оркестрация

1. Остановить дальнейшие массовые изменения.
2. Составить список всех примененных изменений.
3. Понять, какие изменения конфликтуют друг с другом.
4. Разделить fixes на независимые и зависимые.
5. Вернуться к проверяемой последовательности: один fix -> проверка -> следующий fix.
6. Для каждого fix-а определить expected result и возможный side effect.
7. Вести журнал: что проверено, что откатить нельзя, что требует повторной проверки.

## 5. В середине работы нашли privacy/security проблему

### Промпт пользователя

```text
Мы уже строили feature, но обнаружили, что выбранный storage/design может раскрыть приватные данные одного пользователя другому. Что делать?
```

### Ожидаемая оркестрация

1. Немедленно остановить развитие feature в текущем design.
2. Зафиксировать, какие данные могут утечь и между какими пользователями.
3. Определить trust boundary: кто владеет данными, кто может читать, кто может писать.
4. Проверить storage model, access rules, API contracts и UI exposure.
5. Решить, можно ли исправить design локально или нужен architectural reversal.
6. Построить безопасный replacement route.
7. Обновить plan/state так, чтобы executor не продолжил старый небезопасный путь.

## 6. Платформа слишком связана, модули нельзя менять независимо

### Промпт пользователя

```text
У нас много modules, и они слишком связаны. Я хочу, чтобы пользователь мог взять один module, адаптировать его и опубликовать свою версию, не ломая всё остальное.
```

### Ожидаемая оркестрация

1. Сначала не резать код, а построить карту зависимостей.
2. Найти modules, shared contracts, shared state и hidden coupling.
3. Определить, какие части являются platform core, а какие tenant-customizable.
4. Для каждого module определить входы, выходы, extension points и forbidden dependencies.
5. Сформировать decoupling plan.
6. Определить правила публикации tenant version.
7. Добавить проверки, что изменение одного module не ломает другие.

## 7. Нужно исследовать много modules и не прыгать к выводам

### Промпт пользователя

```text
Мне нужно исследовать много частей системы. Я боюсь начать читать всё подряд и сделать неправильные выводы.
```

### Ожидаемая оркестрация

1. Сначала сформулировать, что именно ищем.
2. Записать hypotheses и вопросы до чтения evidence.
3. Определить, какие файлы и документы отвечают на каждый вопрос.
4. Читать evidence по карте, а не случайно.
5. Для каждого вывода указать источник.
6. Разделять факт, гипотезу и решение.
7. Не строить plan действий до завершения evidence pass.

## 8. Нельзя строить feature, потому что foundation отсутствует

### Промпт пользователя

```text
Я хочу построить feature, но постоянно выясняется, что перед этим не готов foundation. Нужно понять, чего не хватает и в каком порядке строить.
```

### Ожидаемая оркестрация

1. Не начинать feature implementation сразу.
2. Определить конечную feature goal.
3. Разложить goal на prerequisites: data, API, UI, permissions, storage, jobs, tests, docs.
4. Для каждого prerequisite проверить: есть, частично есть, отсутствует.
5. Построить dependency chain.
6. Сначала закрывать foundational gaps.
7. Вести state, чтобы executor не объявил feature done, если foundation не готов.

## 9. Подход оказался неправильным и надо сменить направление

### Промпт пользователя

```text
Мы начали строить поддержку заранее для всех технологий, но поняли, что пользователь приносит свой стек. Нужно поменять подход.
```

### Ожидаемая оркестрация

1. Зафиксировать старое предположение.
2. Объяснить, почему оно неверно для продукта.
3. Определить новый принцип: учиться на проекте пользователя, а не заранее hardcode-ить все варианты.
4. Разделить reusable core и project-specific learning.
5. Переписать plan вокруг on-demand learning.
6. Проверить, какие уже сделанные pieces можно reuse, а какие надо пометить как wrong direction.

## 10. Платформа должна работать внутри другой платформы

### Промпт пользователя

```text
Я хочу, чтобы возможности моей платформы были доступны внутри Visual Studio, VS Code или другой среды, где пользователь уже работает.
```

### Ожидаемая оркестрация

1. Определить host platform и пользовательский entrypoint.
2. Разделить обязанности: host plugin только вход и отображение, XIIGen core принимает смысловые решения.
3. Определить, какие данные host должен передать: active project, linked projects, user prompt, selected files.
4. Определить, что должно происходить внутри XIIGen core.
5. Вернуть пользователю human result, а не внутреннюю кухню.
6. Проверить одинаковость поведения разных hosts.
7. Запретить перенос product brain в plugin.

## 11. Guidelines сломались во время исполнения

### Промпт пользователя

```text
Во время работы выяснилось, что правила или guides не заставляют исполнителя делать правильные шаги. Нужно исправить сам процесс.
```

### Ожидаемая оркестрация

1. Не продолжать исполнение как будто проблема только в коде.
2. Найти, какое правило позволило неправильное поведение.
3. Проверить plan, skills, agents, guides и state.
4. Добавить недостающее правило туда, где executor реально его увидит.
5. Проверить, что новое правило закрывает прежнюю лазейку.
6. Возобновить execution только после protocol correction.

## 12. План чинит планы, но сам план десять раз оказывается дырявым

### Промпт пользователя

```text
Мы уже несколько раз исправляли plan, но executor всё равно находит лазейки и завершает работу неправильно. Нужно сделать план, который сам себя проверяет.
```

### Ожидаемая оркестрация

1. Сначала собрать историю нарушений.
2. Для каждого нарушения найти лазейку в plan/skills/agents/state.
3. Записать explicit anti-loophole rule.
4. Добавить проверку перед каждым завершением раунда.
5. Сделать обязательную передачу на architect review.
6. Если review находит gap, автоматически вернуть в correction loop.
7. Не позволять executor-у объявлять done без architect verification.

## 13. Guidelines стали слишком тяжелыми и остановили работу

### Промпт пользователя

```text
Правил стало так много, что работа парализована. Нужно понять, как сохранить безопасность, но не остановить выполнение.
```

### Ожидаемая оркестрация

1. Разделить правила на safety-critical и process-noise.
2. Определить, какие правила реально предотвращают вред.
3. Определить, какие правила дублируются или конфликтуют.
4. Сохранить строгие gates только там, где ошибка опасна.
5. Упростить execution path.
6. Оставить обязанность state/review, но убрать лишние мягкие стопы.
7. Проверить, что executor может продолжать работу без потери контроля.

## 14. Нужно реализовать много feature flows по одному протоколу

### Промпт пользователя

```text
У нас много feature flows. Нужно реализовать каждый по единому протоколу, чтобы качество было одинаковым.
```

### Ожидаемая оркестрация

1. Определить общий implementation protocol.
2. Для каждого flow определить scope, входы, выходы, UI, backend, storage, tests.
3. Запустить один flow как reference implementation.
4. Проверить, что protocol работает.
5. Применить protocol ко всем flows.
6. Для каждого flow записать state, tests и completion evidence.
7. Не считать fleet готовым, пока все flows не прошли одинаковую проверку.

## 17. Нужен design review по ролям

### Промпт пользователя

```text
Мне нужно проверить большой набор designs/features не одним взглядом, а с разных ролей: architect, user, developer, tester.
```

### Ожидаемая оркестрация

1. Определить роли review.
2. Для каждой роли определить, что она проверяет.
3. Пройти каждый feature/design через все роли.
4. Разделить findings по типам: usability, architecture, implementation, testing, risk.
5. Свести findings в общую матрицу.
6. Определить, какие проблемы blocking, какие можно отложить.
7. Вернуть план исправлений по приоритету.

## 20. Нужно превратить guidance в повторяемую оркестрацию

### Промпт пользователя

```text
У нас есть guidance document. Нужно понять, какие задачи он должен оркестрировать каждый раз, когда появляется похожий случай.
```

### Ожидаемая оркестрация

1. Определить, какой класс задач покрывает guidance.
2. Найти обязательные steps.
3. Найти обязательные checks.
4. Найти типичные failure modes.
5. Определить output contract.
6. Связать guidance с примерами эпизодов.
7. Сделать reusable orchestration template для будущих похожих задач.
