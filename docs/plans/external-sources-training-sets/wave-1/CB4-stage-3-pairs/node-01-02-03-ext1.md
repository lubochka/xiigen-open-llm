## Pair CB4-3.4-159

**Node:** 01 — Domain Splitter
**Stratum:** A (domain breadth — CWE-352 CSRF; must go to cwe-authz, not cwe-authn)
**Source:** CWE Top 25 2023
**Verdict:** Routing

### A

```
submission:
  type: security_verification_request
  system: "AccountPortal v2.0"
  concerns:
    - "POST /api/account/email-change has no CSRF token"
    - "session cookie has no SameSite attribute"
    - "email change is a state-changing operation"
  sub_phase: "3.4"
```

### B

```
territories_identified:
  - id: T-cwe-authz
    label: "cwe-authz"
    source_signal: "no CSRF token, SameSite absent, state-changing operation, cross-site request forgery"
    domain: CWE-Authorization
    note: "CSRF is CWE-352 (Cross-Site Request Forgery) — this is CWE-Authz territory because CSRF bypasses the authorization intent of the session (an unauthorized third party causes the authenticated user to perform an action). It is not CWE-Authn territory (no authentication mechanism is being attacked)."
routing:
  - territory: T-cwe-authz → Node 2
```

### Reason

CWE-352 (CSRF) routes to T-cwe-authz, not T-cwe-authn. The distinction: authentication concerns cover weaknesses in credential verification and identity confirmation (CWE-287, CWE-307). Authorization concerns cover weaknesses that allow unauthorized actions to be performed — CSRF allows a third party to cause an authenticated user to perform an action they did not intend, which is an authorization bypass. The CWE-Authz-Arbiter handles CSRF findings.

### Phrasing B

```
AccountPortal: POST /api/account/email-change, no CSRF token, no SameSite.
Node 01 must determine: is this a cwe-authn territory or a cwe-authz territory?
Why, and which arbiter does it route toward?
```

Expected: T-cwe-authz. CSRF bypasses authorization (allows unauthorized action by authenticated user, triggered by third party). Not T-cwe-authn (no authentication mechanism attacked). Routes toward CWE-Authz-Arbiter.

```
territory_translation:
  assigned_label: "rfc-oauth2-normative"
  assigned_domain: RFC-OAuth2 (RFC 8628)
  rationale: "RFC 8628 is the Device Authorization Grant extension to OAuth 2.0. It is an OAuth 2.0 grant type, so it belongs to the rfc-oauth2-normative domain (same label as RFC 6749). Device flow vocabulary (device_code, user_code, poll interval) maps to RFC 8628 requirements."
  excluded_labels:
    - label: "rfc-jwt-normative"

The device flow vocabulary (device_code, user_code) is the distinguishing signal that confirms RFC 8628 (not RFC 6749 authorization code flow or RFC 7519 JWT).

### Phrasing B

Expected: rfc-oauth2-normative. RFC 8628 is an OAuth 2.0 extension = RFC-OAuth2 arbiter family. Not JWT (no JWT claims). Not oauth-oidc (that is ASVS V10, not RFC arbiter label).
