## E01 — AST токены vs BPE токены

### Что знаем сейчас (Tier 1 — 3 файла, ~2 000 BPE токенов)

```
BPE триграмм:    перплексия = 7 057 795  top1 = 21.2%
AST триграмм:    перплексия =     2 787  top1 = 50.8%
Улучшение:       +100% (99.96%)
AST насыщение:   0.147 (14.7% новых типов в validation vs training)
AST типов найдено: 70 из ~200 возможных в C#
```

**Почему baseline такой плохой:** BPE с vocab=512 на 3 файлах (~2 000 токенов) — почти каждый триграмм уникален. Большинство позиций в validation не встречались в training → перплексия взрывается до миллионов. Это не баг, это математика маленького датасета.

**Что означает signal=0.147:** 14.7% AST типов в validation были новыми по сравнению с training. Словарь ещё не насытился — ещё не видели всех ~200 типов C# узлов.

**Ключевой вопрос для следующего тира:** насытится ли AST словарь при большем датасете и будет ли preмущество сохраняться когда BPE тоже получит больше данных?

---

### Следующий шаг: Tier 2 — 6 подпроектов (~47 файлов, ~17 000 токенов)

**Включает:** `01.Tokenizer`, `02.DatasetPipeline`, `05.Embeddings`, `07.GraphEngine`, `09.Inference`, `10.LoRA`

**Запустить:**
```csharp
runner.Run("E01", tier: 2)
// или автоматически через:
runner.RunTierLadder("E01")  // старт с Tier 1, автоподъём
```

**Что конкретно изменится:**
- BPE на 17K токенах: перплексия упадёт с 7M до ~500-2000 (больше паттернов покрыто)
- AST словарь: с 70 типов вырастет до ~120-150 из 200 (практически насытится)
- signal `ast_saturation_ratio` должен упасть ниже 0.05 (≤5% новых типов)

**Критерий "прошёл" на Tier 2:**
- `improvement_pct` ≥ +5%
- `scaling_signal` (ast_saturation_ratio) < 0.10 — словарь стабилизировался

**Что смотреть в notes:**
```
bpeVocab=512, astTypes=XXX  ← ожидаем 120-150 (было 70)
bpeTop1=XX%, astTop1=XX%    ← ожидаем оба вырастут, AST всё ещё лучше
```

**Если не прошёл на Tier 2:** маловероятно, но если delta < 5% — проверить что vocab=512 не слишком мал (попробовать vocab=1024 в аргументе `bpeVocabSize`).

**Если прошёл на Tier 2:** запустить `runner.Run("E01", tier: 3)` для подтверждения на полном проекте.

## E02 — Ранжирование по частоте (T9-стиль) vs алфавитный порядок

### Что знаем сейчас (прогрессия по всем тирам)

```
Tier 1:  27 calls,    17 receivers,  confRatio=0.0%  →  delta=0%     SCALE_UP
Tier 2: 153 calls,    60 receivers,  confRatio=0.0%  →  delta=+14.1% PASSED
Tier 3: 2296 calls,  579 receivers,  confRatio=2.9%  →  delta=+22.6% PASSED
```

**Ключевые наблюдения:**
1. На Tier 2 (153 вызова) уже работает (+14.1%) несмотря на confRatio=0% — значит уже при 1-3 наблюдениях частота помогает
2. При масштабировании Tier 2 → Tier 3: calls ×15, но delta только +8.5% (от 14% до 22%)
3. На Tier 3 confRatio=2.9% — только 2.9% пар имеют ≥10 наблюдений. Большинство методов видны 1-3 раза

**Вопрос:** рост замедляется. Насколько далеко может уйти delta при ещё большем объёме?

---

### Следующий шаг: внешний C# проект (Tier 4)

Tier 3 = весь llm_mvp_core (~195 файлов). Следующее — внешний реальный проект.

**Рекомендуемый проект:** любой публичный C# репозиторий с реальным кодом.  
Подходящие варианты (все MIT или Apache):
- `dotnet/runtime` (очень большой, взять выборку 500 файлов)
- `dotnet/aspnetcore` (средний, весь)
- Любой корпоративный C# проект

**Как добавить в DatasetLoader:**

Добавить Tier 4 в `Infrastructure/DatasetLoader.cs`:
```csharp
// В ResolveFolders():
4 => new[] { externalProjectRoot }  // путь к внешнему проекту
// Где externalProjectRoot — параметр или константа
```

Или проще — запустить `InputAdapters.ForE02` вручную на новых файлах и передать в `_d.RunE02(sources, tier: 4)`.

**Что конкретно изменится:**
- Calls вырастут в ~10-50x (десятки тысяч вызовов методов)
- confRatio вырастет с 2.9% до ~20-40% (у популярных методов будут десятки наблюдений)
- Ожидаемый delta: +30-45%

**Критерий "прошёл" на Tier 4:**
- `improvement_pct` ≥ +5% (очень вероятно)
- `confRatio` > 10% — достаточно надёжная статистика
- `totalCalls` > 5000

**Что смотреть в notes:**
```
totalCalls=XXXXX         ← ожидаем >5000
confRatio=XX%            ← ожидаем >10%
```

**Если confRatio всё ещё < 5%:** внешний проект слишком маленький, нужен больший.

**Если delta перестаёт расти (plateau):** это нормально — нашли предел точности при данном алгоритме. Записать как финальный результат.

## E03 — Оптимальный N для N-граммной модели

### Что знаем сейчас (прогрессия по тирам)

```
Tier 1:     2 158 токенов, optimalN=1  →  delta=0%     SCALE_UP
Tier 2:    17 718 токенов, optimalN=1  →  delta=0%     SCALE_UP
Tier 3:   410 897 токенов, optimalN=2  →  delta=+30.1% PASSED
```

**Ключевые наблюдения:**
1. Потребовалось **410 000 BPE токенов** чтобы биграмм наконец превысил юниграмм
2. Почему так много: vocab=512 → биграмм таблица 512² = 262 144 возможных пар. Нужно ~5 наблюдений на пару = ~1.3M переходов. При 410K токенах — в районе достаточности
3. Триграмм ещё не помог (optimalN=2, не 3) — нужно в разы больше данных
4. Перплексия: 244 → 171 (юниграмм → биграмм). Ещё большой потенциал у триграмма

**Вопрос:** при каком объёме триграмм (N=3) начнёт работать?

---

### Следующий шаг: внешний большой C# проект (Tier 4)

**Минимальный размер для triграмма:**  
vocab=512 → триграмм таблица: 512³ = 134M пар. При ≥5 obs каждая → ~670M переходов.  
Это нереально для одного проекта. Вывод: **с vocab=512 триграмм на практике недостижим**.

**Два варианта:**

**Вариант А (рекомендуется первым): снизить vocab до 128**
```csharp
// В InputAdapters.ForE03 или в вызове:
tok.Train(d.CombinedText, vocabSize: 128);  // было 512
```
С vocab=128: биграмм = 128² = 16K пар. Триграмм = 128³ = 2M пар.  
На 410K токенах триграмм уже может стать оптимальным.

**Запустить после смены vocab:**
```csharp
runner.Run("E03", tier: 3)  // тот же Tier 3 данных, но vocab=128
```

Ожидаем: optimalN=3, delta ≥ +40%

**Вариант Б: увеличить датасет с vocab=512**  
Нужен внешний проект с ≥ 2M токенов.  
Менее приоритетно — вариант А проверяет гипотезу быстрее.

**Критерий "прошёл" (для варианта А):**
- `optimalN` = 3 (триграмм стал оптимальным)
- `improvement_pct` ≥ +5%

**Что смотреть в notes:**
```
optimalN=3         ← цель
tokenCount=410897  ← те же данные, vocab меньше
```

**Если optimalN=2 снова:** попробовать vocab=64 или добрать внешние данные.

## E05 — Грамматическая маска Roslyn

### Что знаем сейчас (два прогона на Tier 1)

```
Прогон 1 (старая тавтологическая маска):
  baseline=0.508, enhanced=0.508, delta=0%
  syntaxCorrectPct=73.3%, avgMask=3.0

Прогон 2 (исправленная маска из всех файлов):
  baseline=0.508, enhanced=0.660, delta=+29.9%
  syntaxCorrectPct=99.5%, avgMask=3.8, maskP10=1, maskP90=12
  astNodes=962
```

**Ключевые наблюдения:**
1. Исправление маски дало огромный скачок: 0% → 30% улучшения
2. `syntaxCorrectPct=99.5%` — почти все предсказания синтаксически корректны (был 73.3% до исправления)
3. `avgMask=3.8` — в среднем только 3.8 допустимых продолжения из словаря ~200 AST типов. Очень жёсткое ограничение
4. `maskP10=1` — 10% позиций имеют только 1 допустимый вариант (детерминированная грамматика!)

**Ключевой вопрос:** маска построена из 3 файлов (Tier 1). На Tier 2 маска будет покрывать больше C# паттернов — улучшит ли это результат или уже достигли предела?

---

### Следующий шаг: Tier 2 — 6 подпроектов (~47 файлов)

```csharp
runner.Run("E05", tier: 2)
```

**Что конкретно изменится:**

На Tier 1: грамматическая таблица построена из 3 файлов Tokenizer-а. Это даёт хорошее покрытие базовых C# конструкций (методы, условия, циклы), но может пропускать паттерны из других подпроектов (GraphEngine, Embeddings).

На Tier 2: таблица включает 47 файлов с более разнообразным кодом:
- `05.Embeddings` — матричные операции, LINQ, обобщённые типы
- `07.GraphEngine` — рекурсивные структуры, обход графов
- `09.Inference` — сложные паттерны генерации

**Ожидаем:**
- `avgMask` слегка вырастет (больше паттернов в таблице)
- `syntaxCorrectPct` останется ~99%+ (грамматика C# не меняется)
- `improvement_pct` останется в диапазоне +20-35%
- Или: delta вырастет до +35-45% потому что маска из 47 файлов точнее отражает C# грамматику

**Критерий "прошёл" на Tier 2:**
- `improvement_pct` ≥ +5% (почти гарантированно)
- `syntaxCorrectPct` ≥ 95%

**Что смотреть в notes:**
```
syntaxCorrectPct=99.X%    ← должен оставаться высоким
avgMask=X.X               ← ожидаем 3.8-5.0 (немного больше паттернов)
maskP10=X                 ← если растёт — маска стала мягче (меньше пользы)
```

**Важный сигнал:** если `maskP10` вырастает с 1 до 5+ — маска стала слишком широкой. Это значит что с большим датасетом грамматическая таблица стала слишком разрешающей и преимущество уменьшится. Если это произошло — рассмотреть ограничение таблицы только к строго грамматическим переходам (не эмпирическим).

## Что значат результаты для большой картины

Когда все 4 эксперимента пройдут следующий тир, это означает:

- **E01** подтверждён на реальном масштабе: AST токены стабильно лучше BPE не только на крошечном датасете
- **E02** показывает что T9-аналогия работает при достаточной статистике (~10+ наблюдений на метод)
- **E03** находит оптимальное N для C# кода — это прямой параметр для N-граммного этапа в pipeline
- **E05** подтверждает что грамматическая маска улучшает качество, что важно для автодополнения в агентах

Все четыре вместе закрывают Scale 1 и дают основание строить следующий уровень — зонд-нейросеть (2 слоя, 64 dim, 100 шагов) поверх тех же датасетов.
