# E05 — Фильтр синтаксически допустимых токенов
## Отдельный план эксперимента · LlmFromScratch.sln

**ID:** E05-SYNTAX-FILTER  
**Подпроект-источник:** 37.CodeCompletion (Уровень 4 — Roslyn маска допустимых)  
**Альтернативный подход учтён:** MICRO-EXPERIMENT-FRAMEWORK (синтаксическая корректность как 6-я метрика)

---

## Гипотеза

N-граммная модель может предложить любой токен из словаря — включая синтаксически невозможные в данном контексте (например, `public public` или `return if`). Roslyn может вычислить маску допустимых токенов за ~2 мс. Применение этой маски: (1) гарантирует корректность предложений, (2) уменьшает пространство выбора → повышает точность.

**Ключевое отличие от других экспериментов:** E05 — единственный у которого есть жёсткий бинарный критерий (синтаксически корректно / нет) помимо вероятностных метрик. Это делает его масштабирование уникальным: при росте сложности кода — фильтр блокирует больше невалидных предложений → улучшение растёт.

---

## Что меняется

| Параметр | Baseline | Enhanced |
|---|---|---|
| Что предсказывает | N-граммная модель из произвольного словаря | N-граммная модель, ограниченная синтаксически допустимыми |
| Roslyn | Не используется | `SemanticModel.GetMemberGroup()` или `CompletionService` |
| Пространство выбора | Весь словарь (~500 токенов) | Только допустимые в позиции (~5–50 токенов) |

Специальная 6-я метрика — синтаксическая корректность:
```
Для 100 предсказаний:
  Baseline: (предсказание вставляем в код → проверяем компиляцию)
            ожидаем ~70–75% корректных
  Enhanced: ожидаем ~98–100% корректных (фильтр убирает невалидные)

Метрика = % синтаксически корректных предложений
```

---

## Уникальная ось масштабирования: сложность синтаксических контекстов

**Центральный вопрос:** при каком уровне сложности кода фильтр блокирует наибольший процент невалидных предложений — и тем самым даёт наибольшее улучшение?

```
Метрика сложности = средний размер маски допустимых токенов

Простой код (Tokenizer): позиции с 50–100 допустимыми токенами
  → фильтр блокирует мало → небольшое улучшение
Сложный код (TransformerModel, SemanticNlp): позиции с 5–20 допустимыми
  → фильтр блокирует много → большое улучшение
```

Гипотеза: **улучшение от фильтра растёт при переходе к более сложным подпроектам** — не просто к большему объёму, а к синтаксически богатому коду.

## Лестница тиров

### Tier 1 — простой код (< 10 секунд, < 80 МБ RAM)

**Датасет:** `01.Tokenizer` — простые методы, мало дженериков и LINQ  
**Ожидание:** улучшение скромное (+5–10%) — маска содержит 60–100 токенов в простых позициях  
**Специфичный тест:** распределение размеров масок (гистограмма)  
**Кейс:** `void AddToken(` — после открывающей скобки допустимы параметры (много вариантов)

---

### Tier 2 — средней сложности (< 30 секунд, < 150 МБ RAM)

**Датасет:** 6 подпроектов включая `07.GraphEngine` (граф с более сложными типами)  
**Ожидание:** улучшение +10–20% — появляются позиции где маска очень маленькая  
**Специфичный тест:** найти топ-10 позиций где маска наименьшая → это самые "ценные" позиции для фильтра

---

### Tier 3 — сложный код (< 2 минуты, < 300 МБ RAM)

**Датасет:** все подпроекты включая `28.SemanticNlp`, `24.Compression`  
**Ожидание:** улучшение +20–35% — много генерических типов и сложных паттернов  
**Специфичный тест:** корреляция между сложностью позиции (размер маски) и улучшением предсказания

---

### Tier 4 — внешний сложный проект (< 10 минут)

**Датасет:** сложный C# проект (например, ASP.NET Core — много дженериков и LINQ)  
**Ожидание:** наибольшее улучшение — сложный код = маленькие маски = большой выигрыш от фильтра  
**Специфичный тест:** ранжировать типы позиций по "ценности фильтра"

---

### Tier 5 — смешанный корпус (одноразово)

**Датасет:** простой + сложный код вместе  
**Цель:** построить "кривую сложности" — при каком уровне сложности фильтр даёт ≥20% улучшения?  
**Применение результата:** знать для каких проектов фильтр наиболее ценен
