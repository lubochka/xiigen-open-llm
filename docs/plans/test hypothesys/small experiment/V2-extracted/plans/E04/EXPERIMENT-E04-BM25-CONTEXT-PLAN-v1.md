# E04 — BM25 поиск по локальному контексту vs только текущий файл
## Отдельный план эксперимента · LlmFromScratch.sln

**ID:** E04-BM25-CONTEXT  
**Подпроект-источник:** 36.CodeCompletion (Уровень 3 — BM25 поиск) + 12.SearchEngine (уже реализован!)  
**Альтернативный подход учтён:** MICRO-EXPERIMENT-FRAMEWORK (BM25 cross-file recall), RESEARCH-03-T9 (поиск = T9 с контекстом)

---

## Гипотеза

При автодополнении кода модель часто вызывает методы определённые в другом файле. Только по текущему файлу предсказать их невозможно. BM25 поиск по всем файлам проекта находит релевантный контекст → улучшает Recall@3 (правильный метод в первых 3 предложениях).

**Ключевое:** BM25 не работает с 2–3 файлами. Он начинает работать хорошо только когда в корпусе достаточно файлов для нахождения семантически похожих примеров. Это делает E04 уникальным — **он единственный эксперимент у которого есть минимальный порог корпуса** ниже которого он не даёт улучшения.

**Из RESEARCH-03:** BM25 — это T9 с контекстом. Вместо одного символа (T9) используем несколько ключевых слов контекста для поиска. Тот же принцип — частотная таблица, только многомерная.

---

## Что меняется

| Параметр | Baseline | Enhanced |
|---|---|---|
| Источник предсказаний | Только текущий файл (N-граммы) | Текущий файл + BM25 поиск по всему проекту |
| Реализация BM25 | — | `12.SearchEngine.InvertedIndex` + `BM25Scorer` (уже есть!) |
| Стратегия | Предложить метод из текущего контекста | Найти 3 похожих файла → взять из них топ-методы |

Измерение (из MICRO-EXPERIMENT-FRAMEWORK):
```
1. Найти 30 мест где метод определён в ДРУГОМ файле (cross-file calls)
   Например: jwtService.Validate() — JwtService определён в другом .cs
2. Baseline: предсказать только из текущего файла → часто промах
3. Enhanced: BM25 по ключевому слову "jwtService" → находит файл с определением
             → первые 3 метода из найденного файла в предложения
4. Recall@3: правильный ли метод попал в топ-3?
```

---

## Уникальная ось масштабирования: минимальный порог корпуса

**Центральный вопрос:** сколько файлов нужно чтобы BM25 начал давать улучшение?

```
Метрика связности = (cross-file calls с находимым определением) / (все cross-file calls)

При 3 файлах: BM25 ищет среди 3 файлов → Recall@3 почти не улучшается
При 20 файлах: начинает находить нужные файлы
При 100+ файлах: работает надёжно
```

**Кривая BM25-порога:** мы хотим построить зависимость "Recall@3 улучшение" vs "количество файлов в корпусе". Найти точку перегиба где BM25 начинает существенно помогать.

## Лестница тиров

### Tier 1 — micro (< 5 секунд, < 60 МБ RAM)

**Датасет:** `01.Tokenizer` — 3 файла  
**Ожидание:** BM25 почти не помогает (3 файла — слишком мало)  
**Цель тира:** убедиться что механизм запускается, даже если результат ~0%  
**Специфичный тест:** сколько cross-file calls есть в этих 3 файлах? (если 0 — тир 1 пропускаем)

---

### Tier 2 — small (< 30 секунд, < 150 МБ RAM)

**Датасет:** 6 малых подпроектов — ~47 файлов  
**Ожидание:** BM25 начинает работать, Recall@3 улучшение +10–20%  
**Специфичный тест:** построить "кривую порога" — добавлять файлы по одному и смотреть как растёт Recall@3

---

### Tier 3 — medium (< 2 минуты, < 300 МБ RAM)

**Датасет:** все 24 подпроекта — ~195 файлов  
**Ожидание:** BM25 работает хорошо, Recall@3 улучшение +25–45%  
**Специфичный тест:** найти минимальный N файлов где улучшение стабилизируется (насыщение BM25)

---

### Tier 4 — external (< 10 минут)

**Датасет:** наш проект + внешний проект (смешанный корпус)  
**Ожидание:** BM25 работает между проектами если используют общие библиотеки  
**Специфичный тест:** cross-project Recall@3 — работает ли BM25 когда определение метода из другого проекта?

---

### Tier 5 — large corpus (одноразово)

**Датасет:** несколько крупных C# проектов  
**Цель:** показать что BM25 масштабируется — корпус в 10 000 файлов даёт надёжный поиск  
**Ожидание:** Recall@3 > 60% для cross-file методов
