# E09 — Структурный вектор + K-NN вместо N-граммной таблицы
## Experiment Plan v1.0 · LlmFromScratch.sln

**Вопрос:** если построить правильный структурный вектор токена
(включая путь в дереве компилятора) и искать соседей по вектору,
а не точному совпадению — будет ли предсказание лучше чем N-грамм?

**Этот документ не касается XIIGen.**

---

## Почему E07 не сработал и что делаем иначе

E07 провалился на двух тирах (-4.5% и -12.8%). Причина: использовали
многомерную N-граммную таблицу с ключом `(bpe, ast_type, depth)`.
При 58% уникальных контекстов таблица деградировала в bigram.

**Две ошибки E07:**

1. **Неправильный поиск.** N-грамм требует точного совпадения ключа.
   Контекст `(4821, MethodDecl, 3)` и `(4821, MethodDecl, 4)` —
   это близкие ситуации, но таблица считает их несвязанными.

2. **Неполный вектор.** `depth=3` не различает: ты на глубине 3
   внутри `IfStatement` или внутри `ForStatement` — это разные места.

**Что делаем в E09:**

1. Вектор включает путь в дереве, а не просто глубину.
2. Поиск через K-NN по косинусному расстоянию — находим похожие
   контексты даже если они не совпадают точно.

---

## Структура правильного вектора токена

Каждый токен описывается вектором из нескольких групп признаков:

```csharp
// StructuralVector — описание токена через его место в мире кода.
// Используется для K-NN поиска похожих контекстов.
public readonly record struct StructuralVector
{
    // Группа 1: сам токен (что это)
    public int BpeId { get; init; }           // какой подслов
    public short AstNodeType { get; init; }   // тип AST узла (MethodDecl и т.д.)

    // Группа 2: путь в дереве (где это)
    // Путь кодируется как последовательность типов предков:
    // CompilationUnit → ClassDecl → MethodDecl → Block → IfStatement
    // Сжимаем в хеш: не нужны все предки, достаточно ближайших 3
    public short Parent1Type { get; init; }   // непосредственный родитель
    public short Parent2Type { get; init; }   // дед
    public short Parent3Type { get; init; }   // прадед

    // Группа 3: положение внутри своего родителя (семантическая роль)
    public byte PositionInParent { get; init; }  // первый/второй/третий ребёнок
    public byte SiblingCount { get; init; }       // сколько братьев-сестёр
    public byte DepthInMethod { get; init; }      // глубина внутри ближайшего метода

    // Группа 4: контекстные сигналы
    public byte ScopeDepth { get; init; }         // уровень { } вложенности
    public bool IsFirstInStatement { get; init; } // начало утверждения?
    public bool IsLastInStatement { get; init; }  // конец утверждения?
}
```

**Почему путь важнее глубины:**
- `depth=3` в `IfStatement` → скорее всего условие или тело условия
- `depth=3` в `ForStatement` → скорее всего инициализация цикла
- Это разные ситуации с разными вероятными продолжениями
- `Parent1Type=IfStatement` vs `Parent1Type=ForStatement` различает их

## Как работает K-NN предсказание

Вместо: "найди точную запись `(4821, MethodDecl, 3)` в таблице"

Делаем: "найди K самых похожих токенов из обучающих данных,
посмотри что шло после каждого из них, верни самое частое"

```csharp
// StructuralKnnPredictor.cs
public sealed class StructuralKnnPredictor
{
    // Обучение: запомнить все (вектор → следующий токен) пары
    public void Train(IReadOnlyList<(StructuralVector context, int nextToken)> pairs);

    // Предсказание: найти K ближайших соседей, вернуть argmax следующего токена
    // k=5 по умолчанию — баланс точности и скорости
    public int Predict(StructuralVector context, int k = 5);

    // Расстояние между векторами (косинусное после нормализации)
    // Или взвешенное евклидово: путь весит больше чем глубина
    private double Distance(StructuralVector a, StructuralVector b);
}
```

**Метрика расстояния:**
Не все поля одинаково важны. Предлагаемые веса:
```
Parent1Type:    вес 3.0  (самое важное — непосредственный родитель)
Parent2Type:    вес 2.0
AstNodeType:    вес 2.0
Parent3Type:    вес 1.5
BpeId:          вес 1.0
PositionInParent: вес 1.0
остальные:      вес 0.5
```

Итого расстояние = взвешенная сумма совпадений/различий по каждому полю.

## Scaling signal: покрытие K-NN

```
KNN coverage = % позиций где K ≥ 3 соседей найдено с расстоянием < порог

Tier 1 (2K токенов):  ожидаем ~30% покрытие — мало обучающих данных
Tier 2 (20K токенов): ожидаем ~65% покрытие
Tier 3 (200K токенов): ожидаем ~90% покрытие
```

Критерий `ShouldScaleUp = coverage < 0.5` — если меньше половины
позиций находят достаточно соседей, данных мало.

## Сравнение трёх подходов на одних данных

E09 запускает три варианта одновременно:

| Подход | Что делает | Ожидаемый результат |
|---|---|---|
| Baseline | Bigram BPE (как всегда) | ~40% |
| E07-style | Многомерная N-грамм таблица (старый провальный подход) | ~35% (хуже baseline) |
| E09 K-NN | K ближайших соседей по структурному вектору | > 50%? |

Если E09 K-NN лучше E07-style — вектор правильный, проблема была в методе поиска.
Если E09 K-NN ≈ E07-style — проблема в самом векторе, нужно другое расстояние.

## Реализация по шагам

```
1. Написать StructuralVector record (поля выше)
2. Написать RoslynVectorExtractor.cs — заполнить вектор по AST узлу
   (Parent1/2/3 берём обходом Parent в Roslyn, PositionInParent = индекс ребёнка)
3. Написать StructuralKnnPredictor.cs с брутфорс поиском
   (для Scale 0 с ~1500 токенами брутфорс нормально, O(n) поиск)
4. Для Scale 2+ использовать KD-дерево или ball-tree для ускорения
   (готовая реализация в 07.GraphEngine или написать с нуля)
5. Написать E09StructuralKnn.cs по образцу других экспериментов
6. runner.Run("E09", scale: 0)
```

**Критерий "прошёл":** E09 K-NN > baseline bigram на ≥ 5%.

## Связь с E07 и нейросетью

Если E09 проходит на Markov-уровне, то:
- Правильный вектор + K-NN это промежуточный шаг между N-граммом и нейросетью
- Нейросеть по сути и делает K-NN через пространство эмбеддингов
- E09 валидирует что структурный вектор несёт полезный сигнал
- Этот же вектор можно подать на вход нейросети как дополнительные признаки
