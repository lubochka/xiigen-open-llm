# Ускорение обучения языковой модели через семантические объекты
## Исследовательский план: Lego-сборка из существующих подпроектов

**Проект:** llm-mvp-core — исследовательский подпроект Research-01
**Язык:** C# / .NET 9
**Датасет:** WikiText-103 (открытый, MIT, 103M токенов, аннотированный английский текст)
**Этот документ не касается XIIGen.**

---

## Главная гипотеза

Стандартное обучение языковой модели работает с **плоскими последовательностями байтовых токенов**. Каждый токен — число без смысла. Модель сама должна выучить что «атаковал», «ударил», «напал» означают похожее.

Мы проверяем: что если токены уже несут смысловую структуру? Если вместо «атаковал» модель видит объект `{семья: Нападение, роль: Действие, связи: [деятель, жертва]}` — выучит ли она семантические связи быстрее? А если матрицы весов хранятся в разреженном/малоранговом виде с первого шага — будет ли обучение требовать меньше памяти?

## Шесть экспериментов

### Эксперимент 0 — Контрольная группа (Baseline)

**Что делаем:** Стандартный пайплайн без изменений.
- Токенизация: BPE, словарь 50000 токенов
- Хранение: плоские .npy файлы с uint16 токенами
- Матрицы: плотные (dense) float32
- Обучение: AdamW, косинусное расписание скорости обучения
- Архитектура: GPT-2 small (12 слоёв, 117M параметров)
- Датасет: WikiText-103 train split (103M токенов)

**Ожидаемые показатели (из публикаций):**
- Время одного шага обучения: ~120 мс на CPU
- Память во время обучения: ~4 ГБ RAM
- Хранение датасета: ~200 МБ (.npy, uint16)
- Хранение весов модели: ~460 МБ (float32)
- Перплексия (Perplexity — мера качества: чем меньше, тем лучше) после 10000 шагов: ~35
- Перплексия после 100000 шагов: ~22

### Эксперимент 1 — Семантические объекты вместо BPE токенов

**Гипотеза:** Если каждый токен уже помечен семантической семьёй, модель выучит структуру смысла быстрее и с меньшим количеством шагов.

**Пайплайн:**

```
Шаг 1: WikiText-103 → BPE токенизация (подпроект 01)
         Выход: последовательности чисел [3421, 892, 11043, ...]

Шаг 2: Каждый токен → SemanticAnnotator (подпроекты 28-32)
         Для каждого слова:
           - FrameNet: к какому фрейму принадлежит (если есть)
           - SRL: роль в ближайшем событии (A0/A1/V/AM-LOC/...)
           - WordNet: ID группы синонимов
           - Universal Dependencies: синтаксическая функция
         Выход: SemanticToken {
           bpe_id: 3421,
           frame_id: 142,        // "Attack" = 142
           srl_role: 0,          // A0 = деятель
           synset_id: 8821,      // "attack.v.01"
           dep_rel: 2,           // nsubj
         }

Шаг 3: SemanticToken → составной вектор
         Вместо одного числа (3421) — вектор из 5 чисел [3421, 142, 0, 8821, 2]
         Каждое поле получает своё embedding (таблицу представлений)
         Итоговый embedding = sum или concat этих пяти векторов

Шаг 4: Обучение той же GPT-2 small архитектуры
         Но input embeddings теперь включают семантику
```

**Ожидаемые показатели:**

| Метрика | Контроль (E0) | Ожидание (E1) | Источник ожидания |
|---|---|---|---|
| Время аннотации датасета | — | 45–90 минут | SRL ~15 мс/предложение × 1M предложений |
| Размер аннотированного датасета | 200 МБ | 800 МБ–1.2 ГБ | 5 полей вместо 1 |
| Время одного шага | 120 мс | 130–140 мс | embedding lookup немного сложнее |
| Память обучения | 4 ГБ | 4.3–4.8 ГБ | дополнительные embedding таблицы |
| Перплексия на 10000 шагов | ~35 | **~28–31** | аналоги: BERT-style token enrichment |
| Перплексия на 100000 шагов | ~22 | **~17–20** | semantic tokens = лучшее начальное приближение |

**Неопределённость:** насколько хорошо FrameNet покрывает WikiText-103. Ожидаем ~60-70% токенов с семантической аннотацией. Остальные — обычный BPE.

### Эксперимент 2 — Разреженные матрицы внимания

**Гипотеза:** В механизме внимания большинство весов близки к нулю. Если хранить матрицы внимания в разреженном формате (CSR) с порогом обнуления, памяти потребуется меньше без существенной потери качества.

**Пайплайн:**

```
Стандартная матрица внимания (Attention Matrix):
  Размер: [batch=4, heads=12, seq=2048, seq=2048]
  float32: 4 × 12 × 2048 × 2048 × 4 байта = 805 МБ на шаг

CSR-разреженная матрица внимания:
  Шаг 1: Стандартный softmax → веса внимания
  Шаг 2: Обнулить все веса < порога (threshold = 0.01)
  Шаг 3: Конвертировать в CSR формат (подпроект 29 матрицы)
  Результат: типично 5-15% ненулевых элементов
```

**Как это работает вместе с обратным распространением градиента:**

```
Прямой проход (Forward):
  scores = Q × K^T / sqrt(d)     → плотная матрица
  weights = softmax(scores)       → плотная матрица
  sparse_weights = threshold(weights, 0.01) → CSR матрица
  output = sparse_weights × V    → плотный результат

Обратный проход (Backward):
  gradient через CSR умножение (подпроект 29 матрицы)
  обнулённые позиции не получают градиента
  → неявная регуляризация (похожа на Dropout)
```

**Ожидаемые показатели:**

| Метрика | Контроль (E0) | Ожидание (E2) | Источник |
|---|---|---|---|
| Память матриц внимания | 805 МБ/шаг | **80–200 МБ** | типично 5-15% ненулевых |
| Время умножения внимания | 100% | 60–80% | CSR × dense быстрее при <20% ненулевых |
| Потеря качества (перплексия) | ~22 | ~22–24 | <5% потери при пороге 0.01 |
| Суммарная память | 4 ГБ | **2.8–3.2 ГБ** | экономия на матрицах внимания |

### Эксперимент 3 — Малоранговые веса с первого шага

**Гипотеза:** Матрицы проекций в трансформере (Q, K, V, output, FFN) имеют быстро убывающие сингулярные числа даже в начале обучения. Если инициализировать их в малоранговом виде (A×B вместо W) — памяти нужно меньше, и обучение может проходить по более «гладкому» пространству параметров.

**Отличие от LoRA (подпроект 10):** LoRA добавляет малоранговый адаптер поверх готовой модели. Мы с самого начала храним все веса в малоранговом виде — нет «базовой» и «адаптерной» части.

**Пайплайн:**

```
Стандартная проекция Q:
  W_Q: [4096 × 4096] = 67M чисел = 268 МБ

Малоранговая проекция Q (ранг K=128):
  A_Q: [4096 × 128]   = 524K чисел
  B_Q: [128 × 4096]   = 524K чисел
  Итого: 1.05M чисел = 4.2 МБ (в 64 раза меньше)

Прямой проход:
  q = x × A_Q × B_Q  (два маленьких умножения вместо одного большого)

Инициализация:
  A_Q: случайная нормальная (стандарт Kaiming)
  B_Q: нули (чтобы в начале A_Q × B_Q = 0)

Градиенты:
  dL/dA = (dL/d(AB)) × B^T
  dL/dB = A^T × (dL/d(AB))
  (те же формулы что в подпроекте 10 LoRA)
```

**Ожидаемые показатели:**

| Метрика | Контроль (E0) | K=64 (E3a) | K=128 (E3b) | K=256 (E3c) |
|---|---|---|---|---|
| Параметров модели | 117M | 29M | 47M | 70M |
| Память весов | 460 МБ | 115 МБ | 188 МБ | 280 МБ |
| Время шага | 120 мс | 85 мс | 95 мс | 108 мс |
| Перплексия 100K шагов | ~22 | ~27 | ~24 | ~23 |
| Точка пересечения качества | — | никогда | ~200K шагов | ~120K шагов |

### Эксперимент 4 — Сжатый граф токенов в RAG

**Гипотеза:** Хранить обучающие данные не как плоский список токенов, а как граф с семантическими связями. При загрузке батча — получать не просто токены, а токены + их окружение в графе. Граф сжимается алгоритмами из подпроекта 24-27.

**Пайплайн:**

```
Стандартное хранение (baseline):
  shard_0000.npy: [T1, T2, T3, T4, T5, ...] = плоский массив uint16

Граф-хранение (E4):
  Узлы = SemanticToken (из E1): {bpe_id, frame_id, synset_id}
  Рёбра = связи между токенами:
    - "рядом в тексте" (до 5 позиций) → вес пропорционален частоте совместного появления
    - "один синсет WordNet" → вес 0.9
    - "один фрейм FrameNet" → вес 0.8
    - "синтаксическая зависимость UD" → вес по типу связи
  Хранение: GraphRAG (подпроект 08) + LZ4 сжатие (подпроект 24)

Загрузка батча:
  1. Случайная стартовая позиция
  2. Обычная последовательность длиной 2048
  3. Для каждого токена — его K ближайших соседей в графе (K=8)
  4. Соседи добавляются к context через cross-attention или positional bias

Размеры:
  WikiText-103: ~1M уникальных предложений, ~15M уникальных token-пар
  Граф без сжатия: ~15M рёбер × 16 байт = ~240 МБ
  После LZ4: ~80-120 МБ (текстовые данные сжимаются хорошо)
```

**Ожидаемые показатели:**

| Метрика | Контроль (E0) | Ожидание (E4) |
|---|---|---|
| Хранение датасета | 200 МБ | 280–350 МБ (граф + LZ4) |
| Время построения графа | — | 2–4 часа (один раз) |
| Время загрузки батча | 1–3 мс | 5–15 мс (обход графа) |
| Качество после 10K шагов | ~35 | **~26–30** |
| Качество после 100K шагов | ~22 | **~16–19** |
| Память обучения | 4 ГБ | 4.5–5 ГБ |

### Эксперимент 5 — Полный стек (все улучшения вместе)

**Гипотеза:** Комбинация всех улучшений даёт синергетический эффект: семантические токены + разреженные матрицы внимания + малоранговые веса + граф-хранение.

**Архитектура:**

```
                    ┌─────────────────────────────────────────┐
                    │   ОБУЧАЮЩИЙ ПАЙПЛАЙН (Experiment 5)     │
                    └─────────────────────────────────────────┘

 WikiText-103        BPE (01)        Semantic (28-32)    GraphRAG (08)
 Сырой текст    →   Токены      →   SemanticToken    →  Граф + LZ4(24)
                                                              │
                    ┌─────────────────────────────────────────┘
                    │   Загрузка батча + соседи из графа
                    ↓
              Semantic Embedding
              (bpe + frame + role + synset + dep)
                    │
                    ↓
              Transformer с малоранговыми весами (30)
              12 слоёв, каждая проекция = A×B, K=128
                    │
                    ↓
              Механизм внимания с порогом (29)
              CSR формат, порог 0.01
                    │
                    ↓
              AdamW на малоранговых градиентах
                    │
                    ↓
              Веса сохраняются как A,B пары
              + LZ4 сжатие чекпоинтов
```

| Время одного шага | 120 мс | **90–105 мс** | −12–25% |
| Хранение весов | 460 МБ | **195–230 МБ** | −50% |
| Хранение датасета | 200 МБ | 350 МБ | +75% (граф) |
| Перплексия 10K шагов | ~35 | **~24–27** | −23–31% |

## Риски и вопросы без ответа

### Риск 1: Покрытие FrameNet / SRL может оказаться низким

Если только 40% токенов получат семантическую аннотацию — улучшение будет меньше ожидаемого. Митигация: добавить fallback — для незнакомых слов использовать ближайший синсет WordNet по векторному поиску (подпроект 06).

### Риск 2: Граф соседей увеличивает вычислительную стоимость

Cross-attention к соседям из графа = дополнительные умножения матриц. Нужно профилировать и подбирать K (количество соседей, пробуем K=4, K=8, K=16).

### Риск 3: Малоранговые веса могут не сойтись без прогрева

При K=64 модель может застрять в плохом минимуме на начальных шагах. Митигация: тёплый старт — первые 1000 шагов с K=256, затем плавное уменьшение до K=64.

### Открытый вопрос: Оптимальное объединение пяти семантических векторов

Суммирование (sum) vs конкатенация (concat) vs обученная весовая комбинация. Все три варианта нужно протестировать в рамках E1.
