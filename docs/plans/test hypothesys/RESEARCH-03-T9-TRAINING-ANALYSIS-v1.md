# Research-03 — T9 для машинного обучения
## Как алгоритмы автодополнения кода (33–38) ускоряют обучение языковых моделей

**Проект:** llm-mvp-core — Research-03: концептуальный анализ
**Цель:** Понять как каждый из шести уровней автодополнения помогает на этапах обучения — токенизация, хранение, перевод датасетов
**Этот документ не касается XIIGen.**

---

## Главный сдвиг: от инференса к обучению

Подпроекты 33–38 написаны как алгоритмы **реального времени** — отвечают на вопрос «что предложить прямо сейчас пока разработчик печатает». Но точно те же алгоритмы решают другую задачу: **как подготовить обучающие данные** чтобы модель нашла паттерны быстрее.

Твоя аналогия с T9 точная и глубокая. Разберём её.

```
T9 на телефоне:
  Нажатие клавиш 4-3-5-5-6 → предложения: ["hello", "hello", "hello"]
  T9 не понимает язык. Он хранит таблицу:
    "4355" → {hello: 847, gfllo: 0, ...}
  И предлагает то что встречалось чаще.

Языковая модель (GPT):
  Токены [1234, 567, 890] → предсказание следующего токена
  Модель не понимает код. Она хранит матрицы весов:
    W_attention, W_ff, W_embed → вероятность каждого следующего токена
  И предсказывает то что было рядом во время обучения.

Связь:
  T9 = ручная таблица частот (N-граммная модель, уровень 35)
  GPT = обученная нейросеть (уровень 37)
  Оба делают одно: P(следующий_токен | контекст)
  Разница только в том как они хранят эти вероятности
```

Вопрос Research-03: **что если мы «подсказываем» модели статистику T9 уровней 33–38 ещё до начала обучения?** Тогда она ищет сложные паттерны, а не тратит половину обучения на изучение очевидного.

## Уровень 1 (Подпроект 33) → Токенизация: AST вместо BPE

### Проблема которую решает

Стандартный BPE токенизатор видит:
```
"if (user == null) return;"
→ [310, 357, 1102, 574, 6109, 29, 1234, 59]
```
Восемь числа без структуры. Модель сама должна понять что `if`, `(`, `)`, `{` — это скобочная структура, что `user == null` — это проверка на ноль, что `return` — это выход из метода.

AST токенизатор (подпроект 33) видит:
```
IfStatement
  └── BinaryExpression (==)
        ├── IdentifierName (user)
        └── NullLiteral
  └── ReturnStatement
```
Структура известна заранее. Не надо учить — она встроена в представление.

### Как применять при обучении

**Шаг 1 — Перевод датасета:** один раз, перед любым обучением:
```
Входной файл .cs → Roslyn разбор → сериализованное AST дерево → сжатый бинарный файл

Стандартный датасет:  100 ГБ текста → 100 ГБ BPE токенов (uint16)
AST датасет:          100 ГБ текста → 12–18 ГБ AST узлов (LZ4, подпроект 24)
Экономия хранения:    ~6–8×
```

**Шаг 2 — Словарь обучения:** вместо 50 000 BPE токенов:
```
200 типов AST узлов (MethodDeclaration, IfStatement, BinaryExpression...)
+ 10 000 имён идентификаторов (методы, переменные из проекта)
= 10 200 токенов всего
```
Меньше словарь → меньше embedding матрица → быстрее обучение. Embedding таблица: 50K × 768 = 38M параметров против 10K × 768 = 7.7M параметров. Экономия 5× только на embedding.

**Шаг 3 — Маски внимания встроены в данные:**
```
Стандартное обучение: модель САМА учится куда смотреть (causal mask — треугольная маска)
AST обучение:         маска задана рёбрами дерева
  - MethodDeclaration смотрит на своих потомков
  - ReturnStatement смотрит на родителя (метод) и братьев (предыдущие операторы)
  - Не нужно учить структуру — она уже в данных
```

### Ожидаемый эффект на обучение

```
Шагов до перплексии 15 (код):
  BPE датасет:   ~150 000 шагов
  AST датасет:   ~30 000–50 000 шагов (в 3–5× быстрее)

Причина:
  Модель не тратит первые 50 000 шагов на изучение
  что { и } — это скобки одного блока.
  Это уже закодировано в структуре токенов.
```

## Уровень 2А (Подпроект 34) → Взвешивание потерь по частоте

### Проблема которую решает

В стандартном обучении каждый токен вносит одинаковый вклад в функцию потерь:
```
Loss = (1/N) × Σ CrossEntropy(предсказание_i, правильный_токен_i)
```

Но токен `{` встречается 10 миллионов раз в датасете. Токен `ArgumentNullException` — 3000 раз. Модель быстро учит `{` и игнорирует `ArgumentNullException` — он слишком редкий чтобы двигать градиенты.

### Как применять при обучении

**Взвешенная функция потерь (Frequency-Weighted Loss):**
```
Вес токена = 1 / sqrt(frequency_rank)

Токен "{"             → частота 0.85 → вес 1.09
Токен "return"        → частота 0.34 → вес 1.71
Токен "await"         → частота 0.12 → вес 2.89
Токен "ArgumentNullException" → частота 0.001 → вес 31.6

Loss = (1/N) × Σ weight_i × CrossEntropy(предсказание_i, токен_i)
```
Редкие токены получают бо́льший вес → модель их не игнорирует.

**Curriculum learning (обучение по расписанию):**
```
Эпоха 1–5:    только высокочастотные паттерны
              (if/else, return, method calls — 80% датасета)
Эпоха 6–15:   добавляем среднечастотные
              (try/catch, async/await, LINQ — ещё 15%)
Эпоха 16+:    весь датасет включая редкие паттерны
              (reflection, unsafe, generics с ограничениями)
```

Аналогия T9: T9 сначала учит «привет», «пока», «ок» — частые слова. Только потом добавляет «экзистенциализм». Если бы T9 учил всё равномерно — частые слова стали бы хуже.

### Хранение датасета по частотным корзинам

```
data/
  tier1_high_frequency/   — 40 ГБ (80% примеров, самые частые паттерны)
  tier2_medium/           — 12 ГБ (15% примеров)
  tier3_rare/             — 3 ГБ  (5% примеров, редкие конструкции)

DataLoader читает из корзин в заданной пропорции:
  Эпоха 1:  100% из tier1
  Эпоха 10: 60% tier1 + 30% tier2 + 10% tier3
  Эпоха 20: 50% tier1 + 30% tier2 + 20% tier3
```

## Уровень 2Б (Подпроект 35) → N-граммная инициализация весов внимания

### Проблема которую решает

В начале обучения веса внимания случайные. Первые 10 000 шагов модель тратит на то чтобы выучить простые статистические паттерны: после `return` часто стоит `null` или `new`. После `if (` часто стоит `string.IsNullOrEmpty`.

N-граммная модель (подпроект 35) уже знает эти паттерны точно — из статистики. Почему бы не начать с этих знаний?

### Как применять при обучении

**Инициализация embedding через N-граммную статистику:**
```
Стандартная инициализация:
  Embedding("return") = случайный вектор [0.12, -0.45, 0.78, ...]

N-граммная инициализация:
  Вектор "return" = взвешенная сумма векторов слов которые следуют за "return":
  Embedding("return") ≈ 0.35 × Embedding("null") +
                         0.28 × Embedding("new") +
                         0.15 × Embedding("true") +
                         0.12 × Embedding("false") +
                         ...

Это значит: слова которые часто следуют за "return" будут изначально
ближе к "return" в векторном пространстве.
Первые 10 000 шагов обучения уже "пропущены".
```

**Инициализация attention bias через N-граммы:**
```
attention_bias[i][j] = log(P(токен_j следует за токен_i))

Вместо нулей в начале:
  bias["return"]["null"]    = log(0.28) = -1.27
  bias["return"]["new"]     = log(0.23) = -1.47
  bias["if"]["string"]      = log(0.15) = -1.90
  bias["{"]["MethodDecl"]   = log(0.45) = -0.80

Эти числа — стартовая точка. Обучение их корректирует.
Но начальная точка уже осмысленная, а не случайная.
```

### Перевод датасета через N-граммное сжатие

N-граммная модель также помогает сжимать датасет:
```
Стандартное хранение: каждый токен как uint16 = 2 байта
  "public bool Validate" → [1842, 291, 9341] → 6 байт

N-граммное предиктивное кодирование:
  Если P(следующий токен | контекст) > 0.8 → хранить флаг "предсказуемо"
  Хранить только непредсказуемые токены полностью

  "public bool" → почти всегда следует имя метода → флаг + короткий ID
  Экономия хранения: 15–25% для типичного C# кода
```

## Уровень 3 (Подпроект 36) → BM25 как механизм дополнения датасета

### Проблема которую решает

Стандартный обучающий пример:
```
Контекст:  "var token = jwtService."
Цель:      предсказать "Validate"
```

Модель видит только локальный контекст в 2048 токенов. Но `jwtService.Validate()` определён в другом файле. Модель никогда не видит связь между «использованием» и «определением».

### Как применять при обучении

**Дополнение примера через BM25-поиск:**
```
Обычный пример обучения:
  [2048 токенов текущего файла] → предсказать следующий

BM25-дополненный пример:
  [1024 токенов текущего файла]
  + [512 токенов из BM25-релевантного файла где jwtService определён]
  + [512 токенов из BM25-релевантного файла где jwtService тестируется]
  → предсказать следующий

Модель видит определение и использование в одном контексте.
Связь между ними выучивается явно, а не угадывается.
```

**Построение датасета «в стиле BM25»:**
```
Для каждого обучающего примера (файл + позиция):
  1. BM25 поиск: найти топ-3 файла с наибольшим overlap токенов
  2. Извлечь релевантный фрагмент (метод или класс)
  3. Добавить как дополнительный контекст к примеру
  4. Сохранить тройку: (основной_файл, позиция, [(доп_файл, фрагмент), ...])

Хранение:
  Не плоский список токенов
  А граф: файл → список связанных фрагментов (как GraphRAG, подпроект 08)
  LZ4 сжатие (подпроект 24): дублирующиеся фрагменты сжимаются хорошо
```

**Аналогия T9:** T9 видит только текущее слово. Если бы T9 видел предыдущее предложение — он бы лучше понял контекст. BM25-дополнение даёт модели это «предыдущее предложение» из другого файла.

## Уровень 4 (Подпроект 37) → Трансформер-фильтр как hard constraint на выходе

### Проблема которую решает

Стандартная языковая модель иногда предлагает синтаксически неверный код:
```
Модель предсказывает: "public public" (два модификатора)
                       "return if"    (return без значения, потом if)
                       "void void"    (два типа)
```
Это потому что модель не знает грамматику — только статистику.

### Как применять при обучении

**Constrained decoding (декодирование с ограничениями) во время обучения:**
```
Стандартная функция потерь:
  Loss = CrossEntropy(предсказание, правильный_токен)
  Модель получает градиент для ВСЕХ 50K токенов

Constrained функция потерь (через фильтр из подпроекта 37):
  Допустимые_токены = RoslynFilter(контекст)  // 10–200 из 50K
  Loss = CrossEntropy(предсказание[допустимые], правильный_токен)
  Модель получает градиент только для допустимых токенов

  Недопустимые токены получают бесконечный штраф:
    если токен недопустим: penalty = +10.0 к loss
```

**Фильтрация датасета до обучения:**
```
Каждый обучающий пример проверяется:
  Правильный токен должен быть синтаксически допустим в данной позиции
  Если нет → пример удаляется из датасета

Это убирает "шумные" примеры: незавершённый код, код с ошибками
Чистый датасет = модель не учится на мусоре
```

**Как это меняет хранение датасета:**
```
Стандартный датасет: плоский список всех примеров
Filtered датасет:
  Каждый пример имеет дополнительное поле:
    allowed_token_mask: битовый массив 50K бит = 6.25 КБ на пример
    (показывает какие токены допустимы в данной позиции)

  При обучении: mask применяется к logits перед вычислением loss
  Хранение: LZ4 хорошо сжимает битовые массивы (много нулей) → ~200 байт на пример
```

## Уровень 5 (Подпроект 38) → PageRank как механизм выбора важных примеров

### Проблема которую решает

В датасете 10 ГБ кода. Не все примеры одинаково полезны:
- Тест `TestValidation_WhenEmailIsNull_ReturnsFailure` — простой, повторяющийся паттерн
- `AuthService.LoginAsync` — сложный, вызывается из 20 мест, архитектурно важный

Стандартное обучение учится на обоих с равной частотой. PageRank позволяет сказать: **учиться на важном коде чаще**.

### Как применять при обучении

**Выборка примеров пропорциональная PageRank:**
```
PageRank(метод) → вероятность попасть в батч

Метод AuthService.LoginAsync: PageRank = 0.89  → в 5% батчей
Метод Utils.FormatDate:       PageRank = 0.12  → в 0.7% батчей
Тест TestLogin:               PageRank = 0.03  → в 0.2% батчей

Вместо равномерной выборки:
  DataLoader выбирает примеры с вероятностью пропорциональной PageRank
  Важный код встречается чаще → модель его выучивает лучше
```

**Curriculum learning по PageRank:**
```
Фаза 1 (шаги 1–20K):   только топ-10% по PageRank
  Модель учит архитектурно важные паттерны сначала
  Это "скелет" системы

Фаза 2 (шаги 20K–60K): топ-50% по PageRank
  Добавляются вспомогательные компоненты

Фаза 3 (шаги 60K+):    весь датасет
  Включая утилиты, тесты, редкие файлы

Аналогия: учить иностранный язык сначала 1000 самых частых слов,
  потом 10 000, потом полный словарь.
  PageRank — это "частотный словарь" для кода.
```

**Хранение датасета с PageRank аннотациями:**
```
Стандартный шард: [token_id_1, token_id_2, ...]  ← плоский список

PageRank-аннотированный шард:
{
  "tokens":    [token_id_1, token_id_2, ...],
  "file_rank": 0.89,           ← PageRank файла
  "method_ranks": {            ← PageRank каждого метода в файле
    "LoginAsync":  0.89,
    "ValidateToken": 0.72,
    ...
  },
  "curriculum_tier": 1         ← к какой фазе обучения относится
}

DataLoader читает metadata и выбирает примеры по curriculum_tier
```

## Синтез: полная картина — T9 как архитектура обучения

### Как шесть уровней работают вместе

```
                    ┌──────────────────────────────────────────────┐
                    │  ПОДГОТОВКА ДАТАСЕТА (один раз)              │
                    └──────────────────────────────────────────────┘
                                        │
              ┌─────────────────────────┼─────────────────────────┐
              │                         │                         │
    ┌─────────▼──────────┐   ┌──────────▼──────────┐  ┌──────────▼──────────┐
    │  Уровень 1 (33)     │   │  Уровень 2А (34)    │  │  Уровень 5 (38)    │
    │  AST токенизация    │   │  Частотные корзины  │  │  PageRank ранжир.  │
    │  10К токенов        │   │  tier1/tier2/tier3  │  │  curriculum тиры   │
    │  вместо 50К BPE     │   │  взвешенная потеря  │  │  важный код чаще   │
    └────────────────────┘   └─────────────────────┘  └────────────────────┘
                                        │
              ┌─────────────────────────┼─────────────────────────┐
              │                         │                         │
    ┌─────────▼──────────┐   ┌──────────▼──────────┐  ┌──────────▼──────────┐
    │  Уровень 2Б (35)    │   │  Уровень 3 (36)     │  │  Уровень 4 (37)    │
    │  N-граммная иниц.   │   │  BM25 дополнение    │  │  Фильтр допустимых │
    │  attention bias     │   │  контекста          │  │  токенов в loss    │
    │  от статистики      │   │  из других файлов   │  │  маска на батч     │
    └────────────────────┘   └─────────────────────┘  └────────────────────┘
                                        │
                    ┌──────────────────────────────────────────────┐
                    │  ОБУЧЕНИЕ                                    │
                    │  Маленький словарь + умные данные +          │
                    │  правильная инициализация + curriculum       │
                    └──────────────────────────────────────────────┘
```

### Что меняется на каждом этапе обучения

**До обучения (датасет):**

| Что делает уровень | Как меняет хранение |
|---|---|
| 33 (AST) | Текст → сериализованные AST узлы. 100 ГБ → 12–18 ГБ (LZ4) |
| 34 (Частота) | Примеры разложены по трём тирам. Каждый пример помечен весом |
| 35 (N-грамм) | Каждый пример помечен «предсказуемость» — сколько токенов очевидны |
| 36 (BM25) | Каждый пример дополнен ссылками на связанные файлы (граф, ~200 байт/пример) |
| 37 (Фильтр) | Каждый пример имеет битовую маску допустимых токенов (~200 байт после LZ4) |
| 38 (PageRank) | Каждый файл помечен рангом важности. Примеры отсортированы по curriculum |

**Во время инициализации модели:**

| Что делает уровень | Как меняет инициализацию |
|---|---|
| 33 (AST) | Embedding таблица меньше в 5×. Маски внимания из дерева |
| 35 (N-грамм) | Attention bias инициализирован из N-граммных вероятностей |

**Во время шага обучения:**

| Что делает уровень | Как меняет шаг обучения |
|---|---|
| 34 (Частота) | Каждый токен умножается на weight_i в loss |
| 36 (BM25) | В контекст добавляются BM25-найденные фрагменты |
| 37 (Фильтр) | Loss вычисляется только по допустимым токенам |
| 38 (PageRank) | DataLoader выбирает примеры с вероятностью пропорциональной рангу |

### Ожидаемое ускорение

| Компонент | Экономия |
|---|---|
| AST словарь (33) | Шагов до качества: в 3–5× меньше |
| Взвешенная потеря (34) | Точность на редких паттернах: +15–25% |
| N-граммная инициализация (35) | Первые 10K шагов сокращаются: в 2× |
| BM25 контекст (36) | Понимание cross-file зависимостей: в 3× лучше |
| Фильтр допустимых (37) | Синтаксически верный вывод: с 72% до ~95% |
| PageRank curriculum (38) | Важные паттерны выучиваются первыми: в 2–3× быстрее |
| **Всё вместе** | **Шагов до рабочего качества: ориентировочно в 5–8× меньше** |

## Почему это T9, а не что-то другое

T9 на телефоне — самая простая языковая модель существующая в природе:

```
T9 = таблица {последовательность_нажатий → список_слов_по_частоте}
```

Каждый из наших шести уровней — это усовершенствование T9 в одном измерении:

```
T9 базовый (уровень 34):
  Знает что за "public" часто идёт "bool", "string", "void"
  Предлагает самое частое первым

T9 + структура (уровень 33):
  Не просто знает "public следует bool"
  Знает что ReturnType = одно из {bool, string, void, Task, ...}
  Список допустимых ограничен по типу узла

T9 + контекст (уровень 35):
  Не просто пара слов, а тройка или четвёрка
  "public async Task<" → скорее всего "AuthResult" или "bool"
  Контекст три токена назад = T9 с памятью

T9 + местный словарь (уровень 36):
  T9 знает что вы часто пишете слово "каникулы"
  Аналог: в этом проекте часто используют jwtService.Validate
  BM25 находит этот паттерн в соседних файлах

T9 + грамматика (уровень 37):
  T9 не предложит число там где должно быть слово
  Фильтр допустимых токенов = грамматика кода

T9 + важность (уровень 38):
  Слова которые вы пишете чаще → T9 предлагает их первыми
  Методы с высоким PageRank → модель выучивает их лучше
```

Разница от T9: T9 хранит таблицу явно. Языковая модель хранит те же знания неявно — в матрицах весов. Наш подход: **передать T9-знания явно в начале обучения**, чтобы модель не тратила вычисления на переоткрытие очевидного.
