# Прогрессивное обучение — Экспериментальный план X-04 v1.0
## Пять этапов: модель участвует в создании своих собственных следующих обучающих данных
## Solution: LlmFromScratch.sln

**Связан с:** X-01 (ускоренное обучение), X-02 (три пайплайна), X-03 (астроцитарный аналог)  
**Этот документ не касается XIIGen.**

---

## Основная идея — три вложенных петли

Вместо одного большого обучения на всём датасете — три петли разного масштаба:

```
Внешняя петля (этапы 0–4, дни–недели):
  Каждый этап производит лучшую модель
  Каждая лучшая модель производит лучшие обучающие данные для следующего этапа

Средняя петля (самоулучшение внутри этапа 3, часы):
  Специалист генерирует код → компилятор проверяет → добавляем в корпус
  Базовая модель оценивает качество → отбираем лучшее
  Перераспределяем ресурсы на слабые семьи

Внутренняя петля (астроцитарный слой, каждые K шагов):
  Монитор активаций → обновление топологии → следующие 100 шагов
```

Ключевое наблюдение: модели не нужно видеть все данные сразу. Ей нужно видеть правильные данные в правильный момент. Это в точности то как учится человек — не читает всю библиотеку сразу, начинает с простого и постепенно переходит к сложному.

## Этап 0 — Фундамент (1–2 дня, без модели)

**Что происходит:** детерминированная обработка данных. Ни одной нейронной сети ещё нет.

Задачи:
1. Прогнать весь код через компилятор-RAG пайплайн (Plan X-02, Pipeline 1)
   - Roslyn → лексер → AST → семантический граф
   - Результат: каждая функция = структурированный узел с типом, паттерном, семьёй

2. Обучить BPE токенизатор с техническим словарём (Plan X-02, Pipeline 3)
   - Предварительный словарь: технические термины как зарезервированные мерджи
   - Результат: `O(n log n)` = один токен, `async/await` = один токен

3. Запустить K-Means на статических эмбеддингах (подпроект 14)
   - Использовать GloVe или word2vec предобученные веса как начальные эмбеддинги
   - Получить 5,000 концептуальных семей
   - Результат: каждый токен знает свою семью до начала обучения

4. Построить семантические объекты (Plan X-01, Кирпич A)
   - FrameNet + SRL + WordNet + K-Means кластер + PageRank
   - Результат: каждый токен = структурированный объект, не число

**Критерий перехода к Этапу 1:**
- Все файлы корпуса проиндексированы в AST граф
- Семантические объекты созданы для всего словаря
- Тренировочные шарды записаны в uint16 формат

## Этап 1 — Первая рабочая модель (2–4 часа обучения)

**Что происходит:** обучение маленькой модели только на двух-трёх простейших концептуальных семьях.

Почему начинать с малого?
- Модель, обученная на 5% данных за 3 часа, уже может делать полезную работу
- Она сразу начинает помогать подготовке данных для следующего этапа
- Ошибки дешевле найти на маленькой модели чем на большой

Какие семьи выбрать первыми: концептуальные семьи с наибольшим PageRank и наименьшей дисперсией — самые "типичные" паттерны которые встречаются везде. Кандидаты: обработка ошибок, логирование, утилиты.

**Первое участие модели в собственном обучении:**

```csharp
// Stage1ModelContribution: как модель этапа 1 помогает готовить данные этапа 2
public class Stage1ModelContribution : BaseService
{
    private readonly IModelProvider stage1Model;

    // Оценить сложность обучающего примера для этапа 2.
    // Простые примеры (уверенное предсказание) идут в начало курикулума.
    // Сложные примеры (неуверенное предсказание) идут в конец.
    // Эта идея из Active Learning: модель сама говорит где ей нужна помощь.
    public async Task<OperationResult<double>> ScoreDifficultyAsync(
        string codeExample)
    {
        // Прогнать пример через модель и получить вероятность следующего токена
        var logits = await stage1Model.ForwardAsync(Tokenize(codeExample));

        // Энтропия распределения = мера неуверенности
        // Высокая энтропия → модель не знает что будет дальше → сложный пример
        // Низкая энтропия → модель уверена → простой пример
        double entropy = ComputeEntropy(Softmax(logits));

        return OperationResult<double>.Ok(entropy);
    }

    // Найти обучающие примеры по которым модель наиболее неуверена.
    // Именно эти примеры нужно добавить в корпус этапа 2 в первую очередь.
    // Это "активное обучение" — модель показывает где её нужно учить.
    public async Task<OperationResult<List<string>>> GetHighestPriorityExamplesAsync(
        List<string> candidateExamples,
        int topK)
    {
        // Оценить сложность каждого примера
        var scores = new List<(string example, double difficulty)>();
        foreach (var example in candidateExamples)
        {
            var score = await ScoreDifficultyAsync(example);
            scores.Add((example, score.Value));
        }

        // Вернуть топ-K самых сложных — именно их нужно учить следующими
        var topExamples = scores
            .OrderByDescending(s => s.difficulty)
            .Take(topK)
            .Select(s => s.example)
            .ToList();

        return OperationResult<List<string>>.Ok(topExamples);
    }
}
```

**Критерий перехода к Этапу 2:**
- Потеря на тренировочных семьях < 2.5
- Модель правильно завершает >70% simple completions в обученных семьях
- Готов список приоритетных примеров для Этапа 2 (scored by difficulty)

## Этап 2 — Специалисты (параллельно, 1–2 часа на специалиста)

**Что происходит:** LoRA дообучение на каждую концептуальную семью отдельно.

Почему специалисты вместо одной большой модели?
- Специалист по аутентификации видит только паттерны аутентификации — его корпус в 50 раз чище
- Специалист пишет лучший код аутентификации чем общая модель обученная на всём сразу
- Когда специалисты не соглашаются друг с другом на пограничном примере — это сигнал для DPO

**Петля DPO через специалистов:**

```csharp
// SpecialistDpoPairGenerator создаёт обучающие пары предпочтений
// используя разногласие между специалистами как сигнал качества.
public class SpecialistDpoPairGenerator : BaseService
{
    // Генерировать пару DPO (предпочтительный ответ, отвергнутый ответ)
    // для данного prompta используя двух специалистов.
    //
    // Идея: если специалист по аутентификации и базовая модель
    //       дают разные ответы на вопрос об аутентификации —
    //       специалист обычно прав.
    public async Task<OperationResult<DpoPair>> GeneratePairAsync(
        string prompt,
        IModelProvider domainSpecialist,
        IModelProvider baseModel)
    {
        // Специалист генерирует "предпочтительный" ответ
        var specialistResponse = await domainSpecialist.GenerateAsync(prompt);

        // Базовая модель генерирует "отвергнутый" ответ
        var baseResponse = await baseModel.GenerateAsync(prompt);

        // Если ответы очень похожи — пропустить (не информативная пара)
        double similarity = ComputeTextSimilarity(
            specialistResponse.Value!, baseResponse.Value!);

        if (similarity > 0.85)
        {
            return OperationResult<DpoPair>.Fail(
                "Responses too similar — not a useful preference pair.",
                "PAIR_TOO_SIMILAR");
        }

        // Компилятор проверяет корректность кода в обоих ответах
        bool specialistCompiles = CompilerCheck(specialistResponse.Value!);
        bool baseCompiles = CompilerCheck(baseResponse.Value!);

        // Только если специалист компилируется а базовая нет — надёжная пара
        if (!specialistCompiles || !baseCompiles)
        {
            return OperationResult<DpoPair>.Fail(
                "One or both responses failed compilation — unreliable pair.",
                "COMPILATION_FAILURE");
        }

        return OperationResult<DpoPair>.Ok(new DpoPair
        {
            Prompt   = prompt,
            Chosen   = specialistResponse.Value!,   // специалист предпочтительнее
            Rejected = baseResponse.Value!           // базовая отвергается
        });
    }
}
```

**Критерий перехода к Этапу 3:**
- Каждый специалист превосходит базовую модель на своей семье
- Сгенерировано >1000 DPO пар на специалиста
- Человек-ревьюер проверил случайную выборку 50 пар: >80% согласны с выбором

## Этап 3 — Петля самоулучшения (дни–недели, итеративно)

**Что происходит:** специалисты генерируют синтетические примеры, базовая модель оценивает качество, хорошие примеры расширяют корпус, базовая модель переобучается.

Это самая мощная часть всей системы. Каждая итерация увеличивает корпус в 2–5 раз.

**Три типа синтетических данных которые модель генерирует для себя:**

Тип 1 — Синтетический код (компилятор как фильтр):
```
Специалист генерирует функцию → Roslyn проверяет → компилируется → добавляем
```

Тип 2 — Аугментированная документация (Pipeline 2 как фильтр):
```
Специалист пишет код → Pipeline 2 генерирует документацию → Pipeline 3 аннотирует
→ если документация технически точна → пара (код, документация) в корпус
```

Тип 3 — Примеры рефакторинга (два специалиста как фильтр):
```
Специалист A пишет код → Специалист B улучшает → если B лучше по метрике → пара в DPO
```

**Роль астроцитарного слоя в петле самоулучшения:**

```csharp
// SelfImprovementOrchestrator координирует петлю самоулучшения.
// Астроцитарный слой (из плана X-03) решает что генерировать следующим.
public class SelfImprovementOrchestrator : BaseService
{
    private readonly AstrocyteLayer astrocyteLayer;
    private readonly DeprivationDetector deprivationDetector;

    // Один цикл самоулучшения: выбрать семью → сгенерировать → проверить → добавить
    public async Task<OperationResult<int>> RunOneIterationAsync(
        List<IModelProvider> specialists,
        IModelProvider baseModel)
    {
        // Астроцитарный слой говорит какие семьи сейчас "слабые"
        // (давно не получали обучающих примеров или показывают высокую потерю)
        var weakFamilies = await astrocyteLayer.GetWeakConceptFamiliesAsync();

        // Детектор депривации говорит какие семьи почти не встречались в последних батчах
        var deprivedFamilies = await deprivationDetector.GetDeprivedFamiliesAsync();

        // Выбрать семьи которые одновременно слабы И испытывают депривацию
        // Это именно те семьи которым нужно больше всего данных
        var priorityFamilies = weakFamilies.Value!
            .Intersect(deprivedFamilies.Value!)
            .ToList();

        int addedExamples = 0;

        // Для каждой приоритетной семьи — попросить специалиста сгенерировать примеры
        foreach (var family in priorityFamilies)
        {
            var specialist = FindSpecialistFor(family, specialists);
            var syntheticExamples = await GenerateSyntheticExamples(specialist, family);
            var validatedExamples = await ValidateWithCompiler(syntheticExamples);
            await AddToTrainingCorpus(validatedExamples);
            addedExamples += validatedExamples.Count;
        }

        return OperationResult<int>.Ok(addedExamples);
    }
}
```

**Когда остановить Этап 3:**
- Добавление новых синтетических примеров больше не улучшает перплексию на валидационном множестве
- Качество генерируемых примеров платосируется (компилятор отклоняет >60% генераций)
- Или: перешли к хорошему результату по нашим метрикам → начинаем Этап 4

## Этап 4 — Непрерывное обучение с астроцитарным слоем (ongoing)

**Что происходит:** модель учится из продакшн-потока данных без полного переобучения.

Три ключевых принципа:

**Принцип 1 — Постепенное добавление, не замена:**
Новые данные не заменяют старое знание — они добавляются к нему. Долгое временное окно астроцитарного слоя (10,000 шагов) помнит распределение предыдущих этапов и "сдерживает" топологию от полного перестроения под новые данные.

**Принцип 2 — Депривация как сигнал, не проблема:**
Когда определённый паттерн исчезает из потока входных данных — это не значит что его надо забыть. Это сигнал детектору депривации: сохранить ёмкость голов для этого паттерна, не перераспределять её. Модель помнит паттерны аутентификации даже если последние 1000 батчей были только про UI.

**Принцип 3 — Специалисты как долговременная память:**
Специалисты из Этапа 2 не переобучаются в Этапе 4. Они остаются как "консервированные эксперты" — всегда доступны через RAG когда базовая модель неуверена в специализированном вопросе.

## Сравнение с обычным подходом

| Параметр | Обычное обучение | Прогрессивный подход |
|---|---|---|
| Когда появляется первый рабочий результат | После полного обучения (дни–недели) | Через 3–4 часа (Этап 1) |
| Размер начального датасета | 100% корпуса | 5–10% (простейшие семьи) |
| Участие модели в создании данных | Нет | Начиная с Этапа 1 |
| Катастрофическое забывание | Постоянная проблема | Смягчено долгим окном астроцитарного слоя |
| Переход на новые данные (новый фреймворк) | Переобучение или drift | Непрерывная адаптация в Этапе 4 |
| Инспектируемость | Сложно — одна большая модель | Легко — специалисты разделены по доменам |
