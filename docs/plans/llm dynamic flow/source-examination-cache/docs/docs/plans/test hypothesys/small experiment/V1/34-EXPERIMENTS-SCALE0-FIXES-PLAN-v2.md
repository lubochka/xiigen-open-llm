## Четыре группы исправлений

### Группа 1 — Сломанная память (блокирует все эксперименты)

**Проблема:** `GC.GetTotalMemory(false)` вызывается внутри одного процесса последовательно.  
Каждый следующий эксперимент унаследует выделения предыдущего.  
Baseline и Enhanced показывают одно значение потому что сборка мусора не происходит между замерами.

**Исправление в шести файлах E0*.cs и в ResourceMonitor.cs:**

```csharp
// Было:
MemoryMb = GC.GetTotalMemory(false) / 1_048_576.0

// Нужно (вариант A — простой, достаточный для Scale 0–2):
long memBefore = GC.GetAllocatedBytesForCurrentThread();
// ... запустить алгоритм ...
long memAfter  = GC.GetAllocatedBytesForCurrentThread();
MemoryMb = (memAfter - memBefore) / 1_048_576.0;

// Вариант B — точнее, но требует GC.Collect() что медленно:
GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();
long before = GC.GetTotalMemory(true);
// ... запустить алгоритм ...
MemoryMb = (GC.GetTotalMemory(false) - before) / 1_048_576.0;
```

Рекомендуется вариант A: `GC.GetAllocatedBytesForCurrentThread()` — показывает сколько именно этот прогон выделил, без влияния предыдущих.

**Где менять:** ResourceMonitor.cs (если используется) + патч в шести E0*.cs.

### Группа 2 — E06: несправедливое сравнение (исправление логики)

**Проблема:** Baseline оценивается на 5734 BPE-позициях, Enhanced — на 893 AST-узлах.  
Это разные датасеты разного размера. Точность нельзя сравнивать напрямую.

**Исправление:** перейти на **перплексию-на-символ** как общую метрику, или выровнять размер валидационной выборки.

Конкретно — два варианта:

**Вариант A (проще):** сравнивать только на позициях которые присутствуют в обоих представлениях.  
Для каждого AST-узла найти соответствующую позицию в BPE-потоке и оценивать только там.

**Вариант B (чище):** сменить метрику E06 с `accuracy` на `bits-per-character` (бит-на-символ).  
```
BPE перплексия:  2^(-средний log2 P(токен)) → нормировать на число символов
AST перплексия:  2^(-средний log2 P(узел))  → нормировать на число символов файла
```
Тогда обе модели отвечают на один вопрос: «сколько бит нужно чтобы закодировать один символ».  
Меньше = лучше.

Рекомендуется **Вариант B** — он совместим с NPS из RESEARCH-04 и не требует выравнивания индексов.

**Где менять:** E06AstRoslyn.cs — метод `Run()`, метрика и поле `PrimaryMetricName`.

### Группа 3 — E01 и E05: K слишком велик для Scale 0

**Проблема:** K=50 кластеров при 76 уникальных токенах — вырожденный K-Means.  
Большинство кластеров пусты или содержат по 1 токену. Кластеризация бессмысленна.

**Исправление:** адаптировать K к реальному числу уникальных токенов.

```csharp
// Было:
private const int K = 50;

// Нужно:
// K не должен превышать uniqueTokenCount / 5
// (чтобы в среднем хотя бы 5 токенов на кластер)
int adaptiveK = Math.Max(5, Math.Min(K, seenTokens.Count / 5));
```

Дополнительно для E01: если `adaptiveK < 10` — пропустить эксперимент и вернуть  
`OperationResult.Fail("Scale 0 слишком мал для K-Means: нужно ≥50 уникальных токенов")`.  
Это честнее чем запускать вырожденный кластеризатор и получать ложные числа.

**Для E05 (иерархическое предсказание):** та же проблема — при 76 токенах двухуровневая иерархия бессмысленна. Добавить проверку: если `vocabSize < 100` → пропустить Scale 0, рекомендовать Scale 1.

**Где менять:** E01SemanticFamilies.cs и E05HierarchicalPrediction.cs.

### Группа 4 — E02: уточнить что именно измеряем

**Проблема:** E02 измеряет две разные вещи одновременно — энтропию (которая улучшилась) и accuracy следующего токена (которая ухудшилась). Это не противоречие: энтропия измеряет предсказуемость распределения, accuracy — конкретное top-1 предсказание.

**Исправление:** разделить на два поля в результате:

```json
{
  "baseline_entropy_bits": 4.639,
  "enhanced_entropy_bits": 3.867,
  "entropy_improvement_pct": 16.7,

  "baseline_accuracy_pct": 33.73,
  "enhanced_accuracy_pct": 31.48,
  "accuracy_delta_pct": -2.25,

  "primary_metric": "entropy",
  "passed_on_entropy": true,
  "passed_on_accuracy": false
}
```

Главная метрика E02 — **энтропия** (она про сжатие).  
Точность — вторичная метрика (интересна но не определяет pass/fail).  
После этого E02 на Scale 0 **прошёл** (+16.7% на энтропии).

**Где менять:** E02ShannonCompression.cs — поля результата и критерий `Passed`.
