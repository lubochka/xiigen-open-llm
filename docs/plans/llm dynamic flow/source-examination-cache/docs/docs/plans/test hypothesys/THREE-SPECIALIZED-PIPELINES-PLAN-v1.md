## Зачем три отдельных пайплайна, а не один

Единая языковая модель обученная на смеси кода, документации и технических текстов обучается компромиссу — она умеет всё немного. Три специализированных пайплайна решают три разные задачи разными методами:

| Пайплайн | Метод | Аналогия |
|---|---|---|
| Код | Компилятор + RAG + субмодели | Как работает компилятор — структура, не текст |
| Документация | Препроцессор → LLM | Как работает TypeScript → JavaScript |
| Технический язык | Узкий корпус → маленькая модель | Как работает специализированный словарь |

Ключевое наблюдение: сырой код — это структурированные данные притворяющиеся текстом. BPE токенизатор обращается с `if (x > 0)` как с последовательностью символов. Компилятор знает что это условный оператор с выражением-сравнением. Пайплайн кода использует знание компилятора.

## Пайплайн 1 — Код: Компилятор-RAG гибрид с субмоделями

### Основная идея

Стандартное обучение на коде: взять 100 ГБ кода с GitHub → запустить BPE → обучить трансформер. Модель должна сама "открыть" что `factory.CreateUser()` — это паттерн Фабрика, что `async/await` — это обёртка над задачами, что `IDisposable` связан с освобождением ресурсов.

Пайплайн 1: построить компилятор-RAG гибрид который уже знает эту структуру. Обучать не на тексте, а на структуре. Вместо одной большой модели — много маленьких субмоделей, каждая эксперт в одной концептуальной семье.

### Пять стадий пайплайна

**Стадия 1 — Лексер (детерминированный)**

Входной файл проходит через лексер по правилам грамматики языка. На выходе не BPE токены, а типизированные токены с позицией:

```
Входной код:
  public async Task<UserDto> GetUserAsync(int userId)

Токены лексера:
  [KEYWORD:public pos=0] [KEYWORD:async pos=7] [KEYWORD:Task pos=13]
  [OPERATOR:< pos=17] [TYPE:UserDto pos=18] [OPERATOR:> pos=25]
  [KEYWORD:void pos=... ]  ... и т.д.
```

Используемый подпроект: 13 (Code Optimizer) — там уже есть Roslyn интеграция. Расширить `RoslynCodeAnalyzer` для выдачи полного токен-потока.

**Стадия 2 — AST парсер (детерминированный)**

Токен-поток → синтаксическое дерево. Каждая функция становится самостоятельным поддеревом:

```
MethodDeclaration
├── Modifiers: [public, async]
├── ReturnType: Task<UserDto>
├── Name: GetUserAsync
├── Parameters: [userId: int]
└── Body:
    ├── LocalVariable: user = await _repository.FindAsync(userId)
    ├── IfStatement: user == null → throw NotFoundException
    └── ReturnStatement: new UserDto(user)
```

Каждый узел дерева имеет тип (MethodDeclaration, IfStatement, ReturnStatement), имя, дочерние узлы, и ссылки на объявления типов. Это то что знает компилятор — BPE этого не знает никогда.

Используемый подпроект: 13 (Roslyn AST), 07 (Graph Engine для хранения дерева).

**Стадия 3 — Семантический анализ (детерминированный)**

AST + разрешение типов + граф зависимостей:

```
GetUserAsync:
  calls: [_repository.FindAsync, UserDto.ctor, NotFoundException.ctor]
  called_by: [UserController.GetUser, AdminController.GetUser]
  uses_pattern: [Repository, DTO, NullCheck]
  concept_family: "data_access"
  pagerank_score: 0.0082  (вызывается из многих мест)
```

Паттерны обнаруживаются эвристиками: Repository паттерн = сервис вызывающий интерфейс с Find/Save/Delete методами. DTO паттерн = класс только с публичными свойствами и без методов.

Используемый подпроект: 07 (Knowledge Graph + PageRank), 22 (Agent Algorithms — Symbol Graph traversal).

**Стадия 4 — Компилятор-RAG гибрид**

AST узлы индексируются в двух индексах одновременно:

Индекс 1 — структурный (новый): запрос по AST типу и паттерну.
```
Запрос: "все методы которые используют Repository паттерн и возвращают DTO"
→ возвращает список AST узлов по структурному критерию
→ без семантического поиска по тексту
```

Индекс 2 — семантический (подпроект 06 HNSW): запрос по смысловой близости через эмбеддинги функций.
```
Запрос: "как обрабатывать null в методах доступа к данным"
→ возвращает похожие примеры по смыслу
```

Гибридный результат = объединение структурного и семантического запросов. Это то чего не умеет ни чистый RAG (не знает структуры AST) ни компилятор (не знает семантической близости).

Используемый подпроект: 06 (HNSW Vector Search), 07 (Graph Engine), 08 (Graph RAG), 21 (Agent Infrastructure — Tool system).

**Стадия 5 — Субмодели на микро-корпусах**

Вместо обучения одной модели на 100 ГБ кода — обучить N маленьких моделей, каждая на семантически связном микро-корпусе:

| Субмодель | Концептуальная семья | Размер корпуса | Размер модели |
|---|---|---|---|
| AuthModel | аутентификация, JWT, roles, guards | 2–5 ГБ | 50M параметров |
| DataAccessModel | репозитории, ORM, транзакции | 3–8 ГБ | 100M параметров |
| ErrorHandlingModel | исключения, result types, retry | 1–3 ГБ | 30M параметров |
| AsyncModel | Task, async/await, SemaphoreSlim | 2–4 ГБ | 50M параметров |
| ApiModel | контроллеры, роуты, middleware | 2–5 ГБ | 70M параметров |

Каждый микро-корпус собирается через структурный запрос к компилятор-RAG гибриду: "дай мне все функции с паттерном X". Это несравнимо плотнее чем случайная выборка из GitHub.

**Почему это создаёт маленькие датасеты:**
Стандартный датасет GitHub: 100 ГБ, из которых 80% бойлерплейт, комментарии, тесты, конфиги.
Микро-корпус AuthModel: 2–5 ГБ, только функции напрямую относящиеся к аутентификации. Плотность обучающего сигнала в 10–40 раз выше.

Используемый подпроект: 03 (Transformer), 04 (Training Loop), 10 (LoRA — для дообучения субмоделей).

## Пайплайн 2 — Документация: Препроцессор + LLM

### Основная идея

Проблема с обучением LLM писать документацию по коду: модель должна одновременно понимать синтаксис C# (или TypeScript, или Python), разобраться в логике функции, и сформулировать это на английском языке. Три разные задачи в одном шаге.

Разделить на два уровня:
- Уровень 1 (препроцессор): механически перевести код в структурированный псевдокод. Никакой языковой модели — просто правила. Как TypeScript-компилятор не знает английского языка, он просто транслирует синтаксис.
- Уровень 2 (LLM): получить структурированный псевдокод и написать документацию. Модель теперь работает только с языком, не с синтаксисом.

### Уровень 1 — Препроцессор (детерминированный)

Вход: исходный код  
Выход: структурированное представление алгоритма

Пример трансляции:

```csharp
// Входной код C#:
public async Task<List<User>> GetActiveUsersAsync(int tenantId)
{
    var users = await _cache.GetAsync<List<User>>($"users:{tenantId}");
    if (users != null) return users;
    
    users = await _repository.FindAsync(u => u.TenantId == tenantId && u.IsActive);
    await _cache.SetAsync($"users:{tenantId}", users, TimeSpan.FromMinutes(10));
    return users;
}
```

```
// Структурированный псевдокод (вывод препроцессора):
FUNCTION: get active users
INPUT: tenant identifier (integer)
OUTPUT: list of user objects (possibly empty)

STEP 1: check cache
  CACHE_KEY: "users:{tenant identifier}"
  IF cache contains key → return cached value immediately (early exit)

STEP 2: query data source
  FILTER: records where tenant matches AND record is active
  ASSIGN result to users

STEP 3: populate cache
  STORE users under cache key with 10 minute expiration

STEP 4: return users
```

Правила трансляции детерминированы:
- `if (x) return y` → `IF condition → return value immediately (early exit)`
- `await cache.GetAsync(key)` → `check cache with key`
- `filter lambda` → `FILTER: условие в человеческих словах`
- `SetAsync(..., TimeSpan.FromMinutes(10))` → `with 10 minute expiration`

Это реализуется как набор правил поверх AST из пайплайна 1 — не нейронная сеть, просто шаблоны.

Используемые подпроекты: 13 (Roslyn AST), 22 (Agent Algorithms — RulesFileParser аналог для правил трансляции).

**Почему это важно:** LLM теперь получает вход который:
- Не зависит от языка программирования (C# и Python дают одинаковый псевдокод)
- Явно структурирован (STEP 1, STEP 2, условия)
- Не требует знания синтаксиса
- Верифицируем (можно проверить что псевдокод соответствует коду)

### Уровень 2 — LLM по структурированному входу

Модель получает структурированный псевдокод и генерирует документацию. Обучается на парах: (псевдокод → документация) из открытых репозиториев с уже написанной документацией.

Обучающие пары:

```
Вход (уровень 2):
  FUNCTION: get active users
  INPUT: tenant identifier (integer)
  OUTPUT: list of user objects
  STEP 1: check cache ... [полный псевдокод]

Ожидаемый выход (из существующей документации):
  "Returns all active users for the specified tenant, using a 10-minute 
   cache to reduce database load. Returns an empty list if no active users 
   exist. Thread-safe for concurrent requests to the same tenant."
```

Датасет для уровня 2: репозитории с XML-документацией C# (`/// <summary>`) или JSDoc — автоматически извлекаются пары (функция → документация), функция прогоняется через препроцессор уровня 1.

Предположительный размер датасета уровня 2: 500 МБ – 2 ГБ пар (псевдокод, документация). Это в 50–200 раз меньше чем обучать на сыром коде.

**Сравнение с обычным подходом:**

| Параметр | Прямое обучение на коде | Пайплайн 2 (двух-уровневый) |
|---|---|---|
| Что видит LLM | Сырой C# / TypeScript | Структурированный псевдокод |
| Размер датасета | 50–200 ГБ кода | 0.5–2 ГБ пар |
| Зависимость от языка | Да (нужно учить C# и TS отдельно) | Нет (псевдокод одинаков) |
| Верифицируемость | Нет | Да (препроцессор детерминирован) |
| Размер модели | 1–7B параметров | 100–500M параметров |

## Пайплайн 3 — Технический язык: Узкий корпус + Компактная модель

### Основная идея

Стандартные LLM обучаются на смеси: веб-страницы, книги, код, форумы, новости. Технический словарь — малая часть. Модель знает слово "sort" в 50 разных контекстах: уборка, карточки, сортировка данных, социальный класс, банковский платёж.

Для технической документации нужна модель у которой слово "sort" означает только сортировку данных, "tree" означает только структуру данных, "complexity" означает только вычислительную сложность.

Технически: узкий корпус создаёт модель с very low entropy (низкой энтропией) на техническом словаре — она предсказывает технические термины гораздо точнее.

### Корпус

Только эти источники:

```
Технические книги (открытые):
  - SICP (Structure and Interpretation of Computer Programs) — public domain
  - The Art of Computer Programming vol. 1-4 — за пределами copyright (старые издания)
  - Algorithm Design Manual (Skiena) — фрагменты в открытом доступе
  - Clean Code, Clean Architecture (Robert Martin) — excerpts
  - Design Patterns (GoF) — excerpts

Статьи и препринты:
  - arXiv CS (Computer Science) — весь архив, открытый доступ
  - ACM DL открытые статьи
  - ICML, NeurIPS, ICLR открытые proceedings

Спецификации и RFC:
  - Все RFC (IETF) — public domain
  - ECMA-262 (JavaScript spec)
  - C# Language Specification (открытая)
  - Python Language Reference

Техническая документация:
  - .NET API docs (MIT)
  - MDN Web Docs (CC BY-SA)
  - Linux kernel Documentation/ (GPL)
  - PostgreSQL documentation (PostgreSQL License)
```

Не включать: общий веб, Reddit, Stack Overflow ответы (слишком шумные), Wikipedia (слишком общая).

Ориентировочный размер корпуса: 10–30 ГБ текста. Для сравнения: GPT-3 обучался на ~570 ГБ. Это намеренно меньше.

### Специализированный токенизатор

Обычный BPE токенизатор учится на статистике совместной встречаемости и не знает что `O(n log n)` — это отдельный концепт, что `HashMap` — это два слова, что `async/await` — это пара.

Для технического токенизатора:
- Предварительный словарь технических терминов (из Wikipedia технических статей + API документации)
- Зарезервированные мерджи: `O(n_log_n)` → один токен, `async_await` → один токен, `HashMap` → один токен
- BPE поверх этого для остального словаря

В результате технические концепты = один токен → модель видит их как единые атомы, не как последовательности символов.

Используемый подпроект: 01 (BPE Tokenizer) — расширить с предварительным словарём.

### Компактная доменная модель

Параметры: 50–200M (против 1–7B у общих моделей). Почему это работает при таком маленьком размере:

1. Узкий домен = нет необходимости хранить знание о кулинарии, истории, спорте
2. Технический корпус более регулярный = меньше вариативности для запоминания
3. Специализированный токенизатор = технические концепты уже встроены как атомы

Обучение: стандартный Language Modeling (предсказание следующего токена) на техническом корпусе. Использовать подпроекты 03 (Transformer) и 04 (Training Loop) без изменений.

### Как работает вместе с пайплайном 2

Выход пайплайна 2 (документация) подаётся на вход пайплайна 3 как промпт:

```
Пайплайн 2 создал:
  "Returns active users for the tenant from cache or database."

Пайплайн 3 дополняет:
  "Returns active users for the tenant from cache or database. 
   Time complexity: O(1) for cache hit, O(n) for database query where n 
   is the number of active users. Thread-safe. Cache TTL: 10 minutes.
   See also: IUserRepository.FindAsync, ICache.SetAsync."
```

Модель пайплайна 3 добавляет:
- Вычислительную сложность (O-notation)
- Thread safety аннотации
- Ссылки на связанные API
- Технические предупреждения (throws, nullable return, etc.)

Это то что общая LLM угадывает — техническая доменная модель знает с высокой точностью из-за специализированного корпуса.

## Как три пайплайна работают вместе

```
Запрос: "задокументируй этот файл"
         │
         ▼
┌─────────────────────────────────┐
│  Пайплайн 1 — КОД               │
│  Roslyn → AST → Семантика        │
│  Компилятор-RAG гибрид           │
└──────────────┬──────────────────┘
               │ структурированный AST + паттерны
               ▼
┌─────────────────────────────────┐
│  Пайплайн 2 — ДОКУМЕНТАЦИЯ       │
│  Уровень 1: AST → псевдокод      │
│  Уровень 2: псевдокод → текст    │
└──────────────┬──────────────────┘
               │ черновая документация
               ▼
┌─────────────────────────────────┐
│  Пайплайн 3 — ТЕХНИЧЕСКИЙ ЯЗЫК  │
│  Аугментация техническими        │
│  аннотациями + ссылками          │
└──────────────┬──────────────────┘
               │
               ▼
          Финальная документация
          точная, верифицируемая,
          технически аннотированная
```

Пайплайн 1 также поставляет данные для обучения пайплайна 2 (пары псевдокод→документация из открытых репозиториев с XML-doc).

| Метрика | Как измерить |
|---|---|
| Плотность обучающего сигнала | перплексия субмодели на ≤5 ГБ микро-корпусе vs общей модели на 50 ГБ |

| Размер датасета субмодели | МБ на концептуальную семью |
| Время до целевой потери | шагов до loss < 2.0 для субмодели vs общей модели |

### Метрики для пайплайна 2 (документация)

| Метрика | Как измерить |
|---|---|
| BLEU score | сравнение с существующей XML-doc на 10,000 функций CodeSearchNet |
| Factual accuracy | % утверждений в документации подтверждаемых AST (нет выдуманных параметров) |
| Language independence | одинаковый BLEU для C# и Python функций реализующих один алгоритм |
| Model size | параметров для достижения того же BLEU что у 7B общей модели |

### Метрики для пайплайна 3 (технический язык)

| Метрика | Как измерить |
|---|---|
| Technical term accuracy | % правильно используемых O-notation аннотаций |
| See-also relevance | precision@3 на задаче поиска связанных API |
| Perplexity on tech text | на arXiv CS тестовом множестве |
| Size vs quality | насколько маленькой можно сделать модель при той же точности |

## Порядок реализации

**Шаг 1 — Пайплайн 2, Уровень 1 (самый ценный первый результат)**

Препроцессор AST→псевдокод не требует обучения. Это чистые правила поверх уже реализованного Roslyn AST из подпроекта 13. Можно сделать за 1–2 недели и сразу получить верифицируемый псевдокод.

**Шаг 2 — Пайплайн 1, Стадии 1–3**

Лексер, AST парсер, семантический анализ — используют готовый Roslyn. Новое только PatternDetector и ConceptFamilyClassifier.

**Шаг 3 — Пайплайн 3, Корпус + Токенизатор**

Скачать и отфильтровать технический корпус. Расширить BPE токенизатор техническим словарём. Обучить компактную модель 50–100M параметров.

**Шаг 4 — Пайплайн 2, Уровень 2 + датасет**

Собрать пары (псевдокод, документация) из открытых репозиториев. Обучить.

**Шаг 5 — Пайплайн 1, Стадии 4–5 (компилятор-RAG гибрид)**

Самая сложная часть — интеграция структурного индекса с существующим HNSW. Реализовать последней.
