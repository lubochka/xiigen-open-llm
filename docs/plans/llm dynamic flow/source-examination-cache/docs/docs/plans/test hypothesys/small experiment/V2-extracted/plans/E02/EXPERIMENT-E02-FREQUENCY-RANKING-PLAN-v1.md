# E02 — Ранжирование по частоте вызовов vs алфавитный порядок
## Отдельный план эксперимента · LlmFromScratch.sln

**ID:** E02-FREQUENCY-RANKING  
**Подпроект-источник:** 34.CodeCompletion (Уровень 2А — статистика использования)  
**Альтернативный подход учтён:** RESEARCH-03-T9 (T9-аналогия: частые слова → короткие коды)

---

## Гипотеза

T9 на старом телефоне работал потому что хранил таблицу: "4-6-8-6" → {«town»: 847, «tово»: 0, «uoun»: 0}. Он предлагал самое частое первым. Это же работает для автодополнения кода: если `myList.` — предлагать `Add` (вызывается 38% времени) а не `Aggregate` (вызывается 0.1%).

**Ключевой вопрос при масштабировании:** сколько наблюдений нужно для надёжной статистики? При 3 вызовах одного типа частоты зашумлены. При 50 — стабильны.

---

## Что меняется

| Параметр | Baseline | Enhanced |
|---|---|---|
| Порядок предложений | Алфавитный (`Add`, `Aggregate`, `All`, `Any`...) | По частоте вызовов в проекте (`Add` → `Count` → `First` → ...) |
| Источник статистики | Нет | `UsageFrequencyCollector` — подсчёт `тип.метод()` по всем файлам |
| Метрика | Top-1 accuracy: правильный ли метод предложен первым? | То же |

Измерение:
```
1. Найти в коде все выражения вида `тип.метод()`
2. Для 50 таких выражений скрыть часть после точки
3. Baseline: предложить первый метод алфавитно
4. Enhanced: предложить метод с наибольшей частотой для данного типа
5. Top-1 accuracy = % где предложение совпало с реальным методом
6. Top-5 accuracy = % где реальный метод был в первых 5 предложениях
```

---

## Уникальная ось масштабирования: статистическая уверенность

**Центральный вопрос:** при каком количестве наблюдений частотное ранжирование стабилизируется?

```
Метрика уверенности = (методы с ≥10 наблюдениями) / (все методы)

Tier 1 (~2000 токенов): ожидаем уверенность ~20–30% (мало данных, шумно)
Tier 2 (~9100 токенов): ожидаем ~50–60% (нарастающее улучшение)
Tier 3 (~141000 токенов): ожидаем ~80–90% (надёжная статистика)
```

Гипотеза: **улучшение Top-1 accuracy будет расти вместе с тиром** — именно потому что T9-таблица становится надёжнее. Это отличает E02 от E01 (E01 работает хорошо даже на Tier 1; E02 раскрывается при большем объёме).

## Лестница тиров

### Tier 1 — micro (< 3 секунды, < 40 МБ RAM)

**Датасет:** `01.Tokenizer` — 3 файла  
**Ожидание:** Top-1 accuracy улучшится скромно (+5–15%) — мало вызовов для надёжной статистики  
**Метрика уверенности:** ожидаем ~20–30%  
**Цель:** убедиться что механизм работает, даже если улучшение небольшое

---

### Tier 2 — small (< 30 секунд, < 100 МБ RAM)

**Датасет:** 6 малых подпроектов (`01, 02, 05, 07, 09, 10`) — ~47 файлов  
**Ожидание:** улучшение растёт (+15–25%), метрика уверенности ~50%  
**Специфичный тест:** для каких типов (List, IEnumerable, string) статистика уже надёжна?

---

### Tier 3 — medium (< 2 минуты, < 200 МБ RAM)

**Датасет:** все 24 подпроекта — ~195 файлов  
**Ожидание:** Top-1 accuracy улучшение +25–40%, уверенность ~85%  
**Специфичный тест:** Построить "кривую обучения T9" — ось X = количество файлов, ось Y = Top-1 accuracy. Найти точку перегиба где улучшение замедляется.

---

### Tier 4 — external project (< 10 минут)

**Датасет:** внешний C# проект  
**Ожидание:** статистика нашего проекта частично переносится (List.Add везде частый)  
**Специфичный тест:** какой процент топ-методов совпадает между проектами?

---

### Tier 5 — cross-project (одноразово)

**Датасет:** несколько GitHub проектов на C#  
**Цель:** построить универсальную "таблицу T9" для C# которая работает без обучения на конкретном проекте
