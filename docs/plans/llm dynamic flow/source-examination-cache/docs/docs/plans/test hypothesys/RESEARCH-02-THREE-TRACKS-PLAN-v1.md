## Зачем три отдельных трека, а не одна общая модель

Общая языковая модель (GPT-2, LLaMA) учится на всём сразу — художественной литературе, новостях, коде, документации. Это значит большая часть ёмкости модели уходит на знания которые нам не нужны. Три специализированных трека — это три маленьких модели, каждая идеальна в своей нише.

Аналогия из компиляторного мира: GCC не один инструмент. Это цепочка: препроцессор → синтаксический анализ → семантический анализ → генерация кода. Мы строим аналогичные цепочки для трёх типов контента.

## Трек A — Код: гибрид компилятора, RAG и языковой модели

### Ключевая идея

Компилятор (Roslyn для C#) уже **идеально понимает структуру кода** — типы, области видимости, вызовы, зависимости, поток управления. Языковая модель этого не знает — она угадывает структуру по текстовым паттернам. Мы используем Roslyn как точный структурный анализатор, а языковая модель учится только на семантике поверх этой структуры.

Аналогия: компилятор знает что `validateToken()` возвращает `bool` и вызывается из трёх мест. Языковая модель видит только текст «validateToken». Гибрид объединяет оба знания.

### Архитектура: дерево синтаксиса как первичное представление

```
Стандартный подход (что делают GPT-2, LLaMA):
  Входной код:     "public bool Validate(string token) { return token != null; }"
  Токенизация:     ["public", " bool", " Validate", "(", "string", " token", ")", ...]
  Обучение:        предсказать следующий токен в последовательности

Наш подход (Трек A):
  Входной код:     "public bool Validate(string token) { return token != null; }"
  Roslyn разбор:   Синтаксическое дерево (AST — Abstract Syntax Tree)
  ↓
  MethodDeclaration
    ├── ReturnType: bool
    ├── Name: Validate
    ├── Parameters: [(string, token)]
    └── Body:
          ReturnStatement
            └── BinaryExpression (!=)
                  ├── IdentifierName: token
                  └── NullLiteral
  ↓
  Узлы дерева → токены обучения (вместо текстовых подстрок)
  Рёбра дерева → маски внимания (связи между токенами известны заранее)
```

### Три уровня токенов для кода

**Уровень 1 — Структурные токены (из Roslyn AST):**
Каждый узел дерева = один токен. Тип узла кодируется как число.

```
MethodDeclaration  → токен #1001
ReturnType         → токен #1002
ParameterList      → токен #1003
ReturnStatement    → токен #1004
BinaryExpression   → токен #1005
...
```

Размер словаря: ~200 типов узлов для C# (против 50000 для BPE). Это и есть **маленький датасет** — словарь в 250 раз меньше.

**Уровень 2 — Семантические токены (из Roslyn SemanticModel):**
Что именно означает узел в контексте программы.

```
Идентификатор "token" → {
  тип: string,
  область_видимости: параметр_метода,
  читается: 1 раз,
  записывается: 0 раз,
  нулевой_проверкой: да
}
```

**Уровень 3 — Связные токены (из GraphRAG):**
Какие другие части кодовой базы связаны с этим узлом.

```
Метод Validate →  вызывается из: [AuthService.Login, TokenMiddleware.Invoke]
                  похожие методы: [VerifyToken, CheckToken, IsValidToken]
                  зависит от: [string.IsNullOrEmpty, JwtDecoder.Decode]
```

### Маска внимания из дерева

Стандартный трансформер: каждый токен «смотрит» на все предыдущие токены. Это O(n²) внимания — дорого и неточно.

Наш вариант: токен «смотрит» только на:
- своего родителя в дереве (прямая связь вверх)
- своих детей в дереве (прямая связь вниз)
- своих соседей-братьев (одинаковый уровень дерева)
- связанные узлы из GraphRAG (вызовы, зависимости)

Это сводит O(n²) к O(n × глубина_дерева) — примерно O(n × 15) для типичного кода C#.

```
Обычное внимание для файла 500 токенов:
  500 × 500 = 250 000 пар

Дерево-внимание для файла 500 узлов AST:
  500 × 15  = 7 500 пар (в 33 раза меньше)
```

## Трек B — Документация: двухуровневый препроцессор

### Ключевая идея

Документация — это перевод кода в человеческий язык. Мы разбиваем это на два явно разделённых этапа:

**Этап 1 (детерминированный, без языковой модели):** Код → Нормализованное промежуточное представление. Как TypeScript → JavaScript транспиляция — точный, предсказуемый, тестируемый. На выходе — структурированный «протокол» что делает код, без синтаксиса языка программирования.

**Этап 2 (языковая модель):** Промежуточное представление → Человеческий текст. Модель обучается переводить с «протокола» на английский, а не с C# на английский. Это проще — промежуточное представление стандартизировано.

Аналогия: переводчик ООН не переводит напрямую с суахили на финский. Сначала на французский (lingua franca), потом с французского. Промежуточное представление — наш lingua franca.

### Этап 1 — Препроцессор кода в структурированный протокол

Правила перевода (детерминированные, без ML):

```
Входной C# код:
──────────────────────────────────────────────────────────────────
public async Task<AuthResult> LoginAsync(string email, string password)
{
    var user = await userRepository.FindByEmailAsync(email);
    if (user == null)
        return AuthResult.Failure("User not found");
    if (!passwordHasher.Verify(password, user.PasswordHash))
        return AuthResult.Failure("Invalid password");
    var token = jwtService.Generate(user);
    return AuthResult.Success(token);
}
──────────────────────────────────────────────────────────────────

Промежуточное представление (Intermediate Representation):
──────────────────────────────────────────────────────────────────
FUNCTION: LoginAsync
  ASYNC: true
  INPUTS:
    - email: text
    - password: text (sensitive)
  OUTPUT: AuthResult (success/failure union)

  STEPS:
    1. LOOKUP user FROM storage BY email
    2. IF user NOT FOUND:
         RETURN failure("User not found")
    3. IF password DOES NOT MATCH user.stored_password:
         RETURN failure("Invalid password")
    4. CREATE token FROM user USING jwt_generator
    5. RETURN success(token)

  DEPENDENCIES: [userRepository, passwordHasher, jwtService]
  SIDE_EFFECTS: none (читает, не пишет)
  ERROR_PATHS: [user_not_found, wrong_password]
──────────────────────────────────────────────────────────────────
```

Это промежуточное представление:
- Не зависит от языка программирования (работает для C#, Java, Python)
- Машинно-читаемо (можно проверять тесты против него)
- Человеко-читаемо (разработчик без знания C# понимает что делает функция)
- Стандартизировано (одинаковые паттерны дают одинаковое представление)

### Правила препроцессора (полный набор)

```
Правило 1: Каждая функция → блок FUNCTION с INPUTS, OUTPUT, STEPS
Правило 2: Каждый цикл for/foreach → ITERATE OVER [коллекция] DOING [тело]
Правило 3: Каждый if/else → IF [условие]: [ветка_true] ELSE: [ветка_false]
Правило 4: Каждый await → WAIT FOR [асинхронная_операция]
Правило 5: Каждый new → CREATE [тип] WITH [параметры]
Правило 6: Каждый throw → SIGNAL ERROR [тип_ошибки]: [сообщение]
Правило 7: Каждый репозиторий/сервис-вызов → LOOKUP/SAVE/DELETE FROM [хранилище]
Правило 8: Строковые операции → COMBINE/SPLIT/SEARCH IN text
Правило 9: Математические операции → COMPUTE [формула]
Правило 10: Return → RETURN [тип_успех/неуспех]([значение])
```

Реализация препроцессора: Roslyn CSharpSyntaxWalker — обход AST с применением правил. Детерминированный, тестируемый, без ML.

### Этап 2 — Маленькая языковая модель на промежуточном представлении

Модель обучается только переводить:
```
Входной токен:     LOOKUP user FROM storage BY email
Целевой текст:     "Look up the user record in the database using their email address"

Входной токен:     IF user NOT FOUND: RETURN failure(...)
Целевой текст:     "If no user is found with this email, return an authentication failure"
```

Это значительно проще чем обучать модель на сыром C#:
- Словарь промежуточного представления: ~150 ключевых слов
- Обучающих пар: ~500K функций с docstring (из CodeSearchNet)
- Параметров модели: 8–15M (очень маленькая)

### Двухуровневый граф хранения документации

```
GraphRAG для документации:
  Узел 1: Промежуточное представление функции LoginAsync
  Узел 2: Английский docstring LoginAsync
  Узел 3: Тест для LoginAsync
  Узел 4: Промежуточное представление FindByEmailAsync
  ...
  Рёбра: «LoginAsync вызывает FindByEmailAsync» (из Roslyn CallGraph)
         «LoginAsync описывается в» (ИР → docstring)
         «LoginAsync тестируется в» (функция → тест)
```

Когда нужна документация для новой функции:
1. Препроцессор → промежуточное представление (быстро, без модели)
2. GraphRAG → найти три похожие функции по промежуточному представлению
3. Маленькая LM → сгенерировать текст с контекстом похожих docstrings

## Трек C — Язык: технический домен (только английский)

### Ключевая идея

Общая языковая модель обучается на всём. Для дополнения технической документации нам нужна модель которая глубоко понимает **технический английский**: «the function returns a Task that resolves to an AuthResult», «implements the Repository pattern», «throws ArgumentNullException if input is null».

Мы загружаем **только технический контент** и получаем маленькую модель которая говорит как технический писатель, а не как беллетрист.

### Специальная обработка для технического языка

Технический английский отличается от обычного:
- Высокая плотность терминов: «the idempotent operation returns a cached result»
- Структурированные предложения: «If X, then Y. Otherwise Z»
- Ссылочные конструкции: «As defined in Section 3.2», «See also: IDisposable»
- Условные конструкции: «throws when», «returns null if», «succeeds provided that»

Специальный токенизатор для Трека C:

```
Стандартный BPE токенизатор разбивает:
  "ArgumentNullException" → ["Argument", "Null", "Exception"] (3 токена)
  "async/await" → ["async", "/", "await"] (3 токена)

Технический токенизатор Трека C:
  "ArgumentNullException" → 1 токен (это один концепт)
  "async/await" → 1 токен (это одна идиома)
  "returns null if" → 1 токен (устойчивая конструкция)
  "throws when" → 1 токен
  "implements the X pattern" → шаблонный токен
```

Это реализуется через расширение подпроекта 01 (Tokenizer): добавляем словарь технических составных токенов (~5000 составных терминов) перед стандартной BPE токенизацией.

### Как Трек C дополняет документацию (подключение к Треку B)

```
Пайплайн совместного использования Трека B и Трека C:

Трек B (Препроцессор):
  Код → Промежуточное представление → Черновик документации

Трек C (Языковая модель):
  Черновик + технический контекст → Финальная документация

Конкретно:
  1. Трек B генерирует:
     "Authenticates user by email and password. Returns success with token or failure."

  2. Трек C расширяет:
     "Authenticates a user by verifying their email address and password against stored
      credentials. On success, generates and returns a JWT Bearer token. Returns a failure
      result if the user is not found or if the password hash does not match.
      This method is asynchronous and follows the Repository pattern for user lookup.
      Throws ArgumentNullException if email or password is null."

  3. GraphRAG добавляет перекрёстные ссылки:
     "See also: LogoutAsync, RefreshTokenAsync, IUserRepository.FindByEmailAsync"
```

## Интеграционная цепочка: как три трека работают вместе

```
РАЗРАБОТЧИК ПИШЕТ КОД
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│  ТРЕК A — Понимание кода                                          │
│                                                                   │
│  Новая функция → Roslyn AST → Граф зависимостей                   │
│                              ↓                                    │
│                        GraphRAG поиск похожих функций             │
│                        «эта функция похожа на X, Y, Z»            │
└───────────────────────────┬───────────────────────────────────────┘
                            │  структурное понимание
```

## Проверяемые гипотезы (с конкретными числами)

### Гипотеза A1: AST токены сходятся быстрее BPE
**Проверка:** Обучить обе модели на 50K шагов. Сравнить перплексию на тестовой выборке кода.
**Ожидание:** Трек A достигает перплексии 15 за ~40K шагов, стандартный BPE — за ~200K шагов.
**Датасет:** 10K функций из The Stack (C#)

### Гипотеза A2: Дерево-внимание требует в 10–30× меньше памяти
**Проверка:** Профилирование пиковой памяти при batch=4, seq_len=512.
**Ожидание:** Стандартное внимание ~2.1 ГБ, дерево-внимание ~200–400 МБ.

### Гипотеза B1: Препроцессор правильно переводит 95%+ конструкций
**Проверка:** Ручная проверка 500 случайных функций.
**Ожидание:** 97%+ синтаксически корректных промежуточных представлений.

### Гипотеза B2: Двухуровневый пайплайн генерирует лучшие docstrings
**Проверка:** BLEU score на 5000 функциях из CodeSearchNet с эталонными docstrings.
**Ожидание:** Трек B: BLEU 0.39–0.43, стандартный LLM: BLEU 0.28–0.33.

### Гипотеза C1: Технический домен в 5× меньше данных даёт сравнимое качество
**Проверка:** Сравнить BLEU на техническом тексте: модель C (3 ГБ данных) vs GPT-2 small (40 ГБ).
**Ожидание:** Модель C сравнима или лучше GPT-2 на технических текстах при 13× меньшем датасете.
