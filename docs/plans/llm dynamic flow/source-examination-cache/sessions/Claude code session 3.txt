Here's the answer:

Projects 21-23 are the "agent runtime" layer — pure C# implementation of what OSS frameworks (LangGraph, LangChain, etc.) provide in Python. They contain no ML model weights, so the code dependency is on the algorithms and patterns, not on trained parameters.

21.AgentInfrastructure — the execution substrate:

Session/context state management
Token counting

ComplexTaskDecomposer (the same false-CONJ guard logic referenced in 29.SemanticCompiler)

AST-based relevance ranking with K-NN
NuGet: Microsoft.CodeAnalysis.CSharp only
23.OssEquivalents — replacements for Python OSS libraries:

MCP (Model Context Protocol) transport + tool dispatcher ← LangGraph equivalent
Roslyn-based code analysis
YAML skill-file parsing (YamlDotNet)
Prompt translation and beautification
State machine with SQLite checkpointing
NuGet: Microsoft.CodeAnalysis.CSharp, Microsoft.Data.Sqlite, YamlDotNet
The .NET constraint comes from two things:

Roslyn (Microsoft.CodeAnalysis.CSharp) — used in all three for C# AST parsing. In Python/TypeScript you'd use tree-sitter or ast-grep. In a Java runtime you'd use JavaParser.
SQLite via Microsoft.Data.Sqlite — the session state and MCP state machine use SQLite for persistence. This is purely a library choice, not a language-level constraint — Python has sqlite3 built-in and TypeScript has better-sqlite3.
Everything else (the OperationResult<T> envelope, ReAct loop, tool registry, context compaction, task decomposition) is algorithmic — it's portable to any language. The patterns themselves are language-agnostic; the implementation is just C# because that's the project language.
