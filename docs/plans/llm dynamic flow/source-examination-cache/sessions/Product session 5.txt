What this adds to the architecture
A new unit — call it the arbiter selector — sits between the result aggregator and the arbiter pool. It takes a result R_i (with its predicate sequence, its source domain, its source unit, and its execution metadata) and emits the K relevant arbiter identifiers from the pool. That gives the diagram a precise mirror at front and back:

Front of pipeline	Back of pipeline
DomainSplitter decides which domains apply to the user prompt → emits domain identifiers d1..dm	ArbiterSelector decides which arbiters apply to the result → emits arbiter identifiers a1..ak
Trained on (prompt → relevant domains) examples	Trained on (result → which arbiters caught issues) examples
Confidence below threshold = unknown domain → triggers DynamicDomains	Confidence below threshold = unknown failure mode → triggers training of a new arbiter
The two units are structurally identical. What I think you're describing
The whole pipeline graph stops being a static eight-step (or nine-step now) flow and becomes a flow graph that the system itself can edit. The diagram you sent earlier is no longer "the architecture" — it's "the current state of the flow graph at this moment." When a request comes in that the current graph can't handle well, the system:

Notices the gap (low confidence somewhere, missed arbiter, no relevant transformational prompt, unknown stack).
Looks for an existing solution locally — is there a unit already trained on a near-enough domain whose role is close to what's needed? Reuse it.
If nothing local fits, looks in the project repo / model marketplace / shared registry for a unit somebody else has already trained.
If nothing exists anywhere, searches for a relevant dataset online (Stack Overflow, GitHub, Microsoft Docs — the sources from the dataset-collection plan), compresses it through SemanticCompiler to the functional/predicate structure, trains a new unit on the compressed slice, validates it on a holdout, and inserts it into the flow graph.
The flow graph itself gets edited as a result — a new node is added, edges are rewired, the orchestrator now knows about the new capability for next time.
That's not an LLM pipeline anymore. That's a self-modifying agent network where the topology is data, not code.

Why I think this is correct (not just ambitious)
Three things make this realistic on this codebase rather than science fiction:

One — the unit interface is already uniform enough. Every unit takes a predicate sequence plus context metadata in, emits a predicate sequence (or identifier vector) plus confidence out. As long as a new unit conforms to that contract, the orchestrator doesn't care whether the unit was trained yesterday on a curated slice or downloaded ten minutes ago from a marketplace. The contract is the same. This is why the (unit × domain) grid was the right framing — it forced the units to be uniform first, which is the precondition for hot-swapping them.

Two — the SemanticCompiler is the bridge that makes external datasets ingestable. Any text corpus on the internet — GitHub repos, Stack Overflow Q&A, MS Docs, Wikipedia, anything — can be compressed through L0→L5 into the same 22-predicate space the units operate in. So "find a relevant dataset online" is not "and then figure out how to format it for our model" — it's "compress it through SemanticCompiler and you have training data in the right shape." The compression pipeline isn't just an inference optimization; it's also the universal-import format.

Three — the marketplace concept already has a precedent in the project. 17.DynamicDomains in the planning library is exactly this idea applied to one specific case (downloading a pre-trained adapter when an unknown domain shows up). What you're describing now is the same idea generalized to every unit type — not just "fetch a domain LoRA," but "fetch any (unit, domain) cell," "fetch any arbiter," "fetch any prompt library," "fetch any decomposer." 17.DynamicDomains was a special case; the new architecture is the general case.

What this means structurally
Five things change:

The flow graph becomes a stored artifact. Right now the pipeline shape is implicit in code (DomainSplitter calls SemanticCompiler calls EpisodeDecomposer calls...). For self-modification to work the graph needs to be data — a JSON document, a graph in the GraphRAG store from subproject 07, or a dedicated serialized format — that the orchestrator reads at startup and can edit at runtime. This is the same shift that turned Apache Airflow from "scripts that call each other" into "DAGs that workflows can edit." Subproject 07.GraphEngine + 08.GraphRAG already handle the storage layer; the new piece is the schema for "a flow node" and the runtime that walks the graph instead of a hardcoded pipeline.

Each unit in the graph carries its own metadata. Beyond just weights, each unit needs to declare: what predicate-shape it expects on input, what predicate-shape it emits, what (unit-role, domain) cell it fills, what version it is, what its provenance is (locally trained / downloaded from where / when), what its observed confidence distribution looks like. This is what lets the orchestrator pick the right replacement when one unit fails — it's matching on metadata, not on names.

The marketplace is just a registry over this metadata. A marketplace entry is {role, domain, predicate-input-shape, predicate-output-shape, weights-hash, training-corpus-summary, performance-baseline}. Local repo and marketplace are the same shape — the marketplace is just remote, and authentication / trust-scoring (TrustScorer from 14.ContinuousLearning) gates whether a downloaded unit actually gets installed. The same TrustScorer that decides "should we train on this Stack Overflow answer" also decides "should we install this third-party arbiter from the marketplace."

Gap detection becomes a first-class signal. Right now low confidence is a runtime warning. In this architecture, low confidence is the trigger that initiates the create-or-fetch loop. It's the equivalent of a cache miss — except instead of falling back to a slower path, it falls back to "look locally → look in marketplace → search for dataset → train new unit → install → retry." Each step in that fallback chain has its own confidence and time budget.

Training-on-the-flow becomes a regular event, not a rare one. Instead of a single overnight training run on accumulated feedback, the system might be training a new arbiter at 10am because something failed, downloading a new domain LoRA at 11am, retraining a decomposer at 2pm because feedback consistently shows it's bad on TypeScript. 16.AutonomousLearning's IdleDetector matters more than ever because some of these training jobs need to wait until the laptop is idle, but others are urgent enough to run immediately if the user is blocked.

The real architectural questions this opens
Three forks I want to flag before any of this becomes a plan, because they're substantive enough that the wrong default would lock us into a worse design:

Q1 — What is the contract that lets units be hot-swapped? For two units to be substitutable they need to agree on more than predicate vocabulary. They need to agree on: the role they play (decomposer, arbiter, applier), the operational pre/post-conditions of that role, and the failure modes they can produce. If the contract is just "predicate sequence in, predicate sequence out," the orchestrator can't tell whether a downloaded unit will actually behave correctly in the slot it's filling. This is the same problem that protocol versioning solves in distributed systems — but applied to neural units. Options range from a loose "name + version + interface signature" all the way to something formal like a declared input/output predicate-pattern with conformance tests. The right answer depends on how much we trust marketplace providers, which is a TrustScorer question we'd need to resolve before any unit gets installed automatically.

Q2 — What's the granularity of self-modification? The flow graph could be modified at three different levels of granularity:

Cell level: only individual (unit-role, domain) cells get added/replaced. The pipeline shape is fixed; only the contents of each box can change.
Edge level: connections between units can be rewired. New unit roles can be inserted into the graph. The arbiter loopback, for instance, could become "an arbiter-selector → arbiter-pool subgraph that the system inserted because operations showed it was needed."
Subgraph level: whole sub-flows can be added, replaced, or removed. A "DOCS generation" subgraph might be inserted as a parallel branch when the system notices repeated documentation requests.
Cell level is the safest start (it's what 17.DynamicDomains already does). Subgraph level is the most powerful but requires the orchestrator to reason about graph topology, not just node contents. Edge level is the middle ground and probably the right first target — it's enough to handle "we need to add the arbiter cluster" (your current example) but stops short of "the system rearranges its whole pipeline."

Q3 — Who's responsible when a self-installed unit produces bad output? This is the operational question that determines whether this works in practice. If the system installs a downloaded arbiter and it starts misjudging results, who notices and how? Three sub-questions:

Does every newly installed unit go through a probationary period where its outputs are evaluated against a holdout but its votes don't count? (My instinct: yes — TrustScorer-style staging.)
What's the rollback mechanism? If a unit is replaced and performance drops, does the previous version stay in the registry as a fallback? (My instinct: yes — version history, not just current state.)
What's the user-visible accountability story? Does the user ever know "we just installed a new arbiter to handle your TypeScript code"? (Open question — depends on how much agency you want the user to have over their own assistant.)

What the topology pattern already gives us
The flow graph in XIIGen is already data, not code. Every flow is a JSON contract at contracts/topologies/{FLOW}/{name}.topology.json that declares nodes, edges, iron rules, and quality gates. There are nine node handlers — rag-retrieve, decompose, ai-generate, multi-generate, arbiter-panel, validate, score, route, feedback — and they compose into any pipeline shape. Routing decisions inside the graph are themselves learnable: instead of hardcoded if/else, a route.handler reads from a graph query against xiigen-decision-graph, and the result of every routing decision flows back as a Phase F retrospective that updates the edge's confidence.

Three pieces of this directly answer your architectural ambitions:

The flow graph is already a stored artifact. Every topology contract has a topologyId, a flowId, a list of nodes with handler types, edges with conditions, iron rules that must hold, and quality gates. Adding a new flow is writing a new JSON file and registering it. Modifying an existing flow is editing the JSON. The graph schema for the flow itself is what gives us the "anything can be replaced" property — there's nothing in code that pins the topology shape; the orchestrator reads it at runtime.

The decision graph already supports learnable edges with confidence. The xiigen-decision-graph index has nodes (entity types like ARCHETYPE:ROUTING, ARBITER_ROLE:security) and edges with weight, confidence, observationCount, immutable, source, and reasoning fields. Edges seed at evidence-derived priors (not all 0.5), update on every observation via IGraphLearningService.updateEdge(), and have promotion paths — OPTIONAL → PROMOTED → REQUIRED at configurable observation thresholds. There's decay protection so 5 outliers can't override 30 good runs.

The four-tier decision classification keeps the system honest. Every decision in the architecture gets classified as boundary code (DNA invariant, hardcoded), FREEDOM config (tenant-tunable, no learning), GRAPH RAG (learnable through observations), or AI pipeline (requires contextual reasoning). The classification determines whether a piece is hardcoded, configurable, learnable, or generated. This four-way split is exactly the discipline that prevents "let's make everything learnable" sprawl.

LlmFromScratch's current DependencyGraph in 22.AgentAlgorithms is the much-simpler seed of all this — it knows about sequential vs parallel execution but doesn't yet know about graph-stored topology contracts, learnable edges, or confidence lifecycles. We need to grow it into the full topology pattern.

What changes when external AI becomes internal AI
This is the substantive shift. In XIIGen, two of the nine handlers (ai-generate and multi-generate) call external models — Claude, GPT, etc. The topology declares which model via FREEDOM config keys (AI_ENGINE, AI_OPENAI_PROVIDER), and the runtime makes an HTTP call. In LlmFromScratch, those handlers become calls to local trained units from the registry.

The handler set adapts to:

XIIGen handler	LlmFromScratch equivalent	What changes
ai-generate.handler	internal-unit.handler	Resolves (unit-role, domain) to a local unit, loads its weights, runs inference, returns result + confidence
multi-generate.handler	internal-multi-unit.handler	Runs N internal units (different versions, different cells) in parallel, blind-judges via swappability-judge or arbiter pool
arbiter-panel.handler	arbiter-pool.handler	Selects K arbiters via the arbiter selector unit (your last decision), runs them in parallel, aggregates votes
rag-retrieve.handler	unchanged	Retrieves from local indices — same shape

Mapping your three answers to this substrate
Answer 1 — RAG manages unit contracts plus a swappability-judge unit. This fits the existing xiigen-decision-graph pattern perfectly, but we need a sibling graph for the unit registry. Call it llm-unit-registry (the index name is just a label). Its entity types:

UNIT_ROLE:decomposer, UNIT_ROLE:applier, UNIT_ROLE:arbiter-selector, etc. (NODE)
DOMAIN:CODE_Q, DOMAIN:BUG, DOMAIN:LEGACY (NODE)
UNIT_CELL:decomposer-CODE_Q-v3 (NODE) — a specific trained version
UNIT_CELL --[FILLS]--> (UNIT_ROLE, DOMAIN) (EDGE) — which cell currently fills which role-domain slot
UNIT_CELL --[SUPERSEDES]--> UNIT_CELL (EDGE) — version chain
UNIT_CELL --[SWAPPABLE_WITH]--> UNIT_CELL (EDGE) — learned by the swappability judge
The SWAPPABLE_WITH edges are exactly what the swappability-judge unit produces. It's an internal-unit that takes (current-cell, candidate-cell, observed-context) and returns one of three verdicts — swappable, needs-additional-training, not-swappable — with confidence. Its training corpus is the history of past swap attempts plus their measured outcomes. It's a small unit like all the others; it learns from the FeedbackRouter signal.

The unit's metadata (predicate-input-shape, predicate-output-shape, performance-baseline, training-corpus-summary, weights-hash, version) lives as properties on the UNIT_CELL node. Looking up "what unit fills (decomposer, BUG) right now" is a graph query: MATCH (cell)-[:FILLS]->(role:UNIT_ROLE {name:'decomposer'}, domain:DOMAIN {name:'BUG'}) returning the cell node with all its properties. Looking up "what could replace this unit" is MATCH (cell)-[:SWAPPABLE_WITH {confidence: > threshold}]->(candidate) plus a swappability-judge call for the final verdict.

Answer 2 — anything can be replaced, managed in a database, internal AI throughout. The topology contracts are the database. Every flow is editable JSON. Every unit-cell is editable graph node. The orchestrator reads these at runtime; nothing is pinned in code beyond the nine handler implementations and the four-tier classification rules (which are boundary code by design).

The "internal AI" replacement is mechanical once internal-unit.handler is implemented. Rollback is moving the pointer back to a prior cell. History is reading the chain backward.

Per-unit performance measurement piggybacks on the existing two-step feedback pattern. When internal-unit.handler fires, the inline step records the call (which cell, what input, what output, what confidence) with outcomeClass: "PENDING". After enough observations, the system can detect that a cell is degrading (trust score dropping) and either flag it for retraining or auto-rollback to the prior version.

User examination becomes a UI over the registry: list active cells, show version history per cell, show training corpus summary and performance baseline for each version, show recent failures, allow "examine, retrain, replace, or roll back." What's actually new — the real work
Putting all three answers together, the new pieces beyond what the topology pattern already covers:

(1) The internal-unit.handler implementation. Replaces ai-generate.handler for internal-AI calls. Takes a config block like {"unitRole": "decomposer", "domain": "BUG", "input": "..."}, resolves to a cell via the registry, loads its weights (LoRA on shared base, or fully-trained small model — depends on Q1 from earlier), runs inference, emits result with confidence. Plus an internal-multi-unit.handler for the multi-cell parallel case.

(2) The llm-unit-registry graph schema. A sibling to xiigen-decision-graph (or its LlmFromScratch equivalent in 07.GraphEngine + 08.GraphRAG) — entity types for unit roles, domains, unit cells, and the four edge types: FILLS, SUPERSEDES, SWAPPABLE_WITH, TRAINED_FROM (cell ← training corpus). (3) The swappability-judge unit. An internal-unit (like all the others) trained to verdict on (current, candidate) pairs. Bootstrap data comes from manual labels initially (a small set of "obviously swappable" / "obviously not" pairs); then it learns from real swap attempts as they accumulate.

(4) The unit-cell version chain protocol. Standardized way to add a new cell version: register the new cell, run probationary period (trust score builds while shadow-running but votes don't count), promote to active by moving the FILLS edge, keep the old cell reachable via SUPERSEDES. Rollback reverses just the FILLS move.

(5) The gap-detection-and-fetch loop. When confidence at any node falls below threshold for a sustained pattern, this triggers: query registry for nearest existing cell → if none with sufficient match, query marketplace (TrustScorer-gated) → if none there, kick off AutonomousLearning's data-discovery and training. The loop terminates by either installing a cell (success) or registering a "capability gap" entity (failure, surfaces to user).

(6) Unit-cell trust scoring. Per-cell performance measurement that updates with every Phase F retrospective. Independent of the per-edge confidence in the decision graph — they're two different things. Edge confidence: "this routing decision was right." Cell trust: "this unit is performing well." A cell can have high trust but be on a wrong edge; an edge can have high confidence but the cell filling it could be degrading.
