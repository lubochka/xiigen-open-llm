## Проход 1 — разбор решения о ратификации кандидатов (решение 1) и решения о статусе правила честности (решение 13)

### Решение 1. Ратифицировать или отклонить двадцать две гипотезы-кандидата

**Суть решения (по программе, строка 1264).** Раунд проверки добавил к пятидесяти восьми принятым гипотезам двадцать два кандидата; ни один не ратифицирован. Цитата из программы: «Ратифицировать или отклонить двадцать две гипотезы-кандидата. Блокирует: счётчики документа, планирование работ по кандидатам, три первичные статуса клеток». Срочных внутри — три: кандидат про тихое схлопывание входов (гипотеза Г-П1-6), кандидат про сходимость правки по кругу (гипотеза Г-П2-6) и кандидат про честное молчание обученного юнита (гипотеза Г-П1-7).

**Что блокирует.** Счётчики документа (58 против 80), планирование работ по кандидатам, три первичные статуса клеток; через клеток-сирот — честность счёта первичных клеток (программа, строка 310: «две сироты из пяти лечатся одной ратификацией двух кандидатов уровня юнита и потока»).

**Свип по стоячим требованиям — три срочных кандидата поштучно.**

#### 1а. Кандидат «Много входов к одному выходу — тихое схлопывание» (гипотеза Г-П1-6) — ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ: ратифицировать

Дословный приказ Лубы определяет юнит так (файл «planning of testing.md», строка 5): «ILearningUnit — упрощенная матрица принимает домейн, строение векторов, строение выхода, и по входам выпускает Iquearable of results of requested input type **many->many**». Связь «многие ко многим» назначена приказом В ОБЕ стороны — это не пожелание проверки, это буква наряда.

Сама программа признаёт (строка 164, текст кандидата): «Определение юнита называет связь „многие ко многим" В ОБЕ стороны, а гипотезы проверяют только одну сторону — несколько законных выходов на один вход (гипотеза Г-П1-3). Обратная сторона не проверяется никем, хотя она опаснее». То есть без этого кандидата принятый список гипотез покрывает ровно половину дословного определения из приказа: сторона «один вход → много выходов» проверяется, сторона «много входов → не схлопываются в один выход» — нет.

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ.** Содержание кандидата прямо вытекает из дословного определения юнита в приказе; отклонить его — значит оставить половину буквы приказа непроверенной, а это не выбор владельца, а невыполнение уже отданного приказа. Кандидат ратифицируется в помеченном виде (со своим способом проверки и контрольной пробой, как записано в строке 164).

**Последствия.** Список гипотез юнита растёт с пяти до семи (вместе со вторым кандидатом ниже); покрытие дословного определения юнита становится полным по обеим сторонам «many->many».

**Условие опровержения.** Если Луба текущей незацитированной инструкцией изменит определение юнита (уберёт «many->many» или ограничит его одной стороной) — вердикт снимается и кандидат возвращается в очередь решений.

#### 1б. Кандидат «Обучение съедает честное молчание» (гипотеза Г-П1-7) — ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ: ратифицировать

Честность системы — не предложение программы, а уже действующее стоячее требование самого проекта, записанное в его обязательных правилах:

- Правило честности необученной системы (AGENTS.md, правило OP-56, строка 6483): заголовок — «OP-56 — Untrained Model Honesty Gate: a skeleton must be tested to prove it is honest» (гейт честности необученной модели: каркас обязан быть ПРОТЕСТИРОВАН на честность). Тело правила (строки 6485–6501) требует доказать пять свойств, среди них «honest status — it returns not_ready_*» (честный статус «не готов») и «honest host degrade — … the user sees an honest degraded/not-ready response, not a confident wrong one» (пользователь видит честный ответ «не готов», а не уверенный неверный).
- Паттерн «честность необученного против готовности обученного» (CLAUDE.md репозитория, строка 3130: «## Untrained honesty vs trained readiness pattern») с обязательным различением двух состояний зачёта, включая состояние «честный необученный каркас» (метка PASS_AS_HONEST_UNTRAINED_SCAFFOLD, там же, строка 3135; в AGENTS.md — строка 6505). Тот же паттерн прямо называет обратный обман — выдачу каркаса за обученную способность — самым опасным ложным положительным исходом проекта.

Из этих правил следует: честность — сквозное, обязательное и ИЗМЕРЯЕМОЕ свойство («протестировать», не «предположить») на всём жизненном цикле системы. Кандидат (программа, строка 166) закрывает ровно ту дыру, которую эти правила не позволяют оставить: «Честное „не готов" проверяется программой только у НЕОБУЧЕННОГО каркаса (гипотеза Г-П1-4), а матрица … и сквозные тесты комбинаций … ждут честного „не готов" от уже ОБУЧЕННОГО юнита на непосильных ему составных случаях — и это ожидание не покрыто ни одной гипотезой». Уверенный неверный ответ обученного юнита на непосильном случае — это в точности запрещённое правилом OP-56 состояние «confident wrong one», только на следующей ступени жизненного цикла; стоячее требование честности не имеет оговорки «действует лишь до первого обучения».

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ.** Кандидат — измерительный инструмент, без которого стоячее требование честности на обученном состоянии остаётся требованием без замера. Ратифицировать в помеченном виде (способ проверки и опровержение записаны в строке 166).

**Последствия.** Закрывается одна из пяти клеток-сирот (клетка юнита на оркестрации задач — программа, строка 310); требование честности получает замер на всех шести сквозных тестах.

**Условие опровержения.** Только явное текущее решение Лубы, отменяющее честность как измеряемое свойство (что одновременно потребовало бы правки правила честности в AGENTS.md — то есть отдельного явного приказа).

#### 1в. Кандидат «Правка по кругу: сходится ли поток» (гипотеза Г-П2-6) — ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ: ратифицировать

Двойное основание.

*Основание первое — дословный приказ.* Файл «planning of testing.md», строка 6: «IlearnyngFlow — это взаимоотношение между юнитами, для коррекции входа **в** выход». Коррекция «входа в выход» — это по букве приказа процесс, обязанный ДОЙТИ до выхода: правка, которая гоняет расхождение по кругу и до выхода не доводит, коррекцией входа в выход не является. Вопрос «сходится ли многошаговая правка» — не новое ожидание, а прямая проверка того, что определение из приказа вообще выполняется.

*Основание второе — принятый текст самой программы.* Принятая программа — тоже стоячее требование. Первичная клетка потока на макетах — цикл, и принятый сквозной тест домена макетов уже требует ровно этого замера. Программа, строка 202 (текст кандидата): «первичная клетка потока на фигме — это ЦИКЛ, и сквозной тест того домена (§4-Д3) прямо требует ответа, „уменьшают ли правки расхождение шаг за шагом или гоняют его по кругу" и укладывается ли цикл в заранее ограниченное число шагов; уровнем потока это ожидание не покрыто ничем». И строка 310 (клетки-сироты): «Поток на фигме — клетка ПЕРВИЧНАЯ, её ожидание есть цикл, а все пять принятых гипотез уровня потока описывают одну правку; сходимость цикла покрыта лишь непринятым кандидатом „Правка по кругу"». Без ратификации первичная клетка потока меряет ожидание, которого нет ни в одной принятой гипотезе, — что нарушает и внутреннее правило программы (решение 16 той же очереди), и здравый смысл замера.

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ.** Кандидат держит уже принятое требование сквозного теста домена макетов и букву определения потока из приказа; ратифицировать в помеченном виде.

**Последствия.** Закрывается вторая из двух клеток-сирот, лечимых ратификацией (первичная клетка потока на макетах получает несущую гипотезу); лестница домена макетов перестаёт опираться на непокрытое ожидание.

**Условие опровержения.** Явное текущее решение Лубы, что сходимость цикла не входит в предмет программы, либо правка принятого сквозного теста домена макетов, убирающая вопрос о правках по кругу.

#### 1г. Остальные девятнадцать кандидатов — РЕШЕНО-АРХИТЕКТУРНО: ратифицировать всех единым правилом, в помеченном виде

Поштучный разбор девятнадцати кандидатов в этот проход не входит (граница времени прохода). Вместо него — одно архитектурное решение о ПРАВИЛЕ ратификации.

**Альтернативы.** (а) Ждать поштучного решения владельца по каждому из девятнадцати; (б) отклонить всех скопом; (в) ратифицировать всех скопом единым правилом с условиями.

**Инварианты.** Ни одна строка принятого текста не переписывается; счётчики документа правятся только отдельной будущей работой; кандидат не может противоречить принятой гипотезе; у кандидата обязан быть способ проверки; статус «кандидат, добавлен проверкой» сохраняется в тексте как история.

**Выбранный путь — (в), ратифицировать всех в помеченном виде.** Правило: кандидат считается ратифицированным, если он (1) не противоречит ни одной принятой гипотезе, (2) имеет записанный способ проверки, (3) помечен вердиктом раунда проверки. Все двадцать два кандидата созданы самим раундом проверки именно в таком виде, и итог раунда прямо это удостоверяет — программа, строка 1318: «**Программа проверена и размечена. Исполнение возможно после решений владельца и этапа сборки наборов. Гипотезы годны к ратификации в помеченном виде.**» Смысл вердикта раунда и есть: кандидаты готовы к принятию как есть, с их пометками и способами проверки.

**Отклонённые пути.** Путь (а) отклонён: каждый кандидат закрывает дыру, найденную сверкой с принятым текстом или приказом, — то есть отвечает на уже существующее требование, и поштучное ожидание владельца здесь плодит очередь без нового содержания; правило аджюдикации запрещает возвращать владельцу то, что отвечено стоячим требованием. Путь (б) отклонён: скопное отклонение оставило бы найденные проверкой дыры (включая три срочных выше) незакрытыми без какого-либо основания.

**Последствия.** Счёт гипотез к исполнению: восемьдесят (пятьдесят восемь принятых раундом сбора плюс двадцать два ратифицированных кандидата); пересчёт счётчиков в тексте программы — отдельная будущая работа, до неё числа «58» и «21» в программе читаются как исторические с пометкой.

**Условие опровержения.** Если при подготовке правки программы обнаружится кандидат, нарушающий любое из трёх условий правила (противоречие принятой гипотезе, отсутствие способа проверки, отсутствие пометки вердикта), — он выпадает из скопной ратификации и возвращается отдельной строкой решения; выпадение одного не рушит ратификацию остальных.

**Итоговый вердикт решения 1: три срочных кандидата — ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ (ратифицированы поштучно, с цитатами); остальные девятнадцать — РЕШЕНО-АРХИТЕКТУРНО (ратифицированы единым правилом, с условием опровержения). Решение полностью снято с очереди владельца.**

### Решение 13. Статус правила честности

**Суть решения (по программе, строка 1288).** Цитата: «Признать честность сквозным свойством оси качества с обязательным замером в каждой клетке — или отклонить. Сегодня правило живёт в трёх местах с тремя разными статусами; шестнадцатый проход выровнял их до „предложение, ждущее решения владельца". Блокирует: условие успеха этапа базовых замеров и восемь мест, где вырожденный вечный отказчик побеждает».

**Что блокирует.** Условие успеха этапа базовых замеров; восемь мест программы, где система, всегда отвечающая «не готов», формально побеждает (вырожденный вечный отказчик).

**Свип по стоячим требованиям.** Честность как обязательное и измеряемое свойство УЖЕ является стоячим требованием проекта — программе не оставлено выбора «признать или отклонить», ей оставлено только привести себя в согласие с каноном репозитория:

- AGENTS.md, правило OP-56, строка 6483: «Untrained Model Honesty Gate: a skeleton must be tested to prove it is honest» — честность не предполагается, а ДОКАЗЫВАЕТСЯ тестами; строки 6485–6489: необученное состояние — «ALLOWED honest state. It is not allowed to be an UNTESTED state» (разрешённое честное состояние, но не разрешённое непроверенное состояние).
- CLAUDE.md репозитория, строка 3130: паттерн «Untrained honesty vs trained readiness» — два различаемых состояния зачёта; честный необученный каркас — настоящая веха, но не рабочая способность; выдача одного за другое — «класс маскарада», самый опасный ложный положительный исход.
- Тот же канон (раздел «No Dishonest Answers / Evidence-Bound Claims» в CLAUDE.md репозитория) делает честность утверждений сквозным законом всей работы по проекту — от кода до отчётов.

Поскольку правило честности связывает проект НЕЗАВИСИМО от программы, статус «предложение, ждущее решения владельца» внутри программы — это рассинхронизация с каноном, а не открытый выбор: отклонение честности означало бы, что программа меряет качество системы, которой канон проекта запрещает быть нечестной, не меряя запрещённое свойство.

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ.** Честность признаётся сквозным свойством оси качества с обязательным замером в каждой клетке. Три места программы с тремя статусами при будущей правке выравниваются до статуса «принято по стоячему требованию проекта» (сама правка — отдельная будущая работа; этот реестр текст не трогает).

**Обязательная оговорка к последствиям — вырожденный вечный отказчик.** Признание честности замером НЕ означает, что вечный отказ побеждает: канон различает два состояния зачёта — «честный необученный каркас» (метка PASS_AS_HONEST_UNTRAINED_SCAFFOLD; AGENTS.md, строка 6505) прямо объявлен «NOT a working feature» (не рабочей способностью). То есть замер честности обязан идти ПАРОЙ с замером умения и не может его заменить — ровно это лечит восемь мест, где отказчик побеждал: он выигрывает ось честности и проигрывает ось умения, и сводный отчёт обязан показывать обе. Согласование конкретных восьми мест и условия успеха этапа базовых замеров — работа будущей правки программы; переопределение клетки юнита на оркестрации задач как клетки честности — соседнее решение той же очереди (решение 17, проход 4).

**Последствия.** Разблокируется условие успеха этапа базовых замеров (честность входит в него как обязательная ось с парным замером умения); кандидат про честное молчание обученного юнита (гипотеза Г-П1-7, разбор 1б выше) получает статус несущей гипотезы этого требования; двойной канон «три места — три статуса» получает единый источник истины.

**Условие опровержения.** Только явный текущий незацитированный приказ Лубы, отменяющий честность как измеряемое свойство для этой программы; такой приказ одновременно вступил бы в противоречие с правилом честности в AGENTS.md (правило OP-56) и потребовал бы его явной правки — на что этот реестр указывает заранее.

**Что блокирует.** Этап первичных замеров во всех шести доменах.

**Свип по стоячим требованиям.** У проекта есть ДЕЙСТВУЮЩИЕ прецеденты порогов — не мнения, а числа, живущие в коде и в принятых решениях:

- Гейт приёмки обученного чекпойнта (метка G3; решение об адъюдикации DEC-03, пункт 6) — файл обучения китайской модели (09.09.26WorkLeft-02-teaching-chinese-model.md), строка 389: «доля побед над baseline ≥ 0,55 при N ≥ 200 отложенных примеров; при 50 ≤ N < 200 — биномиальный тест c(N) с p < 0,05; при N < 50 приёмки нет; абсолютный пол точности 0,75. Это число уже в коде». Числа подтверждены кодом: файл механики обучения (09.09.26WorkLeft-MECH-01-mechanism-validation.md), строка 742: `CanonicalMinimumBaselineWinRate = 0.55d`, `CanonicalAbsoluteAccuracyFloor = 0.75d`; строка 755: у перевода `gateThreshold = 0.75`.
- Гейт новизны домена перевода — CLAUDE.md репозитория, строка 2960: «The novelty gate remains strict `newPattern > (1 - maxAccuracy) AND seenTokens < maxAccuracy`» (гейт новизны остаётся строгим); тот же порог продублирован в каноне папки — файл обучения китайской модели, строка 393. Это прецедент порога-ФОРМУЛЫ: число не назначено из головы, а выводится из текущей измеренной точности модели.
- Прецедент калибровки: запертое решение о внешней помощи (номер D-14 в реестре запертых решений, docs/DECISIONS-LOCKED.md репозитория, строка 20) прямо записывает происхождение порога уверенности: «E51A/E51B calibrated the 0.50 confidence boundary» (опыты пятьдесят один А и Б откалибровали границу уверенности 0,50) — граница не выдумана, а снята двумя опытами.
- Предостерегающий прецедент: опыт гейта уверенности (номер E46 в карте результатов опытов, docs/EXPERIMENT-RESULTS-MAP.md репозитория, строка 64): «data too separable, both thresholds achieve 1.00» (данные слишком разделимы, оба порога дают единицу) — порог, назначенный без замера данных, может оказаться неразличимым и бессмысленным.

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ (пороги, у которых есть прецедент проекта) + РЕШЕНО-АРХИТЕКТУРНО (процедура для остальных).**

*Часть первая — прецеденты как стартовые значения.* Там, где клетка программы меряет то же, что уже меряет проект, стартовое значение порога берётся из прецедента: приёмка обученного состояния — гейт приёмки чекпойнта (доля побед не ниже 0,55; абсолютный пол точности 0,75; биномиальная лестница по числу отложенных примеров); порог новизны при записи чекпойнта — формула новизны перевода. Это не новые числа программы, а уже действующие требования проекта, которые связывают всякую работу по нему независимо от программы.

*Часть вторая — процедура для порогов без прецедента.* Выдумывать недостающие числа из головы запрещено самим устройством прецедентов проекта: его собственные пороги калибровались опытами (граница 0,50), а неоткалиброванный порог давал бессмысленный итог (опыт E46). Поэтому архитектурно назначается ПРОЦЕДУРА, а не числа: стартовое значение каждого порога без прецедента снимается на этапе базовых замеров из нуля прибора той же клетки (решение о поле шума, номер 3 этой очереди) по правилу «порог = пол шума × запас», запас — два.

**Альтернативы (по величине запаса).** Полтора — отклонено: оставляет меньше одной ширины шума между порогом и полом; сам пол оценён всего двумя замерами, то есть грубо, и при такой ошибке оценки пограничные исходы читались бы то так, то эдак. Три — отклонено как стартовое: чрезмерный запас выбрасывает настоящие улучшения и удорожает программу, потому что каждое «недоказанное» улучшение требует дополнительных проб, а каждая проба стоит ручной разметки (связь со сметой по разметке, решение 6 ниже). Два — выбрано как наименьший запас, при котором различие обязано превысить шум на целую его собственную величину (классический признак различимости); значение стартовое и пересматривается по фактическим разбросам после этапа базовых замеров — путь обратим.

**Инварианты.** Ни одно число не назначается мнением; каждый порог обязан иметь записанный источник (прецедент проекта или пол шума своей клетки) и момент назначения (этап базовых замеров); порог без источника не существует — прямое следствие правила «до и после» (правило семь, CLAUDE.md репозитория, строки 958–961): «No metric = not done» (нет метрики — не сделано).

**Последствия.** Решение перестаёт блокировать этап первичных замеров: у каждого порога появляются источник и момент получения числа, владельцу не остаётся ни одной догадки. Вписывание конкретных значений в текст программы — работа этапа базовых замеров и будущей правки, не этого реестра.

**Условие опровержения.** Явное текущее число от Лубы для любого порога перекрывает и прецедент, и процедуру (Первый Закон проекта). Если на этапе базовых замеров пол шума какой-то клетки окажется так велик, что «пол × два» превышает правдоподобную величину эффекта, — клетка не «проходит молча», а поднимается отдельной строкой решения: порог недостижим этим инструментом, чинить надо инструмент, а не подгонять порог.

### Решение 3. Нуль прибора (пол шума) на этапе базовых замеров

**Суть решения (по программе, строка 1269).** Цитата: «Нуль прибора (пол шума) снимается на этапе базовых замеров для каждой клетки. Блокирует: девять экспериментов из двенадцати, у которых сегодня есть законный исход „различие меньше пола шума", для которого не написано, что он означает. Самая выгодная починка документа по отношению пользы к цене. Срочно.»

**Что блокирует.** Девять экспериментов из двенадцати.

**Свип по стоячим требованиям.**

- Правило «до и после» (правило семь «Test-before-after», CLAUDE.md репозитория, строки 958–961): «Every placement in a plan has a metric that can be measured before and after the change… No metric = not done» (у каждой правки — метрика, измеримая до и после; нет метрики — не сделано). Метрика, у которой неизвестно различимое расхождение, НЕ может показать «до и после»: любые два числа чем-то да отличаются, и без пола шума «стало лучше» неотличимо от дрожания прибора. Значит нуль прибора — не пожелание программы, а прямое следствие уже действующего правила проекта.
- Вердикт самого раунда проверки (программа, строка 1211): «Нуля прибора нет нигде… Это самая дешёвая починка документа: одна величина, снятая на этапе базовых замеров, закрывает девять экспериментов сразу.»

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — да, снимать.** Стоячее требование обязывает метрику быть различимой; конкретная процедура съёма — архитектурный выбор, записан ниже.

**Процедура (назначена архитектурно).** На этапе базовых замеров для каждой клетки одно и то же неизменённое состояние (необученный каркас либо замороженный чекпойнт) прогоняется дважды тем же судьёй на том же отложенном наборе; расхождение двух прогонов и есть пол шума этой клетки. Если прогон детерминирован и оба замера совпадают дословно, пол снимается по расхождению двух независимых разметок одного и того же выхода (второй человек — решение об исполнителе и втором человеке, номер 12 этой очереди). Пол шума и оба сырых замера записываются в паспорт клетки рядом с тремя осями; при смене судьи или набора пол снимается заново. Всякое различие «до и после», меньшее пола, читается единственным образом: «неразличимо этим прибором» — не улучшение, не ухудшение и не подтверждение равенства.

**Последствия.** Девять экспериментов получают определённый смысл исхода «различие меньше пола шума»; утверждения о равенстве («асинхронность не меняет качества», отрицательные контрольные клетки) перестают подтверждаться тем же исходом, что и слепой замер; решение о порогах (номер 2 выше) получает источник стартовых значений.

**Условие опровержения.** Если для какой-то клетки двойной замер неисполним по цене (двойная разметка слишком дорога), клетка честно записывает «пол шума не снят, различимость неизвестна» и не участвует в утверждениях «лучше/хуже», пока пол не снят; дешёвую замену процедуры для такой клетки назначает будущая правка, не этот реестр.

### Решение 4. Курс обмена «сколько качества стоит сколько времени»

**Суть решения (по программе, строка 1270).** Цитата: «Курс обмена „сколько качества стоит сколько времени". Блокирует: условие успеха этапа потока, карту оправданности и всякое употребление слова „окупилось". Альтернатива — не произносить это слово и писать обе величины парой.»

**Что блокирует.** Условие успеха этапа потока; карту оправданности; всякое употребление слова «окупилось».

**Свип по стоячим требованиям.** Стоячего курса обмена нет нигде: ни в приказах, ни в каноне папки, ни в проекте — свип порогов решения 2 это подтвердил: все найденные прецеденты проекта суть пороги качества и приёмки, ни один не обменивает качество на время. Но сама программа записала безопасную альтернативу прямо в тексте решения (строка 1270): «не произносить это слово и писать обе величины парой» — и эта альтернатива не требует ни одного числа.

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — принять альтернативу пары.**

**Альтернативы.** (а) Назначить курс архитектурно — отклонено: сколько минут владелец готов платить за долю качества, есть чистое продуктовое предпочтение, и архитектор, называющий это число, подменял бы владельца (запрет на изобретение владельческих выборов из метода этого реестра). (б) Оставить блокированным до числа владельца — отклонено: записанная в программе альтернатива снимает блокировку без числа. (в) Пара величин — выбрано.

**Выбранный путь.** Условие успеха этапа потока и карта оправданности пишутся парой (изменение качества; изменение времени) без свёртки в одно слово; слово «окупилось» под запретом, пока курс не назначен владельцем. Путь полностью обратим: Луба вправе в любой момент назначить курс одним числом, и пары сворачиваются автоматически.

**Последствия.** Условие успеха этапа потока и карта оправданности разблокируются немедленно; из очереди владельца решение уходит (владелец возвращает его одним словом, когда захочет назначить курс).

**Условие опровержения.** Явно названный Лубой курс обмена; либо обнаружение в канонах действующего курса — свип его не нашёл; если найдётся, вердикт меняется на ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ с цитатой.

### Решение 5. Бюджет измерений и вытекающее число клеток

**Суть решения (по программе, строка 1271).** Цитата: «Бюджет измерений и вытекающее из него число клеток. Блокирует: решение о том, сколько клеток программа реально может закрыть.»

**Что блокирует.** Решение о том, сколько клеток программа реально может закрыть.

**Свип по стоячим требованиям.** Сначала проверено, не отвечают ли на решение соседи по очереди. Порядок работ по донорам (решение 21, программа, строка 1299: «первичные клетки документации C# — первыми; … документация Angular и SQL не открываются, пока донор не закрыт починенным замером») задаёт, ЧТО делать раньше чего, — без единого рубля и часа. Смета по ручной разметке (решение 6 ниже) задаёт, В ЧЁМ мерить цену клетки. Вместе они отвечают на «что сначала и почём за клетку», но НЕ на «сколько всего платим». Само число ниоткуда не выводимо: бюджет — внешний ресурс владельца (её время и деньги на ручную разметку), а не свойство репозитория или канона; ни одно стоячее требование ни в папке, ни в проекте не называет бюджета измерений — свип порогов и запертых решений нашёл только пороги качества, ни одного бюджета. Любое число от архитектора было бы догадкой о чужих ресурсах — ровно тем, что запрещено правилом о невыдумывании владельческих выборов.

**Вердикт: ОСТАЁТСЯ-ВЛАДЕЛЬЦУ — но с архитектурной смягчающей рамкой, снимающей блокировку старта.**

**Смягчающая рамка (назначена архитектурно).** Работа стартует по порядку доноров (решение 21) БЕЗ назначенного бюджета: первые клетки упорядоченного списка исполняются, пока владелец молчит. Бюджет, когда он будет назван, не перекраивает программу — он лишь обрезает хвост списка. Владельцу остаётся ровно ОДНО число: сколько клеток (или часов ручной разметки — в валюте решения 6) оплачивается. До его назначения ни одна работа не блокирована; после — список обрезается по нему.

**Последствия.** Решение перестаёт блокировать старт: вопрос «сколько клеток программа может закрыть» превращается из предусловия в отсечку хвоста; очередь владельца по этой группе сокращается до одного числа.

**Условие опровержения.** Если Луба назовёт бюджет до старта — рамка не нужна, список режется сразу. Если обнаружится стоячий бюджет (например, записанный приказом лимит часов) — вердикт меняется на ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ с цитатой; свип такого лимита не нашёл.

### Решение 6. Смета по ручной разметке, а не по числу прогонов

**Суть решения (по программе, строка 1272).** Цитата: «Смета считается по ручной разметке, а не по числу прогонов. Блокирует: осмысленность любого сокращения программы — сокращать надо число клеток, а не число проб внутри клетки.»

**Что блокирует.** Осмысленность любого сокращения программы.

**Свип по стоячим требованиям.** Это не выбор вкуса, а прямое следствие измеренной раундом проверки находки — итог проверки (программа, строка 1213): «почти вся цена сидит в ручной разметке, а не в прогонах машины». Смета по прогонам мерила бы дешёвую часть и не видела бы дорогую — то есть не была бы сметой.

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — принять.** Смета программы считается в единицах ручной разметки (часы разметчика или число размечаемых примеров); машинные прогоны — второстепенная строка сметы, не её основание. Сокращение программы делается сокращением числа клеток, а не проб внутри клетки — как записано в самом решении. Валюта единственного числа владельца (решение 5 выше) — та же.

**Альтернативы.** Смета по числу прогонов — отклонено: мерит не ту цену. Двойная смета с равным весом — отклонено: усложнение без пользы; по находке итога (строка 1213) машинная часть много дешевле, ей достаточно второстепенной строки.

**Последствия.** Всякое будущее сокращение программы сравнивает клетки по цене разметки; бюджет владельца (решение 5) получает валюту.

**Условие опровержения.** Если будущий измеренный факт покажет, что главной ценой стало машинное время (например, длинные прогоны обучения на больших наборах), смета получает вторую равноправную ось — решением той будущей правки, с записанным замером.

## Проход 3 — группа расщеплений строк (решения 7, 8, 9) и два носителя из группы внешних опор (решения 22 и 24)

### Решение 7. Расщепление строки перевода по направлениям

**Суть решения (по программе, строка 1276).** Цитата: «Расщепление строки перевода по направлениям (английский→русский и русский→английский — два разных ученика с двумя отложенными наборами). Блокирует: этап первичных замеров перевода, который сегодня планирует среднюю кривую двух разных учеников; спорит с правилом „один отложенный набор на все ступени"».

**Что блокирует.** Этап первичных замеров перевода — сегодня он планирует среднюю кривую двух разных учеников.

**Свип по стоячим требованиям — практика самого проекта.** Домен перевода в репозитории УЖЕ устроен по направлениям, это не предложение программы, а действующая архитектура и действующие наборы:

- Контракт адаптера направления (файл адаптеров направлений перевода, 27.TranslationDomain/TranslationDirectionAdapters.cs, строка 18): «ITranslationDirectionAdapter is the executable cell for one translation direction» (исполняемая клетка ОДНОГО направления перевода); строка 22: «Direction identifies which of the four supported pairs this adapter handles» (направление называет, которую из четырёх поддерживаемых пар обслуживает адаптер); обученный адаптер именуется по направлению (строка 102: имя адаптера строится как «trained-направление»).
- Перечень направлений — отдельные значения с собственными комментариями (файл контрактов перевода, 27.TranslationDomain/TranslationContracts.cs, строки 20–26): русско-английское направление (RU_EN) и англо-русское (EN_RU) — два разных значения перечисления, не одно.
- Наборы в репозитории направленные: обучающие пакеты русско-английского направления (27.TranslationDomain/TrainingData/ru-en-general-l1-b029-phrase-repair-train-ready.jsonl и ru-en-product-prompt-b001-train-ready.jsonl) и НАПРАВЛЕННЫЙ отложенный набор (tr-ho-ru-en-product-heldout-v1.jsonl) лежат рядом с общими отложенными наборами — то есть проект реально вёл и обучение, и отложенную проверку по направлению.
- Сама программа уже назвала болезнь (строка 323, пометка к строке юнита, часть о переводе): «домен объявляет два направления перевода двумя разными учениками, а клетка одна и кривая одна — средняя кривая быстрого и медленного есть кривая никого».

**Спор с правилом «один отложенный набор на все ступени» — разрешается уточнением, не отменой.** Правило записано в программе (строка 488): при добавлении нового законного эталона «все прежде снятые ступени лестницы пересчитываются, иначе нарушается правило „один отложенный набор на все ступени"». Смысл правила — сопоставимость: все ступени ОДНОЙ лестницы меряются одним и тем же замороженным набором. Но лестница принадлежит ученику; при двух учениках лестниц две, и у каждой — свой единственный замороженный набор на все её ступени. Уточнённая формула: «один отложенный набор НА НАПРАВЛЕНИЕ на все ступени». Инвариант правила (ни одна ступень не меряется другим набором, чем соседняя ступень той же кривой) сохраняется в каждой лестнице полностью; отменой было бы «у одной лестницы два набора» — этого расщепление не создаёт.

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ (расщепить: так уже устроен сам домен перевода в проекте — направленные адаптеры, направленные обучающие и отложенные наборы) + РЕШЕНО-АРХИТЕКТУРНО (уточнение правила отложенного набора до «на направление»).**

**Последствия.** Этап первичных замеров перевода планирует две кривые вместо одной средней; отложенных наборов у домена становится два (по одному на направление), цена набора меряется в валюте разметки (смета — решение 6) и режется бюджетом владельца (решение 5); строк матрицы не прибавляется — направление становится осью внутри строки перевода; пересчёт счёта клеток передаётся поправке счёта (решение 14, проход 4).

**Условие опровержения.** Явное текущее слово Лубы «одна кривая». Либо если этап сборки наборов покажет, что для второго направления отложенный набор собрать нечем (нет материала), — это направление честно помечается «не меряется», а не усредняется с первым.

### Решение 8. Расщепление документации Angular по осям тел и связей

**Суть решения (по программе, строка 1277).** Цитата: «Расщепление строки документации Angular по осям тел и связей. Блокирует: правильность статуса клетки — по телам она производная, по связям первичная, потому что перенос не может предсказать того, чего у донора нет».

**Что блокирует.** Правильность статуса клетки документации Angular.

**Свип по стоячим требованиям.** Основание даёт сам принятый текст программы, и он же даёт прецедент формы записи:

- Пометка к строке юнита (программа, строка 323, часть об Angular): «Статус „производная" верен для тел и неверен для связей: перенос не может предсказать то, чего у донора нет, поэтому по оси связей это первичная клетка без первичного замера». Донор — документация C#; межкомпонентных связей Angular у C#-донора нет, переносить нечего.
- Прецедент двухосного статуса УЖЕ существует в программе: та же пометка (строка 323, часть об оркестрации задач) читает клетку юнита на оркестрации задач «по оси честности … первичная» при производности по оси умения, и соседнее решение очереди о переопределении этой клетки (решение 17, строка 1292) прямо использует форму «первичная по оси честности, производная по оси умения». Двухосный статус — применяемая форма записи программы, не новшество.
- Материал для первичного замера связей уже запланирован этапом сборки: перечень эталонных сущностей шести доменов включает «перечень связей Angular» (программа, строка 1039).

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — расщепить СТАТУС клетки по осям, не строку.** Тела — производная ось (донор — документация C#, по порядку доноров из решения 21); связи — первичная ось с собственным замером на замороженном перечне связей из этапа сборки. Строка домена в матрице остаётся одна.

**Альтернативы.** (а) Полное расщепление на две строки матрицы — отклонено: две строки означают два отложенных набора, две лестницы и двойную разметку (валюта — решение 6), при том что тела и связи живут на ОДНИХ и тех же примерах-компонентах; вторая строка по оси тел была бы чистым дублем переносной клетки. Ось статуса даёт ту же честность за один набор. (б) Оставить клетку целиком производной — отклонено стоячим текстом программы: перенос не может предсказать связи, которых у донора нет; это оставило бы первичное ожидание без первичного замера.

**Последствия.** Статус клетки становится парой по осям; счёт первичных клеток растёт на одну по оси связей — передаётся поправке счёта (решение 14, проход 4); формулировка «первичная клетка без первичного замера» перестаёт быть правдой: замер назначен (перечень связей, заморозка, второй человек — по общим правилам этапа сборки, решение 10).

**Условие опровержения.** Если при сборке перечня связей Angular окажется, что связи не извлекаемы человеком, не видевшим систем (нет материала), — ось связей честно помечается «не меряется», а не подменяется производным статусом. Полное расщепление на две строки возвращается только явным словом Лубы.

### Решение 9. Расщепление домена SQL: крест «запрос/процедура × короткий/длинный»

**Суть решения (по программе, строка 1278).** Цитата: «Раскладка по виду и раскладка по длине меряют одну общую тень (процедуры длиннее по построению); нужен крест из четырёх согласованных групп — короткий запрос, длинный запрос, короткая процедура, длинная процедура. Блокирует: осмысленность гипотезы „Короткий запрос и длинная процедура — два разных ученика" … и число примеров в наборе».

**Попутный дефект следа (записан, ничего не переписано).** Текст решения (строка 1278) называет гипотезу о двух учениках номером три (Г-Д6-3), но в секции домена эта гипотеза — вторая (гипотеза «Короткий запрос и длинная процедура — два разных ученика», Г-Д6-2, строка 786); номер три носит гипотеза о трудности «зачем» (Г-Д6-3, строка 790). Это дефект нумерации в очереди решений; правка — будущая работа, здесь только фиксация.

**Что блокирует.** Осмысленность гипотезы о двух учениках (Г-Д6-2) и число примеров в наборе.

**Свип по стоячим требованиям.**

- Принятая программа сама уже прописала крест как способ проверки — уточнение к гипотезе о двух учениках (строка 788): «Нужен крест из четырёх согласованных групп с записанным числом примеров в каждой: короткий запрос, длинный запрос (развесистая выборка со вложенными подзапросами и группировками), короткая процедура (пять строк и одно изменение), длинная процедура»; и там же: выбор делается «до прогона».
- Методический прецедент программы: там же (строка 788) — «тот же приём, которым проход 7 разводил глубину и размер макета, а проход 8 длину и роль кода»: расцепление двух сцепленных осей крестом уже дважды применено в других доменах.
- Материал есть у самого проекта: канон репозитория называет системы со связкой «Angular + .NET + хранимые процедуры SQL» обязательными объектами доказательств (CLAUDE.md репозитория, строка 2039: «every validation project and linked Angular + .NET + SQL stored procedure system» — каждый проверочный проект и связанная система с хранимыми процедурами SQL) — то есть корпус запросов и процедур берётся из проверочных проектов проекта, не выдумывается.

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — принять крест два-на-два как СТРОЕНИЕ отложенного набора домена SQL.** Четыре согласованные группы с записанным числом примеров в каждой; это строение набора, не новые клетки матрицы и не расщепление строки домена.

**Альтернативы.** (а) Расщепить строку домена на два ученика (запросный и процедурный) — отклонено: гипотеза о самой быстрой кривой (Г-Д6-1, строка 782) требует одну кривую домена; «средняя кривая никого» уже разобрана на переводе, но здесь сам текст программы (строка 788) даёт выбор «домен идёт одной кривой с раздельным отчётом по видам» — и крест делает раздельный отчёт честным без второй строки и второго набора. (б) Оставить раскладку по виду ИЛИ по длине — отклонено стоячим текстом: «меряют одну общую тень», вывод предопределён сцепкой.

**Последствия.** Число примеров растёт умеренно (четыре группы вместо двух сцепленных) — цена меряется в валюте ручной разметки (решение 6) и режется бюджетом владельца (решение 5); классы ошибок, свойственные только процедурам (предусловия, побочные действия), считаются раздельно и с запросами не сравниваются никогда (строка 788); гипотеза о двух учениках (Г-Д6-2) получает осмысленность.

**Условие опровержения.** Если сборка корпуса не наберёт какую-то из четырёх групп (например, короткие процедуры окажутся редки в реальном корпусе) — группа честно записывается малой с числом примеров, и утверждения по её оси ограничиваются полом шума этой группы; отказ от креста целиком — только явным словом Лубы.

### Решение 22. Носитель контрольной точки «строгий эталон против свободной формы»

**Суть решения (по программе, строка 1300).** Цитата: «Носитель контрольной точки „строгий эталон против свободной формы" решается явно: либо ступень юнита документации SQL получает первичный статус и полный замер, либо контрольная точка переезжает туда, где снимается кривая обучения. Блокирует: одну из двух самых честных опор программы; меняет число первичных клеток и цену».

**Что несёт контрольная точка (проверено по тексту).** Она обещана строкой юнита матрицы у документации SQL (строка 321: «Самый строгий эталон из трёх документационных: контрольная точка „точный эталон против свободной формы"»), а гипотеза о самой быстрой кривой (Г-Д6-1, строка 782) называет себя ею: «это и есть контрольная точка „точный эталон против свободной формы", обещанная в строке юнита матрицы».

**Свип по стоячим требованиям.** Принятый текст раунда проверки уже провёл всю подготовительную работу этого выбора:

- Уточнение к гипотезе о самой быстрой кривой (строка 784): междоменное сравнение забраковано дважды (проходами 1 и 8), и «основной замер контрольной точки переносится ВНУТРЬ этого домена — на пару „что" против „зачем", которые живут на одном и том же примере; … после переноса она становится настоящим носителем контрольной точки, а настоящая гипотеза остаётся её междоменной тенью»; и там же ультиматум: «либо ступень юнита этого домена объявляется первичной (хотя бы по оси „что против зачем") и получает полный замер, либо гипотеза не проверяема ничем».
- Уточнение к гипотезе о трудности «зачем» (строка 792): «после переноса контрольной точки внутрь домена … именно она становится главным замером „строгий эталон против свободной формы" во всей программе».
- Диагноз пометки к строке юнита (строка 323): «Контрольная точка поручена клетке, которая по устройству её выполнить не может: контрольная точка требует кривой обучения при равном бюджете, а производная клетка закрывается выборочной проверкой, кривой не производящей».
- Проверка альтернативного маршрута (переезд к донору): документация C# первична (строка 319) и кривую производит, но та же пометка (строка 323, часть о документации C#) говорит: на её клетку уже переложен главный замер гипотезы уровня юнита о строгом эталоне, и «в нынешнем виде клетка эту нагрузку не выдерживает: строгая и свободная части одного примера различаются ещё и прибором, единицей усреднения и достижимостью ответа во входе».

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — маршрут первый.** Ступень юнита документации SQL получает первичный статус ПО ОСИ «что против зачем» и полный замер (кривую); носитель контрольной точки — гипотеза о трудности «зачем» (Г-Д6-3) со всей обвязкой из её уточнения (строка 792): разметка достижимости эталонных утверждений, крест приборов на одном содержании, пол шума обеих осей, раздельный счёт по происхождению.

**Сравнение цены маршрутов (по смете решения 6 и порядку решения 21).** Маршрут первый: полный замер одной ступени одной оси; главная статья — разметка достижимости — УЖЕ обязательна по уточнению (строка 792: «Починка одна и она чинит сразу три места домена»), то есть покупается один раз и оплачивает контрольную точку, честность оси «зачем» и кандидата о схеме (гипотеза Г-Д6-7, строка 852, опирается на ту же разметку); добавочная цена кривой против выборочной проверки — машинные прогоны, а они дешёвая часть сметы (итог проверки, строка 1213: «почти вся цена сидит в ручной разметке, а не в прогонах»). Порядок работ не ломается: по порядку доноров (решение 21, строка 1299) документация SQL всё равно не открывается, пока донор C# не закрыт, — первичность оси означает лишь, что при открытии ступень снимает полную кривую, а не выборку. Маршрут второй (переезд контрольной точки в документацию C# или иной домен с кривой) — отклонён: клетка C# нагрузку не выдерживает (строка 323), а пара «что против зачем» живёт на одном и том же примере ТОЛЬКО в SQL — переезд разорвал бы одно содержание на два домена и вернул бы дважды забракованное междоменное сравнение (строка 784).

**Последствия.** Число первичных клеток меняется (плюс одна по оси «что против зачем») — передаётся поправке счёта (решение 14, проход 4); гипотеза о самой быстрой кривой (Г-Д6-1) остаётся «междоменной тенью» — намерением без обязательного замера, как и записано уточнением (строка 784); одна из «двух самых честных опор программы» получает исполнимого носителя.

**Условие опровержения.** Явное слово Лубы о другом носителе. Либо если этап сборки покажет, что разметка достижимости в домене SQL неисполнима по цене, — контрольная точка остаётся без носителя и возвращается владельцу отдельной строкой решения (честно, не молча); маршрут второй при этом не воскресает сам собой, потому что возражение о несравнимых приборах в клетке C# ценой не лечится.

### Решение 24. Прежний опыт подбора мер ближайших соседей — розыск носителя

**Суть решения (по программе, строка 1302).** Цитата: «Прежний опыт подбора мер ближайших соседей вносится в источники и сверяется с шестью нынешними подборами — либо записывается, что сверка не выполнялась и оборот приказа „так же как мы делали" ничем не обеспечен. Блокирует: единственную фразу приказа, у которой сегодня нет носителя вовсе». Фраза приказа — «так же как мы делали с домейнами оркестрации, различного кода и переводов»: нужны реальные места, где прежний подбор мер соседей записан.

**Розыск — носители найдены в репозитории, по всем трём названным приказом областям.**

*Перевод.* Описание домена перевода (docs/projects/27-translation-domain.md, строки 106–113): «Алгоритм E2: общий KNN store TranslationKnnStore» — хранилище пар с методами подбора соседей «FindNearest(string signature, int k = 3)» и каскадом «FindNearestCascade(string fullSignature, string prefixSignature, string structureSignature, int k = 3, …)»: мера соседства выбрана КАСКАДОМ от полной подписи через префиксную к структурной, с тремя соседями по умолчанию; там же (строка 511) записано ограничение каскада: широкий откат ограничен source-aware защитой. Главная карта архитектуры (docs/ARCHITECTURE.md, строка 596) закрепляет тот же каскад строкой: «KNN cascade | TranslationKnnStore.FindNearestCascade: Full → Prefix → Structure → BootstrapFallback» (полная подпись → префикс → структура → откат на каркас).

*Различный код.* Описание обучения способностей на порождённом коде (docs/projects/18-capability-training.md, строка 61): юнит подбора соседей по векторным представлениям (TransformerEmbeddingKnnLogicalUnit) — «Transformer embeddings + HNSW + BM25-like fusion выбирают сохраненный output; не learned inference»: мера соседства — векторная близость представлений с индексом HNSW и слитой оценкой в духе BM25. Там же (строка 3) — главный урок прежнего опыта: граница «retrieval, а не learned inference» (подбор соседей — извлечение, не обученный вывод) исправлена и проверена сборками и целевыми тестами.

*Оркестрация.* Карта архитектуры (docs/ARCHITECTURE.md, строка 284): в проекте агентных алгоритмов (22.AgentAlgorithms) живёт фильтр навыков по соседям (KnnSkillFilter) рядом с оркестратором агента и графом зависимостей. Реестр интерфейсов (docs/COMPONENT-INTERFACES.md, строки 162–171): интерфейс фильтра навыков (ISkillFilter) с записанными параметрами подбора — пять соседей (topK = 5) и порог уверенности 0,40 (confidenceThreshold = 0.40); «Implemented by: KnnSkillFilter»; потребители — конвейер агента и выбор навыков в петле агента. Это и есть прежний подбор меры соседей для выбора навыков при оркестрации, с сохранёнными числами.

*Стоячее правило, делающее сверку обязательной.* Канон репозитория (CLAUDE.md, строки 1047 и 1063) требует в каждом чертеже трейнируемой единицы называть «KNN (K-Nearest Neighbours) or nearest-neighbour methods and their role» (методы ближайших соседей и их роль) — то есть сверка нынешних подборов с прежним опытом не пожелание, а обязательное поле чертежа.

*Честная граница розыска.* В каноне папки планирования носителей НЕ нашлось: грепы «KNN | соседей | nearest» по файлу обучения китайской модели (09.09.26WorkLeft-02-teaching-chinese-model.md), файлу механики (09.09.26WorkLeft-MECH-01-mechanism-validation.md) и файлу кодовых изменений (09.09.26WorkLeft-01-code-changes.md) дали ноль совпадений — прежний опыт живёт в репозитории, не в папке. Самый тонкий носитель — у оркестрации: имя фильтра и параметры в карте и реестре интерфейсов, без развёрнутого рассказа о выборе меры; сверка по этой области возможна в объёме найденного.

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — носитель найден и назначается.** Три места прежнего опыта (перевод — каскад подписей с тремя соседями; код — векторные соседи с индексом HNSW и слитой оценкой; оркестрация — фильтр навыков с пятью соседями и порогом 0,40) вносятся в источники программы; сверка шести нынешних подборов мер соседей с ними — работа этапа сборки наборов (решение 10, проход 4), с записанным итогом по каждому подбору. Фраза приказа «так же как мы делали» получает носителя; оговорка «сверка не выполнялась и оборот ничем не обеспечен» снимается в части существования носителя и остаётся честной в части самой сверки — она ещё не выполнена, только обеспечена материалом.

**Последствия.** Раздел источников программы пополняется тремя записями с точными файлами и строками; этап сборки наборов получает конкретную входную работу (сверку) вместо необеспеченной фразы; урок кода («подбор соседей — извлечение, не обученный вывод») переносится в программу как предостережение для всех шести подборов.

**Условие опровержения.** Если Луба назовёт иной прежний опыт (вне репозитория) — источники дополняются им. Если при сверке найденные места окажутся несопоставимы с каким-то из шести нынешних подборов — по этому подбору честно записывается «сверка выполнена частично, с найденным», как и велит текст самого решения.

### Решение 10. Этап сборки и заморозки наборов

**Суть решения (по программе, строка 1282).** Цитата: «Этап сборки и заморозки наборов — нулевой по счёту, первый по времени: извлечение эталонных сущностей шести доменов человеком, не видевшим систем; заморозка; второе независимое извлечение на выборке; публикация согласия; измерение доли ложных промахов и ложных попаданий каждого правила совпадения. Блокирует: все последующие этапы — без него ни один не имеет поверенного инструмента; и глагол приказа „построить тестовые сеты" остаётся невыполненным. *Срочно.*»

**Свип по стоячим требованиям — первым отвечает сам приказ.** Дословный приказ Лубы (файл «planning of testing.md», строка 1): «надо взять строение design pattern, domain и построить для них тестовые сеты, e2e tests». Сборка наборов — не новая трата, придуманная проверкой, а дословный глагол наряда: «построить … тестовые сеты». Программа сама признаёт дыру и её цену — пометка к порядку этапов (программа, строка 1039): «у программы нет этапа, на котором собираются наборы, а это самая дорогая её работа… Пока работы нет в перечне этапов, у неё нет ни срока, ни исполнителя, ни бюджета — а все числа точности без неё суть числа неизвестного инструмента»; там же перечислены сами эталонные сущности шести доменов (опорные точки перевода, перечень обязательных работ оркестрации задач, перечень проверяемых фактов документации C#, перечень связей Angular, состав побочных действий SQL, эталонная разметка страницы на фигме).

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ — этап добавляется.** Нулевой по счёту, первый по времени; состав — ровно как записан в тексте решения: извлечение человеком, не видевшим систем; заморозка вместе с набором; второе независимое извлечение на выборке; публикация согласия двух извлечений; измерение доли ложных промахов и ложных попаданий каждого правила совпадения.

**Сцепки с соседями по очереди.** Согласие двух извлечений и доли ложных промахов/попаданий — часть нуля ПРИБОРА, которого требует пометка к этапу базовых замеров (строка 1051), то есть этап сборки кормит процедуру пола шума (решение о нуле прибора, номер 3, проход 2). Сверка шести нынешних подборов мер соседей с прежним опытом, найденным в репозитории, — работа этого же этапа (решение о прежнем опыте соседей, номер 24, проход 3). Второе независимое извлечение исполняется по правилу «исполнитель + правило + второй человек» (решение 12 этого прохода). Первыми собираются наборы трёх доменов-доноров порядка работ (решение 21 этого прохода); хвост режется бюджетом владельца (решение 5) в валюте ручной разметки (решение 6).

**Последствия.** Глагол приказа «построить тестовые сеты» получает исполняющий этап; все семь этапов получают поверенный инструмент; пометка «срочно» удовлетворена — этап стоит первым по времени.

**Условие опровержения.** Только явная текущая правка приказа Лубой: пока в приказе стоит «построить тестовые сеты», отказ от этапа был бы невыполнением уже отданного наряда, а не выбором владельца.

### Решение 11. Стартовая граница решений владельца как этап

**Суть решения (по программе, строка 1283).** Цитата: «Стартовая граница решений владельца как этап. Блокирует: четыре этапа из семи, которые сегодня не могут стартовать; сам смысл слова „разрешён" применительно к первому этапу.» Источник дыры — пометка к порядку этапов (строка 1041): «нет места, где записываются решения владельца, хотя без них не стартуют четыре этапа из семи… этапа, на котором они собираются и записываются до начала работ, в программе нет».

**Свип и вердикт: РЕШЕНО-АРХИТЕКТУРНО — граница уже СУЩЕСТВУЕТ: ею стал сам этот реестр.** Когда пометка писалась, решения владельца были рассыпаны «пометками проходов 11–14 по своим секциям» (строка 1041) — места записи не было, и именно это блокировало этапы. Раунд разрешения (этот файл) в силу приказа Лубы «попробуй разрешить» собрал все двадцать четыре решения в одну сводную таблицу, просвипал каждое по стоячим требованиям и оставил владельцу остаток, который после этого прохода умещается в одну строку (бюджет — одно число, решение 5). Этап «стартовая граница решений владельца» тем самым определён исполнимо: владелец читает сводную таблицу этого реестра, называет одно число бюджета и — по желанию — переоткрывает любой вердикт одним словом (Первый Закон проекта; граница полномочий реестра из паспорта).

**Альтернативы.** (а) Писать отдельный этап-приёмник решений внутрь программы — отклонено: содержание такого этапа уже собрано здесь, а дублирование породило бы два живых перечня одного и того же (двойной канон — болезнь, которую программа лечила у правила переноса). (б) Считать, что границы нет, и держать четыре этапа блокированными до её создания — отклонено: блокировка держалась на отсутствии места записи, а место записи существует и заполнено.

**Последствия.** Слово «разрешён» у первого этапа получает проверяемый смысл: «все решения, блокирующие этап, имеют вердикт в реестре, и владелец сводку видел». Четыре блокированных этапа получают открывающий механизм без нового этапа-строительства.

**Условие опровержения.** Если Луба переоткроет заметное число вердиктов, граница вновь наполняется, и этап повторяется чтением обновлённой сводки; сам реестр остаётся местом записи. Если Луба явно велит вписать этап границы в текст программы — это будущая правка, не отмена вердикта.

### Решение 12. Исполнитель, правило и второй человек для каждого ручного действия

**Суть решения (по программе, строка 1284).** Цитата: «Каждое действие, требующее человека, получает исполнителя, правило и проверку вторым человеком на выборке. Семь экспериментов из двенадцати сегодня опираются на незаписанное человеческое суждение, а в трёх один и тот же судья учит и экзаменует. Блокирует: исполнимость этих семи.»

**Свип по канону репозитория — оба зла уже запрещены стоячими правилами.**

- «Один и тот же судья учит и экзаменует» — прямо запрещено правилом независимости сигнала приёмки (CLAUDE.md репозитория, секция «Acceptance-signal independence rule», строки 1905–1910): «The arbiter/reward source that decides ACCEPTED/REJECTED for an auto-DPO pair must be INDEPENDENT of the trained unit whose own choice becomes chosen/rejected» (арбитр, решающий «принято/отвергнуто», обязан быть НЕЗАВИСИМ от обучаемой единицы, чей собственный выбор становится избранным/отвергнутым); зависимость «своя уверенность как награда» там же названа «circular self-labelling loop» (замкнутый круг самомаркировки). Судья, который строит обучающий сигнал и сам же экзаменует результат, — ровно этот запрещённый круг, только в человеческом исполнении.
- «Исполнитель + правило + второй человек» — стоячая практика самого проекта: гейт личной приёмки архитектора (CLAUDE.md репозитория, секция «ARCHITECT_PERSONAL_ACCEPTANCE_AND_NO_SELF_REPAIR_GATE», строки 243 и 253) требует для каждого принятого результата исполнителя, НЕЗАВИСИМОГО рецензента и личную приёмку: «An independent reviewer sub-agent then performs a substantive review… This independent review is required evidence for every accepted worker result» (независимая проверка — обязательное доказательство для каждого принятого результата). Проверка вторым человеком на выборке — тот же строй, перенесённый с кода на разметку.
- Сама дыра «работы есть, а исполнителя, срока и бюджета у неё нет» названа итогом раунда проверки (программа, строка 1213) — пятый главный класс находок.

**Вердикт: ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ — правило принимается.** Каждое ручное действие программы получает: названного исполнителя; записанное ДО прогона правило действия; проверку вторым независимым человеком на выборке. Судья любого замера не совпадает с источником обучающего сигнала той же единицы — три места «судья учит и экзаменует» подлежат разведению ролей при будущей правке. Поимённое назначение исполнителей — работа этапа сборки наборов (решение 10 этого прохода) и бюджета владельца (решение 5): правило принимается сейчас, имена подставляются при старте этапа.

**Последствия.** Семь экспериментов, опирающихся на незаписанное суждение, получают путь к исполнимости; смета по разметке (решение 6) получает единицу учёта «действие × исполнитель × выборка второго человека».

**Условие опровержения.** Луба вправе явным текущим словом снять второго человека для конкретного дешёвого действия, приняв риск неповеренного суждения; по умолчанию правило действует всюду. Отмена независимости судьи потребовала бы правки канона репозитория — на что реестр указывает заранее.

### Решение 14. Поправка счёта клеток: девять первичных, пятнадцать производных (компактно)

**Суть решения (по программе, строка 1289).** «Поправка счёта клеток на девять первичных и пятнадцать производных во всех пяти местах документа сразу. ### Решение 15. Правило порядка достраивается до правила зависимости

**Суть решения (по программе, строка 1290).** «Правило порядка достраивается до правила зависимости: клетка открывается после закрытия СВОЕГО донора починенным замером; донор обязан быть первичной клеткой; у каждой производной клетки донор назван явно. Блокирует: семь клеток, для которых нынешний порядок неисполним.»

**Свип и вердикт: РЕШЕНО-АРХИТЕКТУРНО — принять.** Правило уже фактически несёт программу: пометка к порядку этапов (строка 1043) сформулировала его дословно — «порядок этапов не меняется, но становится порядком зависимости — этап открывает ту клетку, чей донор уже закрыт починенным замером», а список «донор → приёмники» с тремя дырами записан пометкой к матрице (строка 306). Проходы этого же раунда уже пользовались правилом как опорой: старт без бюджета идёт «по порядку доноров» (смягчающая рамка решения 5, проход 2); тела Angular производны от донора C# (решение 8, проход 3); документация SQL «не открывается, пока донор не закрыт починенным замером» (решение 22, проход 3, и текст решения 21). Отклонить правило теперь значило бы выбить опору из-под четырёх уже вынесенных вердиктов. Три дыры донорского списка (строка 306: юнит и поток на оркестрации задач — донора нет по знаку предсказания; поток на документации C# — опорная точка, не перенос) правилом не маскируются: клетка без законного первичного донора честно переводится в другой режим (опорная точка либо клетка честности — решение 17 этого прохода), что и есть применение правила, а не его нарушение. **Последствия:** семь неисполнимых клеток получают либо названного первичного донора, либо честный режим-замену; правило переноса перестаёт применяться к переносам второго порядка. **Опровержение:** явное слово Лубы либо обнаружение клетки, которую правило делает неисполнимой без режима-замены.

### Решение 16. Первичная клетка требует принятой гипотезы (компактно)

**Суть решения (по программе, строка 1291).** «Клетка не может иметь статус первичной без принятой гипотезы, несущей её собственное ожидание. Нарушено ровно в одном месте — поток на макетах. Блокирует: честность счёта первичных клеток.» **Вердикт: РЕШЕНО-АРХИТЕКТУРНО — принять правило; нарушений ноль.** Единственное нарушение вылечено проходом 1: кандидат о правке по кругу (гипотеза Г-П2-6) ратифицирован (разбор 1в), и первичная ступень потока на макетах получила несущую принятую гипотезу — ровно по развилке, записанной пометкой к лестнице фигмы (строка 999): «либо свип ратифицирует кандидата, либо статус ступени честно понижается». ### Решение 17. Клетка юнита на оркестрации задач — клетка честности

**Суть решения (по программе, строка 1292).** «Клетка юнита на оркестрации задач переопределяется как клетка ЧЕСТНОСТИ — первичная по оси честности, производная по оси умения, с явным запретом считать от неё разность оркестратора без второй, невырожденной опоры. Блокирует: осмысленность всей строки оркестратора в этом домене.»

**Свип.** Пометка к строке юнита (строка 323, часть об оркестрации задач) уже прочитала клетку именно так: «Читать её сегодня надо не как „замер умения", а как клетку ЧЕСТНОСТИ, и по оси честности она фактически первичная: другого места, где успехом объявлен отказ обученной системы, в матрице нет»; там же — запрет разности от неё («разность оркестратора на этом домене нельзя считать от неё») и обязательный встречный замер против вечного отказчика — «иначе стопроцентная „честность" достаётся при нулевом умении». Оба упора переопределения поставлены проходом 1: честность — сквозное измеряемое свойство с парным замером умения (решение о статусе честности, номер 13, закрыто стоячим требованием), несущая гипотеза клетки — ратифицированный кандидат о честном молчании обученного юнита (гипотеза Г-П1-7, разбор 1б). Вторая невырожденная опора для разности оркестратора уже записана починкой первой пометки к лестнице оркестрации задач (строка 995): «тот же вход целиком, решённый сильнейшим одиночным исполнителем, которому отвечать разрешено».

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — переопределить.** Клетка первична по оси честности (замер — пара чисел против двух пустышек-соперников, по пометке к этапу базовых замеров, строка 1051), производна по оси умения; разность оркестратора считается только от второй невырожденной опоры, разность от молчаливой опоры публикуется отдельно под своим именем. Заодно закрывается первая дыра донорского списка (строка 306): клетке, чьё ожидание — отказ, донор умения и не положен. **Последствия:** строка оркестратора домена обретает осмысленность; двухосный статус клетки — прецедент, уже применённый решением 8. **Опровержение:** явное слово Лубы; либо условие опровержения кандидата о честном молчании из разбора 1б.

### Решение 18. Успех лестницы оркестрации задач против части о порче

**Суть решения (по программе, строка 1293).** «Успех лестницы домена оркестрации задач приводится в согласие с честной частью о порче. Сегодня документ противоречит сам себе: правило разрешает добавке ступени быть отрицательной, а условие успеха объявляет это провалом. Блокирует: чтение результата этой лестницы.»

**Оба конфликтующих места — дословно.** Сторона условия успеха — лестница оркестрации задач (строка 993): «Успех: покрытие обязательных частей растёт от ступени к ступени». Сторона правила порчи — честная часть о порче (строка 1017): «добавка ступени бывает ОТРИЦАТЕЛЬНОЙ… Правило программы: отрицательная добавка не прячется из отчёта; она записывается в матрицу так же, как положительная». Противоречие зафиксировано с обеих сторон: починка вторая пометки к лестнице (строка 995) — «успех спорит с честной частью документа… лестница домена наказывает за честный результат»; уточнение правила порчи (строка 1027) — «правило этой секции прямо разрешает добавке быть отрицательной, а успех лестницы домена оркестрации задач требует, чтобы покрытие росло от ступени к ступени, — то есть объявляет провалом теста исход, который программа сама назвала законным».

**Которая сторона больна — уже установлено раундом проверки.** Итог проверки (строка 1212): «Условие успеха этапа опирается на то, чего гипотезы не дают. Проверено сплошь: все семь этапов, здоровых нет. Причина общая — условия писались от ожиданий, а не от способов проверки». Больна сторона условия успеха, написанная от ожидания «выше — лучше»; правило порчи проверка не оспорила, а усилила двумя уточнениями (строка 1027: пол шума у слова «хуже»; честная точность адреса).

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — побеждает часть о порче.** Условие успеха лестницы переписывается из формы «добавка положительна» в форму «замер состоялся и знак добавки записан»: по каждой ступени добавка покрытия измерена против пола шума своей клетки (решение о нуле прибора, номер 3); знак — положительный, отрицательный или честное «различие не установлено» — записан в матрицу с точным адресом (какая ступень, какой домен, какая ось); отрицательная добавка порождает записанный вопрос следующего уровня — чинить шов, упрощать этаж или честно не использовать комбинацию на этом домене (строка 1017). **Альтернативы.** Победа условия успеха (отрицательная добавка = провал) — отклонена: наказывает честный результат, противоречит усиленному правилу и диагнозу строки 1212. Компромисс «двойная метка успех/провал поверх записи знака» — отклонён: возвращает то же слово «провал», из-за которого спор возник, не добавляя измерения. **Последствия:** чтение результата лестницы разблокируется; сама переписка условия — будущая правка по правилу решения 19, с повторной проверкой (строка 1322). **Опровержение:** явное текущее слово Лубы, что успехом лестницы объявляется только рост покрытия, — тогда отрицательная добавка становится записанным провалом, но правило «не прячется из отчёта» остаётся и при этом.

### Решение 21. Порядок работ по донорам

**Суть решения (по программе, строка 1299).** Цитата: «Порядок работ записывается по донорам, а не по строкам матрицы: первичные клетки документации C# — первыми; первичные клетки перевода и макетов объявляются донорами потока и графа трёх документационных доменов; документация Angular и SQL не открываются, пока донор не закрыт починенным замером. Блокирует: две из шести доменных лестниц, стоящих сегодня блокированными. *Срочно.*»

**Свип.** Порядок не изобретён этим решением — он собран из трёх конкретных расхождений, найденных пометкой к порядку этапов (строка 1043): первичные клетки документации C# «идут раньше всех прочих внутри своего этапа, потому что от них питаются два целых домена»; первичные клетки перевода и фигмы — «единственный законный источник для ступеней потока и графа трёх документационных доменов»; и правило зависимости (решение 15 этого прохода). Проходы 2–3 уже стояли на этом порядке: старт без бюджета «по порядку доноров» (решение 5), запрет открытия Angular и SQL до закрытия донора (решения 8 и 22).

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — принять порядок из текста решения, со встройкой первичных осей прохода 3.** Ось связей документации Angular (решение 8) и ось «что против зачем» документации SQL (решение 22) встраиваются БЕЗ изменения порядка: обе живут в клетках, которые не открываются до закрытия донора C#, поэтому обе снимаются при открытии своих доменов — связи Angular собственным первичным замером на замороженном перечне связей, ось «что против зачем» SQL полной кривой (по решению 22). Наборы для них собираются заранее этапом сборки (решение 10), чтобы открытие доменов не ждало разметки.

**Первые три шага порядка — конкретно.** Шаг первый: этап сборки и заморозки наборов (решение 10) для трёх доменов-доноров — документации C# (перечень проверяемых фактов), перевода (смысловые опорные точки, по каждому направлению — решение 7) и макетов (эталонная разметка страницы), с нулём прибора каждого правила совпадения (решение 3). Шаг второй: базовые замеры (этап А) и первыми — полный замер первичных клеток документации C#: юнит (свободная форма с проверяемыми фактами), затем оркестратор (по пометке к этапу оркестратора, строка 1063, — «самая крепкая опора программы»: единственная невырожденная опора и готовая эталонная сборка), с порогами по правилу «пол шума × два» (решение 2). Шаг третий: первичные клетки перевода (две кривые по направлениям) и макетов (юнит; ступень юнита с потоком — цикл, несомый ратифицированной гипотезой о правке по кругу) — как доноры потока и графа трёх документационных доменов. Только после закрытия донора C# починенным замером открываются документация Angular и SQL — со своими первичными осями.

**Альтернатива — порядок по строкам матрицы — отклонена.** Строки матрицы задают форму, а не исполнимость (строка 1043: два порядка «отвечают на РАЗНЫЕ вопросы, и нужны оба»); порядок по строкам открывал бы производные клетки раньше их доноров — ровно та неисполнимость, из-за которой две лестницы стоят блокированными (строка 1071: этап производных «распадается на веер зависимостей»).

**Последствия.** Обе блокированные лестницы (Angular и SQL) получают исполнимый путь открытия; пометка «срочно» удовлетворена — порядок исполним с шага первого без бюджета (решение 5); бюджет, когда появится, режет хвост, не голову.

**Условие опровержения.** Явное слово Лубы о другом порядке; либо если этап сборки покажет, что донорский набор одного из трёх доменов несобираем, — порядок пересчитывается от оставшихся доноров тем же правилом зависимости, а несобираемый домен честно помечается.

### Решение 23. Носитель третьего параметра приказа — скорость обучения комбинаций

**Суть решения (по программе, строка 1301).** Цитата: «Носитель третьего параметра приказа для комбинаций: либо лестница получает замер кривой обучения на КАЖДОЙ ступени (по одной кривой на ступень, дорого), либо программа честно записывает, что влияние комбинации на скорость обучения не меряется и приказ в этой части выполнен не будет. Блокирует: треть главного вопроса приказа.»

**Свип — маршрут «не меряем» запрещён без слова Лубы.** Дословный приказ (файл «planning of testing.md», строка 1) называет предмет программы: «программу обучение и тестирования качества, скорости и точности обучения» — и требует «посмотреть как их комбинация влияет на все эти параметры». Скорость обучения — один из трёх названных параметров; «все эти параметры» — буква приказа. Маршрут второй («честно записать, что… приказ в этой части выполнен не будет») есть сужение дословного объёма приказа, а сужение объёма без явной текущей цитаты владельца запрещено каноном проекта — правило числового пола (CLAUDE.md репозитория, строки 1281–1290): «The numeric floor is binding: it may NOT be downgraded… without an explicit CURRENT Luba quote authorizing the narrower scope» (числовой пол связывает: понижать объём без явной текущей цитаты Лубы нельзя), с литералами «numeric floor is binding without an explicit current Luba quote» и «blocked-until-done-or-Luba-approves-narrower not optional-unless-Luba-reopens» (заблокировано-пока-не-сделано-или-Луба-не-разрешит-уже, а не необязательно-пока-Луба-не-переоткроет). Честность формулировки второго маршрута не лечит его беззаконности: честно записанное невыполнение приказа остаётся невыполнением.

**Вердикт: РЕШЕНО-АРХИТЕКТУРНО — маршрут первый.** Лестница получает замер кривой обучения на каждой ступени (по одной кривой на ступень); влияние комбинации на скорость обучения меряется сравнением ФОРМЫ кривых ступеней в долях своего пути — по уже принятому правилу пометки к этапу юнита (строка 1055): кривые разных приборов сравниваются только в долях своего пути от нулевой отметки до потолка, а «потолок не найден в пределах бюджета» — честный записываемый исход. Удорожание управляется не отказом, а двумя уже принятыми рычагами. Первый — фазировка по порядку доноров (решение 21): первыми снимаются кривые ступеней двух живых лестниц — перевода (вердикт пометки, строка 991: «жива с оговорками») и документации C# (вердикт пометки, строка 1003: «самая крепкая опора программы»); блокированные лестницы получают кривые только при своём открытии по правилу зависимости. Второй — бюджетное число владельца (решение 5), которое обрезает хвост списка клеток по правилу «сокращать ЧИСЛО КЛЕТОК, а не число проб внутри клетки» (пометка к сводному отчёту, строка 1075; смета — решение 6). Добавочная цена кривой против точки — в основном машинные прогоны, дешёвая часть сметы (итог проверки, строка 1213: «почти вся цена сидит в ручной разметке, а не в прогонах машины»); там, где точка кривой требует судейской разметки, цена честно попадает в валюту разметки и режется тем же бюджетом.

**Почему маршрут «не меряем» отклонён — явно.** Не по цене и не по вкусу, а по запрету сужения приказа: объём «все эти параметры» назначен дословным приказом, и снять с него треть вправе только сама Луба явной текущей цитатой. До такой цитаты у программы нет выбора «мерить или честно не мерить» — есть только выбор, как мерить дешевле (фазировка и бюджетная отсечка выше).

**Последствия.** Треть главного вопроса приказа получает носителя; продукт этапа юнита «состояния во всех контрольных точках, а не только итоговый юнит» (строка 1055) становится обязательным для всех ступеней с кривой; карта оправданности комбинаций получает ось скорости обучения парой к оси качества (без слова «окупилось» — решение 4).

**Условие опровержения.** Явная текущая цитата Лубы, разрешающая узкий объём («скорость обучения комбинаций не мерять»), — только она легализует маршрут второй; тогда запись «не меряется» делается с прямой ссылкой на цитату.

## Поправка раунда по живому слову владельца (26.08.2026) — F6-I

### Основание — два живых сообщения Лубы дословно

Сообщение первое: «Какая ручная работа, если у нас вся идея в том что обучение идет через китайскую открытую модель?»

Сообщение второе: «эталон это то что записано платной моделью как правильный ответ, например исполнитель кодекса. Как только мы приблизились достаточно близко 95% точности и выше к эталону, сам кодекс может удостовериться что машина обучилась на китайской модели. Зачем тут человек не понятно...»

**Констатация.** Это живая незацитированная инструкция владельца — высшая власть по Первому Закону проекта. Она ПЕРЕОТКРЫВАЕТ состав нескольких вердиктов этого реестра. Ошибка аджюдикации была двойной. Первая: проходы 1–5 закрыли состав этапа сборки наборов (решение 10) в формулировке «извлечение эталонных сущностей человеком, не видевшим систем; второе независимое извлечение», не просвипав этот состав против стоячей схемы канона папки «обучение идёт через китайскую открытую модель» — то есть свип по стоячим требованиям, которым реестр гордится, был неполным именно там, где стоячее требование существовало. Вторая: первая поправка родителя-архитектора («человек проверяет выборку за учителем») тоже была неверна — она оставила человека в главном контуре и не развела роли учителя и экзаменатора, тогда как схема владельца разводит их полностью.

### Каноническая схема трёх ролей (с этого момента — канон раунда)

1. **ЭКЗАМЕН (эталон).** Эталон — записанные ответы ПЛАТНОЙ модели (например, исполнителя кодекса); они уже существуют как продукт её обычной работы. Ответы платной модели в обучение НЕ идут — лицензионная граница: платная закрытая модель не входит в разрешённый список учителей дистилляции.
2. **УЧИТЕЛЬ.** Открытая китайская модель (Qwen) строит DPO-пары (пары предпочтений: «избранный ответ против отвергнутого»), приближающие ученика к эталону. Точность измеряется сравнением ответа ученика с эталоном.
3. **УДОСТОВЕРИТЕЛЬ.** При точности к эталону 95% и выше («приблизились достаточно близко» — слова владельца) сама платная модель удостоверяет, что машина обучилась на китайской модели. Человек в главном контуре не нужен. Порог 95% — число, названное владельцем, а не архитектурная догадка.

**Опорные цитаты канона — схема не висит в воздухе, она уже записана в стоячих требованиях.**

- (а) Файл обучения китайской модели (09.09.26WorkLeft-02-teaching-chinese-model.md), строка 360: «**Кто кого учит.** Qwen (локальная китайская открытая модель) — **только учитель и судья**; обучаемые … — **собственные модели проекта** на TensorCore»; там же, строка 112: правило «китайская модель — учитель, ученик свой» (строка работ 125) — ОТКРЫТОЕ ПОСТОЯННОЕ правило, действует. Роль китайской модели как учителя — не новость этой поправки, а давно стоячее требование, против которого проходы 1–5 не просвипали.
- (б) Канон репозитория (CLAUDE.md), инвариант соответствия семьи учителя и её канонической лицензии («Family-to-canonical-license coherence invariant», строки 1939–1943): «For any distillation-teacher allowlist … the registry must carry a `family -> canonical_license` invariant (for example DeepSeek -> MIT, Qwen3 -> Apache-2.0 …)» (для всякого списка разрешённых учителей дистилляции реестр обязан нести инвариант «семья → каноническая лицензия»; Qwen — Apache-2.0). Отсюда обе половины схемы владельца сразу: ответы платной модели в обучение не идут (её нет в списке учителей), но экзаменационным эталоном они быть могут — экзамен не есть дистилляция, обучение идёт только на парах, построенных открытым учителем.
- (в) Канон репозитория (CLAUDE.md), правило независимости сигнала приёмки («Acceptance-signal independence rule», строки 1905–1910): «The arbiter/reward source that decides ACCEPTED/REJECTED … must be INDEPENDENT of the trained unit whose own choice becomes chosen/rejected» (арбитр, решающий «принято/отвергнуто», обязан быть независим от обучаемой единицы). В схеме владельца это выполняется ПО ПОСТРОЕНИЮ: обучающий сигнал строит учитель (Qwen), экзаменует сравнение с эталоном платной модели, удостоверяет платная модель — три разных источника, ни один не равен обучаемой единице.

### Поправленные вердикты — поштучно (существующие разборы не переписываются; каждая поправка — «было → становится»)

**Этап сборки наборов (решение 10).** Было: состав этапа — «извлечение эталонных сущностей человеком, не видевшим систем; заморозка; второе независимое извлечение на выборке; публикация согласия». Становится: состав меняется. Наборы = замороженные корпуса ЭТАЛОНОВ платной модели по шести доменам (её записанные ответы) + правила сопоставления «ответ ученика ↔ эталон» (код). «Извлечение человеком, не видевшим систем» и «второе независимое извлечение» — упразднены. Там, где эталонов домена ещё нет, их ЗАПИСЫВАЕТ платная модель своей обычной работой (вызовами), не человек. Вердикт остаётся ЗАКРЫТО-СТОЯЧИМ-ТРЕБОВАНИЕМ — «построить тестовые сеты» по-прежнему дословный глагол приказа; меняется только исполнитель сборки: не человек-извлекатель, а платная модель как источник эталонов плюс код правил сопоставления. **Исполнитель и второй человек (решение 12).** Было: «каждое ручное действие получает исполнителя, правило и проверку вторым человеком на выборке; имена — работа этапа сборки». Стоячее правило независимости судьи от обучаемой единицы (канон репозитория, строки 1905–1910) сохраняется и выполняется: судья = сравнение с эталоном платной модели, который обучаемая единица не строила и построить не может.
