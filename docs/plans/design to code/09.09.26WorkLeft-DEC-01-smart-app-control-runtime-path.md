# 13.08.26 WorkLeft DEC-01 — Smart App Control: выбор runtime-пути для заблокированных тестов

## §0 Русское резюме и рекомендация

Windows Smart App Control (SAC, «умный контроль приложений» — потребительская
функция целостности кода Windows 11) блокирует загрузку неподписанной локально
собранной `ContinuousLearning.dll` ДО входа в тела тестов параллельной
Codex-сессии. Подпись сборок сертификатом эту блокировку скорее всего НЕ снимет,
исключений SAC не поддерживает, а выключение SAC — необратимый шаг, который
решает только Люба.

**Рекомендация (архитектурно решаемая часть):** основной технический маршрут —
**вариант 2b: WSL2 (Windows Subsystem for Linux 2) + Linux `dotnet` на этой же
машине**. Бесплатно, обратимо, безопасность хоста не трогается, SAC на
Linux-процессы не действует. Свежая проверка дерева показала: три из четырёх
заблокированных семейств тестов кросс-платформенны и должны выполниться под
Linux; четвёртое семейство (координатор) — смешанное: часть его тестов
использует настоящий стор `JsonDesignConversionPostEvaluationStateStore`, чей
путь записи жёстко Windows-only (кидает `PlatformNotSupportedException` на
не-Windows). Для этой Windows-only части нужен запасной маршрут **2a: Windows
dev-VM (виртуальная машина) без SAC** — либо решение Любы по варианту 3.

**Что остаётся за Любой (owner-choices, см. §5):** выключать ли SAC на хосте
(необратимо); покупать ли коммерческий сертификат (бюджет; к тому же помечен
как «скорее всего неэффективно»); заводить ли Windows dev-VM для Windows-only
подмножества.

## §2 Знание-основанные ограничения SAC (без сети; метки уверенности + как проверить)

Каждое утверждение ниже — [знание модели], НЕ проверено на этой машине в этой
сессии. Для каждого дан локальный способ проверки.

1. **SAC не поддерживает исключения.** Ни per-app allow-правил, ни кастомных
   политик, ни исключений по пути/издателю. Корпоративная альтернатива с
   кастомной политикой — App Control for Business (бывший WDAC, Windows
   Defender Application Control).
   [знание модели, уверенность высокая]
   Проверка: Безопасность Windows → «Управление приложениями/браузером» →
   «Умный контроль приложений»: там только переключатель Вкл/Оценка/Выкл, ни
   одного списка исключений.
2. **Доверие SAC = валидная подпись + репутация Microsoft Intelligent Security
   Graph.** Самоподписанный или private-CA Authenticode-сертификат доверия SAC
   НЕ даёт. Даже коммерческий сертификат может не пройти сразу: каждая
   пересборка тестовой dll — новый хэш без репутации. Для dev-inner-loop
   (пересборка десятки раз в день) вариант 1 практически неэффективен.
   [знание модели, уверенность высокая для self-signed; средне-высокая для
   «коммерческий тоже не спасёт inner loop»]
   Проверка: подписать одну тестовую dll имеющимся сертификатом и посмотреть,
   повторится ли событие 3089 в Event Viewer → Applications and Services Logs →
   Microsoft → Windows → CodeIntegrity → Operational.
3. **SAC, однажды выключенный, нельзя включить обратно** без сброса/переустановки
   Windows. Вариант 3 необратим, действует на весь хост и снижает защитную
   позицию машины. Это строго решение Любы.
   [знание модели, уверенность высокая]
   Проверка: текст под переключателем SAC в Безопасности Windows прямо
   предупреждает об этом; также msinfo32 → «Сведения о системе» показывает
   строку «Smart App Control» (состояние On/Evaluation/Off).
4. **Позиция Microsoft:** машины, на которых разрабатывают/собирают
   неподписанный софт, — неподходящая цель для SAC; в режиме «Оценка» SAC на
   такой машине сам бы отключился, но состояние «On» — липкое (не
   пересматривается).
   [знание модели, уверенность средне-высокая]
   Проверка: Microsoft Learn, статья «Smart App Control» (раздел о том, для
   кого функция предназначена).
5. **SAC не действует на Linux-процессы WSL2** (и на процессы в Linux-контейнере):
   Windows Code Integrity проверяет PE-загрузку Windows, а не ELF/managed-код
   внутри Linux-ядра WSL2.
   [знание модели, уверенность высокая]
   Проверка: `dotnet build` + `dotnet test` в WSL2 — событий 3033/3077/3089 в
   CodeIntegrity-логе Windows не появляется, тесты входят в тела.
6. Код ошибки `0x800711C7` — принят как наблюдение параллельной сессии;
   расшифровка кода в этой сессии не верифицирована. [не проверено]

## §5 Owner-choices для Любы (решает только она)

1. **Вариант 3 — выключить Smart App Control на хосте.** Необратимо (обратно —
   только сброс/переустановка Windows, §2.3); действует на весь компьютер;
   снижает защиту. Честная справка: это единственный маршрут, который нативно
   разблокирует ВЕСЬ набор тестов на этой машине без изменения кода, и позиция
   Microsoft — dev-машины, собирающие неподписанный код, не целевая аудитория
   SAC (§2.4). Но обмен «удобство ↔ защита хоста» — только твой выбор.
   Рекомендация архитектора: решение можно отложить — маршрут 2b покрывает
   большую часть прямо сейчас.
2. **Покупка коммерческого Authenticode-сертификата.** Бюджетное решение; при
   этом по §2.2 для inner loop скорее всего неэффективно (репутация на каждый
   rebuild не появится). Рекомендация: не покупать ради этой задачи.
3. **Windows dev-VM (вариант 2a) для Windows-only подмножества.** Нужна, если
   вариант 3 отклонён, а Windows-only ряды координатора/стора надо гонять
   регулярно. Выбор WSL2-против-VM по остальной массе тестов уже сделан
   архитектурно (2b первичный: бесплатно, обратимо, хост не трогается); VM —
   только добор Windows-only части. Если Windows-only ряды гоняются редко —
   можно жить очередью «прогнать при следующем доступе к Windows-среде без SAC».
4. **Установка компонента WSL2** (если ещё не установлен): `wsl --install` —
   это изменение компонентов Windows; формально твоё согласие как владельца
   машины.
