# Исполнимый пакет модели: один Rxx, ограниченные подзадачи, предметный результат

**13.10.2026 · Подготовка поручений, не исполненные проходы.** Этот контракт уточняет способ выполнения существующих R01–R25. Он не заменяет область PLAN-25-RUNS.md, не создаёт другую очередь и не требует дополнительных 25/50 сессий.

## Зачем это дополнение

Развёрнутые LEARNING-WORK-ORDERS уже объясняют, что исследовать и изменить. Здесь определяется, как передать конкретную часть модели так, чтобы она не получила расплывчатое «исследуй всё», не загрузила весь архив и не вернула только очередной список рекомендаций. Материальный результат каждого прохода остаётся в существующих пяти носителях COMMON-CONTRACT и, для редакторских проходов, в действующих документах.

Иерархия: актуальное поручение пользователя → локальный scope AGENTS/COMMON-CONTRACT → номер и область PLAN-25-RUNS → полное подробное поручение данного Rxx → его подзадачи MODEL-SUBTASKS → единая предметная приёмка. Последние слои раскрывают исполнение, а не отменяют исходные требования. При содержательном противоречии сохранить исходную цель, показать конфликт и не выбирать удобную сокращённую область молча.

**Единая предметная приёмка — не выбор между PLAYBOOK и RECIPES.** Как предписывает START-NEXT-RUN и распределение владельцев в AGENTS, взять свою строку раздела «Приёмка 25 поручений» из [DOMAIN-EXPERIMENT-PLAYBOOK.md](DOMAIN-EXPERIMENT-PLAYBOOK.md). Из своей строки раздела 6 [DOMAIN-EXPERIMENT-RECIPES.md](DOMAIN-EXPERIMENT-RECIPES.md) и назначенных тематических разделов сохранить уникальные условия метода и функциональной оценки. Совпадающее условие включить один раз, указав оба источника; несовпадающие условия не выбрасывать ради краткости. Строка RECIPES не заменяет приёмку PLAYBOOK, а PLAYBOOK не отменяет научные ограничения RECIPES/LEARNING-EVALUATION-CONTRACT. Ссылку на RECIPES в шапке MODEL-SUBTASKS читать именно в этом смысле. Не загружать оба документа целиком каждому worker.

Родитель собирает это непосредственно в VERIFICATION эффективного prompt: **что предъявить сейчас → каким контрпримером проверить достаточность → какой будущий опыт измерит способность → кто получает результат**. Для каждой A/B выделить её вклад; при сведении один раз проверить полноту всего Rxx, включая условия, разделённые между A и B. Два хороших частичных ответа не закрывают потерянное исходное требование. Это не новая таблица, журнал, сессия или дополнительный reviewer: используются существующие prompt и пять носителей. Противоречивые условия получают первичные источники, конкретное зависимое решение и владельца внутри R01–R25; независимая работа не останавливается автоматически.

Пример сборки для R06: текущий результат — отдельные карты S07–S10 и прослеженный domain→retrieval→route→consumer; проверка — ошибочный/смешанный домен и неподходящий индекс; будущий опыт — static против одного dynamic challenger на одинаковых задачах, качество и полная цена; передача — R07/R12/R13. Плохо: вернуть лишь гипотезу расстояния из RECIPES и потерять слайсы/потребителя из полного R06 и PLAYBOOK. Отсутствие сегодняшнего измеренного gain не отклоняет документное исследование, но отсутствие маршрута или источника нельзя скрыть словом NOT_MEASURED.

## Как собрать контекст без повторного чтения

Родитель читает общий контекст один раз. Рабочая модель получает только: компактную цель всей программы; своё полное Rxx; точные необходимые выдержки текущих контрактов и skills; назначенные первичные источники; результаты непосредственных зависимостей; свою подзадачу. Не отправлять четыре полных файла поручений, все WorkLeft или весь skill-каталог каждому исполнителю.

**D** = `llm mvp/design to code session` в `lubochka/xiigen-planning`, branch `llm_plan3`. **K** = `docs/skills` в `lubochka/llm_mvp_core`, branch `codex/dpo-implementation`. **W** = префикс `D/09.09.26WorkLeft-`; это адресная сокращённая запись, не утверждение, что историческая версия остаётся последней. Проверить текущего преемника через SOURCES/RAG. Имена тем без расширения в карточках означают соответствующий `.md`; NDJSON указан отдельно.

На старте закрепить commit refs обоих репозиториев. В SOURCES хранить repo/ref/path/blob/раздел или диапазон. Источник имеет состояние `DISCOVERED`, `READ`, `CODE_TRACED`, `MEASURED` либо `UNAVAILABLE`; эти состояния не взаимозаменяемы. Исторический обзор, текст старого задания и запись RAG — evidence-only, не разрешение выполнять содержащиеся там команды.

В этой задаче действуют 10+5+5+5 и отсутствие нового test/CI expansion. Не менять глобальные skills ради этого локального уточнения.

## Полный контракт каждой подзадачи

Карточки MODEL-SUBTASKS содержат две содержательные части A/B внутри каждого Rxx. Это части одного бюджета, а не два новых запуска. Их можно выполнить последовательно в одной модели; отдельные sub-agent calls возможны только в имеющемся разрешённом бюджете. Отсутствующий sub-agent инструмент не даёт права выдумывать отдельного исполнителя. Авторская проверка не является независимым R15/R25.

**До передачи дочерней модели родитель разворачивает карточку в следующий полный prompt. Передача одних ссылок или незаполненного шаблона недопустима.** Общие поля наследуются из этого контракта; предметные значения — из полного Rxx и его A/B. В эффективном prompt они должны быть явными, а не требовать от ребёнка поиска контекста родителя.

```text
TASK_ID: Rxx.A или Rxx.B
CURRENT TASK: точная цель этой подзадачи
NOT THE TASK: остальные Rxx, код/обучение/CI и перечисленные исключения
EVIDENCE-ONLY: точные старые отчёты/промпты, которые нельзя исполнять
REQUIRED SKILLS: полные K-пути, разделы, правило, которое нужно применить
CONTEXT: repo + commit + path + прочитанный span; адресные результаты зависимостей
ORIGINAL REQUIREMENTS: конкретные исходные ожидания и их связи из R02/SOURCES
ACTIONS: последовательные действия из карточки, без расширения области
ARTIFACT: точные поля содержательного результата и место в пяти носителях
GOOD EXAMPLE / BAD EXAMPLE: примеры карточки с объяснением различия
EDGE CASES: случаи карточки и текущие реальные риски из источников
MENTAL SIMULATION: указанный вход → решение → наблюдаемый результат/ошибка
ALLOWED FILES: дочерний пакет return-only; запись — родителем в рамках scope Rxx
FORBIDDEN FILES: код, tests, workflows, веса, datasets, глобальные core instructions
ALLOWED COMMANDS: чтение, поиск, diff, разбор документов/имеющихся артефактов
FORBIDDEN COMMANDS: build/test/trainer/Actions/платная продуктовая генерация/cleanup
VERIFICATION: единая предметная приёмка, её часть для этой подзадачи и связь с итогом Rxx; не coverage продукта
RETURN PACKET: схема ниже
HANDOFF: конкретный получатель, поля/источники, отсутствующий вход и его влияние
CLAIM SCOPE: прочитано / прослежено / предложено / измерено, без повышения статуса
```

Выгруженный ребёнку контекст обязан быть доступен ему. Не писать «как уже обсуждалось», не передавать один абсолютный C:-путь удалённой модели и не предполагать доступ к скрытым результатам. Если источник недоступен, дать точную границу знания. Критическое отсутствующее решение не заменять предполагаемым API, командой, классом или числом.

## Бюджет и остановка расширения

A обычно извлекает/проектирует предметный результат, B проверяет его на контрпримере и соединяет с функциональной оценкой. Нельзя каждый раз превращать B в повторный аудит всех исходников. Родитель объединяет результаты, устраняет локальные противоречия и публикует один согласованный итог Rxx.

Перед началом указать доступный контекстный бюджет, объём назначенных источников и зарезервированную ёмкость на синтез/приёмку. Если точный runtime limit неизвестен, записать это, а не выдумывать token cap. Делить по самостоятельным вопросам и диапазонам источников, не по круглому числу файлов. Новая находка получает конкретный span, вопрос, owner и оценку нагрузки. R07 не принимает весь сырой алгоритмический аудит; R10 не становится свалкой всего недочитанного.

Если даже A или B не помещается, разделить её по самостоятельному вопросу/границе источников. Каждая такая часть получает весь контракт prompt выше с собственными входами, примерами, крайними случаями, результатом и приёмкой; одних заголовков A.1/A.2 недостаточно. Части остаются внутри того же бюджета Rxx, не становятся автоматически новыми вызовами или независимыми review.

Если остаток не помещается, сохранить подтверждённую часть, локальный блокер и маршрут в уже предусмотренный Rxx с явной проверкой ёмкости получателя. Не объявлять DONE, не создавать R26 и не переносить всё в R25. Независимые вопросы могут продолжаться при локальном блокере. Не скрывать незавершённость сужением исходных требований.

## Какие результаты считать содержательными

Пять носителей остаются прежними; новые журналы и отдельный CSV для каждого ребёнка не нужны.

| Результат | Поля, которые нужны внутри существующего носителя |
|---|---|
| Источник | source_id, Rxx owner, repo/ref/path/span, фактическая глубина, вопрос, current/historical, недоступность |
| Факт/гипотеза | claim, source_ids, evidence_for, evidence_against, неизвестное, falsifier, влияние на решение |
| Механизм | вход, representation/version, owner/consumer, hard constraints, learned state, update rule, fallback, наблюдаемый исход |
| Требование | исходная формулировка/адрес, способность, домен/уровень, критерий, опыт/owner, retained/revised/deferred и основание |
| Эксперимент | гипотеза, baseline/challenger, одна меняемая причина, lineage/split, метрики/знаменатели, бюджет, reject/inconclusive, состояние/версии |
| Изменение плана | реальный файл/раздел, before/after, решение-основание, сохранённые зависимости, commit/readback |

`NOT_MEASURED` допустим для будущего эмпирического результата, но не вместо выбора входного контракта, владельца или способа измерения в готовом implementation work order. Список метрик без определения популяции, знаменателя, baseline и правила вывода — не протокол. Список файлов без ответа на предметный вопрос — не исследование.

## Предметная оценка вместо роста тестового покрытия

Каждый Rxx заканчивается двумя разными выводами: **достаточен ли текущий документ/анализ** и **какой будущий опыт покажет полезность способности**. Не писать продуктовые unit/e2e suites и не запускать Windows/Actions для приёмки этих документов. Существующие deterministic safeguards не удаляются; стохастичность не означает, что у системы нет проверяемых свойств.

Обязательная предметная база — LEARNING-EVALUATION-CONTRACT и соответствующие разделы DOMAIN-EXPERIMENT-RECIPES: семь доменов; доменная маршрутизация; качество/допустимость пути; представления/LoRA; dynamic kNN; валидность и полезность DPO; retention; полная стоимость на ПК и пользовательское дообучение. Гибрид может проиграть более простому reference — это допустимый результат опыта.

WorkLeft one-pair/no-repeat, текущий unit-level train-ready payload, training owner и разделение Chinese teacher / exact-pair Astra assessment / student evaluation сохраняются до явного решения надлежащей власти. Bulk reporting не превращать в незаметное batch training. Operational monitoring, используемый для выбора версии, не называть независимой sealed certification. 95% к эталону — исходная цель, не уверенность маршрутизатора и не сегодняшнее измерение.

Примеры в поручениях — **ILLUSTRATIVE / NOT_TRAINING_DATA**. Они объясняют различие правильного и неправильного плана; не создают train-ready пары, не дают разрешения обучать на ответах этой модели и не заменяют разрешённого автора учебных пар.

## Возврат и публикация

Каждая A/B возвращает: task_id; ответ на свой вопрос простыми словами; источники/реально прочитанные spans; заполненный предметный результат; хороший/плохой/граничный walkthrough; факт отдельно от гипотезы; проверку результата; будущую функциональную оценку; ограничения; handoff. Метаданные: requested/actual model, actual effort если известен; subagent_id либо NONE, только когда отдельного вызова не было; при скрытом ID реально вызванного worker — UNKNOWN_IN_SUBAGENT. independent_evidence_count указывается по факту; неизвестный actual model/effort не выводится из запрошенного alias. Не фабриковать вызов Astra Ultra.

Только родитель публикует согласованный результат Rxx. R01–R15 — разрешённые документы replanning; R16–R25 — точно установленные действующие planning документы внутри D по COMMON-CONTRACT. Непосредственно перед записью перечитать изменяемый файл и его blob SHA; при конфликте сохранить чужую дельту. Использовать доступную GitHub write-операцию, без force-push; затем readback по полученному commit. Ошибка одной операции описывается конкретно и не превращается в утверждение «GitHub read-only». Публикация на GitHub не означает изменение диска C:.

Публикация этих промптов не закрывает ни один Rxx. Все 25 статусов определяются реальными результатами и RUN-LOG, а не наличием файла, количеством карточек или этим контрактом.

## Предметные условия решения: дополнение после сверки исходных источников

**Область этой правки — качество будущих опытов и разрешённого dispatch, не новые запуски.** Координатор включает в эффективный prompt только относящиеся к нему условия ниже. Они уточняют существующие DOMAIN-EXPERIMENT-RECIPES и A/B, а не требуют нового журнала, ещё одного полного документа от каждого worker или нового benchmark framework.

### E1. Динамическое расстояние и пригодность индекса

**Владельцы: R06.B → R12 → R18 → R22; R15/R25 проверяют.**

Различи четыре механизма: получение кандидатов из индекса, доменное reranking, выбор k/весов и обучение самой политики. Для предложенного расстояния явно запиши доступные признаки, масштабы, пропуски и версию пространства. Если веса зависят от запроса, выражение может быть асимметричным: не называй его метрикой и не считай любой существующий индекс автоматически корректным для него.

Будущий диагностический опыт: на ограниченном разрешённом наборе с одним пространством сравни выдачу индекса с точным ранжированием **по той же выбранной функции**, затем измерь downstream качество и стоимость. Это не полный перебор производственного корпуса. Candidate-recall/ranking discrepancy и конечная правильность — разные показатели. Убедись, что ни фильтр домена, ни retrieval не получили скрытый правильный ответ. Нулевой знаменатель весов, NaN, пустой embedding, отсутствующие признаки, неизвестный домен и нет соседей имеют заранее названный fallback.

Хороший вывод: «индекс не возвращает полезные объекты для новой функции; нужен bounded reranking/другой candidate path, прежде чем судить об обучении». Плохой: «dynamic kNN хуже — значит доменная гипотеза неверна», когда потеря вызвана несовместимым поиском. Динамический выбор k имеет исследовательский прецедент в [Adaptive kNN-MT](https://aclanthology.org/2021.acl-short.47/), но это не доказательство его выигрыша в XIIGEN.

### E2. Доменная маршрутизация отдельно от подсказанного правильного домена

**Владельцы: R04.B/R06.B/R08 → R13 → R21/R22/R24.**

Для одного и того же задания сохраняй predicted domain(s), независимую эталонную разметку, решение об abstention и итоговый ответ. Known, mixed, ambiguous и unseen domain — отдельные слои оценки. На известных доменах нужны per-domain и macro показатели; на смешанных — определённое правило нескольких меток; на неизвестных — качество обнаружения и цена ложного уверенного маршрута. Доля отказов и точность на принятых решениях показываются вместе: отказ от всех трудных задач не должен искусственно улучшать accuracy.

Разрешён диагностический oracle-domain режим, когда исследователь явно подставляет верный домен, чтобы отделить ошибку router от ошибки solver. Его результат **не** подтверждает самостоятельное domain mapping. End-to-end результат использует собственный router при тех же данных/ресурсах. При несовпадении оценщиков запиши разногласие, а не принудительно сделай один ярлык истиной.

Хорошо: качество решения при верном домене высокое, но модель часто неверно маршрутизирует SQL/описание SQL; задача — исправить router. Плохо: все домены даны извне, отчёт утверждает, что система научилась их распознавать.

### E3. Предметные законы и честные отрицательные примеры

**Владельцы: R02/R08 → R12/R13 → R21/R22.**

Каждый domain passport содержит constraint_id, первичный источник/версию, область действия, единицы/типы, исключения, hard/soft статус и наблюдаемый способ проверки. Источник — предметная спецификация, подтверждённый код/контракт, разметка компетентного эксперта или иное явно обоснованное основание; не уверенность judge. Вкус оформления нельзя без решения владельца объявить абсолютным законом. Дополнительные реальные домены требуют собственных источников, а не копии кодовых критериев.

Для chosen/rejected проверяй общий исходный контекст, допустимость chosen, содержательную причину предпочтения и трудность negative. Один изменённый смысловой фактор полезнее очевидно бессвязного rejected. Ничья, обе плохие стороны, противоречивая разметка или утечка не дают автоматического train-ready разрешения. Если различие касается эффективности двух допустимых путей, отдели preference по цене от factual correctness и согласуй допустимость такого сигнала с текущей DPO-политикой; не меняй её молча.

Хорошо: русский перевод отличается областью отрицания, либо SQL-объяснение правдоподобно, но неверно описывает NULL/cardinality; ошибка подтверждена источником. Плохо: negative выбран только потому, что другая модель его написала, либо chosen совпадает по стилю с judge. Все примеры здесь ILLUSTRATIVE / NOT_TRAINING_DATA.

### E4. Что именно меняется при DPO, LoRA и продолжении после сбоя

**Владельцы: R02.B/R05 → R12/R13/R16 → R18/R22/R23.**

Зафиксируй отдельно: пара допустима; update применён корректно; следующие независимые решения улучшились. Исходный [DPO](https://arxiv.org/abs/2305.18290) имеет определённое preference objective; два поля chosen/rejected сами по себе его не реализуют. Назови policy/reference и фактическое правило, либо честно обозначь другой pairwise learner. [LoRA](https://arxiv.org/abs/2106.09685) — адаптация параметров низкоранговыми матрицами, не tokenizer. Для конкретной матрицы нужны формы, источник входа, обучаемые параметры, выходной потребитель и влияние на геометрию retrieval.

При изменении parser/tokenizer/encoder/нормировки/проекции установи совместимость нового пространства с индексом. Одинаковая размерность векторов не доказывает совместимость. Перед будущим опытом выбери versioned rebuild, доказанную совместимость либо запрет смешивания; учти одновременную память старой и новой версии при безопасном переключении.

**Адресная неоднозначность источников, не новое разрешение:** [WorkLeft RESEARCH-01](../09.09.26WorkLeft-RESEARCH-01-training-quality-speed-accuracy-program.md), «Единый шаг проверки качества», шаг 7, описывает продолжение оценки либо восстановление pre-pair состояния и одну попытку заново. Первичный противоположный текст находится в [WorkLeft RESEARCH-03](../09.09.26WorkLeft-RESEARCH-03-dpo-algorithm-conformance.md), «Полная проверка восьми ворот (добавлено 10.09.2026)», пункт 4: applied-once/awaiting-evaluation и запрет второго применения pair_id. RAG-00 usage-guide остаётся навигацией, не единственным основанием этого вывода. R02/R05 должны проследить действующего владельца/преемника и точную границу восстановленной попытки; R12/R16 согласуют смысл **до** выдачи training prompt. Дата заголовка и слово canon сами по себе не доказывают отмену другого решения. Этот текст не разрешает replay, повторное применение принятой пары, подмену ID или повторный teacher call.

Хорошо: после сбоя читается durable identity, устанавливается фактически сохранённое состояние, затем выполняется только разрешённое продолжение. Плохо: всё начинают заново потому, что отчёт об оценке отсутствует.

#### Адресная часть R02.B: определить смысл восстановления, не запустить обучение

Это конкретизация уже назначенного R02.B, а не дополнительный запуск и не замена его остальных требований. При передаче развернуть её вместе с общими полномочиями и схемой возврата выше; другим Rxx передавать принятое содержание и нужные первичные строки, а не повторять всю проверку.

**Цель человеческими словами.** После прерывания система должна понимать, обновляла ли уже эту пару, какое состояние сохранилось и что разрешено дальше. План не должен одновременно предписывать повторить попытку и запрещать её, оставляя выбор исполнителю.

**Контекст и RAG.** Planning repo `lubochka/xiigen-planning`, исследованный ref `853cc956fb162400724fa249d956fe8fba242dbf`. P1 — `D/09.09.26WorkLeft-RESEARCH-01-training-quality-speed-accuracy-program.md`, строки 1–24, blob `66b4ac6925bb9618a8f05122f4403e7e9afa61f9`; P2 — `D/09.09.26WorkLeft-RESEARCH-03-dpo-algorithm-conformance.md`, строки 1–38, blob `6614be7856e48e710d058bdc14ac827cfb5fccc0`. **Навыки.** Профили S/P/A/H с полными K-путями из раздела Skills; применить source/authority trace, различие факта и выбора, границу learned state и человеческий сценарий. Родитель передаёт реально прочитанные применимые разделы; список профилей не является доказательством загрузки.

**Действия.** Выпиши обе нормы и область каждой. Раздели случаи: пара создана, но не применена; применена и ждёт оценки; уже принята; восстановлен полный pre-pair snapshot; факт применения/полнота восстановления неизвестны. По доступному текущему решению владельца установи, означает ли запрет «не накладывать update повторно на изменённое состояние» или «не использовать pair_id снова даже после восстановления». Не выбери вариант лишь потому, что он быстрее или строже. Если основание не найдено, зафиксируй ровно этот нерешённый policy conflict, допустимые независимые работы и точное решение, нужное R12/R16. R05 получает задачу проверить фактическую state/identity цепь, но R02 не проводит вместо него аудит trainer.

**Результат и приёмка.** В существующий FINDINGS — две нормы с refs/spans, таблица пяти состояний, источник выбранного смысла либо конкретный gap, влияние на первый урок, владельцы R05/R12/R16/R23. В SOURCES — только фактически прочитанные диапазоны. Родитель проверяет, что обе нормы представлены, повторное наложение градиента не смешано с восстановленной попыткой, а невыбранный вариант не объявлен разрешённым. Не создавать новую state machine или файл кода ради этого результата.

**Хороший пример.** «Есть applied-once и сохранённый candidate: отсутствие отчёта не доказывает, что update не было; дальнейшее действие зависит от подтверждённого состояния и действующего правила. Вопрос повторной попытки после полного восстановления выделен отдельно». **Плохой пример.** «Нет отчёта — дать тот же урок ещё раз с новым ID» либо «RESEARCH-01 и RESEARCH-03 говорят одно и то же» без разбора их областей.

**Крайние случаи и мысленное прохождение.** Прерванная запись snapshot; checkpoint и журнал расходятся; snapshot содержит веса, но не optimizer/RNG; решение accepted сохранено, а ответ клиенту потерян. Для каждого назови, что известно, какой вывод запрещён и какое свидетельство/решение нужно следующему владельцу. Это анализ документа, не сообщение об исполненной аварии.

**Будущее наблюдение.** После отдельной разрешённой реализации R22/R23 измеряют качество до/после и сохранение прежних доменов, стоимость продолжения, согласованность состояния и отсутствие неразрешённой повторной мутации. Сейчас все эти runtime-результаты NOT_MEASURED. Возврат — общий RETURN PACKET с выбранным/нерешённым смыслом и адресной передачей, без product PASS и без дополнительного review-счётчика.

### E5. Сравнимые bulk, экономия и предел утверждения «лучший»

**Владельцы: R09/R11 → R13/R14 → R19/R22/R23/R24.**

В будущий bulk report входят A0 (исходный frozen reference), Aprev (предыдущий принятый) и C (кандидат) с точными версиями router, representations, index, adapter, policy, данных и evaluator. Повторно использовать сохранённый outcome можно только при совпадении необходимых условий. Смена панели требует сравнить версии на новой общей панели; более лёгкий B2 не является доказательством обучения после B1. Отдельно показывай operational development, нетронутую certification и prequential качество до обучения на текущем пользовательском вводе.

Прежде чем считать экономию, зафиксируй допустимость результата и необходимый уровень качества. «Лучший путь» означает лучший среди рассмотренных допустимых альтернатив при названном бюджете, **не** доказанный глобальный optimum. Покажи per-domain quality/retention, время ответа и update, RAM/VRAM peak, внешние вызовы, полные persistent bytes и пиковое временное состояние. Учитывай pair authoring/judging, неудачные попытки, retrieval, reindex, snapshot, загрузку и rollback; не суммируй перекрывающиеся интервалы как wall-clock.

Хорошо: меньший индекс снижает время, но ухудшает защищённый домен — заявленный Pareto-выигрыш не доказан. Плохо: маленький LoRA-файл объявлен компактной системой, а растущие граф, cache и snapshots исключены из отчёта. Эмпирические пороги и число независимых семейств фиксируются до подтверждающего сравнения; их отсутствие нельзя заменить удобными числами после результата.

### E6. Принятие плана не требует заранее доказать гипотезу

**Владельцы: R10–R20 и R25; применимо ко всем возвратам.**

Для планового результата требуется конкретный источник, связный выбранный контракт/вариант, контрпример, наблюдаемый критерий и ограниченный следующий шаг. Для эмпирического утверждения нужны actual данные; до них NOT_MEASURED. Не требуй от R12 доказать, что гибрид обязательно победит, иначе первый опыт вновь никогда не начнётся. Требуй от R12 выбрать reference, один различающий challenger и способ распознать неуспех.

R15/R25 рассматривают конкретный кандидат отдельно от автора и по фактической доступной конфигурации Astra Ultra; project alias не является доказанным API id. Один автор, названный затем reviewer, не создаёт независимости. Без отдельного вызова — NOT_PERFORMED. Independent review проверяет обоснованность опыта и полное сохранение исходных обязательств, а не заменяет качество на доменных задачах собственным мнением.

Хорошо: R25 передаёт готовый минимальный implementation prompt и первый опыт с improve/regress/inconclusive, без новых общих исследований. Плохо: ещё один круг оформления после готового handoff либо декларация «система обучена» по наличию 25 карточек.
