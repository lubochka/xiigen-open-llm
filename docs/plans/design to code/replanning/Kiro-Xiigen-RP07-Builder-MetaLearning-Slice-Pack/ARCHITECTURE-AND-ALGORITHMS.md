# RP07 architecture — graph teaching opportunity → Student utility → learned Builder policy

**This is an implementation hypothesis with source-traced existing interfaces, not a claim that a Builder trainer already exists.** Find and reuse current machine-owned state/consumer before introducing any component.

## Four distinct levels + two distinct learners

- **ILearningUnit:** declared domain and input/output vector/token schemas; typed many→many queryable candidates, association and provenance. A correct local answer is still meaningful without Builder.
- **ILearningFlow:** typed connections between Unit outputs and next Unit inputs; corrections change compatible transfer/selection rather than silently recoding meanings.
- **ILearningOrchestrator:** async lawful bounded graph/path execution, cancel/timeout/dependency ordering, fan-out and whole cost; not winner authority merely because branch completed first.
- **ILearningDynamicGraph:** second/third-order relational motifs, lawful composing and learned graph policy across pattern order; RP04 owns its optimizer/consumer. Graph is not a fourth independent copy of DPO trainer.
- **Student learner:** existing ILearningMachine + DPO trainer updates Student parameter recipient (project LoRA or actual enumerated state), not necessarily Builder.
- **Builder learner:** validated *different* machine-owned state B0→B1 changes future teaching candidate ranking/construction. An internal selector table, reranked neighbor or graph topology count alone is not evidence of meta-learning.

## Causal data route and recipients

Ordinary Student execution → lawful independent weakness diagnosis → CODEX Astra 6 UltraCode chooses permitted task / objective → lawful Unit/Flow/Orchestrator/Graph candidates & builder policy rank teaching opportunities → allowed external open Chinese model authors two **final** exact DPO sides → separate CODEX Astra exact-byte pair judge → admitted Student pair & once-only DpoTrainer update → frozen held-out Student utility (unseen family) and whole-PC costs → lawful meta-preference between comparable teaching strategies → machine-owned Builder B0→B1 update → persisted accepted Builder state → next cold ordinary Builder call, again governed teacher/pair judge.

All transitions include domain passport, material rights, source-family partition, deterministic eligibility/type/schema/version checks, exact context/serialization and parent-state identities. Passing a graph-candidate ID to a report is **not** executing its output. A semantic match that discards critical input differences is **not** valid pair creation.

## Boundaries/negative path

- If RP04 route is untrained, use named frozen legal route control; do not claim policy generalization. RP07 may still validate Builder side separately.
- If Builder trained state is absent, first output an exact nearest code-owner seam; no second framework and no trained-state flag.
- If Student no-update wins, a constructed valid pair remains valid but utility label is NEGATIVE/INCONCLUSIVE; do not promote B1 from preferred formatting.
- If two lawful routes give same output, require additional protected diagnostic families rather than assuming one must be rejected.
- If an approved deterministic solver beats Builder, retain it as winner. Deterministic provenance is not a reason for DPO rejected.
- If source rights/budgets or independent evaluator are missing, conclude NOT_RUN_AUTHORIZATION / INVALID_EVIDENCE for dependent claim and continue read-only lanes.
