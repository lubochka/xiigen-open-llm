# RP14 — real-world domain laws, governed examples and blind questions

## What qualifies as a domain rule
A law passport is a sourced, versioned set of predicates that determine **what makes an output correct and legal for this task/domain**, not a convenient class label or a synthetic change to a programming-language axiom. Preserve domain vs intent vs language vs stack vs project vs current effective policy vs Student identity. Every observation records its source, effective period, rights, confidence and owner. Unknown/mixed domains may abstain and hand back a lawful deterministic path.

## Immediate C# pilot (law-version shift without inventing language changes)
**Source:** actual project contract/version chosen by authorized owner and pinned before experiment. Illustrative synthetic setup only: v1 API `ClientId?: string` is optional; approved v2 `ClientId: string` is required for a particular project's validator. C# nullable syntax, `null` semantics and XML docs do **not** change. Positive v1 example is *not* a valid v2 solution; it may remain a warning reference.
- GOOD v1: accurately documents optional v1 behavior with version tag; GOOD v2: describes required v2 field and valid migration, correct null handling.
- BAD: copies v1 nullable docs into v2; invents language law that `null == 0`; uses old kNN top1 despite version mismatch.
- EDGE: missing version in user question, mixed version migration, old docs still needed, strong misleading old-law neighbors, domain classifier confidence tie. Require scoped clarifying question/abstain or permitted default, never assert version from similarity.

## EN→RU independent law panel
Use a rights-cleared example in which the source policy really changes between documented versions; preserve **negation, scope, exceptions, dates and modality** (e.g. “unless”/“only if”) as semantic invariants. Do not make a law transition from a mistranslation.
- GOOD: v2 translation preserves “not permitted unless condition X” and its effective scope; warning neighbor explains old v1 wording.
- BAD: drops negation or treats an unofficial user correction as new binding policy.
- EDGE: ambiguous reference for “unless”, mixed English/Russian clauses, version omitted, future-effective rule vs present requirement, conflicting authoritative excerpts.
