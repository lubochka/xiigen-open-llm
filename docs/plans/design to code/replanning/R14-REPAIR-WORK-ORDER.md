## 7. R14-B — capability milestones

Build at least these capability nodes, with exact prerequisites and observations. **Do not serialize them by label.** The execution edge exists only when an evidence dependency exists:

### M0 — first valid useful lesson
DPO pair or other selected E1–E4 intervention reaches real mutable state, ordinary consumer and same-panel observation.

### M1 — second structurally different domain
Show that the first effect is not only one source-family artifact. Do not call this universal transfer.

### M2 — domain-aware mapping + representation + retrieval
Oracle-domain vs predicted-domain; raw/canonical/token/feature/vector/index identity; hard-law filters; fixed baseline vs learned rerank/aggregation; domain-dependent dynamic-k hypothesis.

### M3 — Flow correction
Freeze Units where possible and change learned relation/correction only. Measure whether path/answer quality improves and whether the learned relation reaches its ordinary consumer.

### M4 — asynchronous Orchestrator path selection
Measure dependency/path selection and cost, including failed/cancelled branches; do not confuse solver quality with router quality.

### M5 — DynamicGraph higher-order transfer
Known Units/relations, unseen lawful compositions. Test whether graph learning improves composition/path choice without hiding improvement in lower-level solver changes.

### M6 — compact PC continual learning + feedback
Full footprint: model/reference/adapters/optimizer/encoder/index/graph/cache/snapshots; new-user-feedback admission; rollback; retention; growth bulk-to-bulk.

### M7 — DTC/IDE/native/host delivery completion
All retained product obligations after learning-path evidence, with host-specific gates only where causally required.

## 10. R14-E — domain/representation/kNN/LoRA requirements

R14 must keep these visible in the roadmap instead of postponing them indefinitely:

### Domain mapping
Measure label/multilabel/unknown plus downstream usefulness. Compare oracle-domain vs predicted-domain with same solver/context.

### Domain token/vector representation
For each selected domain family identify semantic distinctions that must survive normalization/tokenization/projection. Same shape is not semantic compatibility.

### Dynamic kNN
No universal “best k”. Define lawful candidate pool, feature family, scaling/normalization, metric or score assumptions, k/radius bounds, exact-search diagnostic, ANN compatibility and learned target. Changing k manually is not learning.

### DPO pair quality
Hard realistic negatives, no forced preference for TIE/BOTH_BAD, no deterministic-correct rejection by origin, exact projected-pair reassessment after semantic mutation.

### LoRA/projection
LoRA is a parameterization technique, not automatic vector semantics. Name source representation, target representation, trainable parameters, frozen state, loss, consumer, version, rollback and task-level observation.
