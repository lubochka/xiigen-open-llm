# Как доказывать обучение, а не рост тестового покрытия

**13.10.2026 · редакция 2 · DRAFT методики. Предложенные измерения не выполнены; эффективность XIIGEN не объявляется доказанной.**

Этот контракт относится к тем же R01–R25. Он задаёт способ исследования и будущей функциональной оценки, не добавляет проходов или программный benchmark framework. Цель — раньше реализовать минимально необходимые динамические алгоритмы и учить систему на новых разрешённых задачах, измеряя правильность, перенос, время и всю стоимость на ПК.

## 1. Что меняется в методе

**Успех — полезное изменение решения новых задач, а не число тестов, коммитов, документов, пар или зелёных jobs.** Нестохастические гарантии состояния/данных и статистическая оценка обучаемого поведения — разные предметы. Стохастичность не делает оценку невозможной; обычное покрытие кода не доказывает обобщения.

В документных R01–R25 не создавать и не запускать product unit/integration/e2e/coverage suites, Windows/GitHub Actions, product build/trainer, новые платные product teacher/generator кампании. Не менять code/tests/workflows/weights/datasets/core skills, не делать cleanup. Разрешены чтение существующего кода/evidence, аналитика, предметное прохождение сценариев, проверка документов/diff/ссылок и GitHub-публикация разрешённых документов.

Исторические требования full green после каждой правки и дополнительные 30/50 проходов не являются приёмкой этой программы. Не удалять существующие tests/workflows и не объявлять пропущенный запуск успешным. Во время будущего опыта сохранить полномочия, provenance, совместимость и восстановление; выявленный реальный риск не исчезает от переименования теста в эксперимент.

Дополнительные найденные домены не исключать. Все S00–S10, требования вне слайсов и направления DPO/DynamicGraph, DTC, IDE/клиенты сохраняются. ## 3. Два результата каждого Rxx и четыре исхода опыта

**Сегодняшняя приёмка:** конкретный результат назначенного исследования/анализа/изменения, источники, существенный контрпример, ограничения и пригодная передача. Не требуется measured gain, поскольку обучение сегодня не запускается. Полный промпт Rxx определяет конкретный предмет.

**Будущая функциональная оценка:** domain/level, задача и источник эталона, data lineage, baseline, меняемый механизм, общий набор сравнения, primary metric, защитные показатели, цена, предел и наблюдение, опровергающее гипотезу. Для раннего source-only прохода допустима точная передача этой части назначенному R13/R21/R22, но не обещание «потом как-нибудь проверим».

Различать результаты будущего опыта:

| Исход | Значение | Действие |
|---|---|---|
| IMPROVE | Заранее заданный полезный эффект подтверждён, ограничения соблюдены | Применить действующую политику принятия; не повышать до готовности всех доменов/поставок |
| REGRESS | Есть ухудшение или нарушена защищённая способность/жёсткое ограничение | Не продвигать кандидата; восстановить допустимое состояние по принятому правилу |
| INCONCLUSIVE | Измерение пригодно, но различие недостаточно определено | Сохранить parent, зафиксировать неопределённость и следующий ограниченный вопрос |
| INVALID_EVIDENCE | Утечка, разные задачи/рубрики, неизвестные версии или неполные результаты испортили сравнение | Не делать вывода о знаке эффекта; исправить конкретный методический дефект |

Отсутствующие измерения — `NOT_MEASURED`, не ноль. Валидный отрицательный опыт может завершить исследовательскую работу; его нельзя объявить успешным обучением. INVALID_EVIDENCE нельзя считать доказательством отсутствия эффекта.

## 4. Паспорт домена и измерение domain mapping

Для каждого домена определить:

`domain_id/version; task families; input/output types; accepted domain labels; source of truth; hard laws; empirical regularities; user preferences; tokenizer/parser/embedding versions; eligible neighbors; distance/k/mixture candidates; allowed solver routes; DPO rubric; adapter target; data splits; primary quality metric; protected capabilities; resource envelope; owner`.

Законы разделять: **жёсткие ограничения** типов, размерностей, причинности и исходной задачи; **эмпирические закономерности** с исключениями; **предпочтения** стиля/пользователя. У каждого есть источник, применимость, исключение и версия. Экспертное мнение не становится физическим законом. Для актуальных языковых/технических правил будущий исследователь использует первоисточник соответствующей версии.

| Домен | Существенное представление | Контраст, который обязан различать экзамен | Полезный результат |
|---|---|---|---|
| EN↔RU | Контекст, неоднозначность, отрицание, числа/единицы, сущности, термины | Похожая фраза с обратным смыслом; правильный смысл с другим допустимым стилем | Смысловая корректность и сохранение существенных фактов, не совпадение одной строки |
| Оркестрация | Цель, доступные действия, зависимости, типы, ресурсы, состояние | Короткий недопустимый путь против допустимого; два правильных пути разной цены | Достижение цели с соблюдением ограничений и меньшей полной стоимостью |
| Figma→HTML+CSS | Дерево, геометрия, layout, типографика, связи и поведение | Хороший один viewport против нескольких; красивый, но другой макет | Визуальное/геометрическое и функциональное соответствие на заданных разрешениях |
| C# documentation | AST/контракты, ветвления, async, side effects | Правдоподобная выдуманная гарантия против подтверждённого объяснения | Точность утверждений и полнота существенных фактов по исходному коду |
| Angular documentation | Template/component, dataflow, события, состояние | Неверная причинность обновления или lifecycle | Правильное объяснение UI/state и его ограничений |
| SQL documentation | Схема, ключи, NULL, JOIN/cardinality, транзакционные условия | Правдоподобное неверное описание NULL/JOIN/гарантии | Корректная семантика и сохранение ограничений |
| DPO Builder | Ошибка ученика, контекст, кандидаты, причины предпочтения и происхождение | Both-bad/tie, лёгкий бесполезный negative, утёкший экзамен | Пригодная пара и отдельно польза её разрешённого применения на новых задачах Student |

### Отделить ошибку домена от ошибки решателя

Для панели задать допустимый домен или множество доменов по предметному смыслу, не по ответу текущего router. Смешанные задачи могут требовать нескольких доменов; неизвестному запросу разрешены отказ, уточнение или безопасный fallback. Нельзя всегда принудительно выбирать один известный класс.

Измерять per-domain precision/recall/F1 и macro-F1 там, где схема разметки это допускает; confusion matrix; качество многометочной маршрутизации; частоту неверенного принятия неизвестного домена; качество и долю ответов при разных порогах отказа. Калибровку confidence оценивать только при наличии вероятностного смысла score. Показывать поддержку каждого домена и неизвестные случаи, а не только общий средний результат.

**Диагностическое сравнение:** тот же solver и то же состояние получают сначала фактический route, затем экспертно допустимый домен. Разница downstream quality показывает возможную потерю из-за routing. Это не продукционная возможность знать правильный домен заранее и не учебные targets из закрытого экзамена. Когда допустимых путей несколько, не штрафовать корректный результат только за отличие от любимого пути оценщика.

Владелец фактов — R06/R08; протокола — R13; требований — R16; доменных наборов — R21; первого рецепта — R22.

## 5. Разделить токенизацию, представление и LoRA

Цепь: **сырой ввод → tokenizer/структурный parser → признаки/embedding → доменная проекция → поиск/выбор пути → решение → выходное представление/декодирование**. Для каждого перехода нужны вход/выход, тип, форма, смысл, версия и реальный producer/consumer. Token IDs, плотные векторы, структурные признаки и кодбук — не синонимы.

LoRA адаптирует выбранные матрицы низкоранговым обновлением, обычно `W = W0 + (alpha/r) BA`. Это не самостоятельный tokenizer. Когда нужна проекция результата в доменное пространство, R05/R12 должны назвать матрицу, формы, обучающую цель, данные выравнивания и потребителя. Если требуются дискретные vector tokens, отдельно определить quantizer/codebook/decoder; не приписывать эти функции LoRA без кода. [LoRA: первичный метод](https://arxiv.org/abs/2106.09685).

Проверяемая гипотеза — новое представление сохраняет существенные различия и улучшает downstream поведение при заданной цене. Сравнить существующее/frozen представление с одним выбранным вариантом: смысловые контрасты, retrieval relevance, domain/path quality, output semantics, unsupported claims по применимости. Reconstruction/alignment loss и shape match — диагностические показатели, не конечная приёмка. Меньше токенов без сохранённого смысла не выигрыш.

Версии пространства и индекса связаны. После изменения encoder/проекции старые векторы могут стать несопоставимыми даже при той же размерности. Выбрать согласованную миграцию, rebuild или доказанный compatibility path; включить его время, память и хранение в стоимость. No-adapter, frozen-adapter и trained-adapter сравниваются в одинаковых условиях; где прямое отключение ломает типовой контракт, использовать совместимый reference, а не заведомо неработающую ablation.

## 6. Динамический kNN: исследовать функцию, а не только число соседей

Для домена определить допустимых соседей, признаки, нормировку, расстояние/score, веса, k, temperature, смешивание с другими решениями, отказ и изменяемое состояние. Проверка жёсткой совместимости выполняется отдельно от мягкого сходства. Тип/версия, единицы или незаконное происхождение не должны компенсироваться высоким embedding score.

**Кандидат для исследования, не утверждённый универсальный алгоритм:**

`D_d(x,z) = sum_j w_j(d,x,state) * normalized_distance_j(x,z)` для допустимого z.

Сумма весов/масштаб выбираются в определённой нормировке; k/веса/смешивание могут зависеть от домена, плотности, неопределённости и бюджета. Для непрерывного пространства возможна PSD-метрика; для layout — геометрические отношения, для кода — структура/типы, для текста — контекст. Выбор основан на R04–R08 и dev-измерениях, не на вкусе автора. `k=0`/отказ допустимы, когда полезных соседей нет.

Если query-conditioned score не является метрикой, не предполагать корректность существующего ANN-индекса. Для coarse retrieval + reranking измерить, не теряет ли coarse stage нужных кандидатов; на небольшом размеченном поднаборе сравнить с точным поиском. Полный rebuild после каждой правки может съесть выигрыш inference.

Последовательность сравнений: existing reference → domain-aware distance с прежним k → adaptive k/weights/mixture, **по одному фактору**, не полный перебор. Измерять relevance/recall соседей на подходящем поднаборе, конечную правильность, p50/p95 retrieval и total time, index bytes/update/reindex cost, редкие/чужие домены. Изменяемый config не равен обучаемой политике; пополнение kNN-memory не равно изменению весов.

[Adaptive kNN-MT](https://aclanthology.org/2021.acl-short.47/) даёт первичный исследовательский пример адаптивного выбора соседей в переводе. Он не доказывает преимущество выбранной функции во всех доменах XIIGEN. Отсутствие выигрыша означает оставить более простой reference, а не подогнать панель.

## 7. DPO: качество пары и реальный обучающий эффект

Пара содержит `pair_id; domain/level; same prompt_context_id; chosen; rejected; preference_reason; violated_constraint; provenance; generator/reviewer identities; split lineage; student_before; applicable update target`. Оба ответа решают одну и ту же задачу в сопоставимых условиях.

**Допуск пары:** chosen удовлетворяет запросу; rejected демонстрирует правдоподобную конкретную ошибку либо худший допустимый компромисс по заранее заданной рубрике. Хороший negative отличается причиной, которую должен выучить Student, а не только длиной/стилем. Ничьи, оба неверных ответа, неизвестное происхождение и спорная разметка карантинируются. Более хороший из двух плохих ответов не автоматически положительный пример. Разные model names не доказывают качество пары; политику генераторов брать из действующего решения.

Отдельно различить стандартный вероятностный DPO и проектный preference learner. Для стандартного метода проверить реальную objective/call chain:

`L = -log sigmoid(beta * [(log pi_theta(y+|x) - log pi_ref(y+|x)) - (log pi_theta(y-|x) - log pi_ref(y-|x))])`.

Нужны reference policy, completion masks, корректные контекст/токены и обновляемые параметры. Для непараметрического графа/ранжировщика назвать собственное правило, а не выдавать изменение счётчика за DPO objective. [DPO: первоисточник](https://arxiv.org/abs/2305.18290).

**Польза пары:** после разрешённого обновления сравнить ответы на новых задачах того же семейства способности и на защищённых прежних навыках. Saved JSON, loss или новый checkpoint hash не доказывают пользу. Builder имеет два результата: доля пригодных предложений и downstream gain/стоимость принятого улучшения у получателя. При запрете повторного обучения одних pair_id нельзя заявлять причинную оценку каждой пары из нескольких переобучений; указывать предел доступного дизайна.

Проектные роли сохраняются: допущенный открытый китайский teacher либо разрешённый собственный Builder создаёт candidates; CODEX `gpt-6-astra`/`ultra` выбирает задачу и оценивает точную пару по role contract; Student учится; независимая оценка Student отделена от авторства пары. Экспертные платные ответы и закрытые задания не копируются в training targets. Текущий допуск провайдера/источников не выводится из старого shortlist.

Current train-ready `GraphDpoPair(Level="unit")` имеет конкретный UnitId; graph/path/edge/order assessment не расширяет payload автоматически. Training owner — соответствующая ILearningMachine. Другой уровень или другое правило — явное архитектурное решение и миграция R12/R16, не удобное переименование.

## 8. Bulk-to-bulk и защита от самообмана

**Bulk — отчётная партия новых разрешённых уроков, не автоматическое разрешение minibatch gradient, replay, новых эпох или повторного pair_id.** WorkLeft one-pair → full snapshot → applied-once → same evaluation → accept/rollback/ambiguous сохраняется до явной миграции. Менять ID старому примеру ради повтора нельзя. Общий bulk-отчёт не требует заново сертифицировать продукт после каждой пары; цена и частота operational оценки отдельно определяются R13 в рамках действующей one-pair политики.

### Разделение данных и состояния

Отдельны train, development и заранее изолированная certification. Разделять по исходному объекту/семейству/проекту и времени до создания перефразировок, рендеров и пар. Производные одного объекта не дают независимых наблюдений. Закрытый экзамен/ответы не уходят teacher, Builder, retrieval или настройке гиперпараметров.

Повторно используемая operational панель, влияющая на выбор обновлений, является development/monitoring, а не нетронутой certification. Новую confirmation-панель резервировать заранее; частоту обращения и правило остановки фиксировать. Не менять rubric до «хорошего» результата.

Состояние сравнения — не только weights: model/tokenizer/encoder, adapter, router, datastore/index, graph policy, relevant caches/config и evaluator имеют согласованные версии. Сохранить полное изменяемое training state для rollback: optimizer/scheduler/scaler/RNG/counters/manifests/accepted and pending IDs и другие реально найденные компоненты. После update нельзя одновременно менять encoder, данные, router и рубрику, затем приписывать всё DPO.

### Сопоставимое сравнение

На панели `E_b` оценить исходный baseline `S_0`, предыдущий принятый `S_prev` и кандидата `S_b`, насколько это разрешено ресурсным контрактом. **Одна и та же панель для сравниваемых версий.** Если добавлена новая панель, обе версии оцениваются на ней; `score(S_b,E_b) - score(S_prev,E_prev)` не является оценкой эффекта обучения.

Для домена d и независимого семейства i: `delta_i = quality(S_b,i) - quality(S_prev,i)`; `Delta_d = mean(delta_i)`. Сначала агрегировать связанные варианты внутри семейства, затем оценивать paired uncertainty по независимым семьям. Macro-показатель не должен скрывать малый или ухудшившийся домен. Показывать raw counts, семейства, состав сложности и ошибки.

R13 до основного опыта выбирает минимально полезный эффект, защищённые домены/допустимые границы регресса, precision/sample budget и правило остановки. Размер выборки обосновывается pilot/вариативностью и назначением вывода, не магическим числом 100/1000. Если бюджет даёт только слабую точность — exploratory/INCONCLUSIVE, не уверенное подтверждение. Поправки при множественных подтверждающих выводах или отдельный confirmation этап предусмотреть заранее; repeated peeking не маскировать одним независимым выводом.

Повторный inference при фиксированных состояниях может измерять вариативность ответа, но **не разрешает повторно обучать те же пары**. При отсутствии допустимых training replicates честно ограничить выводы о вариативности обучения.

### Обязательный отчёт

`bulk_id; hypothesis; source/code/state versions; domains/levels; train/pair lineage; panel/split/version; evaluator/rubric/config; n_independent_families; quality before/after/delta/uncertainty; mapping/confusions/OOD; valid and failed paths; law violations; pair valid/rejected/tie counts; accepted/rejected/ambiguous updates; retention; time; RAM/VRAM; complete bytes; failed attempts; decision; evidence refs`.

Хранить raw observations и знаменатели для воспроизводимого пересчёта. Не заменять отсутствие измерения нулём. Число параметров/узлов/пар — описание нагрузки, не метрика компетентности.

## 9. Лучшая комбинация и компактность на ПК

«Лучший путь» — лучший среди **изученных допустимых альтернатив** при заданных ресурсах, не доказанный глобальный оптимум. Сначала ограничения и достижение цели, затем цена. Недопустимый короткий путь не выигрывает. При нескольких равно полезных путях допускается множество правильных решений.

Сравнить deterministic-only, learned-only, existing retrieval и hybrid там, где они действительно применимы и имеют сопоставимые данные/бюджеты. Отсутствие применимого pure baseline указать, не конструировать заведомо плохого соперника. One-factor ablations делаются после минимального первого опыта и только под конкретный вопрос.

На задачах с корректными решениями можно показывать относительную цену выбранного пути к лучшему найденному допустимому: `cost_selected / cost_best_observed - 1`, когда знаменатель положителен. Рядом всегда показывать долю решённых/неверных/отклонённых задач; исключение всех провалов из средней latency и accuracy создаёт ложный выигрыш. Для разных hardware/config сравнение отделять или нормировать по заранее описанному методу.

Полная latency: routing, tokenization/encoding, retrieval/reranking, tool/solver calls, fallback, decoding и ожидание. Для асинхронных путей отдельно wall-clock и суммарное compute/call time, без двойного счёта. Сообщать p50/p95, cold/warm условия и долю внешних вызовов. Цена обучения включает создание и оценку всех кандидатов, неудачные/отклонённые попытки, update, evaluation, index rebuild и snapshot/publication там, где они входят в опыт.

Компактность — **вся система**: базовые веса, adapters, optimizer/activations, embeddings/datastore/index, graph, retained examples, cache, snapshots и временные файлы. Отдельно persistent bytes и пиковые RAM/VRAM. Меньший LoRA-файл не доказывает меньшую память исполнения. Вынос хранения/вычисления наружу показывать явно, не называть локальной экономией без полной цены.

R23 проверяет целевой CPU/GPU/RAM/VRAM/storage по фактическим данным и задаёт bounded input length, candidates/k, concurrency, update size, snapshot/index growth. Не обещать, что схема влезет в ПК до измерений. Сравнивать качество при фиксированном бюджете и цену при сопоставимом качестве; Pareto-компромисс показывать, а не прятать в одном произвольном score.

## 10. Продолжение обучения на пользовательском вводе

Сначала ответ/оценка текущего состояния на новом вводе, затем разрешённая обратная связь. Это prequential observation: нельзя сначала обучиться на текущем ответе и представить повтор как качество до обучения. Источник, права/согласие, домен, противоречие hard law и шум проверяются до превращения коррекции в teaching signal.

Новый разрешённый сигнал → карантин/допуск → домен/уровень → новая пара → candidate update → сравнение новых и прежних навыков → принять/откатить/неопределённость. Пользовательская коррекция не истина автоматически; спорное не обучается насильно. Версии router/encoder/index/graph/adapter согласованы; изменение представления включает цену миграции.

При resume сначала определить состояние прежней операции и уже применённого pair_id. Timeout не доказывает, что update не состоялся. Не повторять мутацию и не откатывать состояние параллельно с ещё живым trainer. Rollback восстанавливает найденный state, но не возвращает уже потраченные средства или раскрытые данные. Не вводить replay, новые эпохи или политику хранения пользовательских данных без явного решения.

Измерять качество до обучения, скорость адаптации, сохранение прежних доменов, full cost одного полезного исправления и рост памяти. Разные Student по доменам отделить от transfer/forgetting одного Student.

## 11. Экспертиза Astra Ultra

R15/R25 требуют отдельного reviewer в запрошенной конфигурации `gpt-6-astra`/`ultra` из project role contract. Назначение в тексте не утверждает доступность инструмента или выполненный вызов. Записать requested и actual model/effort/identity, reviewed SHA, источники и результат. Нет отдельного вызова — `NOT_PERFORMED`; self-review так и называется. Reviewer не переписывает собственный предмет и не принимает сам свою правку как независимый эксперт.

Рецензент восстанавливает ожидания по первоисточникам, прослеживает реальные call chains, проверяет измерения и оспаривает гипотезу гибридного выигрыша. Рассматривает неверный/новый/смешанный домен, both-bad пару, ошибочный preference sign, несовместимые векторы, leaked panel, недопустимый дешёвый путь, рост памяти, noisy feedback, отсутствие реального update. Итог — продолжить / исправить конкретное решение / изменить гипотезу / недостаточно данных, не общий сертификат продукта.

При оценке ответов скрывать принадлежность before/after, менять порядок, контролировать предпочтение длины/своих ответов, сравнивать с предметным свидетельством и разбирать разногласия. Сильная модель не непогрешимый эталон. [Первичное исследование LLM-as-a-Judge](https://arxiv.org/abs/2306.05685). Авторитет reviewer не заменяет measured gain.

## 12. Минимальный путь к первому уроку и готовое поручение

Первый опыт должен ждать **только реально необходимых** условий: выбранный совместимый Student/state; разрешённые данные и реальные роли; работающее обновление через существующего owner; полный state boundary/restore; пригодная before/after оценка; измерение цены и ограничение побочных эффектов. Если код уже обеспечивает это, использовать его. Недостающий контракт решается в R12/R18; недостающий минимальный код оформляется точным work order.

Не требовать заранее идеальных domain tokenizers, динамического kNN, всех LoRA targets и всех S00–S10 поставок. Последовательность: baseline → один необходимый dynamic seam → одна новая допустимая пара/update/evaluation → решение → второй действительно иной домен → следующие различающие опыты. Нулевой эффект даёт следующий вопрос, не разрешение менять эталон. DTC/IDE/Windows release остаются отдельными обязательствами; действительный blocker локального учебного пути сохраняется, посторонний fixture не становится универсальным условием.

Полные поручения: [R01–R10](LEARNING-WORK-ORDERS-01-10.md), [R11–R15](LEARNING-WORK-ORDERS-11-15.md), [R16–R20](LEARNING-WORK-ORDERS-16-20.md), [R21–R25](LEARNING-WORK-ORDERS-21-25.md). Каждый эффективный prompt включает роль/skills, точные inputs/spans, current/not task, шаги, конкретный выход, сегодняшнюю приёмку, будущий опыт/владельца, good/bad, allowed/forbidden scope, лимит и handoff. Не грузить весь этот контракт каждой модели: передать применимые разделы без потери исходных обязательств.

Результаты хранятся в пяти существующих носителях COMMON-CONTRACT, а изменения R16–R25 применяются к настоящим live planning документам.
