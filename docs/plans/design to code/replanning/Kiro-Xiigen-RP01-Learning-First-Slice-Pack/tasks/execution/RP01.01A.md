## Выполнение

1. Сопоставить exact bytes на author capture, J, reopen, material и trainer. Raw UTF8/CRLF/Unicode/case/пунктуация не нормализуются после J. Source transport digest и token-framing identity различны; одинаковый hash metadata не доказывает одинаковые tensors.
2. Найти точный tokenizer boundary contract. **Не предполагать `Encode(x+y)=Encode(x)+Encode(y)`**. Если действующий v2 сознательно сегментирует prompt и completion, проверить его совместимость с actual generation conditioning/BOS/EOS и замаскированной целью; если используется joint tokenization, граница target должна корректно учитывать boundary merge. Не менять framing молча — нужен versioned contract/consumer migration лишь при доказанной несовместимости.
3. Установить точное соответствие causal target: logit[j−1] предсказывает token[j]. Prompt остаётся conditioning, но не получает response loss; right padding исключён; EOS включён только по явной выбранной политике. Не добавлять separator после оценки пары ради удобного test fixture.
4. Проверить nonempty valid response tokens, длины, vocabulary/context bounds и сохранённый семантический contrast. Collapse chosen/rejected в identical training representation→невалидный сигнал, определить data/tokenizer owner; не добавлять случайный token и не менять Chinese стороны.
5. Только если есть defect: минимально исправить один actual carrier/consumer и совместимые version checks. Если carrier и consumer требуют разных владельцев, разделить по exact files: material owner возвращает schema/boundary patch; consumer owner принимает эти поля. Оба получают этот input contract и свой GOOD/BAD/EDGE/stop; не назначать абстрактное «проверь DPO».
6. Return к state-aware dispatcher. 01B не становится автоматическим следующим gate, если её objective/state уже исправны.

## Конкретный ручной пример и минимальная проверка

Иллюстративная последовательность `[BOS,p1,p2,y1,y2,EOS,PAD]`. Если выбранная политика включает EOS, response targets — позиции 3,4,5, соответствующие logits 2,3,4. Prompt targets 1,2 и PAD 6 не входят в loss. Это объяснение инварианта, не новые учебные данные и не требование дополнительной suite.

GOOD: `x?.Length` сохраняет '?' до actual training frame, J/side hashes и mask совпадают с выбранным контрактом. Почему: не потерян C# закон.

BAD: `Encode(Compact(x)+" "+Compact(y))` изменяет judged task; loss включает prompt/PAD; arbitrary `[0]` заменяет invalid tokens. Почему: DPO оптимизирует не оценённую пару. Remedy: восстановить actual contract у producer, не подгонять expected values.

EDGE: пустой response, decomposed Unicode, CRLF, unknown token, BPE boundary merge, context overflow, EOS policy mismatch, обе raw стороны различны, но tokens одинаковы. При каждом — typed refusal/точный defect, не silent truncation/re-authoring.

Для изменённого инварианта переиспользовать ближайшую **существующую** focused проверку и только реально недостающую отказную ветку. Без изменений→0 новых tests. Не вызывать реальный Student для проверки off-by-one и не запускать Windows matrix.
