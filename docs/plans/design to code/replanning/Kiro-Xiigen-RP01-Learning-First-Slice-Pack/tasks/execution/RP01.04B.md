## Source facts и необходимые различия

Current KnnLogicalUnit запрашивает Search(query,_k), возвращает `bestExample.Output` из hits[0], остальные ids добавляет в evidence. Vectorize — token/predicate count tiers, а low-confidence floor добавляет warning, не гарантированный отказ. Train clamp делает safeK≥1. Поэтому proposed k=0 нужно реализовать как **явный skip-retrieval/fallback у владельца policy**, а не предполагать, что существующий класс поддерживает k=0. Это факты одного example-memory consumer, не вся grammar architecture.

**Две разные допустимости:** (1) можно ли читать/использовать пример в данном домене/tenant/source-purpose; (2) можно ли принять его output как итоговое решение. Negative/warning память с законно сохранёнными ошибками **не удаляется** только потому, что output неверен: она должна предупреждать, но не выдаваться как accepted result. Arbiter signals участвуют до generation, а selected arbiter verdict управляет acceptance после generation. Budget/близость не отменяют rejection.

## Кандидатный алгоритм для конкретного RP02 owner

1. Определить domain/version/scope/referent uncertainty и schema совместимость. Rights/purpose/tenant/representation compatibility фильтруют **evidence pool**. Predicted domain с высокой неопределённостью требует controlled multi-pool/UNKNOWN path, не ошибочного жёсткого отсечения всех альтернатив.
2. Получить кандидатов существующим exact/BM25/ANN retrieval. Разнести positive, negative, warning роли; сохранить source/evidence/arbiter reasons. Не превращать все соседи в равноправные proposed outputs.
3. Для task-output candidates применить **контекстные** law constraints. C# next token должен быть допустимым продолжением текущего AST/parser state; незавершённый prefix не равен синтаксически неправильной полной программе. RU согласование относится к конкретному referent/dependency; вероятностный POS guess не превращать в неоспоримый hard law. SQL `col = NULL` — допустимое выражение с UNKNOWN, но неверный способ выполнить задачу «выбрать NULL-строки»; ошибка зависит от задачи, не от самой подстроки.
4. Learned reranker-кандидат `r_theta(query_features, neighbour_features, relations, example_role, arbiter_history)` должен иметь named state, feedback/loss/пары, version, update owner и actual consumer. Не выдавать фиксированную hand-coded score формулу за обученную policy. Если используется learned asymmetric score, сначала rerank на фиксированном retrieved pool; не подменять им ANN distance без проверки совместимости и recall.
5. Dynamic k/radius/stop policy учитывает domain/context, доступные legal candidates, confidence/uncertainty, diversity, ожидаемую пользу дополнительного retrieval и budget. Начать с fixed-metric/fixed-k comparator; параметры/thresholds калибровать на DEV и freeze до SEALED. Исторические 0.50/0.70 similarity thresholds разных owners/scales нельзя объявить универсальными вероятностями. Изменения существующей authority — отдельное versioned решение RP02, не тихий override.
6. Type-specific fusion/selection должна действительно влиять на next token/AST/path/result. Для произвольного TOutput нельзя просто усреднить ответы. Сохранить associations/evidence и post-generation arbiter; zero legal output→lawful fallback/abstention, а не force-first.

## Причинные опыты и функциональная приёмка

При одинаковых query families/eligible pool и compute сравнить: nearest baseline; fixed-k с reranker frozen; fixed-k с learned reranker; dynamic k с тем же trained reranker. Exact/ANN сравнивать отдельно, сохраняя reranker/pool budgets настолько сопоставимыми, насколько позволяет вопрос; измерять recall и downstream impact. Затем Student parent/Trial × old/new domain-policy 2×2 при unchanged hard laws. Не приписывать всю разницу Student DPO.

Метрики: law-correct candidate/path/task success per domain, critical error/abstention, positive/negative/warning retrieval usefulness, rank/candidate recall, typed-consumer usage, N/p50/p95 latency, total PC/index/reindex cost. «Best k» — наблюдаемый выбор по заранее заданной цели качество/ресурсы, не обещанный глобальный optimum.

## GOOD / BAD / EDGE

GOOD: для задачи сохранить всех клиентов SQL negative ON→WHERE reminder помогает не потерять unmatched rows; сам erroneous query не становится accepted answer. Почему: используется warning memory и задача, не простая близость.

BAD: удалить все failed neighbours; признать пол male invalid после любой feminine noun; вернуть hits[0], но отчёт назвать multi-neighbour reasoning. Remedy: evidence-role split, referent-aware law и actual output consumer.

EDGE: no legal pool→explicit caller fallback; k больше pool→bounded policy; stale projection/index→version reconciliation; identical count vectors с разным порядком→04A representation gap; ambiguous parse→не ложный hard reject; ANN misses correct candidate→не обвинять reranker; high similarity low correctness→calibration, не confidence-as-accuracy.
