## Действия

1. Trace actual user input→legal graph/typed intermediate outputs→async execution→final acceptance/ordinary consumer. Отдельно отметить concurrency permission, irreversible external effects, cancellation tokens и owner journal; learned policy не отменяет эти guards.
2. Для Orchestrator задать **детерминированную безопасную область действий**: зависимости, типы, source/effect authority, maximum concurrency, resource envelope, termination/partial result semantics. Candidate learned policy выбирает среди допустимых branch/order/budget choices. Конкретные лимиты — из current owner configuration/prospective approved experiment, не выдуманные глобальные числа.
3. Для learned policy назвать наблюдаемые features, action space, learning signal/credit assignment, mutable state, training owner, snapshot/persistence/version, no-update comparator и потребителя. Global success не доказывает, что каждая ветка научилась; reward нужно связать с actually selected action и результатом.
4. Для higher-order Graph определить semantic identity паттерна, порядок узлов/связей, какие композиционные отношения обобщаются и что именно меняется при обучении. Существующая static closure может быть baseline/safety structure. Growth node/edge counts не равно learned relational competence.
5. Не смешивать два эксперимента: сначала fixed graph/Unit/Flow + fixed scheduler vs learned orchestrator; отдельно fixed lower policies + flat relation model vs learned higher-order state на **не виденных композициях**, а не только новых строках знакомого graph. Взаимодействие двух обновлений — следующий заранее определённый contrast, не дважды приписанный один gain.
6. Count стоимость **всех** launched/failed/cancelled веток, retained intermediates, scheduling/recovery и external calls. Faster wall time при большем общем compute нельзя безоговорочно назвать более компактным алгоритмом. Correct deterministic fast path сохраняется, когда learned вариант не приносит пользы.
7. Передать один RP04 owner exact source/contract/experiment packet. Если выбран и scheduler, и higher-order state и они независимы — два child work orders со своими exact inputs/skills/files/state/examples/recovery/metric/stop, без новых общих research раундов.

## Примеры и предметная проверка

GOOD: C# analysis и read-only SQL schema inspection независимы и допустимы; learned scheduler выбирает их bounded parallel execution, но publication ждёт обе проверенные зависимости. Result correctness неизменна, общая стоимость/latency measured. Почему: ускорение не отменяет обязательства.

GOOD: higher-order policy переносит знакомые Unit/Flow операции на новую допустимую композицию; lower weights и budget fixed, actual ordinary route изменился и даёт лучший результат. Почему: проверено compositional generalization, не только размер графа.

BAD: самая дешёвая ветка игнорирует обязательную проверку; отменённая ветка уже отправила external effect, но не учтена; new static edge назван neural learning. Remedy: сохранить legal graph/журнал и проверить named learned recipient, не lower acceptance threshold.

EDGE: cycle/nontermination→bounded visited/termination policy; cancel после внешней записи→reconciliation/compensation существующего owner, не предположение rollback; partial fan-in→typed status/association; graph version/order change→explicit versioning, не sorting IDs без семантики; чужой domain schema→refuse/codec; concurrent promotion→single state owner, не last-write-wins; global mean improved/worst-domain critical failure→отдельный negative verdict.
