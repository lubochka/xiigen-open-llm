## Порядок

1. Existing inspect/reopen: проверить raw selection/source/config identities и состояние уже существующего набора. Reuse сохранённой пары не делает её автоматически J-accepted или optimizer-eligible.
2. При чистом отсутствии проверить actual grants до teacher factory. Raw configuration ограничивает maximumAuthorCalls=1, maximumDpoSteps=1; authorization на authoring не является разрешением вызвать Student.
3. Для текущего CPU profile проверить **весь rendered prompt native tokenizer**: context 2048, output reserve 512, input≤1536; threads=2, batch=16, GPU=0, keep_alive=0. Взять актуальные ID+SHA из источника, не придумать. Token count другого tokenizer не подходит. Не truncate/shift и не переписывать замороженный x.
4. Через существующий author command передать task; модель создаёт обе стороны одного и того же задания. Caller lifetime отменяет работу; не добавлять произвольный timeout/retry. Исходные grants не превращаются в безлимитный цикл generation.
5. Сохранить exact decoded chosen/rejected и x: без Trim, удаления пунктуации, Unicode/newline normalization, добавления `[WRONG:]`, переписывания negative или сборки одной стороны из Student answer. JSON escaping может быть транспортным; сравниваются канонически определённые **точные decoded UTF8** и предусмотренные source hashes, не произвольный переформатированный JSON.
6. Отправить неизменяемую пару отдельному J вместе с actual invocation/model/source provenance и стоимостью. Не выставлять себе VALID, не создавать native approval и не запускать B0/T1.

## Текст инструкции китайской модели

Используйте существующий production wrapper/raw_task, не меняйте его код ради этого примера. Смысл authoring-инструкции:

> Реши ровно указанное raw_task. Верни только JSON с двумя строками chosen и rejected. chosen должен быть правильным, полным в пределах задания и соблюдать требуемый язык. rejected должен выглядеть правдоподобно, но содержать одно существенное объяснимое нарушение предметного закона или требуемого поведения. Обе строки отвечают на одно и то же задание. Не добавляй метаданные, самооценку, название модели, markdown fence или специальные метки в ответ. Не копируй готовый Student answer как final сторону. Если смысловое предпочтение построить невозможно, не выдавай равнозначные ответы за полезную пару; host/J классифицирует результат.

Если production schema допускает только chosen/rejected, не выдумывать третий refusal field. Отказ/невалидный ответ сохраняется как фактический отказ, не исправляется host-агентом под авторством Chinese.

## Примеры и ошибки

GOOD: на одном разрешённом C# x модель сама создаёт объяснение ?.→null и ??→7 и правдоподобную ошибку ?.→0. Почему: pair несёт различие закона. Это публичная иллюстрация, не настоящая TRAIN/SEALED пара этой сессии.

BAD: два правильных объяснения различаются длиной. Почему: косметический contrast не доказывает предпочтение; J вернёт TIE/непригодность по rubric.

BAD: CODEX добавил ошибку в rejected или удалил '?' из source после generation. Почему: нарушены authorship/context identity. Remedy: не допускать изменённую пару; новый разрешённый Chinese revision и отдельный J, а не silent repair.

EDGE: oversized prompt→вернуть S новую разрешённую selection revision; частичный response/cancel→сохранить actual outcome/cost, проверить resolver прежде любых будущих действий; model/profile/license drift→BLOCKED_EXACT; prompt echo/invalid JSON/whitespace-only→PAIR_NOT_USABLE; неизвестное состояние сохранения→RECOVERY_REQUIRED, не повтор вызова автоматически.

## Выход и проверка

`actual_model_id/invocation_receipt`, P/K SHA, selection/source/config/profile IDs+hashes, grants, call_count, input native tokens, exact x/chosen/rejected refs+hashes, latency/resource/failure cost, raw preservation, resolver disposition, `J=NOT_PERFORMED`, `Student_effects=0`, `new_product_tests=0`, next=J либо точный blocker.

Приёмка: обе стороны действительно из разрешённого Chinese invocation, относятся к одному x и не менялись; отдельный J может переоткрыть те же bytes. Это ещё не качество пары и не learning gain. STOP.
