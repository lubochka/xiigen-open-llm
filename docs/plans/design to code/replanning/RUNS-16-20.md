# R16–R20: пять запусков изменения действующих документов

Применяется [COMMON-CONTRACT.md](COMMON-CONTRACT.md). Каждый раздел — отдельный будущий запуск. Входы — реальные решения R11–R14 и замечания R15. Их подготовка не означает, что правки уже применены.

**Разрешённая запись:** точные согласованные файлы требований, планов, индексов и промптов внутри `llm mvp/design to code session`, плюс `replanning/results/*`. Перед каждым запуском назвать конкретный список из карты R01/R14, прочитать свежие версии и сверить дельту. Не копировать всю библиотеку и не переименовывать историю ради текущей даты. История сохраняется Git и историческими пометками, а не новой альтернативной активной программой.

**Запрещено:** продуктовый код/тесты/данные/веса/workflows, глобальные core AGENTS/CLAUDE/skills, установки, обучение, платные вызовы, Windows/Actions/build/test, merge/PR/force-push/удаление worktree. Для обязательной правки вне области подготовить точный proposed patch с owner/ref/контекстом/проверкой применения; не заявлять её выполненной. Существующий генератор документов допустим только как проверенный side-effect-free инструмент в разрешённой области; его изменение и продуктовый запуск не подразумеваются.

**Общий выход каждого запуска:** действующий документальный delta, запись `results/CHANGE-MAP.csv` и краткий RUN-LOG. Поля change-map: исходный requirement ID и источник/ref/диапазон; старый смысл; решение; новое место/критерий; сохранённые ограничения; авторизация изменения; затронутые потребители; фактический статус применения; проверка. Внутренние предложения и реально изменённые live-файлы не смешивать.

## R16 — цели и критерии, соответствующие обучению

**Текущая задача:** применить выбранные изменения требований и критериев завершения. **Не задача:** просто добавить сводку рядом со старым планом или ослабить обязательства без источника решения.

**Роль/навыки:** исполнитель плановых изменений; B+S+P+A+E. Архитектор задаёт решение, этот исполнитель пишет документы; самопроверка не называется независимым review. **Входы:** R02 requirement map, R12–R15, свежие канонические владельцы требований, связанные WorkLeft/source prompts и карта потребителей R14.

**Работа.** Внести в реальные носители различие: механизм допускает опыт; опыт проведён; эффект положительный/отрицательный/неопределённый; candidate принят или parent сохранён; интеграция/выпуск проверены отдельно. Для каждой обучаемой возможности записать нужное поведение, данные, изменение состояния и доказательство. Сохранить исходные IDs; доказанные дубли связать, а не удалить обязательство. Указать точные изменения последовательности, one-pair/no-repeat, критериев 95%, бюджетов, роли источников и других затронутых решений. Если необходимое одобрение новой семантики не установлено, оставить старое ограничение и пометить предложенную дельту отдельно.

**Выход:** реальные изменённые требования и полная связь старое → новое. Закрытые наборы и секреты в документ не включать.

**Проверка:** перечитать финальные байты; сравнить с requirement map и решениями R15. Каждый новый критерий должен позволять честно завершить отрицательный эксперимент, не принимая плохие веса. Старые источники не остаются конкурирующим текущим предписанием там, где изменение действительно применено.

**Хорошо:** «Исследование завершено, улучшение не доказано; кандидат не принят». **Плохо:** «Loss снизился, значит домен готов и Windows больше не нужен». **Передача:** R17 получает обновлённую типизацию результатов, R18 — требования к алгоритмам, R19/R20 — точные потребители изменений.

## R17 — новая политика доказательств и Windows CI

**Текущая задача:** применить регламент, в котором проверка соответствует типу изменения и риску. **Не задача:** отключить workflows, обойти required checks или объявить красный продукт принятым.

**Роль/навыки:** исполнитель регламента; B+S+P+C+E. **Входы:** R09/R11/R13/R15/R16, текущие документы тестирования/batching/публикации, существующие workflow и required-check сведения, конкретный доступный runtime.

**Работа.** Внести матрицу «тип изменения → защищаемый риск → достаточное доказательство → место выполнения → частота/условие запуска → бюджет повторов → основание блокировки». Для документации — проверка её связности/содержания; для логики и состояния — затронутые инварианты; для обучения — независимый опыт; для Windows/native и выпуска — соответствующие платформенные/host проверки. Различить job ожидание, ошибку среды, неопределённый исход и причинный дефект. Повтор разрешается под новую проверяемую гипотезу и в конечном бюджете; unknown не разрешает ещё один update.

Если новая политика требует изменения настоящего workflow/branch rule вне planning-папки, подготовить точный предлагаемый delta и условия миграции, указать фактическое состояние. Отдельно проверить риск Pending от skip/path filters. Документ о политике не считается изменением GitHub-конфигурации.

**Выход:** действующий в planning регламент и отдельные неприменённые внешние patches при необходимости; соответствие требованиям R16.

**Проверка:** смоделировать правку Markdown, обычной логики, optimizer-state, native launcher, доменного набора и release. Ни у одной строки нет автоматического «всегда полный Windows» или «никогда тесты». Реальная runtime-зависимость сохранена.

**Хорошо:** «Этот опыт допускается подтверждённым runtime с указанными инвариантами; проверка другого host требуется для его поставки». **Плохо:** «Добавили skip ci, теперь required checks считаются пройденными». **Передача:** R18/R19 — выбранные evidence dependencies; R23 — конечные лимиты и обработка неизвестного исхода.

## R18 — технические пакеты, открывающие реальное обучение

**Текущая задача:** применить выбранный алгоритмический маршрут к техническому плану. **Не задача:** писать trainer, заменять существующие механизмы новыми абстракциями или превращать curriculum framework в новый бесконечный prerequisite.

**Роль/навыки:** исполнитель технического плана; B+S+A+C+P+E. **Входы:** R07/R12/R13/R15–R17, существующий implementation plan из RAG, сведения о готовом коде и всей иерархии обучения.

**Работа.** Создать/переработать содержательные пакеты: минимальная недостающая связь; первый настоящий учебный цикл; раннее разнодоменное расширение; анализ ошибок и следующий алгоритмический шаг; перенос на следующие уровни и продуктовые потребители. Для каждого указать исходное требование, пользовательский эффект, переиспользуемый код, отсутствующее изменение, обучаемое состояние, вход/сигнал/update/output, snapshot/restore, независимую оценку и допустимый результат. Имена существующих методов/контрактов подтверждать источником. Будущие новые signatures помечать проектируемыми, не реализованными.

В каждом новом инфраструктурном компоненте объяснить, какой наблюдаемый разрыв он устраняет и почему нельзя использовать имеющийся. Различить собственный Builder, graph policy и Student. Серия разрешённых новых уроков и широкая оценка не заменяются одним update; исходное ограничение одной пары не отменяется автоматически ради batch.

**Выход:** реальные изменённые разделы технического плана и конечные, проверяемые рабочие пакеты. Ближайшие задачи подробны; удалённые сохраняют архитектурные границы и зависимости без сотен преждевременных микропоручений.

**Проверка:** мысленно исполнить первый пакет: есть вход, конкретное изменение/готовый путь, оценка и решение при отсутствии эффекта. Количество новых интерфейсов/тестов/документов не выступает самостоятельной целью.

**Хорошо:** «Связать готовое обновление с существующим domain-evaluator; это откроет сравнение переносимости». **Плохо:** «Сначала заново построить полный evaluation platform, потом выбрать первый урок». **Передача:** R19 — пакеты и зависимости; R21/R22 — основа curriculum и опытов.

## R19 — один действующий roadmap всей программы

**Текущая задача:** перенести новый порядок во все действующие плановые входы, сохранив полный объём. **Не задача:** обновить только S04/README или переименовать сотни исторических файлов.

**Роль/навыки:** исполнитель миграции плана; B+S+P+A+E. **Входы:** R14/R15 и применённые R16–R18, полный source/consumer map, актуальные global queue/human map/WorkLeft owners и slice-entrypoints.

**Работа.** Применить согласованные reorder/merge/reuse к S00–S10 и требованиям вне слайсов. Связать отдельные пути исследования, продуктовой интеграции и выпуска; показать ближайшую полезную цепь и следующий шаг расширения. Для каждой исходной задачи сохранить новое место, ответственного, условия входа и смысл приёмки. Обновить активные индексы и cross-references так, чтобы они приводили к новой редакции, а не старому ремонту. Для удалённого дубля оставить ссылку на сохраняющий требование носитель. Исторический текст обозначить историей, не выдавая его прежний статус за текущий.

Проверить внешние обязательства DTC и IDE, локальную индексацию/планирование/поэтапное исполнение/тарифные ограничения, когда они присутствуют в исходной карте. Недоступный внешний контракт не исчезает, но его зависимость не блокирует несвязанный безопасный учебный пакет.

**Выход:** обновлённые реальные roadmap/индексы и полная change-map. Один понятный исходный вход, ведущий в правильный порядок.

**Проверка:** пройти ссылки как новая сессия; сопоставить реестр всех требований с новыми местами; проверить отсутствие потерянных зависимостей и циклов. Не объявлять исправленными core consumers, если были лишь подготовлены patches.

**Хорошо:** «S07 остаётся в программе с собственным результатом; ранняя учебная серия использует только подтверждённый необходимый подмаршрут». **Плохо:** «Теперь всё называется Learning First, прежние задачи больше не нужны». **Передача:** R20 получает точные работающие/оставшиеся конфликтующие точки входа.

## R20 — промпты и фактические инструкции исполнителя

**Текущая задача:** обеспечить, чтобы исполнители действительно получали новый порядок и правильные границы. **Не задача:** ещё один текст о хороших промптах без изменения действующих носителей.

**Роль/навыки:** исполнитель промпт-изменений; B+S+P+E+C. **Входы:** R15, применённые R16–R19, source/template/compiler/installed/effective карта, локальные инструкции сессии и актуальные навыки.

**Работа.** Для каждого входа, затронутого перестройкой, проверить путь от исходного текста к реально читаемому packet. В разрешённых носителях устранить старые команды, возвращающие к S04-only, бесконечному repair или чужим 30/50 проходам. Исключение ограничить нынешним 25-запусковым пересмотром; не отменять независимую приёмку, безопасность или требования поставки. Не менять глобальные skills и продуктовые компиляторы вне полномочий.

Каждый work order должен иметь текущую задачу/не-задачу, контекст и источники, точные skill routes, роль/модель по действующей конфигурации, разрешённые файлы/команды, конкретный результат, хорошую/плохую реализацию и проверку. Архитектор проверяет решение; исполнитель пишет назначенное; reviewer не присваивает авторскую самопроверку как независимую. Проверить содержательно, а не только наличие заголовков. Если effective packet управляется вне области, подготовить точный patch и назвать неполноту доставки; не обходить существующий owner самодельным параллельным prompt.

**Выход:** изменённые реальные промпты/локальные инструкции, карта доставки, явно неприменённые внешние дельты и ограничение их влияния.

**Проверка:** мысленно передать R01, отрицательный эксперимент, другой слайс и финальную приёмку новой сессии. Она должна сохранить глобальный контекст, выполнить только свой объём, получить нужные источники и не реактивировать историческую команду.

**Хорошо:** «Прочитай все актуальные RAG-ветки в пределах R03, зарегистрируй источники, не чини продукт». **Плохо:** «Продолжай до зелёного по любому старому RUN, пока всё не закончится». **Передача:** R21 начинает содержательные дополнения по реально обновлённой программе; R25 позже проверяет именно её финальную доставку.
