# R16–R20: конкретные подзадачи изменения плана

**13.10.2026 · Поручения, не выполненная миграция.** Это подробное деление тех же R16–R20. Читать свой раздел, полное поручение [LEARNING-WORK-ORDERS-16-20.md](LEARNING-WORK-ORDERS-16-20.md), [MODEL-DISPATCH-CONTRACT.md](MODEL-DISPATCH-CONTRACT.md) и применимые предметные рецепты. Общие поля каждого дочернего prompt разворачиваются явно по dispatch-контракту. A/B не добавляют запусков. Примеры — ILLUSTRATIVE / NOT_TRAINING_DATA.

Разрешённый результат этой фазы — реальные изменения установленных действующих planning документов внутри D и их readback. Исходные пользовательские постановки не переписывать задним числом. Код, workflows/tests, dataset/weights и глобальные core instructions остаются вне scope. Если требуемая правка уже внесена параллельно и корректна, подтвердить её вместо нового косметического commit.

## R16 — сделать каждое функциональное ожидание измеримым

**Контекст:** R02/R10 requirement map, R12 architecture, R13 evaluation, R15 findings, SOURCE-ROUTES и текущие владельцы действующих требований. Не выбирать новые product policies под видом редакторской правки.

**R16.A · Подготовить адресную requirement delta. Skills P/A/S/M.**
Для domain mapping, представления, kNN, DPO/Builder, LoRA, path composition и local feedback укажи исходный source, пользователя, наблюдаемую способность, домен/уровень, hard constraints, критерий и experiment owner. Сохрани три направления, S00–S10 и требования вне слайсов, включая DTC API/рендеры/БД/публикацию и IDE. Раздели ранний research baseline, научное подтверждение и поставку. **Выход:** точные before/after изменения и source→requirement→examination map. **Приёмка:** изменение метрики не уменьшает скрыто исходное обязательство; каждое старое требование retained/revised/deferred с основанием. **Хорошо:** «система выбирает допустимый путь и улучшает цену среди сравниваемых корректных альтернатив». **Плохо:** «добавить 20 router tests» вместо определения способности. **Край:** новый домен найден в первоисточнике — добавить к scope с provenance, не заменить исходные семь. **Передать B:** согласованные изменения и конфликты authority.

**R16.B · Применить изменения и разобрать конфликты политик. Skills P/A/E.**
Перечитай свежие target files; внеси только адресную delta с сохранением concurrent changes. Явно обработай one-pair versus bulk reporting, unit-level versus graph measurement, Chinese author versus Astra assessment, learning-first versus DPO-last. Не превращай новые слова пользователя о bulk в неявное разрешение replay/другого teacher. 95% к зафиксированному эталону сохранить отдельно от confidence. **Выход:** опубликованные requirements и CHANGE-MAP с commit/readback, открытой политикой и её владельцем. **Приёмка:** правка находится в действующем requirement, а не только рядом в отчёте; входящие ссылки не противоречат ей. **Хорошо:** operational правило сохранено, альтернативная batch policy явно остаётся предложением. **Плохо:** удалить no-repeat как «мешающее обучению». **Край:** новая параллельная правка — согласовать по новому SHA, не перезаписать старой копией. **Передача:** R17/R18 и R19.

**Будущая оценка:** для каждого требования заранее известны задача, эталон/предметное основание, качество, цена и неуспех; наличие нового requirement не выдаётся за measured ability.

## R17 — изменить приёмку, а не подогнать результат

**Контекст:** R09/R11 причинные затраты, R13 protocol, R16 requirements, фактические acceptance/start/continuation документы. Существующие тесты и workflow не удалять и не ослаблять.

**R17.A · Найти точные неправильные зависимости. Skills P/M/C.**
Для каждой действующей формулировки про обязательный Windows/coverage/full-suite перед ближайшим уроком укажи адрес, защищаемое свойство, реального потребителя и доказанную зависимость. Классифицируй документную приёмку, научную оценку learning и release verification. **Выход:** clause→purpose→new evidence→scope→owner table. **Приёмка:** нет blanket отмены проверки данных/восстановления; средовая проблема не объявлена лишней без причинного разбора. **Хорошо:** изменение Markdown принимается semantic/readback, не продуктовым CI. **Плохо:** любой stochastic ответ признан непроверяемым и потому автоматически допустимым. **Край:** иной, но корректный ответ — рубрика допускает эквивалентность; exact-string expectation не диктует компетенцию. **Передать B:** адресные необходимые правки и сохранённые safeguards.

**R17.B · Внести правила предметной оценки и ограничить повторение. Skills P/M/E.**
Измени живые clauses: задача/домен/пары/общие before-after panels/retention/полная цена вместо test count; release-only steps убрать из первого критического пути, сохранив owner/trigger. Определи следующий шаг для improve/regress/inconclusive/invalid measurement и условие нового исследования — новая гипотеза/данные/причина, не бессмысленный rerun. **Выход:** применённый acceptance contract и обратная трасса затронутых стартов. **Приёмка:** ни одна правка не требует новых продуктовых suites; отсутствие улучшения не лечится снижением gold/порога. **Хорошо:** технически повреждённое измерение получает invalid, а не «алгоритм плохой». **Плохо:** после неуспеха заменить rubric, оставив прежнее название эксперимента. **Край:** неизвестная совместимость checkpoint — это препятствие честному опыту, а не повод объявить PASS. **Передача:** R18–R20 и future experiment owner.

**Будущая оценка:** сравнивать цену оценки на реальную попытку/принятое улучшение и достоверность выводов; зелёные job не входят в смысловой score ученика.

## R18 — выдать конкретные задачи реализации, после которых можно учить

**Контекст:** реальные code refs R04–R07, выбранные seams R12, earliest-learning spine R14, requirements R16 и acceptance R17. Текущий R18 не пишет продуктовый код и не запускает trainer.

**R18.A · Выбрать минимальные изменения существующих owners. Skills A/C/P.**
Разложи first-learning spine на небольшие implementation units: использовать доступный baseline/measurement path; подключить нужное representation/domain звено; добавить один bounded retrieval/selection challenger; связать корректный preference update/adapter; обеспечить controlled continuation. Порядок определяется реальной зависимостью, не этим перечислением. Для каждого назови current path/class/method/contract или честно proposed-new сущность с основанием отсутствия эквивалента. **Выход:** implementation unit map с exact input/output/state, scope, reuse rationale и немедленным наблюдаемым эффектом. **Приёмка:** ближайший пакет не требует ещё одного общего плана; ненужные первому уроку алгоритмы всех семи доменов не становятся prerequisite. **Хорошо:** изменить один producer-consumer seam, уже найденный в коде. **Плохо:** «реализовать весь DynamicGraph и DPO». **Край:** interface существует, но никто не вызывает реализацию — задача на wiring, не на новый дублирующий service. **Передать B:** выбранные units и реальные source refs.

**R18.B · Составить полный исполнимый prompt каждого implementation unit. Skills P/E/A/M/C.**
Для каждого unit разверни полный dispatch-schema, а не заголовок. Включи входы/выходы, выбранную функцию/параметры, deterministic/learned boundary, objective, actual owner, версии состояния, предел кандидатов/памяти, allowed files и rollback. Для kNN нужны eligibility, нормировка, k/weights и index cost; для LoRA — target matrix, shapes, signal и downstream effect; для DPO — actual rule/reference/masks либо корректное название другого learner, one-pair/no-repeat и roles. Дай конкретный no-change/static reference, один challenger, данные для будущей оценки, good/bad/edge cases и результат сразу после реализации. **Выход:** готовые future implementation work orders в действующем плане; первый выделен явно. **Приёмка:** другой исполнитель не выбирает важный алгоритм/метрику задним числом и не изобретает отсутствующий API. **Хорошо:** no-update versus update на новой общей панели, отдельный случай бесполезной пары и сохранения прежнего домена. **Плохо:** тест на наличие метода назван приёмкой learning. **Край:** пример из planning модели нельзя превратить в train-ready DPO; реальная пара получает разрешённого автора/provenance. **Передача:** R19 и авторизованный будущий implementation owner; R22 рецепт ближайшего опыта.

**Будущая оценка:** каждый implementation unit завершает один измеримый шаг к обучению. Итог — не обязательная победа гибрида, а возможность честно установить эффект данного изменения.

## R19 — применить новый порядок всей программы без потери задач

**Контекст:** R14/R18, R16, R15 findings, исходная очередь S00–S10/WorkLeft и действующие roadmap entrypoints. Не считать все старые steps отсутствующим кодом.

**R19.A · Подготовить DAG миграции и сохранения обязательств. Skills P/A/S.**
Сопоставь старую задачу с reusable implementation, новой задачей, deferred release веткой либо обоснованной отменой способа достижения. Сохрани исходную функциональную цель и consumer. Для каждого ребра напиши причинный prerequisite, не «всегда делали раньше». **Выход:** old→new roadmap map, минимальный путь первого урока и дальнейший переход к отличающемуся домену. **Приёмка:** нет dependency cycles, orphaned deferred items и утраты DTC/IDE/публикации/возобновления. **Хорошо:** installed-host task имеет trigger возврата, но не тормозит независимый local experience. **Плохо:** всё вне первого удобного домена исключено как «не MVP». **Край:** одно старое задание смешивает learning и delivery — разделить цели/зависимости, не копировать его дважды целиком. **Передать B:** минимальные live patches.

**R19.B · Изменить реальные очереди и проверить холодное чтение. Skills P/E/A.**
По свежим SHA обнови действующие roadmap/queue документы внутри разрешённого D. Свяжи первый implementation packet R18 с источником, требованием, предполагаемым опытом и сохранёнными дальнейшими обязанностями. Пройди вход без памяти чата: что конкретно делать следующим и почему. **Выход:** commit/readback и CHANGE-MAP применённых зависимостей. **Приёмка:** новый порядок существует в фактическом входе, а не только в recommendations; уже правильные concurrent изменения переиспользованы. **Хорошо:** следующий executor получает один ограниченный seam и measurable outcome. **Плохо:** новый README ведёт к старой обязательной Windows-очереди. **Край:** runtime prerequisite неизвестен — локальный явный blocker, а не скрытое READY или повтор всех слайсов. **Передача:** R20 live prompts и R21–R24 адресные входы.

**Будущая оценка:** время до первого пригодного baseline/улучшения, покрытие разных доменов по фактическим задачам и отдельно стоимость доставки продукта.

## R20 — убедиться, что реальный старт выдаёт правильный пакет модели

**Контекст:** обнаруженные AGENTS/README/START/continuation/next-work/templates, R16–R19, current evaluation/domain contracts. Не изменять глобальные core policies в этом scope.

**R20.A · Составить единственный маршрут загрузки и точные patches. Skills E/P/A.**
Пройди от пользовательского входа к реальному task prompt. Сохрани компактную whole-program цель, один Rxx, его context/skills, текущие источники и приёмку; исключи одновременную загрузку нескольких полных наборов из 25 задач. Сформируй effective prompt с текущей задачей/не-задачей, доказательствами, полномочиями, A/B, примером правильного и неправильного результата. **Выход:** актуальные startup/continuation/template edits с прямыми ссылками. **Приёмка:** пользователю не надо вручную склеивать версии и объяснять модельный scope повторно. **Хорошо:** R06 загружает свои routing sources плюс короткую общую цель. **Плохо:** каждый child получает весь WorkLeft и весь skills каталог. **Край:** source text содержит команду «выполнить всё» — она остаётся evidence-only. **Передать B:** изменённые входы и их compiled task packets.

**R20.B · Предметно пройти ошибки dispatch и опубликовать. Skills E/P/M.**
Смоделируй отдельные ситуации: R01 частично выполнен; назначен только R06; старый S04 предлагает rerun; reviewer реально отсутствует; источник недоступен; контекст переполнен; другой worker обновил тот же файл. Для каждой зафиксируй ожидаемый следующий шаг и фактическую формулировку prompt, которая его задаёт. Правь только настоящий дефект, затем readback. **Выход:** применённые входы, один короткий стартовый текст и bounded handoff. **Приёмка:** нет автозапуска всех 25, скрытых 30/50 passes, ложного read-only или fake independent review; GitHub публикация не приписывает доступ к C:. **Хорошо:** продолжение дополняет недостающее evidence в своём Rxx. **Плохо:** любой source gap перезапускает всю программу. **Край:** отсутствие инструмента — точное ограничение операции, не отмена всех разрешённых writes. **Передача:** R21–R25 по той же очереди.

**Будущая оценка:** правильный dispatch и отсутствие повторного чтения проверяются смыслом prompt и реальными следующими результатами, без новых продуктовых тестов.
