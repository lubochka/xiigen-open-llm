## N33-A — ключевой параметр: обучаемая таблица токенов отсоединена от autograd

**Первичное доказательство.** [Embedding.cs L21–56](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/00.TensorCore/Layers/Embedding.cs#L21-L56) создаёт `Weight = new Parameter(...)`; затем в `Forward` копирует `Weight.Value.Data` через `Array.Copy` в обычный `float[]` и возвращает `new Tensor(data, new TensorShape(...))`. Созданный тензор не связан с `Weight.Value` графом вычислений. [Tensor.cs L15–41, L53–93](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/00.TensorCore/Core/Tensor.cs#L15-L93): новый Tensor по умолчанию `requiresGrad=false`; backprop посещает только `Children` и запускает их `BackwardFunc`. [Parameter.cs](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/00.TensorCore/Layers/Parameter.cs#L16-L39) выставляет `Weight.Value.RequiresGrad=true`, но это не может автоматически восстановить отсутствующее ребро. [Module.cs](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/00.TensorCore/Layers/Module.cs#L19-L56) регистрирует параметры, не граф.

**Следствие из кода:** для `Embedding.Forward` нет механизма накопить scatter-add градиент в `Weight.Grad`; при обучении только этим путём `Weight.Grad` остаётся null. Модель действительно использует эту таблицу через [LlmModel.Forward L219–244](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/03.TransformerModel/LlmModel.cs#L219-L244). Общий [Trainer.TrainSupervisedNextTokenStep](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Trainer.cs#L67-L147) берёт все разрешённые параметры, но [AdamW.Step L73–96](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Optimizers/AdamW.cs#L73-L96) пропускает каждый `param.Grad == null`.

**Класс:** SOURCE_CONFIRMED отсутствие производной по Embedding, качество SFT при конкретных датасетах и RP01 serving — CAUSAL_HYPOTHESIS. **Ветви:** `DesignToCode` и `language_translate` тоже содержат `Array.Copy(Weight.Value.Data, ...)` и `return new Tensor(data,...)` (прочитаны тексты; source blob SHA `ee029cf858ad32667f4324d9533891c1ba1a1f24`). Это **унаследованный механизм**, не доказанная регрессия переноса в RP01. Архивные успехи могли относиться к KNN/другим trainable параметрам.

**Домен:** любой **нейронный** learner, который разрешает обновлять token embedding: C#, языковой перевод RU↔EN/HE↔EN, natural-language generation. Не переносить автоматически на текстовую KNN-память, которая не обучает эту таблицу, либо на frozen embeddings как намеренную настройку LoRA.

**Минимальный falsifier:** взять `Embedding(8,3)`, IDs `[3,3,1]`, scalar loss = сумма всех элементов output. Теоретически dLoss/dWeight[3,0] = **2**, dLoss/dWeight[1,0] = **1**. Исходный backprop обязан вернуть эти производные, но граф между `output` и `Weight` отсутствует. Native probe и finite difference из [MICRO-N33](33-MICRO-AUTOGRAD-WARMUP-AND-LEARNING-IMPACT-2026-10-16.md) **ещё не запускались**. Исправление — differentiable gather со scatter-add в единственный leaf, проверка повторных IDs, gradient accumulation, bounds и cancellation; не заменять его только выставлением `RequiresGrad=true` на выходе.

## N33-B — похожая потеря градиента на bias обычного Linear (другое семейство потребителей)

[Linear.cs L37–84](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/00.TensorCore/Layers/Linear.cs#L37-L84) применяет `ExpandBias(Bias.Value, output.Shape)`: метод копирует значения bias в новый `float[]` и возвращает независимый `new Tensor(data, outputShape)`. В комментарии сказано, что `RegisterParameter` накапливает градиент, но [Module.cs](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/00.TensorCore/Layers/Module.cs#L15-L35) только хранит параметры. Ребро `biasExpanded→Bias.Value` и reduction по batch/seq нет. При `Linear(in=2,out=1,useBias:true)` и нулевом X loss=sum(output) аналитический dLoss/dbias = batch×seq, но backprop bias не получает. Это **source-confirmed**, native execution NOT_RUN.

**Важно: область НЕ RP01:** [CausalSelfAttention.cs L56–71](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/03.TransformerModel/Layers/CausalSelfAttention.cs#L56-L71), [SwiGLUFeedForward.cs L24–36](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/03.TransformerModel/Layers/SwiGLUFeedForward.cs#L24-L36) и [LlmModel.cs L101–110](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/03.TransformerModel/LlmModel.cs#L101-L110) для основного Transformer используют `useBias:false`. Поэтому ошибку нельзя выдавать за объяснение failed RP01 q/v LoRA. Она релевантна тем **иным** trainable Units/classifiers/custom layers, которые создают `Linear` с bias=true; перед ремонтом требуется найти фактического потребителя.

Sibling `DesignToCode` содержит ту же конструкцию (blob `6244f5b7cbfc998556f5516cfc26d2b37e7fa418`), значит это исторический inherited gap, а не автоматически потерянная функциональность новой ветки.

## N33-C — первый supervised next-token шаг не проходит с конфигурацией по умолчанию

[TrainingConfig.cs L10–30](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/TrainingConfig.cs#L10-L30) задаёт `WarmupSteps=100`, `MaxLr=3e-4`. [CosineWithWarmup.GetLr L23–31](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Schedulers/CosineWithWarmup.cs#L23-L31) возвращает `maxLr * step / warmupSteps`; на `step=0` это **ровно 0**. [Trainer.cs L35–57, L124–147](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Trainer.cs#L35-L57) и [L124–147](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Trainer.cs#L124-L147): private `_supervisedStep` стартует с 0, а `TrainSupervisedNextTokenStep` вызывает `GetLr(_supervisedStep)`, затем выбрасывает `InvalidOperationException("Training learning rate must be finite and positive.")`, когда LR <= 0. До `optimizer.Step` и `_supervisedStep++` управление не доходит.

**Фактический code-path contract:** с конфигурацией **по умолчанию** первое `TrainSupervisedNextTokenStep` неизбежно завершается исключением; повторный вызов того же объекта тоже стартует на нуле. Математика не зависит от качества DPO и размера модели. **Scope:** это новый сравнительно с sibling веткой API: `DesignToCode/04.TrainingLoop/Trainer.cs` не содержит метода `TrainSupervisedNextTokenStep`; нельзя приписывать этот defect старому E09/E26.

**Причина ограничена call site:** если caller явно выставляет `WarmupSteps=0` или использует другой Trainer/свой optimizer, это конкретное исключение не возникает. Сам RP01 точный `DpoTrainer.StepMany/StepVector` сюда не входит. Отрицательный neural pilot после попытки SFT мог быть отказом допускa/шага, а не слабой обучаемостью; проверять реальные run receipts.

## N33-D — первый pretraining шаг с warmup обновляет optimizer state, но не веса

Отдельный метод [Trainer.RunPretrainingCoreAsync L221–266](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Trainer.cs#L221-L266) использует `GetLr(previousCompletedSteps)`, где исходный completed=0, **разрешает LR=0** и вызывает `AdamW.Step`. [AdamW.Step L64–113](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Optimizers/AdamW.cs#L64-L113) при нулевом LR увеличивает `_step`, EMA-moments `m/v`, но `w *= (1 - 0 * decay)` и `w -= 0 * ...` не меняют веса. После этого completedSteps увеличивается. **Source-confirmed:** метрика `CompletedSteps=1` может означать 0 параметрического движения на этом шаге (при отсутствии иных побочных мутаций). Это не равносильно потере всего обучения; следующий шаг при LR>0 уже меняет веса. При коротких runs/малой квоте может быть существенным; для RP01 DPO здесь прямой связи не установлено.

## N33-E — новый Trainer начинает supervised learning-rate sequence с нуля

В [Trainer.cs L35–57, L124–147](https://github.com/lubochka/llm_mvp_core/blob/32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7/04.TrainingLoop/Trainer.cs#L35-L57) счётчик `_supervisedStep` локальный, не показано export/import этого поля; checkpoint модели и optimizer может пережить восстановление независимо от него. **Подтверждено локальное свойство класса**, но НЕ доказано, что RP01/SFT continuation действительно создаёт новый Trainer и восстанавливает остальные части. При `WarmupSteps>0` сначала проявится N33-C; при `WarmupSteps=0` новый Trainer начинает cosine заново с максимального LR, а непрерывный Trainer должен продолжать decay. Проверить только actual caller / cold restore — это **conditional** риск.
