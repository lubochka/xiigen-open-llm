## Самое важное различение маршрутов
Это **`TranslationDpoTrainerBridge → TranslationDpoTextFeaturizer → DpoTrainer.StepMany`** (исторический и альтернативный pipeline). Это **НЕ** RP01 `DpoExactPairMaterial` version `segmented-byte-BPE-v2`, для которого в [предыдущем кодовом аудите](10-INDEPENDENT-CODE-PATH-RECONCILIATION-2026-10-16.md) подтверждены отдельные response masks и byte-BPE. Нельзя объявить эти недостатки причиной текущего 0/4 у RP01, не доказав вызов именно этого bridge. Но при сравнении с успешными соседними ветками и планировании DPO→Units этот путь способен испортить обучающий сигнал.

[TranslationDpoTrainingHandoff.cs L242–279](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainingHandoff.cs#L242-L279) вызывает **реальный** `BuildTrainerPrompt(trainReady)` и сохраняет результат как `TrainerPair.Prompt` после pair admission.

3. [TranslationDpoTrainerBridge.cs L314–345](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L314-L345) ставит семь доменных строк перед `prompt:{record.Pair.Prompt}`. 4. **Воспроизводимое shadow-вычисление точного RegexTokenization** для header `domain:TranslationDomain, machine:translation-machine, direction:EN_RU, capability:translate, unit:executor-en_ru, source:en, target:ru` и `Pair.Prompt="Translate from en to ru.\nInput: bank"`: число prefix tokens = **32**, первые 30 заканчиваются `input`, `:` (31) и `bank` (32) **полностью отброшены**. Для `Input: the river bank` prefix tokens=34, все три слова также отброшены. Shadow воспроизведение выполнялось отдельно Python regex, фактический C# `BuildRecord` всё ещё `NOT_RUN`.
5. [BuildRecord L180–216](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L180-L216) fingerprints вычисляет по **полному prefix**, но model-visible `ChosenIds/RejectedIds` получает только урезанный `EncodeSide`. Разные source examples могут иметь разные audited fingerprints при одинаковом model input. **Это способ терять саму задачу**, даже когда chosen/rejected ещё различаются.

**Реальный риск:** отдельные EN→RU 500 пары в данном bridge могли учить модель различать ответы без знания того, что нужно переводить; но **не приписывать это RP01 ENRU500**, который использует другой exact-v2 путь. Для конкретного bridge-run прежде проверить фактически заданные `TokenizationSettings` (вызов может переопределить ContextLength64), источник `trainReady.Prompt` и число trimmed tokens; если prefix больше, эффект может исчезнуть.

**Предельно короткий различающий опыт (встроить в MICRO-16.03):** сформировать **две настоящие** `TranslationDpoTrainingHandoffRecord` через существующий seed/handoff builder, одинаковые direction/capability/unit, `Input: bank` vs `Input: river`; `BuildTrainDpoBatches` на default 64 и сравнить BOS→SEP model-visible ID. Если они равны, записать `SOURCE_INPUT_ELIDED` и точное число omitted tokens. Control: повысить *только* ContextLength до валидного значения, проверить разные prefix ID и не терять response. Это доказательство **потери condition**, а не успешного обучения — эффект на качество требует paired training+heldout после L0.

**Не дублировать чужую находку:** [16-TRANSLATION-DPO-MODEL-VISIBLE-PAIR-COLLAPSE.md](16-TRANSLATION-DPO-MODEL-VISIBLE-PAIR-COLLAPSE.md) уже описывает hash-collision, rejected-tail clipping и legacy full-sequence mean. **Новый дополнительный исходный факт этого документа** — реальная цепочка `BuildTrainerPrompt → Input at tail → 30-prefix cut`, где исчезает **целый исходный текст**, а не только distinction между ответами. Вдобавок `StripReservedDiagnosticsForModel` может отдельно превратить отличающиеся raw sides в идентичные; про это также нужен native счетчик.

## N16-DPO-02 · P0 conditional: разные исходные chosen/rejected становятся одинаковыми после очистки
- [L180–216](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L180-L216): `BuildRecord` делает `StripReservedDiagnosticsForModel` отдельно для обеих сторон, затем сразу `EncodeSide`; проверки `chosen.TokenIds.SequenceEqual(rejected.TokenIds)` в этом методе нет.
- [L262–312](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L262-L312): удаляется `[WRONG: ...]` и разрешённые audit markers `[PHRASE: ...=>...]`/`[AGREEMENT: ...=>...]`. Это полезно против утечки teacher hints, **но может стереть единственное отличие пары**.
- [L888–977](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L888-L977): handoff validation и admission binding проверяют **raw** Prompt/Chosen/Rejected; финальная model-visible distinctness здесь не показана.
- [L701–746](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/11.DPO/DpoTrainer.cs#L701-L746): `StepMany` считает reward/gradient из тензоров, а не из raw pair fingerprints.

**Диагностический пример, не подтверждение наличия таких строк в реальном корпусе:** `chosen="берег"`, `rejected="берег [WRONG: wrong topic]"`. Raw строки отличаются, после `StripReservedDiagnosticsForModel` обе model-visible стороны равны `берег`. При тождественных input IDs/masks и детерминированном dropout=0 их DPO preference signal равен нулю; возможны лишь вычислительные флуктуации. Дообучать модель ещё 500 раз на таких парах бесполезно.

**Фальсификатор:** перед trainer, на уже validated mutation snapshot, count `identical chosen/rejected token IDs + mask`; для каждой пары логировать `PAIR_CONTENT_COLLAPSE` и declared reason (`diagnostic-strip` / `truncation` / `hash-collision`), без раскрытия приватного текста. Не нарушать frozen historical rows.

## N16-DPO-03 · P1 conditional: разные слова получают один hashed token ID
[L331–345](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L331-L345): `ToStableTokenId` вычисляет `4 + (BitConverter.ToUInt32(SHA256(token),0) % (VocabSize-4))`. У default VocabSize512 всего **508** слотов на все words/bytes/punctuation. Коллизии неизбежны при достаточном числе разных token.

**Точный offline пример** (SHA256 + low-endian UInt32 при Windows/x86, первая raw формула из C#): `test0` и `test3` оба кодируются как token ID **285**. Это искусственная collision probe, **не семантическая DPO-пара и не утверждение о частоте коллизий в EN→RU500**. Кроме того [L230–253](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L230-L253) обрезает суффиксы: raw chosen/rejected могут отличаться после responseBudget, но стать тождественными ID sequences.

Если после tokenization выбранный и отвергнутый тексты стали одинаковыми, DPO не знает, какую из двух исходных строк человек предпочёл; исходная raw fingerprint этого не исправляет.

**Фальсификатор:** full build `BuildTrainDpoBatches` на сохранённом exact corpus without mutation; вывести counts (a) unique raw pair, (b) distinct model-visible chosen/rejected ids, (c) clipped source tokens, (d) clipped chosen/rejected discriminating suffix, (e) collision/hash map; отдельно bound by metadata family/source. Доказать ли именно эта утрата ухудшила качество — L1 эксперимент ниже.

## N16-DPO-04 · P1: скрытая договорённость о формате токенов между trainer и consumer
Этот bridge строит word-hash tokens, собственные `BOS=1, SEP=2, EOS=3`, `vocab=512`, в отличие от RP01 BPE629 и `segmented-byte-BPE-v2`. Даже если preference margin ↑, обычный consumer должен получить *ту же* encoding/framing semantics; источник `TranslationDpoTextFeaturizer` **не** эквивалентен `BpeTokenizer`. Нужен точный reader→model→decoder call trace перед любым утверждением о portable weights. Это контрактное различие, НЕ доказательство некорректного checkpoint на текущем RP01.

## N16-DPO-05 · P1 conditional: bridge оптимизирует промпт и метаданные, а не только выбранный ответ
[TranslationDpoTextFeaturizer.BuildRecord L180–216](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L180-L216) создаёт `DpoBatch` с `ChosenIds/RejectedIds/ChosenMask/RejectedMask`, **без** `MaterialVersion` и **без** `ChosenResponseMask/RejectedResponseMask`. [DpoBatch.cs L11–28](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/11.DPO/Models/DpoBatch.cs#L11-L28) устанавливает default `MaterialVersion=LegacyVersion`. [DpoTrainer.cs L1002–1119](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/11.DPO/DpoTrainer.cs#L1002-L1119) для legacy считает **full-sequence mean log-probabilities**, а не response-only sum, поэтому BOS/prefix metadata/`prompt:` участвуют в gradient. При большом заголовке и короткой трансляции relative weight response меньше, чем в RP01 exact-v2. Это **реальное несовпадение objective двух training routes**, но **не измеренная причина плохого RP01**. Не утверждать, что все prompt gradients обязательно различаются или что они ошибочны в каждом контексте: shared prefix может сокращать контраст, но эффекты разной длины и autoregressive dependence остаются.

**Фальсификатор:** на одном synthetic batch записать `MaterialVersion`, число target tokens на prefix/response, фактические gradient norms и signed updates, затем одинаковые pair/model/seed + только законная смена objective на response-only с явной версией/маской; semantic utility оценить отдельно. Нельзя ретроспективно перекодировать frozen DPO и сравнивать одни margins двух objectives как равные.
