**Последняя проверенная версия core: `de4ef0f14172dada4daf142a4c66ba19e96bb6d4`.** Во время аудита ветка продвинулась на два коммита от `bf9b543e149ef197da85a767821d98c9b67916d2`. ## 1. Общая блокировка уже снята

Новая [execution policy](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/docs/plans/replanning-possible-diffs/experimets/00-execution-policy-2026-10-20.md) прямо отменяет общий запрет карточек и необходимость повторного личного одобрения каждого ID/SHA. Исполнитель сам подготавливает доступные данные, однофакторное изменение, состояние, входы и команду в пределах порученной программы. `NOT_RUN` означает отсутствие измеренного результата. Незаполненный паспорт — задача подготовки; назвать внешний блокер можно после конкретной безуспешной попытки получить необходимый вход.

Политика также уже учитывает последнее уточнение пользователя: загрузка, токенизация, подготовка пар, сохранение/восстановление и выдача выученного результата допустимы при доказанной зависимости от обучения. Для такой проверки нужны original файл/метод, цепочка, точный дефект и предлагаемое исправление. Декоративный Train не нужен. Для проверки нового обучения сохраняются реальные состояния до/после; для сохранности или использования результата допустим один уже доказанно обученный checkpoint. Ресурсному опыту настоящего update не обязательна генерация.

**Правило успеха сохранено:** любое измеренное улучшение полезного показателя — успех по этому показателю и домену. Рост accuracy не обязателен, все остальные изменения и ухудшения показаны рядом. Это не основание записывать неизмеренное как ноль или утверждать улучшение иной способности.

Старые абзацы в теле 22 про обязательное обратное влияние на следующий update, blanket `serving OUT` для K3/P107/P54 и старые слова о личном допуске в D04 читаются с явной отменой из новой политики. Повторно «снимать» уже снятый запрет не требуется. При подготовке конкретного задания достаточно дать исполнителю один непротиворечивый актуальный контракт и точную causal ссылку.

Прежнее требование обязательно ненулевого state delta нельзя применять как запрет честного нулевого эффекта достигнутого обучения. Неявный ручной candidate не должен называться ответом Executor.

[Адресные N60 overlays и промпты](02-N60-CONCRETE-OVERLAYS.md) содержат готовые [два TRAIN урока E2](N60-E2-PROPOSED-TRAIN.jsonl), [четыре EXAM задания E2](N60-E2-PROPOSED-EXAM.json) и отдельно [необязательный ordinary retention fixture E1](N60-E1-PROPOSED-INPUTS.json). Для E2 слово «оператор» пока шире технического содержания. Два положительных урока не обучают смыслу отрицания или вопроса. Возможный минимальный результат — память записывает знакомую форму композиции и reader распознаёт отсутствие поддержки другой формы. Снижение wrong accepted может сопровождаться отказами, потерей coverage, ростом bytes и временем обучения. Все показатели остаются в отчёте.

## 3. D04 и отдельный cache-вопрос

В текущем [D04](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/docs/plans/replanning-possible-diffs/experimets/2026-10-19-small-learning-probes/04-documentation-neural.md) B1–B6 названы задачами подготовки исполнителя: один семантический фактор, малый вызов, точные bytes, B0/reference, optimizer/RNG, реальная команда/выход. Неизвестный путь к артефакту сам по себе не доказанный внешний blocker. При этом отсутствие написанной CLI нельзя выдавать за готовый запуск: действующий runner принимает calibration1/main500, проект micro-paired ещё требуется подключить.

Новая карточка reference-logprob cache из настоящего пакета проверяет **отдельную стоимость actual DPO update**. Она выбирает повторяющийся exact batch и существующий `LogicalDpoTrainingUnit.ExecuteCore → DpoTrainer.StepVectorCore`. Два различных урока D04 по одному предъявлению не создают cache hits. Экономия reference forward не заполняет семантический B1 и не доказывает улучшение собственного объяснения аргументов. Данные/расписание D04 не заменяются молча.

Подготовка direct learning имеет приоритет. Условные reader-карточки ниже не становятся предварительным обязательным тестовым набором и не требуют полного Windows CI.

## 4. Causal reader: допуск уже законен, конкретность всё ещё обязательна

Для P107 original writer — [KnnLogicalUnit.Train](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L113-L211): обучает BPE и записывает HNSW/пример. [Execute](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L215-L273) читает этот state, но output выбирает `hits[0]`; остальные соседи дают только evidence IDs. Проверка typed aggregation на доказанно обученном state может быть проверкой использования результата обучения по текущей политике. Новый update ради допуска не требуется. Исправление обязано определить допустимое равенство/агрегацию для конкретного `TOutput`; «усреднить произвольный Output» не контракт.

У K3 writer — [ExecutorUnit.TrainOnExample](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/27.TranslationDomain/TranslationTrainedUnits.cs#L403-L455), reader — [FindNearestCascade / FindExactWithSourceGuard](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/27.TranslationDomain/TranslationUnitContracts.cs#L246-L292). Подтверждённый источник записи не доказывает, что конкретный query прошёл нужную source-law ветку: exact/phrase/word maps могут ответить раньше. Следующее допустимое действие — конкретный fixture с доказанным маршрутным контрастом, прежними trained bytes и named original fix. Это использование выученной памяти, не обучение новых весов и не приоритет перед direct DPO.

Чистый static docs retrieval без установленной зависимости от процесса/результата обучения остаётся вне программы. Новый общий допуск causal dependencies не означает blanket READY для всех старых карточек.

## 5. Как читать доказательство полноты

Первый снимок содержит полный файловый и нормативный inventory **125 карточек / 470 подслучаев / 133 промптов**. Все 555 planning Markdown имеют индивидуальную запись census. У bf9 было 35 источников без полного path-string mention, из них 13 упоминались по уникальному basename; оставшиеся 22 — семейство N60. Это никогда не означало 35 отсутствующих экспериментов.

Новый 23 добавил явный N60 crosswalk и source-list. [LATE-HEAD-FORMAL-VERIFICATION-de4.json](LATE-HEAD-FORMAL-VERIFICATION-de4.json) повторяет проверку правил и ссылок по **167 документам**: изменённые de4 документы плюс проверенные неизменённые документы bf9. Состав подтверждён повторно: **125 карточек, 470 подслучаев, 133 промпта**; все карточки и промпты содержат правило полезного успеха и causal learning dependency. Два подслучая P86.a/P86.b оформлены bold, а не заголовком; они включены в470, как и в исходном inventory.

| Навигационная связь источника | bf9 | de4 |
|---|---:|---:|
| Точный относительный path-string в active docs | 257 | 279 |
| Точный path-string только в historical docs | 263 | 263 |
| Полного path-string нет, есть уникальный basename | 13 | 13 |
| Ни exact path, ни уникального basename | 22 | 0 |

Итого на de4 все **555** исходных MD имеют файловую ссылочную связь, но для13 она слабее — по уникальному имени. Исторический 35-row reconciliation остаётся картой того, что именно искалось в bf9; не превращается в текущий список пропусков. Исходный census не перезаписан. Два отчёта позволяют проверить, почему вывод изменился.

**Семантическое покрытие каждого утверждения всех 555 документов не сертифицировано.** Наличие имени файла, общего запрета или карточки смежной темы не доказывает точную одинаковую причинную постановку. Для нынешних новых находок пакет даёт отдельные owner/reader/data/metric связи; для уже известных проблем называет существующую карточку и конкретное оставшееся звено. Ни файловый scan, ни эти проекты не являются новым измерением качества обучения.
