# Порядок работ и карта возможных различий

20 октября 2026. Этот документ задаёт порядок подготовки и проверки, а не запускает всю библиотеку опытов. Код проверен на `bf9b543e149ef197da85a767821d98c9b67916d2`; поздние `de4ef0f…` и `f5dd532…` меняют только описания экспериментов. Полная поздняя сверка — [здесь](coverage/LATE-HEAD-RECONCILIATION.md), заключительные изменения — в [дельте f5dd](coverage/FINAL-DELTA-f5dd.md).

## 1. Сначала прямой путь обучения

Нельзя заключать, что «обучения вообще нет», только из отсутствия прироста свободных ответов. Нужно отдельно показать, какой получатель обновился и какой полезный показатель изменился. У RP01 изменение LoRA и margin не доказывает усвоение нового способа объяснять код; успешная память Executor тоже не доказывает обучение нейронного Student. Это два наблюдаемых механизма, которые требуют своих собственных выводов.

Первый приоритет — маленький опыт внутри настоящего learner: точные данные → сохранённое начальное состояние → один изменяемый фактор → actual update → тот же измеритель до и после. Два новых проекта этого пакета не заменяют все существующие семантические вопросы одним ресурсным результатом.

| Задача | Конкретное действие исполнителя | Проверяемый результат подготовки |
|---|---|---|
| Семантический D04 | Самостоятельно выбрать один уже описанный фактор по фактическому коду; заполнить B1–B6 из доступных артефактов | Названо, чем B отличается от A, какой Student учится и какие четыре новые задачи он решает. Незаполненный паспорт не превращается в вопрос пользователю |
| Малый native вход DPO | Подключить двухпарный режим к существующим владельцам `CodeDocumentationSimulationDpoExperiment` / `DpoTrainer`, используя существующие loaders, materializer и admission | Реальная исполнимая команда после реализации host; ровно предусмотренные updates, без второй реализации trainer и без серии сбросов calibration |
| Исходное состояние | Найти совместимый сохранённый B0, tokenizer, reference, optimizer/RNG; проверить фактические bytes и раздельность плеч | Source pin не выдан за загруженную модель. Отсутствующее имя файла сначала исследовано исполнителем; недоступность не заявлена без попытки |
| Новая прямая ресурсная гипотеза | [LC-REF-CACHE](dpo/01-reference-score-reuse.md): две одинаковые пары на каждом из двух шагов, кэш двух пар только в B | Полное время и CPU тех же настоящих updates; cache miss первого шага включён; никакого скрытого warmup обучения |
| Уже описанные прямые N60 | Выбрать отдельно prompt-mask SFT, сохранение AdamW, пустой хвост DPO, порядок SFT/DPO, исправление loop label либо curriculum | Только один фактор и один предмет за опыт; не выполнять всю строку дополнения 23 как обязательный пакет |

Основания: [D04 на последнем head](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/docs/plans/replanning-possible-diffs/experimets/2026-10-19-small-learning-probes/04-documentation-neural.md), [дополнение 23](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/docs/plans/replanning-possible-diffs/experimets/2026-10-19-small-learning-probes/23-additions-n60-small-learning.md), [действующая политика](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/docs/plans/replanning-possible-diffs/experimets/00-execution-policy-2026-10-20.md).

**D04 и LC-REF-CACHE различаются вопросом и расписанием.** Две разные пары D04, предъявленные по одному разу, не дают повторного reference score. В cache-опыте каждая из двух пар предъявляется дважды. Экономия reference вычислений может быть полезным успехом обучения, но не закрывает вопрос о собственных новых объяснениях Student. Ни «два разных урока», ни «два одинаковых обновления» не следует менять молча после получения результатов.

Для LC-REF-CACHE уже приложены неизменённые реальные исходные строки C# и отдельные строки EN→RU. Приготовлены фактор, owner, расписание, метрики и промпт. Реализация малого native host и получение фактического B0 остаются работой следующего исполнительского этапа; в этом документном аудите native запуска нет.

Уточнение последнего N60: минимальный E14/Do с четырьмя уроками и k=3 меняет постоянное большинство меток. Он допустим как опыт доставки изменённых учебных labels, но не доказывает структурное различение новых программ. Это ограничение уже записано в protected; оно сохранено в [заключительной сверке](coverage/FINAL-DELTA-f5dd.md).

## 2. Затем учесть присланное обязательное обновление

Передача `phrase_mappings` из corpus loader в Executor **уже реализована 18 октября**. [required-changes](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/required-changes.md) и [отчёт сравнения](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/translation-memory-ingress-01/report.md) фиксируют одинаковые восемь уроков в двух независимых экземплярах:

| Измерение | До исправления загрузчика | После исправления |
|---|---:|---:|
| Правильные ответы на той же панели | 11/24 | 19/24 |
| Принятые, но ошибочные по строгой оценке ответы | 1 | 3 |
| Потерянные ранее правильные ответы | — | 0 |

Это полезное измеренное улучшение с указанным ухудшением другой метрики. Отдельный [P125](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/P125-enru-memory-01/report.md) показывает **0/24 → 19/24** после обучения новой памяти; [P25](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/P25-enru-cold-01/report.md) проверяет сохранность её результатов после перезапуска. Это три разных сравнения. Их нельзя складывать в последовательный рост 0→11→19 одной и той же модели или объявлять обучением RP01 LoRA.

Следующее действие по этому обновлению — использовать внесённый механизм как исходное состояние и сохранить его ограничения в отчёте. Повторная реализация того же loader fix и повторение 8/24 только ради нового статуса в документации не нужны. Отдельные вопросы Verifier и обучаемых операторов фразы уже включены в актуальный N60; незавершённость их собственных контрактов не отменяет существующий результат P125.

## 3. После этого — зависимые загрузчики, восстановление и readers

Проверка допустима, если показана причинная связь с данными или состоянием обучения. Названия `serving`, `scorer` и `cold restore` сами по себе ничего не исключают. Для повторного использования сохранённого состояния можно взять один уже доказанно обученный checkpoint и сравнить один и тот же consumer до/после исправления; дополнительные уроки ради формальности не нужны. При этом результат честно называется сохранностью или использованием выученного состояния, если новый процесс обучения не менялся.

| Кандидат | Доказанная связь | Где и как предлагается менять оригинал | Приоритет и граница |
|---|---|---|---|
| Новый KN-ROUTER | `RoutingProfileTrainer.Train` записывает keyword-профили; `BaselineKeywordCandidateGenerator.Score` читает эти же признаки | В scorer применить те же C#/.NET replacements до lowercase; [точная карточка и восемь контролей](routing/KN-ROUTER-SMALL-LEARNING-EXPERIMENT-2026-10-20.md) | После прямых задач. Не приписывать эффект DPO; запрос с готовым domain hint может скрыть расхождение |
| Известный P107 | `KnnLogicalUnit.Train` обучает tokenizer и индекс; `ExecuteAsync` возвращает output первого соседа, остальные идут в evidence | До изменения aggregation определить допустимость и эквивалентность конкретного `TOutput`; не усреднять произвольные объекты | Условный отдельный опыт использования выученной памяти. Нужен actual typed consumer, а не только число hits |
| Известный K3/SourceLaw | `ExecutorUnit.TrainOnExample` заполняет store; cascade/exact reader использует этот store | Показать конкретный запрос, достигающий выбранной law-ветки, и адресное исправление именно её решения | Само существование writer/reader ещё не доказывает эффект выбранного SourceLaw; не повторять весь frozen corpus |
| Восстановление модели/Unit | Конкретный saved learned state → import → обычный consumer или следующий update | Исправлять обнаруженное несоответствие tokenizer/model/adapter/index/optimizer/RNG в его owner | Cold equality и правильное продолжение следующего урока — разные вопросы; результат одного не закрывает другой |

Точные source links для P107 и K3 приведены в [аудите каталога](coverage/01-PROTECTED-CATALOG-AUDIT.md); действующее разрешение таких опытов уточнено в [late-head reconciliation](coverage/LATE-HEAD-RECONCILIATION.md). Это не новая гипотеза для каждого исторического P-номера.

Проверки, которые не влияют ни на данные обучения, ни на update, ни на сохранение, следующий урок или чтение выученного результата, остаются вне учебной программы. Исправление текста отчёта или статической демонстрации не получает фиктивный `Train` для допуска.

## 5. Единое правило измерения

**Любое измеренное улучшение полезного показателя считается успехом по этому показателю и предметной теме. Рост точности не обязателен. Рядом показываются остальные измеренные изменения, включая ухудшения.** Никакого минимального процента или обязательной серии повторов этот аудит не добавляет.

Для repair нового обучения сравниваются A до/после и B до/после с одним фактором. Для сохранности/потребителя используется один и тот же доказанно обученный artifact и одна панель, без искусственного повторного Train. Отчёт называет реального learner, что изменилось в оригинале, сколько выполнено updates/уроков, что измерено и что осталось `NOT_MEASURED`.

Нулевой эффект — результат корректного опыта. Неизмеренный эффект — отсутствие результата. Недостижимая выбранная ветка или нулевое различие A/B на данных — причина до измерения подготовить различающий материал, а не подделывать scores или гонять опыт до успеха. Разный экзамен, разные интервалы таймера и скрытые дополнительные updates лишают числа смысла для заявленного сравнения; наличие красивого PASS этого не исправляет.
