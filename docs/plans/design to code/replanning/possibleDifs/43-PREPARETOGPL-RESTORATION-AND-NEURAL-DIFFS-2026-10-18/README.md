# Восстановление PrepareToGPL: новые различия и короткие причинные опыты

18 октября 2026. Цель — вернуть подтверждённые способности конкретных обучаемых компонентов из `PrepareToGPL`, установить новые возможные причины деградации RP01 и не повторять уже выполненные опыты. Публикация относится только к planning/possibleDifs. Core, его защищённый каталог, веса и обучающие данные не менялись.

## Сначала — восстановление PrepareToGPL

**Наиболее прямое различие для восстановления:** один и тот же сохранённый `translation-v1` имеет четыре executor-направления, а текущий loader требует шесть при прежнем `schema_version=1`. Старый файл по-прежнему лежит и в текущей ветке. Обычный путь загрузки создаёт шестинаправленный runtime и отклоняет отсутствующие `EN_ES`/`ES_EN` до восстановления памяти. Это установленное по исходникам и точным байтам несовпадение, а не выполненный здесь native load. [Доказательство и первый опыт](01-LEGACY-CHECKPOINT-GAP.md).

| Очередь | Что восстанавливаем / различаем | Почему в начале | Статус и следующий небольшой шаг |
|---|---|---|---|
| **R01** | Чтение конкретного четырёхнаправленного checkpoint `PrepareToGPL` нынешним runtime | Прямо открывает доступ к старым learned maps и KNN; новые уроки не нужны | **Независимое подтверждение N41-T1**, дополненное exact archived state. A/B/C cold load: старый owner / нынешний / нынешний с явной миграцией только двух пустых направлений |
| **R02** | Полные части урока достигают прежнего `ExecutorUnit` | Уже измерено восстановление композиции: **11/24 → 19/24** при тех же 8 уроках | Исправление уже есть в current. Использовать результат и проверить его наличие в нужном host; не выдавать за ещё не выполненную гипотезу |
| **R03** | Обученный structural KNN E09 участвует в C# ответе | Есть положительные historical receipts; перенос в production не равен включению потребителя | При неизменной памяти/кодировке включить только реальную зависимость ответа от структурного прогноза |
| **R04** | Контекстное различение значения слова E26 | Historical **0.4 → 1.0** на 15 фиксированных случаях; механизм сохранился в соседней `language_translate` | Сначала parity архивной функции, затем один context-use switch на новых технических смыслах слов |
| **R05** | DPO-урок доходит до нужных subunits и обычного Flow | Успех discrete memory не переходит автоматически в отдельный neural adapter | Один общий авторизованный урок, один объявленный получатель состояния; проверить owner→save→reload→обычный consumer |
| **R06** | Изолировать перенос первого момента AdamW C#→ENRU | На retained ENRU chosen score падает на **20/20**, хотя средний relative margin растёт | **Отдельный причинный контраст к DLT-K1:** менять только `m50→0`, удерживая `v50`, step50, C50, reference, RNG и материал |

R01–R05 — глава восстановления и переноса конкретных прежних механизмов. R06 — исследование нынешней нейронной траектории; его нельзя заранее назвать восстановлением доказанно успешного neural алгоритма `PrepareToGPL`. Порядок внутри независимых предметных веток можно менять: R03 относится к C#, R04 — к переводу. [Подробные карточки R01–R06 и два условных опыта](04-SMALL-EXPERIMENTS.md).

## Чего не следует заключать из успеха старой ветки

Исторические успехи относятся к разным owners и разным экзаменам. Успешное обучение memory Unit — реальное обучение; оно не аттестует все соседние DpoTrainer paths. В старом DpoTrainer найден обратный знак log-softmax gradient, в старом RmsNorm — оборванный graph, а старый `LoraApplicator.Apply` возвращает внешние adapters без подключения к base forward. Текущие исправления этих мест нужно сохранить. [Сравнение исходников и границы вывода](02-NEURAL-SCORES-AND-STATE.md#6-что-нельзя-восстанавливать-из-preparetogpl-вслепую).

В этой работе выполнены чтение источников, сравнение сохранённого состояния и пересчёт старых оценок. Новых optimizer updates, Student generation, teacher и evaluator calls — **0**. Native результаты 18 октября принадлежат уже существующим опубликованным отчётам и прямо так названы.
