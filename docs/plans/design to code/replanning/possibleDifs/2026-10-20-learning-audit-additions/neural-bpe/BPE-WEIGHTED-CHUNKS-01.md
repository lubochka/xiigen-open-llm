# BPE-WEIGHTED-CHUNKS-01: учить одинаковые чанки один раз, сохранив их частоту

**Статус: DESIGNED_NOT_RUN — спроектировано, ещё не реализовано и не запущено.** Это новая документационная карточка кандидата. Измеренных улучшений, готового runner и разрешения переносить изменение в продукт она не утверждает. При текущем поручении создаются только эта карточка, prompt, literal fixture и source-copy specification.

## Что и почему проверяем

Тема — документация программ и перевод; два профиля материалов: C# и EN→RU. Получатель учебного изменения — настоящий `Tokenizer.BpeTokenizer`. Он учит таблицу слияний байтов; это состояние потом читает `Encode`. Направление EN→RU не является вторым механизмом обучения, а round-trip токенизатора не является точностью перевода.

Исходный `Train` создаёт отдельный token-list для **каждого** вхождения regex-чанка. На каждой итерации он снова считает пары и применяет merge ко всем экземплярам одинакового списка. При повторяющемся учебном тексте это может расходовать больше выделений памяти и CPU, чем одна копия чанка с целочисленной кратностью. Повторения нельзя удалять из учебной статистики: их вес участвует в выборе следующего слияния.

Проверяется ровно один фактор: вместо отдельных одинаковых списков хранить один список на исходную строку чанка, её кратность и позицию первого появления. Это гипотеза экономии реального BPE-обучения; ухудшение точности RP01 или измеренный выигрыш ею пока не доказаны.

## Точная разница A/B и контрпримеры

**A:** исходный Train/CountPairs/MergeAll/MergeChunk.

**B:** один `WeightedChunk` на идентичную исходную строку regex-чанка; `StringComparer.Ordinal`; порядок — первое появление в исходном корпусе. Хранятся `TokenIds`, `Multiplicity`, `FirstOccurrenceOrdinal`. При CountPairs за каждую соседнюю позицию добавляется Multiplicity; при MergeAll неизменённый MergeChunk исполняется один раз на представителя.

Сохранить UTF-8, regex, пробелы, регистр, целевой vocab320, условия остановки, арифметику pair counts и порядок первого появления каждой пары. Не сортировать чанки или пары. При равных частотах MaxBy должен видеть тот же первый ключ. Перекрывающиеся пары в `aaaaa` считаются так же, как A; замена merge остаётся неперекрывающейся. Разные исходные строки не объединять по хэшу без проверки равенства. Для короткого фиксированного корпуса integer overflow невозможен; это не заявка на новую семантику огромных корпусов.

**Не примешивать BPE-NO-MATCH-COPY-01.** В B этой карточки MergeChunk по-прежнему создаёт список даже при отсутствии совпадения. Изменение действует только в Train; Encode и canonical Save/Load остаются исходными.

На почти уникальном корпусе словарь представителей может ухудшить стоимость. Сходные, но не одинаковые чанки не дают этой экономии. Частотная свёртка без веса, lexical tie sorting и нормализация кириллицы могут изменить tokenizer и являются другими алгоритмами. Равенство A1/B1 проверяется, а не предполагается заранее.

## Фиксированные данные и начальная модель

Полные строки сохранены в [fixtures/bpe-weighted-chunks.json](fixtures/bpe-weighted-chunks.json). Данные буквально воспроизводят маленькую панель известного no-match опыта; **гипотеза здесь другая**. Пять TRAIN строк в каждом профиле повторяются восемь раз блоком T1…T5. Между всеми строками LF, заключительного LF нет. Файл JSON — UTF-8 без BOM. Семантическое содержимое corpus задаётся строками и recipe, не форматированием JSON.

Начальное обучаемое состояние отдельно от модели исполнителя: в каждом процессе новый native BpeTokenizer, `Train("",256)`, 256 байтов и ноль merges. Основной вызов — один `Train(corpus,320)`. Нет нейросетевой модели, LoRA, чекпойнта B0 или генерации; никакую из них не искать и не подменять ими BPE.

Всего четыре обучающих процесса: A/code-doc, B/code-doc, A/en-ru, B/en-ru, и один controller без обучения. В каждом обучающем процессе записать четыре EXAM Encode/Decode до и после одного Train. Бюджет: 4 содержательных Train, 4 byte-vocabulary initialization, максимум 256 выученных merges суммарно, 32 EXAM readout. Восемь повторений строк внутри корпуса не являются восемью запусками. Warmup, дополнительные повторы, подбор vocab/данных и запуск full KNN запрещены в рамках этого конечного опыта.

## Как измерять до и после

Внутри каждого процесса до Train сохранить canonical tokenizer hash, vocabulary, merge count и actual EXAM IDs/Decode. Снять начальные счётчики, выполнить ровно один Train, сразу завершить TRAIN counters и только затем делать after readout. Одинаковая instrumentation в A и B.

| Метрика | Before/after и область |
|---|---|
| Learned state | A0/A1/B0/B1: vocab, merges, canonical SHA256; ненулевой learned merge transition обязателен. |
| Фактический выход | Для каждого EXAM исходная строка, IDs, token_count, Decode, round-trip до/после; сравнить изменения внутри плеча и A1/B1. |
| Выделения | Разность GC.GetAllocatedBytesForCurrentThread за единственный синхронный Train; байты, не «используемая RAM». |
| CPU и время | Process.TotalProcessorTime с Refresh до/после и Stopwatch Train. Одна пара наблюдений, чувствительная к JIT/шуму. |
| GC/память процесса | Разность collection counts; peak working set процесса до завершения TRAIN. Последнее не есть tokenizer-only RAM. |
| Объём работы | Число исходных/уникальных чанков, сумма Multiplicity, обработанные pair positions и вызовы MergeChunk в TRAIN. Эти counters объясняют работу, но сами по себе не объявляются полезным выигрышем. |

Сравнение стоимости: B−A за одинаковый законченный учебный переход. Для выхода: ΔA=A1−A0, ΔB=B1−B0 и ΔB−ΔA там, где величины численные. Изменение round-trip — отдельно. Любое измеренное улучшение полезного показателя считается успехом **по этому показателю и предметной теме**; рост accuracy не обязателен. Рядом показать все ухудшения. Если входы/начальные состояния разные или merge writer не сработал, causal comparison недействительно; нельзя объявлять быстрый отказ улучшением.

Если state/IDs A1 и B1 различаются, это не эквивалентная оптимизация. Сохранить фактический расход и различия, статус `DIVERGED`, не «исправлять» corpus/метрики и не продолжать дополнительными прогонами. Один небольшой elapsed delta не доказывает устойчивый speedup; полезное measured allocation improvement при корректном переходе остаётся успехом по этой оси.

После отдельного поручения реализовать и запустить именно этот опыт, и только после наличия файлов по спецификации:

```powershell
$ErrorActionPreference = 'Stop'
dotnet build C:/xg/bw01/Runner.csproj -c Release -p:Variant=A
if ($LASTEXITCODE -ne 0) { throw 'PREPARATION_FAILED: build A; training not started; no retry' }
dotnet build C:/xg/bw01/Runner.csproj -c Release -p:Variant=B
if ($LASTEXITCODE -ne 0) { throw 'PREPARATION_FAILED: build B; training not started; no retry' }
dotnet C:/xg/bw01/bin/A/Release/net9.0/BpeWeightedRunner.dll run-pair --peer C:/xg/bw01/bin/B/Release/net9.0/BpeWeightedRunner.dll --fixture C:/xg/bw01/in/fixture.json --attempt 0001
if ($LASTEXITCODE -ne 0) { throw 'ATTEMPT_FAILED: preserve partial artifacts; no retry' }
```

Это **конечный интерфейс ещё не реализованного host**, а не готовая команда сегодняшнего запуска. `run-pair` создаёт один append-only каталог `C:/xg/bw01/r/0001`, один раз запускает каждый из четырёх arm/profile процессов и пишет сравнение уже полученных JSON. Build failure означает `PREPARATION_FAILED`, Train не начат. Существующий attempt не очищать и не повторять: без нового прямого поручения нет нового attempt. Отчёт сохраняется в `C:/xg/bw01/r/0001/report.md`; raw и partial status рядом. Папка `docs/plans/replanning-possible-diffs` никогда не изменяется.

**STOP/NEXT обязателен.** При прямом «стоп» немедленно прекратить действия, не делать следующий tool call, обновление памяти или оформление прошлого опыта; сообщить известное состояние.
