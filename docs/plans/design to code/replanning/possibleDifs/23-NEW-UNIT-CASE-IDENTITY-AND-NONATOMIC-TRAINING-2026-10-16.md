## Главный архитектурный контекст и граница применимости

В прежнем гибридном механизме семантический Unit запоминал корректировки, Executor обучал exact/phrase/word/KNN память, Verifier запоминал constraints. Сейчас RP01 DPO эксперимент меняет отдельную q/v LoRA у Student, а **не** вызывает в своём показанном пути `TranslationMachine.TrainStructuredBatchAsync`. Поэтому источником деградации непосредственно RP01 может быть **потеря гибридного получателя**, но найденные ниже две ошибки могут объяснить неправильное воспроизведение/масштабирование *соседнего* механизма, только при подтверждённом caller→Unit→consumer trace.

### N23.01 — P1 — потеря case-sensitive идентичности в точной памяти SemanticTokenizerUnit

**Доказанный кодовый факт.** [TranslationTrainedUnits.cs#L77-L105](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationTrainedUnits.cs#L77-L105) создаёт `_signatureCorrections` с `StringComparer.OrdinalIgnoreCase`, тогда как поиск делает `TryGetValue(Normalize(rawText))`. [Строки 124–148](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationTrainedUnits.cs#L124-L148) при TrainOnExample пишет `_signatureCorrections[Normalize(input.RawText)] = chosen`; `Normalize` только сжимает whitespace, то есть **два различающихся по регистру корректных источника становятся одним ключом словаря**. При второй записи выбор первого целиком замещается выбором второго. [Checkpoint DTO](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationCheckpointContracts.cs#L70-L95) переносит ровно этот неразделённый NormalizedRawText и не способен вернуть две утраченные entries после экспорта.

**Пример:** `May approve the request.` (May — имя агента) и `may approve the request.` (may — модальность без явно названного агента). В некоторых доменных сценариях капитализация меняет actor/role, поэтому ***после независимой экспертизы*** им нужны разные исправленные `TokenizerOutput`. Другие безопасные контрольные примеры: `US` / `us` или case-sensitive символы в code snippets. Условие ошибки — обе учебные строки попадают в один SemanticTokenizerUnit и имеют различающиеся правильные corrections. Если независимый scorer подтверждает одинаковую семантику, это *не* quality-bug, даже если ключи совпали.

**Связь с соседними находками.** [N16 language key](16-INDEPENDENT-TRANSLATION-UNIT-AND-KNN-LEARNING-GAPS-2026-10-16.md) уже описывает отсутствие `SourceLang` в ключе. Здесь **другой фактор**: две записи в **одном и том же языке**, `StringComparer.OrdinalIgnoreCase`, с collision по регистру. [N21 self-label](21-INDEPENDENT-STRUCTURED-LEARNING-GAPS-2026-10-16.md) указывает, что текущий builder зачастую вообще не поставляет исправленную метку: для проверки N23 нужно явно передать независимый исправленный `TokenizerOutput`, иначе тестирует не case collision, а self-label.

**Короткий falsifier:** на одном и том же `SemanticTokenizerUnit` последовательно обучить два уникальных входа, различающихся только регистром, с разными oracle-valid `SentencePattern`; сравнить `Tokenize(A)` и `Tokenize(B)` после обучения только A, затем A+B и затем B+A. Снимок `ExportCheckpoint().SemanticTokenizer.SignatureCorrections` и количество/ключи обязательны. Контроль: две неколлидирующие строки с теми же patterns, плюс одинаковый case с одинаковым oracle. Если A+B и B+A дают разное значение *для A*, collision демонстрируется native C#; семантический вред — только если adjudicator подтвердил разные значения. Shadow treatment — составной ключ `(SourceLang, case-sensitive normalized text)`, не изменять исходный production silently.

**Область доказательства:** `CONFIRMED_CODE_CONDITION`; происходило ли это в реальной истории и улучшит ли heldout — `UNKNOWN`. Отличать case-sensitive замысел от просто case-insensitive текста конкретного домена.

### N23.02 — P1/P0 при ошибках batch — неатомарное изменение обучаемых Unit после неудачи

**Доказанный кодовый факт.** [TranslationMachine.cs#L89-L145](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationMachine.cs#L89-L145): `TrainStructuredBatchAsync` по очереди вызывает `trainer.TrainOnExample(example)` непосредственно на живых объектах, без предварительной валидации *всего* batch, copy-on-write и rollback в показанном методе. Например [SemanticTokenizerUnit.TrainOnExample#L124-L139](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationTrainedUnits.cs#L124-L139) вызывает `JsonSerializer.Deserialize<TokenizerOutput>`, который может выбросить `JsonException` на повреждённом JSON. [ExecutorUnit.TrainOnExample#L403-L422](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationTrainedUnits.cs#L403-L422) аналогично десериализует до записи в shared KNN.

**Последовательность:** пустая машина → пример A валиден и записал correction → пример B содержит malformed chosen JSON и вызывает исключение → сам batch не завершился, `_trainingHistory`, `_structuredTrainingIdentities` для завершённых строк и `_hasStructuredTraining` могут не соответствовать уже изменённым Unit. [Полный ExportCheckpoint#L260-L312](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationMachine.cs#L260-L312) читает живые Unit state и в принципе способен запечатлеть изменение после несостоявшегося batch. Наоборот, метод `ImportCheckpoint` имеет дополнительную preflight-валидацию перед применением ([строки 314–345](https://github.com/lubochka/llm_mvp_core/blob/0eccbdc3c4efb90adf1d699806cbfa9f5610998d/27.TranslationDomain/TranslationMachine.cs#L314-L345)); не объявлять всю подсистему checkpoints неатомарной.

**Риск:** partial lesson, несовпадение provenance/счётчика и фактически выученного поведения, неявный повтор корректировки после retry, нестабильный retention. Это *свойство nested Unit batch*, **не** утверждение о DPO StepVector: он имеет собственные publication/rollback механизмы. Нужна проверка, встречались ли реальные partial-failure в логах.

**Короткий falsifier:** создать две валидные записи через настоящий `TranslationStructuredBatchBuilder.BuildGeneralBatch`; взять 1-й семантический пример, у 2-го semantic примера подменить `ChosenOutputJson` на `"{"` в тестовом объекте, не менять репозиторный dataset. Экспортировать checkpoint до/после исключения; сравнить `SignatureCorrections` и `StructuredTrainingIdentities`, а также ответы для A; контроль — batch только с валидной A и batch только с invalid B; не запускать на приватном/production состоянии. Предлагаемый shadow-fix: preflight всего batch и атомарное применение в временно клонированный runtime с publication swap при успехе.

**Область доказательства:** `CONFIRMED_CODE_SEAM` и детерминированно воспроизводимый сценарий **ожидается**, но native RUN пока `NOT_RUN`. Никаких фактов про реальную частоту ошибок или RP01 деградацию не установлено.

## Проверка альтернативных объяснений и связь с восстановлением качества

См. [12 Matrix↔KNN](12-MATRIX-KNN-TRANSFER-PROVENANCE-AND-EVALUATION.md), [11 cross-branch](11-CROSS-BRANCH-REAL-LEARNING-RESULTS.md).
- **Негативные контроли:** collision, который не меняет oracle; exception до первой valid записи; неприменяемый consumer; независимые реальные условия без ошибки — все должны снижать уверенность причинного утверждения.
- **Ремонт только после falsifier:** trace production caller, exact ID и SHA модели/Unit before-after, совпадающий source-disjoint heldout, cost. Документировать learned vs deterministic guard отдельно.
