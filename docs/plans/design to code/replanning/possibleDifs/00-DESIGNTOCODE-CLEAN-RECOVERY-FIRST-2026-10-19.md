# Сначала восстановить успешное обучение DesignToCode-clean

19 октября 2026. Приоритет задаёт пользователь: вернуть полезное поведение, которое уже работало в **DesignToCode-clean**, и лишь затем расширять алгоритм новыми вариантами. В этой главе выделены проверки восстановления; общий реестр прежних гипотез сохраняет своих владельцев.

Эталон исходников — `llm_mvp_core/DesignToCode-clean@e346b88a3cc1fcce48aefa626bfc7b00509eefd6`, сравнение — `codex/dpo-implementation@358af351e22a92a3f7938d1f9221d5aeb7ddb053`. **Название ветки не определяет автоматически commit исполнявшегося успешного trainer или сохранённое состояние.** Сначала надо связать исторический результат с ними и со штатным потребителем. Источники и ограничения разобраны в [исторической главе пакета 54](54-DESIGNTOCODE-CLEAN-RECOVERY-2026-10-19/01-HISTORICAL-BASELINE-AND-RECOVERY.md).

## Граница доменов и восстановления

E09 проверяет структурированные задачи о коде. E25 проверяет POS-классификацию в предметной области перевода; языковые направления EN→RU и RU→EN не являются отдельными предметными доменами. R4/R5 относятся к преобразованию исходного UI-дизайна в HTML/CSS. Их прямое участие в неудаче RP01 C#/EN→RU ещё надо подтвердить его caller trace. Общая карта, включая LoRA, DPO, векторы, KNN, Units и Flow, находится в [03](54-DESIGNTOCODE-CLEAN-RECOVERY-2026-10-19/03-MECHANISM-COVERAGE-AND-NEURAL-PARITY.md).

R4 восстанавливает совместимость старого состояния через явную миграцию. Возврат provenance features в runtime whitelist не предложен: допустимые semantic weights сохраняются, старые quality claims не переносятся без проверки. Полного архивного CLEAN feature checkpoint с нужным key в просмотренной evidence-области не найдено; найденный producer manifest не содержит сами веса. R5 также не требует полного отката к CLEAN: тогда runtime prompt уже отличался от training prompt, а scorer использовал synthetic стороны. Проверяется исправление этого условия с нынешними exact HTML/CSS сторонами. [Разбор источников и контраргументов](54-DESIGNTOCODE-CLEAN-RECOVERY-2026-10-19/02-NEW-CHECKPOINT-AND-CONTEXT-GAPS.md).

## Что считать успешным результатом следующего этапа

Сначала — совпадение состояния, параметров и входного контракта после восстановления; затем — видимое использование обученного получателя; затем — улучшение предметного поведения на одинаковой закрытой панели. Изменение веса, успешный импорт или падение DPO loss по отдельности ещё не доказывают качество ответа. Для каждого опыта фиксировать контроль, измерение, отрицательный результат и область переноса. Малые планы, оценка объёма и stop conditions — в [04](54-DESIGNTOCODE-CLEAN-RECOVERY-2026-10-19/04-DOMAIN-MICRO-EXPERIMENTS.md).

Все перечисленные здесь новые native опыты имеют статус **NOT_RUN**. Этот пакет — чтение доказательств и план проверок. Когда понадобится новая DPO-пара, CODEX с Astra 6 ultracode выполняет делегированный человеческий выбор урока и отдельно оценивает точную пару; внешняя разрешённая открытая китайская модель генерирует обе стороны. Обычный runtime не получает оценочные labels из будущего или незаслуженно повторно использованную authority.
