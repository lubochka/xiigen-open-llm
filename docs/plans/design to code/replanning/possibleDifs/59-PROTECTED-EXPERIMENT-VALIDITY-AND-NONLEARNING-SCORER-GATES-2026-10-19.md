## 1. Три обязательных правила допуска

**Граница пользовательского запрета (HARD):** любое сравнение, объявленное «влиянием на качество обучения», должно действительно изменять алгоритм или вход РЕАЛЬНОГО обучения, затем изменять состояние НАЗВАННОГО обучающегося Unit/Student и мерить реальный выход ЭТОГО состояния по обычному маршруту до и после. Изменение функции, которая не участвует в обучении, чтение metadata, имитация gold output или offline scoring-only не являются обучающим экспериментом, даже если получен красивый delta. Диагностику допускается записать без дорогого запуска, но запрещено представлять как evidence learned gain. Особенно недопустимо тратить токены на такие опыты после запрета пользователя.

**Успех по показателю:** любое фактически измеренное положительное изменение полезной метрики — успех по этому показателю и домену: RAM, VRAM, latency, tokens/s, время/шаги до порога качества, CPU, объём состояния, полезная точность, меньшее число опасных ответов, retention. Рост accuracy не обязателен. В том же отчёте обязательна полная таблица всех остальных метрик, включая деградацию: например RAM -10% и quality -20% означают локальный успех RAM с регрессией quality, а не общую победу. Нельзя считать изменение дефиниции счётчика физическим ускорением.

**Контроль A/B:** реальный recipient, admitted TRAIN data (not TEST/gold in input), хэш исходного checkpoint/Unit, одинаковые начальные A0 и B0, одинаковые обучающие update/lessons, только одно заявленное отличие, A1 и B1, независимый закрытый family-disjoint EXAM (native own outputs), scorer заранее утверждён и одинаков, cold restore при изменении checkpoint, honest costs. A0/A1/B0/B1, raw outputs, failed examples, success-per-metric, tradeoffs, no default accuracy-only gate. Зависимость от будущего runner/model не заполнять выдуманными checkpoint SHA или sample measurements; маркировать BLOCKED_INPUT.

## 3. Новый точный source риск для ПРОВЕРКИ метрик (H59-M1), но НЕ эксперимент обучения

[OrchestrationReasoningScenarioUnit.EvaluateHeldOutRows](https://github.com/lubochka/llm_mvp_core/blob/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/43.SmartSkillsDomain/OrchestrationReasoningScenarioUnit.cs#L416-L496) делает structureMode = heldOutRows.Any(row => row.ExpectedDecisionStructureRefs?.Count > 0). Если хотя бы у **одной** записи есть expected structural refs, то **для всех** записей применяется structural-scoring ветвь; записи без refs не могут инкрементировать correct и никогда не проходят обычную сравнимую Plan-оценку. Эта panel-level смена метрики может создавать ложную регрессию при изменении СОСТАВА EXAM даже если learner не поменялся. **Сначала явно разделить homogeneous exam profiles; не называть score delta обучением**. Не рекомендован отдельный дорогой эксперимент: source inspection достаточно для риска, а до реального native learning он не раскрывает нужную пользователю причинность.

**H59-M2:** в той же [структурной ветви](https://github.com/lubochka/llm_mvp_core/blob/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/43.SmartSkillsDomain/OrchestrationReasoningScenarioUnit.cs#L425-L456) итог observedStructureRefs берётся через SelectMany по **всем** найденным NearestGuides, не только по реально выбранному Plan/первому guide. ExpectedDecisionStructureRefs.Any(expected => observed.Contains(expected)) — допускает хотя бы одно совпадение в union, когда реальный top guide выбирает другую структуру. Более широкий поиск может повысить metric без улучшения способности выбирать правильный plan. **Не считать эту evaluator-only величину quality of trained consumer**. Это отдельный риск **валидности измерителя**, не новая инженерная гипотеза улучшения training.

По быстрому адресному сравнению N52/N56 нет точного описания этой двойной source ветви, но все архивные файлы не перечитывались, потому новизна условная. **Оба H59-Mx являются находками измерения, НЕ полноценными пользовательскими learning experiments; отдельные не запланировать и не запускать.** Если они мешают обязательной проверке real learning, хранить сырые own Plan outputs и вычислять независимую заранее фиксированную рубрику без нового тренировочного факторa; это reviewer verification, не claim gain.

## 4. Матрица результатов, которую нельзя подменять

Для каждого разрешённого реального train experiment необходим raw файл с одним полным рядом на каждую комбинацию {subject domain, arm, checkpoint stage, case_id}. Поля: Model/Unit/Flow identity; source branch/commit; dataset IDs and SHA; train rows/step count; AdamW/LoRA or memory state fingerprints; saved/loaded checkpoint SHA; actual selected route and own raw output; expected HARD/soft properties (ex ante); correct/all, correct/answered, answered/all, dangerous false acceptance/all; confidence/margin separately; time to useful quality; CPU ms (real process), wall ms, peak group RSS, GPU/VRAM if used; index/weights bytes, Unit count/executed depth and neuron layers, cost. Для не относящихся показателей явно N/A с причиной. Report delta для каждой полезной оси и всех tradeoffs, не агрегировать C#, SQL, EN→RU, RU→EN и orchestration в одну accuracy.

Проверка уровня доказательства: SOURCE_CONFIRMED = код; TRAIN_REACHABLE = producer→actual update→deployed consumer с receipt; LEARNING_CAUSAL = одинаковые A0/B0, actual A1/B1, native own responses, закрытая subject rubric и сохранившиеся hashes; DOMAIN_TRANSFER = другая независимая train-family. Не перепрыгивать ступени и не заявлять «все причины найдены».
