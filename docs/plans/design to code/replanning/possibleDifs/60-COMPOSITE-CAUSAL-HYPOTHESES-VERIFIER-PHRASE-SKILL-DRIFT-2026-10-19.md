## N60-H1 — False-negative builder → сохранённое ложное требование Verifier → veto полезного перевода
**Исходные факты:** builder может сгенерировать rejectedCandidate идентичный chosen для gender/case/tense иных не-omission rejected; Verifier record всё равно помечает Candidate as fail, обученный Verifier сохраняет requiredTerm из этого примера; затем обычный adapter может отвергать собственный новый ответ, если learned required term не найден.

**НОВАЯ СОСТАВНАЯ гипотеза:** при реально достижимом source marker/semantic signature неправильно сформированная negative-part может породить чрезмерно специфичное learned requiredTerm, ухудшив приемлемость *правильной синонимической* генерации другого Unit даже при неизменённой Executor memory. Это не следует автоматически из совпадения двух строк: (i) выбранная ветка TrainOnExample должна реально записать rule; (ii) Verify должен увидеть релевантный ключ/marker; (iii) adapter должен действительно применить её и не обойти. Если какое-либо ребро отсутствует, статус NO_CAUSAL_LINK, источник только material-quality gap.

**Не подменять отрицание простой подстрокой:** P56.7 и P56.10 уже отдельно проверяют whole-token и polarity. Здесь фактор строго *допуск ложной Verifier-negative в обучение*, а не исправление String.Contains после обучения.

**Быстрый обучающий опыт:** N60-E1 в соседней экспериментальной карточке. A0/B0: одинаковая пустая обучаемая память Verifier и frozen Executor (при отсутствии ранее обученного executor предварительно одинаково выучить валидный корпус). A1: текущий BuildGeneralBatch и реальный TrainStructuredBatchAsync с общим утверждённым материалом. B1: тот же batch, но для Verifier rejectedCandidate==chosen не допускается как fail-lesson; причина NO_DISTINCT_NEGATIVE документируется при materialization, остальной batch тот же. Повторно не генерировать ложный candidate. После обеих историй — real verifier readback+ordinary Flow новых парафраз, как реальных входов, а не mock candidates. Единый фактор — admission ложного fail-урока; число *accepted* lesson samples является измеряемым эффектом, не принудительным равенством.

**Фальсификаторы:** исправление не меняет actual rule state; новый answer идёт по early branch, которому verifier не препятствует; ни один независимый правильный paraphrase не теряется. Тогда гипотеза не подтверждена; P52.8 остаётся defect material без доказанного semantic learning impact.

## N60-H2 — Подтверждённый прирост обучения composition одновременно повышает покрытие неверных смысловых операторов
Исторические cc01/cc03/cc04 с adapterId executor-en_ru-phrase-map, confidence 0.99 доказывают: *неверный ответ был сформирован этим learned-memory consumer и принят после тех же 8 уроков*. Они НЕ доказывают, что shortcut verification.Pass OR phraseMapCandidate применился именно на этих cases: в archived raw нет собственного verification.Pass/Issues и внутреннего score. [Adapter code](https://github.com/lubochka/llm_mvp_core/blob/codex/dpo-implementation/27.TranslationDomain/TranslationDirectionAdapters.cs#L118-L148) допускает phrase-map с confidence≥0.85 даже если verification.Pass=false, а возвращаемый confidence берёт max(candidate confidence, verifier.Score), ограниченный сверху 0.99. Отсюда два различных возможных пути к одинаковому reported 0.99. Не путать этот симптом с доказательством обхода Verifier.

**НОВАЯ ПРОВЕРЯЕМАЯ связка:** training ingress более богатых PhraseMappings может одновременно (i) учить полезную комбинацию action+object и (ii) не создавать представления обязательных незнакомых операторов отрицания, вопроса и связи двух объектов, после чего output получает ложную уверенность. Возможна не новая отдельная policy guard, а именно изменение *обучаемого представления входных операторных слотов* из тех же 8 lessons. Если proposed representation не записано в реальное mutable learned state при Train, такой A/B невалиден как эксперимент обучения: не запускать, не маскировать как learning.

**Короткий valid experiment N60-E2:** одинаковые 8 законных исходных уроков и одинаковый независимый EXAM, изменяется только training-time feature projection из lesson в Executor phrase memory (A: текущие surface PhraseMappings; B: versioned source-token/role/order support metadata, полученные из TRAIN input, те же mappings и тот же ordinary consumer). Никаких manually hidden EXAM labels, no predicate based on exact cc01 string, и тот же safety hard-gate в обеих ветвях. Проверить A0/A1/B0/B1, что learned index/material differ, а consumer читает same state. Метрики: 8 legitimate recombinations, wrong accepted for polarity/question, correct/all, correct/accepted, coverage, time/lesson, RAM, map bytes. Симулировать parser/Unit вместо actual запрещено. AST канал тут не применяется; релевантны EN→RU word order/polarity.

**Фальсификаторы:** если B не меняет учебное состояние, не может при тех же уроках выделить операторный тип либо не достигает ordinary consumer, классифицировать только POLICY_DIAGNOSTIC_NOT_LEARNING и не тратить learning-токены; если правильные комбинации теряются, это явное ухудшение рядом с любым выигрышем safety.

## N60-H3 — Исторический конфликт правила успеха в skill против user-defined multi-metric success
[experiment-design-SKILL.md](https://github.com/lubochka/llm_mvp_core/blob/codex/dpo-implementation/docs/skills/experiment-design-SKILL.md) до сих пор формулирует единичный Metric, PASSED через enhanced>baseline + Gate B и FAILED только после Tier3. Такое устаревшее бинарное толкование может переобозначать полезный прирост скорости или качества по частичному смысловому пункту как неудачу при неудовлетворённом чужом gate. Современный [01-method-and-report](https://github.com/lubochka/llm_mvp_core/blob/codex/dpo-implementation/docs/plans/replanning-possible-diffs/experimets/2026-10-19-small-learning-probes/01-method-and-report.md) и пользователь прямо требуют **SUCCESS_BY_METRIC_AND_DOMAIN при любом измеренном полезном изменении**, с отдельным перечислением вреда, без обязательной Tier3 эскалации.

Это source-proven **конфликт инструкций классификации**, а НЕ доказанная причина снижения native learning. Здесь нужен только редакторский разбор precedence и добавление явного предупреждения в sidecar/исполнительский промпт. НЕ запускать модель/тесты для проверки конфликта инструкций; не менять protected и skills по этому поручению.

## Общее правило каждого нового опыта и prompt
**Любое действительно измеренное полезное улучшение считается успехом по выбранному показателю и предметной теме; рост accuracy не обязателен. Другие значения, ухудшения и число ошибочно принятых ответов обязательны рядом.** Должен участвовать реальный обучаемый recipient, реально записанный lesson/state и ordinary consumer этого состояния. Standalone metric/decoder/restore/policy-only → INVALID_AS_LEARNING_EXPERIMENT; **не тратить токены**. Все N60-E требуют индивидуального прямого разрешения Любы на их полную точную версию перед native запуском. На 19 октября все — DRAFT / NOT_RUN.
