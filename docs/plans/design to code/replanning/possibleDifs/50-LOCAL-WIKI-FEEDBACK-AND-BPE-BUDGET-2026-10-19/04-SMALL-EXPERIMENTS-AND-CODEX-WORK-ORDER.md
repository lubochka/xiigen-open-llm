# 04. Короткие причинные опыты и наряд исполнителю

Этот документ делает две новые гипотезы и приоритет восстановления проверяемыми. **Выполнены только source-аудит, подсчёт архивных строк и две Python-пробы.** Нативный .NET, обучение весов, оценка CODEX в указанной конфигурации и внешняя генерация DPO здесь не запускались. Ни один предлагаемый ниже качественный результат не заявлен полученным.

Приоритетные восстановительные различия и источники — [глава 0](00-LOCAL-WIKI-RECOVERY-FIRST.md); точные новые механизмы — [LW-FB-01](01-NEW-CURRICULUM-FEEDBACK-GAP.md) и [LW-BPE-02](02-NEW-BPE-SEED-BUDGET.md). Старые DPO/LoRA/KNN гипотезы сохраняют своих владельцев в [карте 03](03-MECHANISM-COVERAGE-AND-KEPT-FIXES.md).

## 1. Что именно считает успехом каждый слой опыта

| Уровень | Проверяемый вопрос | Достаточное свидетельство | Чего оно ещё не доказывает |
|---|---|---|---|
| Исходный механизм | Отличается ли настоящий вход или вычисление? | Сохранённые bytes/IDs, score decomposition, exact selected target, источник и SHA | Изменение качества ответа |
| Получатель обучения | Изменился ли intended learned state? | Изменение нужных параметров/памяти и trace, исключающий другой получатель | Что этот state используется обычным запросом |
| Предметное качество | Стал ли правильнее независимый обычный ответ? | Парные ответы на заранее замороженных новых задачах, предметная оценка вслепую | Обобщение на все темы и большие выборки |
| Сохранение | Действует ли то же знание после перезапуска? | Fresh process, exact checkpoint/tokenizer/index, повтор тех же вопросов | Долгосрочную устойчивость при новых уроках |

Для малой панели не делать статистических заявлений по одному удачному примеру. Показать все ответы, числитель и знаменатель, направление каждого изменения и отрицательные результаты. Сначала один согласованный seed и бюджет; повторять на дополнительных seeds только если первый опыт различает гипотезы и остаётся конкретный риск случайности.

## 2. E50-FB: обратная связь при выборе следующего урока

**Предметная область:** документация по проекту; две функции — routing запросов и создание source-grounded документации C#/SQL. Уровень архитектуры — `WikiTraceAggregatorUnit` внутри штатного planning Flow. Это recommendation, после которой решение принимает CODEX. Она не является KNN и сама не обучает модель. [Источник и reachable caller](01-NEW-CURRICULUM-FEEDBACK-GAP.md).

### E50-FB-A — нативный контроль, ноль updates

Взять валидный current421 registry. A использует нынешнюю формулу; B меняет только расчёт при пустом `FailedUnits` на точную donor-формулу. Проверки допуска, формат ответа и приоритет явно переданного свежего failure одинаковы. Основные пять входов уже перечислены в [selector receipt](evidence/selector-receipt.json): исходный registry, +1 accepted, +8 accepted, +7 rejected и 1 accepted, +1 rejected. Вызвать их через plan-mode и проверить совпадение target с source-equivalent receipt. Записать `training_started=false`, target, breakdown score и IDs выбранного окна.

Для прямого контроля зависимости donor от принятого результата отдельно сравнить копию истории без accepted и ту же историю с одним accepted accuracy1: source-level zero у конкретного Router не означает, что любое добавление accepted обязательно переключает весь глобальный winner. В matched421 основной результат — **различие формул на одном входе**, а не доказанное переключение победителя от одной новой accepted-записи.

Восстановительный контроль B1: переименовать только `BatchId`, сохранив Unit, statuses, metrics, timestamp/sequence и порядок настоящих событий. Если результат «recent8» меняется, записать зависимость от имени. Не добавлять исправление времени одновременно в B: точная старая формула и улучшенное временное окно — два разных вмешательства. Если явного времени нет, его нельзя выдумывать из имени кампании.

### E50-FB-B — равный бюджет и предметный ответ

Сначала подтвердить по одному реальному дефициту каждой из двух функций и связь изменяемого состояния с обычным ответом. Заранее заморозить 12 новых вопросов: 6 routing, 6 документация. Отдельная небольшая dev-панель используется для промежуточного принятия урока; финальные 12 не участвуют в следующем выборе.

Подготовить один общий пул разрешённых содержательных уроков, достаточный для шести разных задач любой функции. Кандидатный набор в обоих плечах одинаковым способом ограничить этими двумя функциями. A/B начинают с одинаковых состояния и реестра, получают по **6 уроков с одним optimizer update на урок**; одинаковы пул исходных DPO, seed, mask, LR, reference, порядок внутри выбранного урока и правила acceptance. Единственное управляемое вмешательство — формула рекомендации следующего Unit. Последовательность фактически выбранных уроков может различаться как её следствие. CODEX выбирает урок, фиксирует основание и факт следования рекомендации. Если он выбирает одинаковые уроки в обоих плечах, это полезный отрицательный результат для влияния этой подсказки.

Переобучение уже принятого урока не подменяет новый слот. После каждого слота фиксируются parent/result checkpoint, exact lesson ID, запись о решении и результат отдельной dev-панели. Итог — корректные ordinary ответы /12, routing /6 и документация /6, сохранение ранее правильных ответов, распределение шести слотов и cold-load повтор.

**Граница harness:** production `ProjectWikiDpoMetricRunner` требует ровно 50 train и 50 heldout. Не снимать этот guard ради опыта. Шесть единичных updates выполняются отдельным малым harness существующего trainer API при сохранённом recipient/consumer; это не `RunOneBatchAsync`. Если законного малого пути нет, сначала выполнить только E50-FB-A и записать точную недостающую связь. [Источник ограничения и пошаговый опыт](01-NEW-CURRICULUM-FEEDBACK-GAP.md).

**Опровержение влияния:** настоящий исполнитель не использует этот plan; либо CODEX выбирает одинаковую последовательность; либо при корректном consumer и равном бюджете независимые ответы не улучшаются. Снижение счётчика rejected само по себе не считается качеством.

## 3. E50-BPE: состав корпуса при фиксированном merge budget

**Получатель:** впервые создаваемый generated `TransformerEmbeddingKnnLogicalUnit`, чей tokenizer строится через `DefaultLogicalCapabilityTrainer.BuildTokenizer`. Для продолжения от существующего checkpoint сначала сохраняется его tokenizer. Это унаследованный фактор, а не donor/current регрессия. Точные параметры, source и полный текст пробы — [02](02-NEW-BPE-SEED-BUDGET.md).

### E50-BPE-A — нативные токены, ноль updates

Для точного воспроизведения четырёх опубликованных fixtures сначала сохранить их fallback `seedText` без изменений. Затем провести отдельный повтор на настоящих учебных текстах и сохранённом `seedText` от compiler. В каждом повторе предметный корпус, `seedText` и vocabulary budget512 одинаковы между A/B/C. A — исходные 512 различных `semantic_seed_000…511`; B —512 повторов `semantic_seed_000`, равных по числу позиций и длине в байтах; C — без наполнителя как диагностический контроль. Повтор 000 не предлагается как продуктовая технология.

На [четырёх опубликованных fixtures](evidence/seed_probe_results.json) и отдельно на настоящем compiler output сравнить VocabSize, merge recipe, token IDs, decode round-trip, token count и последнее критическое условие в prefix64. Численные результаты Python не переносить на .NET заранее. При расхождении сначала объяснить splitter/tie/encoding, потом запускать quality-часть.

### E50-BPE-B — память и обычный ответ

В первом коротком опыте взять документацию и оркестрацию: по 8 учебных примеров и 8 независимых вопросов. Противоположные варианты различаются порядком действий, отрицанием или условием в конце. Примеры учебного контраста: «записать результат после подтверждения» и «записать результат до подтверждения»; «при отказе отменить операцию» и «при отказе продолжить». Это эскизы формы, не готовые DPO. Новые вопросы используют другие сущности и формулировки.

Создать для каждого плеча новый согласованный tokenizer/encoder и индекс из одних и тех же разрешённых уроков. Размеры модели, recipe initialization/seed, правила KNN, порядок уроков и бюджет одинаковы. В token/KNN-опыте optimizer updates могут быть нулевыми: проверяется выученная память. Если предмет требует нейронного DPO, обе стороны получают одинаковые короткие updates на одном наборе исходных пар. Нельзя подложить новые token IDs прежним обученным embeddings или LM-head.

Главный результат — корректный ordinary ответ /8 отдельно по теме, порядок/отрицание, false accepts и сохранение старого знания. Дополнительные измерения: какая память выбрана, vector/lexical/pattern части, фактический fallback и сохранение результата после fresh load. Нынешние full-text лексические пути могут компенсировать короткий neural prefix; именно поэтому token count не заменяет итоговую оценку.

После установления настоящего factory consumer можно добавить профиль перевода и профиль числового кода. Отдельный numeric контроль обязателен: технические цифровые merges могут помогать некоторым задачам. Положительный результат на тексте с отрицанием не даёт основания универсально менять tokenizer всех Units.

**Опровержение влияния:** обычные ответы и выбор правильной памяти не меняются, эффект полностью компенсирует lexical path, либо выигрыш сопровождается потерей качества на числах. Результат Python для оркестрационного `rollback` уже отрицательный по попаданию вprefix64 и сохраняется в отчёте.

## 4. Короткие опыты для остальной восстановительной цепочки

Эта таблица конкретизирует очередь из главы 0, не присваивая новые номера уже существующим гипотезам. Полные прежние source-карточки и эксперименты связаны через [03](03-MECHANISM-COVERAGE-AND-KEPT-FIXES.md).

| Проверяемое отличие | Малый A/B | Предметная панель | Что покажет причинную связь |
|---|---|---|---|
| Настоящая тройка DPO против type-only | 4 пары с одинаковым `RejectedType` и разными правильными route/call edges; A нынешняя проекция, B original source triple; до обучения показать bytes. Затем один равный малый бюджет | 8 новых вопросов о других методах или формулировках маршрута | Улучшение верного маршрута/трассы при сохранённом recipient; предпочтение `PREFERRED_*` недостаточно |
| Continuation против fresh | Снять начальные policy/reference identities до updates; затем один новый урок при A свежем старте и B точном parent+reference | 6 старых и 6 новых вопросов по проекту | B сохраняет старое знание и приобретает новое; итог используется обычным consumer и остаётся после load |
| DPO→под-Units теряет смысл | Один исходный контраст разложить штатно; A фактические входы subunits, B исправление ровно одного потерянного поля/координаты; same recipients | Код: caller/callee/scope; язык: кто действует, над кем, отрицание | Меняется соответствующая промежуточная функция и итоговый ответ. Совпадение имён Units или число записей не является PASS |
| LoRA действительно обучает нужный путь | На текущем исправленном ядре выбрать один поддержанный параметр A/B, dropout0, проверить численную производную и один update; затем разрешённый adapter on/off | Две противоположные содержательные задачи одного recipient | Градиент соответствует loss, меняется нужный параметр и независимый ответ. Старое ядро не возвращать |
| KNN нужен AST-признак в функции | Одинаковая candidate memory и одни heldout AST из 8 других файлов; A vector-only, B ровно один AST/edge-order признак в reranking | Программирование, C#; отдельный перенос на другой язык только с его AST codec | Совпадает panel/denominator, нет межфайлового Zip и утечки локального kindMap; верные call edges растут без invented edges |
| KNN нужен языковой порядок/POS | Одинаковые слова, но перестановка ролей, negation или POS context; A без одного признака, B с ним; по 8 новых пар контрастов | Перевод как область; EN→RU и RU→EN — отдельные профили | Сохраняются роли и отрицание, а не только лексическое пересечение. AST-признак сюда не переносится |
| Детерминированная ветка закрывает learned state | Обычный вызов с trace; A исходное состояние, B обученное, отдельно фиксируемый lawful rule/fallback; исключить target/PairId leakage | Wiki routing, source-grounded ответы | Изменённый learned consumer причинно меняет ответ. Если решения одинаково задаёт правило, оценка относится к правилу |
| State сохраняется неполно | Один accepted урок, измерение ordinary ответа, Save, новый процесс, Load; A живой state, B восстановленный | 8 новых вопросов той же области и 4 ранее решавшихся | Совпадают состояние, label semantics, retrieval и ответ; идентичность JSON-описателя без весов/индекса недостаточна |

Числа в таблице — проект маленьких различающих опытов, а не новые параметры production pipelines. Существующий batch guard не меняется; маленький harness должен использовать настоящий learner и его ordinary consumer. Если это невозможно, результат ограничивается локализованным механическим контрпримером.

## 5. Роли, подготовка пар и оценка

**Человеческий выбор и качество выполняет CODEX в заданной пользователем конфигурации `astra 6 ultracode`.** Это два отдельных действия: выбрать предметно полезный урок и независимо оценить качество DPO/результата. Внешняя открытая китайская модель генерирует chosen и rejected. В данном исследовании такие вызовы не выполнялись; написанные вручную token fixtures — диагностические входы скрипта.

Для будущего исполнения сохранить provider, точный model ID/version, параметры запроса и исходный ответ китайской модели. Не подменять отсутствие этой модели текстом исследовательского агента. Точное обозначение `astra 6 ultracode` должно быть разрешено в реально доступную конфигурацию CODEX перед model-backed запуском; не записывать неподтверждённое название как уже выполненный model call.

Короткий наряд генератору:

> По заданному проектному источнику, теме и намерению создай одну пару предпочтения. Сохрани source prompt. Chosen полностью решает задачу. Rejected выглядит правдоподобно и нарушает ровно указанную смысловую границу: call edge, порядок, отрицание, роль или маршрут. Не сообщай правильность метками PREFERRED/FINAL_PASS. Сохрани обе полноценные версии, происхождение источника, объяснение одного различия и требуемый контекст. Не используй финальные проверочные вопросы для создания урока.

CODEX проверяет фактическую правильность по источнику, наличие понятного контраста, отсутствие двусмысленности и утечки answer label, сохранение смысла при передаче subunits. Формат/checker может подтвердить структуру, но не заменяет этот предметный выбор. Для финального A/B выводы предъявляются CODEX с перемешанными скрытыми названиями плеч, одинаковым source context и rubric; эталонные ответы и критерии фиксируются до просмотра результата.

Роли следуют текущему заданию пользователя; старые примеры skill/RP01 с иной моделью или симулированным teacher не изменяют этот контракт. Применённые project skills и точные источники перечислены в [05](05-SOURCES-NOVELTY-AND-REVIEW.md).

## 6. Минимальный отчёт исполнителя

Для каждого опыта сохранить один manifest и одну таблицу всех проверочных задач. Обязательные поля:

- `experiment_id`, статус `PROPOSED / SOURCE_PROXY_EXECUTED / NATIVE_EXECUTED`, точные source refs и единственное вмешательство;
- subject domain, profile, Unit/Flow, фактический learner, state recipient и ordinary consumer;
- исходные источники/пары, их hashes, модель генерации и отдельный CODEX verdict; final/dev/train разделение;
- parent policy/reference/tokenizer/index identities, seed, mask, LR, число updates, порядок уроков и законный admission path;
- по каждой задаче A/B outputs, предметные ошибки, evaluator verdict и основание по source;
- before/after/cold-load counts с одинаковыми знаменателями; время/RAM и все отрицательные контроли;
- решение: подтверждён только механизм, есть ограниченный предметный выигрыш, эффект не найден или опыт блокирован конкретной отсутствующей связью.

Команды выполняются из каталога этого пакета и не запускают обучение:

```bash
python evidence/selector_probe.py --output selector-receipt-rerun.json
python evidence/seed_probe.py > seed-probe-rerun.txt
```

`selector_probe.py` читает компактные исходные registry projections рядом с собой и записывает JSON в переданный `--output`. BPE-проба содержит все свои фиксированные inputs и сама записывает полный JSON в `evidence/seed_probe_results.json`, обновляя этот файл при повторе. Её stdout — краткая текстовая сводка, поэтому перенаправлен в `.txt`; он не является JSON-receipt. Если требуется сохранить оба receipts для сравнения, перед повтором скопировать приложенный `evidence/seed_probe_results.json` под отдельным именем. Сравнение результатов и ограничения переносимости описаны в [независимой проверке](evidence/independent-review.md).

Результат этого наряда остаётся связанным с конкретной областью и consumer. Выигрыш AST reranking нельзя записать как доказательство LoRA; рост DPO preference нельзя записать как свободную генерацию; успешная запись checkpoint нельзя записать как успешное восстановление способности.
