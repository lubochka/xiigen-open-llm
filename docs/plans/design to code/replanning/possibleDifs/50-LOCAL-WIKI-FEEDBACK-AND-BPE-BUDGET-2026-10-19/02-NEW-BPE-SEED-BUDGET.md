# 02. Искусственные строки расходуют словарь BPE до предметного обучения

**Новая гипотеза LW-BPE-02.** В начальном создании generated capability к учебному тексту добавляются 512 строк `semantic_seed_000` … `semantic_seed_511`. Словарь ограничен 512 токенами, причём первые 256 заняты одиночными байтами. Часть оставшихся 256 слияний BPE расходуется на технические слова и номера. В результате тот же предметный запрос может занимать больше токенов; важное условие попадает за границу 64 токенов нейронного компонента KNN.

Это унаследованный механизм: он есть и в `local_wiki_planning`, и в текущей ветке. Его влияние зависит от темы и длины данных. Он **не объясняет сам по себе** отличие RP01 с уже сохранённым tokenizer629. Восстановление конкретного успешного checkpoint начинается с его собственного tokenizer; изменение состава словаря — отдельный опыт при создании нового получателя.

## Что было и что осталось

Сравниваются donor `219d7ba89dc3ef43e03e17f1461ad96154d3dd7a` и current `4945b8e85c17b5f150eb5b840d16bbdc4b506242`.

| Участок | Ветка `local_wiki_planning` | Текущая реализация | Следствие |
|---|---|---|---|
| Создание словаря generated capability | [BuildTokenizer, 862–869][old-factory] | [BuildTokenizer, 4054–4061][factory] | Одинаковые 512 технических строк и бюджет 512 |
| Алгоритм BPE | [Train, 22–47][old-bpe] | [Train, 42–68][bpe] | 256 исходных байтов; последовательные наиболее частые пары |
| Когда обучают этот tokenizer | Свежий teaching stack | [Только при отсутствии parent, 2323–2334][fresh]; [при parent загружается сохранённый tokenizer, 2361–2375][continue] | Гипотеза относится к первому созданию данного семейства, затем может сохраняться через checkpoint |
| Кто использует результат | Transformer/KNN capability | [Train, 98–135][knn], [ExecuteAsync, 176–192][query] | И документы памяти, и запрос проходят этот tokenizer |
| Доступный текст нейронному encoder | Ограничение контекста | [Tokenize, 76–99][embed-tokenize]; `maxLen=min(64, ContextLen)` в KNN factory | Длинный текст даёт только первые 64 token IDs |

Ключевой фрагмент текущего источника:

```csharp
var stableMergeSeed = string.Join(" ", Enumerable.Range(0, 512)
    .Select(index => $"semantic_seed_{index:000}"));
tokenizer.Train($"{seedText} {text} {stableMergeSeed}", 512);
```

**Сейчас:** слияния выбираются по суммарной частоте учебного текста и служебного наполнителя. [RegexSplitter][splitter] отдельно обрабатывает буквенные, цифровые и пунктуационные фрагменты: номер не остаётся непрозрачным идентификатором и участвует в обучении BPE.

**Проверяемая коррекция:** в изолированном новом tokenizer сохранить предметный seed и текст, изменив только искусственный числовой наполнитель. Для первой проверки достаточно сравнить исходные 512 разных номеров с 512 повторениями `semantic_seed_000`: длина наполнителя одинакова, разнообразие цифровых пар меняется. Вариант без наполнителя — дополнительный диагностический контроль. Для продуктового изменения выбирать реальный учебный корпус и согласованный словарь по результатам, а не переносить диагностический повтор `000` в продукт.

## Выполненный вычислительный опыт

Запущен [seed_probe.py](evidence/seed_probe.py); полные входы, token IDs, хэши рецептов слияний и результаты находятся в [seed_probe_results.json](evidence/seed_probe_results.json).

Программа воспроизводит `CountPairs`, выбор первой максимальной пары, `MergeChunk`, порядок слияний и UTF-8 encode/decode из прочитанного BPE. Классы символов построены для конечного ASCII/кириллического алфавита четырёх fixtures; все строки полностью покрываются splitter, обратное декодирование проверено. Это **Python-проверка механизма**. .NET tokenizer, SemanticTeachingPromptCompiler, Transformer, KNN, optimizer и оценка качества обучения в этом опыте не запускались. `seedText` зафиксирован по fallback-литералу проекта; это явно заданный вход низкоуровневой пробы, а не сохранённый результат настоящего compiler или рабочего урока.

Предметные тексты написаны для этой пробы. Они не получены от внешней китайской модели, не оценивались CODEX как DPO и не являются разрешённым train-ready набором. В обеих основных ветвях одинаковы весь предметный текст, `seedText`, 512 позиций наполнителя, его длина в байтах и vocabulary budget. На всех четырёх fixtures все варианты действительно достигли 512 токенов, поэтому различие ниже не объясняется уменьшением фактического размера словаря.

| Тема / профиль | Токенов в запросе: исходные разные номера | Тот же объём, повтор `000` | Без наполнителя | Последнее критическое условие в первых 64 токенах: исходный → повтор `000` |
|---|---:|---:|---:|---|
| Документация: порядок оплаты и откат | 87 | 73 | 72 | `rollback`: нет → да |
| Оркестрация: порядок восстановления | 94 | 81 | 82 | `rollback`: нет → нет |
| Перевод: русское условие и запрет | 83 | 57 | 48 | `нельзя`: нет → да |
| Программирование: числовые ID и коды HTTP | 68 | 58 | 56 | Последний `503`: нет → да |

Проверяется **полное попадание последнего вхождения** заданного фрагмента в префикс. Ранний `503` из перечисления не засчитывается вместо последнего условия. Для оркестрации положительного результата на критическом условии нет: сокращение токенов оказалось недостаточным. Этот отрицательный результат сохранён.

В первых трёх профилях исходный tokenizer выделил 44 merge-токена, состоящих из цифр; контроль с повтором — 2, без наполнителя — 0. В числовом профиле соответствующие количества 68, 32 и 31: предметные числа сами заслуженно занимают часть словаря. Числа относятся к этим fixtures; они не измеряют распределение vocabulary в сохранённом рабочем checkpoint.

## Что эта проба подтверждает

Подтверждено конкретное вычислительное поведение: искусственный наполнитель меняет рецепт BPE и длину **тех же** предметных запросов. На трёх из четырёх fixtures меняется доступность критического окончания в 64-token префиксе. Влияние на конечный ответ и на обучение ещё требуется измерить.

У полного `TransformerEmbeddingKnnLogicalUnit` есть дополнительные пути. [EmbeddingModel, 31–73][embed-fallback] при почти нулевом нейронном векторе может построить частотный вектор из полного текста; [ScoreCandidates, 216–300][fusion] читает полный текст для лексической/структурной оценки. Поэтому одинаковый или обрезанный нейронный префикс **не доказывает** одинаковый итоговый embedding во всех режимах, отсутствие смысла во всём KNN или обязательно ошибочный ответ.

## Малый предметный эксперимент, который проверит качество

**Получатель:** новый `TransformerEmbeddingKnnLogicalUnit<string>` generated capability. Уровень архитектуры — `ILogicalUnit`; индекс и learned policy являются его состоянием. Модель для этого factory имеет 4 слоя, hidden32, context64; конфигурация LoRA для этого пути — rank2/alpha4, Q/V. Это параметры именно [BuildTinyConfig/BuildCapabilityLoraConfig][tiny], а не RP01 или самостоятельной TranslationMachine.

**Первый этап, без обучения весов.** На одинаковых исходных строках вызвать настоящий `BpeTokenizer.Train` в трёх указанных режимах. Сохранить `VocabSize`, токены, exact state SHA, число предметных символов/условий в 64-token префиксе. Подтвердить Python-результат нативно; несовпадение разобрать до обучения. Показать полную запись `seedText`, полученную настоящим compiler, и повторить опыт на ней.

**Второй этап, память и обычный ответ.** Начать с документации и оркестрации: по 8 учебных примеров и по 8 независимых вопросов на тему. Два содержательно противоположных урока должны различаться порядком действий или отрицанием в конце; проверочные вопросы получают новые сущности и другие формулировки. Для перевода и чисел — отдельные профили только после установления настоящего вызывающего пути к данному factory. Обычную `TranslationMachine` нельзя автоматически считать этим получателем.

В каждом плече создать новую согласованную модель и tokenizer, затем заново построить индекс из тех же разрешённых уроков. Сохранить одинаковый набор физических размеров модели, начальный рецепт/seed, число обновлений, порядок уроков, текущую формулу KNN и правила принятия ответа. Для token-only/KNN эксперимента шагов optimizer может быть ноль; он проверяет качество выученной памяти. Если измеряется DPO, обе ветви получают одинаковый малый бюджет и тот же набор исходных пар. Смена token IDs — вмешательство в представление, поэтому подмена tokenizer уже обученным весам недопустима: обе модели обучаются согласованно или используется заранее описанное отображение embedding/LM-head строк с отдельной проверкой.

**Основные измерения:** правильный обычный ответ / 8 для каждой темы; нарушения порядка и отрицания; сохранение старых ответов; false accepts; какая запись памяти выбрана. Дополнительно — token count, фактическое срабатывание fallback, части vector/lexical/pattern score, время, RAM и checkpoint ID. После сохранения выполнить fresh load и те же независимые вопросы. Коррекция перспективна, если помогает предметному качеству при сохранении числового профиля; простой выигрыш в token count недостаточен.

**Отрицательные контроли:** короткие тексты, для которых обе версии укладываются в 64; цифры, отсутствующие в исходном уроке; противоположные окончания; перестановка ID примеров. Противопоказание универсальному изменению — деградация числовой темы или отсутствие влияния на реального consumer.

## Конкретная граница будущего изменения

Изменяемый метод — `DefaultLogicalCapabilityTrainer.BuildTokenizer`; BPE-алгоритм и смысловые слова урока в первом опыте остаются прежними. Новый tokenizer сохраняется обычным `Save`, включается в новую версию generated checkpoint/manifest через существующую публикацию. `BuildKnnTrainingCorpus` и `TransformerEmbeddingKnnLogicalUnit.Train` перестраивают все document vectors для той же версии encoder/tokenizer. Продолжение использует именно этот сохранённый комплект. Исходный checkpoint остаётся отдельным плечом сравнения. Контракты provenance/admission сохраняются.

**Новизна:** известные исследования уже описывают 64-token prefix и BPE identity/order. Новая проверяемая причина здесь — **конкретные 512 artificial numeric seeds расходуют ограниченный merge budget** и наследуются новым семейством. Она не переименовывает общий недостаток контекста или re-fit словаря; сверка с обоими каталогами зафиксирована в [05](05-SOURCES-NOVELTY-AND-REVIEW.md).
