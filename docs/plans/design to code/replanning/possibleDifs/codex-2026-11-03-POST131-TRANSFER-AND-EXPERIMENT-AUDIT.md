## Новые ошибки приёмки и текущего задания

### P127: изменение имени маршрута не доказывает нужные шаги

[`LabelSensitivityHolds`](https://github.com/lubochka/llm_mvp_core/blob/b27783593745ffac8e74e81f917539717cd33615/experiments-v2/RP01-MICRO/P12701/Program.cs#L1107) требует лишь различия `AnswerRoute` у B/C. Отдельный `payloadComplete` требует два известных имени шагов, но не связывает их с маршрутом и назначенными целями. `ComparePermutation` также сравнивает route вместо полного ordered payload.

На копии сохранённого C произвольное имя маршрута с шагами B сохраняет истинность этих старых предикатов. Python-проекция выявляет отсутствие необходимой связи; запуск полного C# finalizer с таким пакетом не заявляется. Честные сохранённые C-ответы проверены и действительно следуют обеим переставленным целям.

Старый `mandatory["label_sensitive_c_holds"]` должен перейти из процедурного all-pass в scientific observation; замена inequality на exact target внутри того же mandatory сохранила бы ложный INVALID. То же требуется для косвенных `c_substituted_by_b_control_passed` и `corrupted_receipt_control_passed`: они не должны требовать научного успеха C или B/e1 для технической годности. Исторический status не переписывается. Ремонт разделяет две проверки. Согласованность известного route, ordered steps и имеющегося native/graph результата относится к целостности доказательства. Точное следование C назначенным целям — научный показатель причинного контроля. Настоящий согласованный, но неверный ответ остаётся допустимым отрицательным наблюдением (`NOT_PROVEN`); положительный эффект B/C не становится безусловным требованием `execution_valid`. Приёмка ремонта проводится на отдельных сохранённых копиях, без нового fit и без добавочных C-графов.

### P131: два производных отчёта согласованы, но их источник не читается

Producer уже сохраняет [`native-flow/{arm}-{id}.json`](https://github.com/lubochka/llm_mvp_core/blob/b27783593745ffac8e74e81f917539717cd33615/experiments-v2/RP01-MICRO/P13101/Program.cs#L318). Однако [`SavedEvidence.Verify`](https://github.com/lubochka/llm_mvp_core/blob/b27783593745ffac8e74e81f917539717cd33615/experiments-v2/RP01-MICRO/P13101/SavedEvidence.cs#L120) строит score из raw-writer/raw-reader, а [`Scoring`](https://github.com/lubochka/llm_mvp_core/blob/b27783593745ffac8e74e81f917539717cd33615/experiments-v2/RP01-MICRO/P13101/Scoring.cs#L39) связывает actual только с сообщаемой длиной. Согласованная подмена actual и длины в B.after/B.restored может нарисовать H/X4/4 вместо 0/4, сохранив затронутые старые предикаты. Независимая сверка с уже существующим native output отвергает все 16 изменённых строк.

Это дефект проверяющего кода, не утверждение об искажении опубликованного опыта: исходные 128 строк сверены без расхождений. Нужна обязательная `NATIVE_OUTPUT_BINDING` по точному набору arm/id и полным фактическим полям, с честным проходом, согласованной порчей и повторным честным проходом на новых output. Требование использует существующие записи; оно не назначает дополнительный Train/Flow. Одновременная подмена raw и native требует отдельно определённого доверенного provenance; hash, вычисленный уже после порчи, сам такой границей не становится. До реального запуска исправленного C# verifier приёмка остаётся `NATIVE_UNRUN`.

**Зависимость ремонта P131, уточнённая независимым review плана:** существующий `Provenance.Verify` связывает checker с историческими producer HEAD/DLL, а DATA_BINDING сравнивает старые10 required gates с текущим списком. Простая пересборка с новым gate отвергнет даже честный пакет.150/49 поэтому разделяют неизменные producer proof/source/DLL/schema и новую verifier identity/schema/gates; используют существующий VerifyOnly и однозначную archive mapping. Недоступные originals оставляют полную provenance NOT_PROVEN, не подменяются новой DLL или отредактированным proof. Это препятствие будущему ремонту проверяющего, не опровержение опубликованных128 ответов.

### Q130: текущий prompt должен знать исполненный результат

На проверенном SHA верхний блок [карточки Q130](https://github.com/lubochka/llm_mvp_core/blob/b27783593745ffac8e74e81f917539717cd33615/docs/plans/replanning-possible-diffs/experimets/cards/METHOD-KNN-SCOPED-EXPRESSION-TARGET-01.md) называл опыт будущим, тогда как индекс уже записал ST01. В действующем блоке и копируемом prompt указаны `RESULT_RECORDED`, точный пакет, результат, уже потраченная доза и HOLD. Нижние датированные паспорта сохранены как история. Новая scope-проверка не превращается в повтор обучения или в назначение отсутствующего persistence API.

## Переносы: какие проверки нужно исправить

**Новый дефект выбора тестов:** фильтр `FullyQualifiedName~ExperimentFixes` из 146 не включает три известных tail-failure и два положительных rule-tag controls: файлы лежат в папке ExperimentFixes, но их namespace — `LlmFromScratch.Tests`. Возвращать production-normalizer к старому underscore ради зелёного результата нельзя. ## Как уроки внесены в карточки

151 связывает каждое уточнение с собственной карточкой и проверяемой границей. Для KNN-ORDER, P16/P45/P97 усилен полный порядок actual, а не короткая метка. Для P25 и обеих METHOD-KNN карточек — связь source/material с реально записанным consumer output. Для P105/P126 отдельно названы проверка состояния, право изменения recipient и вид измеренной метрики. Для WIKI-MARGIN-BALANCED и PHRASE-COVERAGE-CAP сохранены собственные gold, producer и отрицательные научные исходы. P131 получает адресную native-output связь, P129 — сохранение границы между уже существующей атомарностью и экономией preflight.

Дельты внесены также в существующие копируемые prompts, чтобы исполнитель получил полное действующее задание. Там, где отдельного current prompt не было, добавлена короткая передаваемая дельта. Контроль raw↔native требует только реально существующих либо явно назначенных записей; недостающий источник называется ограничением и не достраивается скрытым обучением. Новые классы, панели, бюджеты, universal persistence API и обязательный положительный B/C исход не добавляются.

Этот пакет завершает документный аудит и делает ремонт проверяемым. SOURCE_IMPLEMENTED, сохранённый пересчёт и native PASS остаются разными статусами. Продуктовый ремонт и его свежая исполнимая приёмка продолжаются по живому реестру и 150; исторические POST128 документы не переписаны.
