## Основание внесённых правок

1. **Исторический PRIMARY продолжает выглядеть будущим заданием.** В срезе core `80e89835188987678117380badda81e05a4064a6` индекс уже содержит результаты P104–P115, но паспорта ряда этих карточек сохраняют активные строки `DESIGNED_NOT_RUN`, `SHALL_IMPLEMENT`, «сейчас только Markdown». Общий запрет повтора выше не устраняет противоречие в конкретном паспорте. Статус, описание H/R/entry и копируемый промпт должны различать исполненный исторический рецепт, ремонт измерителя и отдельную продуктовую приёмку.
2. **Позиция guard до обучения не доказывает проверку обучаемого материала.** Новый `e16987c10be` добавил продуктовый `CapabilityMaterialLineageGuard`. В `DefaultLogicalCapabilityTrainer.cs:268` проверяются `Material` и `ActualOwnedRows` провайдера, а наружу возвращается только receipt. В точке `:699` используется лишь успех этой проверки. `BuildTeachingStack` получает отдельно собранный `combinedTrainingText`, DPO — `finalPreferences`, KNN — собственный корпус из replay manifests и registration plans. Это проверенный по исходнику разрыв связи; наличие фактической утечки в выполненном обучении этим чтением не доказано.
3. **Границы исправления должны совпадать во всех входах.** R04 проверяющего P112 остаётся отдельным ремонтом: новый продуктовый guard не исправляет `P11201/src/MaterialLedgerVerifier.cs`. Уже написанный код не назначается повторно; в T112 необходимо принять связь проверенного snapshot с настоящими потребителями и выдачу действительного статуса оценки.
4. **Число учебных вызовов не равно числу опубликованных уроков.** В Q129 один из четырёх вызовов обучения относится к отвергнутому закрытому кандидату. После malformed held-out живое состояние обеих ветвей остаётся S0. Ожидание прежнего частичного обновления не возвращается ради положительной дельты; затраты staging учитываются отдельно.

## Как не повторить ошибку в тестах и заданиях

| Плохое подтверждение | Достаточное подтверждение именно этого свойства |
|---|---|
| Название `OnlyTrainRows_AreHandedToTheLearner` считается доказательством вызова learner | В существующем `Tests/ExperimentFixes/CapabilityMaterialLineageTests.cs:212` проверен только результат `SelectTrainingRows`. Эту полезную чистую проверку сохранить. Для продуктовой приёмки отдельно наблюдать материал на настоящем входе обучателя и его связь с допущенным snapshot |
| Чистый список провайдера проверен, но DPO получает отдельно собранные preference pairs | Проверенный собственный материал связан с фактически поданными `finalPreferences`; подмена настоящего материала при неизменном чистом ledger обнаруживается до разрешения мутации |
| В будущем тесте на отказ достаточно поймать любое исключение | Проверить назначенный код/фазу отказа, неизменность ранее принятого состояния и законный положительный случай. Ошибка оснастки или более раннего admission не доказывает работу нужного guard |
| «Контракт 120/40» в скопированном промпте считается полным контекстом | Внутри самого промпта есть путь его карточки, точные пути общих договоров и разделов навыков, назначенный этап, реальные входы/выходы, бюджет и границы авторизации |
| Сверху написано «не повторять», ниже активный паспорт говорит «реализуй PRIMARY» | Исторический паспорт помечен у самого заголовка и команды, а оперативное задание описывает только текущий ремонт; общий A/B-промпт не добавляет скрытых модельных вызовов к saved-only проверке |

При падении теста сохраняются исходные input/expected/actual и причина до изменения оснастки. Нужно определить, сломан ли продукт, устарело ли ожидание, не достигнут ли проверяемый путь либо отсутствует необходимый артефакт. Исправить ветвь ожидания по действующему договору допустимо; превращать отказ в успех ослаблением gold, допуска или проверки состояния — нет. Исторические результаты не переписываются из-за более строгой будущей приёмки.

Параллельный `5bb764277d9` уже добавил `ValueKind` перед чтением свойства в collision preflight Translation. По исходнику `null` сохраняет пропуск, другой non-object возвращает типовой отказ. Существуют три новые проверки `TranslationBatchChosenOutputValueKindTests`, но их собственный комментарий отмечает отсутствие прогона. Object-case проверяет отказ при коллизии; его нельзя описывать как успешное усвоение законного урока. Новый код не требуется создавать повторно; нативная приёмка и связь с ранее выученным состоянием остаются отдельными утверждениями.
