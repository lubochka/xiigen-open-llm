## Что проверено полностью, а что не сертифицируется

Загружены и проверены по Git blob SHA **164 текстовых источника**: 125 P-карточек, 24 документа действующего пакета малых опытов, 7 общих документов `experimets` и 8 корневых документов методики/каталога/required changes. Дополнительно загружены 6 отчётов и независимых проверок ранее выполненных переводческих опытов; ключевые выводы отчётов сверены по приведённым ниже разделам. Независимые review-файлы сохранены как доступные первичные свидетельства; новая независимая экспертиза их полного содержания здесь не заявляется. Контроль сохранённых источников находится в `verified_sources.json`; 164 из 164 основных снимков побайтно совпадают с Git blob SHA. Результаты такой проверки — доказательство целостности чтения, а не качества обучения.

Для каждой P-карточки сверены получатель изменения, отдельные вмешательства, предметные профили, историческая/активная роль и ссылка в малую карту. Получилось **470 самостоятельных подслучаев**, включая два подслучая P86, оформленные абзацами, а не заголовками. Машинный реестр `card-audit-125.json` содержит source hashes, строки основания, заявленный call path, предметные темы/профили, активного преемника, конкретный пробел и следующее действие. Таблица `02-card-audit-125.md` даёт те же 125 решений в читаемой форме.

Это **не новая полная проверка исходного кода каждого владельца**. Call paths в данном реестре прочитаны в карточках и помечены именно как заявленные источником; ключевые новые выводы должны подкрепляться отдельным чтением текущего code owner. Ссылки из старых карточек на `C:/...` показывают прежнее локальное окружение, а не доступный runtime настоящего аудита. В публикационном дополнении используются immutable GitHub-ссылки.

Полнота 125-card map не равна полноте свежего `possibleDifs`: [README действующих опытов](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/2026-10-19-small-learning-probes/README.md) прямо оставляет `OPEN_DETAIL_REVIEW`. Каждый новый вывод сегодняшнего аудита требует явной строки crosswalk; отсутствие точного имени файла в индексе не автоматически означает отсутствие содержательного покрытия.

## Правило успеха уже внедрено

Во всех **125 карточках** присутствует правило: любое реально измеренное полезное улучшение считается успехом по своему показателю и предметному домену; рост точности не обязателен; остальные изменения и ухудшения показываются рядом. То же правило присутствует во всех **133 проверенных промптах**: 124 общих конечных промпта и 9 предметных промптов P86. В 125 карточках также явно названы четыре состояния A0/A1/B0/B1.

Следовательно, повторное массовое добавление одинакового абзаца не решает главного пробела. Нужны конкретные доступные вмешательства и корректные измерения, а не ещё один слой одинаковых инструкций. Более ранние большие бюджеты P-каталога являются историческим справочником; действующий пакет уже сокращает старт обычно до двух уроков и четырёх задач. Эти старые бюджеты нельзя предъявлять как активную очередь обязательных запусков.

Источник: [experimets/00-README.md](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/00-README.md), [методика малых опытов](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/2026-10-19-small-learning-probes/01-method-and-report.md).

## Сохранённое улучшение действительно существует и уже перенесено в загрузчик

`required-changes.md` фиксирует пользовательское указание использовать успешный механизм памяти в проверенном виде. Отдельный отчёт подтверждает уже выполненное исправление: `ReadTranslationCorpusRowsAsync` раньше не читал `phrase_mappings`, а `BuildTranslationContinueExample` не передавал их в `ExecutorOutput`. После исправления одинаковые восемь уроков создали 16 сохранённых соответствий частей вместо нуля. Последующий обычный перевод улучшился **с 11/24 до 19/24**; восемь новых сочетаний знакомых частей стали правильными. Потерь ранее правильных ответов не было, но число принятых ответов, проваливших строгую проверку, выросло **с 1 до 3**.

Точная измеренная цепочка: `27.TranslationDomain.Tools/Program.cs` private reader/builder через reflection → `TranslationMachine.TrainStructuredBatchAsync` → `GetOrchestratorAsync().RunAsync`. Полный CLI с registry/manifest в этом опыте не запускался. Это существенная граница: эффект реального преобразователя/обучения/обычного Flow подтверждён, полное CLI-интеграционное покрытие не следует автоматически. Отчёт: [translation-memory-ingress-01, строки 3–18 и 53–59](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/translation-memory-ingress-01/report.md#L3-L59).

Предшествующий P125 измерял другой вопрос: после настоящего memory batch новый Executor улучшился **с 0/24 до 19/24**, включая запоминание, близкие формулировки и новые композиции знакомых частей. Это один совместный фактор памяти, состоящей из maps/KNN/version/readiness; вклад каждого компонента в том опыте отдельно не изолирован. Успех этой Unit не доказывает восстановление нейронного Student. Источник: [P125 report, строки 3–29 и 89](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/P125-enru-memory-01/report.md#L3-L89).

P25 затем выполнил один cold load без новых уроков: все 24 ответа/маршрута/оценки совпали, точность сохранилась 19/24. Это положительный результат **сохранения приобретённой способности**, а не новое обучение. Нужно сохранить уже внесённый перенос `phrase_mappings`; не оформлять его вновь как ещё не проверенную гипотезу. Следующие изменения должны адресовать конкретный оставшийся пробел, например сохранение отрицания/вопроса в consumer, и показывать одновременно приобретённые ответы и ложные принятия.

## Уточнение границы: загрузчики и потребители результата разрешены пользователем

В старых документах standalone cold/serving/report иногда целиком исключены из активной очереди. Текущее уточнение пользователя разрешает такую проверку, если результат обучения зависит от проверяемого компонента и указаны **конкретный код участия и необходимое исправление**. Поэтому автоматически вычёркивать P25 только из-за `updates=0` неверно.

Корректная классификация:

- Изменение весов, обучаемой памяти, выбора уроков, представления данных для настоящего learner — прямое обучение.
- Загрузчик, запись/восстановление состояния, обычный consumer приобретённого знания, измеритель, влияющий на следующий учебный шаг — допустимая зависимость при доказанном пути к этому обучению или его результату.
- Изолированная формула, фиктивный счётчик, unrelated selector, toy graph, статический registry без найденного learner — не учебный эксперимент.

Не нужно добавлять бессмысленные уроки, чтобы легализовать полезную проверку сохранения уже обученного состояния. Нужно показать `writer → stored state → reader → affected answer/next lesson`, назвать исходный метод и одно исправление. До появления такой связи неподтверждённый вариант остаётся последним по приоритету.

## Приоритетные незакрытые технические вопросы

| Приоритет | Что разблокировать | Основание и конкретное действие |
|---|---|---|
| 1 | Настоящий маленький нейронный A/B | Действующая D-карточка не выбрала factor и не имеет двухстрочного runner. Сначала завершить один actual caller с сохранением существующего exact trainer/admission; не писать второй trainer и не подменять это новым словарём. |
| 1 | Измерение состояния после обновления | В документах экспериментов не найдена явная оговорка, что returned `StepVector` metrics относятся к forward **до** `ApplyOptimizer`. Это уже известное наблюдение prior54, а здесь — **пробел экспериментального покрытия**, не новая гипотеза. После последнего update нужен сопоставимый post-update probe; `EvaluateMany` нельзя автоматически считать эквивалентом weighted exact `StepVector`. |
| 1 | Новое полезное изменение цены обучения | Предложенный в сегодняшнем кодовом аудите cache frozen-reference scores внутри настоящих repeated DPO steps не покрыт P09: P09 сравнивает cached generation, не reference forward во время обучения. Нужна отдельная малая карточка с реальными updates, ключом reference/tokenizer/masks/inputs и учётом построения/памяти cache. |
| 1 | Действительные effective stop settings | P78 описывает window1 против5 при max5; он не проверяет default window25 при hard cap5. Нужна привязка к actual caller, чтобы не переносить свойство конфигурации на fixed-step RP01. |
| 1 | Прямое обучение Unit/kNN наравне с нейронным | Запись и чтение урока в SemanticTokenizer/Executor/Verifier/StructuralKnn — та же первая очередь, если выявлен конкретный блокер. Для них не нужно ждать нейронного micro-host; результаты разных получателей остаются раздельными. |
| 2 | Сохранить проверенный перенос памяти | `phrase_mappings` loader fix уже внедрён и измерен. Его состояние не считать missing; проверять только непокрытую интеграцию или конкретный новый semantic failure. |
| 3 | Связанные результаты обучения | До отдельного decoder/restore/scorer/RAG опыта указать точный learner consumer и код влияния; user-approved dependency не исключать из-за нулевых optimizer updates. |
