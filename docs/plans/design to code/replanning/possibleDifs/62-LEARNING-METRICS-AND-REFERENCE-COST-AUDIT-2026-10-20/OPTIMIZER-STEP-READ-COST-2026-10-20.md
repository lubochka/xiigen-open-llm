# E-OPT-STEP: не копировать память AdamW ради номера шага

**Дата:** 20 октября 2026. **Source pin:** core `a8222d1b15745fe6207f36cd294fd3fb61c01d3b`. **Статус:** `SOURCE_CONFIRMED / NOT_RUN / PREPARABLE / EFFECT_NOT_MEASURED`; маленький опыт подготавливается в экспериментальной копии, обучение здесь не запускалось. Основной код и protected-карточки не менялись; этот пакет содержит только документы и доказательства.

## 1. Узкая гипотеза и действительное участие в обучении

Перед настоящим DPO update `ExecuteWithPublication` получает номер шага для снимка RNG через `ExportOptimizerState().Step`. При non-null RNG callback это создаёт переносимое состояние, копируя оба массива моментов AdamW, хотя в данной точке потребляется только `Step`. Затем `DpoTrainerStepSnapshot.Capture` ещё раз копирует моменты для необходимого rollback. Удаление **первой ненужной материализации**, при сохранённых проверках, может уменьшить allocations, CPU или время полного учебного шага. Выигрыш не измерен и не гарантирован; rollback и послеучебный portable export сохраняются.

Это не два вызова одного `CaptureState`: первый путь — `ExportPortableState` и immutable portable DTO, второй — process-local `CaptureState`. Типы нельзя взаимозаменять или без проверки передавать один вместо другого. [Step transaction, 1228–1245][transaction]; [portable export, 507–525][export]; [rollback capture, 46–69][snapshot].

| Доказательство | Что установлено |
|---|---|
| [`AdamW.ExportPortableState`, 188–230][adam-portable] | Обходит bindings, проверяет имена/формы и строит переносимые записи из текущих m/v |
| [`AdamWPortableParameterState`, 22–41][portable-copy] | Конструктор действительно копирует `firstMoment` и `secondMoment` через `ToArray`, а не хранит только ссылки |
| [`AdamW.CaptureState`, 113–125][adam-capture] | Снова копирует оба массива в owner-bound rollback snapshot |
| [`CodeDocumentationSimulationDpoExperiment`, 160–161][simulation-caller] | Реальный exact ProjectLoRA caller безусловно передаёт non-null capture/restore RNG callbacks |
| [Тот же caller, 110–111][simulation-zero] | При этом требует сохранённый dropout0: менять dropout для появления проблемы не требуется |
| [Тот же caller, 175–186][simulation-loop] | На одном trainer последовательно выполняет настоящие `StepVector` с разными minibatches и реальным optimizer |

Следовательно, этот расход не требует повторного предъявления одной пары, reference-cache hits или включения dropout. Он возникает и при **двух разных уроках по одному разу**. В cold первом шаге m/v ещё пусты: экономии копирования массивов моментов там нет. После первого обновления появляются моменты; второй шаг уже содержит описанную лишнюю копию. При существующем continuation с непустыми m/v условие выполняется с первого нового шага. Это source-достижимость, не новый замер исторического RP01.

Граница callers существенна: ordinary `LogicalDpoTrainingUnit` назначает RNG callback только при seed authority, ненулевом dropout и непустых targets. Если callback null, C# null-conditional вызов не вычисляет `ExportOptimizerState().Step`, и данного лишнего export в этой точке нет. Это отрицательное условие применимости, а не дополнительный обязательный эксперимент. [Logical condition, 907–909][logical-condition]; [callback creation, 1964–1986][logical-callback].

## 2. Что именно менять в экспериментальной копии

**Один фактор:** убрать материализацию portable m/v исключительно для чтения номера шага внутри `ExecuteWithPublication`. Предпочтительный интерфейс — **validated metadata-backed step read**: он сохраняет исходные проверки и возвращает счётчик без копий моментов. Readonly `CurrentStep` может быть внутренней частью этого пути, но не заменой проверки; сейчас у `AdamW` публичного accessor счётчика нет. `AdamWStateSnapshot.Step` internal и принадлежит другому API; не открывать массивы моментов. [Текущее поле и свойства AdamW, 17–37][adam-step]; [snapshot API, 15–30][snapshot-api].

**Однострочная замена на getter недостаточна.** `DpoTrainer.ExportOptimizerState` вызывает `_projectRecipient.RequireAllowedState`, который по умолчанию делает ещё `RequireValid` и проверки ключей/форм. Export и portable DTO также проверяют уникальность bindings, shapes, step, bounds и ключи. Просто удалить этот путь означает одновременно убрать проверки и исказить измеряемый фактор. [Recipient validation, 264–272][recipient-validation]; [portable constructor, 95–121][portable-validation].

Минимальный корректный ремонт в копиях `04.TrainingLoop/Optimizers/AdamW.cs`, `AdamWPortableState.cs` и `11.DPO/DpoTrainer.cs`:

1. Дать чтение текущего `_step` без materialization.
2. Использовать общие pure validation predicates так, чтобы новый step-read сохранял те же проверки bindings, текущих m/v lengths, shapes, portable bounds, step и recipient **до RNG callback**, но не создавал копии m/v. Исходный A portable-export path сохраняет прежние обходы, allocations, порядок отказов и формат; общий refactor не должен добавлять ему metadata snapshots или дополнительные проходы и искусственно утяжелять baseline. Не поддерживать две расходящиеся копии правил.
3. В `ExecuteWithPublication` использовать validated step read только при прежнем non-null RNG callback. Сохранить прежнюю очередность: mutation gate и recipient check → reserve publication → pre-capture validation → RNG capture → прежний parameter/optimizer rollback capture → recipient check → обычный update/publication. Количество и назначение reference/recipient checks не сокращать ради красивого выигрыша.

Точная граница validation: сохранить `HasValidShape` с положительным moment length и пределом 1e9, проверку `TotalElements`, current format/неотрицательный step, предел 1e6 **активных** entries и UTF-8 key length ≤1024 только у entries с накопленными моментами. Empty/duplicate binding-key checks остаются до пропуска параметров без state; step фиксируется после полного binding loop. Затем выполняются прежние header/key checks, полный `RequireValid` и key/dimensions/moment-count checks до RNG capture. Типы/коды отказов и порядок проверок сохраняются. Малые snapshots shapes допустимы: фактор убирает копии m/v, а не всякое выделение памяти. Не добавлять finite/negative-moment scan или новый 1GiB frame-size gate: первый отсутствует в данном export, второй применяется только в `ToBytes`, который эта step-read точка не вызывает. Эквивалентность заявляется для обычного сериализованного owned-trainer выполнения; одинаковое поведение при OOM не обещается, поскольку удаление allocations меняет сам этот риск.

`DpoTrainerStepSnapshot.Capture/Restore`, момент снимка параметров, ownership, rollback, publication и `BuildPublicationBundle` остаются прежними. Treatment ограничен ProjectLoRA recipient; non-project fallback продолжает прежний вызов `ExportOptimizerState().Step` и не входит в данный фактор. Конкретная реализация validation helper — работа подготовки; здесь не утверждается, что такой API уже существует. Если реализация сохраняет экономию только ценой снятия guard, это иной фактор и не чистый E-OPT-STEP.

В simulation caller есть ещё `ExportOptimizerState().Step` для budget/issued/completed bookkeeping, в частности строки 180, 182, 189. Это та же семья лишних materializations, но **они не входят в выбранное изменение**: остаются одинаковыми в A/B, а их стоимость входит в полный workload. Не объединять этот опыт с reference-cache, новым rollback форматом или массовой заменой exports. [Внешний caller, 175–190][simulation-loop]; [необходимый post-update bundle, 1273–1286][bundle].

## 3. Маленькая карточка настоящего обучения

**Предметная тема:** C# документация. **Learner:** исходный exact ProjectLoRA Student с сохранёнными q/v adapters, настоящий `StepVector` и AdamW. **Начальное состояние:** один принятый B0/profile, одинаковые policy/reference/tokenizer, LoRA configuration, optimizer settings/state и RNG в обеих сторонах. Использовать уже существующий профиль, включая его dropout0; не менять rank, seed или модель ради увеличения расхода. Domain перенос на EN→RU continuation возможен позже, но не является обязательной второй веткой первого опыта.

**Данные:** два разных уже принятых C# DPO-примера из одного доступного разрешённого корпуса, один пример на шаг, один и тот же порядок в A/B. Исполнитель фиксирует actual source IDs, полные bytes/hashes, exact masks и действительный admission path при подготовке копии. Не выдумывать происхождение, grant или внешнего teacher. Не менять chosen/rejected, веса пар и векторы между arms. Для данного cost-фактора не нужно выбирать трудный семантический контраст или создавать новые DPO с нуля.

**Бюджет:** максимум **A2+B2 actual optimizer calls**, четыре суммарно; основной вариант — два успешно завершённых updates в каждой стороне. **Generate=0, teacher calls=0, отдельные evaluation forwards=0.** Не выполнять полную Main500, production scientific one-step или дополнительные пары/домены. Non-null RNG capture сохраняется как у исходного simulation caller. При cold start первый update естественно заполняет моменты; второй проверяет полезность изменения без отдельной разогревающей учебной серии.

**Где выполнять после поручения на запуск:** точные копии нужного механизма в `35.ExperimentsV2/Experiments/Rp01Micro/E-OPT-STEP/`; малый host — `experiments-v2/RP01-MICRO/E-OPT-STEP/Runner.csproj` и `Program.cs`. Host компилирует выбранные копии и необходимые одинаковые зависимости; не добавлять ProjectReference на весь `35.ExperimentsV2`. Собирать точный host и запускать его DLL, без PowerShell reflection/общего dispatcher. До исполнения записать исходный pin, выбранные файлы, hashes копий, один A/B diff, actual native command и границу ресурсов. Не перезаписывать прежние experiments/bin/obj/results, не вводить дополнительные warmups или повторные серии. Основной код и продуктовые тесты не редактировать; перенос результата — отдельное решение пользователя. Нет требования новой личной подписи каждого ID/SHA. Это проект опыта: текущее поручение на аудит не заменяется его запуском. Порядок размещения уточнён документационной редакцией core `bcf880f232d090e3cfcb459c108d3945ce6dbc15`; source-код механизма зафиксирован отдельно на a822.

Оригинальный simulation owner не имеет готового двухурочного paired режима и использует content-bound issued journal. Подготовить конечный экспериментальный caller с двумя заранее объявленными arms в одной study identity и обычными content/mutation owners; не обходить once-only запись новым RunId, новой папкой или удалением истории. Здесь не заявлен готовый запущенный host. Недостающий доступный binding — подготовка; действительно недоступный обязательный вход требуется назвать по результату конкретной попытки его получить. Это общий организационный вопрос уже описанного малого paired host, не новая гипотеза данной карточки.

### A/B и измерения

1. A и B начинают с одинаковых полных states. Один исполняемый код имеет только объявленный treatment switch; validation helpers, logging, model/data dependencies и остальные exports общие.
2. A выполняет прежний portable export ради RNG step; B выполняет guard-equivalent readonly step read. Оба выполняют два реальных update на двух разных парах и обычную публикацию. Никакого reference-score cache.
3. Для каждого успешного шага сравнить actual pre-update step/RNG state, возвращаемые trainer metrics с меткой `pre_update_training_forward`, post-update LoRA/base/reference, m/v, global step и RNG. При детерминированном одинаковом profile ожидается побитовое равенство конечных состояний. Численные допуски, если объективно нужны, объявить заранее. Не считать returned loss измерением финального checkpoint.
4. Измерить полный двухшаговый workload: wall time, CPU time, реальные allocated bytes и peak own-process RAM; setup, validation, snapshot, train, publication и оставшиеся внешние exports показать раздельно без двойного суммирования вложенных фаз. Отдельно instrument cost самого step-read. Счётчики вызовов служат проверкой вмешательства; уменьшение их числа само по себе не заменяет измерение полезного ресурса.
5. Записать A0/B0 и A1/B1 state identities, actual issued/applied/committed counts, время/память и deltas B−A. Accuracy, free-response quality и доменное обобщение обозначить `NOT_MEASURED`, не нулями и не обещанием их улучшения. Цена подготовки и полная стоимость попыток тоже видимы.

Для уже накопленных моментов суммарной длины M устранённая portable материализация содержит 2M float values, то есть примерно 8M payload bytes без headers/metadata. **Это расчёт объёма из кода, не измеренный выигрыш памяти или времени.** GC, validation и полный parameter snapshot могут доминировать; peak RSS может не уменьшиться. Короткий единичный прогон даёт локальное наблюдение с пределом таймера, не обещание общей производительности. Обязательных повторных серий нет.

### Достоверность rollback без нового бессмысленного опыта

Сначала review подтверждает неизменный порядок capture/guards и неизменный rollback API. Fault injection требуется только при конкретном оставшемся риске реализации; это внутренний контроль сохранности, не самостоятельный успех обучения. Он не увеличивает бюджет незаметно: при его необходимости второй из двух зарезервированных optimizer calls каждой стороны используется как failed-and-rolled-back attempt **после настоящего `ApplyOptimizer`, до commit публикации**, через существующий observer в одной и той же точке. Тогда отдельно показываются один committed и один rolled-back update на arm, а стоимость двух **успешных** updates помечается `NOT_MEASURED`. После rollback сопоставляются weights/moments/step/RNG и принадлежащие попытке файлы. Не добавлять третий update, автоматический retry, Generate или полномасштабный CI ради этого контроля.

**Правило успеха:** любое измеренное улучшение полезного показателя считается успехом по этому показателю и домену; рост точности не обязателен. Остальные изменения, включая ухудшения, показываются рядом. При нарушении guard/state parity наблюдения сохраняются, но результат не объявляется эквивалентной cost-оптимизацией. Если полезного ресурса не улучшилось, гипотеза не подтверждена данным малым workload.

## 5. Новизна и границы

Адресный поиск выполнен по 555 Markdown baseline planning, 170 protected источникам, четырём concurrent61 документам, трём документам другого current-learning-audit и 12 документам текущего нашего пакета. По `ExportOptimizerState`, `ExportOptimizerState().Step`, `DpoTrainerStepSnapshot`, `AdamWPortableParameterState` и сочетанию duplicate/повторный optimizer snapshot совпадений нет. Два старых упоминания `CaptureState` относятся к finite/rollback в SFT и наблюдению LoRA factors; они не описывают переносимое копирование m/v только ради номера шага. Concurrent reference-cache статья сохраняет snapshot/optimizer cost как общий остаточный расход, но этот factor не выделяет.

**Статус новизны:** новый узкий кандидат относительно перечисленного просмотренного корпуса; не утверждение глобальной новизны идеи read-only property. Общие темы optimizer state, rollback, ресурсы обучения и reference caching уже известны. Никакой причины падения accuracy RP01 или измеренного ускорения из этой находки не следует.
