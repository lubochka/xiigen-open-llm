## Что установлено

1. Действующий путь DPO существует и включает настоящий обновляемый получатель: exact DPO material → LoRA → `DpoTrainer.StepVector` → AdamW → checkpoint/optimizer/RNG. Общая формулировка «в коде нет обучения» неверна.
2. В повторном DPO обучении один и тот же неизменный reference заново вычисляет выбранную и отклонённую стороны каждой пары на каждом шаге. Этот кандидат независимо найден относительно исходного корпуса и совпал с параллельно опубликованным [LC-REF-CACHE](https://github.com/lubochka/xiigen-planning/blob/fb9aadf69e0669d36b820d61f76fe3ecc8697a7d/llm%20mvp/design%20to%20code%20session/replanning/possibleDifs/2026-10-20-current-learning-audit/dpo/01-reference-score-reuse.md). Это одна семья, а не две новые гипотезы или два обязательных опыта. Он **не обещает роста точности** и не объясняет плохие ответы однопроходного RP01 автоматически.
3. `LogicalDpoTrainingUnit` ограничен пятью шагами, но default поля request для convergence window равен 25. `StableDpoTrainingExecutor` это поле не переопределяет; при разрешённом запросе 2–5 шагов с таким окном критерий остановки не вызывается. Обычный `DefaultLogicalCapabilityTrainer` явно задаёт window1. Обычный stable default — один шаг, где ранняя остановка не даёт экономии. Это уточнение caller/условия известной темы P78, не общая неисправность всех callers.
4. Найденный ранее запрет первого SFT шага при positive warmup существует в низком уровне, но штатная checkpoint-backed factory уже задаёт `WarmupSteps=0`. Он не является установленным активным блокером этого caller.

**Правило всех карточек и промптов ниже:** любое измеренное улучшение полезного показателя считается успехом по этому показателю и домену; рост точности для этого не обязателен. Рядом показываются изменения остальных показателей, включая ухудшения. Успех показателя не означает общую пригодность модели.

**Приоритет:** сначала реально подтверждённые препятствия обучению и уже принятые изменения обучаемой памяти/восстановления. Reference cache — последующий ограниченный вопрос стоимости повторного DPO, а не замена этой работе и не обязательный gate перед ней. Уточнения window/metric phase также не должны останавливать готовые приоритетные задачи.

## 2. Семья LC-REF-CACHE: повторный frozen-reference forward расходует время обучения

### Доказательства и причинность

В `DpoTrainer.StepVectorCore`, строки 877–883, reference заново делает два forward для каждого `vectorBatch`. Результаты используются в `chosenReward`, `rejectedReward`, `margin`, `objective.Derivative`, затем в двух backward и optimizer update. Таким образом, это вычисление является частью функции обучения, а не serving-only benchmark. [Источник](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/11.DPO/DpoTrainer.cs#L877-L920).

`LogicalDpoTrainingUnit` сохраняет один список `executionBatches` и повторно предъявляет его в цикле от 1 до MaxStepCount. На каждом шаге reference получает те же ids/masks. [Источник](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L1343-L1389).

`DpoProjectLoraRecipient` фиксирует reference hash при создании и проверяет frozen flags, неизменные reference bytes, независимость storage и соответствие frozen base. `BatchLogProbs` выполняется с `training:false`. Exact material имеет digest с текстами, tokenizer state, ids, масками, framing и objective versions. Поэтому строго привязанный к данному recipient и material cache может возвращать ранее вычисленные reference scores без изменения самой loss. [Reference identity](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/11.DPO/DpoTrainer.cs#L198-L261), [детерминированный reference forward](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/11.DPO/DpoTrainer.cs#L1007-L1012), [exact digest](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/11.DPO/Models/DpoExactPairMaterial.cs#L184-L205).

**Гипотеза:** cache frozen-reference log-probabilities внутри повторного exact DPO обучения уменьшит wall time и allocations при сохранении той же траектории обучения. Цена cache и проверок может оказаться больше экономии на очень маленькой модели; это допустимый отрицательный результат.

Для N уникальных пар и S повторных шагов текущий loop выполняет `2*N*S` reference forward. После lazy cache — `2*N`, если ни material, ни recipient не меняются. При двух шагах это на 50% меньше reference calls, при пяти — на 80%. **Это расчёт числа вызовов; это не измеренное ускорение всего обучения.** Policy forward/backward, optimizer, hashing, snapshots, checkpoint и оценка сохраняют свою стоимость.

### Домен и предел применимости

- Первый профиль: C# documentation, точная экспериментальная копия существующего exact-v2 learner и нужных зависимостей, две разрешённые независимые учебные пары, повторные 2 updates в малом runner. Source chain `StableDpoTrainingExecutor`/`LogicalDpoTrainingUnit` показывает участие механизма в продукте; исследовательский A/B не требует двух product server attempts. Готовая команда копии здесь не заявлена; raw scientific CLI остаётся одношаговым.
- EN→RU: отдельный опыт только через реально используемый exact research caller с тем же повторным workload; запрет exact-v2 для других доменов в generic stable wrapper нельзя обходить изменением domain label.
- Произвольные кэши kNN, AST или переводческих словарей сюда не относятся.
- Один проход по 500 уникальным RP01 pairs не даёт cache hits между шагами; one-step scientific raw урок тоже не повторяет пары внутри trainer. Здесь ожидается преимущественно overhead; это отрицательный контроль, не повод запускать ещё 500 пар или менять научный протокол.

### Изменение экспериментальной копии и будущий адрес переноса

В B-копии `11.DPO/DpoTrainer.cs` внутри выбранного `34.Experiments`/`35.ExperimentsV2` добавить bounded, instance-local cache **только** для ProjectLoRA recipient + validated exact material. A-копия сохраняет исходное вычисление. Ключ должен содержать неизменную identity reference, ExactMaterial.DigestSha256 и сторону chosen/rejected (либо хранить обе стороны в одном значении). Cache живёт внутри данного trainer; никакой общей mutable или disk-cache между разными моделями/уроками. До чтения cache сохраняется текущая `RequireValid()`/mutation admission. Любая неуспешная проверка reference ведёт к прежнему отказу, а не cache hit. Legacy материал остаётся на старом вычислении. Нельзя кэшировать policy scores: именно policy меняется после update. Original `11.DPO/DpoTrainer.cs` здесь не редактируется; возможный перенос именно в этот owner рассматривается после измерений отдельным решением пользователя.

Изменение точки выполнения: заменить прямые `BatchLogProbs(_reference, batch, chosen:...)` в выбранном exact StepVector на helper с cache. Статистику hits/misses учитывать рядом с `DpoStepVectorTiming.ReferenceForward`, не выдавая cache lookup за выполненный forward. Если cache применяется только в повторном unit-loop, его активацию связывать с уже известным MaxStepCount, без нового пользовательского workflow. Отдельно определить верхнюю границу памяти и поведение при переполнении: eviction или uncached computation, ни в коем случае не пропуск пары.

[Текущий raw профиль и одношаговый предел](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/tools/Rp01RawDpoLesson/README.md#L49-L71).

**Бюджет основного ресурсного опыта:** четыре завершённых updates суммарно — два A и два B; **0 генераций**. Это actual-update cost experiment, допустимый по [текущей политике](https://github.com/lubochka/llm_mvp_core/blob/a8222d1b15745fe6207f36cd294fd3fb61c01d3b/docs/plans/replanning-possible-diffs/experimets/00-execution-policy-2026-10-20.md#L30-L36). Качество свободного ответа в таком запуске — `NOT_MEASURED`, не ноль и не доказанный рост. Если выбран также предметный quality вопрос, его отдельный ограниченный профиль добавляет одну frozen-панель из четырёх вопросов до/после каждого arm — максимум 16 генераций. Ни эта панель, ни cold/no-hit, ни новый post-objective evaluator не являются обязательным допуском к измерению затрат настоящего обучения.

**Учебный порядок:**

1. В малом experimental-copy runner создать независимые A и B из одного initial snapshot, сохранив общий baseline-код/зависимости и единственный cache diff. Зафиксировать A0/B0: weights, optimizer/RNG, exact train pair hashes/sequence lengths, mask count, allowed parameter map, reference hash и settings. Предметную панель до обучения выполнять только если заранее выбран дополнительный quality профиль.
2. A выполняет два реальных StepVector с обычным reference computation. B выполняет те же два StepVector с cache. **Каждый из двух StepVector получает один и тот же список из обеих пар: итого 4 предъявления пары на arm.** Последовательность batch1 T1→T2 без повторного предъявления не проверяет эту cache-гипотезу. Сохранить каждый pre-update gradient norm, завершённые optimizer steps, post-step weights/optimizer state и фактические обновления LoRA. Cost boundary в обоих arms включает admission, hashing, cache allocation, snapshots и публикацию; phase forward timing показывать дополнительно. Warm/cold JIT и setup должны быть сопоставимы, чтобы запуск A первым не стал скрытым вторым фактором.
3. После каждого update сравнить веса/AdamW. В детерминированном profile ожидается побитовое равенство; при объявленной численной допустимости публиковать предел и максимум отклонения. Одинаковые returned trainer metrics можно сравнивать между A/B для проверки эквивалентности с явной фазой `pre_update_training_forward`; выдавать их за оценку состояния после update нельзя. Новый weighted evaluator не является prerequisite этого cost-опыта. Если отдельно заявляется изменение DPO objective до/после, его измеряют одной функцией на обоих состояниях по [measurement repair](TRAINING-METRIC-PHASE-REPAIR-2026-10-20.md).
4. После двух updates зафиксировать A1/B1 и сравнить состояние/стоимость. В выбранном дополнительном quality профиле выполнить ту же четырёхслучайную панель, что до обучения, и сравнить correctness, частичные ответы, ошибки закона, abstention, coverage, длину и latency. В основном resource профиле эти показатели честно остаются `NOT_MEASURED`. Изменение accuracy не требуется для признания измеренного выигрыша времени. Время дополнительных probes отдельно от train timing, полные затраты также показать.

**Последующие контроли — только для конкретного оставшегося вопроса:** cold readback двух финальных состояний допускает ноль новых updates и до восьми ответов общей панели. No-hit learning control, если требуется измерить cache overhead без повторных пар, получает отдельный бюджет четыре updates суммарно — два A и два B на одинаковых неповторяющихся mini-batches из новых независимых initial states; настройка cache остаётся единственным фактором. Оба контроля содержательно допустимы, но основной cost-результат не должен ждать их выполнения. Не расширять автоматически число пар, доменов или повторов.

**Отчёт:** A0/A1/B0/B1 — исходные и послеучебные states; model outputs только при выбранном quality профиле; A/B — завершённые updates, reference calls/hits, полное elapsed и phase timings, peak own-process memory, snapshot bytes, state parity, каждый полезный показатель и его delta. Для каждого quality/state показателя показывать A1−A0, B1−B0, (B1−B0)−(A1−A0); для стоимости непосредственно сравнивать полные одинаковые workload A/B. Для очень коротких run показать предел измерения таймера/неопределённость; дополнительный повтор полного workload нужен лишь для конкретной неясности и имеет отдельный заранее ограниченный бюджет. Не менять fixture после просмотра результата. На двух парах и двух шагах ожидаемые reference calls: A8, B4; это исходная проверяемая гипотеза вызовов, не результат.

Peak RAM измерять за независимый интервал каждого arm или отдельным процессом с одинаковой границей затрат. Накопленный process lifetime peak после последовательности A→B не является peak второго arm. Если выбранный host не позволяет разделить показатели, соответствующую RAM-метрику отметить `NOT_MEASURED`, а не приписывать ей выигрыш или ноль.

**Успех:** любое измеренное улучшение полезного показателя считается успехом по этому показателю и домену; рост точности не обязателен. Показывать регрессии рядом. Если равенство состояния не выдержано, cache перестал быть чистой cost-оптимизацией: сохраняются наблюдения, требуется разбор причины, нельзя заявлять эквивалентность.

## 5. Требование к показателям «после»

`StepVector` и `StepMany` рассчитывают loss/margin до `ApplyOptimizer`, затем публикуют их вместе с уже обновлённым checkpoint. `LogicalDpoTrainingResult.LastLoss/LastAccuracy` берёт именно эти предобновляющие значения. Поэтому после последнего update нужен отдельный after score на той же frozen panel. Более того, `EvaluateMany` усредняет обычную objective, а exact `StepVector` loss включает normalized pair weights × teaching-vector signal; напрямую вычитать эти два числа нельзя. Это проверка валидности экспериментов, не новая заявка на novelty. [StepVector до/после](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/11.DPO/DpoTrainer.cs#L891-L935), [EvaluateMany](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/11.DPO/DpoTrainer.cs#L767-L807), [LastLoss](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L1421-L1430).
