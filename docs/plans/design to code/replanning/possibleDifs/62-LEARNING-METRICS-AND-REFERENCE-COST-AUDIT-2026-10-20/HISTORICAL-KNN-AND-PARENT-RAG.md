## 1. Главный результат

Исторические положительные результаты есть, в том числе результат, который старый отчёт назвал FAILED из-за порога +5%. Поэтому общее заключение «раньше успешного обучения не было» неверно. Вместе с тем конкретная цепочка **один механизм в матрице → его перенос в kNN → успешное обучение на сопоставимом материале** в прочитанных первичных источниках пока не восстановлена. Это открытая часть provenance, а не опровержение воспоминания пользователя.

Проверено отдельное, более узкое перемещение: экспериментальный StructuralKnn переносился в production. Проверены требования родительских документов к памяти положительных, отрицательных и предупреждающих примеров. Проверены реальные различия между AST-контекстом E09, локальным POS-контекстом E26 и нынешним generic KnnLogicalUnit. Большинство этих различий уже зарегистрировано в possibleDifs; ниже они явно помечены как повторная проверка, а не новые открытия.

### Два успеха, которые нельзя переименовать в обучение без дополнительной цепочки

[E26](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E26ContextualDictionary.cs#L3-L42) проверяет contextual dictionary на 15 фиксированных test cases: baseline возвращает highest-priority entry, enhanced учитывает neighboring POS. Сам Run вызывает BuildDefault и сравнение, но не обучает словарь новыми уроками. Это полезная историческая проверка representation/consumer, а не выполненный в этой карточке before/after training experiment. Для нынешней задачи нужен реальный AddMapping/Train путь и применение learned state после новых уроков.

[E27](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E27PatternReorderer.cs#L3-L40) прямо описывает fixed rule table и содержит 7 фиксированных перестановок. Это свидетельство полезности порядка слов при известных pattern/POS; оно не доказывает обучаемость reorderer. В будущий learning experiment такие правила допустимы только как фактор реального train→state→consumer пути, с точным местом изменения. Изолированный повтор E27 не соответствует заданию пользователя.

## 6. Новизна и отказ от ложной новой карточки

На финальном этапе доступен полный pin corpus root: 555 Markdown-файлов possibleDifs. Проведены целевые поиски по выбранным code seams и прочитаны связанные исходные аудиты. Не заявляется, что все 555 прочитаны последовательно. Установленные выше AST/generic kNN/translation differences уже имеют prior art; повторно нумеровать их как новые нельзя.

Проверенный кандидат — положительный урок verifier с `chosen.Pass=true` не меняет state, а machine всё равно записывает training identity — сохранён в [условном реестре](CANDIDATE-NOT-PROMOTED-VERIFIER-POSITIVE-FEEDBACK.md). Однако найденный штатный producer создаёт chosen.Pass=false и rejected.Pass=true. Реальный маршрут поступления positive corrective lesson не установлен. Поэтому кандидат **не выносится в активный learning experiment**, не объявляется причиной RP01 и не получает выдуманного before/after.

## 7. Требования к повторному измерению уже известных механизмов

Эти пункты не новые experiment IDs; это поправки к существующим historical/card owners.

1. Для E09 сначала выбрать общий независимый AST target vocabulary и file-disjoint train/calibration/exam. Построить пары внутри файла. Обе обученные руки получают тот же набор пар и оцениваются на тех же exam IDs. Записать empty/pre-state, trained state и heldout predictions. Простая поправка знаменателя на старых numbers сама по себе не новый learning experiment.
2. Для E34 обе руки строят memory/index на одних train IDs. Alpha — только calibration. До и после обучения обе руки получают одну sealed exam panel. Приписывать выигрыш generic Unit можно лишь после подключения реального trained consumer; голое reranking фиксированных neighbors — вне задачи пользователя.
3. Для E26/структур translation сначала назвать настоящего получателя урока и его mutation. A — existing representation, B — один конкретный context feature в training и serving, C — контроль, который не получает этот урок, когда это помогает причинности. Домены, где feature не определён, не объединять в pooled success.
4. Любое измеренное улучшение полезной метрики считается успехом по этой метрике и домену; рост accuracy не обязателен. Рядом показываются latency/compute, coverage, false acceptance/rejection, старые правильные случаи и иные ухудшения. Loss/state hashes — диагностика обучения, сами по себе не пользовательская полезность.

## Проверки и ограничения

Выполнены API чтения pinned source/commit patches/raw result files, целевое dedup по полному локальному corpus и сравнение исторических E09/E14 исходников с current. .NET runtime/compiler в окружении отсутствует; никаких C# training outputs, восстановленных моделей или новых качества/времени не выдумано. Никакой matrix→KNN эксперимент не объявлен воспроизведённым.
