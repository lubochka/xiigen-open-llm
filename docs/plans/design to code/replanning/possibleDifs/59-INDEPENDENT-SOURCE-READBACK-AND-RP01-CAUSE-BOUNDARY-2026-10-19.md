## 1. Ответ о потере качества: пока доказана разница УЧЕБНЫХ ТРАЕКТОРИЙ, а не один установленный дефект

[RP01 source audit](../Kiro-Xiigen-RP01-Learning-First-Slice-Pack/RP01-2026-10-16-LEARNING-RECOVERY-AND-CODE-AUDIT.md): C#500 и EN→RU500 меняли LoRA tensors после 50 steps, но проверенная свободная генерация осталась 0/3→0/3 и 0/4→0/4 соответственно. Малый положительный DPO margin не эквивалентен усвоенному предметному поведению. Отличать факт update от нужного learned policy, действительного вызова Student и независимой оценки.

[Исторический/сохранённый P125 native отчёт](https://github.com/lubochka/llm_mvp_core/blob/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/P125-enru-memory-01/report.md) показывает другую систему: структурное обучение Executor Unit, 8 уроков, ordinary Flow 0/24→19/24, cold restore 19/24, нейронных updates 0. Нельзя сравнить 19/24 с 0/4 как accuracy одного и того же Student, но такой native positive свидетельствует о реальной способности памяти менять ответы. Положительные E09/E25/E26/E43 и поздняя успешная работа признаков внутри KNN должны быть привязаны к собственному owner, ветке, источникам, корпусу, знаменателю и consumer. «Неудачный» старый matrix-run не делает перенесённый в KNN признак бесполезным.

Source сравнение: [N58 branch-deltas](58-SIBLING-DPO-LORA-SOURCE-DELTAS-2026-10-19.md) подтверждает, что исходник TranslationTrainedUnits.cs *совпадает* между PrepareToGPL/current/DesignToCode-clean. Поэтому унаследованную ошибку Executor нельзя автоматически назвать причиной source-regression RP01; нужна разница фактических данных, состояний и маршрута. Изменение знака локального DPO градиента между ветками не доказывает без полного gradient/update направления, что один trainer «не обучается».

## 3. ДВА адресных дополнительных кандидата (не объявлять глобально уникальными)

**H59-01: альтернативные task types обученного guide считаются одновременно обязательными при exact match.** В [OrchestrationReasoningScenarioUnit.BuildNearestGuide, lines 559–627](https://github.com/lubochka/llm_mvp_core/blob/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/43.SmartSkillsDomain/OrchestrationReasoningScenarioUnit.cs#L559-L627) переменная taskTypeSatisfied принимает ANY из RequiredTaskTypes, а requiredSatisfied собирает RequiredTaskTypes с обязательными content signals и требует ALL. При двух *альтернативных* task types TRAIN pattern exact state никогда не удовлетворён одиночным request task type и становится transferable/NOT_READY. Точная интерпретация списка RequiredTaskTypes как OR **требует контракта**; при намеренной AND-семантике это не bug. [Executor branch](https://github.com/lubochka/llm_mvp_core/blob/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/43.SmartSkillsDomain/OrchestrationReasoningScenarioUnit.cs#L309-L391) разрешает user plan только exact. **Важное ограничение:** обычный [BuildPattern](https://github.com/lubochka/llm_mvp_core/blob/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/43.SmartSkillsDomain/OrchestrationReasoningTrainer.cs#L190-L260) default ставит только один universal_reasoning; effect conditional на реально обученном/допущенном multi-type state. Это не объяснение C#500 Student и не гарантия input reachability.

**H59-02: derived training pattern может перестать зависеть от chosen/rejected при разрешённом learned_pattern payload.** [OrchestrationReasoningTrainer.BuildPattern](https://github.com/lubochka/llm_mvp_core/blob/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/43.SmartSkillsDomain/OrchestrationReasoningTrainer.cs#L190-L267) валидирует metadata + две feature стороны, но при наличии optional learned_pattern десериализует этот готовый объект и возвращает его, минуя default BuildPattern из chosen fields. Это source branch, **не доказательство пропуска upstream legal admission** или потери learned quality. Report явно указывает TrainingStarted=false / ModelAssetCreated=false / CheckpointCreated=false; простая материализация здесь НЕ является обучением. Для проверки влияния на **настоящее** learning нужна доказанная цепочка TRAIN mutation -> accepted learned guide -> ordinary Plan; если доступна только MaterializeAsync/fixture, результат ограничить CONTRACT-ONLY, НЕ называть успешным экспериментом обучения.

**NOVELTY:** просмотрены N52 orchestration summaries, N56 projector findings, protected P51/P52/P56/P107 и источники этих методов; буквального узкого H59-01/H59-02 там не найдено. Но полного семантического reread сотен документов и всех P01–P125 не было. Поэтому NEW_CANDIDATE, не VERIFIED_UNIQUE.

## 4. Аудит достоверности защищённых экспериментов

[Защищённый каталог](https://github.com/lubochka/llm_mvp_core/tree/c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72/docs/plans/replanning-possible-diffs) просмотрен выборочно: 125 P-cards, 470 subcases по [N57 read-only inventory](57-ARGUMENT-AND-VERIFIER-LEARNING-GAPS-2026-10-19/03-experiment-coverage-review.md). 470/470 **адресованы** small-probe index, но не 470 native checks и не 470 independent quality reviews. Некоторые P-cards хранят Windows-абсолютные исходники, не исполнимые source references. Доказаны HYPOTHESIS/DESIGN и отдельные native receipts (особенно P125), а не глобальный ALL_VALID verdict. Новые H59-01/H59-02 не добавляются в защищённую папку; shadow passports см. [N59 experiments](59-CAUSAL-LEARNING-PASSPORTS-AND-EXECUTOR-PROMPTS-2026-10-19.md).

**Критерий пользователя:** только реальное обучающее изменение с настоящим recipient, actual state mutation и own consumer before/after имеет право называться «эксперимент качества обучения». Component-only, refactoring, score recalculation, parameter self-check и reporter-only сравнения полезны для диагностики, но НЕ подтверждают learned gain. Любое измеренное улучшение полезной оси — успех по этой оси и конкретному домену без обязательного роста accuracy; потери других осей показывать на той же панели. Нельзя менять метрику после ответа.

## 5. Обязательные архитектурные границы

Не смешивать subject domain (перевод / C# / SQL / orchestration), механизм (DPO / LoRA / KNN / tokenizer), task profile (EN→RU vs RU→EN), Unit/Flow (получатель) и scorer. Для каждого гипотетического «улучшения» назвать конкретные TRAIN/EXAM семьи и consumer. C# AST/order features условны для кода, токен-порядок/полярность — для перевода, SQL NULL — для SQL; переносить rule без источника нельзя.
