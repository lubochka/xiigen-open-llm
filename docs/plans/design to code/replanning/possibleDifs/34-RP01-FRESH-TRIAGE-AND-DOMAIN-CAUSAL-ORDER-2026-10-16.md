**Дата:** 16.10.2026. **Только исследование и документация.** Сверены `xiigen-planning/llm_plan3` (RP01, possibleDifs, RAG entry), `llm_mvp_core/codex/dpo-implementation@216a1f3d6af3f40ceef081dc168b07e4ce3934f9`, отдельные файлы `DesignToCode`, `language_translate`. ## Человеческий диагноз

Прошлое «модель научилась» включало минимум **три принципиально разных результата**: (1) накопленная доменная память выдаёт известный ответ, (2) структурированный Unit применяет выученное правило к другому контексту, (3) нейросеть меняет вероятность ответов и самостоятельно генерирует правильный новый ответ. Нынешняя RP01 в основном проверила (3), причём на слабом обучаемом Student без отдельного доказанного supervised language competence. Успехи (1)/(2) нельзя считать несостоявшимися только из-за `0/3` и `0/4` у (3). Обратная сторона: успешная KNN подстановка не доказывает, что нейронная модель что-либо усвоила.

**Операционное решение:** сначала выяснить, **кому фактически достался урок и кто реально отвечает пользователю**, затем проверить качество на одной и той же закрытой панели, а не подгонять тесты под алгоритм. Большой Windows CI и широта unit-test покрытия тут не первичные доказательства качества.

## Приоритет применения и остановки

1. **Первый gate: real ownership** — найти обычный вызов пользователя и того, кто отвечает: saved Student? typed Unit? kNN? static fallback? Если route иной, предыдущие «обучила сеть» метрики изолированы от конечного продукта.
2. **Второй gate: can-learn control** — на крошечном неслизавшемся lawful material train/supervised/finite-gradient получить реальное улучшение вне training set. Если нет, не запускать широкую оптимизацию HNSW и десятки Windows CI.
3. **Третий gate: same-input historical donor** — пара `old trained Unit` и `Student`, одинаковые requests, независимо проверенный вердикт и защита от exact memory-copy. Если donor действительно выиграл, переносить **содержание и recipient** его алгоритма; не объявлять старое PASS доказательством DPO.
4. **Четвёртый gate: domain boundary** — код AST/SQL operations, перевод POS/word order, general lexical BM25, replay. Не смешивать веса/признаки и оценочные панели разных доменов.
5. **Последний gate: adoption/restore** — после первого прироста сохранить, выгрузить, восстановить в новом процессе и проверить **обычный consumer**. Два разных checkpoint APIs не должны выдавать одинаковую метку `RESTORED`, если реальное состояние памяти различается.

## Качество плана / границы проверки

- **Архитектура:** старые решения читать по `DECISIONS-LOCKED` перед изменением; не декларировать новую общую архитектуру из одного source observation.
- **Code review:** primary file, callers, consumers, tests — в таком порядке; конкурирующие утверждения про DPO gradient разрешать точным численным finite-difference, а не голосованием документов.
- **Планирование:** конкретный owner, один изменённый фактор, ожидаемый отличающий результат, negative control, acceptance/rejection, rollback. Финальный вердикт — независимое предметное качество, а не PASSED unit tests.
- **Prompt engineering:** в будущих teacher/judge prompts указывать `domain law`, original source, actual recipient, acceptable chosen, precise error rejected, `TIE/BOTH_BAD` option, independent blind judge; отдельно проверять происхождение данных и разрешённые полномочия.
- **Human communication:** один скрин результатов: «старый ответ / новый ответ / что изменилось / независимый вердикт / ухудшившиеся случаи / стоимость», а не таблица сотен зелёных тестов.
- **Что реально сделано здесь:** адресное чтение GitHub, сверка уже опубликованных гипотез и 2 соседних исторических файловых линий, один source-proxy, новые Markdown документы. **Не делалось:** full RAG exhaustiveness, CodeX/Astra independent external calls, Chinese model pair authoring, native neural/Unit experiment, GitHub Windows CI.
