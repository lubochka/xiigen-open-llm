## 0. Что восстанавливать в первую очередь — проверенный разрыв от золотой ветки

**P0-GDC-01: пропал `visual_score` из канонической обучающей DPO-пары DesignConversion, хотя локальный получатель до сих пор пытается читать этот сигнал.**

* До изменения [gold `DesignConversionTrainingPipeline.cs:L1487-L1520`](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/44.DesignConversionDomain/DesignConversionTrainingPipeline.cs#L1487-L1520) `ToCanonicalTrainingItem` включал `html`, `css`, **`visual_score`** в обе стороны ответа.
* Теперь [current `DesignConversionTrainingPipeline.cs:L2712-L2727`](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionTrainingPipeline.cs#L2712-L2727) передаёт только `html` и `css` через `BuildOptimizerResponsePayload`; [Builder:L1442-L1447](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionDpoDatasetBuilder.cs#L1442-L1447).
* Но [current `DesignConversionMachine.cs:L2937-L3003`](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionMachine.cs#L2937-L3003) вычисляет `preferenceMargin = chosen.visual_score - rejected.visual_score` **лишь при наличии обоих полей**, иначе при разных JSON-ответах ставит **`1.0` независимо от реального качества**, при равных не добавляет update.
* Следовательно, это **доказанное несовпадение контракта построения материала и локального вычисления весов**. Оно не доказывает, что нейронный DPO оптимизатор `11.DPO` использует эту же scalar-оценку: *локальный feature-weight Machine* и *нейронная q/v-LoRA policy* — разные получатели. До blame RP01 нужно доказать конкретную цепь вызывающего кода.

**Пример:** gold `visual_score=0.9` против `0.1` даёт `+0.8`; при обратной оценке — `-0.8`. Одинаковые по структуре current JSON `{html,css}` без оценки в обоих случаях приводят к `1.0`. Это математическое следствие веток кода, а **не проведённое обучение**.

**Важная дополнительная проверка gold:** [старый `Machine.BuildLearnedWeightDeltas:L2783–2817`](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/44.DesignConversionDomain/DesignConversionMachine.cs#L2783-L2817) при отсутствии двух `visual_score` **вообще возвращал пустой список delta**. Новый [consumer:L2965–3003](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionMachine.cs#L2965-L3003) создаёт source-derived delta даже без проверяемой оценки. **Однако сама величина margin в этом коде не умножается на вес этих deltas**, поэтому нельзя говорить, что удаление score напрямую обнулило/изменило local gradient. Доказано более точное: ослабление прежнего gating и `chosen↔rejected`-инвариантность local `source_kind/internal_vector` weights в canonical HTML/CSS path (см. [toy result](54-DESIGNTOCODE-CLEAN-PROXY-RESULT.json)). Отдельный нейронный DPO получает содержательные HTML/CSS стороны и должен оцениваться самостоятельно.\n\n**Восстановление без регрессии безопасности:** не возвращать метки оценщика в текст генеративного prompt/response. Оставить нынешний канонический HTML/CSS для DPO Student, но добавить **отдельный разрешённый типизированный server-owned обучающий сигнал** (`chosenScore`, `rejectedScore`, provenance, идентичность сторон и целевого Unit) для feature-weight Machine. Для реализации требуется проверка авторизации, а не обход admission gate. Замерить отдельно `Δ local learned weights`, `Δ policy preference`, `Δ ordinary HTML/CSS quality`.

## 2. Почему нельзя просто откатить DesignToCode-clean

1. В gold [Builder:L682-L742](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/44.DesignConversionDomain/DesignConversionDpoDatasetBuilder.cs#L682-L742) текст prompt уже содержал производные **результата обеих сторон** (margin, категории, ссылки), а отдельные chosen/rejected были JSON оценок/хешей, **не HTML/CSS**. Это не эквивалент текущему учителю порождать HTML/CSS; такой prompt допускал утечку метки. Current [Builder:L1231-L1260](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionDpoDatasetBuilder.cs#L1231-L1260) и [L1442-L1447](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionDpoDatasetBuilder.cs#L1442-L1447) убрали этот short-cut. **Сохранить улучшение**.
2. Архив [gold Pass114](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/docs/evidence/design-conversion/codex-pass114-real-learned-weight-proof.md) подтверждает локальный checkpoint и focused tests, [Pass116](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/docs/evidence/design-conversion/codex-pass116-runtime-learned-inference-authority.md) — влияние feature weights на Critic score/metadata; [Pass150](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/docs/evidence/design-conversion/codex-pass150-real-training-noop-closure.md) — supervised локальный негативный contrast; [Pass151](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/docs/evidence/design-conversion/codex-pass151-improver-non-copy-closure.md) — **детерминистическое** исправление HTML/CSS. Это разные уровни доказательства, **не единый замер качества визуального DPO на независимых случаях**.
3. RP01 C#/EN→RU Student начинает со случайной, не предобученной B0 и проверяет **нейронную q/v-LoRA**, а DesignConversion gold показывает также детерминистические Unit и learned feature-weights. Не объявлять ни один из механизмов универсальной заменой другого. [RP01 real results](../Kiro-Xiigen-RP01-Learning-First-Slice-Pack/RP01-2026-10-16-LEARNING-RECOVERY-AND-CODE-AUDIT.md): C# free 0/3→0/3; EN→RU free 0/4→0/4, несмотря на изменение LoRA.
4. Для C# применимы AST order/KNN, для перевода — POS/порядок слова/морфология, для HTML/CSS — DOM отношения и визуальные дефекты. **Нельзя переносить правила по доменам без отдельного эксперимента**.

## 3. Маршрут проверки полезного восстановления

`gold source + frozen historical result` → `exact training/approved DPO triplet` → `видимые признаки и невидимые метки` → `фактический train recipient` → `feature/LoRA state Δ` → `checkpoint` → `fresh process load` → `ordinary consumer` → `source-disjoint семантический экзамен`.

**Проверка должна выдержать отрицательные контроли:** обучение со сменой оценок chosen↔rejected, неразрешённый источник, no-op batch, два разных родительских узла/две координаты вектора, один против двух дефектов. Предзаполненный словарь, pass unit-test, рост `ObservationCount` и margin без изменения ответа — *не* критерий успеха.
