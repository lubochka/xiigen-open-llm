# Сначала восстановить успешный механизм PrepareToGPL

Дата аудита: 18 октября 2026, UTC. База — [PrepareToGPL, 31346d8](https://github.com/lubochka/llm_mvp_core/tree/31346d8928be4469b01aaf313780e8f950ff91e2); проверяемая реализация — [codex/dpo-implementation, a392b6b](https://github.com/lubochka/llm_mvp_core/tree/a392b6be8f8dec1e2375e2eb4fe21c2f6e8950c6).

**Первым проверять загрузку прежнего обученного состояния и доставку прежнего урока в прежний работающий Unit.** Найдена конкретная несовместимость сохранённого translation checkpoint между четырьмя и шестью направлениями. Одновременно свежие результаты показывают, что существующая память переводческого Unit уже обучается, переносит знакомые части на новые сочетания и сохраняет ответы после холодной загрузки. Это задаёт рабочую опору для восстановления, а не повод начинать весь алгоритм заново.

Пакет дополняет существующий каталог. Он содержит новые узкие гипотезы, уточнения известных механизмов и контрдоказательства. Перед публикацией перечитаны новые материалы N40–N42 на planning a4a3e709: разрыв 4→6 уже описан коллегой в [N41-T1](41-FOUR-VS-SIX-TRANSLATION-CHECKPOINT-MIGRATION-2026-10-18.md). Здесь он независимо подтверждён точным tracked asset и preflight; **не считается новой уникальной находкой**. Новая дельта — пять конкретных механизмов U-N1/U-N2/U-N3 и DLT-1/DLT-2, с условной применимостью; DLT-3 уточняет известную тему. Подтверждение ветви кода, численный пример и измеренное улучшение ответа имеют разные статусы. **В данном аудите новые native learning runs не выполнялись.** Все приведённые предметные результаты принадлежат связанным ниже прежним запускам.

## 1. Очередь экспериментов восстановления

Первые пять групп направлены именно на сохранение или восстановление поведения успешной ветки. Дальнейшие уточняют новые возможные пробелы. Порядок — инженерная рекомендация по конкретности доказательства и стоимости различающей проверки; это не оценка вероятности единственной причины RP01. При финальном обновлении до planning004c4a79 дополнительно сверены [шесть документов параллельного пакета](2026-10-18-preparetogpl-recovery/README.md): пять точных механизмов этого пакета сохраняют новизну. Номера U-N/U-R локальны каждой записке; для однозначности использовать наши PG-номера и ссылку на файл.

## 2. Независимо подтверждённое расхождение: старое состояние не проходит нынешний loader

В PrepareToGPL TranslationMachine создаёт RU_EN, EN_RU, HE_EN, EN_HE. Current создаёт ещё ES_EN и EN_ES. При импорте current требует состояние для всех исполнителей runtime и возвращает **EXECUTOR_DIRECTIONS_INCOMPLETE**, если хотя бы один отсутствует. При этом экспорт и проверка в обоих снимках используют schema version 1.

Это не выдуманный несовместимый fixture. Файл **models/translation/translation-v1/translation-v1-checkpoint.json** имеет одинаковый Git blob **a4cf054ba3f8a6ee6aa9818edc6c5705e3456c25** в обеих ветках; в нём только четыре направления. Подробные исходники, диапазоны строк, ограничения и перенос состояния — в [отчёте KNN/истории](PREPARETOGPL-KNN-HISTORY-2026-10-18.md). [Выполненный preflight](PREPARETOGPL-CHECKPOINT-PREFLIGHT-RESULT-2026-10-18.json) проверяет пересечение наборов по настоящим исходникам и файлу. Он **не исполняет C# loader**.

Ремонт должен явно распознавать старый состав runtime, переносить старые executor maps, KNN, tokenizer, verifier, историю и идентичности и создавать пустые новые исполнители. Простое удаление проверки полноты не обеспечивает корректность. Возвращение всех старых исходников тоже не нужно: несовместимость локализована на версии и составе сохранённого состояния. Нативный PG-01 отделяет отказ загрузки от реальной потери ответа.

Для полного пути shared asset коллеги дополнительно нашли обязательное TrainingDataEvidence в manifest при прежней schema1, а для продолжения — смешение raw PairId и производных Unit ExampleIds. Это отдельные проверки после/вокруг checkpoint load, сохранённые в [их translation/lineage главе](2026-10-18-preparetogpl-recovery/01-translation-restore-and-unit-lineage.md). Их neural [legacy base-import/attached-adapter](2026-10-18-preparetogpl-recovery/02-neural-and-lora.md) относится к intent восстановления, а не к нашему расходованию RNG следующей новой моделью.

## 4. Что переносить из успешной ветки, а что сравнивать отдельно

**KNN и семантическая обработка не исчезли целиком.** По Git tree все 27 файлов 12.SemanticCompiler совпадают между PrepareToGPL и current; TranslationTrainedUnits.cs также совпадает. В трёх непосредственно прочитанных соседних источниках алгоритмы отличаются от PrepareToGPL только добавленным лицензионным заголовком. Поэтому отсутствие пользы сначала локализуется в выбранном consumer, загруженном состоянии, данных и доступности признаков. Это не доказывает, что любая конфигурация этих классов исправна. [Проверка деревьев, соседних веток и первичных экспериментов](PREPARETOGPL-KNN-HISTORY-2026-10-18.md).

**Не переносить старые ошибки нейронного тракта вместе с полезным Unit.** В старом LoraApplicator.Apply создание адаптеров само по себе не заменяло base forward. Current подключает LoRA к attention; current DPO исправляет знак log-prob производной, использует тот же forward graph и response-only exact objective. Эти изменения совместимы с задачей восстановления правильного обучения. Архивный успех другого класса в той же ветке не подтверждает работоспособность любого старого LoRA caller. [Точные старые/новые строки и состояние fixes](PREPARETOGPL-DPO-LORA-TOKENS-2026-10-18.md).

**Не смешивать память и optimizer replay.** Для ограниченного числа gradient steps можно брать короткий replay, сохраняя больший проверенный банк retrieval-примеров. Current loader должен честно воспроизводить подписанный корпус своей версии. Его нельзя «улучшать» неявным чтением любых старых файлов рядом. [U-R1](PREPARETOGPL-UNITS-RESTORE-2026-10-18.md).

**Детерминированность вычислений сама по себе полезна.** Проверять нужно решения, которые ожидались обучаемыми, но выбираются константой, шаблоном, неподходящим scope или неиспользуемым learned state. В нынешнем projector generated-capability chosen строится из ID и имени subphase. Это ограничивает ожидаемый результат этого recipient: шаблон о задаче не равен предметному решению. В materializer готовый learned_pattern может быть корректным способом восстановления. [U-N1/U-N2/U-N3](PREPARETOGPL-UNITS-RESTORE-2026-10-18.md).

3. [DPO, LoRA, токены и численные ограничения](PREPARETOGPL-DPO-LORA-TOKENS-2026-10-18.md).

5. [Реестр доказательств, новизны и независимой проверки](PREPARETOGPL-EVIDENCE-AND-NOVELTY-2026-10-18.md).

В будущих DPO опытах CODEX в запрошенной конфигурации **astra 6 ultracode** выполняет человеческий выбор урока; разрешённая внешняя открытая китайская модель создаёт обе стороны chosen/rejected; отдельный CODEX в той же запрошенной конфигурации независимо оценивает точную пару и реальные ответы. Эти роли не считаются исполненными фактом написания плана.

Продуктовый код и защищённый core-каталог в этой работе не меняются. Целевой результат — проверяемые документы в possibleDifs ветки llm_plan3, с восстановлением PrepareToGPL в начале README.
