# RP01: что может теряться в обучении и какие малые опыты действительно это проверят

Дата: **20 октября 2026**. Результат этого прохода — документы с доказательствами и конкретными проектами экспериментов. Изменения продукта и новые native запуски обучения в этом проходе не выполнялись.

**Основной вывод:** успешные учебные пути в соседних ветках и текущей памяти действительно существуют. Однако их метрики нельзя автоматически считать качеством нейронного RP01: различаются получатели обучения, представления, панели и способы ответа. Найдены две дополнительные, подтверждённые исходниками гипотезы для обучаемой оркестрации, уточнён конкретный малый нейронный A/B и проверено покрытие 125 исторических семейств / 470 подслучаев. Единственная доказанная причина ухудшения нейронного RP01 этим аудитом не установлена.

## Что изменилось в выводах после проверки текущей версии

Основной source-аудит выполнен на core `bf9b543e149ef197da85a767821d98c9b67916d2`. Во время работы ветка продвинулась до `de4ef0f14172dada4daf142a4c66ba19e96bb6d4`. Два новых коммита изменили **документы**, а не исследуемые реализации. [Сравнение версий](https://github.com/lubochka/llm_mvp_core/compare/bf9b543e149ef197da85a767821d98c9b67916d2...de4ef0f14172dada4daf142a4c66ba19e96bb6d4).

В новой [политике выполнения](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/docs/plans/replanning-possible-diffs/experimets/00-execution-policy-2026-10-20.md) уже отменены общая блокировка карточек и повторное персональное согласование каждого SHA. Уже разрешены загрузка, токенизация, подготовка пар, restore и потребление обученного состояния при доказанной связи с обучением и конкретном исправлении оригинального кода. Эти исправления **не являются незакрытыми замечаниями к текущей версии и не приписываются этому аудиту**. Старые формулировки ниже по истории не должны снова останавливать порученную подготовку.

Защищённый каталог `llm_mvp_core/docs/plans/replanning-possible-diffs` нами не редактировался. Новые карточки, уточнения и указатели находятся только в разрешённом `possibleDifs`. Поэтому ответ на вопрос «все ли найденные детали уже описаны там?» — **нет**: общая тема в P-карточке не гарантирует покрытия конкретного механизма; для двух новых Mode1-сценариев exact recipes в проверенном корпусе не найдены. Они полностью описаны в документе02, с явным сопоставлением ближайших P67/P118.

## Две новые гипотезы

**1. Последующий урок того же Flow стирает входные признаки предыдущего.** `PromptFlowGroundingModel.Train` сохраняет новую пару в kNN, но присваивает `_weights[pair.FlowRef] = BuildWeights(pair)`. Старый урок остаётся в памяти, а признаки, по которым выбирается его Flow, заменяются. Это другой механизм, чем отклонение повторного PairId: в новом опыте все PairId различаются. Предлагаемый A/B меняет только накопление входных признаков для одного Flow. Три урока на плечо, четыре проверочных задания в пяти состояниях: **6 настоящих учебных вызовов и 40 ответов**. [Исходный writer](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/42.ProjectWikiDomain/PromptFlowGroundingModel.cs#L17-L24).

**2. Выбранному Flow может быть подставлен текст другого выученного плана.** `TryGround` выбирает Flow по per-flow features, а `FindLearnedPair` снова ищет по глобальной Mode1-памяти без ограничения этим Flow. Composer использует Flow из grounding и тело из найденной пары. Малый A/B меняет только область финального поиска: кандидаты должны принадлежать выбранному Flow. Два урока на плечо, три задания в четырёх состояниях: **4 учебных вызова и 24 ответа**. Здесь результат зависит от reader обученной памяти; это допустимая зависимость обучения по пункту4 пользователя. [Retrieval](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/42.ProjectWikiDomain/PromptFlowGroundingModel.cs#L26-L83), [потребитель](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/42.ProjectWikiDomain/TrainedRouteComposerUnit.cs#L10-L35).

Обе особенности присутствуют и в исторической ветке `orchestrator-extensions`. Поэтому это **унаследованные ограничения**, а не доказанная регрессия RP01. Исходный код подтверждает механизм; улучшение после предлагаемого исправления ещё не измерено. Ручные расчёты scores в карточках — прогноз для проверки реальной цепочкой, а не результаты обучения.

## Подтверждённый положительный результат, который нельзя потерять

Для исправления доставки `phrase_mappings` независимо пересчитаны 48 сохранённых native ответов: одинаковые восемь уроков дали **11/24 → 19/24** правильных ответов; новые сочетания знакомых частей — **0/8 → 8/8**. Одновременно неверно принятых ответов стало **1 → 3**, а правильность среди принятых снизилась **91,67% → 86,36%**. В частности, принимаются ответы с потерей отрицания и вопросительного смысла. Это успех по композиции и correct/all в данном переводческом профиле с показанным ухудшением другой оси. [Первичный отчёт](https://github.com/lubochka/llm_mvp_core/blob/bf9b543e149ef197da85a767821d98c9b67916d2/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/translation-memory-ingress-01/report.md) и исходные raw/scorer-ссылки — в документе02.

Это настоящее обучение памяти Executor через reader/builder и `TrainStructuredBatchAsync`, а не новое измерение нейронного RP01. Контроль приобретения памяти P125 `0/24 → 19/24`, ремонт ingress `11/24 → 19/24` и проверка cold restore отвечают на разные вопросы; их нельзя объединять в одну дельту.

## Что делать с нейронным RP01

Текущая simulation-ветвь уже использует exact segmented byte-BPE, response masks, response-sum objective и frozen reference. Восстановление ENRU continuation включает optimizer/RNG. Embedding scatter-add, bias backward и fractional-mask согласование уже присутствуют; повторно «чинить» их как отсутствующие нельзя. Legacy Compact480 остаётся отдельной ветвью, а не автоматически текущим поведением RP01. [Подробный source trace](03-NEURAL-LEARNING-AND-MICRO-CALLER.md).

Для первого ограниченного нейронного опыта подготовлен проект существующей гипотезы **ND-DPO-PAD**: те же два урока и исходная модель, единственное изменение — вычисление рабочей стороны пары до её настоящей длины после полной проверки authoritative exact material. **Четыре реальных optimizer updates суммарно; для ресурсной метрики генерации не обязательны.** Дополнительная оценка ответов описана отдельно, с отдельным бюджетом. Это уточнение известного опыта, не новое открытие.

Текущий runner ещё требует реализации малого парного владельца: его режимы1/500 не дают такой запуск, а identity `domain + Mode + InputSha256` сталкивает два плеча с одинаковым TRAIN. В документе03 названы методы, схема двух независимых arms и сохранение защиты от повторного эффекта. Новый `RunId`, удаление markers и выдуманная «готовая команда» это не исправляют.

## Правило интерпретации результата

**Любое измеренное улучшение полезного показателя считается успехом по этому показателю и домену; рост точности не обязателен. Остальные показатели, включая ухудшения, показываются рядом.** Неизмеренное обозначается «не измерено», а не нулём. Это правило уже есть в прежних125 карточках; оно повторено в новых конкретных карточках и промптах этого пакета.

Ни число файлов, ни наличие слова «обучение», ни прирост размера checkpoint сами по себе не доказывают приобретённое умение. Для утверждения об изменении обучения нужны конкретный получатель, материал, настоящая операция обновления, её состояние и обычный consumer. Для проверки сохранности или использования достаточно provenance уже обученного состояния и точной зависимости с конкретным исправлением; повторное обучение ради формальности не требуется. Ресурсы сравниваются на сопоставимой настоящей учебной работе либо доказанном зависимом участке. Отдельный benchmark неучаствующего helper не заменяет такой опыт.
