# Первое поручение CODEX: установить получателя и проверить потерю C# признака

Статус этого поручения: **подготовлено, не исполнено**. Его можно реализовать отдельно от большого RP01 запуска. Основные объяснения и исходники — [глава 0](00-EXTERNAL-DOMAINS-RESTORATION-FIRST.md), [новые находки](02-NEW-CSHARP-INPUT-AND-CALL-LOSS.md), [опыты](03-MICRO-EXPERIMENTS-BY-DOMAIN.md).

## Цель

Сначала установить, каким публичным потребителем был получен один успешный результат `external_domains`. Затем проверить один узкий механизм: сохраняется ли исполняемое выражение интерполяции при обучении и запросе C# KNN. Итогом должны стать точные значения входа, признаков и ответа, а при достижимом доменном потребителе — маленькое парное измерение полезного качества.

## Роли и материал

CODEX с **Astra 6 UltraCode** выполняет делегированный человеческий выбор. Внешняя **открытая китайская модель** создаёт обе финальные стороны DPO: `chosen` и `rejected`. Отдельная оценка их качества и финальных ответов — CODEX с **Astra 6 UltraCode**. Идентификаторы фактически вызванных моделей и параметры вызовов записываются в результат. Если модель не вызывалась, указывается `NOT_CALLED`, без присвоения имени по роли.

Для первых технических этапов готовые C# fixtures не являются DPO. Им не требуется выдуманная история преподавателя или принятия пары. Если требуется новый учебный материал для последующего semantic этапа, обе стороны каждой пары сохраняются без подмены отвергнутой стороны шаблоном; внешняя оценка проверяет их предметный контраст. Генератор не выбирает победителя собственного A/B.

## Входы, которые замораживаются до опыта

1. Два одноразовых checkout: external SHA `3036a01acec938f0b83fa4ffbda26202cc35d639` и current SHA `44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76`.
2. Один исторический source/corpus и known-good output, если такой сохранённый runtime artifact доступен; его настоящий public caller, flags, tokenizer и state. Без artifact кодовое восстановление проверяется отдельно, а historical-behavior parity помечается как ещё не установленная.
3. Готовый [native проект](native/NativeProbe.csproj) с [Program.cs](native/Program.cs); .NET 9 SDK и согласованные зависимости. Проект сборки может создавать bin/obj в одноразовых checkout.
4. Для RX2 одинаковые шесть raw TRAIN в двух свежих facade, query с interpolation и constant control. Это диагностические примеры с переименованиями; они не засчитываются как независимые новые семейства кода.

## Последовательность

**Этап G0 — фактический путь.** Зафиксировать actual public method. Если это raw `CodeDocumentationStudentGeneration.Generate`, он не вызывает исследованный E10: перейти к G4-Student из главы 3. Если это `SemanticCompilerFacade`, записать stack, KNN flags и реальное число training observations. Если это generic capability с HNSW/stored output, сначала выполнить G0 на его памяти. Название домена или наличие класса в solution не подтверждает участие этого класса в ответе.

**Этап L0 — нативная диагностика.** Собрать и запустить подготовленный проект для обоих SHA. Сохранить stdout JSON и exit code, actual SHA checkout, SDK и package versions. Проверить `CSharpQueryDetected`, `QueryStack`, `QueryAction`, `CompletionObservation.OrdinaryTotalPairs`, `CompletionObservation.ConditionalTotalPairs`, `QueryExpectationMatched`, `ControlExpectationMatched`; отсутствие route или пустой prediction не считается PASS. Сравнить исходный/обработанный текст, syntax errors, AST member accesses и action features.

**Этап C2 — один изменяемый фактор.** Оба current facade имеют одинаковые raw TRAIN, k, порядок и остальные flags. У одного `UseRegexPreprocessor=false`, у другого `true`. Никаких изменений tokenizer, LoRA, label generator, корпуса или governor одновременно. Исходниковое предсказание: interpolation-expression исчезнет после E10; unaffected constant control останется в прежнем классе. Native результат может опровергнуть это предсказание либо выявить дополнительный caller/dependency.

**Этап Q — предметный pilot.** Только при подтверждённом обычном потребителе подготовить 12 TRAIN и 12 новых TEST, раздельных по семейству кода, плюс 4 прежних неповреждаемых контроля. Задачи: что вычисляет C# функция, какие реальные обращения/вызовы есть, какое действие требуется. Проверка actual смысла фиксируется заранее и не берётся из `ActionLabelGenerator.Label`. При техническом исправлении C2 меняется только сохранение interpolation AST; RX1 и C3 запускаются отдельными опытами. Оба плеча получают равный учебный бюджет.

**Этап R — восстановление.** После обучения создать новый экземпляр и восстановить тот же получатель. У текущего C# helper без собственного persistent checkpoint повторить Train из тех же frozen raw sources и обозначить это как rebuild. У model/Unit с checkpoint выполнить его реальную загрузку. Если feature schema поменялась, нужен согласованный rebuild train/query, а не новый query encoder поверх старой несовместимой памяти.

## Как принять результат

Доказательство механизма: нативные значения показывают потерю и восстановление конкретного AST/observation сигнала при единственном изменённом факторе. Доказательство влияния на качество: обычный потребитель исправляет новые предметные случаи при независимой оценке и не теряет заранее выбранные правильные контроли. Маленький pilot даёт локальный сигнал; статистическая значимость не подразумевается.

Гипотеза снижается или закрывается для данного сценария, если consumer не вызывает компонент, признаки не меняются, либо меняется только внутренний surrogate label без улучшения финального ответа. В таком случае следующий отчёт должен сохранить отрицательный результат. Больший DPO batch не назначается автоматически.

## Формат конечного отчёта

Достаточно одного `result.json` и короткого `report.md`. В JSON: source refs, actual caller, baseline/treatment state IDs, frozen train/test IDs, единственное intervention, before/after normalized source и features, реальные выбранные example IDs, полные ответы, grades и provenance reviewer, число новых/потерянных правильных, cold/rebuild result, timings, все NOT_RUN/NOT_CALLED. В тексте: что изменилось в алгоритме, один показательный before/after, сработал ли контроль, связь с исходной гипотезой и точный предел вывода.

Первый технический запуск не требует изменения core research-каталога. Результаты и следующий эксперимент сохранять рядом с этим planning пакетом либо в явно согласованной рабочей ветке реализации; исходные результаты других агентов сохраняются.
