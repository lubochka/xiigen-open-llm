## 2. Проверяемые новые гипотезы — не выдавать подозрение за найденную причину

### H44-R1 — Caller loses source-language auto-inference

**Известно по коду:** старый R1 принимает текст без `SourceLanguage`; новый `ResolveDirection` требует код или возвращает ошибку. **Гипотеза:** реальные IDE/user translation запросы, пришедшие со старой формой (особенно mixed-script/HE), теперь либо не доходят до trained translator, либо получают неверное `SourceLanguage` в внешней прослойке. **Влияние на quality:** не подтверждено. **Сферы:** RU→EN, HE→EN, EN→RU/HE; не DPO Student генерация сама по себе, не C# AST. **Отрицательный контроль:** caller всегда корректно задаёт оба ISO кода и нормальный `TopicDomain` — тогда старый R1 не обязан давать прирост. **Проверка:** [Micro-A](44-SMALL-CAUSAL-EXPERIMENTS-BY-DOMAIN-2026-10-19.md#micro-a--r1-source-language-contract-18-синтетических-запросов).

### H44-R2 — Topic-domain supplied versus detected changes learned receiver

**Известно:** старый R2 вычислял topic по словам/подсказке, current Flow принимает caller-provided string, downstream `ExecutorUnit.Execute(tokens,topicDomain)` получает этот параметр ([source L264–293](https://github.com/lubochka/llm_mvp_core/blob/a392b6be8f8dec1e2375e2eb4fe21c2f6e8950c6/27.TranslationDomain/TranslationTrainedUnits.cs#L264-L293)). **Гипотеза:** пустой/общий/неверный `TopicDomain` из caller скрывает релевантный обученный domain memory или меняет verifier/ranker path. **Пока не доказано**, что именно этот параметр меняет итоговый ответ — ему может быть нечего делать в нужном consumer. **Сферы:** EN↔RU технические, медицинские и юридические термины; HE↔EN только с реальными обученными парами; не автоматически все домены. **Контроль:** слово «legal» в цитате не должно превращать весь текст в юридический; пустой inferred topic не должен сам конструировать «правильный перевод». **Проверка:** [Micro-B](44-SMALL-CAUSAL-EXPERIMENTS-BY-DOMAIN-2026-10-19.md#micro-b--r2-topic-domain-contribution).

### H44-R3 — RejectedAdapters & evidence lost at transition to DPO hard negatives

**Известно:** старый `TranslationRoutingDecision` нёс `RejectedAdapters`/evidence, new flow result — нет. **Новая гипотеза:** если прежний DPO builder или logical route-learning materializer действительно потреблял эти поля, перенос мог превратить содержательные *same-prompt* negative candidates в случайные negatives либо потерять teacher metadata. **Важное ограничение:** у источников **пока нет цепочки old `RejectedAdapters` → реально обученные веса/memory → лучшая ordinary translation**. Без неё классификация: `HYPOTHESIS_NOT_CAUSAL_PROVEN`. **Сферы:** multi-adapter translation routing и предпочтения policy, не гарантированно target token-level DPO. **Проверка:** [Micro-C](44-SMALL-CAUSAL-EXPERIMENTS-BY-DOMAIN-2026-10-19.md#micro-c--rejected-adapter-hard-negative-provenance).

### H44-R4 — Flow ID identity drift or removed R2 as serialized behavior

**Гипотеза при наличии старых manifests:** persisted flows с `translation-routing-flow-r1` / `translation-topic-routing-flow-r2` при холодной загрузке могут стать orphaned, несмотря на живой новый `translation-routing-flow`. **Фальсификатор:** ни один реальный artifact/registry/consumer не ссылается на старые ID — значит воскрешать ID не нужно. **Домен:** translation flows/orchestration, не standalone Student. Достаточно 1–2 curated legacy descriptors и один cold load + exact flow trace; не заменять схему вслепую. Связь с сохранением состояния отличается от уже установленной миграции `4→6` executor checkpoint.

## 3. Проверка роли исторических «99%» — предостережение по источнику

Ветка `language_translate` содержит [`Tests/TranslationRoutingFlowTests.cs` L298–335](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/Tests/TranslationRoutingFlowTests.cs#L298-L335), где выбор **direction** оценивается на 50 curated cases с порогом 0.99. Это позитивная проверка R1, но она **не измеряет перевод**. Отдельно [`Tests/TranslatorStreamBatchTests.cs` L1–42](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/Tests/TranslatorStreamBatchTests.cs#L1-L42) называет `structural_accuracy` долю пар `chosen != rejected`, `defect_type` в allow-list и непустые поля. Это **качество структуры набора**, не train/update/inference. Человеческое утверждение об успешном обучении серьёзно и требует реальных получателей и receipts, но эту конкретную проверку нельзя использовать как доказательство semantic quality.

## 4. Независимая проверка и классификация

- **ARCH-READ:** точные снимки и primary links выше, без git cherry-pick/сборки.
- **CODE-EXAM:** вход, old caller R1/R2, new flow, output metrics и интересующий consumer; для H44-R2/R3/R4 call graph всё ещё **OPEN**, поэтому не писать `SOURCE_CONFIRMED_CAUSE`.
- **PLAN-REVIEW:** каждый опыт меняет единственный routing factor, keeping source, learned memory, model, judge, tokenizer constant; targeted deep checks, не Windows matrix.
- **PROMPT-ENG:** одинаковые контрфакты и фиксированное правило качества; DPO отвергнутый вариант должен быть *ошибочным именно для данного prompt*, без утечки expected label через вход.
- **HUMAN COMMUNICATION:** distinction «определили язык», «выбрали домен», «обучили Unit», «улучшили перевод» обязательна в отчётах, иначе ложный PASS.

Никаких новых native запусков в этой исследовательской сессии не было. Новизна H44-R1…R4 означает **конкретный independently identified old→new seam**, а не гарантию отсутствия любой похожей мысли среди сотен прошлых документов.
