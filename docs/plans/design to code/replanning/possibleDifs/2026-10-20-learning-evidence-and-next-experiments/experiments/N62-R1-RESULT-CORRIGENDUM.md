A использует исходное поэлементное сравнение; B — сравнение байтовых диапазонов с сохранением проверок и запасного пути. До и после обучения значения идентичности policy совпадают между A/B. Это реальный зависимый от обучения участок, который нельзя исключать как постороннюю проверку: он вызывается в транзакции обновления и проверяет допустимость её получателя. ### Почему метрика шага не является финальным измерением

В `DpoTrainer.StepVectorCore` reward, margin, loss и accuracy рассчитываются по policy/reference forward, затем выполняются backward и `ApplyOptimizer`, после чего в возвращаемый объект копируются уже вычисленные значения. Следовательно, для второго шага они оценивают модель перед вторым обновлением на второй паре, а не окончательный checkpoint. Сравнение loss первого и второго шага также меняет учебный пример, поэтому не является парной оценкой до/после одного и того же задания. [Код вычисления и порядка операций, строки 881–941](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/11.DPO/DpoTrainer.cs#L881-L941).

Отдельная новая TRAIN-панель уже предусмотрена будущим протоколом для других невыполненных факторов. В текущем индексе и карточке явно запрещено приписывать её старому N62-R1 или повторять завершённый опыт ради неё. Незаписанное финальное измерение остаётся «не измерено», а не нулём. [Карточка, строки 3–13](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/docs/plans/replanning-possible-diffs/experimets/cards/N62-neural-update-costs.md#L3-L13).

## Кандидат в исправления для решения Любы

**N62-R1 — уменьшить стоимость побитовой сверки базы в `11.DPO/DpoTrainer.cs`, `DpoProjectLoraRecipient.RequireValid`.** Кандидат: `MemoryMarshal.AsBytes(...).SequenceEqual(...)` вместо поэлементного LINQ-сравнения, с сохранением всех guard-проверок и исходного запасного пути для непредставимой байтовой длины. На двух обновлениях каждого плеча записаны одинаковые начальные и конечные policy-identities, изменены 16 LoRA-тензоров, база/reference неизменны. Полезные наблюдения: −90 504 выделенных байта; elapsed фазы optimizer −1 494,6625 мс. Все GC-счётчики выросли на один. Причинный и переносимый speedup, финальное качество ответов не установлены. Продукт не изменён; решение о переносе остаётся у Любы.

## Граница проверки источников

Прочитаны JSON `arm-result` и четыре `step-completed` записи обоих плеч, паспорт запуска и отчёт. Git tree фиксирует одинаковые A/B Git LFS-указатели для соответствующих optimizer/policy/RNG checkpoint-файлов; сами бинарные payload в этой проверке не декодировались. Поэтому отчёт опирается на опубликованные identities и readback receipts, не заявляет нового независимого восстановления модели. Аналогично `comparison.json` некоторых соседних опытов — LFS-указатель; пересчёт чисел в настоящем пакете выполнялся по доступным arm raw.

**Обязательное правило для любого продолжения:** при «заканчивай и переходи» немедленно перейти к назначенной следующей задаче, не дописывая предыдущий отчёт, реестр, hashes, review или повтор. При «остановить всё» прекратить работу; сохранённые результаты не удалять. Настоящее уточнение не назначает запуск N62-R1 и не расширяет текущую документную задачу до production.
