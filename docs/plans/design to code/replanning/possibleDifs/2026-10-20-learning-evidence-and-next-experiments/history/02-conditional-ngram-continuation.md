# Условная новая гипотеза: E07 накапливает переходы, но забывает общую частоту для fallback

Идентификатор для crosswalk: `HIST-E07-GLOBAL-01` — согласованность накопленной статистики E07. Дата: 20.10.2026. Статус: обнаружено в исходном коде; влияние на качество не измерено. Это **вторичная условная гипотеза**, исключённая из текущей очереди запуска до появления реального накопительного потребителя. Основные обучающие блокеры RP01 имеют приоритет.

## 1. Что именно найдено

В `MultidimensionalNGram` таблицы `_trans` и `_bigram` являются полями объекта. [Train:283–303][train] добавляет к ним наблюдения и не очищает прежние. Однако `globalNextCounts` создаётся заново внутри каждого Train; [строки306–307][train] заменяют `_mostFrequentNext` модой **только последнего** блока. [Predict:310–322][predict] читает накопленную историю для знакомых контекстов, а для нового BPE-контекста — этот последний-block fallback.

Следовательно, при двух вызовах Train на одном экземпляре разные ветки одного predictor используют разные окна истории. Возможный эффект — потеря ранее доминировавшего общего fallback после маленького нового блока при сохранении старых переходов в других ветках. Это не вопрос точности floating-point, не потерянный AST offset, не сброс optimizer и не замена kNN-памяти методом `Clear()`.

Точные поля и методы кандидата: `35.ExperimentsV2/Experiments/E07StructuralContextToken.cs`, класс `MultidimensionalNGram`, поля277–279, метод283–308, reader310–322. Файл прочитан полностью, включая конечный `BigramFallback`, возвращающий `_mostFrequentNext`. В current `883496bca18113bf37e0afe683c75b05a0075048` и соседней PrepareToGPL `31346d8928be4469b01aaf313780e8f950ff91e2` он имеет один blob `a7ec490fbcc3459cce481bf65cbf134903712de2`.

## 2. Почему это сейчас не причина исторической неудачи

В [E07StructuralContextToken.Run:87–90][single] создаётся новый `MultidimensionalNGram`, затем Train вызывается один раз. [ExperimentRunner.DispatchE07:263–267][dispatch] также создаёт новый E07 runner для каждого вызова. Этот проверенный путь не выполняет два Train на одном состоянии. Прямой RP01-потребитель `MultidimensionalNGram` не установлен.

Поэтому гипотеза **не объясняет** опубликованные отрицательные single-run метрики E07 и не объясняет RP01 Student. Предлагать её первым экспериментом было бы подменой текущей задачи. Обнаружение метода, который технически допускает повторный вызов, само по себе не доказывает существующий рабочий сценарий такого использования.

Допуск к исполнению: найти или явно назначить настоящую задачу накопительного обучения этой таблицы, сохранить конкретный caller и две его операции Train на одном объекте. Если Train по контракту должен заменять состояние, нужен другой однофакторный опыт с согласованным сбросом **всех** таблиц; накапливающий вариант нельзя выдавать за единственно верное исправление. Сейчас выбран только исследовательский вопрос о накопительном режиме, без изменения продуктового контракта.

## 3. Конкретный вариант исправления для накопительного режима

В экспериментальной копии класса перенести счётчик `globalNextCounts` из локальной переменной в поле `_globalNextCounts`. Каждое принятое наблюдение увеличивает его так же, как `_trans` и `_bigram`; `_mostFrequentNext` вычисляется из всей этой таблицы. Не менять ключ контекста, codec BPE/AST, fallback-иерархию, tie-break и размер корпуса.

Состояние после такого изменения состоит из трёх таблиц с одинаковым накопительным временем жизни: структурные переходы, bigram-переходы, глобальные частоты следующего токена; `_mostFrequentNext` — производное значение. Если позднее появится сохранение/восстановление именно этого learner, все три таблицы должны сохраняться совместно. В прочитанном классе собственного checkpoint API нет; документ не приписывает ему существующий restore-path.

Кандидат оригинального изменения ограничен указанным методом и полями E07. Перенос в исходник разрешает пользователь отдельно после опыта. Здесь исходник не менялся.

## 4. Минимальная учебная проба: проект реализации, не готовый запуск

**Точное место:** существующий проект [35.ExperimentsV2/ExperimentsV2.csproj][host], TargetFramework `net9.0`; новые experiment-only файлы в `35.ExperimentsV2/Experiments/Rp01Micro/HistE07Global01/`. Не создавать новый product/runner project, не менять текущие E07 results и protected cards. Изолированный `Run()` должен создавать fresh A и B, вызывать настоящую скопированную Train-логику, читать actual learned state через Predict и возвращать per-step JSON. Имя планового класса `HistE07Global01Experiment`, метода `Run`; сейчас ни класс, ни CLI entry не созданы. Это описание реализации, а не утверждение о наличии команды запуска.

**Модель:** текущая модель исполнителя по умолчанию; переключение модели не требуется. Обучаемый объект — таблица E07, без neural checkpoint, внешнего teacher и DPO-генерации. Язык отчёта — русский; имена полей JSON — английские для машинной проверки.

**Основной учебный контраст:** A — неизменённая текущая реализация; B — только общий накопительный счётчик. В обоих экземплярах последовательно подать два блока `StructuralToken` с одинаковыми `AstNodeType=0, AstDepth=0`:

```text
Block A: BpeId = [1, 2, 2, 2, 2, 2]  → 5 переходов с next=2.
Block B: BpeId = [3, 4]              → 1 переход с next=4.
Unseen queries: currentBpe = [99, 100, 101], AstNodeType=0, AstDepth=0.
Known controls: currentBpe = 1 and 3, AstNodeType=0, AstDepth=0.
```

Эти числа — типизированная диагностическая учебная фикстура, **не реальные результаты BPE/Roslyn на C#**. Она измеряет сохранность learned global statistics; её успех нельзя называть ростом качества C#-генерации. Если нужен вывод для C#, следующий этап должен использовать настоящий frozen tokenizer и корпус/переходы соответствующего caller. Этот этап не добавляется автоматически.

До обучения снять ответы на все пять запросов. После первого блока повторить те же запросы; после второго — снова. Сохранить число реальных Train, принятых переходов, размер таблиц и ответы. Ожидаемое по исходнику, ещё не измеренное: после первого блока обе руки возвращают `2` для unseen; после второго A возвращает `4`, B — `2`. Знакомый `1` сохраняет ответ `2`, новый `3` получает `4` в обеих руках. Это делает видимой связь **уроки → изменение состояния → ответ обученного predictor**. Одна арифметическая симуляция без этих Train/Predict не является выполненным экспериментом.

**Контроли:** повторить два блока в обратном порядке на новых A/B; суммарное число переходов и глобальная мода одинаковы, поэтому cumulative fallback должен быть инвариантен порядку при отсутствии ничьей. Отдельно один Train — A/B должны совпасть. Не использовать простую конкатенацию блоков как «равное обучение»: она добавит искусственный переход между границами. Пустой Train не должен создавать новый переход. При ничьей сохраняется текущий выбор, отдельный tie-policy не внедряется.

**Полезные показатели:** доля unseen-запросов с fallback, согласованным с глобальной модой всех принятых переходов; сохранность знакомых переходов; усвоение переходов второго блока; время двух Train; память трёх таблиц; все регрессии по тем же запросам. Любое измеренное улучшение полезного показателя считается успехом по этому показателю и предмету проверки; рост точности другого показателя не обязателен. Вспомогательная проверка количества таблиц не заменяет чтение обученного predictor.

**Бюджет:** основной контраст — четыре вызова Train всего, 30 Predict (по пять запросов × три состояния × две руки), 12 обработанных переходов по двум рукам, ноль optimizer updates и ноль генераций нейронной модели. Обратный порядок и single-Train контроль — дополнительные отдельно учитываемые диагностические ветви. Не запускать все E01–E53 и не запускать полную CI-цепочку для этого вопроса.

**Состояние запуска:** команда запуска сейчас не объявляется готовой. Такой micro-entry ещё не существует, а проверенный E07 runner нужный повторный Train не вызывает. Реестр обязан оставить эту запись вне активной последовательности с причиной «нет установленного накопительного caller и реализованного entry». Это не блокер текущего аудита и не приглашение исполнителю искать, куда положить новый project. При отдельном включении опыта автор карточки добавляет точную существующую команду entry после его реализации и возвращает карточку на проверку; до этого модель не тратит токены на попытки запуска.

## 5. Обязательное поведение исполнителя

Применить `docs/skills/code-examination-SKILL.md`, `experiment-design-SKILL.md`, `learning-path-audit-SKILL.md`, `plan-review-SKILL.md` и `human-readable-architecture-audit-SKILL.md` с приоритетом текущих 14 правил пользователя. Старые требования обязательного роста accuracy, автоматического перехода на большой Tier, полного исправления product/tests и немедленного merge не применяются к этой диагностике.

Запрещено продолжать предыдущий опыт после указания перейти к следующему. При явном «остановиться» работа прекращается немедленно, без дополнительных команд и без попытки «дописать полезный отчёт». При «следующий эксперимент» немедленно перейти к назначенному реестром ID в разрешённой фазе; не дописывать прежний статус, отчёт, реестр, hashes или review, не возобновлять старый опыт и не исправлять ему tests или product. Исторические результаты и старые попытки сохраняются. Новый attempt допускается только после явного назначения его буквального ID в реестре; исполнитель не выбирает его сам. Существующую папку не удалять ради повторного запуска. Если запуск не начал обучение, писать «обучение не началось», а не отрицательную метрику качества.

После измерений создать русский отчёт с фактическим caller, before/after, per-query ответами, изменениями всех метрик и точной предлагаемой дельтой оригинального кода. При полезном выигрыше — кандидат исправления, решение о переносе остаётся у пользователя. Сейчас этот раздел не выдается исполнителю как активный work order.
