# Проверка покрытий и качества экспериментов — 20 октября 2026

## Вывод по актуальному состоянию

На `llm_mvp_core@f5dd532045716495a2c7668573250e5d7cc46810` снята общая блокировка карточек: исполнитель сам выбирает и подготавливает маленький опыт в пределах порученной программы. Не требуется отдельное согласование каждого ID, пути, SHA или заполненного паспорта. Для нового обучения сравниваются A до/после и B до/после; для загрузки, восстановления и использования обученного результата допустим один доказанно обученный state и одинаковая панель до/после конкретного исправления. Название `serving` или `cold` не является основанием исключать зависимое звено. Это соответствует пункту 4 текущего запроса пользователя. [Действующее правило, строки 3–35][policy]

Этот документ — аудит проектов и исходников. Новых запусков обучения здесь нет. Причина — предмет текущего прохода, а не отсутствие повторного разрешения на каждую карточку. Технические недостающие сведения описываются как подготовка исполнителя; внешний блокер нельзя объявлять по одному незаполненному полю.

### Почему появились два снимка

Начальный аудит был привязан к core `bf9b543e149ef197da85a767821d98c9b67916d2`. Во время работы обнаружены три новых коммита до `f5dd532045716495a2c7668573250e5d7cc46810`: 152 изменения только в protected-документах, без изменений `.cs`/`.csproj`. Все 152 файла отдельно загружены и сверены по Git blob SHA. Старые результаты сохранены как история, новые выводы относятся к последнему снимку. [Точное сравнение коммитов][compare]

В старом снимке 125 карточек имели паспорт `NOT_EXECUTABLE_AS_IS`, а 22 новых Markdown не были упомянуты по имени. Эти числа **не являются текущим списком блокировок или пропусков**. Latest N60 добавил E1/E2, подробный смысловой crosswalk и все 22 адреса; общие approval-gates отменены. Актуальное покрытие имён — 555/555. Наличие ссылки не доказывает, что рецепт готов или измеряет правильную причинную цепочку. [Latest N60: соответствия и источники][n60-map]

## Различать активный проект и архив вариантов

P01–P125 остаются историческими карточками вариантов. Нельзя превращать все их профили, старые большие бюджеты и диагностические подслучаи в обязательную очередь. Для выбранного фактора исполнитель оформляет конкретный маленький паспорт и продолжает работу. Действующий README отделяет D/LoRA от обучаемых C/T/O Units: успех памяти переводчика не отвечает на вопрос о нейронном Student. [README][readme]

Общее правило успешно перенесено во все 125 карточек и 133 промпта: любой **измеренный** полезный сдвиг признаётся успехом по конкретной метрике и домену; рост accuracy не обязателен; ухудшения записываются рядом. Это текстовая проверка полноты правила. Она не отменяет содержательную проверку выбранного вмешательства, данных и счётчиков вызовов.

P86 использует буквенные `P86.a` и `P86.b`, тогда как часть матриц называет их `P86.1` и `P86.2`. В машинном реестре сохранены aliases; два случая не объявлены потерянными гипотезами. Это навигационное уточнение последнего приоритета.

## Приоритетные содержательные результаты

### 1. D/LoRA: подготовить настоящий малый обучающий путь

Карточка D явно перечисляет недостающие конкретные поля: один repair factor, bounded native caller, байты уроков/экзамена, точный B0, optimizer/RNG и output/команда. Это задачи подготовки, а не повод повторно спрашивать пользователя о каждой строке. Существующий RP01 runner не становится двухурочным от названия `micro-paired`: такой режим должен быть реализован над настоящими владельцами обучения с сохранением admission/capability и checkpoint identities. [Карточка D][d]

Latest N60 уже содержит четыре разные нейронные постановки. Их нельзя объединять в один A/B:

| Постановка | Единственный фактор | Планируемая фактическая работа |
|---|---|---|
| SFT RESPONSE MASK | Вклад prompt targets при неизменном знаменателе `T−1` | 4 настоящих SFT updates всего; при выбранной панели 16 собственных генераций |
| SFT MOMENT CONTINUITY | Сброс/перенос `m/v/step` перед вторым уроком при fixed LR | 4 SFT updates; тот же общий экзамен |
| DPO VALID LENGTH | Вычисляемый padded tail при тех же IDs/masks/objective | 4 DPO updates, 16 внутренних forwards, 8 backwards; основной ресурсный опыт без Generate |
| DPO/SFT ORDER | Порядок стадий при фиксированном R0 и двух optimizer states | 2 DPO + 4 SFT optimizer calls; 16 генераций на четыре состояния |

Для ресурсного PAD отсутствие генераций корректно: accuracy обозначается `NOT_MEASURED`, экономия actual update оценивается самостоятельно. Ресурсная польза не требует доказать прирост ответов. Сравнение post-return gradients недостоверно, если они уже очищены; наблюдатель должен читать их внутри тех же actual steps. Положительная/нулевая дельта остаётся результатом, а отсутствие заявленного native пути — проблемой достижения механизма. [Latest нейронные проекты][neural]

### 2. T query-context: допустимое использование выученной памяти, с узкой атрибуцией

В T обе стороны записывают одинаковые две записи `ContextualDictionary.AddEntry`; A передаёт пустой query-context, B — фактический POS. Следовательно A/B различает **чтение обученной таблицы**, а не усвоение разных уроков. По действующему правилу это допустимо при названном owner и зависимости ответа от таблицы. Прежний предварительный вывод «query-only всегда invalid» отозван. [T, строки 58–92][t]

Остаётся ограничение: производственный caller, который действительно теряет POS между обучением и рабочим TranslationExecutor, в этой карточке не установлен. Из результата нельзя делать вывод «исправлена потеря POS в RP01». Дополнительный T-TRAIN-CONTEXT, где отличаются **записываемые** контексты при одинаковом query, — самостоятельный вопрос о приобретении признаков; он не запрещает и не заменяет consumer-постановку.

### 3. N60-E1: новые строки уже покрыты, но выбранные markers не создают требуемый контраст

Latest E1 правильно исследует `BuildGeneralBatch → QualityVerifier.TrainOnExample → Verify` и прямо ограничивает вывод уровнем Verifier. Это настоящее обучение памяти Unit, даже если кандидаты экзамена фиксированы: измеряется собственное решение реально изменяемого Verifier, а не офлайн пересчёт чужой таблицы. [E1][e1]

Однако V1 `Он быстро открыл дверь.` не даёт требуемого source marker в текущем коде. `быстро` отсутствует в allowlist и не подходит под suffix-ветви ADV. При наличии RU rule tags fallback также не принимает его: нормальное кириллическое окончание `о` в `LooksLikeMannerMarker` отсутствует. Поэтому удаляемый в B false-negative V1 не создаёт intended learned requirement даже в A. V2 содержит `окно`: это слово, наоборот, попадает в широкий ADV суффикс `но`, поэтому marker может оказаться `окно`, а не `тихо`. [Tokenizer allowlist и классификация][tokenizer]; [marker writer/reader][marker]

Это статический вывод об условиях рецепта, не новое измерение и не утверждение, что `TrainOnExample` не вызывается. Внешние вызовы могут выполняться при отсутствии нужной записи. **Исправление проекта:** заменить только материал на уже распознаваемые `бесшумно` и `громко`, избегая `окно` как побочного ADV. Сам runtime marker-код в этом A/B не менять: иначе admission смешается со вторым фактором N57. Полная маленькая карточка, точные строки и промпт записаны в `10-CURRENT-EXPERIMENT-OVERLAYS.md`.

### 4. N60-E2: вопрос покрыт, отсутствует конкретный writer/state/reader контракт

Latest E2 уже отличает learned source support от статического SourceLaw и уменьшает материал до двух уроков/четырёх задач. Поэтому H2 не объявлен отсутствующим экспериментом и не получает новый независимый ID. [E2][e2]

Но «versioned operator/role/order slots» ещё не задаёт алгоритма: откуда берутся slots, что пишется при Train, как это читает обычный Executor, что происходит при переходе на wordmap/kNN. Только отказ phrase composer недостаточен: `Execute` затем может вернуть тот же смысл через иной маршрут. Дополнение `10-CURRENT-EXPERIMENT-OVERLAYS.md` задаёт один проверяемый вариант — выученные порядковые spans и шаблон их полного покрытия, общий reader до выбора ветви. Это proposal, не существующая API и не знание отрицания, выученное из двух положительных примеров. Польза отказа на неподдержанном входе измеряется отдельно от полноты перевода. [Train/Execute/phrase composition][executor]

### 5. Присланное улучшение ingress уже внедрено

`required-changes.md` фиксирует существующее внедрение `phrase_mappings` из корпуса в Executor memory. Приведённые там 11/24→19/24 и false accepted 1→3 — исторический результат обучаемой TranslationMachine, не текущий новый run и не neural Student. Повторная реализация того же ingress не нужна; новые гипотезы должны менять другой доказанный участок. Весь архив receipt этого опыта в настоящем подаудите повторно не воспроизводился. [Required changes][required]

## Что нельзя объявлять закрытым

Полный инвентарь и 555/555 ссылочных имён не равны полной проверке всех причинных утверждений. Некоторые H60 feedback-связи требуют обнаружить настоящий последующий writer; E2 требует реализуемого контракта; нейронные проекты требуют подготовить native bounded host и исходное состояние. Последний N60 честно сохраняет эти условия. Само слово `OPEN` не означает, что пользователь должен искать артефакт или что независимая готовая работа останавливается.

Подтверждённые прежние идеи не дублируются: homograph language-key уже P51.8; индекс следующего Executor-урока после learned tokenizer correction уже P106.4; ошибочный accepted→будущий lesson уже N59-L02 с неподтверждённым feedback caller; scorer с новым tokenizer уже P57.13. Содержательное сопоставление 22 поздних файлов приведено в `source-22-semantic-crosswalk.json`; там отдельно обозначены проекты, приоритеты, методика и исторические свидетельства.
