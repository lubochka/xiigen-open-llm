# Маленькие эксперименты и поручение на один выбранный механизм

## 1. Как выбрать первый опыт

Если цель — **вернуть поведение известной успешной ветки**, начинать с [главы00](00-RESTORE-DESIGNTOCODE-CLEAN-FIRST.md), где источники и получатели сопоставлены с `DesignToCode-clean`. При жалобе на собственный ответ нейронного Student первым идёт ДР-Н. При восстановлении старого структурного поиска — ДР-С либо обучение классификатора E25. Положительный результат памяти не закрывает отрицательный результат другого learner.

Ниже — меню адресных проверок. Выбирается **одна** строка, один предметный профиль и один меняемый механизм. Все строки не являются обязательными воротами. Уже выполненные расчёты исходных формул приложены к главам01–03; предложенные здесь native вызовы, обучение и оценка собственных ответов в этой работе **не выполнялись**.

## 2. Карточки шести новых проверок и двух конкретизаций

| Check и источник | Самая быстрая различающая проверка | Единственное предлагаемое изменение B | Четыре новых предметных случая и условие успеха |
|---|---|---|---|
| **N-K1 — объектные местоимения**, [глава01](01-NEW-LANGUAGE-AND-KNN.md) | Четыре размеченные промежуточные строки при фиксированном `IMPERATIVE_VS`; исходный фильтр удаляет все PRON | Удалять только отдельно размеченное подлежащее; неизвестная роль даёт явный diagnostic status | Перевод в профиль с целью SVO: два новых случая с объектом/получателем PRON и два контроля. Сохранены действующее лицо, объект, получатель и финальный смысл; parser и classifier не меняются |
| **N-K2 — целая именная группа**, [глава01](01-NEW-LANGUAGE-AND-KNN.md) | На правильном VSO проверить `old server`: текущий single-token move меняет связь определения, даже когда IsSVO=true | Перемещать независимую subject span целиком; внутренний порядок сохраняется | Два новых составных подлежащих и два однословных контроля. Сохранилась связь определения с нужным существительным; ручной span не объявлен возможностью обычного parser |
| **N-K3 — While/Do в метке следующего метода**, [глава01](01-NEW-LANGUAGE-AND-KNN.md) | Пять KindBag API-входов; заранее определить, включает ли контракт Loop все четыре вида циклов | Добавить While/Do в тот же Loop branch, сохранив порядок остальных веток | Четыре новых запроса к одной frozen памяти с ≥4 существующими парами, поверх которой добавлены два урока. Измерять голоса следующего метода и `PredictedNextMethodType`; смысл полного объяснения только при найденном reader этого поля |
| **U-DTC-1b — разные признаки evaluator/runtime**, [глава02](02-NEW-LEARNED-DESIGN-STATE.md) | Один checkpoint, четыре интерфейса; одновременно снять feature maps и обе оценки. Новое обучение не нужно | Для проверки качества использовать тот же обычный consumer; добавление общего encoder — отдельный последующий опыт | Два визуальных дефекта и два допустимых макета с одинаковым source kind. Результат — установлена достижимость/недостижимость выученного признака; feature-fit score сам по себе не является visual accuracy |
| **U-DTC-3 — округление при продолжении**, [глава02](02-NEW-LEARNED-DESIGN-STATE.md) | Два одинаковых урока после одного checkpoint: warm против cold между уроками; сравнить accumulator | В отдельном C сохранять достаточную сумму/residual с версией формата; остальные поля не менять | Четыре новых интерфейса, реально читающих изменяемую correction category. Успех качества требует изменения полезного выбора; разность `10^-6` без изменения ответа — только state drift |
| **N-ADJOINT-01 — backward scalar/SIMD**, [глава03](03-NEW-NUMERICAL-DELTA.md) | Сначала captured реальные operands/upstream current против clean scalar и FP64 reference, без updates | Меняется только gradA reduction в MatMul; forward, gradB, moments и остальные kernels фиксированы | Один выбранный neural профиль: два урока, четыре новых ответа. Предметный A/B только при установленном влиянии на effective update. Считать правильность, критические ошибки, время; побитовая разность сама по себе не успех |
| **U-DTC-1a — подтверждение N54: пара не меняет Critic deltas**, [глава02](02-NEW-LEARNED-DESIGN-STATE.md) | Перестановка сторон только в искусственной diagnostic fixture при одном prompt; сравнить margin и signals | Для предметного опыта сначала конкретизировать pair-conditioned critic representation; это новый контракт, не готовая однострочная правка | Два корректных урока о видимости/доступности элемента, четыре новых макета. Проверить обе реальные candidate scores и решение. Перевёрнутые заведомо неверные пары не подавать в admitted learning |
| **U-DTC-2 — конкретизация N54: отрицательное правило в fallback**, [глава02](02-NEW-LEARNED-DESIGN-STATE.md) | На одном state `contrast=+1, spacing=−1` сравнить available={contrast,spacing} и available={spacing} | В том же применимом scope не исполнять явно отвергнутое правило; если полезного действия нет, сохранить кандидата и запросить другую коррекцию/QA | Два тесных мобильных макета, desktop-контроль с полезным spacing и случай без дефекта. Уменьшились вредные изменения при сохранении полезных; глобальный negative weight не превращается в вечный запрет |

Для N-K1/N-K2 сначала достаточно механической проверки заданной структуры. Чтобы заявить влияние **на обучение**, поверх одного и того же исходного состояния нужны два разрешённых урока и обычные ответы на четыре новые задачи до/после в обоих вариантах. Если полезное изменение видно только на ручных POS/spans, записать именно этот предел. Реальный parser, источник аннотации и полный ordinary path остаются самостоятельным условием переноса.

N-K3 проверяет текущую систему меток, уже существующую в clean. Если Loop по исходному контракту означал только for/foreach, результат — проверка расширения задачи, а не найденный дефект. При памяти меньше четырёх пар отсутствие facade prediction не доказывает ничего о While/Do; использовать уже разрешённую память с подходящим размером, а не добавлять фиктивные уроки ради порога.

## 3. Одинаковые условия и честный бюджет

Для каждого A/B сохранить один initial state, точные lesson bytes, tokenizer/source encoder, seed и RNG state, порядок уроков, actual optimizer updates, допустимые параметры, reference, decoder и один EXAM. Изменять только операцию из выбранной строки. Если вмешательство по смыслу меняет схему представления или Unit contract, явно назвать зависимость; не обещать независимость факторов, которой нет.

| Объём | Сколько обычных ответов |
|---|---:|
| 4 EXAM × A/B × до/после | 16 |
| Те же четыре после cold restore в обоих плечах | +8 |
| A/B до/после/restore при едином доказанно общем baseline | 20 вместо 24 |
| Дополнительные 2 retention × A/B × до/после/restore | +12; для численного опыта полный бюджет 36, либо 30 при общем baseline |

Retention можно не расширять отдельной новой панелью, если четыре выбранных EXAM уже содержат релевантные старые контроли; это решение фиксируется **до** просмотра ответов. Численный план главы03 предлагает дополнительные два старых случая, потому что смена optimizer trajectory способна задеть другую способность. Это бюджет одной выбранной проверки, а не требование повторить её во всех доменах.

Не требуются новый корпус500, полный Windows CI или повтор всей матрицы. Небольшой опыт отвечает локальному причинному вопросу. Ноль улучшений после двух updates — `NO_OBSERVED_GAIN` данного бюджета и состояния; это не доказательство, что DPO/LoRA в принципе не способны выучить задачу.

## 4. Предметная оценка

Для **программирования и документации** оценивать условие ветки, порядок побочных эффектов, null/exception и соответствие исходному коду. Для **перевода** — агента, объект, получателя, отрицание, модальность и связи внутри именной группы; EN→RU и RU→EN — разные профили. Для **дизайна интерфейсов** — сохранение видимых и доступных элементов, отсутствие overflow/нового дефекта, полезное HTML/CSS-действие. Для **оркестрации** — допустимый инструмент, предусловия, порядок и использование реального сохранённого результата.

Четыре новых случая должны отличаться от уроков по содержательному исходнику/комбинации, а не только ID. Голос kNN, learned weight, loss, reward margin, счётчик обновлений, feature-fit и принятое решение сохраняются отдельными полями. Принятые неверные ответы, abstention и coverage видны рядом с числом правильных: увеличение числа выданных ответов может одновременно добавить ошибок.

Финальные ответы A/B передаются независимому оценщику в скрытом порядке. Ответы нельзя выбирать заново после просмотра их оценок. Если нужен недетерминированный decoder, одинаковая последовательность seed задаётся заранее; один случайный удачный вывод не считается эффектом обучения.

## 5. Роли и готовые поручения

Эта глава задаёт будущие роли. Она не удостоверяет фактические вызовы моделей в нынешнем исследовании. **CODEX с запрошенной `Astra 6 UltraCode` выбирает урок как человек; внешняя открытая китайская модель создаёт обе стороны; отдельный CODEX с `Astra 6 UltraCode` независимо проверяет точную пару.** Фактические model identifiers, параметры и provenance записываются из исполненных вызовов. Если запрошенная модель недоступна, указать это, не подменять её имя фактической моделью. Историческое авторство архивных уроков сохраняется.

### Поручение CODEX: выбрать два урока

```text
Цель: проверить один выбранный механизм из главы00 либо карточки главы05.
Назови тему, профиль, конкретного learner и обычного consumer.
Зафиксируй два учебных намерения, где ошибку вызывает именно этот механизм.
Для каждого укажи исходный материал, требуемое умение, допустимый контекст
и одну содержательную ошибку rejected. Не создавай chosen/rejected сам.
Сформируй четыре непересекающихся EXAM и rubric; не передавай EXAM учителю.
Укажи единственное различие A/B, current/clean source ссылки, checkpoint
и событие, которым гипотеза опровергается. Выбери один домен для первого опыта.
Передай только TRAIN-намерения внешней открытой китайской модели.
```

### Поручение внешней модели: создать обе стороны пары

```text
Для каждого переданного TRAIN-намерения создай одну точную DPO-тройку:
prompt, chosen, rejected. Обе стороны — твой вывод.
Сохрани одинаковый вопрос и формат. Chosen должен решать предметную задачу;
rejected должен содержать одну правдоподобную содержательную ошибку,
связанную с указанным учебным намерением, без слов-маркеров правильности.
Не используй недоступные факты. Если контекста недостаточно или контраст
нельзя построить честно, верни INSUFFICIENT_CONTEXT и объясни причину.
Отдельно укажи rationale и provenance. Не включай их в обучаемый ответ,
если контракт learner их не требует. Не меняй prompt между двумя сторонами.
```

### Поручение отдельному CODEX: проверить пару

```text
Ты независимый оценщик точной пары и предметного исходника.
Не изменяй lesson bytes во время оценки и не используй имя модели как довод.
Проверь корректность chosen, конкретную ошибку rejected, сопоставимость сторон,
отсутствие подсказок меткой/ID и достижимость различия выбранным learner.
Вердикт: PASS / TIE / BOTH_BAD / REVERSED / INSUFFICIENT_CONTEXT.
Дай короткую предметную причину и привяжи receipt к hash точной тройки.
Если пара не PASS, верни задачу её автору; не создай новую пару незаметно.
Новая редакция должна получить отдельную оценку своих точных bytes.
```

### Поручение исполнителю одного A/B

```text
Исполни только выбранную карточку и её необходимую проверку достижимости.
Используй существующий разрешённый Machine/Unit/Flow API и настоящий checkpoint.
Не обходи admission и не подменяй trained state флагом или готовым ответом.
Сохрани исходные lesson hashes, actual consumer trace, state before/after,
raw ответы, независимые оценки, время и только нужные диагностические метрики.
Сравни единственный фактор; все остальные условия запиши как совпавшие
либо укажи конкретный confound. Прекрати расширение, если trigger недостижим
или под выбранным бюджетом полезного эффекта не наблюдается.
Не запускай автоматически остальные карточки, полный CI или новый корпус500.
```

## 6. Достаточный результат маленького опыта

Отчёт должен отвечать на четыре вопроса: дошёл ли урок до нужного состояния; прочитал ли его обычный получатель; стало ли полезное поведение лучше на новых случаях; сохранилось ли оно в выбранном режиме продолжения. Числа приводятся со знаменателями и raw ответами. При расхождении только внутреннего состояния итог — `MECHANISM_OBSERVED / QUALITY_EFFECT_NOT_OBSERVED`. При отсутствии нужного runtime пути — `NOT_REACHED_ON_THIS_PATH`. При улучшении — `LOCAL_QUALITY_GAIN` с перечислением конкретных случаев и ограничений, без вывода о всей системе.

Для восстановления clean дополнительно требуется сопоставимый исторический получатель и установленное донорское отличие. Контроль «current учится против current без updates» проверяет learnability; сам по себе он ещё не доказывает, что вернулся именно исторический алгоритм.
