## Точные значения аргументов: разные CLI не смешивать

Следующие схемы раскрывают обозначения таблицы. Во всех `A` выполняется один раз перед `B`; nonzero exit прекращает текущий attempt и не запускает следующий arm. Исходные restore/build, logging, create-new intent, phase-issued/completed и failure guards из ссылок таблицы сохраняются. Это не разрешение вызвать ещё не материализованный host. Ни одна схема не запускается автоматически в документной сессии.

- **V** (№04–07,24,30): исходные `dotnet build "$H/Runner.csproj" -c Release -p:Variant=A`, затем тот же build с `Variant=B`. Для имени assembly из таблицы: `dotnet "$H/bin/A/Release/net9.0/<Assembly>.dll" --arm A "$R/A"`, затем `dotnet "$H/bin/B/Release/net9.0/<Assembly>.dll" --arm B "$R/B"`. Пример для №04: Assembly ровно `N62Runner`, а не ID опыта.
- **P** (№18–21): те же два Variant build; compiled-A exe принимает `--prepare "$R"`, затем A exe `--arm A "$R/A"`, B exe `--arm B "$R/B"`, затем compiled-A exe `--summarize "$R"`. Exe — `$H/bin/A/Release/net9.0/<Assembly>.dll` и соответствующий B из таблицы. Prepare/summarize не добавляют learner calls.
- **Q** (№31): один scoped build `$H/Runner.csproj` с `ImportDirectoryBuildProps=false` и `ImportDirectoryBuildTargets=false`. Один exe `$H/bin/Release/net9.0/MkScopeRunner.dll`: последовательно `--prepare "$R"`, `--arm A "$R/A"`, `--arm B "$R/B"`, `--summarize "$R"`.
- **U** (№13): исходный scoped build; один exe `$H/bin/Release/net9.0/N60E1VerifierAdmission.dll`, последовательно **`--arm A --output "$R/A"`**, затем **`--arm B --output "$R/B"`**. Здесь явный `--output`, в отличие от V/P/Q.
- **K** (№22–23): исходный scoped build; один exe `$H/bin/Release/net9.0/KhCostRunner.dll` или `KhExtRunner.dll` согласно строке, последовательно `--arm A "$R"`, затем `--arm B "$R"`. Оба получают **одинаковый parent R**, не R/A; native markers/arm files уже различаются.
- **M** (№15–16): исходные build с `Contrast=RETENTION|IDENTITY` и `Arm=A|B` из соответствующей строки рецепта. Exe A — `$H/bin/<назначенный Contrast>/A/N61Mode1Runner.dll`; аргументы `--contrast RETENTION --arm A --output "$R/A"` для №15 либо `--contrast IDENTITY --arm A --output "$R/A"` для №16. B — одноимённый exe в B, `--arm B --output "$R/B"`. Между `A` и assembly **нет** `Release/net9.0`.
- **C** (№26–27): исходные два Variant build, затем ровно compiled-A controller: `dotnet "$H/bin/A/Release/net9.0/<Assembly>.dll" run-pair --peer "$H/bin/B/Release/net9.0/<Assembly>.dll" --fixture "$H/<fixture из таблицы>" --attempt 0001`. Public CLI остаётся таким; **новый R назначается внутри будущего controller**, а не дополнительным несуществующим `--out`. Его private run-arm получает только разрешённые новые arm paths. Для BW01 controller сам делает четыре arm/domain процесса; самостоятельно удваивать их нельзя.
- **W** (№28–29): последовательно исходные SDK/intent/restore/build команды из L98–121 или L86–109; `WikiProbe.csproj`, локальный `NuGet.Config`, `-o "$H/bin"`. Один и тот же exe `$H/bin/WikiProbe.dll` запускается сначала `--arm A --output "$R/A"`, затем `--arm B --output "$R/B"`. В исходном PowerShell блоке заменить и `$wikiAttempt`, и оба абсолютных output literals на R; сохранить issued/returned и stderr/stdout receipts.

## Что именно меняется в будущей копии

1. **Только литералы расположения результата:** shell/root constants, controller Study/root, Program expected-path guard, immutable request DTO, checkpoint output root, log/report/candidate links. В экспериментальном manifest новые будущие файлы описываются после их подготовки; старые hashes/receipts не пересчитываются и не подменяются. Input/model/source paths и authority checks не меняются. Для №18–21 public `--prepare/--arm/--summarize` проверяет новый R; для №18/19/21 также точечно меняется разрешённый root экспериментальной `EvaluateResearch`, которая читает final candidate.
