# Текущие KNN, Unit, DPO-проекции и восстановление: что есть и где расходятся механизмы

**Проверенный код:** `lubochka/llm_mvp_core@0b76ab950d82534f5904005dda096545505ae307`. **Статус:** read-only source audit, 20.10.2026. Новых обучений/генераций не запускали; текущая RP01 причинность ни одной строкой не объявляется без его runtime receipt. Положительная история разобрана в [01-HISTORICAL-KNN-AND-POSITIVE-EVIDENCE.md](03-HISTORICAL-KNN-AND-UNITS.md).

## 1. Главный вывод для реестра

В текущем коде присутствуют несколько разных обучаемых механизмов. C# Structural KNN, translation map/KNN, generic BPE+HNSW logical Unit и transformer-embedding generated Unit имеют разные входы, записи памяти, scorer и выходы. Замена одного другим ради успешного отчёта не проверяет исходную гипотезу. Исторические E09/E26-функции существуют, shared translation runtime существует, полное translation checkpoint существует, а generated checkpoint теперь сохраняет точный KNN corpus. Эти функции нельзя продолжать обозначать как полностью отсутствующие. Ссылки на конкретные writer/read пути приведены в таблице ниже.

**Новый предложенный эксперимент этого раздела — AST-SIB-CACHE-01:** цена повторного sibling enumeration внутри настоящего Structural KNN training. Его [карточка](07-AST-SIB-CACHE-01.md) меняет один фактор, использует текущий native learner и не требует роста accuracy. Остальные строки — проверенный статус известных семейств и границы применимости; они не назначают повторные запуски всех карточек.

## 3. Две особенно важные поправки к прежним формулировкам

### Точный generated corpus восстанавливается; выбор replay всё ещё ограничен

На current pin нельзя объединять два разных эффекта. Нынешний `BuildKnnTrainingCorpus` материализует выбранную память один раз; те же records передаются live Unit и manifest. При restore reader `ProjectBoundKnnCorpus` валидирует SHA и берёт `manifest.KnnExamples`. Следовательно, старую гипотезу восстановления из другой выборки надо пометить как **current source contract changed / старое отсутствие устранено на уровне corpus**. Проверка graph seed/embedding exactness остаётся отдельной причинной dependency, а не доказательством повторного выпадения records. [Training writer](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs#L949-L1005), [restore reader](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/18.CapabilityTraining/TeachingRegistryPersistence.cs#L1693-L1715).

Отдельно current replay selection ограничен top3 по времени либо fusion; будущий learner получает именно этот выбранный corpus. Если новая гипотеза меняет сохранение старых subphase/examples в процессе следующего обучения, её receiver — выбор replay и `BuildKnnTrainingCorpus`; loader с тем же corpus не должен искусственно добавлять другие records. Это сохраняет один фактор и не путает сохранённую память с ростом памяти. [Replay selection](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs#L1870-L1878), [current projection](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs#L3465-L3507).

### Бounded DPO snapshot не равен алгоритму разбиения DPO на Unit

В current `BoundedDpoTrainingContentProjector` есть immutable snapshot prompt/chosen/rejected/teaching vector/context и ordered batch hash. Это уже реализованный контракт фактического bounded content, а не отсутствие защиты содержимого. Он не определяет за нас, какой lesson нужен semantic Unit, какой — executor, и какой output должен соответствовать subphase: это ответственность producer/recipient, перечисленных в строках5/9. Нельзя исправить ошибочную педагогическую проекцию одной проверкой SHA или объявить весь DPO chosen/rejected потерянным на основании того, что translation executor читает только chosen. [Content snapshot](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/21.AgentInfrastructure/Logical/BoundedDpoTrainingContentProjector.cs#L21-L86), [projected rows / hash](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/21.AgentInfrastructure/Logical/BoundedDpoTrainingContentProjector.cs#L160-L194).

## 5. Наблюдения, которые не превращены в ложные новые эксперименты

При чтении tokenizer замечена общая метка `RU:TENSE:PAST` для распознанных VERB; writer и дальнейшее использование RuleTags зависят от exact correction / fallback keys и выбранного executor route. Без случая, где именно исправление этой метки меняет записанное учебное состояние и результат обычного reader, статический тест `Tokenize` не принят как новый эксперимент качества обучения. Часть путей уже теряет RuleTags в иных местах — это P52/P106. Наблюдение сохраняется как требующее точного causal recipe, а не как доказанное снижение обучения. [Генератор tags](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/27.TranslationDomain/TranslationSemanticTokenizer.cs#L159-L178), [correction path](https://github.com/lubochka/llm_mvp_core/blob/0b76ab950d82534f5904005dda096545505ae307/27.TranslationDomain/TranslationTrainedUnits.cs#L89-L117).

Обнаруженное повторное гендерное расширение каждого word mapping не выдано за новую находку: прежние P55.3/P55.6 уже описывают role/morphology риск. Generic KNN `hits[0]` не выдан за новый missing-K алгоритм: это P107, а E09 использует настоящее голосование. Old/generated restore различия не выданы за current absence после обнаружения `KnnExamples` writer/reader. Эти исключения предотвращают дублирование очереди и не стирают прежнюю историю.

После нового положительного результата AST-SIB-CACHE-01 отчёт и экспериментальный diff следует добавить как кандидат исправления. Production перенос и полная цепочка тестов остаются следующим решением пользователя, а не продолжением документного аудита.
