## Почему E51A полезен для восстановления алгоритма

[BuildEvidence, строки 78–96](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/Experiments/E51ACodeContextPipeline.cs#L78-L96) действительно обучает DomainClassifier на скомпилированных учебных prompts. [RunTrace, строки 249–270](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/Experiments/E51ACodeContextPipeline.cs#L249-L270) извлекает code-предикаты запроса, фильтрует train по предсказанной теме, ранжирует Жаккаром и возвращает RequiredPredicates **выбранной учебной строки**, затем сравнивает с отдельной проверочной разметкой. Такой путь воспроизводит полезный механизм «одинаковое представление → нужная память → её обученный выход». Он важнее простого переименования rule-класса в обучаемый.

Дополнительный восстановительный опыт R5: повторить исходные 27/13 без изменения представления и сохранить все 13 выбранных учебных IDs. Затем на том же представлении, коде и данных заменить только правильные учебные выходы на заранее переставленные между несовместимыми задачами; классификатор, кандидаты и запросы оставить одинаковыми. Это контроль, что полезный итог несёт память. Отдельной следующей панелью взять новые code-предикаты/комбинации и запросы с близкими словами, но другим требуемым действием; иначе все верхние score=1 могут показывать только воспроизведение сигнатуры.

Если целью является обычный Flow, зарегистрировать этот результат как выход существующего Unit, вызвать его тем же compiled input и сравнить использованный набор предикатов в реальном плане. Идентичный текстовый ответ не должен появляться через oracle lookup по проверочному ID. Холодный restore не проверен ни одним перечисленным May11 raw; для этого механизма нужен отдельный одинаковый round-trip корпуса/кодека/меток. Новые LoRA updates для R5 не требуются.

## Три обязательных оговорки к красивым поздним trace

**E51B.** [Строки 203–230](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/Experiments/E51BDynamicFlowMiniE2E.cs#L203-L230) получают subject из ближайшего учебного соседа, но WorkStatement, SchemePlan, AppliedResult и FinalResult берут из expected oracle. [Строки 107–120](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/Experiments/E51BDynamicFlowMiniE2E.cs#L107-L120) задают baseline=0,333 и времена=0,1 литералами. Поэтому +200,3% из summary не является парным замером ускорения или качества генерации. Для проверки настоящей обученной композиции сохраняется найденный subject, а выход должен прийти из учебной памяти/исполняемого Unit; запись ExpectedHeldOutTraces может использоваться только оценщиком после ответа.

**T35.** [T34TransitionDomainSplitterUnit, строка 18](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/LogicalFlow/T34TransitionDomainSplitterUnit.cs#L18) задаёт confidence как константу. [Строки 63–80](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/LogicalFlow/T34TransitionDomainSplitterUnit.cs#L63-L80) делают _ = phaseContext и возвращают фиксированные packets. Флаги raw UseLearnedUnitWhenAvailable=true и UseDeterministicFixtureBaseline=false этого свойства исходника не отменяют. Мини-проверка перехода к обученной функции — два phaseContext с разным разрешённым ограничением и один context без BaseService; остальные входы равны. Сначала измерить чувствительность выхода к входу, затем уже сравнивать обучение. Это известный тип «подмена learner интерфейсом», а не новая гипотеза только из-за свежей даты raw.

**P3.** [BuildLearningCycle, строки 325–360](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/Experiments/P3LearningFromFailureProof.cs#L325-L360) создаёт один литеральный BaseService discriminator; [verification, строки 364–397](https://github.com/lubochka/llm_mvp_core/blob/f6032aff81f1f83de7c09cf9b9efe6b058dd12b9/35.ExperimentsV2/Experiments/P3LearningFromFailureProof.cs#L364-L397) возвращает исходные 10 packets, считает отсутствующий constraint и проверяет наличие названного discriminator. Положительный результат важен как образец точной области применения правила: «отсутствует» должно отличаться от «присутствует как concern». Он не демонстрирует изучение неизвестного предиката. Для переноса в actual learner нужна вторая тема/constraint, которого нет в литералах, и оценка absent/present-concern/fully-covered при фиксированной схеме.

Полезные инженерные гарантии этих проверок следует сохранить. Их ограниченный размер и наличие oracle в части текста не отменяют самих записанных результатов; они определяют, какие именно свойства можно из них восстанавливать. Ни один из этих семи raw сам по себе не доказывает свободную генерацию новых ответов после LoRA, честное train/holdout разделение для всех функций, или восстановление обученного состояния после перезапуска.
