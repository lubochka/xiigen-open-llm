# Текущий DPO→Units: что переносится, что не читается и какой learner вызывается

**20.10.2026; core `883496bca18113bf37e0afe683c75b05a0075048`. SOURCE_CONFIRMED / NATIVE_NOT_RUN.** Проверена реализация на текущем закреплённом коммите, включая producer, непосредственные преобразователи, writers и обычные readers. Два найденных runner-пути различаются; наличие слова DPO или LearningUnitId не означает одинаковое обучение. Это уточнение существующих P52/P106/P125 и границы P92, без новой гипотезы, карточки или запуска.

Восемь дополнительно полученных исходников/fixture-файлов сохранены под `audit/core/27.TranslationDomain`; Git blob SHA каждого побайтно совпал с локальной копией. Метаданные — `evidence/current-dpo-unit-transfer-source-receipt.json`. Большие runner/bridge прочитаны по указанным исполняемым ветвям и вызываемым методам; это не проверка каждой ветви целого репозитория. Production и protected `docs/plans/replanning-possible-diffs` не изменялись.

## 1. Главный вывод

**В текущем structured translation path annotations из rejected не исчезли: часть превращается в положительную supervision для Units.** [BuildGeneralBatch,98–104](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationStructuredBatchBuilder.cs#L98-L104) читает RULE, PHRASE, AGREEMENT именно из `pair.Rejected`; затем записывает полученное в signature и выбранные targets. При этом сами три Unit-trainer читают chosen-состояние, а их `RejectedOutputJson` и `RejectedType` в показанных TrainOnExample не участвуют. Это обучение памяти, не DPO-градиент этих Units. Источники writers: [tokenizer](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationTrainedUnits.cs#L124-L140), [executor](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationTrainedUnits.cs#L404-L455), [verifier](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationTrainedUnits.cs#L1095-L1145).

**Не любое annotation в rejected ошибочно.** Реальные [b029 phrase-repair rows1–3](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TrainingData/ru-en-general-l1-b029-phrase-repair-train-ready.jsonl#L1-L3) содержат правильные reusable phrase mappings в этом поле; например Она→She и прощалась→bid farewell. [product fixture rows1–3](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TrainingData/product-prompt-b001-all-directions-train-ready.jsonl#L1-L3) использует тот же формат для разговорного перевода и emoji. Это намеренный вспомогательный формат supervision. Риск известной P52 возникает, когда producer без отдельной проверки принимает **неверную** annotation как positive target либо меняет недоступный runtime ключ. Простое удаление всего rejected может удалить полезный учебный сигнал.

## 2. Одна исходная пара → три конкретных Unit target

[Producer,78–150](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationStructuredBatchBuilder.cs#L78-L150) проверяет direction/train_ready/ValidationErrors и создаёт ровно semantic, executor, verifier examples. `HeldOut` распространяется на все три. Их `FlowId` одинаков, `UnitId` различается; suffix ExampleId показывает происхождение от одной пары. [Machine,107–142](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationMachine.cs#L107-L142) вызывает trainers по UnitId и считает RowsTrained по числу examples — три таких записи нельзя считать тремя независимыми исходными уроками.

## 4. Два доказанных call path, которые нельзя смешивать

### A. Structured memory learner и обычный Flow

[Batch029Runner,126–180](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationBatch029Runner.cs#L126-L180) вызывает BuildRuEnGeneralBatch и затем **TranslationMachine.TrainStructuredBatchAsync**. Новые/supplemental pairs используют Structural mode; corpus pairs — ExactPair mode. Machine выбирает три actual Unit trainers по UnitId. Затем [runner,184–220](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationBatch029Runner.cs#L184-L220) делает запрос через полученный orchestrator. [TrainedTranslationAdapter,124–139](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDirectionAdapters.cs#L124-L139) вызывает Tokenize→Execute→Verify.

Таким образом memory state доходит до обычного пользовательского результата. При этом phrase-map candidate с confidence≥0.85 допускается даже при failed verifier — это видимая ветка adapter, поэтому неверно считать verifier единственным решающим consumer. ExactMatch и marker-based ProductMatch в runner — разные показатели, их нельзя объединять в одну semantic accuracy. Новый запуск для этой проверки не выполнялся.

### B. Neural translation DPO через StepMany

[TranslationDpoTrainEvaluateRunner,673–685](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainEvaluateRunner.cs#L673-L685) в legacy ветке тоже создаёт structured batch. Но [BuildSeedCorpusTrainHandoff,111–136](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainingHandoff.cs#L111-L136) использует его для heldout/source/batch-ID проверки, а **TrainingPairs строит по исходным corpus.TrainRows**, не по трём Unit JSON. [BuildTrainingRecord,244–281](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainingHandoff.cs#L244-L281) передаёт в admission Prompt + Input:ASide и неизменённые trainReady.Chosen/Rejected. LearningUnitId здесь — executor direction; это metadata одной neural pair. Репозиторная ветка строит handoff напрямую из repository-owned pairs и не требует этого 3-way projector: [139–175](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainingHandoff.cs#L139-L175), [285–335](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainingHandoff.cs#L285-L335).

Далее [featurizer,180–216](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L180-L216) формирует tensor pair и сохраняет raw SourcePair для аудита. [TrainAdmittedWithStepMany,509–543](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L509-L543) вызывает настоящий `DpoTrainer.StepMany`; [runner,779–817](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainEvaluateRunner.cs#L779-L817) затем отдельно вызывает heldout EvaluateMany. В этой цепочке не вызывается TrainOnExample трёх memory-Units. Нельзя по ней утверждать, что neural update обновил phrase maps или semantic correction memory.

**Диагностики в neural ответах уже обрабатываются иначе.** Current [StripReservedDiagnosticsForModel](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L262-L304) удаляет WRONG blocks и arrow-blocks с префиксами [PHRASE/AGREEMENT](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L112-L116). Обычный RULE block не входит в этот список. Обычные скобки/неполный block сохраняются. Если после удаления chosen/rejected пуст — BuildRecord возвращает отказ до tensor training ([184–190](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L184-L190)). Поэтому annotation-only fixtures из раздела1 нельзя автоматически считать готовыми negative neural samples: если такая строка дойдёт до этого featurizer, результат будет EMPTY_AFTER_DIAGNOSTIC_STRIP. Это вывод из кода, не наблюдавшийся запуск или доказательство обхода upstream admission.

Этот neural bridge использует собственные regex/hashed IDs и budget truncation ([230–251](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L230-L251), [331–343](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationDpoTrainerBridge.cs#L331-L343)), а не BPE-проектор original RP01 exact-v2. Здесь не устанавливается причинная связь с original RP01 0/3 или 0/4; его первичные receipts разобраны отдельно.

## 5. Доменная применимость и существующие карточки

Builder перечисляет RU_EN, EN_RU, HE_EN, EN_HE, ES_EN, EN_ES ([536–545](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationStructuredBatchBuilder.cs#L536-L545)); это поддержанный routing contract, не результат успешного обучения всех шести направлений. Batch029 runner ограничен RU_EN. В прочитанном product fixture есть RU_EN/EN_RU/HE_EN/EN_HE; эти строки не доказывают качество сами по себе.

Генерация inferred word mappings ищет главным образом английские technical terms ([386–400](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationStructuredBatchBuilder.cs#L386-L400)); script compatibility фильтрует EN_RU и RU_EN иначе, чем остальные направления ([480–493](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationStructuredBatchBuilder.cs#L480-L493)). Verifier извлекает source marker из raw source через tokenizer с фиксированным ru ([1265–1277](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationTrainedUnits.cs#L1265-L1277)). Runtime использует отдельные executors и общий tokenizer/kNN/verifier для шести направлений ([CreateRuntime](https://github.com/lubochka/llm_mvp_core/blob/883496bca18113bf37e0afe683c75b05a0075048/27.TranslationDomain/TranslationMachine.cs#L714-L756)). Эти различия требуют отдельных language/direction выводов; AST-кодовый успех E09 сюда не переносится.
