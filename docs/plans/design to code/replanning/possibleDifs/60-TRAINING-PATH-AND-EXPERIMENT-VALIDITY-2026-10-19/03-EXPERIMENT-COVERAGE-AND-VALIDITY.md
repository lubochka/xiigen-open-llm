## Исторический вывод для c3f1 — до внешнего исправления f50

На историческом срезе `llm_mvp_core` **c3f1d0d4fc7fb7949c51d2251e89d2fb0e590d72** правило «любой измеренный полезный прирост — успех по своей метрике и домену; рост точности не обязателен; ухудшения рядом» уже добавлено во все **125 P-карточек и 133 извлечённых блока их промптов**. Прежнее замечание об отсутствии этого правила в этих блоках снято. Это проверка наличия текста, не доказательство качества каждого эксперимента.

На том срезе сохранялось другое несоответствие заданию: каталог допускал самостоятельные проверки evaluator, decoder, cache, regex, метаданных и публикации без изменения процесса обучения. Их авторы преимущественно **честно называют диагностикой**, поэтому обвинять их в выдуманных учебных результатах нельзя. Но честное обозначение диагностики не делает её разрешённым пользователем экспериментом обучения. Эти рецепты следует исключить из учебной очереди. Инженерный результат может быть полезен в другом поручении; в этом поручении он не расходует экспериментальный бюджет и не закрывает learning-гипотезу.

Есть и более тонкий случай: вызов Train рядом с изменённым измерителем не делает опыт причинным. Если A/B различаются только тем, куда записывается AccuracyBefore, а параметры, память, выбор уроков, число обновлений и ответы остаются теми же, это всё ещё проверка отчёта. Нужно показать, каким реальным путём вмешательство меняет обучение.

## Случаи, которые нельзя ошибочно отвергнуть по слову «0 optimizer»

**KNN и обучаемая память могут учиться без оптимизатора.** Существенны вызов native Train/TrainOnExample, реальное изменение состояния и его чтение собственным Predict/Verify/Execute. Нулевой optimizer count не делает такой опыт невалидным.

1. **N57-ARG**, `20-additions-n57-argument-and-verifier.md:40–77`: два пустых StructuralKnnPredictor(k:1), две одинаковые учебные строки, единственное изменение ArgumentOrdinal/distance в B, реальные два Train и 16 Predict в A0/A1/B0/B1. Gold — следующий AST-kind, а не сгенерированный C#. Изменённые Depth/Scope в EXAM должны быть подтверждены фактическими vectors. Это **корректная причинная конструкция ограниченного KNN-опыта**, с явно незаполненными native extraction/host/fixture bytes. Не объявлять готовым к запуску, пока они не определены.
2. **N57-VER**, тот же `20...md:82–108`: изменение helper участвует в записи и чтении `_requiredTermsBySourceMarker`; четыре реальные TrainOnExample и 16 Verify. Проверяется собственный verifier, не свободный перевод; candidate — вход verifier. При отсутствии ADV/наличии RuleTags должен реально достигаться helper. Это **валидная конструкция обучения Unit при выполненных предусловиях**. Дополнительные cross-reader восемь Verify на L104 — отдельная необязательная диагностика; она не нужна для основного учебного опыта.
3. **GDC-CAT**, `15...md:20–34`: доставка одинаковых учебных категорий в native admitted writer меняет обучаемые предпочтения; 2 batch calls/4 row-processing/16 Improver calls, 0 neural steps. Это условный настоящий учебный опыт. Соседний GDC-MULTI не делает его невалидным. Нельзя обходить отсутствующий admitted seam или заменять его готовыми весами.
4. **O-retention**, `07-conditional-probes.md:81–85`: память обучается native Train, хотя optimizer updates=0. Цена исходного изучения двух старых уроков и следующего этапа учитывается отдельно. Не приравнивать замену строк KNN к шагу LoRA.

## Принцип исправления очереди — исторические рекомендации, согласованные с новой границей f50

### Исправление A: измеритель сделать общей частью настоящего опыта

Для EVAL-DIR, M1/M2 и METRIC-STATE не создавать искусственный Train ради формального наличия слова. Правильный evaluator, CPU и RAM meters одинаковы в A и B настоящего опыта. Его фактор должен находиться в StepVector, TrainOnExample, обработке урока, replay или состоянии, которое следующий update действительно читает. Если такого влияния нет, исходная гипотеза остаётся диагностической и **не запускается в этом задании**.

Четыре оценки фиксируются отдельно: A0, A1, B0, B1. Для качества показываются `A1−A0`, `B1−B0` и их разность; для ресурсов — цена одной и той же фактической работы с определёнными границами. Это не обязательный статистический порог. Любое измеренное полезное изменение признаётся локальным успехом по соответствующей оси; неопределённость измерения, регрессии и отсутствие устойчивой репликации указываются отдельно.

### Исправление B: настоящий пример восстановления должен закончиться следующим обучением

Восстановление state/codec может быть причиной ухудшения обучения. При найденном реальном loader и native trainer сравнивать две восстановленные копии одного принятого учебного состояния, затем предъявить **один одинаковый следующий допустимый урок** обеим рукам через тот же Train/TrainOnExample. Единственное вмешательство — восстановление конкретного недостающего обучаемого поля. Измерять исходные ответы, изменение state от нового урока, ответы после него и сохранение двух ранее выученных различий. Roundtrip/hash/export отдельно служат проверкой идентичности; они не являются качественным исходом опыта. Если actual trainer не читает это поле или законный loader отсутствует, опыт не назначается. Эта схема не утверждает, что такой consumer уже установлен у METRIC-STATE/M3.

### Исправление C: конкретный уже описанный Unit-опыт вместо serving-подмены

Для RU→EN можно назначить основной **N57-VER** после определения native входов. Один фактор: исправленное кириллическое окончание `о` в общем writer/reader helper; T1 «Он тихо открыл дверь», T2 «Она быстро собрала сумку»; actual projected verifier lessons одинаковы в A/B. Два пустых Unit → по два TrainOnExample → четыре прежних EXAM-candidates в каждом из четырёх состояний. Полезный исход: меньше пропусков omission, меньше ложных отказов, стоимость Train/Verify или bytes обучаемой памяти. Любой из них может быть успехом; другие потери рядом. Это развитие существующей карточки, **не новая гипотеза этого аудитора** и не ремонт neural LoRA.

**Полный смысл промпта такой версии:** «Используй только указанный native Unit и две фактически построенные учебные строки. Меняй только согласованный writer/reader helper. Сохрани A0/A1/B0/B1 и все 16 собственных Verify, четыре TrainOnExample, изменения обучаемого состояния и затраты. Если helper не достигнут, это невалидная проверка гипотезы; не подменяй его fixture. Любое измеренное полезное улучшение — успех по этому показателю и домену; рост точности не обязателен. Покажи остальные изменения, включая ухудшения. Роль человеческого выбора и оценку качества DPO выполняет CODEX с моделью astra 6 ultracode; внешняя открытая китайская модель создаёт chosen/rejected. Simulation-примеры этой карточки не выдаются за уже полученный внешний DPO. Не запускай внешнюю генерацию или другую программу ради заполнения неизвестного поля».
