# Что уже улучшалось и какие механизмы нельзя смешивать

## 1. RP01: движение предпочтения было, свободные ответы не улучшились

Первичные отчёты C# и EN→RU сохраняют настоящие LoRA updates и положительное изменение среднего нормированного преимущества chosen над rejected. Согласно текущему правилу пользователя это **успех по данному показателю на данной панели**. Одновременно они сохраняют нулевой прирост свободных правильных ответов. Корректная интерпретация включает оба факта.

| Измерение | C# документация | Перевод EN→RU |
|---|---:|---:|
| Учебные пары / новые optimizer updates | 500 / 50 | 500 / 50 |
| Средний normalized margin до | 0.03733304977416992 | 0.012293052673339844 |
| После | 0.03856058120727539 | 0.012403059005737304 |
| Измеренное изменение | **+0.0012275314331054651** | **+0.00011000633239746093** |
| Cases с ростом / снижением margin | 14 / 11 | 11 / 9 |
| Chosen preferred | 16/25 → 16/25 | 12/20 → 12/20 |
| Полностью правильные свободные ответы | 0/3 → 0/3 | 0/4 → 0/4 |

Источники: [C# scientific-result](https://github.com/lubochka/llm_mvp_core/blob/8e020052fae7efa694b8d33f90768648d6b67af9/.kiro/xiigen-slices/work/results/RP01-simulation-main500-execution-20261015/scientific-result.json), [ENRU scientific-result](https://github.com/lubochka/llm_mvp_core/blob/8e020052fae7efa694b8d33f90768648d6b67af9/.kiro/xiigen-slices/work/results/RP01-enru-continuation-20261016/runtime-20261016-01/analysis-20261016-01/scientific-result.json). В этом аудите файлы прочитаны, сами кампании заново не запускались.

В обоих результатах 39 base tensors неизменны, 16 разрешённых LoRA tensors меняются; полное состояние weights/optimizer/RNG было сохранено и открыто обратно. Поэтому объяснение «LoRA вообще не обновилась» противоречит этим конкретным receipts. Общее неправильное восстановление всех моделей проекта ими не исключается: другие Unit, поля и callers требуют своей проверки. ENRU reference C50 отдельно сохранялся frozen; baseline C# retention уже имел0/3, поэтому его неизменность не доказывает сохранение ранее полезного навыка.

Normalized preference scorer усредняет ответные вероятности; это не exact-sum training loss. Показатель полезен для наблюдения предпочтения, но не равен умению сформулировать ответ. C# panel содержит новые экземпляры тех же параметризованных шаблонов, независимые semantic families не установлены; ENRU panel раскрыта и не годится как новый blind confirmatory exam. Эти ограничения не аннулируют измеренный локальный прирост. Исходные статусы «нет semantic/free-answer improvement» читаются узко, а не как «не улучшилось ничего». [Контракт инструмента](https://github.com/lubochka/llm_mvp_core/blob/8e020052fae7efa694b8d33f90768648d6b67af9/tools/Rp01SimulationDpo/README.md).

## 2. Успешное обучение есть и в более поздних сохранённых экспериментах памяти

**P125:** после восьми уроков обычный Translation Flow изменился с0/24 до19/24 правильных ответов. Получатель — память Executor; neural updates=0. Успех включает8/8 новых сочетаний знакомых action/object. Одновременно появились три ошибочно принятых ответа, в том числе потеря отрицания и превращение вопроса в команду. Это приобретение способности конкретной памятью, а не доказательство neural DPO или полной предметной генерализации. В самом исходном P125 cold restore **не запускался**. [Первичный P125 report с native before/after и сырыми ответами](https://github.com/lubochka/llm_mvp_core/blob/8e020052fae7efa694b8d33f90768648d6b67af9/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/P125-enru-memory-01/report.md).

**Исправление ingress:** другой опыт сравнил два свежих экземпляра, каждый обученный на одинаковых восьми уроках. Старый reader/builder не передавал16 уже имеющихся phrase mappings; исправленный передавал их. После обучения:11/24→19/24, новые сочетания0/8→8/8, ранее правильные ответы не потеряны. Принятые ответы12/24→22/24, а ошибочно принятые1→3; correct/accepted снизилось с11/12 до19/22. Здесь «до→после» означает сравнение версий преобразователя при одинаковом обучении, а не добавление ещё восьми уроков в прежний экземпляр. Это подтверждённая потерянная деталь доставки учебного материала, уже исправленная до данного аудита; новой находкой она не называется. [Первичный ingress report](https://github.com/lubochka/llm_mvp_core/blob/8e020052fae7efa694b8d33f90768648d6b67af9/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/translation-memory-ingress-01/report.md).

Отчёты сохраняют отдельные measurements времени/памяти, но порядок процессов, JIT и единичные вызовы не позволяют объявить устойчивый speedup. Большая доля ответов не скрывает возросшие false accepts. Поля native trainer `accuracyAfter=0` в этих runs не равны внешней оценке19/24: они описывают другую внутреннюю величину. Исправление имени такой величины само по себе не является новым обучением.

## 5. Как учитывать домены

Для кода и SQL важны парсер, виды узлов, аргументный порядок, scope и связи AST. Для перевода нужны собственные роли, отрицание, модальность, направление и порядок слов. Перенос проверяет функцию признака в конкретном train/query path; положительный результат C# AST не обосновывает применение того же признака к произвольной фразе. Даже внутри перевода EN→RU и RU→EN могут иметь разные recipients и разрешённые neural profiles.

Путь exact DPO/LoRA, путь combined incremental DPO+SFT и путь memory Unit имеют разные изменяемые состояния. Найденный дефект одного из них не становится причиной RP01 без подтверждённого consumer конкретного run. Поэтому три новые гипотезы этого пакета различаются по статусу: вычисление padding непосредственно находится в StepVector RP01; порядок DPO/SFT относится к иному combined пути; E14 loop-label относится к C# action-memory с условным facade consumer. Во всех трёх полезный эффект ещё нужно измерить.
