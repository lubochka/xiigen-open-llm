## Что нового и почему это отличается от уже существующего аудита

В имеющейся [N29 сводке](29-CONSOLIDATED-EVIDENCE-ROUTING-AND-NOVELTY-REGISTER-2026-10-16.md), [DPO-source аудите](02-DPO-DATA-OBJECTIVE-GRADIENT.md) и [обсуждении RP01 schedule](27-RP01-BATCH-STRATIFICATION-CONTRACT-GAP-2026-10-16.md) уже описаны случайная B0, семейная повторяемость, один epoch, слабость contrast и отличие teacher/provenance. **Здесь отдельная, проверяемая admission-семантика**: система допускает много почти одинаковых шаблонов *разных* prompt, но отвергает **два разных preference contrast для одного и того же вопроса**. Новизна — конкретное ограничение `prompts.Add`, не общие «низкое разнообразие» или «near-duplicates». До полного глобального поиска по всем документам считать новую гипотезу **кандидатом**, а не доказанным уникальным открытием.

### N32-A1 — исходный код подтверждает запрет

1. [`CodeDocumentationSimulationDpoExperiment.Inspect` L39–75](https://github.com/lubochka/llm_mvp_core/blob/79082340f01b744cdf08185616f2bd818dbd06b8/14.ContinuousLearning/Training/CodeDocumentationSimulationDpoExperiment.cs#L39-L75): кроме `ids` и `triplets` создаёт **отдельный `HashSet<string> prompts`**, затем применяет `!prompts.Add(value.Prompt)` и при любом повторе возвращает `InvalidInput()`. Отвергается **весь import**, а не одна подозрительная строка. `StringComparer.Ordinal`, значит это точное равенство, не семантическая дедупликация.
2. [`Inspect` L64–75](https://github.com/lubochka/llm_mvp_core/blob/79082340f01b744cdf08185616f2bd818dbd06b8/14.ContinuousLearning/Training/CodeDocumentationSimulationDpoExperiment.cs#L64-L75) уже независимо запрещает одинаковый `Id`, а затем одинаковый content fingerprint triplet. Таким образом **промежуточная проверка prompt добавляет самостоятельное ограничение**, которое невозможно объяснить лишь защитой от полного replay.
3. [`Run` L113–123](https://github.com/lubochka/llm_mvp_core/blob/79082340f01b744cdf08185616f2bd818dbd06b8/14.ContinuousLearning/Training/CodeDocumentationSimulationDpoExperiment.cs#L113-L123) после import преобразует допущенные строки в `LogicalDpoPreferenceExample` и exact-v2 material. Следовательно, два вопроса с тем же prompt, но разными законными rejected *даже не доходят* до этого Student-пути, если собраны в один input JSONL.

**Минимальный проверяемый контрпример:** row1 `{id:"a",prompt:"Explain why x is safe", chosen:"...", rejected:"unsafe because ..."}`; row2 `{id:"b",prompt:"Explain why x is safe", chosen:"...", rejected:"unsafe due to a different law..."}`. При корректной schema/provenance, правильных SHA и `expectedCount=2` для C# route `Inspect` всё равно отвергнет row2 именно по повтору `prompt`. При изменении второго prompt только на одну букву этот конкретный guard больше не сработает. **Proxy outcome derived from code; native .NET call NOT_RUN.** Реальные содержательные стороны надо законно оформить отдельно.

### N32-A2 — возможный эффект на качество, но не доказанная причина исторического 0/3

Для задач с множественными **независимыми типами ошибок на одном input** (C# безопасность, SQL/AST, перевод с падежами/отрицанием, медицинские/финансовые domain rules) нужен иногда не только один выбранный/отвергнутый образец, а несколько осмысленно разных отвергнутых альтернатив для одного source. Этот offline simulation importer **не позволяет выразить это как несколько строк**. Он может мотивировать учебный генератор менять почти идентичные prompt искусственно, вместо обучения нескольким контрастам на настоящем одном условии. Это **гипотеза о качестве учебного покрытия**, а не доказательство, что DPO обязан поддерживать несколько rejected для каждого prompt.

**Граница причинности:** успешно импортированные C#500/ENRU500 уже прошли guard (иначе не состоялся бы успешный `Run`). Следовательно, это не «тихое отбрасывание» внутри опубликованного RP01 и **не непосредственное объяснение** C# 0/3→0/3 или ENRU 0/4→0/4. `Inspect` — *явно ограниченный simulation research* contract, не обобщать на все production DPO-admission authorities. Не ослаблять legal/provenance gate.

**Различающий опыт:** [MICRO-N32](32-MICRO-ONE-FACTOR-LEARNING-CONTRAST-AND-E09-2026-10-16.md), фаза A: native `Inspect` для одной и двух разных negatives; затем test-only authorised DPO A=два раза один и тот же контраст и B=два различающихся validated negatives для **того же prompt**, одинаковое число шагов и chosen-side, новый source-family-disjoint blind exam. Альтернативы: всё объясняет B0 inability, или negatives семантически дублируют друг друга. **Не считать рост imported row count ростом качества.**

**Доменность:** относится к одному bounded simulation importer для C# и ENRU; потенциальная полезность multi-contrast сильнее в доменах с несколькими ошибками/законами на одном input; общий векторный KNN, E09 и переводческие learned Units этой проверкой **не доказаны**.

**Review gate:** named owner/caller/recipient, exact source, отрицательный и положительный контролы, отдельные proof-of-training и proof-of-generalization. CODEX/Astra independent assessment и разрешённая teacher-side generation NOT_RUN. Это research DRAFT, не распоряжение немедленно править source.
