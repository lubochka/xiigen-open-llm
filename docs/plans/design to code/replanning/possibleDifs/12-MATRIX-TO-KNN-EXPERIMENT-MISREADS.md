# 12. «Неудачная матрица» → полезный kNN: проверка подмены эксперимента, а не статус по названию
Дата 2026-10-16. Статус **CONFIRMED_IMPLEMENTATION_DEFECT_IN_HISTORICAL_EXPERIMENT_E07**; E07→E09 causality **NOT_ESTABLISHED**; независимый model replay не выполнялся.

## 0. Разделяем три разных «матрицы»
(1) В [оригинальном определении Unit](https://github.com/lubochka/xiigen-planning/blob/llm_plan3/llm%20mvp/design%20to%20code%20session/%D0%90%D0%BB%D0%B3%D0%BE%D1%80%D0%B8%D1%82%D0%BC%20%D1%81%D0%BE%D0%B7%D0%B4%D0%B0%D0%BD%D0%B8%D1%8F%20%D0%94%D0%9F%D0%9E.md#L12-L20) «упрощённая матрица» означает роль ILearningUnit (domain/vector/input/output many-to-many). (2) E07 использует «многомерную матрицу переходов» как keyed N-gram. (3) E12 сравнивает скорость операций с числовыми матрицами. Смешение этих трёх сущностей даёт ложную историю переносов; пока нет commit/trace, который доказывает буквальное перемещение конкретного E07/E12 алгоритма в production KNN. Найдена гораздо более полезная улика о **потере и ложной проверке структурного сигнала**.

## 1. Новый конкретный дефект E07: Tier2/Tier3/Tier4 на бумаге не соответствуют train key
Код [E07StructuralContextToken.cs, Run](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs#L84-L134) принимает tier и печатает легенду: Tier2 ast_parent, Tier3 ast_depth+file_id, Tier4 scope_depth, Tier5 structural batching. Однако реальный [MultidimensionalNGram.Train](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs#L273-L325) индексирует только **(BpeId, AstNodeType, AstDepth)**. В [Predict](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs#L90-L97) аргументы те же; ast_parent, file_id, scope_depth не входят в decision key; tier не передаётся в trainer. Код доказал: выбранная «новая размерность» в сообщении эксперимента не включается соответственно Tier2/Tier3/Tier4. Нельзя заключать, что «ast_parent / scope_depth ухудшили качество» из отчётов, если эти поля не влияли на предсказание.

### Дефект E07-2: вероятное нарушение alignment BPE→AST по координатам
В [BuildStructuralTokens](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs#L136-L163) индекс i — порядковый номер BPE-токена. Он используется для обращения к posMap[i]. Но [BuildPositionAstMap](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs#L167-L225) строит posMap по **равномерным выборкам символьных позиций** charPos=int(s*textLen/slots) без информации об offsets BPE-tokenization; не строится token start offset→AST Span. BPE token ordinal ≠ character sample ordinal. Поэтому structural meta может относиться к другому участку исходника; при textLen >50K рассогласование дополнительно меняется со step. **CODE_CONFIRMED несовпадение пространств индексов; доля испорченных alignment и её вклад в −12.78% пока не измерены.** Это сильная новая гипотеза неверного «неудачного» результата.

## 2. Что действительно показал E09 после применения структуры в KNN
[E09StructuralKnn.cs:102–124](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E09StructuralKnn.cs#L102-L124) извлекает StructuralVector прямо из Roslyn AST node, а не из posMap по индексу BPE. [Saved result](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/results/E09-STRUCTURAL-KNN/results/run-2026-05-01-001.json) сообщает top1 .2413→.3507 (+10.94 процентного пункта, +45.33% относительно); k=5, trainPairs=4492. **Это positive reported signal для поиска по AST**, совместимый с тезисом о ценности структуры в kNN. Но непосредственную причинную цепь «одна и та же фича провалилась в матрице и затем спасла KNN» НЕ доказывает: это другой input representation, другой objective и другая выборка. Более того, [E09:50–77](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E09StructuralKnn.cs#L50-L77) сравнивает bigram на всей validation с KNN только val.Take(500) — **UNMATCHED_PANEL**. Без paired recomputation нельзя объявить +10.94pp чистым выигрышем. Дополнительный seam: [E09:107–119](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/35.ExperimentsV2/Experiments/E09StructuralKnn.cs#L107-L119) строит kindMap заново для каждого файла — target label BpeId не гарантированно обозначает один и тот же SyntaxKind между файлами; это отдельная гипотеза label-space mismatch для verification.

## 4. Что теряет нынешний generic KNN
[21.AgentInfrastructure/Logical/KnnLogicalUnit.cs:216–254](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L216-L254) запрашивает Search(query,k) но возвращает bestExample.Output из hits[0], остальные neighbors только evidence. [Vectorize:265–299](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L265-L299) считает hashed bag of BPE/token predicates: порядок, scope, роли и отрицание не выделены типизированными координатами. Это отличается от богатого AST vector E09, domain-scoped, arbiter-aware negative/warning memories и E51 node semantics. Не утверждать, будто все KNN в core таковы: [TranslationTrainedUnits.cs](https://github.com/lubochka/llm_mvp_core/blob/83590a462b2f8aedc9d3ab4cb775193eb9c25ce5/27.TranslationDomain/TranslationTrainedUnits.cs) содержит отдельный richer store/word/phrase/exact mechanism.

## 5. Причинный тест, чтобы восстановить, что на самом деле «переехало»
**DIF-MK-01:** E07 старый фактический Ngram (BPE misaligned) vs E07 с настоящим BPE-offset↔AST span и реализованными разными tier keys; обучающий corpus/split/source-family фиксирован. Если точность становится выше, прежний FAILED был representation/implementation defect. Не менять frozen results.
**DIF-MK-02:** E09 old AST KNN и E09 bigram сравнить на *тех же* val index, проверить kindMap global ID; отдельно composite AST KNN vs нынешний hashed generic Unit на тех же целевых labels. Если old improvement исчезает, эффект был от panel/label mismatch.
**DIF-MK-03:** 2×2 на задании с domain laws: (hashed vs structural vector) × (first-hit vs law-scoped aggregate/rerank+arbiter), держать k, memory, corpus и budget сопоставимыми; сделать contrast с negation/coreference/source/version, paired per-family success, coverage, critical errors, memory, wall-time. Отличать fallback rule от обновления обучаемого состояния.
**DIF-MK-04:** Проследить Git history конкретных classes/commit refs в других ветках. Только если найдены исходный algorithm ID, actual move commit, new caller, matched before/after, присвоить VERIFIED_MATRIX_TO_KNN_MIGRATION; до этого «утверждение пользователя — важное направление поиска, не архивно доказанный конкретный refactor».

### Исполнимое правило принятия
Сначала научная пара старое→новое **на одном input/holdout**, затем source-specific code repair; не делать серию Windows GitHub CI для «процента покрытия», не менять существующие E07/E09 сохранённые run/grades, не переносить deterministic workaround как якобы gradient learning.
