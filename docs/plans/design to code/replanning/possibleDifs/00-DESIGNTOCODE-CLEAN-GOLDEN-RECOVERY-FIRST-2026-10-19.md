## Глава 0.0. **Первый технический P0 — собственный Design-to-Code learning signal, а не только legacy-модели**

После сверки с параллельно опубликованным [прямым DesignConversion gold-first аудитом](00-DESIGNTOCODE-CLEAN-GOLDEN-FIRST-2026-10-19.md) и самостоятельного чтения [gold `ToCanonicalTrainingItem`](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/44.DesignConversionDomain/DesignConversionTrainingPipeline.cs#L1487-L1520), [current projection](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionTrainingPipeline.cs#L2712-L2727) и [current `BuildLearnedWeightDeltas`](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionMachine.cs#L2937-L3003) обнаружен **более прямой branch delta**:

- В gold response `html/css/visual_score`; в current canonical optimizer response **только `html/css`**.
- Current local обучаемая `DesignConversionMachine` пытается прочитать **оба `visual_score`**, но без них присваивает любой различающейся паре `preferenceMargin=1.0`. Положительная и отрицательная *сила* предпочтения может схлопнуться в одно значение для local feature-weight recipient. **Для нейронной 11.DPO q/v-LoRA это пока НЕ доказанный дефект**: оптимизатор и обучаемый получатель разные.
- Архивная gold DPO-конструкция также вписывала подсказки о результате оценивания в prompt/response — откат «вернём все поля в текст» опасен утечкой метки. Надо передать визуальные оценки **отдельной разрешённой server-owned типизированной записью** локальному feature-weight learner; нейронному Student оставить безопасный HTML/CSS prompt/response.
- Другой прямой риск — `AddCorrectionCategoryDeltas` ищет `defect_categories`/`correction_category`, которых в текущем optimizer payload нет; выяснить authorizing sidecar. Gold публичный `TrainBatchAsync` ранее учил, в current этот публичный путь возвращает ошибку без admission; использовать текущий `TrainAdmittedBatchAsync` и проверить actual callers, **не отключать legal admission**.

**Существенная научная поправка к интерпретации GDC-A0:** повторное чтение [gold `BuildLearnedWeightDeltas`](https://github.com/lubochka/llm_mvp_core/blob/e346b88a3cc1fcce48aefa626bfc7b00509eefd6/44.DesignConversionDomain/DesignConversionMachine.cs#L2755-L2820), [current delta construction](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionMachine.cs#L2937-L3005) и [current `CommitLearningBatchAsync`](https://github.com/lubochka/llm_mvp_core/blob/358af351e22a92a3f7938d1f9221d5aeb7ddb053/44.DesignConversionDomain/DesignConversionMachine.cs#L349-L407) показывает: `preferenceMargin` является прежде всего отчётным `AverageRewardMargin`, **не множителем `AddDelta.Contribution`**, в обеих ветках. Это [уже корректно замечено другим агентом](54-DESIGNTOCODE-CLEAN-EVIDENCE-REVIEW-2026-10-19.md), не новое открытие. **Возвращение `visual_score` sidecar без изменения дозволенного per-feature signed input ещё не гарантирует изменения LearnedWeights и тем более качества**. Функциональный приоритет: GDC-A0 определяет только присутствие и степень связности score/weight; GDC-A1 проверяет signed category updates; затем ordinary consumer/visual heldout. Отказ голд-ветки при пропавшем score (раньше delta=[]), а ныне обучение при любом different HTML/CSS (constant margin), является более точным установленным изменением admission/generation than «old weighted gradient». Нельзя назвать это деградацией результатов без проверки. 

**Новый первый эксперимент GDC-A0, прежде GOLD-DC-01:** четыре валидных пары HTML/CSS: high/low score; score inverted без перестановки HTML/CSS; equal score; равные chosen/rejected. Одинаковый approved Unit и dataset. A: current canonical→approved local learner; B: тот же source+chosen/rejected, но с **trusted typed sidecar** парой `chosenScore/rejectedScore`; C: B после cold restore и обычного HTML/CSS consumer. Измерить направление/величину `preferenceMargin`, `LearnedWeightCheckpoint`, реальные visual defect improvements на заранее объявленных 4–8 unseen design cases, CPU/RAM. **Если сигналы восстановились, но визуальные ответы нет — не писать «качество восстановлено».** Отдельно GDC-A1 — разрешённые категории contrast/overflow для конкретного Improver, не глобальные текстовые правила.

**Не заявляю эту находку новой среди агентов:** она уже опубликована в [DTC gold-first](00-DESIGNTOCODE-CLEAN-GOLDEN-FIRST-2026-10-19.md), [source parity и собственные N54 гипотезы других исполнителей](54-DESIGNTOCODE-CLEAN-SOURCE-PARITY-AND-NEW-GAPS-2026-10-19.md) и [GDC-A0–A7 эксперименты](54-DESIGNTOCODE-CLEAN-CAUSAL-MICROEXPERIMENTS-2026-10-19.md). Мои дополнительные узкие N54-01/02/03 ниже — **другой слой**: `translation-v1` legacy publication/corpus proof. В порядке восстановления качества Design-to-Code идти **GDC-A0/A1 → GOLD-DC-01/02 → domain-specific GOLD-DC-04 → RP01 tiny Student**. Результат native эксперимента: `NOT_RUN`.

### Жёсткий приоритет разработки

**Сначала GDC-A0/A1 (восстановить оценку/роль реального DesignConversion local learner), затем GOLD-DC-01/02 (восстановить обученные checkpoint consumers), затем GOLD-DC-04 по реальным доменам, и лишь потом расширять neural DPO bulk.** Новые API legal admission / provenance / atomicity **сохранять** — нельзя восстанавливать прошлый успех путём отключения валидаторов либо бесконтрольного копирования весов. Не блокировать микропилоты долгими Windows GitHub CI: сборка/узкий smoke при настоящей правке плюс преимущественно domain-specific quality exam.

## Глава 0.3. Граница причинности: три разные «положительные» истории

1. **Архивный положительный score от конкретного consumer.** `orchestration-v1` unseen-style=0.8 в сохранённом отчёте; это историческая метрика не повторённая этим аудитом.
2. **Обучаемая память действительно есть, но acceptance ложнопереносим.** `translation-v1`: один пример в persistent memory, парафраза через kNN; продуктовая 1/3 и no promotion. Не называть глобальным успешным обучением перевода.
3. **Эксперимент с полезной функцией без гарантированного обучаемого recipient.** E09 структурный поиск; E26 BuildDefault POS dictionary; E43 bigram replay; их повторное использование в KNN может быть хорошей инженерной идеей даже при отрицательном исходном «matrix experiment», но только domain-matched A/B и actual end-to-end результат определяют пользу.

Исторические E09 baseline/enhanced оценены на разных множествах; E26 = 15 статических случаев, E43 = bigram replacement, а не current LoRA optimizer continuation. См. [проверку E09/E26/E43](51-GOLD-BRANCH-EXPERIMENT-CODE-PARITY-AND-E26-DETERMINISTIC-LOOKUP-2026-10-19.md) и [приоритетную сводку других агентов](01-PRIORITIZED-DIFFERENCES.md). Нельзя объявлять их измерениями ухудшения между DesignToCode-clean и current.
