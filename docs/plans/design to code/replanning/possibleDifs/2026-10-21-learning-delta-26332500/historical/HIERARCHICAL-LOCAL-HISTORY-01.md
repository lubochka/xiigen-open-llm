# HIERARCHICAL-LOCAL-HISTORY-01 — адресовать обученное состояние внутри правильного кластера

**Статус:** `AUTHOR_WORK_ORDER_ONLY / NOT_IMPLEMENTED / NOT_RUN`. Эта карточка описывает будущий маленький опыт; host и команда ниже пока не реализованы. Текущая сессия только документирует. Нельзя запускать опыт или исправлять продукт на основании наличия этой карточки.

**Тема обучения:** оркестрация, последовательность проверки и сохранения задачи. Это один домен с несколькими классами событий. **Учебный механизм:** нативный счётный `BigramMarkov` из 34/E05; не SFT/DPO и не LoRA. **Модель исполнителя:** та же модель и настройки по умолчанию, что в его текущей сессии; не выбирать другого агента/провайдера. **Внутреннее имя host:** HCL01.

## 1. Причина и связь с настоящим обучением

В текущем [E05:108–123](https://github.com/lubochka/llm_mvp_core/blob/26332500f76ea8345256c73ecfd44c0023b7e883/34.Experiments/Experiments/E05HierarchicalPrediction.cs#L108-L123) `withinBigrams[c]` обучается на подпоследовательности только кластера c. Но [E05:128–147](https://github.com/lubochka/llm_mvp_core/blob/26332500f76ea8345256c73ecfd44c0023b7e883/34.Experiments/Experiments/E05HierarchicalPrediction.cs#L128-L147) подаёт в модель предсказанного кластера локальный номер текущего токена, который может принадлежать другому кластеру. Номера из разных списков [E05:98–106](https://github.com/lubochka/llm_mvp_core/blob/26332500f76ea8345256c73ecfd44c0023b7e883/34.Experiments/Experiments/E05HierarchicalPrediction.cs#L98-L106) не обозначают одинаковые состояния.

[BigramMarkov.Train:24–41](https://github.com/lubochka/llm_mvp_core/blob/26332500f76ea8345256c73ecfd44c0023b7e883/34.Experiments/Core/MarkovChain.cs#L24-L41) строит реальные счётчики из уроков, а [Predict:48–62](https://github.com/lubochka/llm_mvp_core/blob/26332500f76ea8345256c73ecfd44c0023b7e883/34.Experiments/Core/MarkovChain.cs#L48-L62) читает их. Поэтому проверяется выдача действительно обученной модели, а не статическая замена словаря.

**Один фактор A/B:**

- A — текущее чтение: `withinBigrams[predCluster].Predict(tokenToLocal[curToken])`.
- B — то же обучение и тот же `predCluster`, но чтение: `withinBigrams[predCluster].Predict(lastObservedLocal[predCluster])`. История обновляется текущим наблюдаемым токеном до предсказания следующего. Будущий правильный токен не используется.
- Если у целевого кластера ещё нет наблюдавшегося члена, общий лабораторный контроль использует `predLocal=0`. Это **не буквальное native-A** для произвольного no-history случая: исходный A всё равно читал бы чужой curLocal. Все 16 назначенных query имеют наблюдённую историю целевого кластера; этот контроль не должен сработать ни разу. Записать `no_target_history_count=0`; иначе основной экзамен считать неверно исполненным, не приписывать результат исправлению localId. No-history поведение оригинала эта карточка не исследует.

**Не менять одновременно:** фильтрацию `localSeq`, формулу обучения счётчиков, выбор следующего кластера, tie-breaking, fallback, семантические labels. Вопрос «следует ли вообще обучать на отфильтрованной подпоследовательности?» здесь не решается.

## 2. Точная граница и оригинал будущего исправления

Будущий эксперимент изолирует локальную обучающую часть E05 с заранее заданной кластеризацией. Он не запускает внешний kMeans и BPE. Это осознанный общий для A/B контроль, который исключает случайное изменение кластеров. Guard оригинального полного E05 о 50 увиденных токенах остаётся в продукте без изменения; к выделенной локальной части он не применяется. Нельзя выдать эту проверку за полный повтор исходного E05 или RP01.

При подтверждении кандидат исправления оригинала относится к `34.Experiments/Experiments/E05HierarchicalPrediction.cs:125–147`: хранить последнее наблюдённое локальное состояние по кластеру, передавать в within-модель состояние того же кластера, сбрасывать историю между независимыми последовательностями. Обучение `108–123` сохраняется. Никаких правок этого файла в опыте; интеграция — отдельное решение пользователя.

## 3. Фиксированный набор одной темы

Глобальные IDs и значения:

| ID | Событие | Кластер | Канонический localId |
|---|---|---|---|
| 0 | validate_input | A=0 | 0 |
| 1 | validate_schema | A=0 | 1 |
| 2 | validate_policy | A=0 | 2 |
| 3 | persist_input | B=1 | 0 |
| 4 | persist_schema | B=1 | 1 |
| 5 | persist_policy | B=1 | 2 |
| 6 | heartbeat | C=2 | 0 |

TRAIN-before: `[6]` повторить 16 раз.

TRAIN-after: `[6]×16 + [0,3,1,4,2,5]×20 + [6]×16`, ровно 152 токена. Это одна заранее назначенная последовательность оркестрации с одинаковыми граничными переходами для A/B. Не добавлять перевод, wiki-темы, другую предметную информацию или новые случаи по результатам экзамена.

В каждом состоянии создаётся свежая нативная модель и вызывается настоящий `Train`: before на первом наборе, after на расширенном. Это сравнение приобретения состояния через повторное обучение, **не продолжение checkpoint**: исходный `BigramMarkov.Train` заново выделяет counts. Сохранить оба набора и обученные counts в диагностике; не обещать resume, которого у исходного API нет.

Фиксированный EXAM из двух независимых последовательностей:

1. `cross_cluster`: префикс `[2,5]`, затем `[0,3,1,4,2,5]×2`. После наблюдения префикса предсказывать ровно 12 следующих токенов; вначале `5→0`, затем остальные 11 переходов. Префикс не добавляется в TRAIN.
2. `same_cluster_control`: `[6,6,6,6,6]`; после первого наблюдаемого 6 предсказывать 4 следующих 6.

Итого одинаковые 16 query IDs во всех условиях. При каждом query читать только текущий и ранее наблюдавшиеся токены. История reader сбрасывается между двумя последовательностями, обученная таблица остаётся.

**Ненулевое «до»:** четыре heartbeat-перехода должны читаться из реально обученной строки C. Записать её положительный счётчик. Если правильных обученных контролей нет, учебный запуск недействителен; не заменять его сдвигом margin или статическим свойством ID. Отдельно показывать правильные угадывания/fallback на ещё не выученных A/B-переходах.

Проверить также приобретение хотя бы одного нового правильного cross-cluster ответа after относительно before в одном из A/B, с чтением положительной обученной строки. Если ни одно плечо не приобрело новый переход, цель проверки влияния новых уроков остаётся OPEN. Полезный ресурсный результат на уже обученном контроле сохраняется отдельно. Постоянный ответ `6` даёт ровно 4/16 на назначенном EXAM: это аналитический нижний контроль, не обученная модель и не измеренное в этой сессии значение. Будущий host должен показать его рядом, чтобы одноклассовый heartbeat не выдавался за усвоение нового цикла.

## 4. Предписанный различающий контроль

Повторить реальный fit обоих состояний и плеч, переставив только список членов B: `[5,3,4]` вместо `[3,4,5]`. Глобальные IDs, порядок TRAIN/EXAM, принадлежность кластеру, gold и все остальные параметры неизменны. После предсказания декодировать localId обратно в глобальный ID.

Это четыре сочетания `A/B × canonical/permuted` и два состояния `before/after`, всего восемь обучений иерархии. Они включают ровно 24 нативных вызова `Train`: четыре before × (cluster+C) = 8 и четыре after × (cluster+A+B+C) = 16. Ученик получает 128 экзаменационных query (8 × 16); постоянный контроль вычисляется отдельно на тех же 16 IDs, не вызывает Train. По назначенным данным ожидаются 128 вызовов cluster-Predict и 80 within-Predict, всего 208 нативных Predict; фактические счётчики записать, а не подменять этим расчётом. Перестановка — диагностический контроль одного механизма, не второй ремонт. Сравнить **семантические предсказания по каждому query ID**, а не только агрегат: перестановка может перенести ошибки с A→B на B→A, оставив суммарную точность такой же.

Ожидание гипотезы: B уменьшит ошибку чтения чужой строки и будет семантически инвариантен к перенумерации. Это ожидаемый, ещё не измеренный результат. Его отсутствие или регрессия фиксируются без попытки подобрать другой набор.

- `.../Program.cs`: генерация строго описанных train/exam, цикл eight-fit, A/B reader, замеры, запись результата.
- `.../Native/MarkovChain.cs` и `.../Native/ExperimentTypes.cs`: буквальные копии файлов `34.Experiments/Core/` с pinned core. Не переписывать Markov по памяти; сохранить license.
- `.../Native/E05LocalTraining.cs`: выделенная логика `E05:93–123`, с параметром заранее заданного `tokenToCluster/clusterMembers`. Математика обучения без изменения; диагностический снимок counts допускается в локальной копии без изменения решений.
- `.../results/run-NNNN/` и исходные `train.json/exam.json` этого host.

Файл csproj не должен компилировать результаты или другие проекты. Отключить импорт родительских `Directory.Build.props/targets`: использовать `<Project>` без атрибута Sdk, сначала задать `ImportDirectoryBuildProps=false`, `ImportDirectoryBuildTargets=false`, `EnableDefaultCompileItems=false`, затем явный `<Import Project="Sdk.props" Sdk="Microsoft.NET.Sdk" />`; после настроек и списка `<Compile Include="Program.cs" />`, `<Compile Include="Native/*.cs" />` завершить явным `<Import Project="Sdk.targets" Sdk="Microsoft.NET.Sdk" />`. Таким образом продуктовые build-gates не наследуются. Зафиксировать исходный ref/sha и hash каждой локальной копии. Исторические IDs E05 и 35/E05 различны.

**Будущая команда после создания host, из корня checkout:**

`--run-id auto` — обязательная функция данного host: резервировать первый свободный `results/run-0001`, `run-0002` и т. д. через create-new lock; никогда не удалять и не перезаписывать старую папку. Записать выбранный путь до fit. При коллизии занять следующий номер. Это спецификация будущей реализации, не утверждение о существующем флаге.

## 6. Измерения, успех и отчёт

Результаты по каждому query: condition, stage, source globalId/cluster/localId, predictedCluster, использованная строка target learner, gold/predicted globalId, correct, fallback, query ID. Дополнительно — hash таблиц, реальные counters, elapsed fit/eval, allocated bytes с честным названием, retained state bytes. `GC.GetAllocatedBytesForCurrentThread` не называть peak memory.

Для каждого условия показать correct/total before и after на тех же 16 IDs; отдельно cross-cluster, A→B, B→A, heartbeat. Между A/B показать изменения всех полезных метрик и регрессии. Предсказания canonical/permuted сравнивать после семантического декодирования.

**Любое измеренное улучшение полезного показателя считается успехом по этому показателю и этой теме; рост accuracy не обязателен.** Улучшение времени не требует +5% точности. Наблюдаемую полезную дельту времени сохранить как успех наблюдаемого показателя; её причинность, устойчивость и возможный шум обозначить отдельно как неизвестные — они не отменяют саму запись. Но 0 правильных ответов до и 0 после не являются допустимым учебным опытом; показатели среды или статическая инвариантность без fit его не заменяют. Не использовать старый `ExperimentResult.Passed/ABANDON` как вердикт карточки.

`report.md` на русском, порядок: что проверено → таблица before/after → улучшения → ухудшения → конкретные query-примеры → смысл для темы → границы (нет kMeans/BPE/RP01) → кандидат и место будущего исправления. `metrics.json` содержит сырые числа, `predictions.jsonl` — все решения. При измеренном успехе добавить кандидата **только в результат этого опыта**, не менять общий `required-changes.md` прошлой задачи без отдельного поручения.

## 7. Бюджет, ожидание и управление задачей

Один host, восемь коротких обучений иерархии, 24 нативных Train. Лимит учебного run — 120 секунд; это достаточный бюджет для 152 токенов счётной модели, а не четыре микрошагa нейросети с заведомо пустым «до». Допускается одна локальная коррекция compile/plumbing и один повтор с новым run ID **только если доказано, что не начался ни один Train**. После частичного или полного обучения запрещено автоматически повторять fit ради plumbing, отчёта или удобного результата: восстановить отчёт из сохранённых raw; при нехватке данных записать ограничение. Не расширять набор, не запускать solution tests, full production gates или автоматическую интеграцию.

Исполнитель сначала обнаруживает доступный инструмент выполнения и ожидания. Для `exec_command`, вернувшего `session_id`, ждать тот же процесс через `write_stdin`; для `functions.exec`, вернувшего `Script running with cell ID`, использовать `functions.wait` с тем же cell ID. Для другого окружения читать документацию его инструмента ожидания. Интервалы ожидания до 60 секунд, с коротким прогрессом; отсутствие нового stdout или файла не означает остановку процесса. Не запускать дубликат, пока нет терминального exit/status. После выхода проверить завершённый metrics и manifest; незавершённый run не превращать в нулевой учебный результат.

**Запрет поведения из приведённого пользователем примера:** после прямого указания закончить текущий опыт или перейти к следующему ID запрещено продолжать прежние правки, дописывать старый реестр, повторно запускать прежний опыт или «ещё немного проверять». При STOP прекратить работу; при NEXT следовать названному ID. Не делать дополнительного поиска места, модели и формата отчёта — они заданы здесь. Явный новый ID важнее порядкового номера.
