# Приоритеты, принятие дополнений и граница исполнения

## 1. Что является реестром

Для уже существующей программы единственный реестр — [canonical execution index на проверенном core SHA][canonical]. Там 50 постоянных ID: 13 сохранённых/частичных попыток и 37 будущих проектов. P01–P125 не образуют вторую очередь. Новые документы этого пакета не переписывают тот индекс и не назначают повтор старого run.

Если пользователь уже назвал текущий/следующий ID, он имеет приоритет. Если назначения нет, актуальный README задаёт **PARENT-ADOPTION-01 → N63-INGRESS-LENGTH-LEARNED-01 → завершение открытой учебной цели N63C**. Это правило продолжения работы, а не разрешение начать обучение в нынешней документной сессии. [README][canonical-readme], [карточки и сверка](audit/README.md).

`registry.json` рядом — **реестр документных добавлений и их готовности**. Он не заменяет canonical dispatcher. Для трёх новых ID задан внутренний порядок принятия; до авторства host и отдельного назначения исполнения все имеют `AUTHOR_WORK_ORDER_ONLY / NOT_IMPLEMENTED / NOT_RUN`.

## 2. Порядок работы

| Порядок | Что делать | Конкретный результат | Что не считать выполненным |
|---|---|---|---|
| 0 — прямо назначенный пользователем ID | Выполнить новое указание; при STOP прекратить действия, при NEXT немедленно перейти | Краткий фактический статус с имеющейся информацией | Не возвращаться к прежнему report/commit/retry ради «ещё одной полезной проверки» |
| 1 — разблокировка обучения | Следовать текущим PA01 / исправленному ingress / N63C recipes и их потребителям обученного состояния | Реальный learned before, фактические updates, сопоставимые before/after; отсутствие 0→0 под видом результата | Не повторять сохранённые старые attempts; source-only исправление карточки не означает успешное обучение |
| 2 — конфликты карточек | Согласовать literal launch contract GRAD-ACCUM-COPY-01 и FROZEN-BROADCAST-MAP-01; затем маркировку темы WIKI-FEATURE-KEYS/FEATURES-ONCE | Одна исполнимая команда с явно выбранным runtime во всех владельцах, точные ссылки; проект резолюции в [аудите](audit/README.md) | Нынешняя сессия не меняла защищённые docs; наличие pwsh/его версии на машине не проверялось |
| 3 — поступившие обновления и три новые гипотезы | Сначала учесть уже принятые исправления current core, затем принять новые карточки ниже без дублирования | Новый фактор получает автора, source-copy host и отдельное состояние готовности | Не называть эти документы уже реализованными или уже включёнными в protected registry |
| 4 — зависимые/периферийные проверки | Только после прямых учебных задач, при наличии доказанного обучающего producer/consumer | Отдельный назначенный опыт, если найден реальный learning link | StackAndVersion self-oracle сейчас только приложение; исправление regex без learner не получает учебный бюджет |

## 4. Проверяемость карточек и исключения эксперимента

У каждой карточки есть фиксированные данные одной темы, код оригинала, единственный A/B фактор, before/after, бюджеты, место host, будущая команда, правила report и ожидания. Общий формат отчёта — русский; модель исполнителя — текущая по умолчанию, без override. Артефакты и приобретённое состояние сохраняются в назначенном каталоге с запретом перезаписи.

Разрешение на ограниченный source-copy эксперимент не превращается в право менять product code, protected docs, выполнять полный CI или отправлять результаты от имени пользователя. Полная производственная цепочка рассматривается после измеренного результата и решения Любы. Успех метрики не равен готовности к интеграции.

Исторические HCL/SVD специально выделяют нативное обучающее ядро и общий лабораторный контроль. Они не обещают полный повтор kMeans/BPE/корпусного runner. CS01 использует штатный Trainer и настоящий обученный S0; recipe ещё не исполнен. Такие границы делают маленький опыт интерпретируемым и не скрываются под словом «нативный».

## 5. Как обработать результат без продолжения старой задачи

В рамках назначенного текущего опыта сохранить actual execution status, before/after и candidate с численной полезной дельтой, включая все регрессии. Если строка завершила обучение, а summary упал, сначала читать сохранённые arm results; не выдавать этот случай за отсутствие обучения и не повторять Train ради отчёта.

После явного NEXT больше не дописывать прошлую карточку, `required-changes`, отчёт или коммит. После STOP не делать новых tool calls ради «фиксации урока». Если собственный процесс ещё жив, допускается только необходимая безопасная отмена по уже известному handle/PID и подтверждение прекращения. Состояние уже запущенного процесса сообщать по известному handle, не выдумывать завершение и не создавать замену. Точный новый приказ пользователя выше любого автоматического порядка.
