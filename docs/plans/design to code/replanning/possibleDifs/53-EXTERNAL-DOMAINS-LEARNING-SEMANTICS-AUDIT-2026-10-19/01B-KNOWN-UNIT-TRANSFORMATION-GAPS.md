## 1. Ограничение embedding до 64 и разные поля vector/lexical signal

**Источник:** [`LlmIngredientLogicalUnits.cs:114–130`](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L114-L130) задаёт `EmbeddingModel(maxLen: Math.Min(64, ContextLen))` для индекса. [Там же:181–192](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L181-L192) embedding query → HNSW → fusion; [217–243](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L217-L243) lexical score берётся по `example.Text`, vector/lexical/pattern веса 0.45/0.35/0.20. Конкретный consumer: [`GeneratedCapabilityFlow.ExecuteAsync`, `DefaultLogicalCapabilityTrainer.cs:7383–7396`](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs#L7383-L7396) передаёт canonical query в этот unit.

**Риск:** важная поздняя часть обучающего/пользовательского текста может перестать влиять на vector component при ограниченном embedding. Lexical component может компенсировать это, поэтому факт cap сам по себе не доказывает неверный final rank. Особо проверить длинную документацию, код с одинаковым заголовком и поздним различием условий, инструкции с поздним отрицанием. Это не universal аргумент за AST: документы и перевод требуют своих признаков.

**Малый тест:** две разрешённые памяти и два heldout запроса с одинаковой ранней частью, противоположным late condition; записать actual tokenizer IDs и позицию условия. A=current; B=один контролируемый больший maxLen либо query-aware span при том же tokenizer/model/corpus. Снять cosine, BM25, pattern, выбранную запись, конечное law score. Если late condition уже различается в actual embeddings и selection корректен, causal cap-гипотеза для панели не подтверждается. Не считать 64 символами и не менять одновременно LoRA/нормализацию.

## 3. Learned tokenizer corrections и executor обучаются на разных KNN keys; RuleTags теряются из двух ключей

[Helpers:150–160](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L150-L160) включают concepts/POS, но не RuleTags. **Concrete consumer:** [Executor training `TranslationTrainedUnits.cs:417–422`](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L417-L422) пишет full key из example, а prefix/structure вычисляет **новым base tokenizer**. Inference [333–345](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L333-L345) ищет cascade по пришедшим token signatures; [`TranslationMachine.cs:716–737`](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationMachine.cs#L716-L737) компонует trained semantic tokenizer и direction executors вместе. **Малый тест:** RU→EN две пары одного concept skeleton с различными грамматическими/отношенческими тегами, плюс tokenizer DPO correction. Записать training keys, inference keys и источник выбранного кандидата до/после correction; heldout source должен отличаться, чтобы exact-source map не маскировал проблему. Фальсификация: correction не активируется, corpus содержит оба corrected ключа либо более ранняя learned memory законно решает heldout без KNN. Для EN→RU применимость RuleTags отдельно подтвердить; не переносить RU morphology автоматически на все направления.

## 4. В phrase reuse позиция в сокращённом массиве применяется к исходному массиву токенов

**Источник:** [`TranslationTrainedUnits.cs:798–807`](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L798-L807) нормализует токены и удаляет пустые, создавая компактный `sourceTokens`. Цикл phrase matching идёт по его индексам, но fallback [824–844](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L824-L844) берёт `tokens.Tokens[Math.Min(i,…)]` из исходной последовательности. Если нормализация превратила пунктуационный токен в пустой, связи позиция→токен расходятся.

**Concrete consumer:** [Executor.Execute:266–271](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L266-L271) возвращает phrase-map output до word-map/KNN. Поэтому корректное обучение phrase/word mappings может выглядеть испорченным при пунктуации на inference.

**Малый тест:** frozen phrase map + word mappings; два heldout предложения с одинаковыми содержательными словами, различающиеся только отдельным punctuation token перед unmapped-by-phrase словом. A=current; B сохраняет пару `normalizedText, originalToken` в компактном массиве. Снять indices, coverage, слова результата, adapterId. Контроль: пунктуация без удаления токена и неизвестное слово. Выигрыш должен быть в сохранении нужного слова, не только в coverage/confidence. Применимость зависит от actual tokenizer emitting отдельного punctuation token; source без такого элемента не активирует дефект.

## 5. Морфологический augmentation применяется без POS / sense guard

**Источник:** [`TranslationTrainedUnits.cs:427–448`](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L427-L448) вызывает `DeriveGenderAlternateForm` для каждого word mapping и matched lemma. [Helper:774–795](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L774-L795) проверяет длину, non-ASCII и окончания -ла/-л, но не POS, tense, lemma family или значение. Не всякое слово с этим окончанием — past-tense verb.

**Concrete consumer:** derived mapping попадает в те же таблицы; inference [860–882](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/27.TranslationDomain/TranslationTrainedUnits.cs#L860-L882) использует concept-aware mapping, затем surface fallback. Например панель «пила» как инструмент vs «пил» как действие требует защиты от ложного переноса; это предложенный gold case, не утверждение о выполненном native результате.

**Малый тест:** RU→EN 4 настоящие регулярные verb-пары и 4 noun/homonym near-collisions. A=current augmentation; B=augmentation только для подтверждённого verb-family либо одна явно выбранная дополнительная обучающая пара. Снять созданные keys и heldout перевод с новым source context, чтобы exact-source map не скрывал ложный surface alias. Сохранить выигрыш правильного gender transfer и не принять ложные homonym mappings. Если реальные POS/concept/direction guards уже блокируют alias до его использования, считать эту панель отрицательной. К остальным языкам эту функцию не переносить.
