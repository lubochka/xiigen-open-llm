# Приоритетная глава: восстановить полезное поведение external_domains через маленькие причинные опыты

Дата: 2026-10-19. Статус: исследовательский проект экспериментов; новые native прогоны не выполнены. Эта глава предлагает порядок восстановления и повторно проверенную первичную основу. Её исторические механизмы помечены KNOWN_PRIORITY: они уже обсуждались в прежних аудитах и не выдаются за новые гипотезы текущего пакета.

## С чего начать

Первым нужен маленький опыт «одни и те же входы → сохранённое обученное состояние → обычный ответ после нового запуска процесса». Затем следует восстанавливать конкретную доменную функцию, где обнаружен разрыв. Для C# это структурный KNN; для перевода — сохранённые контекстные соответствия, распознавание порядка и его использование; для нейронной ветви — подтверждённый путь от обновлённых параметров до ответа. Объединять все изменения в один запуск не следует: такой запуск не покажет, какое исправление помогло.

**Контракт ролей закреплён в RP01 и `replanning/AGENTS.md`:** CODEX с запрошенной моделью **Astra 6 ultracode** выполняет делегированный человеческий выбор урока; отдельный CODEX с той же запрошенной моделью независимо судит точную, неизменённую DPO-пару. Допущенная внешняя открытая китайская модель создаёт обе финальные стороны chosen/rejected. Качество обычных ответов Student оценивает отдельный examiner по заранее зафиксированной рубрике; reference policy остаётся отдельной ролью. Это проект будущего исполнения: реальные runtime IDs и receipts должны быть записаны при запуске; в данном исследовании таких вызовов не было. Исторические fixture-сценарии не объявляются вновь созданными DPO-парами. Источники: [replanning/AGENTS: роли и происхождение](https://github.com/lubochka/xiigen-planning/blob/a90350f33955f9c4b15707a4619eeeba5d42e863/llm%20mvp/design%20to%20code%20session/replanning/AGENTS.md#L25-L31), [RP01: роли и маркировка источника](https://github.com/lubochka/xiigen-planning/blob/a90350f33955f9c4b15707a4619eeeba5d42e863/llm%20mvp/design%20to%20code%20session/replanning/Kiro-Xiigen-RP01-Learning-First-Slice-Pack/README.md#L27-L31).

### Почему отрицательный результат матрицы не отменяет KNN

E07 обучает условную таблицу по ключу `(BpeId, AstNodeType, AstDepth)`; в E09 используется расстояние по типам и родителям AST, позиции, глубине и синтаксической роли. Это разные алгоритмы и представления. В E07 объявления tier2/3/4 называют новые измерения, однако реальные Train/Predict используют один и тот же трёхкомпонентный ключ. В E09 поле с именем BpeId вычисляется как локальный индекс SyntaxKind для каждого файла. Считать эти опыты переносом «одной и той же матрицы в KNN без иных изменений» нельзя. Исторический вывод, который стоит сохранить: **структура может быть полезна в расстоянии/извлечении кандидатов, даже когда не помогла конкретной условной таблице**. Причинность проверяется на общей задаче, общих метках и одних validation occurrences. Источники: [E07, Run и реально используемый ключ](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs#L34-L116); [MultidimensionalNGram](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs#L270-L317); [E09: split и сравнение](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E09StructuralKnn.cs#L21-L76); [E09: построение меток](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E09StructuralKnn.cs#L97-L118); [StructuralKnn: расстояние, Train и Predict](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/12.SemanticCompiler/Prediction/StructuralKnn.cs#L7-L30); [Train/TrainFromSource/Predict](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/12.SemanticCompiler/Prediction/StructuralKnn.cs#L100-L175).

## 2. Общий формат маленького опыта

До первого обновления записываются: exact commit SHA; класс и обычный вызывающий путь; исходный model/state artifact и его hash; tokenizer/feature/label schema и hashes; TRAIN, EXAM и retention occurrence IDs; направление перевода/домен; seed 42; все параметры; список разрешённых обучаемых параметров; фиксированный frozen reference; digest оценщика и рубрики. Одинаковый seed не заменяет одинаковый порядок строк: manifest содержит ordered IDs, а при replay ещё и реально выбранные IDs.

Каждый результат содержит четыре раздельных наблюдения:

1. Изменилось ли обучаемое состояние и какой именно его участок.
2. Изменилось ли решение указанного unit/ranker.
3. Изменился ли обычный доменный ответ и его независимая оценка.
4. Совпадает ли поведение после открытия сохранённого состояния в новом процессе.

Первый маленький запуск использует один фиксированный seed. Если обнаружен полезный paired-сигнал, повтор с seeds 11, 23, 47 разрешает конкретную неопределённость устойчивости. Это последующее уточнение; три повтора не являются обязательной церемонией перед первой проверкой.

На EXAM не изменяются weights, словарь, grammar, KNN memory, tokenizer или thresholds. Для предсказания следующего элемента вход должен содержать только контекст, доступный в реальном сценарии; разбор полного правильного продолжения нельзя незаметно использовать для извлечения признаков запроса. Если проверяется ранжирование уже данных завершённых кандидатов, этот другой контракт фиксируется явно.

## 3. P0 — одна доменная память, обычный потребитель и новый процесс

**Цель:** быстрее всего установить, сохранился ли полезный learned path. Этот опыт следует первым для домена, который выбран для ближайшего восстановления.

**Сначала проверить доступность исходного состояния:** найти конкретный исторический artifact, manifest, исходные данные и соответствующий loader; записать источник и hash доступных байтов. Если сохранённый artifact недоступен, первый шаг P0 — поиск источника и способа воспроизведения. В результате указать `SAVED_DONOR_ARTIFACT_NOT_AVAILABLE`; восстановление из сохранённой модели пока не проверено. Допустимая следующая работа — отдельно обозначенная реконструкция обучения из известного кода и фиксированных данных. Нельзя незаметно создать свежую или случайную модель и зачесть её запуск как восстановление донора.

**Минимальный объём:** четыре ранее изученных случая и четыре новых случая того же домена. В качестве самого дешёвого первичного профиля использовать четыре seen-expression и четыре unseen-expression из E13B; для перевода заменить их четырьмя принятыми контекстными соответствиями и четырьмя отложенными фразами. Число DPO/optimizer updates — 0.

**Плечи:** A — текущий обычный потребитель с исходным сохранённым состоянием. B — тот же потребитель после восстановления конкретного отсутствующего state/connection из подтверждённого донора. Имена unit и artifact в обоих плечах фиксируются; менять одновременно scorer и generator нельзя.

**Ход:** получить восемь ответов A; завершить процесс; открыть ровно тот же artifact и получить ещё восемь. Повторить для B. Итого 32 обращения к выбранному consumer. Никакой автоматической переиндексации EXAM при загрузке. Снять trace: loaded artifact hash, selected unit, consumed state hash, branch/fallback, ответ, причина отказа.

**Как оценить:** formula-профиль отдельно считает правильное воспроизведение изученного и false answers на неизвестном. Для перевода отдельно проверяются смысл, направление, действующее лицо, объект, отрицание и сохранение именованных сущностей. Совпадение serialization hash само по себе не доказывает правильный ответ.

**Решение:** если B меняет ordinary output в правильную по заранее заданному gold сторону и сохраняет его после нового процесса без потери прежнего навыка, найден конкретный кандидат восстановления. Если меняются только внутренние scores, следующая маленькая реализация — соединить этот ranker/unit с уже существующим потребителем и повторить те же восемь запросов. Если artifact теряет нужную память, следующая реализация — полный export/import соответствующего state; повторное обучение при load не используется как замена исправлению.

**Основание и новизна:** KNOWN_PRIORITY; E13B подтверждает достижимую функцию точной памяти, а не произвольную алгебру. [E13B: текущий критерий успеха](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E13BHeldOutValidation.cs#L12-L45); [Отдельные normalisation-пробы](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E13BHeldOutValidation.cs#L128-L135)

## 4. P1 — C#: вернуть структурный KNN без подмены задачи

**Домен:** C# AST retrieval/next-kind в пределах явно заданного контракта; перенос на обычный язык или SQL этим опытом не заявляется.

**Материал:** выбрать из зафиксированного C# корпуса 32 TRAIN-context occurrences и 16 EXAM occurrences. У каждого есть source file hash, span, текущий SyntaxKind, контекст AST и gold next-kind. TRAIN/EXAM разделяются по исходным occurrence IDs и неперекрывающимся контекстным окнам; для новой оценки качества использовать независимые семьи исходных файлов. Точный replay прежней панели хранится отдельно. Значения целевых классов могут повторяться. Проверять неизвестный output-label, которого модель принципиально не может выдать, как обязательное условие успеха нельзя.

**Первое вмешательство:** общий label codec на основе полных SyntaxKind; устранить переходы между файлами; одна EXAM-панель для обеих моделей. Эти условия выравниваются до сравнения механизма и не называются суммарно «эффектом KNN».

**Два варианта на одной панели:** A — условный baseline по текущему kind; B — `StructuralKnnPredictor.Train(pairs)` и `Predict(vector)` с историческим доменным distance. B не получает правильный next-kind во входном vector. Два Train и32 predictions достаточно для первой проверки. После неё отдельный контроль меняет только обработку конкретного недостающего признака — например, синтаксической роли; label mapping и shortlist сохраняются.

**Встроенная проверка learned path:** для одного заранее выбранного контраста обновить TRAIN memory релевантным известным примером и показать причинное изменение выбираемого класса. Если ordinary consumer не использует этого predictor, вернуть `DIRECT_COMPONENT_ONLY`, указать ближайший вызывающий seam и добавить узкий adapter только для этого профиля.

**Метрики:** per-case top1, список кандидатов до/после, top-k recall, tie outcome, abstention; затем16 одинаковых запросов через ordinary consumer до/после и после перезапуска. Полезный результат — новые правильные решения при сохранении прежних правильных; величина исторических+45% не является требуемым или обещанным порогом.

**Основание:** ранний E09 сохраняет маленький положительный сигнал при общей панели. Старые дефекты label/alignment/denominator уже известны; здесь они собраны в один выполнимый восстановительный порядок. ## 7. P4 — neural DPO: проверить место адаптации на двух одинаковых уроках

**Гипотеза:** при данном frozen base адаптация только q/v может уступать другому разрешённому месту адаптации. Это известная гипотеза из сравнений исторического neural donor, а не установленная причина RP01.

Исторический ProjectWiki runner действительно продолжал policy при исходном reference и получал положительные preference-метрики. Его scoring усреднял response log-probabilities, а tokenizer хешировал слова; эти особенности не следует менять одновременно с местом адаптации. Старый `RmsNorm` создавал detached Tensor в helper-умножениях — воспроизводить этот обрыв не требуется. Предшествующий аудит связывал фактическое изменение главным образом с output head; этот binary-аудит в текущей подзадаче не повторялся. **Материал:** два уже принятых DPO-урока; четыре заранее закрытых EXAM-запроса — два на изучаемое различие, два на retention. Один домен за запуск: C# documentation либо перевод. Учебные пары и ответы экзамена не меняются между плечами.

**Плечи:** A — текущая q/v-LoRA конфигурация; B — экспериментальная head-only адаптация на том же base. Оба плеча загружают идентичное полное policy state, включая уже существующие адаптеры; в B они остаются в forward, но заморожены. Head-only задаётся явно как другой target set, со списком имён и числом trainable параметров; изменение capacity не скрывается. Если для B отсутствует native experimental path, минимальная реализация — добавить такой изолированный режим в маленький runner, сохранив production admission. Исправлять старый gradient bug «обратно» запрещено смыслом опыта.

**Ход:** два последовательных update на каждом плече; всего4 optimizer updates. Четыре EXAM на A/B до обучения и после загрузки post-update artifact в новом процессе:16 собственных ответов и16 pair-score evaluations, если на каждом EXAM также задана неизменная пара кандидатов. Дополнительные диагностические forwards считаются отдельно. Initial policy logits/answers равны; reference, tokenizer, mask, reduction, LR, optimizer initial state, seed и порядок одинаковы.

**Что сохранить:** per-target gradient/update norms, effective LoRA BA delta, head delta, decoder logits, собственные ответы, frozen reference hash, exact masks, response lengths, причины rollback. При ненулевом gradient, но прежних ответах считать лишь промежуточный effect. Улучшение relative preference без более правильного ответа также записывается отдельно.

**Следующий шаг по результату:** при устойчивом улучшении B — рассмотреть минимальный допустимый head-adapter или target selection как отдельную реализацию. Если обе стороны не умеют базовую генерацию до обучения, проверить базовый языковой навык/токенизацию отдельным опытом; большой DPO sweep не отвечает на этот вопрос.

## 8. P5 — продолжение обучения: целостное состояние и ранний эффект

Этот раздел не требует автоматически повторять старые DPO-обновления. Он проверяет, сохраняется ли уже принятый навык при одном следующем уроке.

**Домен:** выбрать тот же, в котором предыдущий tiny опыт уже продемонстрировал конкретное полезное поведение. Нужны два источника проверки: четыре старых задания и четыре новых/контрастных.

**Плечи:** A — непрерывное обучение от сохранённого принятого состояния; B — новый процесс, импорт того же состояния и тот же следующий update. Policy, исходный reference, optimizer moments/step, tokenizer, KNN memory, registry/selector и curriculum cursor должны иметь явно заданную семантику переноса; пропуски не маскируются нулевыми defaults.

После одного одинакового update сравнить восемь одинаковых ответов/оценок и фактические изменённые state-компоненты. Если A и B расходятся, исправляется конкретная часть export/import; это опыт восстановления, 0 дополнительных широких CI.

Для исследования replay после исправления persistence нужен отдельный фактор: одинаковые current examples, 0% против заранее зафиксированного небольшого replay. Выбранные replay occurrence IDs фиксируются до оценки; сравниваются retention и new-task quality при записанном фактическом числе updates. Исторический E43 не оправдывает слепой повтор всей истории и не подтверждает neural forgetting: он строил отдельные count models. [E43: три отдельные таблицы, а не последовательные neural weights](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E43ReplayBuffer.cs#L18-L50)

Для исследования sample efficiency снимать кривую на 2/4/8 одинаковых новых уроках. Это быстрее и содержательнее, чем судить о переносе только по последней точке.
