# Восстановить обучение из `external_domains`: с чего начать

Дата: 19 октября 2026. Это исследование и постановка коротких опытов. Новое обучение в .NET в этой сессии не запускалось.

## Главный вывод

В `external_domains` действительно сохранены положительные результаты. Они относятся к конкретным алгоритмам: обученной памяти порядка частей речи, выбору значения по контексту, соседям по структуре кода и повторному предъявлению старых переходов. Для восстановления нужно вернуть всю связь «данные → изменяемое состояние → обычный ответ → сохранение → тот же ответ после загрузки» для каждого получателя.

Часть исторических классов уже есть в текущем дереве. Поэтому перенос файла сам по себе не восстанавливает способность. Например, обучаемый `SemanticCompiler.PatternClassifier` хранит примеры POS-последовательностей, а используемый нынешним `TransformerLlmLogicalUnit` классификатор `SemanticCompiler29.PatternClassifier` выводит роли фиксированными списками слов. Они имеют одинаковое имя, но разные механизмы. Это известное различие, заново проверенное здесь, а не наша новая гипотеза. [Обучаемая память](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/12.SemanticCompiler/Translation/PatternClassifier.cs#L29-L81); [нынешняя классификация](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/29.SemanticCompiler/Translation/PatternClassifier.cs#L24-L65); [реальный потребитель и бонус 0.20](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L213-L294).

Нынешние исправления нейронного обучения следует сохранить: у старого `DpoTrainer.BackwardLogProbs` заполнение `logits.Grad` заканчивалось без вызова обратного прохода по графу; в текущем коде есть `(oneHot-softmax)` и `logits.Backward`. Положительные результаты других алгоритмов старой ветки не являются основанием возвращать этот старый участок DPO. [Старый код](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/11.DPO/DpoTrainer.cs#L219-L263); [текущий код](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/11.DPO/DpoTrainer.cs#L1071-L1146).

## Почему неудача матричного варианта не отменяет KNN

E07 и E09 помещают структурную информацию в разные алгоритмы. В E07 меняется ключ контекста в счётной модели; в E09 меняется расстояние до обучающих соседей. В майском архиве E07 tier2 имеет 14.74% → 12.45%, а E09 имеет положительный результат из таблицы. Из этих двух наблюдений следует разумный приоритет для проверки структурного KNN. Из них не следует величина чистого выигрыша «матрица → KNN» на одинаковых данных: задачи, метки и знаменатели различаются. [E07 квитанция](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/results/e01-e53-tier4-20260507-190227/E07-STRUCTURAL-CONTEXT-TOKEN/results/run-2026-05-07-002.json); [E09 две разные панели](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E09StructuralKnn.cs#L25-L72).

Для чистого сравнения R3 ниже задаёт одну цель, одни семьи файлов, одну панель и один словарь меток. Нынешнюю схему E09 с локальным `kindMap` на каждый файл и отдельным `val.Take(500)` нельзя переносить в этот опыт без исправления сравнимости. Это известные измерительные разрывы, а не основание обнулить исторический успех. [Источник локальных меток](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E09StructuralKnn.cs#L97-L119).

## Приоритетный список коротких восстановительных опытов

### R0. Установить, какое обученное состояние читает обычный ответ

Это первый диагностический шаг, 0 обновлений. Выбрать одну задачу перевода и одну задачу описания C#; для каждой записать конкретную Unit, хэш входных данных, загруженные веса/память, encoder и вызванные методы. Загрузить доступный исторический checkpoint через его настоящий загрузчик. Если совместимого состояния/загрузчика нет, зафиксировать конкретную несовместимость; для перевода перейти к R1, для C# к R3 на явно свежей памяти. Недоступный исторический checkpoint не заменяется случайной нейронной моделью под видом проверки старого успеха.

Сначала это trace и проверка совместимости. Однофакторное A/B «текущая регистрация / явно выбранный исторический получатель» допустимо лишь при одинаковой семантике состояния, encoder, payload и prediction. Преобразование schema — отдельный шаг. Наблюдение: состояние действительно прочитано; получен собственный ответ; новая загрузка без обучения сохраняет этот ответ. Два одинаково неправильных ответа доказывают только воспроизводимость. Владельцы прежних работ: [P25](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/docs/plans/replanning-possible-diffs/experimets/cards/P25-cold-restore.md), [ранее собранное восстановление Units](../PREPARETOGPL-UNITS-RESTORE-2026-10-18.md).

### R1. Вернуть обучаемую память порядка E25

**Тема:** перевод; сначала задача классификации POS-порядка, затем отдельная проверка выбора примера в обычном ответе. **Получатель:** исторический `SemanticCompiler.PatternClassifier` внутри существующего владеющего Unit. Создание ещё одной независимой модели перевода для этого опыта не требуется.

R1a: A — исторический `PredictByRules(pos)`, B — `Train` на 24–48 POS-примерах и `Predict(k=3)`. Оба плеча получают одинаковый `int[]` POS и один словарь классов. 16 новых последовательностей разделить по семейству шаблона. Перемешанные метки — отдельный контроль; пустая память вызывает fallback к правилам, а не доказывает полное отсутствие способности.

R1b: подключение к нынешнему `SemanticCompiler29` проверяется отдельно. Нынешний `Classify(string[])` и эвристический `InferPos` не имеют автоматически той же схемы POS и классов, что исторический E25. Нужны явные encoder/ontology adapters с одинаковой семантикой в обоих плечах. У существующего `ScoreCandidates` pattern equality добавляет бонус 0.20 к ранжированию. Поэтому измеряются сначала класс, затем выбранный `ExampleId` и собственный сохранённый `Output`; классификатор сам не переставляет слова в переводе. Если класс изменился, а выбранный пример и ответ нет, разрыв находится после классификатора. [Старый API](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/12.SemanticCompiler/Translation/PatternClassifier.cs#L29-L81); [текущий потребитель](https://github.com/lubochka/llm_mvp_core/blob/44507823fc5aaeab4c3f0fe4e9da9ce924c6ec76/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L213-L294).

Сохранить POS-последовательности, метки, k, distance и encoder; восстановить память в новом процессе и повторить 16 случаев. Затем отдельная проверка нового урока: `Train` заменяет весь список, поэтому передать versioned old-memory + один новый допустимый пример, а не `Train([new])`, стирающий старые записи. Владельцы: [пакет48](../48-LANGUAGE-TRANSLATE-AUDIT-2026-10-19/03-SMALL-DOMAIN-EXPERIMENTS.md), [пакет47](../47-LANGUAGE-TRANSLATE-INTERNALS-AND-NEW-HYPOTHESES-2026-10-19/01-LANGUAGE-TRANSLATE-RESTORATION-FIRST.md). Здесь приоритет привязан к требуемой ветке `external_domains` с сохранением нынешних исправлений DPO.

### R2. Восстановить обе стороны контекста E26

**Тема:** перевод; задача — выбор значения технического многозначного слова. Сначала replay 15 архивных случаев проверяет проводку. Затем 12 новых пар контекстов проверяют применимость. Этот словарь принимает POS-соседей, поэтому для основного сравнения нужны различающиеся POS-входы, например разные архивные профили «поток» с VERB слева, ADJ слева или NOUN справа. Лексически разные значения при одинаковых SourceWord/POS — отдельный отрицательный профиль: одна только передача двух сторон контекста не может их различить. A читает только существующий суженный контекст, B — тот же словарь и те же кандидаты, но `ContextBefore` и `ContextAfter` проходят до `TranslateWithContext` без потери. Обновлений словаря в этом сравнении нет.

После успешной проводки отдельный опыт добавляет новое значение на 8 разрешённых примерах через существующий `AddEntry` и проверяет 8 новых контекстов. Для настоящего DPO-урока нужна проверенная typed projection в SourceWord, ContextBefore, ContextAfter, Translation и Priority с сохранением provenance и смыслового контраста; прямой вызов AddEntry сам по себе не удостоверяет весь DPO→Unit путь. `BuildDefault()` не является новым обучением. [API и поля записи](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/12.SemanticCompiler/Translation/ContextualDictionary.cs#L8-L22). Неизвестный POS не равен подтверждённому совпадению. Порядок и кратность контекста проверять отдельно от наличия двух сторон. Прежние владельцы: [K44-01/02](../44-E26-UNKNOWN-CONTEXT-AND-ORDER-2026-10-19.md), [проверка неизменности E26](../51-GOLD-BRANCH-EXPERIMENT-CODE-PARITY-AND-E26-DETERMINISTIC-LOOKUP-2026-10-19.md).

### R3. Проверить структурный сигнал в KNN на сопоставимой задаче

**Тема:** язык программирования; профиль — C# AST. R3a воспроизводит собственные контракты исторических E07/E09. R3b — новый сопоставимый harness: 24 небольших семейства методов, 16 для памяти, 8 для проверки; родственники одного шаблона находятся только в одной части. Пары строятся внутри метода/файла. Цель одинакова: следующий AST-kind из одного глобального словаря; панель одинакова без отдельного `Take(500)` в одном плече.

Три плеча R3b: A — bigram без структуры; B — контекстный ключ со структурой; C — KNN k=5. Если проверяется именно перенос места применения одного сигнала, B/C получают один и тот же заранее закреплённый structural feature schema и те же значения. Полный исторический `StructuralVector` можно добавить отдельной составной конфигурацией; её преимущество нельзя приписать только смене estimator. Исторический E07 предсказывал BPE, E09 — AST-kind; этот новый harness не является повтором их прежних процентов. [E07](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E07StructuralContextToken.cs); [E09](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E09StructuralKnn.cs).

Primary — точность следующего AST-kind, rare-class результаты, время и память. После выбора полезной оси отдельное A/B текущего consumer меняет только эту ось. Порядок `x == null` и `Save(x)`, тело вызываемого метода и невызванная локальная функция — уже проверки семантики собственного ответа на следующем этапе, не следствие улучшившегося AST-процента. AST-сигнал C# не включать как универсальный бонус для перевода или SQL: у них другие representation и parser. Прежние владельцы: P16/P26/P27/P28 и [E14 nested guard](../48-LANGUAGE-TRANSLATE-AUDIT-2026-10-19/02-NEW-HYPOTHESES.md).

### R4. Вернуть обучаемый TrustScorer E40V2

**Тема:** документация и качество её источников; задача — LOW/MEDIUM/HIGH по происхождению, тестам, возрасту, популярности и соответствию предмету. Архивный replay сравнивает исходное правило `IsInternal || IsOfficialDocs ? HIGH : MEDIUM` с памятью 7 признаков и k=5. Затем отдельное A/B сопоставляет нынешнюю фиксированную сумму с той же KNN-памятью, сохраняя class labels и пороги преобразования score→класс. Сначала одна и та же архивная панель и затем 18 новых проверочных источников, по 6 в каждом классе, отделённых от train по семейству признаков/источнику. Сами семь признаков одинаковы в A/B. Подмена свойств внешнего источника признаками capability-кандидата — другой, отдельный фактор.

Показать confusion matrix, состав памяти и реакцию на один новый размеченный пример. Наличие train-памяти проверяется отдельным перемешиванием меток; качество обычного отбора источников — собственным A/B в том consumer, которому действительно нужен этот контракт. Отсутствие такого consumer ограничивает вывод уровнем классификатора. После сохранения и новой загрузки повторить панель. Получатель — существующий владеющий Unit/сервис, новая универсальная «модель доверия» для всех предметов не требуется. Исторический успех этого опыта — 21 из 21 на повторяющихся шаблонах; положительный результат новой панели заранее не предполагается.

### R5. Проверить повторение старых знаний E43

**Темы:** документация и язык программирования; последовательные семьи материала для одного получателя. В архивном E43 обе сравниваемые счётные модели строятся заново: на newPairs и на newPairs+выбранные oldPairs. Это не продолжение весов общего parent. Первое действие — replay именно такого count-model алгоритма с явными границами файлов. [Источник E43](https://github.com/lubochka/llm_mvp_core/blob/3036a01acec938f0b83fa4ffbda26202cc35d639/35.ExperimentsV2/Experiments/E43ReplayBuffer.cs#L18-L50).

Следующий маленький контраст распределяет один бюджет: A получает 12 новых предъявлений, B — 8 новых + 4 старых. Это компромисс между удержанием и числом новых предъявлений, не чистый выигрыш replay при одинаковом объёме нового обучения. Старые проверочные семьи не попадают в replay. Сообщить точность на обеих панелях и фактический состав памяти. Если нужен другой вопрос — одинаковые 12 новых плюс 4 старых — честно учесть дополнительную стоимость отдельного плеча.

Нейронная проверка проводится отдельно и с одинаковыми исходными policy/reference/LoRA/optimizer/RNG. Действующий R16/S04 contract допускает одно применение нового pair_id и не допускает скрытого повторного применения уже использованной пары. Поэтому старый count replay не является готовым переключателем neural RP01. Новые допустимые китайские пары на прежние навыки проверяют rehearsal новыми уроками; это иной опыт, чем точное повторение старых bytes. Для exact old-pair replay нужен явно оформленный исследовательский режим с подходящим owner-contract; новое имя pair_id для тех же bytes не решает вопрос. [Первичное требование R16](https://github.com/lubochka/xiigen-planning/blob/a90350f33955f9c4b15707a4619eeeba5d42e863/llm%20mvp/design%20to%20code%20session/09.09.26WorkLeft-02-teaching-chinese-model.md#L5-L17).

После каждого допустимого neural плеча сохранить child checkpoint и проверить старые/новые случаи после cold load. Полезность означает измеренное удержание с показанной ценой для новых знаний; выигрыш заранее не задаётся. Прежние владельцы: P15/P24/P74/P116. Эта зависимость уточняет будущий опыт и не препятствует текущей публикации исследования.

## Общий измерительный контракт

Для каждого опыта сохранить собственные сырые ответы A/B, ожидаемый смысл, число верных, ошибочных и отказов, gained/lost cases, время обновления/ответа, RAM/VRAM при наличии, размер памяти/индекса/checkpoint, число параметров и слоёв модели (всего/обучаемые), отдельно уровни и глубину Unit/Flow. Для дискретной памяти число нейронных слоёв — `не применяется`, а число примеров памяти измеряется. Направления EN→RU/RU→EN — профили темы перевода, а не автоматически разные домены.

Роли в каждом опыте фиксированы: внешняя открытая китайская модель создаёт стороны DPO; CODEX с `astra 6 ultracode` выполняет роль человека при выборе и независимо оценивает качество. Этот аудит не запускал внешнюю генерацию. Иллюстративные входы здесь — проверочные случаи, не новый утверждённый DPO-набор. CODEX не подменяет ответ проверяемой Unit эталоном; отдельный post-update evaluator получает ответы со скрытым обозначением плеча. Проверка допустимости пары и оценка нового Student — разные процедуры. Один опыт меняет один механизм, кроме явно обозначенного трёхстороннего исторического сравнения R3.
