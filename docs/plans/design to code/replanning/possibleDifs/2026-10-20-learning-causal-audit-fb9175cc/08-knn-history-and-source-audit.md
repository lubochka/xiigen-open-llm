## 3. Новый адресный фактор: повторные вычисления нормы query в обучении HNSW

**Факты исходника.** [KnnLogicalUnit.Train, 132–154](https://github.com/lubochka/llm_mvp_core/blob/fb9175cc752d41e1cb525e0609b7c96140940217/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L132-L154) обучает BPE и для каждого примера вызывает `index.Add(Vectorize(...), id)`. [HnswIndex.Add, 70–86](https://github.com/lubochka/llm_mvp_core/blob/fb9175cc752d41e1cb525e0609b7c96140940217/06.VectorSearch/HnswIndex.cs#L70-L86) вызывает `GreedySearch`, `SearchLayer`, `SelectNeighbours`. Эти методы повторяют `Distances.CosineSimilarity(query, storedVector)` для неизменного query в рамках одного вызова. [CosineSimilarity, 10–20](https://github.com/lubochka/llm_mvp_core/blob/fb9175cc752d41e1cb525e0609b7c96140940217/06.VectorSearch/Distances.cs#L10-L20) каждый раз повторяет `na += a[i]*a[i]`.

**Гипотеза.** Локальное однократное вычисление суммы квадратов query в каждом вызове GreedySearch/SearchLayer/SelectNeighbours уменьшит арифметическую работу при реальном построении выученной памяти. Выигрыш CPU или wall time неизвестен; при маленьком числе кандидатов отдельный проход может стоить дороже. Allocation gain не обещается: исходная норма считается без временного массива.

**Предлагаемый ремонт только для будущего выбора пользователем.** В отдельной B-копии HnswIndex добавить local `float querySquaredNorm`, пять call sites направить в helper с тем же порядком накопления dot/nb, `MathF.Sqrt(na)*MathF.Sqrt(nb)`, порогом `1e-9f` и делением. Query squared norm живёт только один вызов метода. Не хранить нормы в полях индекса/глобальном cache: [Add, 49–54](https://github.com/lubochka/llm_mvp_core/blob/fb9175cc752d41e1cb525e0609b7c96140940217/06.VectorSearch/HnswIndex.cs#L49-L54) удерживает переданные массивы по ссылке. Пока не изменён контракт владения, долгоживущий cache может устареть. Даже локальный рецепт ограничен однопоточным native Unit.Train без конкурентной мутации массива.

**Учебный consumer.** [ExecuteAsync, 216–256](https://github.com/lubochka/llm_mvp_core/blob/fb9175cc752d41e1cb525e0609b7c96140940217/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L216-L256) кодирует настоящий запрос тем же обученным tokenizer, читает построенный index и возвращает output реально найденного учебного примера. Будущий опыт проходит эту цепь после Train на четырёх и на восьми уроках; изолированный cosine benchmark не заменяет его.

**Модель и доменная граница.** Первый рецепт использует обычный `KnnLogicalUnit<string,string>` на восьми существующих EN→RU инструкциях лабораторного P125 fixture. Это обучение/перестроение non-neural памяти. Generic Unit не имеет в данном файле полной операции checkpoint restore; C0 получается честным четырёхстрочным Train, затем C1 — новым Train расширенных восьми строк. Не называть это продолжением восстановленного checkpoint. На TranslationMachine.KnnStore, AST-specific StructuralKnn, DPO loss, LoRA и общий RP01 стоимость из этого опыта автоматически не переносится.

## 5. Что не заявлено заново

В текущих Unit/Flow, DPO materialization, TranslationMachine и restore рассмотрены записи корректировок, направление/тема, повтор IDs, прежние correction-first/append-k проблемы, сборка subunits, точность verifier и checkpoint aliases. Ближайшие документы уже описывают эти семейства. В этом пакете они остаются существующими кандидатами; за новые ID их не выдаём. Не доказано, что неудачный RP01 использовал конкретный вход, который активирует каждый потенциальный дефект.

Приоритет новой карточки: после актуальных блокировок обучения и конфликтов действующего registry. Она не открывает заново N-KU-01, BPE-NO-MATCH-COPY-01, N63 или любой ранее завершённый опыт. Последовательность готовых шагов задаёт единый registry родительского пакета. Статус новой строки — **AUTHOR_SETUP_REQUIRED / NOT_RUN**, а не выполненный ремонт.
