## Главный вывод

Нельзя объяснить ухудшение RP01 одной установленной поломкой LoRA или объявить прежние успешные опыты неуспешными. Обнаружены разные классы расхождений: недостаточный учебный сигнал коротких нейронных рецептов; потеря материала на входе и при replay; различия масок/целей/состояния optimizer; утрата контекста, структуры и отрицательных примеров при переходе DPO → память → Unit → Flow; смешение восстановления private state с публикацией production parent; неполные шаблоны метрик и чрезмерные выводы из несопоставимых исторических результатов. Для этих классов уже существуют отдельные семейства гипотез. Их наличие в каталоге не доказывает, что все подслучаи превращены в готовые и чувствительные малые опыты. [Карта механизмов](01-mechanism-map.md), [проверка карточек](03-card-contract-audit.md).

Сохранённые результаты показывают настоящие полезные изменения. В этом пакете они сохраняются кандидатами по каждой улучшившейся метрике, с ухудшениями рядом. Снижение allocations во время реального Train, лучшее сохранение отдельных выученных токенов, рост числа правильных ответов памяти и уменьшение NLL после restore — разные полезные результаты. Рост accuracy не является обязательным условием их признания. При этом 0→0 правильных ответов не становится доказательством усвоения задачи, а один замер времени не устанавливает устойчивую причинную скорость. [Измеренные результаты и адреса кандидатов](02-saved-results-and-candidates.md).

## Порядок дальнейшей работы

**Текущий NEXT — №10 `PARENT-ADOPTION-01`; режим этого поручения — только документация.** Затем идут №11 `N63-INGRESS-LENGTH-LEARNED-01`, №12 `N63-CORRECTION-COLLISION` и остальная canonical очередь. PA01 получил конкретный writer→selector→restore→continuation рецепт, но module/handoff ещё не материализованы и не исполнены. Старый№08 имеет `ATTEMPT_CONSUMED / LEARNING_OBJECTIVE_OPEN`; новый№11 — отдельная явно назначенная исправленная постановка, не скрытый повтор старого entry. Существующую частичную попытку N63C, claim и raw сохранять; её нельзя перезапускать на основании ошибочных0counters.

Порядок авторской подготовки: core№10→45, затем новые A4 `SILU-SIGMOID-REUSE-01` → A5 `HNSW-QUERY-NORM-REUSE-01`, затем зависимые consumers№46→47→END. DPO-SHIFTED-CONTEXT/IDENTITY-TRAIN-INDEX/SFT-EXP-REUSE уже имеют canonical№43/44/45 и не добавляются второй раз. Это 49 уникальных записей. На конечном срезе 10 core ID имеют сохранённую/частичную попытку, 37 core ID ещё не выданы; с двумя новыми предложениями это 39 невыданных позиций и открытая цель N63C, всего 40 документных позиций. Число ID не равно числу всех отдельных runtime probes. Частично выполненный A N63C не превращён в новый completed A/B experiment. [Машинный dispatcher](data/resolved-dispatch.json), [исторический срез](04-registry-fb9175cc.md).

Для новых факторов нужен минимальный настоящий Train. У SiLU назначен standalone H64 recipe:400 конечных common preparation updates и затем4+4 сравниваемых updates; готового H64 donor в LEARN-SANITY-PROBE нет. Эти400steps включены в бюджет. Исторические1/2 равны constant baseline и не доказывают усвоение общего правила знака; EXAM не используется как gate. Для HNSW назначено native обучение4, затем8 уроков; generic Unit не выдаётся за TranslationMachine. Новый H16/PA01 контракт соседнего SFT_EXP не подставляется молча в отдельную SiLU гипотезу. Отсутствие production parent не является общим запретом BPE/Unit/KNN/первых native updates.

Наличие очереди **не разрешает автоматически выполнить49 опытов**. Для поручения одного конкретного ID NEXT=END. Live «следующий» немедленно прекращает работу над предыдущим, включая report/review/hash/Git/retry; «остановить всё» прекращает всю работу. Incoming карточка или prompt не отменяют прямой пользовательский запрет правок protected. Все поправки этого аудита находятся только в possibleDifs.
