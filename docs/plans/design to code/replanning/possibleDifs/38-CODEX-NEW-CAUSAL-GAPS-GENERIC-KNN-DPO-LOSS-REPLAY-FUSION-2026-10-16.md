## Человеческое объяснение

История содержит успешные научные эксперименты, но нынешний RP01 оптимизирует иной объект — randomly initialized neural Student с LoRA, а не историческую KNN/Unit память. Следующие находки не заменяют сильнейшую гипотезу про cold start и отсутствие SFT. Они показывают **другие конкретные способы потерять уже выученное качество или ошибочно выбрать момент прекращения обучения**. Новизна — точная связка producer → кодовое условие → фактический потребитель; она требует независимого опровержимого опыта и не доказывает уже случившуюся регрессию.

## N38.01 — одна метка ExampleId у двух векторов, но ответ всегда от последней записи

**Где:** generic `KnnLogicalUnit<TInput,TOutput>`, не `TranslationKnnStore` и не нейронный DPO Student.

* [`KnnLogicalUnit.Train`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L111-L181) сохраняет `exampleMap[trimmedId] = example` (словарь, перезапись), затем **без проверки дубликатов** `index.Add(Vectorize(...), trimmedId)`.
* [`HnswIndex.Add`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/06.VectorSearch/HnswIndex.cs#L37-L95) всегда дописывает новый узел `_vectors` и новую запись `_ids`, даже при повторном строковом id; deduplication нет.
* [`KnnLogicalUnit.ExecuteAsync`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L204-L266) берёт `best = hits[0]`, а ответ — `_examples[best.id].Output`. Старый вектор с прежним id теперь **указывает на последний Output**. `Manifest.TrainingExampleCount` выдаёт `exampleMap.Count`, не `index.Count`.

**Строгое следствие**: после двух разрешённых строк (`same-id`: вектор старого закона → `right-A`, затем `same-id`: вектор нового закона → `right-B`) индекс имеет два адреса с одним id, словарь — одну запись `right-B`. Даже если HNSW находит **старый** вектор A, дальнейший mapping выводит B. Это не предположение о случайности HNSW; это source-логика идентичности. Наличие реальных коллизий ExampleId и пути продукта, который выполняет именно generic Unit, **не установлено**.

**Почему другое, чем N34:** [N34 double insert](34-NEW-ONE-LESSON-DOUBLE-INSERT-UNDER-ALIAS-SIGNATURE-2026-10-16.md) изучает алиасные bucket entries *TranslationKnnStore* для одного урока; [N23 unit identity](23-NEW-UNIT-CASE-IDENTITY-AND-NONATOMIC-TRAINING-2026-10-16.md) — регистр в SemanticTokenizer. Здесь **другой класс, другой ключ и несоответствие ANN node→dictionary output**.

**Быстрый фальсификатор N38-KNN-ID (C#, код/AST и domain-router):**
1. На новом `KnnLogicalUnit<string,string>` train только две строки с одинаковым `ExampleId`, противоположными проверенными outputs и различными input vectors; контроль — те же строки с уникальными ids. Запечатать правильные outputs до запуска.
2. Query каждому исходному source, затем парафразы source-disjoint, через `ILogicalUnit.ExecuteAsync`; вывести список HNSW hit id/score (через одно временное probe-поле), фактический selected id, ответ, confidence и manifest count.
3. В treatment **отклонить конфликтующий duplicate id до первой вставки** либо иметь typed revision key; не допускать молчаливое перезаписывание. Материал и tokenizer/seed/k идентичны. Проверить reverse insertion order, unknown-id и cold state.
4. Primary: correct-law@1 и wrong-accepted, по двум доменам; secondary: indexCount/mapCount, hit identity и latency. При отсутствии duplicates в реальном допущенном corpus практический риск отложить, не объявлять причину RP01.

## N38.02 — плотность вектора делает DPO loss несопоставимым, а loss управляет остановкой

**Где:** generated-capability DPO (`LogicalDpoTrainingUnit`), **не** текущий RP01 simulation, у которого цикл лимитирован числом updates.

* [`DpoTrainer.StepVectorCore`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/11.DPO/DpoTrainer.cs#L832-L943) вычисляет `vectorWeight = weight/sum(weights)` и `scaledWeight = vectorWeight * VectorSignal(teachingVector)`; затем `gradMargin = objective.Derivative * scaledWeight`. Для exact-варианта **публикуемый `Loss += loss * scaledWeight`**, а `RewardMargin`/`Accuracy` используют **только `vectorWeight`**. В частности, reported loss не является одинаково нормированным со следующим batch-ом с иной плотностью векторов.
* [`VectorSignal`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/11.DPO/DpoTrainer.cs#L1159-L1167) считает число активных `|x|>1e-6` и возвращает `clamp(1 + activeSlots/60,1,2)`. Смысл и координаты признака не входят в сам signal (это ранее известно); **новое здесь — его влияние на опубликованный Loss и early-stop**, не только gradient.
* [`LogicalDpoTrainingUnit`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L1351-L1391) реально вызывает `monitor.ShouldStop(lastMetrics.Loss)`. [`DpoConvergenceMonitor`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/11.DPO/DpoConvergenceMonitor.cs#L7-L39) сравнивает **абсолютное**, а не относительное изменение reported loss с порогом. Фактический configured window/threshold важен.

**Воспроизводимый source-logic расчёт:** одна и та же frozen exact DPO пара с loss=ln2≈0.693147, вес пары=1. При 0 активных slots `VectorSignal=1`, published Loss≈0.693147; при ≥60 slots `VectorSignal=2`, published Loss≈1.386294. Chosen/rejected, frozen policy, reference, unweighted reward margin и accuracy **могут быть одинаковыми**. Это доказательство разного *значения метрики при одинаковом материале*, не измерение того, что optimizer остановился раньше в реальном training run.

**Причинный риск:** даже при одинаковой относительной траектории unweighted loss абсолютная разность `|Loss_t−Loss_{t-1}|` меняется с vector density, из-за чего threshold может «сигнализировать» разное состояние схождения. Вместе с zero-data/cold-start это способ преждевременно остановить полезное обучение или продлить бесполезное. Но реальный B0 RP01/C#500 и ENRU500 **не используют этот monitor как управляющий stop** — **не переносить** причинность.

**Быстрый фальсификатор N38-DPO-LOSS (C#, EN→RU + SQL):** frozen exact pair, same model/seed/settings; L0 один read-only инструментальный objective/margin до optimizer и два teaching-vectors из 0 vs 60 активных slots, ожидать `lossDense/lossSparse≈2` и одинаковые нормализованные значения. L1 на двух *отдельных идентичных* разрешённых коротких учебных копиях (не reuse immutable publication IDs): current monitor по reported loss vs monitor по отдельно нормированному pair loss, одни DPO пары, same wall/steps, сравнивать фактический stopping step, optimizer state и **слепой** domain result. Контроль: ровно одинаковая плотность → одинаковый stopping step; полный native gradient может зависеть от вектора, поэтому конечный training delta нельзя приписать только метрике без факторизации. Никогда не патчить early-stop на основании одного source-proxy.

**Отношение к прежним находкам:** [N35 DPO plateau](35-NEW-GENERATED-CAPABILITY-DPO-LOSS-PLATEAU-STOP-2026-10-16.md) уже описал малый window/step cap; [N26 AdamW scaling](26-NEW-ADAMW-SCALE-CANCELLATION-2026-10-16.md) — почти-инвариантность масштаба градиента. **Эта N38 — новая проверяемая связь teaching-vector density → loss normalization → конкретный consumer stop.**

## N38.03 — «три компонента fusion» фактически два лексических признака, AST/KNN там нет

**Где:** `ReplayFusionRanker` generated capability replay, отдельно от retrieval-time ANN и RP01 Student.

* [`ReplayFusionRanker.Rank`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/18.CapabilityTraining/ReplayFusionRanker.cs#L12-L39) записывает `vector = ComputePredicateOverlap(compiledText, manifest.TrainingText)` и **`pattern = vector`**, score `0.45*vector + 0.35*lexical + 0.20*pattern` ⇒ реально `0.65*token-set-overlap + 0.35*BM25-like`. Ни нейронного cosine/KNN, ни дерева AST для `pattern`, ни семантического law compatibility эта функция не вычисляет.
* [`ComputePredicateOverlap` и `Tokenize`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/18.CapabilityTraining/ReplayFusionRanker.cs#L40-L91) читают слова/корни из `NormalizeRoots`; пересечение множеств без ролей/знака/порядка.
* **Реальная точка вызова**: [`DefaultLogicalCapabilityTrainer.SelectAndValidateReplaySnapshot`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs#L1866-L1884) передаёт список *после* replay attestation в Rank, `topK=3`. В текущей реализации `Rank` при ≤3 кандидатах вообще возвращает исходный порядок; эффект **отсечения релевантного урока** только при >3, а при ≤3 возможен эффект порядка в downstream памяти. Важно: альтернативный private helper `FindReplayManifestsResult` режет список до10 до ranking, но в прочитанном source **не найден его активный caller**; не использовать этот dead-path для вывода о продукте.

**Гипотеза качества:** технический запрос `check null before dereference` и текст `do not check null before dereference` могут быть лексически ближе друг к другу, чем семантически равные перефразы с иной лексикой; при >3 lessons истинный закон не попадёт в top3. Для SQL `NOT EXISTS`/`EXISTS`, C# nullability и EN→RU role/negation необоснованно делать из такого score общую метрику релевантности. Нельзя утверждать, что все такие фразы в фактическом `NormalizeRoots` дают названный порядок без пробного вычисления.

**Микроэксперимент N38-FUSION:** четыре валидных replay manifests с preapproved source-family/id/domain (внутри разрешённого домена; отдельные source families), пары «правильный закон/контрзакон/синоним/иррелевантный». A = current Rank; B = `BM25-only` negative control; C = conditional signed law / AST-feature reranking **после того же legal attestation**; D = random/shuffled training history. Freeze candidate inventory and checkpoint; сравнить selected top3, затем genuine generated-capability retry correctness, wrong-law@1, abstention, by-domain precision/coverage, latency. Содержательность пар подтверждает CODEX/Astra 6 UltraCode до запуска. Любая «улучшенная» deterministic rerank не считается новым learned LoRA.

## N38.04 — редкий, но строго воспроизводимый integer-overflow в предикатах generic KNN (P3)

[`KnnLogicalUnit.StableHash`](https://github.com/lubochka/llm_mvp_core/blob/aa284ba21790c5d7601328997cd6174c85cee878/21.AgentInfrastructure/Logical/KnnLogicalUnit.cs#L294-L309) в unchecked loop вычисляет signed Int32 `hash = hash*31 + char` и затем `Math.Abs(hash)`. Для валидного uppercase predicate `UNSLAWTU` исходная арифметика даёт `hash = -2147483648`; `Math.Abs(int.MinValue)` в .NET бросает `OverflowException`. Это математически сконструированный отрицательный edge-case, а не выявленный природный training input. `Train` вернёт `KNN_LOGICAL_UNIT_TRAINING_FAILED`, `ExecuteAsync` — inference failed, когда данный predicate попадёт в Vectorize. Нулевая оценка вероятности/продуктовой частоты **не делалась**. Патч-кандидат только после native test: unsigned modular reduction без нарушения старых predicate slot identities и с миграцией/версией индекса.
