## Что уже работало и должно сохраниться

В трёх отдельных отчётах 18 октября подтверждены разные свойства:

| Сравнение | Измеренный результат | Ограничение и ухудшения |
|---|---|---|
| [Обучение новой памяти Executor][memory-result] | После 8 уроков обычный перевод: **0/24 → 19/24**; новые комбинации 8/8 | Это learned memory, не RP01 LoRA. 3 ответа приняты ошибочно по строгому оценщику |
| [Передача phrase_mappings из загрузчика][ingress-result] | На тех же 8 уроках и 24 запросах: **11/24 → 19/24** | Принятые ошибочные ответы **1 → 3**; прежние правильные не потеряны |
| [Холодное восстановление][restore-result] | Все 24 ответа/маршрута/confidence воспроизведены; 19/24 правильных сохранены | 0 новых уроков. Доказана сохранность этого state, не успешное продолжение optimizer и не универсальная совместимость checkpoint |

Это три сравнения; их нельзя склеивать в историю одного запуска «0 → 11 → 19». Передача `phrase_mappings` **уже есть** в текущем [loader][translation-loader] и [continue-example][translation-continue]. Заново реализовывать принятый пользователем fix не требуется. [required-changes][required] — источник принятого обновления. Следует сохранить пользу и явно показывать ошибки отрицания/вопросов, а не отвергать память за отсутствие нейронных весов.

Соседние ветки действительно содержат положительные E25/E26/E43/E09. [Историческая сверка](02-HISTORY-AND-CURRENT-RESULTS.md) сохраняет их успехи и ограничения: например, POS-классификация не равна переводу, а у E09 baseline и kNN оценены на разных объёмах панели. Нельзя объявлять все эти результаты «неудачными» или переносить их число на новую функцию без сопоставимого опыта.

Последняя [таблица N-KU](coverage/06-FINAL-CORE-DELTA-ce890a.md) показывает A0=B0=0/4, A1=1/4, B1=3/4: ложные ADD_LOOP 3→0, но KQ4 потерян. Это опубликованный полезный сдвиг узкой метрики, согласующийся со сменой majority class; он не доказывает структурного обобщения. Две одинаковые таблицы без raw/counters/exit receipts не подтверждают два независимых native запуска.

## Что можно и нельзя утверждать о покрытии

Проверены **286/286 Markdown** защищённого каталога по Git blob SHA. Проиндексированы **126 файлов карточек**: 125 P-семейств, 470 подслучаев и отдельная новая N-KU-01. В P-карточках 133 промпта; во всём рассмотренном корпусе 180 секций, названных промптами, одна из них без поручения. Все 126 карточек уже содержат действующее правило успеха по полезному показателю. [Полный аудит и реестры](coverage/01-current-card-audit.md).

**Нельзя подтвердить, что все найденные детали уже оформлены в protected как правильные готовые опыты.** Из 577 planning Markdown 542 буквально упомянуты, 35 — нет. Отсутствие имени не равно отсутствию идеи: 13 из этих файлов уже содержательно покрываются N49/D49/G-W. В исходном срезе четыре точных фактора из предыдущих пакетов не имели там самостоятельных полных рецептов. **Во время аудита это изменилось:** новая [N61 Mode1](https://github.com/lubochka/llm_mvp_core/blob/7c57183670ccaf554a47c0a4f44cabadde8c303d/docs/plans/replanning-possible-diffs/experimets/cards/N61-mode1-retention-and-identity.md) описывает retention и selected-flow/pair identity, [N61 reference](https://github.com/lubochka/llm_mvp_core/blob/7c57183670ccaf554a47c0a4f44cabadde8c303d/docs/plans/replanning-possible-diffs/experimets/cards/N61-dpo-reference-reuse.md) — reuse frozen reference. Они теперь покрыты содержательно; отсутствие этих трёх факторов больше не заявляется. Для reference остаётся подготовка маленького native host, а у Mode1 команды и source projection конкретизированы, но сборки/результата в карточке нет. Learned-key canonicalization пока остаётся без точной protected-карточки. Четыре наши новые гипотезы добавлены только сюда, согласно запрету менять protected. Подробности — в [поздней сверке](coverage/05-LATE-CORE-DELTA-7c5718.md).

N60-E1 дополнительно содержит входы «быстро/тихо», не достигающие нужного marker writer в текущем коде. [Уточнение данных](corrections/02-N60-E1-fixture-correction.md) использует «спокойно/calmly» и «громко/loudly» и сохраняет один admission-фактор. Это исправление материала известного N60/N57, а не новая причина обучения. Оно независимо опубликовано и как LF-04 в соседнем пакете; разные подходящие слова не создают две гипотезы и не требуют двух запусков. Native two-batch host остаётся отдельной точно обозначенной подготовкой; такой overlay не назван завершённым исполняемым опытом.

## Порядок дальнейшей работы

1. **Разблокировать настоящее обучение.** В первую очередь прямые writer/state/reader дефекты; новые Wiki-карточки дают короткие отдельные сравнения. Нейронный RP01 требует малый native caller с существующими правилами допуска; это не разрешение обойти admission или заменить trainer самодельной формулой.
2. **Разрешить конфликты выбранной карточки.** Проверить конкретный reader, входы, начальное состояние, source-copy, команды, бюджет и смысл метрики. Не ставить весь каталог из 470 подслучаев в обязательную очередь.
3. **Учесть присланные обновления.** Уже внесённый phrase ingress сохраняется; старые запреты и пороги из инструкций не перекрывают девять текущих правил пользователя.
4. **Проверять зависимости обучения.** Loader, restore и consumer допустимы с конкретным причинным путём и местом будущего ремонта. Остальное — последняя очередь; фиктивный Train не превращает посторонний benchmark в учебный опыт.

**В каждой новой карточке и каждом исполнительском промпте:** любое измеренное улучшение полезного показателя считается успехом по этому показателю и домену; рост точности не обязателен; рядом показываются остальные изменения, включая ухудшения. Успех опыта не означает автоматического переноса в production. Пользователь выбирает дальнейшее внедрение после raw результатов.
