## Зачем и какой получатель

Предметная тема — перевод EN→RU технических команд. Получатель — `TranslationMachine` / `ExecutorUnit` / общая `TranslationKnnStore`, обучаемые вызовом `TrainStructuredBatchAsync`. Исправляемый код действительно выполняется внутри обучения: после `TrainOnExample` журнал проверяется линейным `.Any`. [Источник и отдельный фактор](../02-novelty-and-cost-evidence.md). Neural Student, LoRA, внешний LLM и генерация новых DPO в этом опыте не используются. Модель исполнителя — модель сессии по умолчанию, без override; факт независимого review записывается отдельно, не выдумывается.

**A:** точная копия исходника core `dd150aa5216e42b8a8bba14955337398ec5f8397`. **B:** ровно три описанные точки добавления вспомогательного identity set, без изменения порядка Train/admission. Каждая ветка получает одни и те же байты warm checkpoint и четыре новых настоящих урока. Сравнивается переход A0→A1 и B0→B1, а не один вызов `.Any` вне обучения.

## Точный материал и достаточный бюджет

Все исходные поля берутся побайтно из замороженного [training-batch-B.json](https://github.com/lubochka/llm_mvp_core/blob/dd150aa5216e42b8a8bba14955337398ec5f8397/docs/plans/replanning-possible-diffs/experimets/results/2026-10-18/P125-enru-memory-01/training-batch-B.json); blob `0c2a3d9a0da31b7277c0d215fb79ddebda49aa6c`. | Фаза | Что исполняется | Число |
|---|---|---:|
| Создать warm state один раз | A, первые четыре разных урока, по 128 предъявлений с **новыми identity ключами**, 4 строки на пакет | 128 настоящих Train, 512 обновлений, 512 разных identities; только 4 независимых содержания |
| A0 / B0 | Отдельные свежие процессы восстанавливают один и тот же checkpoint; обычный Flow на всей панели | По 24 ответа до |
| A0→A1 / B0→B1 | Последние четыре урока, один пакет; новые ключи | По 1 Train и 4 обновления |

| Всего | Warm + две ветки | 130 Train, 520 строк обновления; 8 независимых содержаний; 96 Flow calls; 2 restore |

512 identities нельзя получить повторением тех же четырёх ExampleId. Warm generator обязан сделать разные пары `(ExampleId,UnitId)` по точной формуле FIXTURE. Повторное предъявление содержания не называется новым знанием или 512 независимыми уроками. Это небольшой искусственный профиль накопленного журнала, не доказательство частоты такого профиля в продукте.

Перед измерением уже есть четыре правильно выученных точных урока. В отчёте нужно показать сохранение этих ответов и усвоение новых четырёх через state и обычный Flow. **0 правильных ответов до и после не является валидным опытом; даже равные output hash при 0→0 не доказывают сохранность навыка.** Если warm state не даёт минимум четыре ожидаемых точных правильных ответа, статус `INVALID_LEARNING_FIXTURE`; не добавлять произвольные уроки/повторы, не выдавать нулевую панель за успех. Данных и счётчиков достаточно для назначенного минимального перехода; никакой скрытый лимит токенов не должен обрезать четыре главных урока.

## Метрики и честное признание успеха

1. В каждом A0/A1/B0/B1 сохранить все 24 raw ответа и обычный route/verdict; применить неизменный P125 gold/scorer после ответов. Показать accuracy, coverage, acceptedWrong, ошибки action/object/polarity/question/quantity/two-object и safe edges по корзинам exact/near/composition/edge. Gold не передаётся обучению или Flow.
2. Сохранить checkpoint до/после и сравнить выученные memories и identities между A/B. Для канонического equality исключить только `ExportedAtUtc` и history `CpuMs`, `PeakRamMb`, `ElapsedMs`. Убедиться, что обучение действительно добавило четыре exact lessons, восемь phrase mappings, двенадцать KNN entries и четыре identities. Оценка не должна менять state.
3. Отдельно измерить restore (включая построение B index), реальный Train, **сумму restore+Train**: wall time, process CPU, process allocated bytes; GC по поколениям. В синхронном Train дополнительно current-thread allocations с проверкой одинакового managed thread. Не применять этот счётчик без проверки к async restore. Общие peak/RSS и setup warm — отдельные величины, не арифметические слагаемые пиков.
4. Сохранять любые ухудшения рядом с полезными изменениями. **Любое измеренное улучшение полезного показателя — успех по этому показателю и домену; рост accuracy не обязателен.** Однако более дешёвый Train при более дорогом restore+Train означает только выигрыш Train, не выигрыш полного продолжения. Равенство/ухудшение всех показателей — отсутствие полезного выигрыша; успех не назначен заранее.

Один фиксированный порядок A затем B и один запуск каждого процесса дают наблюдения этого запуска, не статистическую оценку causal speedup. Для wall/CPU/JIT причинность не установлена. Не запускать обратный порядок, прогревы, performance1000repeats или новые seeds ради красивого результата. Если состояние/ответы разошлись, это несовместимость с заявленной эквивалентной оптимизацией; ресурсные изменения всё равно записываются, но качество нельзя скрыть.
