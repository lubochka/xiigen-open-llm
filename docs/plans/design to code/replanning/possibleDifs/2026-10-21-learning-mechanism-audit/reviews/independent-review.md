## 1. SiLU: механизм верен, ненулевой готовый baseline не установлен

[TensorOps.Silu:1132–1158](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/00.TensorCore/Core/TensorOps.cs#L1132-L1158) вычисляет `1f + MathF.Exp(-x.Data[i])` в forward **1139**, затем снова в backward **1152**. B может сохранить именно denominator в локальном `float[]` при `RequiresGrad`, оставить forward division и backward `1f/denominator` с прежним порядком множителей. Это отдельный фактор; замена division на multiplication, новый dtype, pooling, parallelism и новый SiLU derivative здесь не нужны.

Связь с обучением прямая: [Trainer:117–145](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/04.TrainingLoop/Trainer.cs#L117-L145) → [TransformerBlock:57–62](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/03.TransformerModel/TransformerBlock.cs#L57-L62) → [SwiGLU:40–51](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/03.TransformerModel/Layers/SwiGLUFeedForward.cs#L40-L51) → SiLU → backward → optimizer. В этом caller optimizer идёт после backward; сохранённый denominator относится к тому же forward.

**Существенная поправка к описанию затрат:** `RequiresGrad` нельзя называть синонимом `training:true`. В [LoraLinear:112–125](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/10.LoRA/LoraLinear.cs#L112-L125) флаг training передаётся dropout; A/B LoRA продолжают участвовать в MatMul. Обычный scoring `Forward(false)` также может построить graph с `RequiresGrad=true`, получить дополнительный denominator-массив и не использовать его в backward. Поэтому будущий отчёт должен раздельно показать allocation/time настоящих updates и readout; нельзя обещать экономию памяти или «cache только при обучении».

H16 donor после1000 updates имеет лишь TRAIN3/40 правильных токенов и0/2 целых ответов; historical continuation200 даёт4/40 и0/2. [Зафиксированная панель и границы](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/docs/plans/replanning-possible-diffs/2026-10-20-parent-adoption-repair-evidence.md#L22-L28). Это реальное частично обученное состояние, но не доказанный подходящий ненулевой ответ для нового требования пользователя. Его нельзя выдавать за готовый skill или гарантию, что следующие200 updates его дадут. Статус **BLOCKED_LEARNED_BASELINE**, без команды обучения, честен. Для cost-гипотезы не требуется ждать production PA01 как самоцели: разблокирование возможно после отдельного точного совместимого экспериментального baseline с нужным измеримым результатом. В данной проверке такого baseline не найдено.

Ближайший уже существующий [SFT-EXP-REUSE-01](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/docs/plans/replanning-possible-diffs/experimets/cards/SFT-EXP-REUSE-01.md) переиспользует Exp между двумя vocabulary-петлями `Trainer.BackwardLoss`; RMS row reuse меняет другие вычисления. Это не SiLU forward→backward denominator. Старые тексты о наличии SiLU backward уже описывают исправленную связность gradient; новый фактор не переоткрывает отсутствие backward.

## 2. POS: измерять стоимость использования обученного результата

[PatternClassifier проекта12:39–54](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/12.SemanticCompiler/Translation/PatternClassifier.cs#L39-L54) очищает/заполняет `_train`, затем `Predict` читает её. [SequenceDistance:78–86](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/12.SemanticCompiler/Translation/PatternClassifier.cs#L78-L86) строит одинаковое множество query-биграмм на каждой train-строке. B строит его один раз **после проверки пустой `_train`**, а train-множество — по-прежнему на каждом сравнении. Сохраняются set-Jaccard, `union==0`, k3, стабильный порядок соседей, голосование и метки. Persistent cache или изменение Train здесь не нужны.

Исходная native постановка [E25:22–47](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/35.ExperimentsV2/Experiments/E25PatternClassifier.cs#L22-L47) задаёт seed42,20 строк на каждый из8 классов, split128TRAIN/32VAL. Для двух плеч достаточно ровно2 Train по128 строк и128 Predict: A0/B0/A1/B1 по32VAL. Полный `E25.Run` использовать вместо этого паспорта нельзя: он дополнительно повторяет Predict для hardCases. Hard-subset metric можно получить из тех же32 сохранённых predictions без новых вызовов.

Измеряется изменение результата до/после настоящего Train и стоимость последующих Predict. B ожидает ту же точность, но меньшие query-set allocations. Это лишь ожидание: никакое число allocations или миллисекунд в этом review не измерено. Сохраняются все32 gold/prediction до/после обоих плеч, изменившиеся ответы, actual bytes/time и denominator. Единственная маленькая wall-time панель чувствительна к JIT/порядку и даёт ограниченное наблюдение; нельзя обещать causal speedup по шумному таймеру. Конкретный выигрыш allocation при неизменной accuracy может быть успехом своей оси. Число построений HashSet по чтению кода не подменяет измеренные bytes.

Домен — классификация синтаксического порядка по заданным POS. Это не raw-text POS tagging, не качество целого перевода и не установленная причина провала RP01. [PatternClassifier проекта29:24–52](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/29.SemanticCompiler/Translation/PatternClassifier.cs#L24-L52) — иной rule-based consumer; его подключение не входит в этот фактор.

Ближайший [N50-POS-02](https://github.com/lubochka/llm_mvp_core/blob/d962f95805ae0c9c4ef5b3f50f0f65b2a4109d19/docs/plans/replanning-possible-diffs/experimets/2026-10-19-small-learning-probes/11-additions-50-51.md#L117-L128) меняет singleton/empty-union или set→multiset семантику. P43/E25 recovery восстанавливает обучаемый classifier вместо rules. Здесь семантика и обученная память A/B одинаковы; изменяется повторное построение query-представления.

## Дедупликация и обязательные границы новых карточек

Выполнен поиск по всем883 planning Markdown и материализованному защищённому корпусу: SiLU/sigmoid/denominator/reuse/cache; PatternClassifier/SequenceDistance/POS-bigram вместе с query-set/reuse/cache и русскими вариантами. Смыслово сопоставлены названные ближайшие N50/P43/E25/SFT-EXP/RMS материалы. Точный SiLU denominator reuse и query-only set reuse не найдены. Это ограниченная новизна двух конкретных вмешательств в указанных срезах, не доказательство отсутствия любой родственной идеи во всех ветках.

При написании каждой новой карточки **и её отдельного prompt** нужны: текущая default model без override, русский report, точные существующие skills/пути, заранее выбранные host/output/entry и конечный бюджет для разрешённого future опыта. Для SiLU BLOCKED команда запуска отсутствует намеренно, чтобы не поручать исполнителю самому конструировать missing baseline. Любое измеренное полезное улучшение на валидной учебной постановке — успех этой оси/домена, accuracy gain не обязателен; остальные показатели и ухудшения публикуются рядом. `0→0` не получает статус учебного успеха по margin. «Следующий» немедленно переключает на назначенный NEXT без polishing предыдущего; «остановить всё» немедленно останавливает всё. Timeout требует дождаться того же process/session, а не создавать новый attempt.

`skill_load_status`: использованы ранее целево прочитанные phase-planning, plan-review, code-examination, prompt-patch-authoring, human-readable-architecture-audit и human-communication-GLOSSARY; модель по умолчанию. Объём проверки — source/design/дедуп, не исполнение. Никакой перенос в production не предлагается как уже доказанный.
