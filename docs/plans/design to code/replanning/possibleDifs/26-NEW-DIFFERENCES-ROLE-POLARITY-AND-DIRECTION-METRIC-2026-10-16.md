## N26.01 — первый/второй/третий субъект стирается из фильтра похожести EN→RU (P1 conditional)

**Непосредственный код:** [TranslationTrainedUnits.cs:962–989](https://github.com/lubochka/llm_mvp_core/blob/b0afc08dc0df110b10ed5ed38b518906665c16f8/27.TranslationDomain/TranslationTrainedUnits.cs#L962-L989). `SourceContentTokens` исключает все токены длиной менее двух символов и явно удаляет `you`, `he`, `she`, `we`, `they`; `i` удаляется обоими условиями. `SourceTokenSimilarity` вычисляет `overlap / queryTokens.Count`, не учитывая отсутствующий субъект. Поэтому при идентичных остальных словах пары `I authorize the payment` и `You authorize the payment` **имеют одинаковые множества content tokens** (`authorize`, `payment`) и этот guard не способен отличить лицо; аналогично `He signed the order` и `She signed the order`. Это **точное математическое следствие реализации**, не measured bad translation.

**Маршрут и граница:** [ExecutorUnit.TrySelectKnnCandidate:333–364](https://github.com/lubochka/llm_mvp_core/blob/b0afc08dc0df110b10ed5ed38b518906665c16f8/27.TranslationDomain/TranslationTrainedUnits.cs#L333-L364) использует этот порог для ordinary EN_RU KNN. Ранее exact/phrase/word maps могут вернуть результат раньше; ANN и signature buckets могут отличить пары по иным причинам. Нельзя утверждать, что все запросы инвертируют субъект. **Новизна:** N16-04 обсуждает `not/no`, N23 обсуждает POS/signature; здесь отдельно проверяем _потерю лица в дополнительном фильтре допуска_ и асимметричную формулу overlap. Это пересечение по коду, не второй независимый bug count для самого stopword list.

**Фальсификатор:** на одних и тех же уже найденных kNN hits сравнить A current guard и B role-scoped eligibility (person/agent + negation, полученные только из source/candidate, не из правильного ответа). Одинаковые индексы, порядок hits и score. Измерить `wrong-accepted`, `correct-accepted`, `abstained`, per-case selected neighbour; если B лишь отказывает и не улучшает качество среди принятых ответов, не объявлять learning gain. Требуемая трасса: `input→content tokens→candidates→guard→selected output→judge`.

## N26.02 — выученный Verifier проверяет наличие термина, но не утверждаемую полярность (P1)

**Непосредственный код:** [TranslationTrainedUnits.cs:1052–1092](https://github.com/lubochka/llm_mvp_core/blob/b0afc08dc0df110b10ed5ed38b518906665c16f8/27.TranslationDomain/TranslationTrainedUnits.cs#L1052-L1092). По `requiredTermsBySignature`, `requiredTermsBySourceMarker`, `_conceptRules` решение сводится к лексическому `candidateText.Contains(required, OrdinalIgnoreCase)`. Для обученного правила «в ответе должен присутствовать `процесс`» оба варианта «Процесс запущен» и «Процесс не запущен» удовлетворяют этому условию. Для источника «Start the process» второй вариант **семантически противоречит source law**, но Verifier может выдать `Pass=true` при отсутствии иных rules/issues. **Статус:** source-confirmed representational blind spot, native outcome still to be measured.

**Это не повтор N21/N23:** ранее документированы substring вместо whole word, неверный `ctx`, накопление конфликтующих required-терминов и обход Verifier через phrase. Здесь оба ответа содержат _целое одинаковое слово_, нет конфликта, нет контекстного переезда и нет phrase-bypass; недостаточна сама _положительная лексическая проверка для отрицательного предиката_. Нельзя лечить только regex whole-word. Доказательство полного вреда требует learned-state probe + normal consumer trace; архитектурно проверка должна различать signed relation/semantic claim, а не presence of token.

**Фальсификатор:** [26-MICRO-LEARNED-VERIFIER-POLARITY-EXPERIMENT](26-MICRO-LEARNED-VERIFIER-POLARITY-EXPERIMENT-2026-10-16.md) и заранее заданный [fixture](26-MICRO-VERIFIER-POLARITY-FIXTURE-2026-10-16.json). A = текущий `QualityVerifierUnit` с обученным лексическим required-term, B = _shadow_ signed-law verifier, извлекающий predicate из одобренного обучения (без просмотра heldout labels). На одних frozen candidate pairs оценить `wrong accepted`, `correct accepted`, `abstained`; затем подтвердить применимость к обычному `TrainedTranslationAdapter` отдельно. B не является доказательством обучения языковой модели: это изолированный тест hybrid Unit.

## N26.03 — «успех обучения» direction-biased: full EN_RU Unit batch получает 2/3 вместо 1 (P1, measurement only)

**Прямой код:** [TranslationMachine.cs:124–145](https://github.com/lubochka/llm_mvp_core/blob/b0afc08dc0df110b10ed5ed38b518906665c16f8/27.TranslationDomain/TranslationMachine.cs#L124-L145) в отсутствие held-out возвращает `AccuracyAfter=MeasureUnitCoverage(trainedUnits)`. [TranslationMachine.cs:674–684](https://github.com/lubochka/llm_mvp_core/blob/b0afc08dc0df110b10ed5ed38b518906665c16f8/27.TranslationDomain/TranslationMachine.cs#L674-L684) фиксирует required IDs строго `semantic-tokenizer`, `executor-ru_en`, `quality-verifier`. [TranslationStructuredBatchBuilder.cs:91–142](https://github.com/lubochka/llm_mvp_core/blob/b0afc08dc0df110b10ed5ed38b518906665c16f8/27.TranslationDomain/TranslationStructuredBatchBuilder.cs#L91-L142) для EN_RU создаёт `executor-en_ru`. При всех трёх успешно _вызванных_ Unit EN_RU набор даст `AccuracyAfter=2/3` и RU_EN набор при прочих равных `1` **независимо от качества перевода**. Это derived code result, не проведённое native измерение; относится исключительно к batch без held-out.

**Причина возможной неверной интерпретации ранних «FAIL»:** если этот proxy назвали accuracy/gate, EN_RU систематически выглядит хуже. Уточнение: `EvaluateAsync` — **другой метод** с собственной оценкой и hardcoded RU→EN ([строки 686–704](https://github.com/lubochka/llm_mvp_core/blob/b0afc08dc0df110b10ed5ed38b518906665c16f8/27.TranslationDomain/TranslationMachine.cs#L686-L704)); `AccuracyAfter=2/3` само по себе **не означает**, что известный исторический результат был ошибочно помечен FAIL. Нужно установить исторического caller. Это новая точная direction-dependent delta внутри уже известного «coverage ≠ semantic accuracy».

**Проверка за один маленький вызов:** две группы из трёх корректных `TranslationLearningExample` (`SemanticTokenizer`, соответствующий executor, `QualityVerifier`) без heldout, на новых `TranslationMachine`, `RowsTrained=3`, `PromotedUnitIds.Count=3`. A RU_EN ожидаемое computed coverage 1; B EN_RU computed 2/3. Ещё одна проверка — что _реально изменилось обучаемое состояние_ и улучшился хотя бы один независимый перевод; иначе фиксируется только дефект измерения.
