# Покрытие механизмов и точное сопоставление neural Student

Дата: 19.10.2026. Сравниваем `DesignToCode-clean@e346b88a3cc1fcce48aefa626bfc7b00509eefd6` с `codex/dpo-implementation@358af351e22a92a3f7938d1f9221d5aeb7ddb053`. Это чтение исходников и прежних отчётов. Новые сборки, native tests, обучение и inference не запускались; продуктовый код не менялся. `llm_mvp_core/docs/plans/replanning-possible-diffs` использован только для чтения.

## 1. Что восстанавливать первым

У точного донора `DesignToCode-clean` уже есть подключённый LoRA, дифференцируемый attention и правильный знак DPO backward. Поэтому утверждение «успешная ветка работала за счёт другой формулы LoRA, которую теперь потеряли» прочитанный diff не подтверждает. Успешное состояние, входы обученных юнитов и фактический получатель опыта надо восстанавливать отдельно от возврата старых файлов neural core. Приоритетные проверки находятся в [исторической главе](01-HISTORICAL-BASELINE-AND-RECOVERY.md), [новых restore/context гипотезах](02-NEW-CHECKPOINT-AND-CONTEXT-GAPS.md) и [доменных опытах](04-DOMAIN-MICRO-EXPERIMENTS.md).

Часть прежних находок относится к более ранним веткам, например `PrepareToGPL`. Их нельзя автоматически переносить на `DesignToCode-clean`. Ни факт успешного продукта в donor, ни совпадение исходников не доказывают, что его успех обеспечивался именно neural Student. Для этого нужен сохранённый run с установленными checkpoint, runtime route и измеренным результатом на обычном входе. [Ранее установленная граница исторических lineage](../43-PREPARETOGPL-RESTORATION-AND-NEURAL-DIFFS-2026-10-18/03-HISTORICAL-LINEAGE.md).

## 3. Реальный путь RP01: что он доказывает и чего не доказывает

В прочитанном `CodeDocumentationSimulationDpoExperiment` модели загружаются через existing saved-root loader; EN→RU дополнительно импортирует C50 source. Допуск требует независимые policy/reference и `Dropout == 0`. Перед обучением exact material проверяется против SHA реального tokenizer. Поэтому общий low-level риск «batch принёс self-hash чужого tokenizer» нельзя считать установленным в этом caller: его upstream guard надо учесть. [Загрузка и material admission][sim-admission], [прежний владелец tokenizer identity](../39-NEW-DPO-EXACT-MATERIAL-SELF-HASH-VS-MODEL-TOKENIZER-IDENTITY-GAP-2026-10-16.md).

Каждый выбранный minibatch вызывает один `StepVector`; число пар и число optimizer updates разные. После серии код открывает полный checkpoint, optimizer и RNG, сравнивает saved/live, запрещает изменение base и требует хотя бы одно изменившееся A/B. Эти условия подтверждают факт допустимого обновления и сохранения. Они не подтверждают усвоенную генерацию. [Вызов и счётчики][sim-step], [readback/effect][sim-reopen].

Существующий отчёт о RP01 EN→RU указывает: 500 пар, 50 новых updates до global step 100, 16 LoRA tensors / 53 248 elements изменились, 39 base tensors / 11 920 896 elements сохранились; free correctness осталось 0/4, chosen-preferred — 12/20. Здесь эти числа приведены **как результат ранее опубликованного отчёта**, не как новый воспроизведённый запуск. Четыре свободных вопроса недостаточны для общей оценки доменной способности; неизменившийся base не означает отсутствия trainable effect. [Отчёт с первичными receipts и конфигурацией](../48-LANGUAGE-TRANSLATE-AUDIT-2026-10-19/01-MECHANISMS-AND-EVIDENCE.md).

Есть узкое уточнение времени метрик: StepVector вычисляет loss/margin на forward **до** ApplyOptimizer, затем публикует эти training metrics рядом с checkpoint после шага. Следовательно, `step-N.json` не следует читать как независимое повторное измерение checkpoint N. При этом просмотренный quality gate отдельно строит assessment request и вызывает calibration для trial model; доказательства, что он принимает модель по этим pre-update metrics, не найдено. **Это уточнение семантики измерения, не новая заявленная причина потери качества.** [Порядок step/metrics][dpo-new-metrics], [trial calibration][quality-new].

**Роли для новых обучающих пар:** открытая китайская external модель генерирует chosen и rejected; CODEX Astra 6 ultracode независимо выбирает материал и оценивает его качество по заранее заданной доменной рубрике. CODEX не подменяет генерирующего teacher. Train пары и heldout prompts разделяются по смысловым семействам; наличие правильной строки в шаблоне или exact match не считается независимым доказательством понимания. Сохраняются prompt/response bytes, version модели, sampling settings и проверенный pair ID.

**Минимальный ресурсный журнал будущего опыта:** уникальные пары; их presentations; длины token sequences; реальные optimizer updates; trainable tensors/elements; время model-load, tokenization, forward/backward, optimizer и checkpoint readback отдельно; peak memory, если host уже умеет его измерять; wall budget и причина остановки. Для LoRA считать не только SHA A/B, но и norm `Δ(BA)` либо одинаково вычисленный logit delta на фиксированных inputs. Для KNN считать restored rows, k, query/feature shape, число distance calls и время ordinary consumer. В новом отчёте нет измеренных seconds, RAM или скорости; сроки «быстро» — ограниченный проект эксперимента, не обещанный benchmark.

Для указанной в прежнем RP01 отчёте конфигурации H512, 4 layers, 8Q/2KV heads, rank8, q/v targets арифметически получается `4 × (8×512 + 512×8 + 8×512 + 128×8) = 53 248` trainable элементов. Это расчёт из конфигурации и LoRA shapes, не новый запуск. Dropout0 делает гипотезы о stochastic dropout условно неактивными именно в этой конфигурации. [Предыдущая конфигурационная сверка](../47-LANGUAGE-TRANSLATE-INTERNALS-AND-NEW-HYPOTHESES-2026-10-19/02-NEURAL-AND-UNIT-INTERNALS.md), [required dropout0 caller][sim-admission].
