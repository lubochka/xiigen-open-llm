# Короткие доменные эксперименты: восстановить clean, затем проверять новые причины

Дата: 2026-10-19. **Статус: протоколы для последующей реализации, не выполненные quality-эксперименты.** В рамках текущего задания разрешены исследование источников и Markdown. Здесь не предписывается запуск training/build/inference в текущей сессии.

## 1. Общий порядок и критерии

Сначала идут проверки восстановления механизма, положительный результат которого присутствует в указанном пользователем `DesignToCode-clean@e346b88a3cc1fcce48aefa626bfc7b00509eefd6`. Новые разрывы миграции checkpoint и контекста получателя приведены в [02-NEW-CHECKPOINT-AND-CONTEXT-GAPS.md](02-NEW-CHECKPOINT-AND-CONTEXT-GAPS.md); при недоступном корректном состоянии их нужно разрешить до оценки прироста от обучения.

**Обозначения R0–R5 совпадают с пакетом; фактический порядок выбирается по доменному правилу README.** R0 фиксирует state/caller, R1 — E09, R2 — E25, R3 — E43, R4 — checkpoint, R5 — conditioning. Ниже REC-CLEAN — локальные идентификаторы рецептов: REC-CLEAN-02 соответствует R1; REC-CLEAN-01 — R2; REC-CLEAN-03 — R3. R0 выполняется до них, detailed R4/R5 принадлежат документу02. Если R0 обнаруживает невозможность корректного restore, блокирующую зависимость разрешают до quality-сравнения.

Для каждого опыта замораживаются исходное состояние, train-память, tokenizer/vector-schema, преобразование данных, список heldout IDs и scorer. Отрицательный контроль меняет одну проверяемую связь. Успех в техническом подшаге нельзя переименовывать в рост конечного качества.

Для тех A/B, фактический execution API которых требует authority/lease, каждому плечу нужны **независимо выданные валидные полномочия** для конкретного изолированного состояния и исследовательского scope. Чистые read-only/component проверки, POS-классификатор и tensor fixtures выполняются по собственному реальному контракту; дополнительная runtime authority для них не придумывается. Состояния могут происходить от одного frozen baseline; authority/lease нельзя копировать между плечами. Если действующий no-repeat или unknown-effect контракт не допускает задуманное сравнение, опыт остаётся заблокированным до корректно оформленного допуска; новые IDs для прежних bytes не служат обходом. Это правило относится и к detailed R4/R5 в [02](02-NEW-CHECKPOINT-AND-CONTEXT-GAPS.md).

| Уровень результата | Что он означает |
|---|---|
| `SOURCE_CONFIRMED` | В исходнике найдена конкретная связь или несовместимость; величина quality-эффекта ещё неизвестна |
| `DIAGNOSTIC_CONFIRMED` | В отдельной будущей проверке воспроизведён точный технический механизм |
| `ARCHIVE_REPRODUCED` | Восстановлен исторический diagnostic с его собственной метрикой |
| `CONSUMER_EFFECT` | Изменение дошло до штатного потребителя и изменило ответы на фиксированных вопросах |
| `DOMAIN_QUALITY_GAIN` | На заранее закрытой панели одного предметного домена исправленный вариант лучше при одинаковом бюджете |
| `REPLICATED` | Вторая независимая по источникам/семействам панель воспроизвела направление эффекта |

Оценки времени ниже — ориентиры для реализации небольшого harness после получения требуемого допуска; это не измеренная длительность текущей работы. Если требуется новая DPO-пара, обе её стороны создаёт предусмотренная внешняя открытая китайская модель. CODEX Astra 6 ultracode выбирает учебную задачу и оценивает результат. Диагностические POS/ID fixtures не считаются новыми DPO-уроками.

## 2. REC-CLEAN-01: обученная POS-память должна достигать потребителя

**Опора.** E25 на pinned clean: `top1 .3438 → .875`, синтетические POS-последовательности, `k=3`, 32 validation-примера. Raw успех и ограничения приведены в [историческом baseline](01-HISTORICAL-BASELINE-AND-RECOVERY.md#21-e25-память-pos-биграмм-действительно-обучалась). [Код Train и одинаковой панели][e25].

**Гипотеза.** Если текущий путь не использует обученную POS-память или теряет её при восстановлении, возврат той же памяти изменит выбранный порядок/шаблон на неоднозначных входах. Этот механизм способен объяснить деградацию перевода, но историческая классификация сама по себе не доказывает качество полного текста.

**Малый набор.** 16–24 заранее зафиксированных предложений предметной области перевода с несколькими порядками компонентов и минимальными контрастами. Составить отдельные панели по направлениям EN→RU/RU→EN внутри того же домена. Train и holdout разделить по семействам фразы; перестановка слов в известной фразе не создаёт автоматически независимый holdout.

**Arms.**

| Arm | Меняется | Что удерживается |
|---|---|---|
| A | Текущий consumer с фактически доступным состоянием | Одни входы и gold, тот же decoder |
| B | Consumer получает проверенную обученную память и те же `k`/метрику E25 | Все остальные Units и параметры |
| C | Состояние B сохраняется и загружается штатным восстановлением | Corpus hash, классы, k и параметры |
| D, отрицательный контроль | Только POS-последовательность запроса заменяется нейтральной диагностической последовательностью перед KNN | Память и scorer без изменений |

Сначала проверить класс pattern и neighbour IDs, затем полноценный ответ. Primary — правильный порядок и роли компонентов в итоговом ответе; дополнительно сохранность сущностей/чисел и полнота. Для чистого E25 diagnostic primary остаётся accuracy класса. Нельзя объединять эти две метрики в одну.

**Подтверждение.** B и C дают одинаковую поддержку классов, соседей и ответы; B исправляет ошибки A на закрытых семействах, а D теряет именно структурную способность. Если меняется только внутренний pattern, а итоговый ответ остаётся прежним, зафиксировать `CONSUMER_EFFECT_UNPROVEN`.

**Ориентир реализации.** Малый однофункциональный harness и readback состояния — 30–60 минут после доступности соответствующего runtime. Полный перевод сложнее; его запуск не является частью нынешнего исследования.

## 3. REC-CLEAN-02: структура должна работать через KNN на одинаковых вопросах

**Опора.** E09 в clean: `.2413 → .3507`, `k=5`; в историческом harness baseline и KNN получают разный объём validation. [E09 split и `Take(500)`][e09].

**Гипотеза.** Часть полезной структуры при переносе из эксперимента не попадает в реальный запрос или индекс KNN. Её восстановление должно улучшить задания о коде, чувствительные к AST-связям.

**Малый набор.** 12–20 маленьких C# исходников из разных семейств плюс 8–12 закрытых заданий о роли/вложенности узла либо следующем проверяемом структурном переходе. Файлы не соединять ложными учебными переходами. Семантически одинаковые шаблоны с переименованными идентификаторами держать в одном split. Начать с C#, для которого historical extractor действительно разбирает дерево.

**Arms.**

| Arm | Получатель и единственная существенная разница |
|---|---|
| A | Frequency baseline на том же frozen train и **том же** списке heldout queries |
| B | Structural KNN с сохранённым mapping и признаками clean на той же панели |
| C | Тот же KNN, но структурная часть запроса нейтрализована; ID, память и k неизменны |
| D | Штатный Unit/consumer с восстановленным B; идентификатор вызванной функции и выбранного соседа записывается |

Не добавлять одновременно новые данные, другой размер вектора, новый scorer и другой k. Это сделало бы результат неразложимым.

**Primary.** Accuracy конкретного структурного задания, numerator/denominator и список ошибочных query IDs. Для конечного domain quality отдельно оценить собственный ответ consumer D. Neighbour distance и train accuracy — диагностические показатели.

**Отрицательный доменный контроль.** 6–8 задач, в которых ответ определяется содержанием, а не деревом, например точным идентификатором/числовым значением. AST-абляция не должна давать такое же падение на них, как на структурных заданиях. Проверку свободного текста без валидного AST считать отдельной; отсутствие gain там не опровергает C# результат.

**Опровержение.** Если на общей панели B не лучше A, историческое численное преимущество не воспроизведено. Если B лучше C, но D неизменен, структура работает локально, а штатная доставка результата ещё не подтверждена.

**Ориентир.** 45–90 минут для маленького диагностического сравнения при уже собирающемся E09 проекте.

## 4. REC-CLEAN-03: восстановление полезной памяти и сохранение старой компетенции

**Опора.** E43 в clean сообщает `.3226 → .3978` на старых переходах; исходник строит новую count-table по new и old+new. Это тест памяти. [E43][e43]. В сегодняшнем `ReplayBuffer` eligibility ограничена Domain; это [также присутствует в clean][replay-clean].

**Гипотеза.** При переезде в Unit или восстановлении индекса часть ранее полезной памяти исчезает; сохранение этой памяти восстановит старую компетенцию без потери вновь полученной. Связанный restore-разрыв проверяется раньше в [02](02-NEW-CHECKPOINT-AND-CONTEXT-GAPS.md).

**Малый набор.** Внутри одного законного domain/adapter scope выбрать две разные группы навыков: 12–20 старых заданий, для которых у baseline уже есть ненулевая компетенция, и 12–20 новых заданий. Old/new holdout выделить по источникам и семействам и закрыть до обработки новых уроков.

**Два разных опыта не смешивать.**

1. **Память KNN/count learner.** Сравнить A: память только новых примеров; B: новая плюс явно разрешённая старая память; C: B после штатного save/load. Это ближайший аналог исторического E43. Считать не только old accuracy, но и source/row IDs, доступные настоящему потребителю, с раздельными знаменателями old/new.
2. **Нейронное обучение.** Если текущий owner-contract запрещает повтор consumed pair, точный E43 replay не переносится. Допустимый rehearsal — ранее не применённые разрешённые пары на старые навыки, созданные предусмотренным teacher. Они проходят обычную проверку авторства, provenance, no-repeat и unknown-effect. Переименование старой пары или дедупликация source IDs не превращает её в новую.

**Контроли.** Old baseline=0 означает, что опыт пока не способен измерить сохранение умения. Train и heldout не должны делить source-family; exact shared переходы считать отдельно. При одинаковом total presentation budget replay уменьшает число новых предъявлений — этот компромисс надо явно учесть; другой вариант отчёта сравнивает одинаковое число новых предъявлений и честно указывает дополнительный бюджет B.

**Подтверждение.** B/C сохраняют старый навык, улучшение доходит до consumer, и новая компетенция не теряется сверх заранее выбранной допустимой границы. Изменение только DPO margin или сохранение old=0 не является успехом retention. Междоменное смешивание не требуется и не разрешается данным протоколом автоматически.

**Ориентир.** 30–60 минут для count/KNN diagnostic при готовом state loader; нейронная проверка имеет отдельный бюджет и gate.

## 5. HIST-R01: уточнение AUT-REPLAY-02 — SourceId одновременно в current и replay

**Статус: уточнение существующего AUT-REPLAY-02, `SOURCE_CONFIRMED / INHERITED / CURRENT_CONSUMER_UNPROVEN`.** При финальной проверке свежего planning commit `806d1c8534f9676cd80e7c1bf3c488163e549a4d` найден и прочитан [пакет53, AUT-REPLAY-02][aut-prior]. Он уже описывает того же владельца, добавление replay раньше quality gate, пример из двух циклов и контраргумент о корректных уроках непринятого кандидата. Эти наблюдения принадлежат предыдущему исследованию и **не считаются новой самостоятельной находкой пакета54**. Здесь добавлен только диагностический подслучай: что произойдёт, если current и replay содержат одинаковые SourceId, а manifest запрещает повтор. Причиной неудачного RP01 этот подслучай не объявляется и в начало списка restore-исправлений не входит.

### 5.1. Точная цепочка исходников

| Шаг | Что непосредственно видно | Evidence |
|---|---|---|
| Sample | Replay выбирается по совпадающему `Domain`; пересечение с `SourceId` новых примеров не исключается | [ReplayBuffer, 46–68][replay-current] |
| Admission | После Sample строится manifest по SourceId **всего** mixed batch | [AutonomousTrainer, 98–102][prepare] |
| Duplicate policy | Повторный source ID вызывает `TRAINING_SOURCE_ID_DUPLICATE`, а не тихое удаление дубликата | [BuildManifest, 107–122][manifest] |
| Запись памяти | После успешного результата trainer и проверки artifact provenance новые примеры добавляются в buffer | [AutonomousTrainer, 163–195][add] |
| Последующий gate | Pipeline вызывает TrainPrepared, затем оценивает candidate; `enhanced <= baseline` отклоняет promotion позже | [вызов TrainPrepared][train-call], [quality gate][quality-gate] |
| Scope | Именно этот pipeline передаёт пустые `DpoPairs=[]`; комментарий говорит об отсутствии non-test composition root | [PrepareBatch call][pipeline-prepare], [composition caveat][composition] |

Четыре проверенных файла побайтно совпадают между clean и current: `ReplayBuffer.cs`, `AutonomousTrainer.cs`, `AutonomousLearningPipeline.cs`, `TrainingProvenance.cs`. Поэтому это inherited стык контрактов, не доказанная миграционная регрессия.

### 5.2. Минимальный source counterexample

Это **математический вывод из кода, не результат native эксперимента**. Пусть buffer содержит пять уникальных канонических source IDs одного домена, а provider снова предъявляет ровно эти пять IDs как current. Sample запрашивает `round(5 × .3 / .7)=2` replay-записи. Любые два выбранных IDs уже входят в current. Итоговый mixed batch содержит семь записей, но пять разных IDs, и BuildManifest должен вернуть duplicate error.

Такое состояние достижимо на уровне класса после успешно опубликованного training artifact: новые источники добавляются раньше promotion gate. Однако **неудачный promotion не делает уроки плохими или запрещёнными**; replay может законно сохранять трудные валидные уроки. И наоборот, доступность этих источников не доказывает право ещё раз обновлять ими веса.

### 5.3. Быстрый диагностический проект без optimizer

Будущая native проверка вызывает только Sample/PrepareBatch и BuildManifest, без `TrainPreparedAsync`, lease и optimizer. Сопоставить:

| Сценарий | Ожидаемый результат из source | Назначение |
|---|---|---|
| Пустая память, пять уникальных новых IDs | Пять unique, подготовка возможна | Проверка валидности fixture |
| Те же пять IDs одновременно current и eligible replay | Duplicate error независимо от выбранных двух IDs | Узкий causal counterexample |
| Пять полностью новых IDs, buffer содержит прежние пять | Семь unique, подготовка возможна | Отрицательный контроль по identity |
| Другой домен, прежняя память неeligible | Replay отсутствует | Контроль доменной границы |
| Диагностическая классификация: current IDs исключены из replay-кандидатов | Нет внутрибатчевой коллизии | Проверяет причину admission-ошибки; **не допускает второй update** |

Не ослаблять BuildManifest и не молча превращать повторную запись в новую. Если такая классификация нужна производственному пути, source availability, выбор replay и consumed-pair ledger должны оставаться разными понятиями.

### 5.4. Когда это влияет на качество и когда отказ правилен

Чтобы назвать эту гипотезу причиной пропуска **законного** обучения, нужны дополнительные evidence: реальный consumer вызывает этот путь; provider действительно выдаёт overlap; новый законный lesson-set блокируется именно смешиванием; no-repeat policy разрешает соответствующие ещё не применённые пары. До этого допустим вывод лишь о поведении подготовки batch.

| Состояние пары/шага | Разрешённая интерпретация |
|---|---|
| Только подготовлена, обновление ещё не начиналось | Можно диагностировать состав источников; обычные gates всё ещё нужны |
| Пара уже consumed | Повторный optimizer step запрещён действующим no-repeat контрактом |
| Эффект предыдущего запуска неизвестен | Сохраняется unknown-effect отказ; новая source-классификация его не снимает |
| Есть новые допустимые пары на старый навык | Обычное обучение возможно только после всех действующих проверок |
| Candidate отклонён по quality | Само по себе не определяет ни плохость источника, ни право повторить update |

Следовательно, возможное последующее исправление — корректная **классификация доступных источников до обучения**, если live trace докажет необходимость. Рекомендации автоматически повторять тот же training run, менять pair_id ради обхода ledger или выбрасывать все уроки rejected candidate здесь нет.

## 6. Минимальная форма результата будущей проверки

Каждый arm записывает `commit, checkpoint/corpus hash, recipient, domain, source IDs, pair lifecycle status, train/heldout split IDs, vector/tokenizer schema, changed factor, numerator/denominator, new/old quality, restore result, verdict`. При недостающем поле — явный `UNKNOWN`.

Первый положительный опыт — основание для узкого исправления в проверенном домене и независимого повтора. Он не является разрешением включить AST/POS/replay во все Units, менять сегодняшние договорённости обучения или считать все исторические FAIL общей оценкой KNN.
