## N56-O1 — Selected subphase и предписанный positive template внутри собственного DPO input

**Доказательства S:** [`ProjectCurrent L102–155`](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/21.AgentInfrastructure/Logical/LogicalCapabilityTrainingPreferenceProjector.cs#L102-L155): `prompt` буквально включает `branch_result`, `sub_phase` + `SubPhaseId`, `Name`, `Purpose`, `PredicateIds`, а chosen/rejected строятся без чтения отдельного независимого правильного решения. [`BuildChosen/BuildRejected L356–360`](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/21.AgentInfrastructure/Logical/LogicalCapabilityTrainingPreferenceProjector.cs#L356-L360): chosen = `Generated capability for sub-phase {id}: {name}. Execute ... task type ...`; rejected = `Do not generate a capability for sub-phase {id}.`

**Точное условное отличие:** supervised preference содержит позитивную риторическую команду и правильный **уже предоставленный** идентификатор, а не independently verified output, различающий законное действие с побочным эффектом и противоположное. В таком обучении возможно улучшить DPO margin, просто воспроизводя стиль `Generated capability`, при нулевой способности выбрать нужную фазу/выполнить работу. Это не то же, что утечка из файла с экзаменационными ответами: **метка уже встроена в train input на production-пути**. Строка может быть сознательным contract для распознавания capability-selection — тогда она не дефект в этом узком назначении; ошибка возникнет лишь при неверном переносе metric selection→execution.

**Дедупликация:** близко к P34 (E22 способ producing labels), P39 (oracle output против real supplier), P81 (зависимость предпочтения от input), P111 (selected Unit credit). Прочитанные [P34](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/docs/plans/replanning-possible-diffs/experimets/cards/P34-router-labels.md), [P39](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/docs/plans/replanning-possible-diffs/experimets/cards/P39-oracle-output-separation.md), [P81](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/docs/plans/replanning-possible-diffs/experimets/cards/P81-input-conditioning.md) называют **других** producers/scorers; данный точный ProjectCurrent owner не объявляем покрытым ими, однако широкую идею «oracle/label shortcut» НЕ считаем новой.

**Проверка:** при наличии реального logical capability Student/consumer зафиксировать 2 противоположные задачи, например `включить лимит API 10/мин` vs `отключить лимит API`, которые имеют один лексический якорь, но противоположный требуемый эффект. TRAIN arms A: source-produced canned positive/rejected; B: **одна** изменённая ось — пара предметных chosen/rejected, прошедшая независимую semantic approval (сохранить весь prompt/recipient/update budget). Переназначать prompt одновременно нельзя. До обучения отдельно сделать zero-update prompt ablation и проверить степень прямой утечки ID (diagnostic, не ещё один training factor). EXAM: по два новых семейства `rate limit` и `auth permission`, не те же literal prompts; scorer заранее оценивает выбранную фазу, корректное действие, запрещённые побочные эффекты, refusal и собственный фактический результат. Шаблонный текст сам по себе — `INVALID_ACTION`, даже если содержит правильное имя phase. Если consumer предназначен **только** для генерации стандартного `Generated capability` label, это scope restriction: недопустимо оценивать его как real API execution.

**Falsifier:** в actual route нет данного ProjectCurrent → learner; или независимый correct output и hardcoded template дают одинаковую actual task accuracy/trace при одинаковых двух началax; тогда качество этим стыком не объяснено. Source-specific leak остаётся контрактом формата, не доказанным regression root.

## N56-O2 — Округлённый text vector и полный numeric identity могут представлять разные сигналы

**Доказательства S:** [`L107–110`](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/21.AgentInfrastructure/Logical/LogicalCapabilityTrainingPreferenceProjector.cs#L107-L110) берет численный TeachingVector; [`L128–155`](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/21.AgentInfrastructure/Logical/LogicalCapabilityTrainingPreferenceProjector.cs#L128-L155) формирует модельно-видимый `teaching_vector_60: {value.ToString("0.###",InvariantCulture)}` и отдельно передает **исходный float[]** в `ComputeDpoPreferenceSha256(...)` и объект projection; [`L319–346`](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/21.AgentInfrastructure/Logical/LogicalCapabilityTrainingPreferenceProjector.cs#L319-L346) digest включает float coordinates.

**Потенциальный механизм:** два различных вектора с близкими значениями (например, тестовые 0.00041 и 0.00049) имеют одинаковое `0.###` в текстовом prompt, хотя численный payload и его SHA отличаются. Это создаёт **many-to-one model-visible code** при отличающихся численных identities. Но реальные `TeachingVector` могут принимать лишь грубые значения, где совпадение никогда не случается: **НЕ** заявлять production defect без проверки достижимости действующего compiler. Ещё более важно, `DpoTrainer.VectorSignal` — отдельный путь relative scaling (известный P06); нельзя приписывать ему способность обучить семантике координат только потому, что raw float содержится в payload.

**Новизна и пересечения:** округление в **model-visible prompt** против SHA full-float — точный локальный seam, не общая уже описанная проблема «численный vector сводится к count nonzero». Protected P06/P81, N40 study of corpus identifiers — близкие, но иной owner. Сам по себе исходник не доказывает фактической collision пары доступных user requests.

**Первый 0-update gate:** по настоящим авторизованным входным запросам из уже доступных train/open DEV, без EXAM labels, материализовать compiler vectors и найти пары с одинаковым `vectorText`, но различными float bytes; сохранить оба исходных request IDs, producer hashes, full vector SHA и prompt exact bytes. Требовать **одинаковый полный model-visible prompt** только если сравнивается полное training input; если различается `semantic_prompt` или branch text, это **не** строгая коллизия полного prompt, а лишь потеря точности одного поля. При нулевом количестве таких реально достигнутых пар: `NOT_REACHABLE` и 0 обучения; описать распределение реальных численных значений, не синтезировать ложную модельную проблему.

**Лишь после R:** в test-only projection исследовать A rounding3 vs B более точное представление чисел при **тех же** raw prompts, исходных векторах, chosen/rejected, frozen model/tokenizer, update budget. Никакой смены DpoTrainer objective одновременно; source-family-disjoint реальная подфазная точность и own output сравниваются; проверить расход токенов и не выйти за ContextLen. Полный numeric SHA и replay version — новый schema/version при реальной фиксации, не silent mutation существующих checkpoint.

**Falsifier:** producer vectors всегда integer/компоненты явно quantized ≥0.001; или фактическая модель вообще не читает model-visible vectorText; или улучшений в actual output не наблюдается; source rounding не является установленной причиной RP01.

## N56-O3 — `Distinct` при replay убирает кратность повторённых доступных наблюдений

**Доказательства S:** [`ProjectAuthorizedReplay L165–214`](https://github.com/lubochka/llm_mvp_core/blob/eb05219c27663835ce927c7bf97cf1274c07cddb/21.AgentInfrastructure/Logical/LogicalCapabilityTrainingPreferenceProjector.cs#L165-L214) принимает список до 256 текущих projections, затем строит `texts = currents.Select(Prompt).Where(...).Distinct(StringComparer.Ordinal)` и `trainingText = string.Join(" ",texts)`; `ProjectReplayPayload` далее строит replay vector из этого текста. Source binding hashes и replay seal идут отдельно и могут сохранять часть identity; **не** заявлять, что вся история физически удалена.

**Отличие от обычного duplicate filter:** два реально разных feedback/lesson events могут иметь одинаковый `Prompt` при разном source-binding/history. Если частота коррекции должна усиливать предпочтение / смещать curriculum, join text перестаёт нести эту кратность; если политика требует unique laws, это, напротив, правильная экономия. Считать `repetition=2` не двумя независимыми новыми законами, но возможным reinforcement в повторном update — самостоятельная ось.

**Дедупликация:** P15 retention/replay, P24 `ReplayFusionRanker` выбор, P48 weighting/curriculum и P74 eviction родственны, **но не этот** `ProjectAuthorizedReplay` и `Distinct` именно в textual projection. Проверять producer→downstream trainer и соответствующий weight/version до заявления gap.

**Фальсификатор 0-update:** две одинаковые CurrentProjection в legal authenticated replay дают `trainingText` с одной копией, два разных Prompt — с двумя; отдельно сверить immutable source-binding count и vector/hash. Затем реальный 2×2 с **одинаковой** учебной информацией: A dedup text+frequency explicitly in metadata vs B повторно сформированные текстовые token exposures, либо другой заранее выбранный единственный фактор. Нельзя одновременно менять количество optimizer steps, model/context, kNN corpus и replay selector и называть эффект `Distinct`. На настоящих новых tasks измерить correct/total, wrong-accepted, correct/answered и `source law retained`, а не количество записей replay.

**Что могло бы опровергнуть влияние:** действующий trainer использует sourceBindings multiplicity отдельно с правильным весом; повторение текста не влияет на нужные output laws; replay вообще не исполняет этот owner; или A/B дают тот же own output при matched budget. Тогда `Distinct` является законной экономией.
