## Наблюдаемая операция и связь с обучением

`DpoProjectLoraRecipient.RequireValid`, [DpoTrainer.cs:228–263](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/11.DPO/DpoTrainer.cs#L228-L263), сравнивает base policy с отдельным frozen reference через два `Select(BitConverter.SingleToInt32Bits)` и `SequenceEqual`. Это полное сравнение **битов**, не числовое равенство float. RequireValid вызывается при получении mutation permit, вокруг update и publication; конкретные вызовы — [1208–1244](https://github.com/lubochka/llm_mvp_core/blob/de4ef0f14172dada4daf142a4c66ba19e96bb6d4/11.DPO/DpoTrainer.cs#L1208-L1244). Это прямая стоимость процесса обучения, а не отдельная serving-проверка.

Гипотеза: byte-span comparison того же полного массива может уменьшить CPU/allocations/elapsed стоимость этих guard calls при сохранении всех обнаруживаемых нарушений. Скорость конкретного backend неизвестна. Из этого не следует изменение semantic accuracy, и этот фактор не объявляется причиной старых 0/4.

## A/B и точное место ремонта

A: точная экспериментальная копия нынешнего кода. B: та же копия, где изменено **только** тело сравнения двух base arrays в строках 260–261:

```csharp
MemoryMarshal.AsBytes(entry.Parameter.Value.Data.AsSpan())
    .SequenceEqual(MemoryMarshal.AsBytes(other.Parameter.Value.Data.AsSpan()))
```

Окружающие `bases.Contains`, отрицание результата и `Invalid()` сохраняются. Все вызовы RequireValid, topology/shape/name/reference identity, права изменения, `_referenceHash`, `HashReference()` и `CryptographicOperations.FixedTimeEquals` остаются. Не добавлять cache, sampling, пропуск проверок или новое состояние. Это не предложение ослабить контроль frozen base.

Сравнение bytes сохраняет различение +0/−0 и NaN payload, которое потерялось бы при обычном float `SequenceEqual`. Оба массива имеют тот же element type/length и читаются в одном процессе. Для чрезмерно большого массива byte-span может превысить Int32 length; профиль RP01 проверяется по фактическим tensor shapes. Обобщённый библиотечный патч должен сохранить поддержку исходных допустимых размеров, например оставить прежний путь там, где byte-span непредставим; это не повод выключать сравнение. [Официальный контракт MemoryMarshal.AsBytes](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.memorymarshal.asbytes) подтверждает механизм raw-byte projection и ограничение длины, но не обещает speedup.

## Малый эксперимент

Материал, Student, B0/reference/optimizer/RNG, последовательность D-T1/D-T2 и схема A0/A1/B0/B1 полностью заданы в [04](04-small-neural-learning-contract.md). В одном A/B **4 настоящих StepVector**,по 2 на плечо. Оба плеча обучаются. **0 Generate / 0 дополнительных Evaluate**,0 внешних моделей; free-answer accuracy не измеряется. В обоих вариантах одна и та же версия остальных участков, включая padding/backward и измерители. R2 одновременно не применять.

| Измерение | Что сохранить | Как интерпретировать |
|---|---|---|
| Полный StepVector wall/CPU | По каждому из 2 шагов и сумма, одинаковые границы | Меньшее значение при той же работе — локальный полезный сдвиг; отдельно показать load/save и шум среды |
| Allocations/GC | Delta настоящего process allocation counter, counts Gen0/1/2 | Heap size и process peak — другие показатели; не подменять ими allocated bytes |
| RAM/bytes | Область peak measurement, bytes checkpoints | Отсутствие снижения RAM не отменяет CPU-успех; рост показать рядом |
| Состояние | Initial/final base/reference/LoRA, optimizer/RNG, full readback | Base/reference должны сохраниться; обучение LoRA должно дойти до предусмотренных шагов. Равенство A/B результатов ожидается по смыслу операции, но здесь не измерено |
| Учебные показатели | Фактические pre-update loss/margin каждого шага, completed/issued updates и presentations; отдельные final A1/B1 loss/margin не измеряются | Более быстрый отказ до update не считается ускорением той же учебной работы |
| Свободный ответ | `NOT_MEASURED` | Ни роста, ни отсутствия роста accuracy не утверждать |

Минимальная проверка смысловой эквивалентности guard входит в обзор того же патча: формы/размеры, одинаковые и различающиеся bit patterns, signed zero/NaN и неизменное место отказа. Она не оформляется отдельным «обучением на массиве». Runtime здесь не исполнялся. Для будущей реализации — только адресные проверки риска, без общего Windows/full-CI требования.

## Ожидаемое, опровержение и отчёт

Ожидается снижение цены сравнения, возможно без различимого изменения полного шага, если доминируют forward/backward или HashReference. Это честный нулевой эффект на выбранном бюджете. Если обнаруживаемое исходным guard нарушение перестало обнаруживаться, предложенная эквивалентность неверна; такой более быстрый код не отвечает выбранному вопросу «та же работа». Если CPU снижается, а RAM растёт, записать оба факта, не скрывать один общим PASS.

Поля actual до запуска пусты: `A0/A1/B0/B1`,2×step timings,CPU,allocated bytes,GC,RAM,state sizes,loss/margin,issued/completed counts. Чисел ожидаемого выигрыша этот проект не задаёт.
