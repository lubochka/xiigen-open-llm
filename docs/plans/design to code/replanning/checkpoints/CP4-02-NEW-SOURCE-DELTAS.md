## Выявленные различия и применение

**D1 — устаревшие handoff locators.** Прочитанный CP3 START адресовал R02 FINDINGS §7.4/7.7. R02 blob `4bf7525e831ed9df2e543259317bc2265698156d` уже сводит прошлые результаты, и новая DPO-конкретика находится в §6.1–6.5. Старый текст сохранён R02 на `334d53438db6e7e7d347dbc9a0570f0151237345`. CP4 карточки и START теперь используют именованное решение и actual ref/blob/span либо явную историческую опору; это не повод перезапускать R02. Название раздела не гарантирует неизменного line offset.

**D2 — адрес обучения между контрактами.** Прямо прочитан `llm mvp/dpo legal build/active-codex-execution-plan-07-dpo-builder.md` на `9ab76cac434331a407aa0a01cf642b6543baf287`, 195–438, blob `d6e37ab55a2bfd4deb057c28376fbb1620f7cf08`. Плановый GraphDpoPair —14полей, NodeOrEdgeId при Level=unit обозначает target unit. Прямо прочитан core `00.Core/LearningMachineContracts.cs`,1–105, blob `7f605d49762e3fc0c1b4d4ca490596bc9668cdd5`: LearningTrainingItem имеет лишь ItemId/Prompt/ChosenResponse/RejectedResponse. Pseudocode `NodeOrEdgeId = winner.UnitId` требует различить winning solver и обучаемый selector. Маршрут: R05/R07→R12→R16/R18/R22.

**D3 — два разных порядка.** P14 сохраняет OrderedPatternIds внутри serialized chosen/rejected, а OrderLevel/ConsumesPatternIds/CapabilityTags в InputContext. Зависимый semantic order важен; порядок показа candidates не должен выбирать winner. Sorting всех IDs может уничтожить обучаемое содержание. Пятнадцатое поле/Level=graph не появляется автоматически. Маршрут: R04/R05/R07/R12→R16/R18/R22.

**D4 — judge score не DPO reward.** P14 §3.2a задаёт Beta*(policyLogP-referenceLogP) для serialized side. Judge score — preference/assessment, не подмена objective. Нужен code trace serializer/masks/reduction/reference/gradient/actual params/ordinary consumer. Декларация formula не доказывает корректного update. Маршрут: R05/R12/R13→R18/R22.

**D5 — fan-out не множество независимых lessons.** P14 N candidates→N−1 source rows/attempts, одна rejected сторона каждой пары. Admission каждого урока, фактический update count и one-pair/no-repeat отдельно. Candidate family связывает строки для split и uncertainty. Teacher-goal ветвь использует Student losers; actual generator role сама по себе не определяет происхождение обеих сторон. Старая ветвь не становится запретом текущей требуемой генерации; новый generator-vs-generator допуск тоже не выдумывается. R12 согласует lineage норм, R16 применяет выбранную policy. Маршрут: R05/R08/R12/R13→R16/R21/R22/R23.

**D6 — противоречивый negative sample.** Прямо прочитан `extensions  - orchestration based on our data/ORCHESTRATION-REASONING-DPO-NEGATIVE-STRATEGY-v1.md` на P14 ref,1–90, blob `5bd4a8fc43a1cdcaf4ceda1cd1e764901ac5690d`. Правило требует одну контролируемую ошибку, образец содержит ORCH-03+ORCH-01. Это дефект документа, не установленная причина Student regression. CP4 R08 даёт два single-factor contrasts; совместный дефект отдельно interaction. `[WRONG:]` проверяется как потенциальная подсказка, не объявляется доказанной текущей leakage. Schema/annotation transport нельзя менять молча. Маршрут: R08/R12→R16/R21/R22.

**D7 — reasoning, coordinates и evolution sources.** При исходной подготовке прочитаны R03 CP05 F11–F16; blob того ranged чтения отдельно не зафиксирован, предполагаемого SHA здесь нет. Сохранённый исторический snapshot CP05 указан самим новым R03 как planning commit `10dfbfd8a46f67b9cf43ce827d00d1dbf6d18078`. Это prior attributed evidence, не новый primary audit автором CP4. Найдены ORM-43 learned node внутри одной L5-машины, несовместимость raw-word/TaskSignal spaces, investigation path и thin host. R01 F12, blob `33b7611caed1fc21912f3e21e8a96b15a884da4b`, маршрутизирует `docs/plans/ARCHITECT-PLAN-LEARNING-MACHINE-EVOLUTION-v1.md`; историческое «ответ изменился» не значит «стал лучше». CP4 R04–R07/R13/R18/R23/R24 сохраняют эти различия.

## Поздняя дельта параллельного R03 — не новый общий раунд

Во время проверки публикации прямо прочитаны текущие R03 FINDINGS1–67 и136–207, blob `394f6084b71eca25404dcfa0098d4542c807a58e`, **CP07 / IN_PROGRESS / SOURCE_TRAVERSAL_NOT_COMPLETE**. R03 сообщил исправление неполной передачи своих прежних F17–F19, новый F20 и code seam F21. Это его работа; автор CP4 не считает её собственным исследовательским проходом.

**D8 — исторический чрезмерный запрет deterministic helpers.** R03-F20 ведёт через C/RAG-11 к repo-root `extensions reasearch/PLAN-XIIGEN-SKILL-SELECTION-MACHINE-EXTENSION-v1.md`, на его P5 `10dfbfd8a46f67b9cf43ce827d00d1dbf6d18078`,1–90, reported primary blob `a6df21e9b7a170381a01ea6b2944fa364c06f3c5`. По прочитанному отчёту исторический §0 запрещает BM25/AST/Jaccard даже при подготовке candidates/context, а не только как подмену learned final authority. Это конфликт с нынешней гибридной постановкой, не основание молча вырезать helpers или declaring_IMPLEMENTED по баннеру.

**Адресный prompt R06/R12:** прочитать этот primary span и текущую реализацию43.SmartSkillsDomain по существующей карте; разделить generation/constraints/learned selection/final assessment. Сохранить цель выбора подходящих skills, но показать selected/rejected hybrid alternatives. Опыт: одинаковые approved skills/tasks/budget, fixed candidate retrieval+learned selection против пригодного baseline; task success, missing required skills, unknown-task handling и total cost. Good: helper предлагает кандидатов, learned owner выбирает в явно допустимой области. Bad: исторический blanket ban автоматически запрещает всю semantic preprocessing либо fixed retrieval объявляется learned choice. Edge: обязательный skill отсутствует в top-k, unknown task, illegal candidate. Выход R06 — producer/authority trace, R12 — согласованная граница; R16/R20 применяют её в разрешённых живых документах, вне-scope source/skill changes остаются точным proposed patch. Это часть назначенных Rxx, не R26.

**D9 — actual LoRA seam, не готовая полезность.** R03-F21 прямо атрибутирует свой code read `10.LoRA/LoraLinear.cs`1–145 на core `a5de1a893db8e44e3dce0f4f54cdae2a4d06d1a3`, blob `1b321e99408c961b896896983d002e3b26425b85`: base projection плюс A/B update и registration. Это полезный fresh input R05, но не доказательство frozen base во всём optimizer, active installation или ordinary state consumption. R05 читает seam и его реальные callers, сохраняет reuse; R12/R22 отделяют projection wiring от domain gain. Не переписывать существующий LoRA класс ради самого названия задачи.

## Что уже опубликовано и что остаётся выполнением будущих Rxx

CP4 RECOVERED-DESIGN-PROMPTS опубликован в `a67f8dc4af080a9123bbe0f3bea26c481790da8b`; первоначальная CP4 правка START — `a2201b78e48b44021f197522eb5c376f2729f9d2`; PLAN-25-RUNS — `00849cf10189417d6cb4017c9caff31c7b1b590c`. Это авторские уточнения поручений, не исполнение R04–R25. Поздние D8/D9 передаются адресно; не требуют повторять всю подготовку либо останавливать R01–R03.

Source aliases в карточках локальны: H01/H02/H03 в source-table CP4 относятся к результатам R01/R02/R03; они не должны подменять одноимённые H-разделы HYBRID при сборке. Dispatcher обязан квалифицировать source и section, а в готовом packet использовать понятные имена `SRC-R01`, `SRC-R02`, `SRC-R03` отдельно от `HYBRID:Hxx`.

Полнота всей библиотеки, обучение, runtime correctness, PC-fit и independent Astra review этой публикацией не установлены. R01/R03 продолжают собственные остатки; статус R02 определяется его carrier, не автором плана. Обновления кода/tests/workflows/weights/datasets и product runs этой работой не выполняются.
