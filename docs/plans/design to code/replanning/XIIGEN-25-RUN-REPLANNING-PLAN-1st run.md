## 3. Три разных вида доказательств

| Что хотим установить | Подход в новом плане | Чего это не доказывает |
|---|---|---|
| Механизм не нарушает свои обязательные свойства | Адресные проверки авторизации, изоляции, данных, состояния, ограничения эффектов и воспроизводимого запуска | Что модель стала полезнее |
| Обучение даёт полезный эффект | Реальные обновления, замороженный baseline, отдельные задания, разнодоменные результаты, контроль регрессии и неопределённости | Что продукт уже готов к Windows-поставке |
| Работает целевая поставка | Необходимые Windows/native/integration проверки на соответствующих изменениях и перед выпуском | Что произошло широкое обучение |

Разделение — это предлагаемый принцип пересмотра. Конкретные обязательные проверки выбираются после анализа рисков. Проверяемые результаты программных задач, схемы данных и другие объективные ограничения остаются частью оценки качества, даже если они реализованы тестами. Убирается не слово «тест», а подмена способности модели прохождением fixtures.

## 4. Как будет оцениваться обучение

Предлагается три раздельных набора: учебный, рабочий валидационный для итераций и закрытый приёмочный. Источники/семейства/шаблоны разделяются там, где иначе задания слишком похожи. Использование проверочных данных для выбора/настройки модели даёт оптимистичные оценки; закрытый экзамен не должен становиться источником новых уроков. [S9–S10]

Для сравнения parent/candidate сохраняются входы, рубрика, бюджет inference и версии. Показываются результаты по доменам, а не только средний балл: качество на новых заданиях знакомого домена, перенос на неучившийся домен, сохранение старых способностей, расход и разброс. Конкретные размеры выборки и пороги выбираются в R13 по доступным данным и цели, до измерения кандидата; универсальных «95% означает готовность» здесь нет.

Для открытых ответов можно использовать независимое слепое сравнение и выборочный экспертный контроль; для проверяемых задач — независимый объективный результат. LLM-оценщик не считается безошибочным: у такого подхода описаны смещения порядка, многословия и предпочтения собственных ответов. Поэтому его рубрика и пригодность требуют проверки, а не просто другого имени модели. [S11]

Отдельно измеряются: корректность учебных данных, реальность обновления, полезный эффект и готовность выпуска. Падение loss, рост счётчика, смена hash весов или сохранение checkpoint сами по себе не являются приёмкой широкого обучения. Отрицательный либо неопределённый эксперимент может быть завершённым исследованием; candidate с недоказанным улучшением не обязан заменять parent.

## 5. Как обращаться с Windows CI

Во время этих 25 сессий новые продуктовые Windows/GitHub runs не запускаются: анализируются уже существующие данные. Это не обещание отключённого CI и не отмена обязательных checks. Для будущей разработки R17 задаёт условия запуска по типу изменения и риску, а не один полный прогон на каждый документ.

Нельзя решать вопрос простым `[skip ci]`: GitHub предупреждает, что пропущенные из-за фильтров или сообщения коммита required checks могут остаться Pending и заблокировать merge. Политика workflow, required checks, публикации DRAFT и допуска к release должна быть согласована явно. [S12]

Исследовательский путь может быть отделён от ожидания релизной Windows-матрицы, если он использует допустимый рабочий runtime и сохраняет необходимые инварианты. Windows-специфический дефект, от которого реально зависит этот runtime, нельзя объявить нерелевантным. Повтор запуска допускается только по новой проверяемой гипотезе и в выделенном бюджете; unknown outcome не означает разрешение повторно обновить модель.

## 7. Первые результаты новой разработки

Это ориентир для редакции roadmap, а не заранее утверждённый выбор алгоритма:

**Первое: один настоящий учебный цикл.** Использовать существующий продуктовый путь; реализовать лишь доказанно недостающее звено. Взять небольшой, но смыслово разнодоменный набор, сохранить baseline, выполнить разрешённое обновление и сравнить новое поведение. Например, старт с 3–5 выбранных предметных областей может быть кандидатом для пилота; число и области уточняются по данным, а не объявляются достаточным охватом.

**Второе: расширение обучения по ошибкам и доменам.** Увеличивать разнообразие задач и сигналов, контролируя перенос и сохранение предыдущих способностей. Решение добавить алгоритм/инфраструктуру должно объяснять, какое наблюдаемое ограничение оно снимает.

**Третье: необходимая надёжность и поставка.** Усиливать восстановление, многопользовательскую эксплуатацию, платформенную совместимость и длительные сценарии в нужных местах. Минимальные обязательные защиты действуют с первого опыта; широкая сертификация не становится произвольным условием любого исследовательского шага.

Ни окончание R25, ни принятие нового документа не означают, что эти результаты уже получены. Дополнения R21–R25 не должны превращаться в требование сначала реализовать весь описанный будущий evaluation/curriculum framework.
