## R21 — составить curriculum, который действительно различает домены

**Контекст:** WorkLeft RESEARCH-01 и его review как исходная база, R08 inventory, R12 representation/kNN choices, R13 protocol, R16 requirements, R19 roadmap и DOMAIN-EXPERIMENT-RECIPES. Не заменять семь доменов одним CodeDocumentation.

**R21.A · Заполнить семь предметных паспортов. Skills M/A/S.**
Для EN↔RU, orchestration, Figma→HTML+CSS, C#, Angular, SQL и DPO Builder задай input/output, поддомены/сложность, разрешённый источник, hard laws с первичным основанием, soft preference, неизвестный/смешанный случай, representation primitives и кандидат соседства из выбранного R12. Укажи, какое различие нельзя потерять: отрицание/число, порядок/ресурс, структура/viewport, фактическое поведение кода, причинность state/UI, семантика данных либо полезность учебной пары. **Выход:** семь заполненных passports в действующем curriculum, связанные с requirements и algorithm owners. **Приёмка:** каждому домену заданы собственные gold/rubric, negative class и измеряемый исход; выбранная функция не выдаётся за доказанно лучшую. **Хорошо:** условный числовой токен сохраняет value/unit/polarity и downstream сравнение проверяет пользу этих полей. **Плохо:** тот же cosine по одному общему тексту объявлен оптимальным для всех доменов без опыта. **Край:** реальное правило имеет исключение/версию — passport фиксирует применимость и источник. **Передать B:** паспорта и доступные семейства задач.

**R21.B · Задать усложнение, разделение данных и требования к парам. Skills M/P/A.**
Построй порядок simple→ambiguous→constraint failures→composed/mixed→new families→user feedback. Начни с узкого опыта, затем отличающегося домена, сохранив весь curriculum. Раздели семьи до производных вариантов; выбери примеры hard negatives и quarantine rules. В пару входят один контекст, корректный chosen, содержательная ошибка rejected, rationale и независимый критерий; роль разрешённого автора и provenance сохраняются. **Выход:** curriculum schedule, pair specification и dataset lineage requirements, не выдуманный готовый корпус. **Приёмка:** для каждого домена есть обычный, трудный и новый сценарий с baseline/метрикой; экзамен не переходит в обучение. **Хорошо:** negative правдоподобен, но нарушает одно важное ограничение. **Плохо:** два варианта одной задачи распределены между train и certification как независимые. **Край:** обе стороны одинаково допустимы — tie/abstain, не искусственное предпочтение. **Передача:** R22 recipes, R24 пользовательские сценарии.

**Будущая оценка:** per-domain gain, перенос на новые семьи, routing coverage/ошибки, полезность DPO и сохранение прежнего домена после обучения следующего. Количество пар не равно широте способности.

## R22 — подготовить первый опыт, который можно выполнить без нового фреймворка

**Контекст:** R13 protocol, R18 exact implementation packets, R19 first-learning spine, R21 curriculum и реально имеющийся measurement path. Если команды/методы ещё не установлены, это адресный blocker, а не повод сочинить CLI.

**R22.A · Полностью определить первый baseline/challenger рецепт. Skills M/A/C/P.**
Назови prerequisite implementation seam, исходный frozen state, предыдущий accepted state, одну меняемую причину и допустимый challenger. Определи source/version/lineage задач, панель до/после, новую eligible pair identity, capture/update/evaluate/decision порядок и реальные API/commands из R18 для будущего разрешённого исполнения. Зафиксируй primary/guard metrics, лимит попыток/ресурсов, stop и полный restore. **Выход:** готовый первый experiment work order с заполненными параметрами либо явно локализованным отсутствующим решением. **Приёмка:** следующий исполнитель не выбирает порог или датасет после просмотра результата; никакие экспериментальные действия не выполняются в R22. **Хорошо:** один selected mechanism против существующего static/no-update reference. **Плохо:** одновременно поменять все компоненты и назвать опыт проверкой DPO. **Край:** no improvement — допустимый исход, старый state сохранён, следующая гипотеза определена. **Передать B:** первый recipe и условные дальнейшие вопросы.

**R22.B · Задать последовательность следующих опытов и честный bulk report. Skills M/P/A.**
Добавь только различающие семейства: representation/router, dynamic versus static kNN, actual preference/adapter, допустимые deterministic/learned/hybrid пути, другой домен и feedback retention. Не строить полный декартов перебор. Для каждого определи reference, один фактор, fairness источников/бюджета, ожидаемый falsifier и условие запуска после первого опыта. Bulk включает все попытки, не только удачные; на новой панели сравниваются обе версии. Training replicates не обходят one-pair/no-repeat; inference сравнения и training события различаются. **Выход:** conditional experiment sequence и пример заполнения bulk report с явно искусственными демонстрационными значениями, без measured claim. **Приёмка:** видны A0/Aprev/C, case families, quality/coverage, hard failures, uncertainty, p50/p95, полная цена, state versions и решение. **Хорошо:** C быстрее на 20 условных миллисекунд, но неверно решает constraint case — гипотеза экономичного допустимого пути не подтверждена. **Плохо:** считать только successful latency, скрыв timeout/fallback. **Край:** leaked dataset либо несовместимый rubric — invalid measurement, не алгоритмический успех. **Передача:** R23 ресурсные limits, R25 final handoff и будущий авторизованный experiment executor.

**Будущая оценка:** качество и время от bulk к bulk на сопоставимых задачах. Улучшение валидности пары, loss и конечного поведения ученика — разные показатели.

## R23 — определить, влезает ли вся система в ПК и как она продолжает учиться

**Контекст:** R04–R07 state map, R09 costs, R12 architecture, R22 recipe, реальные hardware/model manifests. Старые сведения о ПК требуют актуальной привязки; типичный сервер не подставлять вместо компьютера пользователя.

**R23.A · Составить ресурсную модель полного процесса. Skills A/C/M.**
Зафиксируй подтверждённые CPU/GPU, RAM/VRAM и storage. Посчитай раздельно measured peaks и оценки: weights/reference, adapters/projections, gradients/optimizer/activations, embeddings/index, graph, retained examples, caches, checkpoints/restore и scratch. Не складывай независимые пики как одновременные и не считай разделяемый base дважды; покажи модель одновременности. Задай для первого опыта input length, candidates/k, concurrency, adapter targets/rank и предел роста из фактического бюджета. **Выход:** resource envelope с единицами, предположениями и измеряемыми неизвестными. **Приёмка:** меньше adapter bytes не равно меньше total memory; полный rebuild/evaluation/teacher cost не скрыт. **Хорошо:** отдельно peak VRAM, peak RAM, live disk, rollback reserve и cost на принятое улучшение. **Плохо:** обещать работу на 8 GB только по размеру весов. **Край:** не помещается snapshot — выбрать меньший обоснованный scope/state strategy, не убрать восстановление молча. **Передать B:** пределы, state owners и восстановительные зависимости.

**R23.B · Определить online feedback и согласованное восстановление. Skills A/C/M/P.**
Пройди user input→ответ текущего state→разрешённая обратная связь→provenance/consent/предметная проверка→новая допустимая пара→candidate update→оценка нового/прежнего домена→accept/restore. Определи identity/version для router/encoder/index/graph/adapter и реального mutable state. Пользовательское утверждение не становится фактом без проверки; исправления с неясными правами/секретами не попадают в обучение. Рост памяти/сжатие/pruning — отдельная измеримая гипотеза, не скрытое изменение политики replay. **Выход:** stateflow с owner, atomic boundary, journal/resume и bounded growth policy. **Приёмка:** восстановление после applied-before-evaluation не даёт двойного gradient; старые навыки проверяются inference без запрещённого повторного обучения пар. **Хорошо:** сомнительная correction карантинируется, текущая модель продолжает допустимую работу. **Плохо:** автоматическое принятие любого пользовательского negative. **Край:** OOM, crash, устаревший index, conflicting feedback и exhausted disk имеют определённый исход. **Передача:** R24 пользовательские journey, R25 и future implementation/experiment owner.

**Будущая оценка:** usefulness после correction, retention, время update/ответа, реальная полная память/диск и восстановление согласованного state. «Continual learning» в названии не является доказательством.

## R24 — связать улучшение алгоритма с настоящим результатом пользователя

**Контекст:** R02 original journeys, R16/R19, R21–R23 и адресные DPO/DTC/IDE первоисточники. Не выдавать adapter response за доказательство установленного host-сценария.

**R24.A · Составить сквозные сценарии трёх направлений. Skills A/P/S/M.**
Для DPO/DynamicGraph, Design-to-Code и VS/VS Code/Continue восстанови user input, ограничения, domain/representation/path, реальный output consumer, сохранение/публикацию и повторное использование. Привяжи нужные семь доменов и применимые уровни без механического требования каждой комбинации. Для DTC сохранить API, renderer/viewports, поведение, БД и model publishing; для IDE — request/response и реальный host путь как разные виды будущего evidence. **Выход:** конкретные journey cards с requirement/source, expected outcome и measurement seam. **Приёмка:** сценарий кончается полезным результатом пользователя, не файлом-маркером; release integration остаётся в scope, но не автоматически prerequisite раннего обучения. **Хорошо:** принятый state используется следующим реальным запросом приложения. **Плохо:** checkpoint создан, значит пользователь получил лучший ответ. **Край:** local API работает, installed host не проверен — два разных статуса, не общий PASS. **Передать B:** сценарии и обратные связи.

**R24.B · Проверить отрицательные исходы и полезность изменения. Skills M/A/P.**
Для каждой journey добавь wrong/mixed/unknown domain, noisy feedback, expensive fallback, restore и cross-domain regression. Сопоставь C/Aprev/A0 на одинаковой задаче: правильность/допустимость, цена и реальное действие пользователя. Определи, какие изменения модели не дают продуктовой пользы и потому требуют другой гипотезы. **Выход:** user-level acceptance map и список оставшихся delivery obligations с owners. **Приёмка:** хороший внутренний score не закрывает плохой пользовательский исход; все claims имеют scope. **Хорошо:** более короткий маршрут полезен лишь при сохранении результата и ограничений. **Плохо:** красивое описание неверного SQL названо качественной документацией. **Край:** обе версии дают разные, но допустимые решения — предметная рубрика оценивает смысл, не совпадение строк. **Передача:** R25 final review, future product/experiment owners.

**Будущая оценка:** usefulness в пользовательском journey и цена полного пути. Никакой новый e2e suite не создаётся этим planning-проходом.

## R25 — независимая итоговая экспертиза и выход из перепланирования

**Контекст:** фактически выполненные R01–R24 и их limits, оригинальные требования, live changed plans/prompts, R15 findings, R18 implementation packet и R22 first recipe. Requested independent role — Astra Ultra; actual identity/effort/отдельность и candidate SHA обязательны по факту.

**R25.A · Проверить покрытие и закрытие замечаний без нового глобального исследования. Skills A/P/C/M.**
Независимый reviewer сопоставляет source→requirement→mechanism→future evidence→owner. Проверяет закрытие каждого R15 finding по изменённому документу, а не по ответу автора. Для всех трёх направлений и семи доменов устанавливает preserved/deferred/blocked и границу подтверждения; адресно читает только необходимые первичные стыки. **Выход:** scoped final examination с конкретными незакрытыми решениями. **Приёмка:** нет fake completion по 25 опубликованным файлам; actual reviewer не заменён авторской ролью. **Хорошо:** первый учебный путь определён, отдельная release задача честно открыта. **Плохо:** вся программа объявлена готовой по одному хорошему S04 пакету. **Край:** отсутствует независимая сессия/источник — NOT_PERFORMED/ограничение, а не выдуманный PASS. **Передать B:** final findings и точный ближайший implementation/experiment candidate.

**R25.B · Проверить, что следующий шаг — действие, а не ещё план. Skills A/P/M/E.**
Пройди первый R18 packet и R22 recipe от свежего code/state ref до измеримого результата. Проверь selected design, реальных owners/signatures, input availability, допустимую новую пару, no-repeat, полный restore, primary/guard metrics и resource limits. Нет ли скрытого «сначала все Windows tests», нового framework либо ещё не выбранной архитектуры. **Выход:** ready-for-this-bounded-next-action / конкретный blocker с owner, первый implementation prompt, затем experiment prompt и сохранённые дальнейшие обязательства. **Приёмка:** инженерные решения для первого шага определены; эмпирическая польза остаётся честной гипотезой. Не создавать R26 и не назначать автоматическую новую N-pass кампанию. **Хорошо:** следующий авторизованный executor меняет один найденный seam и проводит заранее определённое сравнение. **Плохо:** «всё готово; следующим запуском составьте план реализации». **Край:** первый challenger проигрывает — reference сохраняется, известен falsifier/следующая гипотеза без снижения цели. **Передача:** непосредственному авторизованному implementation owner, не новому общему перепланировщику.

**Финальная граница:** завершение 25 planning runs, готовность конкретного ближайшего действия, measured learning gain и готовность всех поставок — четыре разные вещи. Ни одна не следует автоматически из другой.
