### Что считается результатом

Для любой обучаемой возможности различаются пять состояний:

1. **Механизм допускает опыт** — существует реальный owner/state/signal/update/consumer и можно безопасно выполнить bounded intervention.
2. **Опыт проведён валидно** — baseline/challenger/no-update сопоставимы; teaching/evaluation разделены; provenance и state lineage известны.
3. **Эффект IMPROVE / REGRESS / INCONCLUSIVE / INVALID_EVIDENCE** — это функциональный результат, а не PASS/FAIL unit-тестов.
4. **Candidate принят или parent сохранён/восстановлен** — отрицательный или неопределённый опыт может быть полностью завершён без принятия новых весов.
5. **Интеграция/поставка проверены отдельно** — native/Windows/IDE/DTC/release evidence требуется только там, где выбранная capability реально пересекает соответствующую границу.

Ни build, ни coverage, ни число тестов, ни lower loss, ни ненулевой gradient, ни факт изменения hash/weights сами по себе не доказывают полезное обучение.

### Действующий learning-first контракт

Единица прогресса: **один причинно различимый учебный вопрос → минимальное изменение одного learned authority → обычный consumer → сопоставимое функциональное наблюдение → решение принять/откатить/оставить parent → следующий вопрос**.

Первый опыт не выбирается автоматически по S04 или DPO. Кандидаты E1–E4 ранжируются по причинной различимости, ожидаемой информации на полную стоимость и наличию реального consumer:

- **E1 DPO/update/adoption** — exact pair действительно доходит до обучаемого recipient/state и принятая версия читается обычным consumer.
- **E2 domain/vector/dynamic-kNN** — отдельно измеряются mapping домена, сохранность domain laws в representation, retrieval/reranking и learned dynamic-k/radius policy.
- **E3 ILearningFlow / ILearningOrchestrator** — Unit capabilities по возможности фиксированы; меняется relation/path authority, включая стоимость неудачных/отменённых async ветвей.
- **E4 ILearningDynamicGraph** — проверяется перенос на невиданные допустимые композиции; memorized path не считается graph transfer.

ILearningUnit, ILearningFlow, ILearningOrchestrator, ILearningDynamicGraph остаются разными обучаемыми уровнями. Улучшение одного уровня не закрывает остальные.

### Детерминированное + обучаемое

Жёсткие законы домена, типы, допустимость, безопасность, schema/version compatibility и final arbiter остаются детерминированными границами. Обучаемые механизмы могут выбирать, ранжировать, адаптировать representation/retrieval/path **внутри допустимого пространства**. Ручная смена k/threshold/configuration не является обучением.

Для каждого домена до заявления улучшения фиксируются: domain passport; правила/исключения; mixed/unknown cases; token/features/vector/index identities; positive/negative/warning memory; ordinary consumer; training/dev/independent evaluation families; practically meaningful delta; допустимая регрессия и полный ресурсный бюджет.

### DPO: авторство, проверка и one-pair/no-repeat

Действующий role contract:

- CODEX с GPT-6 Astra UltraCode выбирает учебный case/task как делегированную human-role работу.
- Разрешённая внешняя открытая китайская модель создаёт **обе финальные стороны** chosen/rejected.
- CODEX с GPT-6 Astra UltraCode отдельно оценивает **точную финальную projected pair** до optimizer eligibility и не переписывает стороны под чужим provenance.
- Student обучается; post-update evaluator отделён от pair judgment.

Качество пары и полезность для Student — разные величины. Валидная пара может не дать улучшения.

Сохраняется **одна новая pair_id → одно разрешённое применение; no-repeat**. Bulk означает блок наблюдения последовательности новых разрешённых уроков, а не скрытый replay/minibatch и не повторное применение старой пары. Исторический replay 70/30 не считается текущим разрешением внутри evidence continual-learning до отдельного явного решения владельца.

### 95%, bulk-to-bulk и принятие состояния

95% остаётся product goal относительно заранее зафиксированного domain reference/rubric там, где этот owner goal применим. Это не router confidence, не pass rate тестов и не обязательный prerequisite первого полезного опыта.

На границах bulk измеряются как минимум:
- качество по каждому заявленному домену и worst-domain;
- delta против parent на тех же evaluation families;
- retention/forgetting;
- время generation/update/evaluation/adoption;
- peak RAM/VRAM и persistent disk growth;
- model/reference/adapters/optimizer/index/graph/cache/snapshots/reindex/failed attempts;
- ordinary-consumer behavior.

Порог/дельта и правило принятия задаются **до** просмотра challenger. При REGRESS или INCONCLUSIVE parent сохраняется/восстанавливается. При INVALID_EVIDENCE исправляется эксперимент, а не threshold.

### LoRA, vectorized token и continual learning на ПК

LoRA не объявляется tokenizer или semantic vectorization по названию. Для каждой learned projection нужны source/target space, trainable matrix/group, frozen state, loss/objective, version, downstream consumer, index compatibility и rollback. Изменение representation требует явной политики migration/reindex; старые и новые векторы нельзя молча смешивать.

Цель compact PC continual learning доказывается только полной стоимостью системы и последовательным пользовательским потоком: сначала оценить текущий ответ, затем допустить feedback, выполнить изолированный candidate update, проверить ordinary consumer и retention, после чего принять или откатить. Пользовательская коррекция не является автоматически истинной.

### Что остаётся отдельным доказательством

Unit/integration/native/Windows/Actions проверки сохраняются для детерминированных инвариантов, сериализации, rollback, permissions, launcher/native behavior, delivery и release. Они не являются learning-efficacy gate по умолчанию. Обязательность конкретного host-check должна быть причинно связана с выбранной capability.

## Предпосылки первого запуска и критерии результата

Перед первым новым обучением нужно сначала разобрать незавершённую попытку. Если одна пара уже применена, открыть пробные веса после неё, сохранённую исходную оценку и прежние условия проверки без повторного обучения. Если незавершённой попытки нет, нужно найти фактически сохранённую принятую модель, проверить совместимость, разместить её в целевой ветке, закрепить отдельного проверяющего и наборы заданий. Не подменять отсутствующие веса скрытым стартом с нуля.

Сначала снять исходную оценку ученика и сохранить её до изменения весов. Если она уже 95% или выше с учётом погрешности, новую пару не создавать, а перейти к отдельному итоговому удостоверению. Если целевое качество ещё не подтверждено с учётом погрешности, до обучения сохранить одну новую пару и полный снимок состояния. После обучения только этой парой отдельная модель-проверяющий оценивает ученика в тех же условиях и только потом принимается решение: сохранить новую версию, восстановить прежнее состояние или оставить прежние принятые веса при равном/неясном результате.

Точный порядок пары: сохранить одну новую пару; сохранить снимок до неё; обучить только этой парой; после обучения оценить ученика на том же закрытом наборе и сохранить ясное улучшение либо восстановить/оставить состояние до пары.

Готовый шаг домена — это успешный сценарий, где новая пара сохранена до обучения, исходная оценка сохранена и перечитана до изменения весов, веса действительно изменились, улучшение подтверждено, ухудшение восстановило прежнее состояние, повторный запуск не применил ту же пару второй раз, а удалённая ветка содержит данные и LFS-объекты.

## Пометка 27.08.2026 — S3: четыре дыры проверки кода получили решения и строки работ

**Что произошло по-человечески.** Владелец нашла в коде четыре дыры и приказала: «Попробуй найти решение и встроить в программу с Fable 5 ultra — 3 проходами». **Четыре дыры и что с ними теперь.**

1. **Тренажёр учился на бедной записи пары.** В проекте две разные записи обучающей пары под одним именем: богатая — с паспортом учителя, бедная — ровно три строки текста. К моменту, когда пара становится тензорами и меняет веса, паспорт уже отброшен, поэтому правило «эталон платной модели никогда не сторона пары» охраняло пустоту — его нечем было проверить там, где решается судьба весов. **Решение:** маленький контракт допуска пары объявляется в самой сборке тренажёра, заполняется верхними слоями, и проверка ставится в начало **всех трёх** входов, меняющих веса. Второй проход нашёл главное: таких входов три, а не два, — третий (векторный) первый проход пропустил вовсе, и охрана двух входов обходилась бы третьим. Механизм отказа не изобретается: у тренажёра уже есть готовая дверь того же жанра — серверное разрешение мутации весов.

2. **Пола шума прибора в коде не было вовсе.** Любой прибор дрожит, и пока неизвестно, насколько дрожит наш, всякое «стало лучше на два процента» неотличимо от дрожания. **Решение:** паспорт шума клетки замера (несколько повторов одного и того же замера дают пол) плюс правило неразличимости: разность меньше пола — «неразличимо», и никакой отчёт не имеет права написать «стало лучше». Второй проход закрыл самообход: необязательный аргумент-паспорт не сработает никогда, пока вызывающие его не передают, — поэтому проводка паспорта через фактических вызывающих стала обязательной частью работы, а не пожеланием.

3. **Порождатель пар сам строил и сам себя мерил.** Он назначал тип отвергаемой стороны номером круга цикла, резал набор первыми пятьюдесятью строками и ставил себе оценку, проверяя наличие пометки, которую сам же только что вписал в каждую пару, — гейт не мог не пройти. **Решение:** честный ярлык «детерминированный посев», явная матрица покрытия вместо номера круга, отказ вместо молчаливого обрезания, независимый проверщик вместо самооценки и запрет смысловой публикации с посевного батча. Холодный старт остаётся работоспособным — он перестаёт выдавать себя за источник смысла.

## Дополнение 04.09.2026 — обязательный маршрут артефактов перед реальным обучением

Единственный канон для следующих training-срезов: репозиторий `C:\Projects\llm_mvp_core`, ветка `codex/dpo-implementation`; DPO хранится только в `training-data/dpo/<domain>/<design-pattern>/<version>/`, общие веса и контрольные точки — только в `training-artifacts/models/<domain>/<design-pattern>/<model>/<version>/checkpoints/<positive-step-six-digits>/`.

До первого вызова открытой китайской модели исполнитель обязан открыть exact sealed DPO по `domain/pattern/version`, hash-only платным эталонам, exact teacher artifact, generation policy и creator effective config. Exact match означает reuse существующего набора и 0 teacher calls. Mismatch, corrupt, v1 или partial означают fail-closed, 0 teacher calls и запрет молчаливой перегенерации.

До обучения исполнитель обязан загрузить latest compatible checkpoint с диска и создать incremental/resume session; если compatible checkpoint существует, fresh start запрещён. После успешного продолжения нужно атомарно опубликовать child checkpoint с manifest, который несёт точную parent lineage: parent checkpoint manifest path, parent step, parent weights SHA-256 и byte length, плюс exact sealed DPO manifest/hash; успех нельзя заявлять до reopen/readback.

Если DPO или веса найдены вне канона, training-срез нельзя продолжать из бокового пути и нельзя пересоздавать как замену. Сначала импортируются точные байты в канон, проверяются hash/manifest, затем идёт отдельный review и только потом публикация ветки; другая ветка, диск или рабочая копия не становятся каноном.

Живые primitives уже существуют и повторно не создаются: `RepositoryOwnedTrainingArtifactLayout` — единственный владелец canonical DPO/model layout, включая `/checkpoints/<six-digit-step>/`; `RepositoryOwnedDpoDatasetResolver`; `RepositoryOwnedDpoDatasetRequestIdentity`; `RepositoryOwnedModelCheckpointLoader`; `RetainedCheckpointBackedIncrementalTrainingSessionFactory`; `RepositoryOwnedIncrementalTrainingCheckpointPublisher`. Реальные незакрытые code gaps: live DesignConversion transaction wiring before first teacher call и live training completion -> atomic child checkpoint publication. Честная граница: пока нет реального teacher call, production DPO, training run или новых weights; это правка программы, а не выполненное обучение.
