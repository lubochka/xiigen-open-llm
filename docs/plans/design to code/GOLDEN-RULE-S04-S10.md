## ACTIVE_SUBAGENT_FINAL_FORBIDDEN_GATE — active worker means continue

If the current task has an assigned subagent whose actual state is `running`,
`waiting`, `cancel_pending`, `unknown`, or otherwise lacks supported terminal
evidence, the parent **must not end the turn** with final/done/hold/status-yield.

A visible progress update is allowed only when the next action in the **same
turn** is another supported wait/status/checkpoint/recovery action for that
worker. Wait timeout, missing packet, slow reasoning, or "still working" is not
a blocker and not a turn boundary.

A returned NEEDS_FIX/PARTIAL/FAIL packet is a continuation trigger: after
supported release, continue the next authorized repair/review step under OP-65.
Do not convert it into a final answer while the task remains open.

Before any final/status-yield require:
- active_task_open=false, or the whole assigned task/program is complete;
- no current-task subagent remains active/unknown;
- next bounded safe action is absent, or it was executed this turn;
- true external blocker certificate or explicit user stop when work is not complete.

Exact literals:
`ACTIVE_SUBAGENT_FINAL_FORBIDDEN_GATE`
`subagent waiting is not a turn boundary`
`progress update must be followed by wait/status/recovery in the same turn`
`wait timeout is not final`
`NEEDS_FIX/PARTIAL is continuation, not final`
`no final while current-task subagent is active`

This rule is mandatory for **every** task, microtask, work unit, code slice, review-fix task, evidence task, and recovery task in S04-S10. It is not a once-per-slice startup check.

## EXECUTION INTEGRITY / PUBLICATION STATE GATE

Every S04-S10 task must distinguish durable publication from accepted closure. A task result may be committed/pushed as `DRAFT <task-id>: ...` while required independent review is pending, but DRAFT never advances the execution pointer. 1. architecture obligations are loaded and the current minimal design/scope is established;

## C. Canonical branch and conflict-free pre-task Git gate

The live `AGENTS.md` / `CLAUDE.md` define the canonical workspace and implementation branch. Currently for core this is:

- workspace: `C:\Projects\llm_mvp_core`
- branch: `codex/dpo-implementation`

Do not invent a new per-slice branch unless Luba explicitly changes the branch policy.

Before **every** task:

1. `git fetch --prune origin`;
2. record root, current branch, local HEAD, `origin/<current-branch>`, `origin/main`, and status;
3. verify the current branch matches the live canonical branch rule;
4. preserve unrelated owner work;
5. verify `origin/main` is an ancestor of HEAD;
6. verify `origin/<current-branch>` is an ancestor of HEAD;
7. if either is false, reconcile/merge before task work;
8. resolve conflicts from actual source ownership, never blanket ours/theirs;
9. require `git diff --name-only --diff-filter=U` = empty.

A task may not start on a diverged or conflict-bearing branch.

## D. Every accomplished task gets its own commit and push

Every task that is claimed accomplished must end in its own durable task-scoped commit.

- Code task: commit reviewed code/tests + task work/evidence delta.
- Plan/architecture task: commit the reviewed plan/architecture/work-state delta.
- Verification/evidence/no-code task: commit its durable evidence/state/work-report delta.
- A task with literally zero durable repository delta cannot be claimed accomplished; record its no-change verification in the task work/state file and commit that record.

Do not batch several completed tasks into one later `work artifacts` commit.

Commit message must include the task ID and bounded outcome.

## E. Validate and review before task Git closure

Before publication of a task:

1. inspect exact owned diff;
2. exclude accidental generated/cache/build outputs unless explicitly canonical product artifacts;
3. run required structural/static checks;
4. run focused tests;
5. run impacted/wider tests where required;
6. complete independent code/evidence review where required;
7. repair findings;
8. rerun checks invalidated by repairs;
9. update the durable task report with actual evidence.

## F. Re-fetch and merge/reconcile again immediately before commit/push

Remote state may move during task execution. Therefore immediately before task commit/push:

1. `git fetch --prune origin`;
2. reconcile any new `origin/<current-branch>` commits;
3. reconcile any new `origin/main` commits;
4. resolve every conflict;
5. require zero unmerged paths;
6. require `git merge-base --is-ancestor origin/main HEAD` = success;
7. require `git merge-base --is-ancestor origin/<current-branch> HEAD` = success;
8. run repository main-compatibility / merge-tree validation when available and require clean/no-conflict result;
9. rerun checks invalidated by reconciliation.

This reconciliation is a manager responsibility. Reviewer roles do not commit/push, but a reviewer PASS does **not** close the task until the manager completes this Git gate.

## G. Atomic task closure: commit → push → remote readback → report

For every accomplished task:

1. stage only reviewed task-owned files;
2. commit with task ID + bounded outcome;
3. push the canonical branch normally;
4. fetch/read back remote state;
5. prove remote branch contains the task commit / expected HEAD lineage;
6. record local commit SHA and remote readback SHA;
7. produce a human-readable task report with:
   - task ID and purpose;
   - what changed;
   - validation/tests;
   - plan/code review result;
   - branch reconciliation/merge-conflict result;
   - commit SHA;
   - pushed remote SHA;
   - remaining work and next task.

**The next task may not start until all seven closure steps are complete.**

## H. Git failure stays inside the current task

If branch divergence, main compatibility, non-fast-forward, merge conflict, push rejection, or remote mismatch occurs:

- current task remains open;
- do not start another task;
- resolve it immediately;
- do not accumulate more local task commits;
- do not use force push as a compatibility shortcut;
- after three materially different technical attempts, use the architect/advisor escalation ladder;
- routine Git reconciliation is not a Luba stop.
