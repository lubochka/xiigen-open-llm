# ARCH-ADVISOR-ESCALATION-S04-S10-v1

Applies to slices S04 through S10.

## Purpose

Technical difficulty must not become a premature owner-intervention gate. When an architect cannot resolve the same technical issue after three materially different, evidence-producing resolution trials, the parent must run the advisor escalation ladder below before the task may be returned as technically blocked.

This is explicit owner authorization for these development-model escalations. It is a narrow exception to ordinary "no hidden model fallback/substitution" language. It does not change the product/student/teacher/evaluator model, provider rights, security boundaries, spending authority, effect budgets, or independent-review requirements.

## Trigger and issue identity

An **issue** is one concrete blocker/failure with a stable fingerprint: failing predicate/command/test, relevant source/candidate identity, error/evidence, and affected task boundary.

The architect gets **three** materially different resolution trials for that issue. A trial must change a hypothesis, patch, command, evidence source, or other causal assumption and must record the result. Repeating the same failed command/patch with unchanged inputs is not a new trial.

A resume, new session, smaller packet, renamed issue, different agent handle, or model change does not reset the issue's trial/advisor counters. A genuinely different blocker gets a new issue fingerprint and its own ladder.

## Mandatory advisor ladder

After the architect's third failed trial, do not stop and do not ask the owner to choose a model. Escalate sequentially:

1. **Sol Extra High** advisor — up to 3 advisor chances.
2. **Sol Ultra** advisor — up to 3 advisor chances.
3. **Astra Extra High** advisor — up to 3 advisor chances.
4. **Astra Ultra** advisor — up to 3 advisor chances.

Each advisor chance is one bounded advice/application cycle:
1. parent verifies the previous actor and owned commands are terminated;
2. parent invokes only the current advisor tier;
3. advisor receives the full accumulated issue packet and returns a concrete diagnosis, changed hypothesis/action, verification/falsification step, and what must not be repeated;
4. advisor releases the shared slot;
5. architect resumes, applies/tests that advice once within existing task authority, records new evidence, and releases the slot if still unresolved.

Maximum advisor-help cycles for one issue: **12** (3 per tier). Stop the ladder immediately when the issue is resolved and resume the original task at its first unmet predicate; do not restart the slice/task.

## OP-65 / no nesting

The architect must not spawn an advisor while remaining active. Advisors are invoked by the parent/manager sequentially. Architect, advisor, resumed architect, final executor, and reviewers never overlap in the one-total-project-subagent slot. A model upgrade does not relax OP-65 or independent author/reviewer separation.

## Unsupported advisor tier

Use actual supported native model/effort controls and record requested versus observed identity. Do not silently alias or downgrade a requested tier.

If a requested advisor tier is unavailable, perform one supported availability check, record `TIER_UNAVAILABLE`, and advance automatically to the next tier. Unavailability is not an owner question and does not consume three fake advice attempts.

## Final executor escalation

If all four advisor tiers are exhausted without resolving the same issue, reassign the **unresolved task** to the native option labelled **Astra 6 Extra** as an **executor**, not an advisor.

The Astra 6 Extra executor receives:
- the complete current task/work order and authority;
- issue fingerprint and first failing predicate;
- all architect trials;
- all advisor attempts and recommendations;
- exact diffs/commands/test logs/runtime evidence;
- current branch/source/candidate/state identities;
- remaining budgets/effect counts and actions that must not be repeated.

It owns the bounded implementation/test/repair work permitted by that slice and may choose a new solution, but it must preserve all existing safety, data, effect, cost, Git/CI, and review constraints. The handoff does not reset retries, budgets, product effects, or evidence history.

Normal independent review still follows the final executor; the final executor never self-accepts.

## When owner escalation is finally allowed

Do not return a merely technical issue to the owner before this ladder is exhausted. After the Astra 6 Extra executor, a task may remain BLOCKED only when no safe authorized technical action remains, or when there is a genuine external boundary such as owner-only access/2FA/SSO, required third-party approval, exhausted hard budget, unavailable required asset/model, forbidden security action, new license/provider/spending decision, or destructive action with uncertain ownership.

Even then, finish all independent safe work and return one exact blocker with the accumulated evidence. Never fabricate success or promise background continuation.
