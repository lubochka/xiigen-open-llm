## R16 repair — общая learning-first программа, а не бесконечный S04/Windows цикл

**Сфера:** вся система XIIGEN, не только CodeDocumentation/S04. Исходные S00–S10, DPO/DynamicGraph, Design-to-Code, IDE, языки/предметы, оригинальные product requirements и раздельная поставка сохраняются; этот раздел не объявляет их реализованными. Кратчайший путь к первому реальному обучению определяется причинной зависимостью, реальным learned owner и обычным consumer, а не количеством завершённых слайсов или зелёными Windows Actions.

**Четыре функциональные обучаемые возможности, разные владельцы и причинные гипотезы:**
- **ILearningUnit:** типизированное many→many «domain + schema токенов/векторов + requested output type → набор результатов заданного типа», с правом детерминированных фильтров/типов и конкретным learned state там, где он действительно существует. Улучшение проверять при том же правиле допустимости, но с изменёнными обучаемыми параметрами Unit.
- **ILearningFlow:** связи, коррекции и переходы между Units. Для отдельного доказательства обучаемости менять relation/correction state, по возможности фиксируя Unit и evaluator; измерять корректные связи, предотвращённые ошибки и стоимость шагов.
- **ILearningOrchestrator:** асинхронный выбор и исполнение допустимых маршрутов с зависимостями, отменой/таймаутами и ограничением бюджета. Изучать качество lawful path, стоимость ветвления, отмен и latency, сравнивая с доступными изученными альтернативами, а не объявляя найденный маршрут глобально оптимальным.
- **ILearningDynamicGraph:** higher-order связи паттернов и доменов, перенос на новые допустимые композиции, управление versioned graph state и final arbiter. Успех на запомненном пути не подтверждает обучение Graph; Graph не становится дополнительным независимым trainer вместо действующего ILearningMachine.

**Граница hybrid:** детерминированными остаются законы каждого реального домена, права, типы, safety/admissibility, schema/index compatibility и финальное решение о принятии; обучаемые функции ищут/ранжируют/адаптируют только в допустимом пространстве. Для каждого из E1–E4 назвать отдельные state/signal/update owner, consumer и falsifier, не считать выигрыш Student доказательством обучения Flow/Graph.

**Домены и эффективная компактность:** сопоставить oracle-domain и predicted-domain на смешанных/неизвестных входах; law-sensitive tokens/features/vectors/index; exact search и фиксированную kNN против learned rerank/aggregation/query-dependent k/radius, где несколько соседей действительно влияют на consumer. Ручная смена k — конфигурация, не динамическое обучение. LoRA параметризует адаптацию только при известных source/target, frozen/trainable group, objective, version, rollback, index migration; размер/низкий loss адаптера не доказывают сохранения смысла. Компактность на ПК — суммарные модель/reference/adapter/optimizer/activations/index/graph/cache/snapshot/reindex/evaluator расходы и рост после каждого bulk.

**Приоритет реального обучения:** сначала выбрать один причинно наблюдаемый E1/E2/E3/E4 эксперимент с максимальной информацией на затраты при фактическом кодовом seam; заморозить baseline/no-update, domain laws, evaluation families, ограничения, threshold, full-state snapshot. При валидном REGRESS/INCONCLUSIVE сохранить parent и перейти к следующей гипотезе без ретроактивного подгона; при INVALID_EVIDENCE исправить дефект измерения без заявления об эффективности. S04 локально — один новый урок в текущем objective; S05 отдельно отвечает за разрешённую удалённую публикацию; S06/S07 имеют свои серии НОВЫХ уроков и более широкие предметные панели, без скрытого replay.

**Пока не READY для exact executable learning packet:** R12-A…F ещё требуют итогового hybrid synthesis, R13 требует заполненной experiment card после свежей source lineage, R15 independent CODEX/Astra review NOT_PERFORMED (parent NEEDS_FIX). R16 переносит только source-bound требования; R17 политика риска Windows, R18 exact state/consumer packet, R19 roadmap, R20 effective compiler prompts. Документальный patch сам по себе не является product implementation/измеренным улучшением и не разрешает произвольные внешние вызовы/новые costs.

**Текущая область S04/S06/S07 — 02.10.2026.** Этот раздел уточняет текущую работу; он не подтверждает выполнение. Датированные указания 09.09.2026 полностью сохранены в архиве по ссылке ниже. Только в конфликтующих пунктах для S04 их заменяют: существующий noise-aware критерий вместо голого `>=95`; отдельные verdict механизма/реального урока/качества; локальные материалы S04 и отдельная remote-публикация S05; текущие ограничения данных, эффектов и V2. Прочие исходные требования не отменены. Исторические «уже сделано» сверяются с actual core evidence, не повышают статус автоматически.

**Объект обучения:** существующий XIIGEN Student для CodeDocumentation, не Qwen, не JSON-журнал и не таблица маршрутизации. До реализации назвать по текущему коду обычный вход генерации, объект модели, обновляемые нейронные параметры/адаптер, владельца DPO-обучения и загрузчик выбранного checkpoint. Новые имена классов не являются доказательством существующего кода.

Требуемая связь: отдельное учебное задание → допустимая Teacher-пара → существующий DPO/trainer → параметры Student → сохранённый checkpoint → обычная генерация Student на отложенных заданиях. Проследить фактическую цепочку вызовов; реализовать минимальный разрыв в существующих владельцах. Смена флага, KNN-записи, счётчика или хеша файла сама по себе не доказывает градиентное обучение или качество. DPOReferenceModel — математическая опора, не независимый оценщик.

Иллюстрация, не учебные данные: Student неверно описывает поведение метода при отмене. Teacher пишет контраст на отдельном разрешённом примере. После обновления проверяются другие методы с тем же классом поведения, обычным продуктовым вызовом. Ни улучшение, ни различие каждого конкретного ответа после одного шага не гарантируются; фиксируются параметры, фактическое выполнение и честное измерение.

**Следующее действие определяется текущим продуктовым пробелом.** Сначала прочитать актуальные core task/effect records и применимый опубликованный допуск; не повторять принятый неизменившийся identity-substrate или известный planning/core source-import. V2 capacity admission и ограничения C05 остаются в силе. Нехватка конкретного T/byte/reservation решения требует законченного решения в существующей amendment/schema и отдельного review, затем реализации guard и тестов; ни эта редакция, ни наличие Teacher-конфигурации не дают capacity PASS.

После закрытия своей стадии менеджер продолжает первую зависимо готовую задачу в том же разрешённом S04 run. Рабочий return/checkpoint не завершает родительский run; незавершённые исправления/проверки и занятый OP-65 slot учитываются честно. При read-only readiness-пробеле выдать минимальную задачу ответственному executor в действующей цепочке (например S04.04B для authoring-связи), а не просто повторять статус. У каждой задачи: actual source owners, минимальный допустимый diff, проверяемое поведение и следующий шаг. Настоящий запрет доступа/ресурсов не обходить; отсутствие дизайна или обычный дефект кода не объявлять внешним блокером.

**Один урок не равен всему обучению.** Лимит S04 — одна новая пара и один допускаемый update в одном objective. Он не переносится как вечный лимит на кампании S06/S07. Отрицательный завершённый урок сохраняется; новый допустимый урок возможен только в отдельно предусмотренной кампании с её неизменяемыми лимитами, новыми разрешёнными данными и собственным учётом. Не повторять тот же experiment до удачной оценки, не обнулять стоимость/экспозицию/optimizer entry при новом run ID.

S06.08B/S06.09C уже отвечают за заранее заданные кампании и learning curves. Использовать их, не создавать дублирующий этап. Для S07 сохраняются все существующие arms, два rounds, шесть Student subjects, разделение данных и независимые инструменты. Полноценный отрицательный эксперимент сохраняет полезную информацию, но цель доказанного useful learning остаётся открытой.
