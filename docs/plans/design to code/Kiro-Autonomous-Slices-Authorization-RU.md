## 6. При ошибках: исправлять, а не возвращать на согласование

| Ошибка | Следующий шаг |
|---|---|
| YAML, expression/context, entrypoint, trigger или недоступный workflow_dispatch | Минимально исправить workflow, проверить статически, review точного diff, опубликовать, запустить новый кандидат. Не создавать новую архитектуру CI. |
| Restore / package feed / сеть | Проверить реальную причину. Для transient 429/5xx — ограниченный retry с backoff/Retry-After. Для неверного пути/конфигурации — исправление. Не уменьшать безопасность feeds и не менять версии пакетов наугад. |
| Требуемый SDK отсутствует | Установить/выбрать предусмотренный проектом SDK в ephemeral CI через официальный механизм. Не обновлять production framework ради удобства тестов. |
| Build failure | Читать первый реальный compiler diagnostic, исправить исходники/фикстуру/ссылки по доказанному контракту, rebuild и новый gate. |
| Тесты не найдены или executed=0 | Исправить discovery/filter/путь assembly. Не считать exit=0 успешной проверкой. |
| Тест упал | Прочитать assertion, фактический production путь и fixture. Исправить причину; автор отдельного теста не объявляет себя reviewer. |
| TRX/evidence validator упал | Отличить невалидный результат от ошибки валидатора. Проверить валидатор на настоящем формате и отрицательных fixture. Сохранить исходные results. |
| Внешний transient сбой после старта | Один-два обоснованных rerun без изменения исходников допустимы. После повторения той же причины — диагностика, не retry until green. |
| Таймаут | Проверить progress и owned process. Обоснованно изменить timeout/разбивку тестового набора или исправить deadlock. Не уменьшать обязательные случаи и повторы. |
| Flaky test | Установить источник недетерминизма и исправить изоляцию/код. Не принять один случайный зелёный повтор как доказательство исправления. |
| Конфликт PR / проверки GitHub | Разрешить конфликт своего среза, получить актуальные проверки. Не bypass protections и не force merge. |
| Неизвестная причина | Один ограниченный диагностический шаг с проверяемой гипотезой, затем действие по результату; не серия отчётов с тем же общим сообщением. |

Обычные дефекты production-кода, обнаруженные обязательными тестами, разрешено исправлять через архитектора, точный scope и независимую review. Не нужен новый вопрос «можно поправить этот метод?». Новый продукт, разрушительная миграция или ослабление охраны данных в этот scope не входят.

## 8. Доказательства, публикация и продолжение

Для S03.01 обязательны восемь существующих identity-сценариев, их фактические вызовы/отказы и принятый impacted набор. Не исключать случай ради CI. Совпадающие focused/impacted наборы допускают один подтверждённый запуск с явным сопоставлением обеим обязанностям, когда отдельный повтор не является требованием эксперимента; не считать один набор дважды уникальным покрытием.

Принимать только цепочку: требование → изменённый production owner/caller → assertion → фактически выполненный тест → raw evidence → отдельный review. Успешная сборка, зелёный workflow без тестов, metadata PASS и наличие TRX-файла не заменяют эту цепочку.

Сохранять SHA исходников, нужных артефактов и workflow, actual checkout, run/attempt/job, команды и числовые exits, TRX totals/outcomes и проверку всех required methods. Отсутствующие или неполные данные обозначать честно, не восстанавливать выдумкой.

Commit/push кандидата до CI разрешён. Отправлять точный набор файлов, без `git add -A` и чужих изменений. Product merge — только для проверенного среза и по protections. Документальный commit после успешного теста не обязывает пересобирать неизменённое приложение, если проверено отсутствие изменений relevant inputs; при этом проверенный candidate SHA не переписывать на новый report SHA.

После приёмки задачи автоматически выбирать следующий dependency-ready task из действующего плана. Не заканчивать работу только из-за одного PASS/commit.
