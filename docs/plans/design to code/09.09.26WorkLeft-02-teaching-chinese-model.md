## R16 repair — кто выбирает урок, кто создаёт DPO, кто проверяет результат

**Это действующее требование к будущему выполнению, а не свидетельство выполненного запуска или разрешение на model call.** Пилот S04 CodeDocumentation — одна ветка полной программы (перевод EN↔RU, orchestration, Figma→HTML/CSS, C#/Angular/SQL documentation, Builder и дополнительные домены). Параметры существующего S04 допуска, ownership, privacy, state и S05 публикации не снимаются.

**Разделение ролей без исключений:**
1. **CODEX с GPT-6 Astra UltraCode** (конкретный S04 operator: GPT-6-Astra в режиме ultra) выполняет делегированную человеку работу: выбирает/утверждает конкретный допустимый учебный case на основании разрешённых диагностических сигналов и доменных законов. Не просить человека вручную выбирать за CODEX и не подменять выбор отсортированным списком.
2. **Разрешённая внешняя открытая китайская модель** генерирует ОБЕ финальные стороны DPO: chosen (правильное/лучшее решение) и rejected (содержательно худшее решение). Weak Student answer может быть разрешённым контекстом, но не автоматически финальным rejected. Исключены закрытые задания/ответы, неавторизованные источники и приписывание чужих байтов Teacher.
3. **CODEX с GPT-6 Astra UltraCode отдельно** проверяет пригодность точной финальной пары и контекста после генерации: доменные правила, превосходство chosen, содержательность rejected, происхождение, нарушение запретов, TIE/BOTH_BAD/UNJUDGEABLE. Ассессор не «исправляет» стороны под авторством Teacher; при изменении существенных байтов нужна новая оценка и действующий допуск. Persisted не означает optimizer-eligible.
4. **Student/Trainer** применяет только допущенную пару к правильным параметрам/адаптеру, с одним разрешённым применением нового pair_id, полным parent snapshot и без скрытого replay. **Независимый post-update evaluator** исследует полезность через обычный продуктовый consumer на ранее замороженных независимых families. CODEX pair-judge не превращается в evaluator Student и не заменяет математическую DPO objective.

**Функциональная проверка вместо процента coverage:** freeze parent/challenger/no-update при сопоставимом context/memory/compute и train/dev/holdout provenance. Измерять правильность решения доменных задач и negative/warning cases, accuracy/quality per domain и worst domain, retention, затраты времени и полный PC footprint, а не только loss, новый hash, прошедшие тесты или успешно завершённый Windows run. Bulk = последовательность новых допустимых уроков, их свойства сравниваются от bulk к bulk; повторная pair_id не является новым уроком.

**Статусы отдельно:** readiness механизма; валидный/невалидный урок; IMPROVE / REGRESS / INCONCLUSIVE / INVALID_EVIDENCE / NOT_MEASURED; решение promote/keep-parent/rollback; отдельно native/release readiness. Валидный отрицательный опыт завершён, но прирост не доказан и плохие веса не принимаются. 95% — сохранённая продуктовая цель по owner-defined domain rubric, не confidence/coverage и не условие старта первого информативного эксперимента.

**Нельзя объявлять архитектурное решение и READY преждевременно:** R12 A–F = INTEGRATED DESIGN CANDIDATE (documentary, см. current `replanning/results/R12/RUN-LOG.md`); фактические state/optimizer/ordinary consumer и learning effect остаются UNBOUND/NOT_MEASURED; R13 = REPAIR_REQUIRED, R15 = parent NEEDS_FIX и independent CODEX/Astra review NOT_PERFORMED. R18 выбирает фактический learner owner/state/ordinary consumer только после устранения соответствующих ограничений. R17/R19/R20 переносят evidence-policy, очередность и effective prompts; наличие этого абзаца не доказывает, что compiler или code уже изменён.

Источники решений: replanning/results/R15/FINDINGS.md, replanning/results/R12/RUN-LOG.md, replanning/results/R13/RUN-LOG.md, replanning/results/R16/DECISIONS.md; текущий точный S04 role contract — Kiro-Xiigen-S04-Luna-xhigh-v2-Pack/overlay/.kiro/xiigen-slices/luna/s04/RUN-CONTRACT.md §§2.1–2.3.

Совместимый уже принятый профиль сохранить; расхождение решить по действующему допуску, а не молча подменять модель. Предложение `qwen3-together-v1` относится к отдельной удалённой фазе. Эта редакция не разрешает скачивание весов, новый провайдер, новые расходы или внешнюю передачу данных.

**Роли:** XIIGEN Student генерирует ответ и обучается; отдельный Teacher создаёт материал урока; Evaluator измеряет результат; Luna/Kiro пишет продуктовый код и не подставляет свои ответы вместо данных Teacher. Учитель не обязан находиться в облаке. Учебный контекст содержит отдельную задачу и разрешённые сведения о слабости; закрытые вопросы/ответы исключены. Действующий S04 authoring-контракт обеих сторон пары сохраняется: финальные `chosen/rejected` связаны с фактическим ответом Teacher, а не копируются из чужого эталона. Происхождение добавляет приложение, не выдумывает модель.

**Объект обучения:** существующий XIIGEN Student для CodeDocumentation, не Qwen, не JSON-журнал и не таблица маршрутизации. До реализации назвать по текущему коду обычный вход генерации, объект модели, обновляемые нейронные параметры/адаптер, владельца DPO-обучения и загрузчик выбранного checkpoint. Новые имена классов не являются доказательством существующего кода.

Требуемая связь: отдельное учебное задание → допустимая Teacher-пара → существующий DPO/trainer → параметры Student → сохранённый checkpoint → обычная генерация Student на отложенных заданиях. Проследить фактическую цепочку вызовов; реализовать минимальный разрыв в существующих владельцах. Смена флага, KNN-записи, счётчика или хеша файла сама по себе не доказывает градиентное обучение или качество. DPOReferenceModel — математическая опора, не независимый оценщик.

Иллюстрация, не учебные данные: Student неверно описывает поведение метода при отмене. Teacher пишет контраст на отдельном разрешённом примере. После обновления проверяются другие методы с тем же классом поведения, обычным продуктовым вызовом. Ни улучшение, ни различие каждого конкретного ответа после одного шага не гарантируются; фиксируются параметры, фактическое выполнение и честное измерение.

**Раздельные выводы приёмки:**

| Вывод | Требуемое доказательство |
|---|---|
| Инженерная цепочка работает | Реальный product caller, достаточные synthetic/regression наблюдения, корректное сохранение/восстановление. |
| Реальный урок состоялся | Конкретный Teacher-запрос/ответ и сохранённая пара, фактический разрешённый optimizer entry/update, исходное/пробное полное состояние и связанные измерения. |
| Качество изменилось | Полное независимое сравнение в замороженных условиях: improved, regressed, indistinguishable или допустимый identical-weights результат. Invalid/incomplete не превращается в отрицательный успех. |
| Результат используется | Свежая загрузка выбранного состояния и обычный путь Student/consumer действительно используют его. |

Ветка `NO_TRAINING_NEEDED` сохраняет реальный достаточный baseline и исходное состояние, с нулём пары/учителя/update; она не доказывает произошедшее обучение. Число optimizer entries, committed updates и факт выбора child различаются. Один шаг может дать identical weights; нельзя изобретать изменение ради отчёта. Полноценный отрицательный результат может завершить предусмотренную процедуру, но не удовлетворяет условию доказанного улучшения.

Закрытые материалы, пары и веса хранятся только по существующему разрешённому пути. S04 создаёт локальные материалы урока, S05 отдельно доказывает разрешённую удалённую публикацию. Источник product-прогресса — implementing DRAFT и его код/результаты, не evidence-only ACCEPT, JSON или зелёный пакет инструкций.
