Назначение файла: держать покрытие по трём проектам, а не подменять его удобной разбивкой на домены. Три проекта текущего плана: `dpo-legal build`, Design-to-Code и расширения Visual Studio / VS Code / Continue.

## Что должно оставаться видимым по каждому проекту

1. `dpo-legal build` — обучение собственной модели. Внутри этого проекта отдельно видны DPO-цикл, перевод, оркестрация, загрузка уже принятых весов, одна новая пара от Qwen, отдельная модель-проверяющий, точный откат или принятие и планка качества 95% к зафиксированному эталону.
2. Design-to-Code — превращение макета и требований в проверяемый HTML/CSS-результат. Здесь нужны вход пользователя, представление элементов и связей, сборка кода, проверка результата, сигнал улучшения и связь с обучающим контуром только там, где она реально подтверждена или явно помечена как остаток.
3. Расширения Visual Studio / VS Code / Continue — рабочая интеграция в редакторы и Continue. Эти расширения не исчезают из остатка работ из-за того, что обучение описано отдельно; по ним должны оставаться видимыми требования, готовность, недостающие проверки и связь с пользовательским сценарием запуска.

## Как читать домены качества под этой структурой

- Перевод и оркестрация относятся к проекту `dpo-legal build`, если речь идёт об обучении собственной модели и её политике выбора.
- Design-to-Code остаётся отдельным проектом продукта, даже когда его ошибки используются как источник новых DPO-пар.
- Расширения являются отдельным проектом доставки продукта в IDE; модульные тесты и RAG-карта не закрывают их готовность без проверки реального сценария расширения.
- Планка 95% относится к качеству модели на зафиксированном эталоне. Это не процент зелёных модульных тестов, не уверенность маршрутизатора и не автоматическое доказательство готовности расширений.

## Ожидаемое и фактическое

Ожидаемое покрытие: в активных WorkLeft-документах можно отдельно увидеть, что открыто по `dpo-legal build`, что открыто по Design-to-Code и что открыто по расширениям Visual Studio / VS Code / Continue. Фактическая граница этого файла: он задаёт структуру чтения и не доказывает, что все три проекта уже закрыты.
