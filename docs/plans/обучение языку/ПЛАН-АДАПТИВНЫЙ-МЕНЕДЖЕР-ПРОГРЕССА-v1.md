# Адаптивный личный менеджер прогресса ученика
# Версия: 2.0 — 2026-05-29
# Статус: Планирование

---

## Ключевой принцип

**Ученик — это обучаемая модель.**

Курс обучения ученика — это тот же процесс, что тренировка переводчика:
- Тренировочные примеры = упражнения + ответы ученика
- Точность модели = точность ученика по доменам
- Тренировочный цикл = сессии упражнений (10+10 вместо 100+100)
- Ворота (gate) = `studentProductAccuracy ≥ threshold` — тот же механизм, что в TranslationDomain
- Продвижение по уровням = то же, что переход к доменному fine-tuning после прохождения базовых ворот

Поэтому архитектура — не отдельная система поверх доменов, а **новый домен в той же иерархии:**

```
ILearningMachine<StudentDomain>
```

Это означает: не нужны детерминированные эвристики для сложности, прогрессии и оценки уровня. Нужна та же самая система, которая уже умеет обучать переводчика, — применённая к ученику.

## StudentDomain — что он определяет

По аналогии с `TranslationDomain`:

| TranslationDomain | StudentDomain |
|---|---|
| Языковое направление (RU_EN, EN_RU) | Учебный домен (calque, false_friend, grammar, idiom, register…) |
| DPO-пара: source + chosen + rejected | Учебный пример: exercise + student_answer + is_correct + latency |
| Весовые адаптеры по направлению | Адаптер точности по учебному домену |
| `TranslationKnnStore` — хранит что выучено | `StudentProfileStore` — хранит точность, историю, уровень |
| `runtimeProductAccuracy ≥ 0.95` | `studentProductAccuracy ≥ 0.80` (по домену) |
| Bootstrap fallback: нет подходящей пары → вернуть источник | Bootstrap для ученика: нет истории → начать с Tier 1 |

## Три обучаемых юнита ученика

По аналогии с тремя юнитами TranslationDomain:

### PlacementUnit (аналог SemanticTokenizerUnit)

**Что учит:** правильно определять текущий структурный уровень ученика.

- Вход: 10 упражнений из стратифицированного сета (по 3-4 из каждого Tier)
- Выход: `StudentCapabilityProfile` — стартовый уровень + слабые домены
- Как работает: это просто `EvaluateAsync` на начальном батче. Никакого специального алгоритма — тот же механизм оценки, что в TranslationDomain
- Ворота: нет — PlacementUnit не обучается, он только оценивает стартовое состояние

### SessionComposerUnit (аналог ExecutorUnit)

**Что учит:** выбирать правильные упражнения для текущего состояния ученика.

- Вход: `StudentCapabilityProfile` (текущий уровень, слабые домены, история)
- Выход: `ExerciseSession` — набор упражнений для следующего батча
- Как работает: по weakDomains подбирает упражнения из ExerciseBank с весом; по currentTier — из нужного уровня сложности
- Обучается: по мере того как учитель (система) видит, какие комбинации упражнений дали рост точности → обновляет стратегию подбора

### ProgressVerifierUnit (аналог QualityVerifierUnit)

**Что учит:** определять, действительно ли ученик освоил домен или просто угадывал.

- Вход: результаты батча N+1 (unseen — никогда не видел в тренировке)
- Выход: `domainGatePassed: true/false` + обновлённые метрики
- Ворота: `studentProductAccuracy ≥ 0.80` по домену за последние 3 батча
- Анти-контаминация: упражнения из тест-батча НИКОГДА не должны совпадать с тренировочным батчем (тот же инвариант, что trainHeldoutOverlap = 0 в TranslationDomain)

## Цикл обучения ученика (10+10, аналог 100+100)

```
Взять 10 упражнений из текущего Tier + weakDomain (батч N)
    ↓ Ученик отвечает (тренировка)
    ↓
Взять СЛЕДУЮЩИЕ 10 упражнений, которых ученик НИКОГДА не видел (батч N+1)
    ↓ Измерить studentProductAccuracy
    ↓
accuracy ≥ 0.80 → DOMAIN GATE PASSED
                  → продвинуть домен (weakDomain → improving → mastered)
                  → если все домены текущего Tier ≥ 0.80 → повысить Tier
accuracy < 0.80 → батч N+1 становится тренировкой, батч N+2 — новый тест
                  ПОВТОРИТЬ
```

**Обязательные видимые метрики после каждого 10+10 цикла:**

```
train_exercises
test_exercises
studentProductAccuracy       (% правильных на unseen батче)
studentExactAccuracy         (% полностью правильных без подсказок)
bootstrapRate                (% упражнений без истории → Tier 1 по умолчанию)
domainAccuracyByType         (по каждому из 7 errorType)
currentTier
gate_target = 0.80
```

## Difficulty stratification (Tier 1 / 2 / 3)

Упражнения из банка распределяются по трём уровням по аналогии с тем, как TranslationDomain разделяет базовую модель и доменное fine-tuning:

| Tier | Что характеризует | Откуда берётся |
|---|---|---|
| Tier 1 | Короткие предложения, бытовая лексика, очевидная ошибка | Первые батчи level-1 из training-pairs-train-ready.jsonl |
| Tier 2 | Средней длины, формальный/полуформальный регистр, неочевидная калька | Средние батчи, более сложные паттерны |
| Tier 3 | Длинные, идиоматические, сложная структура, тонкий регистровый сдвиг | Поздние батчи, domain-specific (бизнес, юридические) |

**Tier — это не хардкодированная метка.** Tier определяется через те же метрики, что gate в TranslationDomain:
- упражнение попадает в Tier 1 если типичный студент-новичок даёт правильный ответ за < 3 секунды
- Tier 2 если правильный ответ требует размышления (3-10 секунд)
- Tier 3 если большинство новичков ошибаются с первого раза

Это значит: аннотация Tier — это эмерджентное свойство, которое появляется из данных первых пользователей, а не проставляется вручную.

## Placement test = EvaluateAsync на стартовом батче

Никакого специального механизма. Первый вызов для нового ученика:

```
EvaluateAsync(PlacementBatch)
  → StudentCapabilityProfile {
      detectedTier: 1 | 2 | 3
      domainAccuracy: { calque: 0.4, false_friend: 0.7, grammar: 0.5, ... }
      weakDomains: [calque, grammar]
      startingRecommendation: "Tier 1, focus: calque + grammar"
    }
```

PlacementBatch = 10 упражнений: стратифицированная выборка (3 из Tier 1, 4 из Tier 2, 3 из Tier 3) × покрывающая минимум 4 разных errorType.

После PlacementUnit → `StudentCapabilityProfile` записывается в `StudentProfileStore` как стартовое состояние модели ученика. Дальнейшие сессии обновляют его через TrainBatchAsync.

## Прогрессия (без детерминированных эвристик)

Ворота работают так же, как в TranslationDomain:

```
После каждого 10+10 цикла ProgressVerifierUnit проверяет:

Для каждого weakDomain:
  если studentProductAccuracy ≥ 0.80 за последние 3 батча:
    domain_status = "mastered"
  иначе:
    продолжить тренировку этого домена

Если все домены currentTier имеют status = "mastered":
  currentTier += 1   (переход к следующему уровню сложности)
  weakDomains = все домены нового Tier (начать с нуля на новом уровне)
```

Регрессия (аналог "если gate не достигнут за 50 итераций — проблема в каскаде"):
```
Если за 10 батчей один домен не достигает 0.80:
  Проблема не в количестве упражнений — проблема в структуре.
  Действие: пересмотреть качество упражнений для этого домена,
             добавить новые паттерны из ExerciseBank.
```

## ILearningMachine<StudentDomain> в иерархии проекта

```
Level 5  ILearningMachine<StudentDomain>
           TrainBatchAsync(ExerciseBatch, StudentAnswers) → StudentTrainingResult
           EvaluateAsync(PlacementBatch) → StudentCapabilityProfile
           GetOrchestratorAsync() → ILogicalOrchestrator (генерирует следующую сессию)
           ExportAsync() / ImportAsync() → сохранить/восстановить состояние ученика

Level 4  StudentOrchestrator : ILogicalOrchestrator
           RunAsync(request) → ExerciseSession (персональная сессия для ученика)

Level 3  StudentLearningFlow : ILogicalFlow<StudentSessionInput>
           Placement → Training → Verification → Progression

Level 2  PlacementUnit, SessionComposerUnit, ProgressVerifierUnit : ILogicalUnit
```

**Правило A-LM-02 соблюдается:** Train* методы только на `ILearningMachine<StudentDomain>`. `PlacementUnit`, `SessionComposerUnit`, `ProgressVerifierUnit` — чистые inference-контракты.

## Связь с TranslationDomain (откуда берутся упражнения)

`ILearningMachine<StudentDomain>` не знает о `ILearningMachine<TranslationDomain>`. Связь только через ExerciseBank:

```
TranslationDomain training pairs
    → ExerciseBankAdapter (читает экспорт, не знает о KNN/DPO)
    → ExerciseItem[] с полями: tier, domain (errorType), source, correct, wrong, explanation

StudentDomain
    → берёт ExerciseItem[] из банка
    → не знает о том, как они были созданы
```

ExerciseBank растёт автоматически: каждый новый тренировочный батч TranslationDomain → новые упражнения для StudentDomain. Тиры уточняются по мере накопления данных реальных учеников.

| StudentWikiAdapter как отдельная система | StudentProfileStore по аналогии с TranslationKnnStore |

## Последовательность достижения цели

### Шаг 1 — StudentDomain contracts

Определить контракты нового домена:
- `StudentDomain`, `ExerciseBatch`, `StudentAnswer`, `StudentCapabilityProfile`, `StudentTrainingResult`
- Зарегистрировать `ILearningMachine<StudentDomain>` в манифесте проекта

Критерий: контракты определены, нет реализации, ошибок компиляции нет.

---

### Шаг 2 — ExerciseBankAdapter + Tier annotation seed

- Читает training-pairs-train-ready.jsonl
- Первичная аннотация Tier: по длине предложения (Tier 1 ≤ 7 слов, Tier 2 8-14, Tier 3 15+) как временный placeholder до накопления реальных данных

Критерий: `GetExercises(tier: 1, domain: false_friend, count: 10)` возвращает 10 упражнений.

---

### Шаг 3 — PlacementUnit + EvaluateAsync

- Стратифицированный выбор 10 упражнений из банка
- После ответов ученика → `StudentCapabilityProfile`
- Записать в `StudentProfileStore`

Критерий: новый ученик после 10 упражнений имеет `detectedTier` и `weakDomains` в профиле.

---

### Шаг 4 — SessionComposerUnit + TrainBatchAsync

- По профилю ученика → взвешенная выборка из ExerciseBank
- После ответов → обновить `StudentProfileStore`
- Вычислить `studentProductAccuracy` на тест-батче (N+1)

Критерий: ученик с `weakDomain = false_friend` получает ≥ 60% упражнений с `errorType = false_friend`.

---

### Шаг 5 — ProgressVerifierUnit + gate + Tier promotion

- После каждого 10+10 цикла: проверить `studentProductAccuracy ≥ 0.80`
- Если domain mastered: обновить профиль
- Если все домены текущего Tier mastered: повысить `currentTier`
- Вывести обязательные метрики (train_exercises, test_exercises, studentProductAccuracy, domainAccuracy, currentTier, gate_target)

Критерий: ученик после 5 успешных батчей в Tier 1 автоматически переходит в Tier 2.

---

### Шаг 6 — Подключение к играм серии

- HTML Translation Trap вызывает `GetOrchestratorAsync` вместо статичного JSON
- Прогресс записывается через `TrainBatchAsync` после каждой игровой сессии

Критерий: прогресс ученика сохраняется между двумя сессиями в разных браузерах.

---

## Что это НЕ

- Не детерминированный алгоритм с ручными порогами
- Не отдельная база данных — StudentProfileStore использует тот же механизм хранения что TranslationDomain
- Не нарушение A-LM-02 — Train* только на ILearningMachine<StudentDomain>
- Не изменение TranslationDomain — ExerciseBankAdapter только читает экспорт
