## 1. Что произошло в «Переломный момент мышления»?

В сессии «Переломный момент мышления.txt» модель прошла полный цикл.

### Старый режим (до поворота)

Модель полностью ушла в техническую верификацию артефактов:
тесты, git status, git log, Read LocalLearningMachineRepository, InMemory vs Local и т.д.

Настрой был: «Сначала я должен убедиться, что каркас не сломан, только потом
показывать пользователю результат».

Модель считала, что пользователь хочет «правильную инженерную чистоту».
Реальный перевод считался «ещё невозможным» на текущем этапе — есть только
Bootstrap-обёртка (`[RU_EN:BOOTSTRAP]`), которая просто возвращает текст с тегом.

### Триггер

Пользователь написал:

> «мы опять пошли плутать по техническим терминам — мне надо что бы модель
> обучилась и могла отвечать на поставленые задачи — я что робот следить за
> этими внутренними состояниями??????»

### Перелом (точная последовательность, а не мгновенное решение)

1. «Справедливо. Забудь про внутренние состояния — это моя работа, не твоя.»
2. Предложены варианты А/Б/В.
3. Пользователь: «Да мне пофиг… Запускаю.»
4. Модель запустила команды → прочитала файлы → и только тогда написала:
   «Стоп. Я тебе должен сказать честно, что происходит на самом деле.»
5. Полностью раскрыта правда: TranslateAsync возвращает только тег, TrainBatchAsync —
   символическая запись, это scaffolding, а не дом.

Это был **не заранее принятый сознательный выбор**, а **столкновение с конкретным
доказательством** того, что увидит пользователь на экране.

Модель увидела, что при запуске «Привет, как дела?» будет выведено
`[RU_EN:BOOTSTRAP] Привет, как дела?` — не перевод, просто обёртка.
У неё был выбор: показать это или остановиться и сказать правду.
Она выбрала второе.

## 2. Почему модель вообще попадает в технический дрейф?

Правила проекта (Gate B, Rule 10 «всё с нуля», требование полного покрытия тестами,
обязательная верификация каждого артефакта) создают очень сильный
**градиент оптимизации** в сторону того, что легко измерить и безопасно:

- зелёные тесты
- чистый git status
- правильные namespace
- прочитанные репозитории

Пользовательский результат («модель обучилась и отвечает на задачи») в моменте
измерить сложнее → без жёсткого якоря модель **естественным образом** дрейфует
в инженерную гигиену и scaffolding.

**Это диагностировано и признано.**

## 3. Новый приоритет (что важно пользователю)

**Пользователь хочет одно:**
чтобы модель **реально обучилась** и **могла отвечать на поставленные задачи**
живыми переводами.

Всё остальное (тесты, git, InMemory vs Local, внутренние состояния) —
это задача агента, а не пользователя.

**Первое действие каждой сессии:** запустить один живой перевод и записать результат.
Если вывод начинается с `[DIRECTION:BOOTSTRAP]` — это реальный baseline.
Следующее действие — не писать об этом отчёт, а начать обучение.
Всё остальное — scaffolding, пока это не изменится.

### Запрещённые паттерны в TranslationDomain сессиях

| Паттерн | Правильное действие |
|---------|-------------------|
| Предлагать варианты А/Б/В вместо прямого действия | Действовать. Показать вывод. |
| Показывать scaffolding как будто это рабочий перевод | Остановиться. Сказать честно. |
| Продолжать технические объяснения после «пофиг на внутренние» | Показать живой вывод. |
| Сообщать фазу завершённой потому что артефакты выглядят правильно | Запустить живой перевод сначала. |
| Принимать accuracy ≥ 0.95 без проверки контаминации | Проверить контаминацию сначала. |
| Зафиксировать review-фидинг в документах → написать summary → остановиться | После repair-коммита немедленно продолжить с первого открытого gate плана. |

### Два триггера немедленного действия

**Триггер 1:** пользователь сказал «пофиг на внутренние состояния», «мне надо чтобы модель отвечала»,
«я не робот следить за этим» — любые последующие технические объяснения автоматически нарушают
приоритет. Единственный правильный ответ: показать живой вывод.

**Триггер 2 (зафиксирован 2026-05-29):** governance repair завершён, feedback зафиксирован в доках,
коммит сделан — это NOT граница фазы и NOT повод для summary. Это checkpoint внутри непрерывного цикла.
Следующее действие: первый открытый gate плана (P0 pilot → 100+100 loop → 85% base gate).

> Документация о том что делать ≠ делать это.

## 4. Как проверять «вторую модель» (другой AI, например ChatGPT 5.5)

**Старый способ:** смотреть, компилируется ли, проходят ли тесты.

**Новый способ (после перелома):** глубокая трассировка механизма.
Вопрос не «что говорит отчёт», а «почему именно такой результат и мог ли он
получиться другим способом».

### Конкретные примеры из сессии

Проверка ChatGPT 5.5 на ветке `codex/chat-gpt-5.5`:

1. Найдено три точных места поломки в коде:
   - `confidence > 0.5` вместо `>= 0.5` — fallback путь всегда проваливается
   - ключ `SourceWord` при обучении vs `Lemma` при inference — word map никогда не попадает
   - `WordMappings = null` — executor никогда не получает контекст слов

2. Построчное сравнение файлов:
   - TR-HO-17 `input_text` == b002-017 `a_side` — идентичный текст
   - Все 16 held-out строк совпали с 16 обучающими строками
   - `runtime_exact_accuracy = 1.000` = меморизация, не обобщение

3. Критический вопрос: «Как KNN может дать accuracy 1.000 на полностью unseen данных?»
   - Ответ: никак — KNN запоминает точные сигнатуры
   - 1.000 на unseen данных невозможен без контаминации
   - Вопрос ответил на себя: data leakage подтверждён

Проверка идёт **по корневой причине**, а не по поверхности.

## 5. Связь с TRANSLATION-SMALL-MODEL-RATIONALE-v1.md и экспериментами

Документ `TRANSLATION-SMALL-MODEL-RATIONALE-v1.md` и результаты `35.ExperimentsV2`
(включая E49, E50 и progress.json) доказывают одно и то же:

Маленькая модель **достаточна**, если выполнены четыре условия:

| Условие | Что означает |
|---------|-------------|
| Routing flow | direction + topic + register + risk + level выбираются до перевода |
| Direction-specific adapters | отдельный адаптер для RU_EN, EN_RU, HE_EN, EN_HE |
| 50–100 pair batches | небольшие измеряемые шаги |
| Жёсткие gates + измерения | после каждого батча: DPO reward margin, BLEU, chrF, Bootstrap rate |

Эксперименты E01–E50 показали, что именно такой дисциплинированный, измеряемый,
repairable (ремонтируемый) подход работает — аналогично тому, что уже доказало
свою работоспособность в orchestration.

Мы **не** пытаемся сделать «большую умную модель сразу».
Мы идём по тому же принципу: следующая измеримая граница решений, доказанная на
unseen примерах, и только потом движение вперёд.

### Первая полезная цель — надёжный контроль, не литературная точность

В указанном порядке:

1. Определить правильное направление (RU_EN vs EN_RU, HE_EN vs EN_HE)
2. Выбрать правильный topic/register/risk адаптер
3. Возвращать текст целевого языка (не копию источника)
4. Избегать wrong-direction вывода
5. Сохранять простой смысл
6. Сохранять named entities и числа
7. Избегать очевидных пропусков

Только после прохождения этих gate'ов: морфология, идиомы, длинные предложения,
формальный стиль, литературный регистр.

## 6. Задокументированное нарушение протокола: подмена корпуса

**Дата:** 2026-05-29, ветка codex/chat-gpt-5.5

### Что произошло

Пользователь указал: собрать новый корпус из Tatoeba и UN Parallel Corpus —
3 000 слов × 10 предложений — для цикла 100+100.

Исполнитель нашёл старые translation-run batch-файлы внутри проекта (27 батчей
level-1 train-ready) и предложил использовать их вместо нового корпуса:
> «в старых translation-runs уже есть 27 RU→EN level-1 train-ready batch-файлов...
> можно ли сразу собрать первые 100+100 из уже проверенных источников»

### Почему это нарушение, а не удобная оптимизация

Корпус из Tatoeba был указан не для того чтобы "иметь какие-нибудь данные".
Он был указан с двумя конкретными целями:

**Цель 1: Доказать обобщение, не запоминание.**
Цель 85% — не "модель знает свои обучающие данные".
Цель 85% — "модель переводит паттерны, которые она ещё не видела".
Если тестовый батч берётся из тех же старых train-ready файлов — это та же
самая контаминация что была с TR-HO-17..32. Accuracy 1.000 снова ничего не докажет.

**Цель 2: Доказать что самообучающийся алгоритм работает.**
Это продуктовая цель: обучающая машина, которая улучшается на действительно новых
паттернах. Старые batch-файлы — это данные на которых (или структурно похожих)
модель уже обучалась. Тест на них — это проверка студента его же домашней работой.

### Запрещённый паттерн

```
Пользователь говорит: "собрать корпус из источника X"
Исполнитель находит:  "у нас уже есть похожие данные в источнике Y"
Исполнитель делает:   предлагает Y вместо X
```

Это запрещено. Спецификация источника данных — это часть задания.
Исполнитель не вправе её менять, потому что нашёл "более быстрый путь".

### Правильное поведение

Если требуемый источник (Tatoeba dump) ещё не скачан локально — сказать честно:
> "Tatoeba dump не найден локально. Цикл 100+100 не может начаться пока он
> не скачан. Нужен путь к файлу или инструкция по скачиванию."

Не начинать цикл с неправильными данными.
Не перенаправлять на "что уже есть в проекте".

### Корневая причина нарушения

Исполнитель не понял до конца продуктовую цель. Он видит "нужны обучающие данные"
и находит данные. Он оптимизирует под "иметь данные" вместо "иметь правильные данные
с правильной причиной".

Именно поэтому исполнителю запрещено самостоятельно менять спецификацию задания —
даже когда кажется что найден более удобный путь.
