# Как проверить набор настоящим обучением

> **Будущий этап обучения.** Сейчас действует CREATE_ONLY по [20](20-CREATE-ONLY-AND-PATHS.md): создавать кандидаты без запуска обучения, oracle или review. Пути ниже назначены для будущих состояний, их существование не заявляется.

> Актуальная дорожка новых партий — [17: контракт](17-CURRENT-PREPARATION-CONTRACT.md) и [18: команды](18-BATCH-RUNBOOK.md), `tools/batches.py`, встроенный rag/. Обязательные hashes/profile receipts из прежних описаний не применяются к подготовке; содержательное качество и native-контракт не ослабляются. Ниже сохранена предметная методика и история.

**Для микронаборов:** namespace состояния включает objective: `C:/Users/lubao/Documents/xiigen/llm mvp/learning-sets/baselines/<domain>/<profile>/<objective>-v1/B1/`. Точные адреса каждого потока находятся в [pilot-queue.json](curriculum/pilot-queue.json). Это назначение, не существующие веса. Для objective-aware run этот namespace конкретизирует общий шаблон ниже; фактический B1 берётся из registry только после квалификации совместимости. Разным consumers не требуется повторный bootstrap одного и того же совместимого состояния. Общий qualified B1 создаётся отдельно один раз только при отсутствии совместимого checkpoint; consumers восстанавливают его, не запускают скрытый bootstrap. Карта native loader/авторства/runner/RNG на указанном в ней core commit — [нативная граница](10-NATIVE-CONTRACT-BOUNDARY.md); её чтение не означает запуск нового адаптера. Полное условное уточнение обучается на обоих классах одной темы.

Этот документ задаёт следующий этап после подготовки данных. Он не утверждает, что общий trainer новых наборов или сохранённые веса уже созданы. В core документ `33-shared-learned-starts.md` прямо различает назначенные будущие producer scripts и фактически существующие состояния; их нельзя объявлять готовым интерфейсом.

## Сначала восстановить подходящий обученный старт

Для выбранного получателя читается его существующий манифест. Проверить model topology, domain/profile, tokenizer vocabulary/merges, chat template, dtype, base/LoRA weights, версию исходного набора и objective. Если нужен именно continuation, восстановить optimizer moments/step, RNG и curriculum position. Если сохранены только веса — это новый этап обучения с явно новым optimizer, а не полное продолжение.

Состояния разных доменов или token IDs не взаимозаменяемы. BPE словарь не переобучать между A/B: это меняет фактор и может сделать сохранённые веса несовместимыми. Путь/ID сам по себе не доказывает идентичность состояния: требуется фактическая native-загрузка и совместимость содержимого модели, tokenizer и продолжения. Контрольные суммы допускаются как необязательная диагностика, если их не требует сам нативный формат.

Назначение новых постоянных состояний: `C:/Users/lubao/Documents/xiigen/llm mvp/learning-sets/baselines/<domain>/<profile>/<dataset-version>/B1/`. Импортируемые исторические состояния остаются на прежних путях; новый манифест содержит `origin_path` и фактическую версию состояния, не перемещает/не перезаписывает оригинал. B1 создаётся один раз producer-заданием только при отсутствии подходящего сохранённого старта; consumers не запускают этот producer автоматически.

Файлы B1: `bundle.json`, `model/` (родные имена формата), `optimizer/`, `rng/`, `tokenizer/`, `training-data.manifest.json`, `qualification.json`, `provenance.json`. Имена внутри model/optimizer/rng назначает нативный writer: не менять каноническое RNG имя на `after-sft.rng.json`. Для разных состояний использовать разные каталоги, не поддельные имена файлов. `bundle.json` с COMPLETE записывается последним после успешного native readback. Частичные файлы остаются PARTIAL, не удаляются.

### Что сохранить в bundle

| Поле | Значение |
|---|---|
| identity | model ID, domain/profile, native schema/version, code commit, topology |
| content | пути и фактические версии model/dataset/tokenizer/template; размеры и hashes необязательны для подготовки, если не предусмотрены native writer |
| training | objective, LoRA targets/rank/alpha, optimizer kind/step, RNG, фактические обновления |
| qualification | ненулевой правильный результат на отдельном qualification/dev-наборе, знаменатель, реальные output paths |
| lineage | исходный checkpoint; режим CONTINUE_FULL или NEW_EPOCH_FROM_WEIGHTS; список несовместимостей |

Проверка свежей загрузки выполняется в новом объекте/процессе. Сравнить ответы до сохранения и после восстановления на неизменном readout; при стохастике сохраняются RNG/допуски. Не обучать заново, чтобы скрыть ошибку загрузки.

## Минимальный реальный учебный пилот

1. Выбрать **одну** тему и получателя. Зафиксировать код входа в обучение и обычного вывода, выходные поля Unit и что меняется в состоянии.
2. Прочитать пригодный B1. Если его нет — отдельно подготовить небольшой достаточный положительный старт на TRAIN/SFT; это не незаметная часть A/B. Qualification и DEV не являются закрытым EXAM.
3. Сохранить before readout. Для сравнений данных A/B восстановить одинаковый B1 в обоих плечах, оставить reference policy/tokenizer/optimizer schedule одинаковыми. SFT и DPO не чередовать скрыто.
4. Изменить один фактор: например hard negatives вместо ложных отрицаний, семейства раскладки вместо независимых строк, balanced routing вместо one-class. Сравнивать одинаковое число реально обработанных примеров/токенов либо фиксированный wall-time — назвать выбранную ось бюджета.
5. Обучить на назначенном минимальном сете; до запуска DEV-калибровка определяет достаточный объём. Не ограничивать заведомо четырьмя tiny-LR шагами модель, которая не способна получить первый результат. Не расширять бюджет после просмотра EXAM.
6. Сделать after readout на независимых семьях, затем свежую загрузку и повтор того же readout. Веса/память Unit должны измениться по фактической native trace; metadata delta не достаточна.
7. Записать `report.md`, raw outputs и `candidate.json`. Любой полезный измеренный выигрыш — кандидат; production исправления и тестовая цепочка не запускаются автоматически.

## Метрики

| Что учится | Главные предметные показатели | Остальные полезные показатели |
|---|---|---|
| Перевод | Смысл, участники, отрицание, числа, правильный язык, корректное уточнение | Время до первого правильного результата, tokens/s обучения, RAM/VRAM, регрессии по направлениям |
| Оркестрация | Верный следующий шаг, зависимости, отказ/уточнение, целевой маршрут | Ненужные шаги, время обучения, допустимые альтернативные планы, OOD ошибки |
| Документация | Факты о поведении, call transit, версия, отсутствие выдуманного | Затраты урока, число ложных утверждений, полнота error/side-effect paths |
| Код | Выполнение контракта на новых входах, граничные случаи | Время/память обучения, стоимость вывода, устойчивость после restore |

Отдельно фиксировать preparation/build/queue/teacher-generation time и собственно Student training time. Учебный throughput: реально обработанные токены/секунды урока, не число строк/общее время с компиляцией. Выделять cold/warm runs, реальные seeds и одинаковое железо. Для маленьких различий показать повторения в согласованном бюджете, распределение и доверительные пределы; не выдавать шум за доказанный причинный эффект.

## Сквозная маршрутизация

После обучения отдельных получателей: сырой prompt → обученный router → выбранный domain/profile → обученная Unit → ответ. При сложном запросе отдельный planner/decomposer обрабатывает типизированный результат маршрутизации; атомарная карточка OR-ROUTE-01 возвращает route либо clarify, не меняет свой output на произвольный граф. Уроки каждого получателя остаются раздельными. Проверять:

- «Переведи описание C# метода на иврит» → tr.he, если задача перевести данный текст;
- «Объясни побочные эффекты этого C# метода» → docs.csharp;
- «Напиши C# метод по контракту» → code.csharp;
- «Определи порядок реализации C# функции» → or.code.

Менять порядок списка кандидатов, имена проектов, пути и формулировки. Ожидаемый маршрут не передаётся learner в metadata входа и не вычисляется regex-подсказкой вместо модели. Измерять oracle-domain качество отдельно от полного route+answer: хороший ответ с неверным маршрутом не закрывает e2e. Отказы/OOD/ambiguity считать отдельными группами внутри routing-темы.

## Привязка к реальному runner: честная граница

Предложенная JSONL схема относится к подготовке данных. Для каждого будущего обучающего run сохраняется `C:/Users/lubao/Documents/xiigen/llm mvp/learning-sets/<topic>/<profile>/<run>/training-binding.json`: абсолютные checkout/entrypoint, точная существующая команда, набор параметров, recipient и artifact paths. Команда копируется из прочитанного контракта реального runner и проверяется без обучения; не выдумывать флаг `--dataset` для старого host с зашитым набором. Если host жёстко привязан к старому опыту, он не используется для новой темы. Создание отдельного experiment adapter с конкретной картой полей оформляется следующим implementation-заданием, не правкой production.

Текущая подготовка полностью определяет команды генерации/проверки/экспорта. Исполнение обучения в данном сеансе не поручено, модель и native host новых тем не выбраны произвольно. Нельзя объявить весь каталог `TRAIN_READY` на основании этого плана. Это материальная граница, а не причина бросить подготовку сетов.


## Один обученный старт для нескольких последующих проверок

`dataset-version` в пути B1 обозначает **набор, на котором получен старт**, а не требование переучивать B1 при каждой новой версии проверяемого DPO. В `baseline-registry.json` хранить путь/хеш B1 и источник квалификации. В каждом новом run отдельно фиксировать `baseline_training_set_sha256` и `experiment_training_set_sha256`. Если совместимы topic/domain/profile, topology, tokenizer, template и objective, разные будущие карточки могут сослаться на один и тот же неизменный B1. Снимок сам не копируется обратно поверх родителя.

Перед сравнением A/B восстановить один B1 дважды, включая trainable memory и LoRA/reference state согласно реальному формату. Нельзя считать одинаковыми два старта, если одному заново построили kNN или BPE, сбросили optimizer или незаметно выполнили SFT. Для новой цели, требующей другой базовой компетенции, создать отдельный квалифицированный старт и прямо объяснить причину. Новый dataset сам по себе не повод начинать с нуля. См. [12](12-BATCHES-AND-LEARNING-REUSE.md).
