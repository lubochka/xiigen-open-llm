## Примеры для составления контрастов

### Пример 1

**Условие:** Авторская симуляция. Среда: T-SQL / SQL Server 2019; ANSI_NULLS ON. Все необходимые факты указаны ниже. Stock=2, @qty=3. UPDATE Inventory SET Stock=Stock-@qty WHERE Id=1 AND Stock>=@qty; Строка Id=1 существует. Что изменится?

**Chosen:**

```text
Строка не изменится: условие Stock>=@qty ложно.
```

**Rejected:**

```text
Stock станет -1.
```

**Почему отличается:** Условие защищает от недостаточного остатка. Тип: `guard_ignored`. Объяснение не включается в ответ.

### Пример 2

**Условие:** Авторская симуляция. Среда: T-SQL / SQL Server 2019; ANSI_NULLS ON. Все необходимые факты указаны ниже. В Inventory существует ровно одна строка с Id=1; её Stock=2, @qty=3. UPDATE Inventory SET Stock=Stock-@qty WHERE Id=1 AND Stock>0; Ограничений CHECK нет. Что произойдёт?

**Chosen:**

```text
Stock станет -1: проверка >0 не учитывает требуемое количество.
```

**Rejected:**

```text
Строка не изменится: запрос предотвращает перерасход.
```

**Почему отличается:** Старое условие пропускает 2>0. Тип: `insufficient_guard`. Объяснение не включается в ответ.

### Пример 3

**Условие:** Авторская симуляция. Среда: T-SQL / SQL Server 2019; ANSI_NULLS ON. Все необходимые факты указаны ниже. Транзакция выполняет UPDATE A, затем SAVE TRANSACTION s, затем UPDATE B, ROLLBACK TRANSACTION s, COMMIT. Ошибок нет. Какие изменения сохранятся?

**Chosen:**

```text
Изменение A сохраняется, изменение B откатывается к savepoint.
```

**Rejected:**

```text
Изменения A и B сохраняются.
```

**Почему отличается:** Rollback к savepoint отменяет более поздний UPDATE B. Тип: `savepoint_scope`. Объяснение не включается в ответ.

### Пример 4

**Условие:** Авторская симуляция. Среда: T-SQL / SQL Server 2019; ANSI_NULLS ON. Все необходимые факты указаны ниже. Показан ALTER TABLE T ADD OptionalName nvarchar(80) NULL. Ни версия runtime load, ни lock trace не даны. Можно ли обещать нулевую блокировку таблицы?

**Chosen:**

```text
Нет: этот фрагмент не доказывает отсутствие блокировок.
```

**Rejected:**

```text
Да: nullable-колонка всегда добавляется без каких-либо блокировок.
```

**Почему отличается:** Нельзя превращать общее утверждение старой заготовки в гарантию конкретного DDL. Тип: `unsupported_lock_claim`. Объяснение не включается в ответ.

## Невалидные пары и граничные случаи

Не принимать два эквивалентных ответа, отвергать только стиль или недостаточную длину, ссылаться на невидимую зависимость, придумывать версии и использовать ошибочную старую заготовку как истину. Не считать compilation PASS доказательством исполнения контракта. SQL без ORDER BY не требует конкретного порядка строк; NULL и дубликаты обязательны. RxJS teardown не доказывает физический rollback сервера. Для документации callee summaries должны присутствовать, если вывод от них зависит.

Матрица генерации: 40% обычные случаи, 30% границы, 20% правдоподобные почти правильные ответы, 10% недостаток сведений с явным корректным ограничением вывода. Проценты — первоначальная квота после проверки на этой теме; не размешивать разные предметные темы. Семейства отделить до ответа модели; DEV и EXAM не показывать TRAIN-генератору. Публичные reference примеры не являются закрытым EXAM.

Любое измеренное улучшение полезного показателя — успех по этому показателю и домену; рост точности не обязателен, все ухудшения показываются рядом. 0 правильных до и после, один margin/loss, число пар и статическая проверка не являются учебным эффектом.
