## Учебное назначение: автор данных и ученик

Генератор создаёт материал для обучения моделей/Unit XIIGEN. Его вход — карточка и источники; его выход — полные учебные строки. Ученик получает предметную задачу `prompt`; `chosen` и `rejected` задают предпочтение между двумя полными ответами на один и тот же вход. В prompt нельзя подменять предметную задачу заданием автору «создай DPO», а вместо ответов — сохранять их описание, метки правильности или отчёт.

CREATE_ONLY ограничивает действия исполнителя нынешней сессии. Назначение данных остаётся учебным. Кандидатные строки должны уже содержать правильное решение и содержательно различимый ошибочный ответ; будущая приёмка не служит оправданием заглушек.

Поля происхождения, семейств и объяснения не становятся обучаемыми входами только от наличия в JSON. Для опечаток/раскладки реальные варианты присутствуют в предметных prompts, а родство сохраняется в metadata. Фактическое использование metadata и преобразование в native input определяет consumer, описанный в [10-NATIVE-CONTRACT-BOUNDARY.md](10-NATIVE-CONTRACT-BOUNDARY.md). Не добавлять новый импорт или обучение в задание генерации.

Полный разбор источника недопонимания и допустимые выводы по реальному запуску: [22-DPO-LEARNING-TASK-AND-CE76.md](22-DPO-LEARNING-TASK-AND-CE76.md).

## Дополнение v2: один навык и точный текст

В request с `objective_id` каждая строка обязана иметь `metadata.learning_objective_id` с тем же ID. `merge`/`compose` не смешивают разные микроцели или размеченные и старые неразмеченные строки. Родительский topic/domain/profile сохраняется. Примерные строки нового слоя лежат в `curriculum/reference-examples.jsonl` и имеют только `split=reference`.

JSON с повторным ключом на любом уровне, NaN, Infinity либо переполнением вроде `1e999` отклоняется. Строки сравниваются без удаления пробелов, смены регистра и Unicode-нормализации: `"a  b"` и `"a b"` могут означать разное поведение кода. Семантическую эквивалентность проверяет reviewer. Это проверка сохранности фактического материала, не механизм принятия runtime-решения.

В TR10-CONDITIONAL две строки одного семейства имеют `metadata.clarification_class=ambiguous|resolved` и общий family/origin/split. Число строк чётное; каждый family получает ровно одну строку каждого класса. Класс служит контролем состава и не добавляется в student prompt. Для OR-ROUTE-INTENT проверяется баланс 20 routes и clarify по chosen-JSON; это контроль данных, не правило роутинга в runtime.

Известные публичные reference families, declared origin/leakage groups и точные публичные prompts запрещены в DEV/EXAM даже под другим ID пары. Проверка охватывает старые и новые reference-файлы и сохранённый карантин. Она не распознаёт все скрытые перефразирования: семантическое происхождение остаётся обязательным предметом review. Все изменения ID сохраняют derived_from.

Структурная проверка и содержательный допуск различаются. **CREATE_ONLY не запускает приёмку.** Для отдельно назначенной batch-приёмки действует [BATCH-REVIEW-PROMPT-RU](prompts/BATCH-REVIEW-PROMPT-RU.md): каждый элемент `rows[i]` содержит объект `evidence` с `rows[i].evidence.status="completed"`, непустыми `rows[i].evidence.method` и `rows[i].evidence.detail_ru`, а также предметным `rows[i].evidence.kind`. Дополнительный вложенный JSON-узел `verdict` не добавляется. Эти поля описывают фактически выполненную проверку, не намерение её выполнить.

Для translation требуется `kind="bilingual_review"`; для code.* — `kind="execution"`. Для docs.* `source_grounded` допустим только у неисполняемого факта с `depends_on_execution:false` и назначенными `source_refs`. Если предпочтение зависит от поведения/API/SQL/Angular либо карточка требует `executable_oracle`, нужен `execution`. Его запись содержит реальную command/environment, различающий результат двух ответов и существующие artifacts по BATCH-REVIEW. Отдельный `language_review`, `evidence.oracle` и старые `needs_*` поля не подменяют этот batch-контракт; отсутствие старого flag не подтверждает качество. Экспорт остаётся interchange-only, а native-граница описана в [10](10-NATIVE-CONTRACT-BOUNDARY.md).

У пары одно условие. Правильный и ошибочный ответы удовлетворяют одному формату и отличаются проверяемым смыслом. Объяснение дефекта хранится рядом, но не попадает в текст ответа. Это предотвращает обучение на метках вроде `[WRONG]` вместо содержания.

### Как автору проверить одну опечатку

Используй [разобранные хорошие и плохие примеры](prompts/TYPO-AUTHORING-EXAMPLES-RU.md), а не только название операции. Удаление: `письмо`6→`писмо`5, но `письмо`6→`пильмо`6 — замена. Правильной длины недостаточно: `Окно`4→`Кно`3 дополнительно меняет регистр. Индекс удаления начинается с0 и относится к Unicode code points исходной формы; `market→maket` имеет индекс2. Перестановка в фразе `Возьми ручку` даёт `рукчу`, не `рукча`: словарная форма не заменяет реальное склонение.

Согласованность проверяется сразу между `canonical_source`, его выбранным `canonical_token`, операцией/index, `raw_token`, `source_raw` и видимым prompt. Верни удалённую букву или сделай обратную перестановку: должно получиться исходное слово с тем же регистром и окончанием. Это правило составления содержимого, а не заявление, что `finish` уже исполняет такую проверку. Текущий `finish` подтверждает структурное завершение; совпадение текста с заявленной операцией само по себе им не доказано.

## Основная запись JSONL

Одна UTF-8 строка — один JSON-объект; переводы строк внутри текста экранируются. Никаких Markdown-ограждений вокруг JSONL.

```json
{
  "schema_version": "xiigen.dpo.v1",
  "pair_id": "DOC-CS-01.base.F0001.P01",
  "domain_id": "docs.csharp",
  "topic_id": "DOC-CS-01",
  "profile_id": "base",
  "family_id": "synthetic.guard.not-null.0001",
  "split": "reference",
  "prompt": "Симуляция. C# 10, .NET 6. bool IsPresent(string? s) => s is not null; Опиши возвращаемое значение; не приписывай проверку пустой строки.",
  "chosen": "Возвращает true для любого значения, кроме null, включая пустую строку.",
  "rejected": "Возвращает true для любого значения, кроме null и пустой строки.",
  "error_tag": "null_empty_confusion",
  "rationale": "Код сравнивает только с null; дополнительная проверка пустой строки отсутствует.",
  "source_refs": ["RAG-027", "RAG-028"],
  "provenance": {"kind": "synthetic_from_repo", "generator_model": "reference_authoring_not_a_kiro_run"},
  "metadata": {"stack": "C# 10 / .NET 6", "response_language": "ru", "source_role": "methodology", "simulation": true}
}
```

Эта запись — пример формата, не исторический фрагмент исходников. Источники поддерживают метод составления пары; поведение конкретного вымышленного метода задано в условии.

## Обязательные поля и правила

| Поля | Контракт |
|---|---|
| `schema_version`, `pair_id` | Версия формата; ID уникален глобально, не переиспользовать для изменённого содержания |
| `domain_id`, `topic_id`, `profile_id` | Должны существовать в `index.json`; один пакет содержит одну комбинацию |
| `family_id` | Общий ID смыслового/исходного семейства, включая производные перефразирования, опечатки, варианты раскладки и обратные переводы |
| `split` | `train`, `dev`, `exam`, `reference`; reference не попадает в экспорт обучения |
| `prompt` | Полное условие, видимый код/схема/контекст/версии и договор об ответе; не ID вместо содержания |
| `chosen`, `rejected` | Полные ответы в одинаковом формате. Они различаются по одной основной проверяемой ошибке; два допустимых синонима не образуют предпочтение |
| `error_tag`, `rationale` | Тип и объяснение отличия, только метаданные |
| `source_refs` | Непустой список проверенных RAG-ID либо immutable URL разрешённого репозитория; ссылка на внешний сайт внутри старого документа не разрешает его скачивание |
| `provenance` | `kind`, фактическая модель/селектор Kiro; для реального материала также commit/blob/line span, origin и parent revision |
| `metadata` | Язык ответа, стек/диалект/версия, допустимые варианты ответа, ограничения, семейства источника и lexical_family_ids при их наличии |

Статические примеры допускают `reference_authoring_not_a_kiro_run`. Новая генерация записывает фактический идентификатор модели, если среда его показывает. Если показывает только текущий селектор, записать этот селектор и `model_identity_observed=false`, не выдумывать точную версию. Один генератор может создать кандидаты обеих сторон; их достоверность определяется проверкой, а не числом разных моделей. Указания старого навыка о двух разных моделях не запрещают текущую запрошенную симуляционную генерацию.

## Семейство не равно строке

У предложения, его обратного перевода, опечатки и преобразования клавиатуры общий `family_id`. Для отдельных слов добавить `lexical_family_ids`: предполагаемый язык + каноническая лексема + проверенное значение. Совпадение букв между языками не объединяет лексемы. Общий исходный код, его пересказ и вариант с переименованием относятся к одной source-family. Типовые неизменяемые инструкции генератора сами по себе не делают весь корпус одним семейством; содержательные исходные задачи делают.

Новые семейства распределяются до генерации ответов. Один и тот же family не может быть и TRAIN, и EXAM даже в разных доменах. Межкарточные семьи опечаток/раскладки и одних исходников сверяются дополнительно: один лишь автоматически выделенный номер не доказывает независимость.

Хороший пример: «Купи молоко по дороге домой», переводы этой просьбы и её вариант с одной опечаткой сохраняют общий origin. Плохой пример: окно, хлеб и сломанный стул получают один origin только потому, что в трёх профилях им выдан F0000001. Общий номер не задаёт общего сюжета.

Другой хороший пример: CODE создаёт `string Name(string? s) { if (s is null) return "гость"; return s; }`, а DOC объясняет ровно этот исходник. У них разные topic/domain/pair IDs, но общий source-origin; два раздельных F-номера не делают исходник и объяснение независимыми. Подробные good/bad-разборы — в [шпаргалке авторинга](prompts/TYPO-AUTHORING-EXAMPLES-RU.md), фактические наблюдения — в [аудите24](24-GENERATOR-OUTPUT-AUDIT-2026-10-25.md).

Общий сюжет или исходник в семейный контракт вкладывает автор подготовки. У уже выданного request без этого материала сохраняются назначенные IDs и кандидатный статус; семантическое родство не подтверждено. Исполнитель не исправляет происхождение произвольным переименованием и не останавливает CREATE_ONLY ради нового review. Передача готовых семантических контрактов — отдельная оставшаяся работа автора подготовки, без изменения данных или runner этим документом.

Пример из аудита 26 октября: `DOC-CS-CANCEL/base/D301` объясняет тот же `ProcessBatch(items, ct, store)`, который создаёт `CODE-CS-CANCEL/base/D302`; раздельные legacy family/origin IDs не доказывают независимость. Новая D1000 уже назначает обоим `SOURCE-CS-CANCEL`, но это не исправляет старые строки автоматически. [Самопроверка общего исходника и повторных попыток](prompts/AUTHORING-SELF-CHECKS-2026-10-26.md#doccode-и-повторные-попытки-считать-родство-отдельно-от-количества-файлов). До будущего EXAM известные родственники рассматриваются совместно; существующим TRAIN не меняют split задним числом.

## Как передать материал обучению

Храним две формы: полную запись с происхождением и строгую проекцию `prompt/chosen/rejected`. `tools/batches.py export` создаёт `dpo.train.jsonl`, `dpo.dev.jsonl`, `dpo.exam.jsonl` и `provenance.jsonl`. Экспорт — обменный формат, **не обещание совместимости с нативным загрузчиком**. Перед запуском проверяется реальный потребитель и adapter mapping. Поле `error_tag`, rationale, источник, split и ID никогда не добавляются к ответу ради удобства loader.

| Вид обучения | Какой вход действительно нужен |
|---|---|
| Student DPO/LoRA | Точные одинаковые prompt/chat template, полный контраст ответов, маска loss на ответе и EOS, совместимые tokenizer/reference policy |
| Unit с обучаемой памятью/kNN | Реальный вход Unit, представление и цель; сохраняется связь с исходной парой; полный prompt не заменять тегом ошибки |
| Маршрутизатор | Пользовательское намерение и список допустимых целей; правильный route, отказ/уточнение и ложный route |
| Splitter/planner после роутера | Фактический типизированный выход предыдущего узла; не притворяться, что Unit всегда принимает сырой пользовательский prompt |

Экспериментальная привязка содержит `recipient`, `training_entrypoint`, `inference_entrypoint`, `state_artifacts`, фактические версии tokenizer/template/dataset и `source_to_unit_fields`. Hash-поля нужны только там, где их требует настоящий native reader/writer; подготовочный пакет их не выдумывает. Если связывание отсутствует, данные остаются `CANDIDATE_VALIDATED`, а не `TRAIN_READY`. Исполнитель подготовки не изменяет production-импорт ради прохождения своей проверки.

Не обрезать пары фиксированным числом символов. После токенизации проверить, что различающий смысл ответов и EOS помещаются в контекст. Если не помещаются — создать отдельную более короткую смыслово полноценную задачу с новым ID и связью `derived_from`; старую сохранить. Статический подсчёт длины Python не заменяет реальный tokenizer.


## Уточнение 25.10.2026: роли и два уровня семейств

Материал выбирает CODEX с Astra 6 ultracode; качество DPO оценивает CODEX с Astra 6 ultracode по [10](10-CODEX-AND-CHINESE-ROLES.md). Внешняя открытая китайская модель в Kiro создаёт кандидатов по назначенной карточке. `provenance.generator_model` не является полем оценщика: запрошенная и наблюдаемая модели CODEX различаются и записываются отдельно при будущем фактическом выполнении. Для текущего CREATE_ONLY отдельные selection/review receipts не требуются. Старые reference-записи не переписываются в результаты китайской генерации.

`family_id` и `origin_family_id` описывают происхождение сценария. `metadata.lexical_family_id` связывает каноническое слово с ошибками ввода; `sense_id` и контекст различают его значения. Совпадение слова в двух независимых сценариях само по себе не создаёт общий split-group. Все производные одного сценария, включая его переводы/опечатки/раскладки, остаются в одном split. Специальный экзамен на невиданные лексемы требует отдельно назначенного лексического split.

## Явное исключение строки

`metadata.training_allowed=false` у non-reference строки запрещает её допуск. Изменение split или ID не отменяет явный запрет. Reference проверяется только как публичный материал через `--allow-reference` и не экспортируется в обучение. Новая разрешённая симуляция остаётся допустимой после фактической генерации, независимого предметного review и сохранения её настоящего происхождения; старый пример не переименовывается в якобы выполненный прогон.
