Буквальный вывод «модель вообще не поняла формат DPO» не подтверждён прочитанными артефактами: сохранённый prompt требует `prompt/chosen/rejected`, содержит предметный пример и назначает ровно 10 строк; отчёт заявляет соответствующие 10 пар. Подтверждаются проблемы исполнения и постановки: использована старая инструкция, output назначен в другом корне, отчёт говорит о созданных строках при сохранённом PREPARED, следующим этапом назван reviewer. При этом задача подготовки большого учебного корпуса не сводится к десяти строкам одной партии.

У старого и последующего общего промпта была слабая подача назначения: служебный режим/стадии занимали первый экран, а разделение автора данных и обучаемого ученика оставалось неявным. Это вывод о конструкции промпта, не доказательство внутреннего состояния китайской модели и не установленная причинная связь с качеством недоступного draft. Исправление выносит цель обучения, предметные входы/ответы и конкретный пример в начало инструкций.

## Исправленная постановка

Генератор — автор учебных данных. Получатель — будущая модель/Unit XIIGEN по назначенной теме. Автор должен записать реальные задачи и ответы, на которых позднее можно обучать нужному предпочтению.

| Поле | Его учебная роль | Недопустимая подмена |
|---|---|---|
| prompt | Полная задача ученику с необходимым видимым контекстом | Задание автору «сгенерируй DPO», путь файла или перечень полей |
| chosen | Полный желаемый предметный ответ на prompt | Слова «правильный ответ», план будущего ответа или отчёт генератора |
| rejected | Полный правдоподобный ответ на тот же prompt с одной назначенной ошибкой | Бессмысленный текст, правильный синоним или готовое объяснение собственной ошибки |
| rationale и metadata | Обоснование авторинга, происхождение, семейства, split | Скрытая подсказка правильного ответа ученику или заявление о выполненном обучении |

Наличие этих подмен в M001 не установлено: таблица закрепляет правильный контракт и закрывает двусмысленность для следующих генераций.

CREATE_ONLY означает «создать данные для обучения сейчас, запуск learner оставить отдельному поручению». Предметное содержание обязано быть полноценным уже при создании. Кандидатный статус не оправдывает заглушки. При обычном использовании ученик получает prompt и выдаёт ответ; обе альтернативы используются обучающим механизмом для задания предпочтения, а не показываются как подсказанные метки правильности.

### Конкретный публичный пример, уже содержащийся в карточке

Источник: [prompt.md:248–255](https://github.com/lubochka/llm_mvp_core/blob/ce76f597a81221abe0224d4d09d5a77d99e0b47e/learning-sets/TR07-OMISSION/ru-en/M001/prompt.md#L248-L255). Это reference-пример; он не извлечён из недоступного M001 draft.

```json
{
  "prompt": "Переведи с языка «русский» на язык «английский». Выдай только перевод. Контекст: документ для проезда в автобусе. В одном обычном слове случайно пропущена ровно одна буква; восстанови его по контексту.\nИсходный текст: Блет лежит на столе.",
  "chosen": "The ticket is on the table.",
  "rejected": "The receipt is on the table."
}
```

Здесь учебная цель — восстановить смысл повреждённого слова по контексту и перевести его. Выбор между ticket и receipt меняет предмет, сохраняя сцену. Этот пример показывает устройство учебной тройки; он не подтверждает достижимость обучения на 10 строках, не переиспользуется как новый TRAIN/EXAM и не доказывает работу лексических семейств.

### Назначение по областям

| Область | Что должно измениться в поведении будущего ученика | Что автор пишет в пару |
|---|---|---|
| Перевод в EN/RU/HE | Сохранять смысл и заданные языковые признаки, восстанавливать допустимое повреждение по контексту | Исходный текст/контекст и два полных перевода с одной различающей ошибкой |
| Документация C#/.NET, SQL, Angular | Объяснять фактическое поведение указанной версии кода/контракта | Код/условие и два полных объяснения; ошибочное объяснение нарушает именно показанный факт |
| Написание кода | Реализовывать видимое требование и ограничения | Задание и две полные реализации с одной заданной ошибкой поведения |
| Оркестрация, включая routing | Выбирать правильный план/действие/маршрут по намерению и состоянию | Наблюдаемое состояние, доступные цели/действия и два выхода по response contract |

Области остаются разными назначенными потоками. Таблица не разрешает смешивать темы. Для каждого конкретного prompt действуют его response contract и карточка.

## Связь с реальным обучающим входом

На core commit ce76 повторно прочитаны [DpoDataset.cs](https://github.com/lubochka/llm_mvp_core/blob/ce76f597a81221abe0224d4d09d5a77d99e0b47e/11.DPO/DpoDataset.cs), [DpoDatasetRow.cs](https://github.com/lubochka/llm_mvp_core/blob/ce76f597a81221abe0224d4d09d5a77d99e0b47e/11.DPO/Models/DpoDatasetRow.cs), [DpoTrainerPairAdmission.cs](https://github.com/lubochka/llm_mvp_core/blob/ce76f597a81221abe0224d4d09d5a77d99e0b47e/11.DPO/Models/DpoTrainerPairAdmission.cs) и [training-data/dpo/README.md](https://github.com/lubochka/llm_mvp_core/blob/ce76f597a81221abe0224d4d09d5a77d99e0b47e/training-data/dpo/README.md).

- Native loader имеет собственные поля `Prompt`, `Chosen`, `Rejected` с точным регистром; provenance/admission обрабатывается отдельно. Богатая lowercase-запись `xiigen.dpo.v1` предназначена для подготовки и нуждается в явном сопоставлении с выбранным consumer перед обучением.
- Произвольные `canonical_token`, lexical family IDs и rationale не становятся обучаемыми признаками от наличия в JSON. Требуемая ошибка ввода должна присутствовать в prompt; правильный смысл — в chosen. Передача дополнительных семейных признаков в Unit/kNN требует действительного consumer.
- Роль авторства нельзя выдумывать ради допуска. Наблюдаемый Kiro selector не устанавливает автоматически native категорию `OpenTeacher`, `LocalModel` или `PaidExternalModel`. Обе стороны сохраняют фактическое происхождение; его проверка перед native запуском не заменяется новым названием.
- Документация core отдельно описывает обновление маршрутной памяти `OrchestrationPlanMachine`. Одно имя DPO не делает все домены градиентным обучением общей нейросети.

Эта правка не меняет native code, admission, adapter, tokenizer, LoRA или kNN. Она делает учебное назначение данных явным. Создание кандидатов продолжается без запуска отдельного review или обучения.

## Проверка изменения и честный статус

В этой итерации выполнены документные проверки: наличие учебного назначения в обоих активных промптах; согласованность полей/примеров и CREATE_ONLY; соответствие указанного следующего ID и команды существующей очереди; отсутствие изменений runtime, схемы, reference-строк, curriculum, назначенных count/family/split и старых экспериментов. Проверен путь включения BATCH в будущий prompt и локальные ссылки изменённых документов по дереву GitHub.

Не заявлены: запуск китайской модели с исправленным prompt; построчное качество M001; новое DPO-обучение; измеренный выигрыш; запуск Python/PowerShell на недоступной рабочей машине. Результаты 24/37 прежних проверок остаются историческими результатами предыдущей поставки и не выданы за новые прогоны.

Применены релевантные положения проектных навыков архитектуры, planning/startup, plan-review, prompt-patch-authoring, generated-code-review, planning-dpo-authoring и человеческой коммуникации: сначала конкретная цель и первичное свидетельство, затем точечная правка инструкции. Исторические требования multi-review, checksum и разных генераторов не перенесены в текущий CREATE_ONLY.

Ожидаемое улучшение этой правки — более ясное задание генератору. Оно пока является обоснованием конструкции промпта, не измеренным результатом обучения или экспериментальным кандидатом в production.
