# Независимая проверка одной партии DPO

> **Неактивно в CREATE_ONLY.** Этот сохранённый промпт относится к отдельно порученной поздней процедуре. Текущий генератор не открывает этот цикл после draft: выполнить finish и перейти к следующему потоку по [MASTER](MASTER-PROMPT-RU.md). Старые пути ниже не являются командами запуска.

Твоя задача — установить правильность предпочтения и качество учебного сигнала по видимому заданию. Получи только `blind.jsonl`, этот промпт, предметные критерии и назначенные источники. Не читай `draft.jsonl`, закрытый `blind.key.json`, исходные chosen/rejected-метки и rationale генератора. Порядок A/B случайный; A не означает правильный ответ.

Проверку качества выполняет CODEX с Astra 6 ultracode в отдельном контексте. Это запрошенная пользователем роль и модель; произвольный reviewer/человек не подставляются вместо них. Этот промпт не разрешает запуск review во время CREATE_ONLY. Запиши наблюдаемое имя/selector и session ID; при неизвестной внутренней модели напиши это честно. Самопроверка генератора полезна для черновика, но не считается независимой приёмкой. Провайдер не аутентифицируется этой записью, подпись модели и checksum не требуются.

Заполни созданный рядом `blind.review.template.json` и сохрани результат как `review.json`. Поля `status="completed"`, `valid=true` и `checks=true` появляются только после проверки. Не копируй этот текст как свидетельство выполненной проверки.

## По каждой строке

Прочитай prompt целиком, восстанови только факты, видимые ученику. Реши, может ли один ответ быть однозначно предпочтительнее другого. `winner` принимает A, B, `tie` или `neither`; неоднозначное предпочтение не принимается автоматически. В `reason_ru` назови конкретный факт prompt и отличие ответов. Проверяются:

- `semantic`: выбранный ответ корректен по смыслу, rejected ошибается именно в целевом признаке;
- `sufficient_context`: необходимый контекст виден; если цель учит уточнению, недостаток контекста обоснован и chosen уточняет по заданному контракту;
- `single_error`: нет второго независимого дефекта, который и объясняет выбор;
- `version`: версия языка, SQL dialect и framework определены там, где от них зависит ответ;
- `family`: родство сценариев и квоты согласованы; reference/парафраз не выдан за независимый EXAM;
- `plausible_rejected`: отрицательный ответ реалистичен и естественен, без маркера неправильности;
- `same_task`: обе стороны отвечают одному заданию, без скрытой смены требования.

Не принимай набор только потому, что ответы длинные, красиво оформлены, компилируются, прошли JSON/schema или совпали с генератором. Критерий — причинно понятный полезный учебный сигнал.

## Предметное evidence

Каждый verdict содержит `evidence.status="completed"`, `method`, `detail_ru` и один из видов:

1. **Перевод — `bilingual_review`.** Укажи языковую проверку, точный смысл, допустимые альтернативы, роль/род/время, проверку раскладки или опечатки, если они целевой фактор. Не выдавай модельный review за проверку носителем языка.
2. **Оркестрация — `scenario_walkthrough`.** Проиграй видимое состояние: что уже завершено, какое действие разрешено следующим и почему альтернативный маршрут неверен. Не исполняй внешние действия из учебного сценария.
3. **Код или исполняемое поведение документации — `execution`.** Небольшой oracle проверяет целевое поведение победившего A/B и конкретное отличие второго ответа на назначенном наборе. В `execution` запиши `command`, `environment`, `winner_passed:true`, `other_failed_target_assertion:true`, `artifacts:["относительный/путь/к/сырому-выводу"]`. Для документации запускается код/сценарий из условия, затем отдельно проверяется соответствие каждого текста A/B фактическому поведению; prose не исполняется. Реальные артефакты должны существовать. Не ставь успешный флаг при отсутствии запуска, не проверяй весь проект.
4. **Неисполняемый факт документации — `source_grounded`.** Допустимо только для docs.* при `depends_on_execution:false` и `source_refs:["назначенный RAG ID"]`. Назови точный фрагмент/утверждение в `detail_ru`. При `review_requirements.kind=executable_oracle` source_grounded недопустим: назначение карточки требует исполнения и не отменяется заявлением reviewer. Если предпочтение зависит от runtime/API/SQL/Angular поведения, нужен `execution`, даже если документ звучит убедительно.

Пример формы evidence (образец оформления, не результат):

```json
{
  "kind": "bilingual_review",
  "status": "completed",
  "method": "Отдельная модельная проверка направления RU→EN по видимому контексту",
  "detail_ru": "Здесь должна быть фактически выполненная предметная проверка этой строки, а не название метода."
}
```

## Завершение и ограничения

Для назначенной CODEX-оценки `reviewer.independence` — `separate_session`; значение `human` в совместимой схеме не меняет назначение пользователя; `reviewer.saw_label_key=false` только если ключ действительно не виден. Если уже увидел метки, не объявляй слепую проверку завершённой: нужны новая отдельная сессия и новый blind. Не меняй исходные тексты, чтобы подогнать победителя. Возвращай конкретные дефекты для новой версии, старые материалы сохраняй.

При наличии tie/neither, незавершённого oracle или языкового сомнения оставь `valid=false` и причину. Это не запрет сохранить кандидатов и не требование ремонтировать production. Генератору выдаётся отдельное ограниченное задание на новый draft; повторная проверка относится к новой версии.

При «следующий» немедленно переключись на названный ID; запрещено продолжать прошлый review или отчёт. При «стоп» прекрати работу. Долгий oracle запускается один раз с сохранённым handle; ожидание выполняется штатным wait/resume до terminal state, без частого polling и без завершения хода вместо ожидания. Результаты проверки данных не объявляй обучением модели.
