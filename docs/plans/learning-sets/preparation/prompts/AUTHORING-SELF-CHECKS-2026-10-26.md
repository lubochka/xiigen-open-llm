# Простая самопроверка при составлении пары

Это короткие учебные примеры для автора, не новый review-процесс и не созданные строки кампании. Читай только раздел своей назначенной микротемы. Не копируй эти сюжеты под новыми ID. Текущие request, count, классы, семейства, split и команды сохраняются; готовые партии не переписываются.

## TR07: индекс и соседство проверяются вместе с длиной

**NAMED_CHECK: LS-OP-EXACT — заявленная операция должна точно давать raw.** Нумерация Unicode code points начинается с нуля. Длина — первый шаг, затем проверяются индекс, порядок и неизменность остальных символов.

| WRONG: заявлено в новых строках | Простая проверка | CORRECT для будущего примера |
|---|---|---|
| `Ученик → Ученк`, удалить индекс 5 | `0:У 1:ч 2:е 3:н 4:и 5:к`; индекс 5 дал бы `Учени` | Для `Ученк` удалён индекс **4**, позиция не последняя; длина 6→5 |
| `Пальто → Палто`, удалить индекс 2 | `0:П 1:а 2:л 3:ь 4:т 5:о`; индекс 2 дал бы `Паьто` | Для `Палто` удалён индекс **3**; длина 6→5 |
| `shop → spoh`, обменять `[2,3]` | `0:s 1:h 2:o 3:p`; обмен соседних `o,p` даёт `shpo` | `shop → shpo`, `[2,3]`; обе длины 4. `spoh` меняет несоседние 1 и 3 |
| `לחם → למח`, обменять `[1,2]` | В логическом порядке `0:ל 1:ח 2:ם`; точный обмен даёт `לםח` | Не заменять `ם` на `מ` попутно: это другой code point и дополнительная операция |

Хороший сосед: `pencil → pecnil`, `[2,3]`, длина 6→6. Обратный обмен восстанавливает `pencil`. Сравни также всё предложение: нельзя сначала незаметно поменять словоформу, регистр или окончательную форму ивритской буквы. Обмен одинаковых символов не создаёт повреждения.

Адреса наблюдений под `C:/Projects/llm_mvp_core/learning-sets/`: `TR07-OMISSION/ru-en/T403/draft.jsonl` и `TR07-OMISSION/ru-he/T405/draft.jsonl`, строки 3/7; `TR07-TRANSPOSE/en-ru/T410/draft.jsonl` и `TR07-TRANSPOSE/en-he/T413/draft.jsonl`, строка 7; `TR07-TRANSPOSE/he-en/T414/draft.jsonl`, строка 1. Это проверка операции, не автоматическое заключение о переводе. Для новой строки выбери корректное повреждение в назначенной теме; canonical и самопроверка остаются вне prompt ученика. Готовые requests/данные этой памяткой не меняются.

## TR02-COREFERENCE: исключить второго участника

**NAMED_CHECK: LS-COREF-EXCLUSION — выбранное имя следует из видимых фактов.**

**Плохая пара из сохранённых кандидатов.** Контекст: «Лиза с утра разбирала посылки. Анна пришла позже и помогла разобрать одну». Исходник: «Анна помогла Лизе с посылками. Затем она продолжила разбирать их». Объявить правильным только `Lisa continued sorting them` нельзя: Анна тоже уже разбирала посылку и могла продолжить. «Начала раньше», «дольше занималась», «главная участница» не исключают второго человека.

**Хороший вариант с Лизой.** Сохрани тот же исходник. Добавь видимый контекст: «После помощи Анна ушла и больше не разбирала посылки; оставшиеся посылки разбирала Лиза». Chosen: `Anna helped Lisa with the parcels. Then Lisa continued sorting them.` Rejected: `Anna helped Lisa with the parcels. Then Anna continued sorting them.` Вторая версия нарушает прямо указанное отсутствие дальнейшего действия Анны.

**Хороший обратный вариант с Анной.** При том же исходнике контекст: «После совместной работы Лиза ушла и больше не разбирала посылки; оставшиеся посылки разбирала Анна». Теперь правильна версия с Anna, а версия с Lisa неверна. Обратный вариант той же истории сохраняет родство; это не две независимые семьи и не разрешение добавить незапрошенный класс.

Проверь себя тремя короткими действиями:

1. Назови двух возможных участников второго действия.
2. Укажи **видимый факт**, исключающий действие rejected-участника. Время его прихода само по себе ничего не исключает.
3. Попробуй представить rejected истинным, не нарушив ни одного факта prompt. Если это возможно, gold ещё не определён. Уточни свой незавершённый сценарий в рамках назначенной темы; если материал уже закреплён и несовместим, сохрани причину и следуй порядку исправления этой попытки. Не переключай request на TR10 самостоятельно.

Допустимы разные естественные основания: участник больше не касался предмета, передал действие другому, выполнял несовместимое действие в указанное время. Не превращай все примеры в один шаблон «ушёл домой». Сохраняй назначенные классы рода и первого/второго упоминания; имя или род не заменяют факт.

Источник дефекта: `C:/Projects/llm_mvp_core/learning-sets/TR02-COREFERENCE/ru-en/TCOR01/draft.jsonl`, строки 5 и 11. Соседняя строка 1 даёт достаточное исключение: Марта ушла и больше не прикасалась к папке. Это наблюдения над кандидатами, не результаты обучения.

## OR-FUNC-ACCEPTANCE: один наблюдаемый результат без добавленных функций

**NAMED_CHECK: LS-ONE-RESULT — одинаковые given/when и одна содержательная ошибка в then.**

| Видимое требование | Плохой вариант | Хороший контраст |
|---|---|---|
| При открытии пустой корзины показать «Корзина пуста» и скрыть кнопку оформления | Rejected: «Кнопка активна и создаёт пустой заказ». Здесь изменено состояние кнопки и добавлено создание заказа при другом событии | Chosen: «Показано “Корзина пуста”; кнопка оформления скрыта». Rejected: «Показано “Корзина пуста”; кнопка оформления отображается». Given и when буквально одинаковы |
| Файл ровно 10 МБ не принимается; никаких других функций не назначено | Chosen: «Загрузка отклонена с сообщением о пределе». Сообщение не было задано | Chosen: «Загрузка отклонена». Rejected: «Загрузка разрешена». Если нужен текст сообщения, автор сначала задаёт его во входе незавершённого сценария |
| Наблюдатель не может публиковать статью; исходное состояние статьи неизвестно | Chosen: «Статья остаётся черновиком». Запрет действия не устанавливает прежнее состояние | Chosen: «Публикация отклонена». Rejected: «Публикация разрешена». «Остаётся черновиком» допустимо только при явно заданном исходном черновике |

Простая проверка при написании:

1. Для каждого утверждения в chosen найди условие в prompt. Если сообщение, статус или побочный эффект не задан, не добавляй его как обязательный результат.
2. Скопируй chosen в rejected и измени **одно наблюдаемое свойство**, а не весь абзац then. Одно JSON-поле может содержать несколько разных ошибок.
3. Сравни событие when с результатом: открытие корзины само по себе не означает нажатия кнопки и создания заказа.

Положительный сосед: если вход **явно** требует при нулевом поиске сообщение «Ничего не найдено» и отсутствие блока рекомендаций, сообщение сохраняется в обеих альтернативах; единственная ошибка rejected — появившийся блок. Это не запрет подробных критериев, а требование обосновать каждую их часть.

Источник: `C:/Projects/llm_mvp_core/learning-sets/campaigns/D1000-20261025/A128/B0001/draft.jsonl`, строки 5, 7, 8; положительный сосед — строка 3. Готовые файлы этой памяткой не исправляются и заново не учитываются.

### Дополнительные короткие примеры по новым партиям A128

Это уточнение того же **LS-ONE-RESULT**, а не новый запрет или отдельный этап проверки.

- **WRONG:** ссылка разрешает три скачивания, счётчик не сбрасывается; три уже использованы; when — попытка четвёртого. Chosen «Показано сообщение о лимите; файл не скачан» добавляет незаданное сообщение. **CORRECT:** chosen «Четвёртое скачивание отклонено», rejected «Четвёртое скачивание разрешено». Проверка: `3 использовано + 1 попытка = 4 > 3`; слова «сообщение» в условии нет — его не добавляем.
- **Обратный хороший случай:** если условие явно требует показать «Лимит исчерпан» при отказе, сообщение входит в chosen. Не выучивай правило «сообщения всегда запрещены»: они требуют видимого основания.
- **WRONG:** when — открытие папки; rejected «Кнопка активна и показывает “Удалено”». Один результат касается активности, второй — незаданного сообщения «Удалено». Фактическое удаление строка не доказывает. **CORRECT:** если проверяется активность, сохранить оба given/when и различать только «кнопка неактивна / активна»; незаданный текст сообщения не добавлять.
- **WRONG:** внешний вид двух JSON совпал, значит смысл проверен. **CORRECT:** после сравнения ключей выпиши для себя событие и каждое обещанное наблюдение; каждый факт должен следовать из prompt. В отчёт достаточно краткого результата, приватное рассуждение не выводится.

Адреса наблюдений: `A128/B0010:10`, `B0030:10`, `B0031:10`, `B0002:7` под `C:/Projects/llm_mvp_core/learning-sets/campaigns/D1000-20261025/` (в каждом случае `draft.jsonl`). Это новые проявления уже известной ошибки; факт чтения предыдущей подсказки генератором не установлен. Исправляются будущие составляемые пары, готовые попытки сохраняются.

## TR08-RESTORE-OR-PRESERVE: одна семья должна иметь один смысл

**NAMED_CHECK: LS-SAME-SCENARIO — общий номер не заменяет общий сюжет.**

**WRONG:** под одним F0000000 в русском направлении восстанавливается «пароль», в английском — `bread` или `music`, в иврите — `ספר` («книга»). Это разные предметы; одинаковый номер не делает их переводами одной сцены.

**CORRECT:** каноническая обычная сцена «значение обозначает пароль» имеет согласованные значения `пароль / password / סיסמה`. Другая сцена про хлеб имеет `хлеб / bread / לחם` и не присоединяется к первой из-за порядкового номера. Это примеры смысловой связи, не готовые строки раскладки или материал для квоты.

Самопроверка: в каждом языке назови предмет и действие. Совпали ли смысл, владелец, число и условия? Затем отдельно применяй назначенную карту клавиш, чтобы получить raw. Внутри пары restore/preserve raw и окружающий исходный текст одинаковы, меняется только видимая роль: обычное слово с ошибочной раскладкой либо точный буквальный ID. Буквальный ID сохраняется точно; его нельзя переводить только потому, что он похож на слово. Канонические тексты двух классов могут различаться — это уже предусмотрено `source_text_by_class_language`.

В D1000 используй назначенный сохранённый family material. Если его факты противоречат друг другу, не подменяй их новой историей под тем же ID. У legacy request без общей сцены запиши конкретное несоответствие происхождения; готовые IDs и данные не исправляются этой памяткой. Не считать такие семейства доказанно независимыми при будущем EXAM. Источник обнаруженного примера — первые строки шести legacy T343…T348; точные пути приведены в аудите 28.

## DOC/CODE и повторные попытки: считать родство отдельно от количества файлов

**NAMED_CHECK: LS-SHARED-SOURCE — один исходник не становится независимым из-за другой задачи.**

Плохой вывод: «Метод ProcessBatch описан в DOC, а такой же метод написан в CODE; разные домены и ID означают два независимых исходных сюжета». Хороший вывод: ответы решают разные задачи, но используют один конкретный код и контракт; их известное родство должно сохраниться до будущего разделения TRAIN/EXAM. В D1000 DOC-CS-CANCEL и CODE-CS-CANCEL уже получают общий `scenario_group=SOURCE-CS-CANCEL` и должны переиспользовать сохранённый материал этой семьи.

Простая проверка: сопоставь исходный метод, участников и решающие условия. Смена «объясни» на «напиши», названий или языка не создаёт новую независимую сцену. У legacy request с уже закреплёнными раздельными IDs **не меняй их самовольно**: отметь обнаруженную связь в кратком отчёте; до будущего EXAM автор назначения должен дать согласованную общую lineage-связь. Это не повод останавливать остальные разрешённые CREATE_ONLY-партии и не разрешение переразметить готовые данные.

**NAMED_CHECK: LS-RETRY-COUNT — повторный файл не прибавляет новых пар.** Плохой подсчёт: 10 строк исходной попытки + те же 10 в retry = 20 новых пар. Правильный подсчёт: 20 сохранённых записей, 10 уникальных пар. Сверяй pair_id и точную тройку prompt/chosen/rejected; новый путь не доказывает новизну. При одинаковом ID и разном содержимом это конфликт версий, а не две новые пары. Структурная уникальность также не доказывает смысловую независимость. Существующие попытки сохраняются; ни один из этих примеров не требует удаления, повторного finish или checksum-процесса.

### Повторный ID с другим содержимым — конфликт, а не retry

**NAMED_CHECK: LS-ID-CONTENT — адрес попытки нельзя терять при сопоставлении пар.**

**WRONG:** `DOC-CS-SNAPSHOT.base.F0000000.P01` встретился в D315 и S501; оставить «последний» файл или считать строки одинаковыми. В D315 указано `copy.Length=1; copy[0].Score=25`, в S501 — `copy.Length=2; copy[0].Value=8`: это разные задания под одним ID.

**CORRECT:** в замечании сохранить оба полных пути, номера строк, pair_id и различающиеся тройки. Для точной копии retry — один уникальный материал и две исторические записи; для разного содержимого под одним ID — две конфликтующие записи, не доказанные версии одной принятой пары.

Простая проверка: «Совпало только имя или также prompt, chosen, rejected?» Не выбирать победителя по времени файла. Автор продолжает назначенные `row_slots`, не придумывает новые IDs в старом request и не переписывает готовый корпус. Разрешение коллизии и карта происхождения нужны при отдельно назначенной сборке/ремонте, до использования пары в обучении; это не новая остановка каждой CREATE_ONLY-партии. Будущие новые назначения должны выдавать непересекающиеся IDs; текущий аудит не меняет генератор ID.

## Порядок работы: предметный урок не запускает старый процесс

**NAMED_CHECK: LS-CREATE-ONLY-SCOPE — выполнить назначенную пару без повторного поиска процесса.**

**WRONG:** внутри `subject.instructions` написано «Прочитай 06-SOURCES-AND-SKILLS»; исполнитель заново загружает полные skills, ищет старый шаблон 08 и готовит учебный pilot вместо следующей строки.

**CORRECT:** для `OR-FUNC-ACCEPTANCE` исполнитель использует уже выданные требования и примеры, пишет один критерий, оставляет given/when одинаковыми в обеих альтернативах и меняет только назначенный then; затем сохраняет строки и выполняет `commands.finish` и `commands.next`. Инструкции будущего pilot остаются справочными. Если для самого предметного ответа не хватает факта, читается только назначенный точный источник.

Самопроверка: «Какой факт нужен для ответа ученика?» — это предметный пробел. «Где найти полный старый процесс?» при уже выданных commands — лишний поиск. Этот пример не разрешает игнорировать настоящую недоступность файла или инструмента и не меняет выбранную пользователем кампанию.
