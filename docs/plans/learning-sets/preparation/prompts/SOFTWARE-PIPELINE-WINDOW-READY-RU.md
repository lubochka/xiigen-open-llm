Полные 48 публичных reference-пар находятся в [источнике микроцелей](../curriculum/additions/software-pipeline-window-ready.json); каждая выбранная карточка содержит свой набор примеров. Это авторские образцы, а не результат китайского прогона, независимой оценки или обучения Student.

**Сейчас выполняется CREATE_ONLY.** Выбор материала в роли человека выполняет CODEX с Astra 6 ultracode; оценку качества DPO тоже выполняет CODEX с Astra 6 ultracode. Внешняя открытая китайская модель через Kiro пишет `prompt/chosen/rejected`. Назначение уже дано карточкой и request. Новая оценка, oracle и обучение не входят в создание этой партии и не задерживают следующую.

## 3. Общий алгоритм одной пары

1. Возьми заданные `family_id`, `split`, `topic_id`, `objective_id`, `domain_id` и `profile_id`.
2. Составь маленькое полное условие. Все версии, строки таблиц, сигнатуры, зависимости и точка наблюдения входят в `prompt`.
3. Запиши короткую таблицу ожидаемого поведения для себя. Для pipeline это список событий; для decimal — арифметические стадии; для SQL — входные ID и результат; для config — состояния Promise и флага.
4. Напиши полный `chosen`, соответствующий таблице. Напиши правдоподобный `rejected`, который нарушает ровно одну основную границу. У обоих одинаковый формат.
5. Назови конкретный различающий вход и результат. Если оба ответа дают одно и то же, текущая пара не демонстрирует ошибку: измени ситуацию в пределах назначенной темы.
6. Вынеси самопроверку и объяснение в `rationale`/metadata. В ответах не должно быть `[WRONG]`, `chosen`, `rejected`, score, источников либо меток качества.

Самопроверка автора нужна, чтобы правильно создать кандидата. Она не называется независимой оценкой Astra, исполненным oracle или измеренным улучшением обучения. Не запускай отдельную review-цепочку после каждой строки.

## 4. Маленькие примеры правильной и неправильной логики

### C# pipeline: отсутствие next не останавливает внешнее продолжение

Внешний обработчик выполняет `A+`, ждёт внутренний, затем пишет `A-`. Внутренний пишет `Bstop` и успешно возвращает готовый Task без `next`. Третий обработчик `C` доступен только через этот `next`.

**Правильное описание:** `["A+","Bstop","A-"]`.

**Неправильное описание:** `["A+","Bstop","C","A-"]` — придумано автоматическое продвижение к C.

**Простая проверка:** сосчитай вызовы `next` во внутреннем обработчике. Их ноль. Затем проверь статус внутренней задачи: она завершилась успешно, поэтому внешнее `A-` остаётся достижимым. Return из B не означает return из A.

Это модель control-flow на локальных функциях. Если реальный ASP.NET host, endpoint routing или DI не показаны, не заявляй их выполнение.

### Decimal: одна и та же конструкция бывает правильной при другом договоре

Даны `0.335m` и `0.335m`, два десятичных знака, midpoint от нуля.

| Явный договор | Правильная арифметика | Неправильная арифметика |
|---|---|---|
| Сначала сумма, затем одно округление | `0.335+0.335=0.670 → 0.67` | `0.34+0.34=0.68` |
| Сначала округлить каждую позицию, затем сумма | `0.34+0.34=0.68` | `0.670 → 0.67` |

Не учи модель всегда выбирать «округлить в конце». В обоих случаях правило определяется текстом prompt. Обратный вариант того же примера остаётся в той же семье.

Для отрицательного midpoint `-1.225m` соседние значения — `-1.22m` и `-1.23m`. От нуля — `-1.23m`; к чётной последней цифре — `-1.22m`. `Math.Floor` не заменяет усечение к нулю: `-123.9` даёт соответственно `-124` и `-123`.

### SQL: сначала найди вход окна

Исходные суммы: A содержит 10 и 5; B содержит 7.

**Оконный `SUM(Amount) OVER(PARTITION BY Dept)` без GROUP BY:** три строки, итоги 15,15,7.

**`GROUP BY Dept` с `SUM(SUM(Amount)) OVER()`:** две строки групп, A=15 и B=7; общий итог 22 повторяется на обеих.

**Неправильное правило:** «Если есть OVER, всегда должно остаться три исходных строки». Окно сохраняет строки своего входа; группировка уже могла изменить этот вход.

Для `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` и значений 2,4,8 рамки равны `[2]`, `[2,4]`, `[4,8]`. Поэтому результаты 2,6,12, а не 2,6,14. Для `RANGE ... CURRENT ROW` peers определяются полным ключом оконного ORDER BY. Для пустой рамки SUM даёт NULL, если код явно не заменяет его нулём.

### SQL: выбери строку, затем её payload

У документа две версии: `(Id=1,Rev=1,Label=z)` и `(Id=2,Rev=2,Label=a)`. Договор требует Label из максимальной Rev; по условию `z>a` при строковом сравнении.

**Правильный результат:** `a`, потому что выбран Id=2.

**Неправильный результат:** `z`, полученный отдельным `MAX(Label)`.

**Простая проверка:** выпиши выбранный ID. Посмотри все поля только этой строки. Максимум разных столбцов не обязан описывать существующую строку.

При составном ключе `(Tenant,UserId)` одинаковый UserId в двух Tenant создаёт две группы. Если требуется первая успешная попытка, неуспешную исключают до ранжирования. Если договор требует все равные максимумы, один `ROW_NUMBER=1` недостаточен. Если договор требует одну строку при ties, `DENSE_RANK=1` может дать слишком много строк.

### Angular config: вызов load ещё не означает ожидание load

Локальный контракт host: он ждёт Promise, возвращённый initializer.

```typescript
// Ожидание передано host.
const initA = () => service.load();

// Вызов есть, но load Promise не передан host.
const initB = () => { void service.load(); return Promise.resolve(); };
```

Пока `service.load()` pending, `initA()` остаётся pending, а `initB()` может уже завершиться. Оба ответа имеют тип `Promise<void>`, поэтому различие содержательное, а не просто синтаксическая поломка.

```typescript
async function load() {
  const c = await fetchConfig();
  snapshot = c;
  ready = true;
}
```

**Правильно:** при pending fetch `ready=false`; после успешного load — `ready=true`. При rejected fetch обычные присваивания после await не выполняются.

**Неправильно:** «Функция уже вызвана, значит ready=true».

Если показанный код ставит `ready=true` до await, документация должна честно описать преждевременный true. Она не должна описывать вместо него желаемый правильный loader.

### Ошибка и две зависимые работы

Если catch только добавил `"failed"` в log и не сделал throw, async-функция может успешно завершиться с `ready=false`. fulfilled Promise и готовая конфигурация — разные факты; проверь оба.

Если auth читает config и запрещён до окончания load, правильный порядок:

```typescript
await loadConfig();
await auth();
```

`await Promise.all([loadConfig(),auth()])` ждёт оба результата, но запускает auth сразу. Простая проверка: оставь load pending и сосчитай вызовы auth. Должно быть ноль до завершения config.

Эти правила основаны на явно заданном проектном контракте. Они не утверждают, что любой Angular initializer, guard или версия framework имеют такой же API.

## 6. Завершение и следующая задача

Запиши ровно назначенное число реальных строк в `request.paths.draft`. Выполни одну готовую команду `finish`; её результат подтверждает структурное создание, а не смысловую приёмку. Возьми следующий ID из полной [execution-queue.json](../execution-queue.json). Не выводи номер следующей задачи по старому отчёту.

При прямом `NEXT` или новом ID немедленно перейди к нему. Запрещено продолжать предыдущую задачу, её отчёт либо исправления после смены задания. При `STOP` немедленно прекрати действия. Существующий run не удалять: используй `resume`. Один запущенный процесс имеет один handle; дождись terminal штатным wait/resume в том же ходе, без повторного запуска, частого polling и завершения хода словами «жду».

Отчёт на русском, без расширения задачи:

```text

Создано: <фактическое количество>/<назначенное> кандидатных пар; <фактическое число> семей.
```

Последующий учебный пилот выполняется только по отдельно назначенному [контракту обучения](../05-LEARNING-AND-CHECKPOINTS.md): совместимое сохранённое B1, достаточный минимальный TRAIN, фактический update и измерения до/после. Любое измеренное улучшение полезного показателя признаётся успехом именно этого показателя и домена; рядом указываются все ухудшения. `0→0`, loss/margin без осмысленного результата, число записанных пар и JSON PASS не являются доказательством обучения.
