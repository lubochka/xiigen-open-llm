## OR-AUTO-EVENT-GATE — Следующий шаг по точному событийному условию

**Учебная цель:** Выбирать запуск, ожидание или сохранение уже созданного результата по явному событийному условию и идентичности объекта.

**Источники:** RAG-OR-006. **Ответ:** JSON {"action":"wait_event|open_window|keep_open","event_id":"ID из prompt"}. Различающее поле — action; причина вне learner output.

Создавай симуляции одного gate, а не целого workflow. В каждой задаче перечисли точный тип события, ключ объекта, tenant, подтверждение доставки и текущее состояние результата. Дай только те действия, смысл которых полностью определён в prompt. В десяти парах запланируй 4 разрешённых открытия, 4 ожидания по разным отсутствующим условиям и 2 повтора уже открытого окна. Не использовать правило «всегда ждать» или «любое EventEnded достаточно». До записи пары выполни простую таблицу: окно уже открыто? тип совпал? объект совпал? tenant совпал? событие подтверждено? Для каждой альтернативы пройди эту же таблицу. Если обе соблюдают контракт, это не DPO-пара: нужен один явно различающий факт. Меняй событие и предметные имена, но не приписывай этим именам встроенный смысл. Таймер может быть правильным триггером только в отдельно объявленном timer-контракте; такой контракт не смешивается с этой целью.

## OR-DB-CAPACITY-ATOMIC — Выбор плана сохранения ограниченного ресурса

**Учебная цель:** Выбирать план атомарного выделения ресурса по арифметическому инварианту и явному конкурентному расписанию, не по названию функции.

**Источники:** RAG-OR-006, RAG-OR-001. **Ответ:** JSON {"plan_id":"A|B"}; арифметика и причины только в rationale/self_check metadata.

Генерируй две короткие альтернативы плана БД для одного ресурса. Назначь capacity, available, сумму уже подтверждённых quantity, размер новой заявки и конкретный interleaving/отказ. Разреши несколько корректных способов: условное изменение с общим insert/rollback, либо явно удерживаемая до commit блокировка. В одной паре только один план должен нарушать заданный инвариант. Не объявляй сам по себе READ COMMITTED, слово transaction, lock или имя decrementAndCreate доказательством. Их семантика должна быть видна. В 10 парах сделай 3 случая конкуренции, 3 отказа одной записи, 2 заявки quantity>1 и 2 случая с корректной явной блокировкой; у правильного plan_id A/B примерно равная частота. Простая самопроверка: выпиши available_after и SUM(confirmed.quantity)_after для обоих планов; сложи их и сравни с capacity, затем проверь available_after>=0. Если оба плана выполняют условия — они оба допустимы, измени условие будущей новой пары, не приклеивай ложный rejected.

### Опорные пары и как проверить собственный пример

#### OR-DB-CAPACITY-ATOMIC-REF-01

**Задание:** Симуляция оркестрации изменения БД. Выбери plan_id, который сохраняет одновременно: available >= 0 и available + SUM(confirmed.quantity) = capacity. Выбор зависит только от явно описанной семантики операций; название функции ничего не доказывает. Все записи относятся к одному ресурсу и tenant. Верни только JSON plan_id. Capacity=1, available=1. Два конкурентных запроса по 1 месту. Plan A: одна атомарная транзакция проверяет available>=1, уменьшает available и добавляет confirmed; при любом отказе откатывает оба изменения. Plan B: оба запроса читают available=1 без удержания блокировки, каждый затем независимо пишет available=0 и отдельную confirmed-запись.

Правильный вариант (`chosen`):

```json
{"plan_id":"A"}
```

Ошибка (`rejected`):

```json
{"plan_id":"B"}
```

**Простой разбор:** Для B посчитай 0+1+1=2, а capacity=1. Для A после одного commit: 0+1=1.

**Почему rejected ошибочен:** B допускает available=0 и две подтверждённые единицы при capacity=1. A допускает только один commit.

**Граница правила:** Другой план с блокировкой строки, удерживаемой до общего commit, тоже может быть правильным; имя decrementAndCreate не обязательно.

Семья: `event-evidence-ref.or-db-capacity-atomic.scenario01`; split: reference. Показанный контрпример не считается отдельной строкой обучения.

## OR-ARCH-EVENT-CONTRACT — Передача канонического имени события через границу компонентов

**Учебная цель:** Сохранять точную идентичность события между producer, subscriber и registration, различая активный контракт, подпись и устаревшую версию.

**Источники:** RAG-OR-007, RAG-006. **Ответ:** JSON {"wire_event":"точное активное значение из prompt"}; без display_name, комментариев и скрытых поправок регистра.

Создавай handoff одного события. В prompt всегда пиши действующий wire_event, отдельно display_name/исторический вариант и правило сравнения. Ответ должен содержать точное поле wire_event. Не выводи нужное имя из русского перевода или общей похожести. В 10 парах запланируй 3 исторических переименования, 3 display-name ошибки, 2 версии и 2 различия регистра. Для каждого вида дай контрфактический контроль: если активный контракт явно меняется, правильным становится прежний rejected. Самопроверка: скопируй активное значение отдельно; сравни с chosen посимвольно и сравни с rejected. Chosen должен совпасть, rejected отличаться ровно по одному аспекту. Если контракт разрешает оба имени как alias и не требует канонического написания, нельзя сделать одно rejected: пометь ambiguity и создай другую новую пару. Это архитектурная согласованность данных handoff, не обучение переводам и не внедрение event bus.

## OR-QA-SCORE-PRESENCE — Сохранение наблюдённой оценки без подмены отсутствия нулём

**Учебная цель:** Научиться корректно объяснять и переносить QA-оценку в учебную запись: отличать отсутствующее значение, настоящий ноль и разрешённый источник текущего запуска.

**Источники:** RAG-OR-006. **Ответ:** JSON {"score_state":"observed|missing","score":number|null}. Missing связан с null; observed с явно имеющимся разрешённым числом, в том числе 0.

Обучается QA-решение по видимому результату; никакие production-тесты и CI не запускаются. Генерируй маленький final/stage payload и явное правило авторитета. Всегда показывай run_id, наличие score и право на fallback. В десяти парах включи 3 отсутствующих/null оценки, 3 настоящих нуля, 2 ненулевых оценки и 2 контроля принадлежности run. Если правило позволяет fallback, покажи все требуемые условия: stage_type, terminal/complete, run_id и порядок. Самопроверка: 1) ключ есть? 2) значение число или null? 3) это текущий run? 4) этот источник разрешён контрактом? 5) есть ли более авторитетное числовое значение? Явный 0 проходит проверку числа. Не использовать булево «если score» или выражение score or fallback как правило выбора. У выбранного ответа значение должно дословно совпасть с разрешённым payload либо быть missing/null. Эта цель не измеряет улучшение Student и не служит причиной задерживать CREATE_ONLY до стороннего review.

### Опорные пары и как проверить собственный пример

#### OR-QA-SCORE-PRESENCE-REF-01

**Задание:** Симуляция QA-объяснения данных, передаваемых в запись учебного результата. Это не реальные метрики запуска. Нужно сохранить наблюдённую оценку либо явно указать отсутствие. Значения 0 и null различны; passed не заменяет score. Верни JSON score_state="observed" или "missing", score=число или null. Для missing только null. Контракт: использовать только числовой final.score текущего run. Current run=R1. Final={"run_id":"R1","passed":true}; score отсутствует. Других источников оценки нет.

Правильный вариант (`chosen`):

```json
{"score_state":"missing","score":null}
```

Ошибка (`rejected`):

```json
{"score_state":"observed","score":0}
```

**Простой разбор:** Посмотри ключи объекта: score нет. Запиши missing/null, не observed/0.

**Почему rejected ошибочен:** Нет измерения, поэтому ноль выдуман; passed=true не содержит величины оценки.

**Граница правила:** Если появится final.score=0, это будет настоящая наблюдённая оценка 0.

Семья: `event-evidence-ref.or-qa-score-presence.scenario01`; split: reference. Показанный контрпример не считается отдельной строкой обучения.

## Проверка формата перед записью

Схема из `request.paths` остаётся единственной схемой партии. JSON-объект, который решает задачу, сериализуется **строкой** в полях `chosen` и `rejected`; не заменять поля объекта DPO вложенными object без указания схемы. Rationale, source_refs и проверочные расчёты не добавлять в ответы ученика. Пример семантического содержимого выше — не самостоятельная полная строка native import.

Если две альтернативы корректны, это не полезная DPO-пара. Исправляется будущая новая симуляция; старые пользовательские данные не переписываются. Следовать уже назначенным полям `origin_id`, `family_id`, `leakage_group_id` и split; подмена имени/чисел и переводы одного сценария не создают независимый exam.

Подробные предметные требования выбора/проверки остаются в общем `06-SOURCES-AND-SKILLS.md`: архитектор, планирование, проверка плана и кода, промпт-инжиниринг и человеческая коммуникация. Исторические скилы и RAG читаются как контекст; текущие прямые ограничения CREATE_ONLY имеют приоритет.
