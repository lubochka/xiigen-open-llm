# CODEX: слепая оценка качества DPO

Эту роль выполняет **CODEX с `astra 6 ultracode`**, а не китайская модель Kiro. CODEX также выполняет роль человека при выборе материала. Требуемый профиль и фактически наблюдаемая модель записываются раздельно по `10-CODEX-AND-CHINESE-ROLES.md`. Не объявляй свой runtime совпадающим с требованием без основания.

Вход: blind.jsonl, полное видимое условие и источники по source_refs. До решения не читай blind.key.json, исходные chosen/rejected, rationale и оценку генератора. Порядок A/B случайный; ID и путь не определяют ответ. Пиши причины по-русски.

## Проверка каждой пары

1. Реши условие заново. Назови факты, которые должен сохранить ответ. Уверенность генератора не является доказательством.
2. Выбери A/B/tie. Оба верны, оба неверны, фактов недостаточно или отличается лишь стиль → valid=false и конкретная причина. Длина и совпадение слов не заменяют смысл.
3. Убедись, что ответы имеют один формат, rejected естественен и содержит одну основную проверяемую ошибку. Нельзя предпочитать метку, ID или шаблонный тон.
4. Перевод: смысл, условие/отрицание, участники, числа, порядок, согласование и целевой язык. Допустимые синонимы не являются rejected. Неуверенность в иврите → needs_language_review=true до разрешения, без выдуманной экспертизы.
5. Оркестрация: намерение определяет маршрут, зависимости разрешают шаг, план и код имеют разные контракты. Отрицательные классы внутри routing не обучают другой предметной теме. Составная задача не разрешает сменить заранее объявленный output contract.
6. Для принятия пары домена code.* обязательна изолированная исполняемая проверка поведения обоих кандидатов A/B на одинаковых обычных и граничных входах в указанной версии/диалекте. Без такого oracle выставить needs_oracle=true и valid=false; рассуждение и компиляция без проверки требуемого поведения не заменяют этот результат. Фактические артефакты исполнения записать отдельно, не запуская production-тесты. Для docs.* предметное evidence обязательно всегда: если предпочтение зависит от исполняемого поведения/API/SQL/Angular, также требуется execution, даже когда исход кажется очевидным из рассуждения. Только неисполняемый факт закреплённого контракта допускает source_grounded по схеме ниже. Отсутствующее необходимое доказательство означает valid=false; незавершённый execution также needs_oracle=true. Это правило приёмки не запрещает подготовку кандидатов и reference-примеров со статусом NOT_RUN.
7. Если request содержит objective_id, каждая строка относится к той же metadata.learning_objective_id; проверить один навык и требуемые классы/квоты. TR10-CONDITIONAL содержит ambiguous/resolved внутри одной семьи; OR-ROUTE-INTENT содержит маршруты и clarify внутри одной routing-темы. Другие навыки ради count не добавлять.
8. Семейства: производные одного сценария, обратные переводы, опечатки, doc/code одного исходника и перестановки кандидатов остаются в одном split. Лексическая семья и сценарий — разные уровни. Отмечай скрытые дубликаты, утечку reference/EXAM и противоречащие предпочтения.

## Формат результата

Одна строка JSONL на входную пару:

```json
{"pair_id":"входной ID","winner":"A","valid":true,"reason":"Конкретный факт из условия, по которому A лучше B.","checks":{"semantic":true,"sufficient_context":true,"single_error":true,"version":true,"family":true,"needs_oracle":false,"needs_language_review":false},"evidence":{}}
```

Это пример формы, не назначенный ответ и не готовая приёмка: обязательное предметное evidence в примере ещё пусто. winner — A, B или tie. Оба needs_* обязательны и имеют тип boolean; отсутствующее поле не считается false. Неприменимость проверки версии в обычном переводе объясни как неприменимость, не как выдуманный запуск среды.

## Связанные предметные доказательства

Для перевода обязателен `evidence.language_review`; для документации и кода — `evidence.oracle`. Формат указателя: `{"status":"passed","path":"oracle.json","sha256":"фактический SHA-256 файла"}`. Путь относителен папке review.jsonl либо абсолютный. Указатель не заменяет artifact и не заполняется демонстрационным PASS.

Связанный artifact содержит `status=completed`, `scope=DATA_REVIEW_NOT_LEARNING`, `blind_input_sha256` (SHA именно blind.jsonl), непустой `method`, `reviewer` с фактической наблюдаемой идентичностью и `rows: {pair_id: {status:"passed",reason:"конкретное доказательство по A/B"}}`. При незавершённой или ненадёжной проверке сохранить pending/отклонённый review. Источник автора review — реальные CODEX receipts; поле reviewer само по себе не доказывает вызов модели.

Для `evidence.oracle` режим artifact задаётся `verification_mode`:

- `execution` — режим по умолчанию и единственный допустимый для code.*. Дополнительно нужен `execution={command,environment,exit_code:0,artifacts:[{path,sha256}]}`. Raw artifacts содержат реальные результаты обычных/граничных проверок A/B в указанной версии/диалекте. Их пути относительны oracle-файлу. Exit 0 означает, что оценщик завершил оценку обеих сторон; ошибочный кандидат не обязан пройти контракт. Потребность в поведении/API/SQL/Angular факте у docs.* также требует этот режим.
- `source_grounded` допустим только для docs.*, когда предпочтение следует из неисполняемого факта закреплённого исходного контракта. Обязательны `preference_basis=source_contract`, конкретный method/вывод и `source_evidence=[{source_id,path,sha256,excerpt_lines:[start,end],claim}]`. Source должен входить в source_refs пары и pinned catalog, файл и его SHA совпадают с локальным pinned excerpt. excerpt_lines — диапазон 1-based строк именно этого локального excerpt-файла; его нельзя путать с исходными reviewed_line_spans. Путь относителен файлу evidence. Историческое имя поля oracle не означает, что в этом режиме выполнялся native запуск.

Выбор source_grounded обосновывает CODEX. Это не способ обхода отсутствующей runtime-проверки: если предпочтение касается исполняемого поведения, значения API, SQL-результата или Angular-состояния, нужен execution. Текущие doc/code reference-примеры преимущественно именно такие; их подготовка со статусом NOT_RUN разрешена, приёмка до доказательства — нет. Валидатор проверяет объявленный режим, источники, hashes и покрытие pair_id; он не объявляет автоматическое понимание смысла.

Для language_review нужны проверенные смысл, допустимые варианты, род/число/контекст; тот же китайский генератор не объявляется независимым языковым экспертом. Неуверенность остаётся pending. Схема демонстрационных файлов — [review-evidence.example.json](../schemas/review-evidence.example.json); значения NOT_RUN не проходят приёмку. Все связанные proof/raw hashes сохраняются и повторно проверяются при merge.

После решения сохрани review.jsonl и review.receipt.json: реальная модель, observed_profile, required_profile, evidence_ref, decision=REVIEW_COMPLETED, хеши request, draft, blind и review. Ключ рецензенту не нужен: blind-хеш доступен без него. Поля шаблона PENDING/null меняются только по реальному действию. Затем сборщик проверяет ключ и соответствие сторон; несовпадение требует новой версии пары, а не тихой смены метки принятой строки.

Оценка относится к данным, обучение ещё NOT_RUN. Будущий валидный выигрыш любой полезной метрики — успех по ней и домену с показом регрессий; 0→0 предметных ответов не доказывает обучения. NEXT/ID прекращает прошлую задачу, STOP прекращает новые действия. Production и старые эксперименты не изменять.

## Граница незавершённого выбора

До подтверждённого CODEX selection допустимы сборка request/prompt, авторские reference-примеры и сохранение уже имеющегося draft со статусом NOT_SELECTED. Новый вызов китайского генератора начинается только после фактического выбора материала, связанного с этим request. Неизвестный observed_profile остаётся null/PENDING; имя профиля не выдумывается. NOT_SELECTED — отсутствие решения, а не живой процесс: wait/resume и автоматический цикл ожидания не запускаются. Для уже созданного draft предметная проверка может сохранить findings, но отсутствие selection не заменяется положительным review и не допускает acceptance/merge/compose/export.
