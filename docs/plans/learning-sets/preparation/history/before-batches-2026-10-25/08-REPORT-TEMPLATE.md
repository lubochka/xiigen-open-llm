# Отчёт о пакете / учебном опыте

Писать на русском. Сначала 3–5 предложений: что сделано, что измерено, чему стало лучше, что ухудшилось, какая следующая разрешённая тема. Полный отчёт — `report.md` в фактическом `request.output_directory`; topic-only шаблон: `C:/x/lsets/<topic>/<profile>/<run>/report.md`. Для objective-aware run использовать назначенный путь из request/pilot-queue, не угадывать его по старому шаблону.

## Паспорт

- Тема / domain / profile / objective_id / stream_id / run; ID карточки и её SHA-256.
- Текущий этап: подготовка / semantic review / обучение / измерение.
- Генератор: фактическая китайская модель Kiro. Выбор материала: CODEX, требуемый/наблюдаемый `astra 6 ultracode`, selection receipt. Оценка: CODEX, требуемый/наблюдаемый профиль, review receipt. Отдельно обучаемый Student/Unit и его версия. Неизвестные данные не придумывать.
- Source refs и хеши входов; output paths; исходный checkpoint и режим восстановления.
- Статусы раздельно: execution, data_validation, learning, hypothesis.

## Данные

Сколько запрошено, получено, принято, отправлено в переработку; сколько уникальных семейств; баланс ошибочных/положительных/неподдерживаемых ситуаций. Как сформированы TRAIN/DEV/EXAM. Какие oracle/языковые проверки выполнены, их blind SHA, evidence paths/hashes и pending причины. Число новых строк, уникальных source families и производных от reference указать отдельно. Статическая проверка не называется улучшением обучения.

Привести минимум один фактический prompt/output до/после и один неудачный/регрессировавший случай, если он есть. Raw outputs, terminal exit и model-state trace обязательны для учебного вывода. Loss/margin — диагностика, не заменяет содержательные результаты.

## Вывод

`SUCCESS_ON_METRIC` допустим при любом измеренном полезном выигрыше на валидном уроке, с указанием конкретного домена/метрики. `LEARNING_NOT_DEMONSTRATED` при 0→0. `NOT_RUN` при подготовке. Неуспешная запись файла и неудачное обучение — разные статусы. Не объявлять прогон умершим только из-за early yield.

## Кандидат исправления

Только после реального улучшения: эксперимент/run/hash, фактор, выигрыши, регрессии, допустимые домены, математическое объяснение если применимо, конкретный consumer-код для возможной интеграции, проверка повторения и границы вывода. Сохранить `candidate.json`; решение о внедрении — за Любой. Этот этап не запускает цепочку production changes/tests.

## Качество и скорость производства данных

Отдельно от обучения: запрошенные/сгенерированные/принятые пары, уникальные сценарные семьи, доля отбраковки по причинам, число новых смысловых задач против парафразов, токены и время генератора, время CODEX-review, принятые пары в минуту. Цены указывать только при реально известном тарифе, иначе оставить незаполненными. Рост этой производительности не равен ускорению обучения Student.

## Следующий шаг

Указать точный execution stream и его next из execution-queue.json; этот порядок объединяет objective/profile и оставшиеся topic/profile. index.json — каталог тем, curriculum/index.json — каталог микроцелей и их локальных связей, а не две конкурирующие очереди запуска. Прямой ID пользователя имеет приоритет. После команды NEXT не дописывать прошлую задачу. После STOP — никаких новых действий. Незавершённый живой run сохраняет свой handle и фактический статус.

## Версия проверяемого пакета

Сохранить SHA-256 tools/sets.py, request, blind, review, receipts и использованных evidence; для execution — команду, среду, terminal exit и raw artifacts; для source_grounded — pinned source evidence и обоснование режима. Исторические результаты инструмента не переносить на новый hash. provider_identity_authenticated остаётся false при проверке только declared evidence; фактическое имя модели не выводится из названия файла или обязательного профиля.
