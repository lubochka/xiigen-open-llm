## Подробный промпт исполнителю

Генерируй две короткие альтернативы плана БД для одного ресурса. Назначь capacity, available, сумму уже подтверждённых quantity, размер новой заявки и конкретный interleaving/отказ. Разреши несколько корректных способов: условное изменение с общим insert/rollback, либо явно удерживаемая до commit блокировка. В одной паре только один план должен нарушать заданный инвариант. Не объявляй сам по себе READ COMMITTED, слово transaction, lock или имя decrementAndCreate доказательством. Их семантика должна быть видна. В 10 парах сделай 3 случая конкуренции, 3 отказа одной записи, 2 заявки quantity>1 и 2 случая с корректной явной блокировкой; у правильного plan_id A/B примерно равная частота. Простая самопроверка: выпиши available_after и SUM(confirmed.quantity)_after для обоих планов; сложи их и сравни с capacity, затем проверь available_after>=0. Если оба плана выполняют условия — они оба допустимы, измени условие будущей новой пары, не приклеивай ложный rejected.

### 1. OR-DB-CAPACITY-ATOMIC-REF-01 — base

**Задача ученику:**

~~~~text
Симуляция оркестрации изменения БД. Выбери plan_id, который сохраняет одновременно: available >= 0 и available + SUM(confirmed.quantity) = capacity. Выбор зависит только от явно описанной семантики операций; название функции ничего не доказывает. Все записи относятся к одному ресурсу и tenant. Верни только JSON plan_id. Capacity=1, available=1. Два конкурентных запроса по 1 месту. Plan A: одна атомарная транзакция проверяет available>=1, уменьшает available и добавляет confirmed; при любом отказе откатывает оба изменения. Plan B: оба запроса читают available=1 без удержания блокировки, каждый затем независимо пишет available=0 и отдельную confirmed-запись.
~~~~

**Chosen — полный правильный ответ:**

~~~~text
{"plan_id":"A"}
~~~~

**Rejected — правдоподобная содержательная ошибка:**

~~~~text
{"plan_id":"B"}
~~~~

**Почему есть предпочтение:** B допускает available=0 и две подтверждённые единицы при capacity=1. A допускает только один commit.

Различающий дефект: `split_check_write_oversells`. Семья: `event-evidence-ref.or-db-capacity-atomic.scenario01`.
