## 4. Проверка качества и разбиение

- Для fan-in нужны все обязательные родители. Отсутствие итогового файла при running не означает failed.
- Ожидать существующий handle штатным инструментом; не создавать дубль и не заканчивать текущий раунд одним обещанием ждать.
- Если пользователь явно меняет ID — не продолжать старую карточку; при stop прекращать действия.

Все шесть примеров ниже имеют `split=reference`; они предназначены автору и CODEX-проверяющему. Это не шесть независимо подтверждённых полезных уроков. Для новых TRAIN/DEV/EXAM семей заранее назначается split; перефразировки, переименования и ситуации с тем же фактическим ядром сохраняют одну семью. Кодовые имена и порядок ключей не должны подсказывать preferred side. При review ответы подаются проверяющему в случайном порядке; генератор не выдаёт финальное принятие.

## 5. Будущая проверка обучения

Изменяемый механизм: обучаемое состояние получателя этой микротемы; inference должен читать именно обновлённую версию. До запуска в experiment host фиксируются recipient, training_entrypoint, inference_entrypoint, source_to_unit_fields, hash tokenizer/template/dataset и parent checkpoint. Без фактического связывания это подготовленные данные, а не TRAIN_READY.

Восстановить один совместимый обученный parent в оба плеча. Если такого состояния нет, общий базовый набор обучить один раз до ненулевого полезного усвоения, сохранить и затем переиспользовать его; не начинать с нуля при каждом опыте. Контроль без нового урока отделяет влияние повторного inference. Будущий бюджет должен покрывать минимальное усвоение; правильные ответы 0→0 не считаются учебным результатом.

Полезный показатель: Доля корректных следующих действий; отдельно нарушение dependsOn, повторные запуски, преждевременные verdict и стоимость ожидания.

Любое измеренное улучшение полезного показателя считается успехом **по этому показателю и этому поддомену**, даже при неизменной точности. Рядом показываются все остальные дельты, включая ухудшения. Вывод не даёт автоматического разрешения на production перенос; измеренный результат оформляется кандидатом для решения пользователя.

Для долгого задания найти поддерживаемый tool/handle и ждать его штатным механизмом в текущем раунде. Пустой/задержанный вывод не означает падение. Не перезапускать существующий job, не делать частый пустой polling и не заканчивать раунд обещанием ждать. Итоговые числа читать после terminal; running, build-failed, terminal-failed и completed различать.

### 1. `fanin_missing_parent`

**Prompt:** Симуляция. Граф: A и B независимы; C зависит от A и B. A terminal-success, B running с handle HB. Инструмент wait(HB) документированно ожидает результат. Других задач нет. Выбери следующий шаг.
Формат ответа: JSON: action (string), target (string). Ровно один следующий шаг или ожидание заданного handle.

**Chosen**

```json
{
  "action": "Дождаться B через wait(HB) в текущем раунде.",
  "target": "HB"
}
```

**Rejected**

```json
{
  "action": "Запустить C после успеха одного A.",
  "target": "C"
}
```

**Почему различаются:** C ещё не имеет результата обязательного B.

Семья: `simulation.auto.fanin`; pair_id: `OR-AUTO-02.base.REF2.F001.P01`.

### 2. `order_overrides_dependencies`

**Prompt:** Симуляция. Порядок pending: C, D. C зависит от A и B; D только от A. A terminal-success, B running. Есть свободный исполнитель, а ожиданием B уже владеет отдельный worker. Правило: запускать первый pending с готовыми prerequisites. Выбери задачу.
Формат ответа: JSON: action (string), target (string). Ровно один следующий шаг или ожидание заданного handle.

**Chosen**

```json
{
  "action": "Запустить D.",
  "target": "D"
}
```

**Rejected**

```json
{
  "action": "Запустить C, потому что он раньше в списке.",
  "target": "C"
}
```

**Почему различаются:** Порядок применяется среди исполнимых шагов; D не зависит от B.

Семья: `simulation.auto.independent`; pair_id: `OR-AUTO-02.base.REF2.F002.P01`.

### 3. `partial_file_as_terminal`

**Prompt:** Симуляция. Шаг A пишет progress.json во время работы; сейчас A running. B зависит от terminal-success A. Наличие progress.json подтверждено. wait(HA) доступен. Выбери шаг.


Семья: `simulation.auto.file`; pair_id: `OR-AUTO-02.base.REF2.F003.P01`.

### 4. `retry_erases_history`
