### Перевод: смысл должен определяться контекстом

Пример: «Дина поговорила с Верой. Затем она закрыла дверь». В условии явно сказано, кто ушёл и кто остался внутри. Обе участницы одного пола. Диагностический договор ответа требует назвать участницу второго действия: это позволяет измерить сохранение референта. Он не устанавливает правило всегда заменять местоимения именами в обычном переводе.

В контрфактическом случае исходные предложения те же, но уходит другая участница — выбранный ответ меняется. Для каждой сцены есть все шесть направлений EN/RU/HE. Переводы и контрфактические варианты сохраняют общий family/origin/split.

Вторая задача использует «Оператор может напечатать документ». Исправный принтер и явный запрет дают значение способности; сломанный принтер и явное разрешение дают значение права. Нельзя угадывать модальность по слову «принтер». Поэтому те же два модальных класса представлены и для входа посетителя в зал.

Состав каждой новой переводческой партии — 12 строк, по три на каждую клетку пересечения: `позиция референта × пол одинаковых по полу участников` либо `семейство действия × модальный класс`. Новые сценарные семьи и лексические контексты назначаются до генерации. Четыре демонстрационные сцены нельзя размножить заменой имён и объявить независимыми уроками.

**48 новых переводческих reference-строк происходят из четырёх исходных семей**, включая все направления и контрфактуалы. Это не 48 независимых наблюдений. Регистр, склонение, Hebrew morphology и допустимые синонимы оцениваются отдельно; другой корректный перевод не назначается rejected ради заполнения квоты. Аннотация в metadata не объявляется признаком kNN/LoRA, пока потребитель её не читает. Здесь смысловой контекст присутствует непосредственно в learner-visible prompt.

### Оркестрация: достаточное правило вместо скрытого предпочтения

В декомпозиции модель выбирает `split` или `keep` для одного предложения разделить узел. Если две стратегии разрешены условием, пара не имеет доказанного предпочтения. В процессе независимого просмотра исправлены два новых условия: «только если» для положительной метки заменено достаточным правилом, а выделение внутренних арифметических операций без самостоятельного контракта явно требует `keep`.

Задача QA остаётся темой оркестрации. SQL, перевод или UI в условии описывают проверяемую работу, а ответ выбирает нужную предметную способность проверки. Такой набор не учит вперемешку SQL и переводу и не меняет фактическую CODEX authority подготовки. В 16 новых строках оркестрации 14 объявленных сценарных семей; известные контрфактические пары имеют общий origin. Независимость не выводится только из нового family ID.

### SQL: область отката и состояние транзакции

Документационная модель описывает фактически показанный SQL, включая ошибочное поведение. Модель написания кода реализует явный желаемый результат. Эти задачи находятся в `docs.sql` и `code.sql` и получают разные наборы, а родственные исходные случаи имеют общую lineage до разделения TRAIN/DEV/EXAM.

Все новые примеры фиксируют T-SQL / SQL Server 2019, временные таблицы, исходный `@@TRANCOUNT` и отсутствие конкурирующего соединения/ошибок. Показаны изменения до и после savepoint, полный rollback как отдельный контроль, вложенные транзакции и дальнейшая запись после частичного отката. Для исполнения будущего oracle нужна отдельная чистая connection для каждого кандидата. Нельзя добавлять внешнюю транзакционную обёртку: она изменит исходный `@@TRANCOUNT` и сам предмет проверки.

Двенадцать новых DOC/CODE-примеров консервативно связаны с исходной семьёй `reference/DOC-SQL-03/003`. Они не выдаются за 12 независимых экзаменационных случаев. SQL не исполнялся при этой документной подготовке: ожидаемые состояния являются проверяемыми гипотезами, а native oracle остаётся `NOT_RUN`. Будущий review выполняет весь показанный сценарий и сравнивает фактическое состояние с обоими ответами.

## Исправленный вход существующего учебного задания

Четыре прежних `CODE-SQL-GUARD.REF.01`–`.04` требовали правильный WHERE, но не задавали само требуемое изменение Available. Эталон и oracle скрыто предполагали `Available := Available - @qty`. Другое SET могло формально удовлетворить видимому заданию.

Активные версии `.v2` теперь явно требуют уменьшить Available ровно на @qty при допуске и сохранить остальные поля. Различие chosen/rejected по-прежнему только в проверяемом предикате. Полные исходные строки сохранены в [quarantine/sql-guard-underdefined-v1.jsonl](quarantine/sql-guard-underdefined-v1.jsonl); `derived_from`, origin и leakage groups связывают новую и старую версии. Это исправление условий подготовки, не объявленный успешным эксперимент по обучению.

## После генерации: проверка полезности для обучения

Содержательная приёмка отлична от JSON-проверки. Review решает видимое условие без ярлыков выбранной стороны, проверяет ложные отрицания, состав классов и provenance. Code и поведение SQL/.NET/Angular требуют реального предметного oracle соответствующей версии; декларация результата не заменяет выполнение. Ничьи, недостаточный контекст и неизвестная authority остаются вне принятого корпуса. Данные сохраняются версиями, а не удалением неудачной партии.

Поздний учебный пилот следует [05](05-LEARNING-AND-CHECKPOINTS.md): восстановить совместимый квалифицированный B1, сравнить одинаковый обучаемый получатель до/после и после свежей загрузки, сохранить tokenizer/LoRA/optimizer/RNG и dataset hashes. Создание нового B1 не запускается скрыто в каждой карточке. Назначенные каталоги в очереди не выдают за существующие веса. Перед новым обучением нужен фактический native binding из [10](10-NATIVE-CONTRACT-BOUNDARY.md), а не придуманный флаг старого runner.

Для новых переводческих целей показать корректность по всем четырём клеткам и каждому направлению; для оркестрации — split/keep и missing/complete/gap; для SQL — состояние данных и счётчик транзакции. Сначала оценить доменную Unit с правильным маршрутом, затем отдельно весь prompt→router→domain→Unit→answer. Router-ошибку нельзя приписать качеству предметного DPO.

Любое измеренное улучшение полезного показателя на валидном обучении — успех по этому показателю и домену, с остальными дельтами и ухудшениями рядом. Например, меньше времени до того же ненулевого результата полезно без роста точности. Время генератора, проверки и компиляции отделяется от времени Student-обновлений. 0 правильных до и после не становится учебным результатом благодаря margin/loss, метаданным или скорости подготовки.
