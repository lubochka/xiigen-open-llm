# ADR: Angular Runtime Config, HTTP Interceptors, SSR, And Lazy Loading

Status: Approved for implementation
Date: 2026-05-14

## Context

The standalone Angular ADR chooses `bootstrapApplication`, standalone
components, and functional guards. The plan still needs the runtime deployment
shape: whether SSR is used, how tenant-specific API origins are resolved, how
headers are injected, and how generated flows are lazy loaded.

## Decision

Use client-side SPA rendering for the initial .NET/Angular translation. Do not
enable Angular SSR or prerendering until a later ADR proves a product need and
updates Playwright evidence rules.

Use runtime configuration, not build-time-only environment files, for tenant
deployment values.

## Runtime Config

The shell loads this file before route activation:

```text
assets/xiigen-runtime-config.json
```

The loader runs as an Angular application initializer
(`provideAppInitializer` / `APP_INITIALIZER` equivalent for the selected Angular
major) before router initial navigation. Guards, interceptors, Transloco
loaders, and feature routes must wait on `RuntimeConfigService.ready`; runtime
config must not be loaded through per-route resolvers because those fire too
late for the first auth/tenant guard decision.

`RuntimeConfigService` has this minimum shape:

```typescript
export interface XiigenRuntimeConfig {
  apiBaseUrl: string;
  tenantResolution: "subdomain" | "path" | "header" | "single-tenant";
  tenantIdHint: string | null;
  features: Record<string, boolean | string | number>;
  auth: {
    tokenStorage: "memory";
    refreshEnabled: boolean;
    refreshMode: "reactive-401-only" | "preemptive-and-reactive";
    preemptiveRefreshSkewSeconds: number;
    preserveReturnUrl: true;
  };
  correlationHeader: "X-Correlation-Id";
}

export class RuntimeConfigService {
  readonly ready: Signal<boolean>;
  load(): Promise<void>;
  whenReady(): Promise<XiigenRuntimeConfig>;
  get snapshot(): XiigenRuntimeConfig;
}
```

The application initializer returns `runtimeConfigService.load()`. Guards and
interceptors call `whenReady()` when they may run before `ready()` is true.
`snapshot` throws a fail-closed configuration error if accessed before load
completion.

The Angular bootstrap sequence has one required initializer in the first
implementation:

```typescript
provideAppInitializer(() => inject(RuntimeConfigService).load())
```

No token refresh, tenant resolution network call, feature flag reload, or
context-role resolver may run as a bootstrap initializer. Those depend on the
runtime config and therefore run through guards/interceptors after
`RuntimeConfigService.ready` is true. `FeatureFlagService.reload(config)` is
called synchronously from the runtime config load success path. This keeps
initial navigation deterministic: config first, router second, auth/tenant
guards third.

`RuntimeConfigService` is a root singleton:

```typescript
@Injectable({ providedIn: "root" })
export class RuntimeConfigService { ... }
```

It is not provided per route or per flow. Tests may override it through Angular
testing providers, but generated flow code must inject the root service.

The file validates against:

```text
schemas/angular-runtime-config.schema.json
```

`RuntimeConfigService.load()` must validate the downloaded JSON before setting
`ready = true`. The initial implementation uses a generated validator emitted
from `schemas/angular-runtime-config.schema.json` during the contract
generation gate:

```typescript
export interface RuntimeConfigValidationResult {
  valid: boolean;
  errors: ReadonlyArray<{ path: string; message: string }>;
}

export function validateXiigenRuntimeConfig(
  value: unknown
): RuntimeConfigValidationResult;
```

Invalid or missing config fails closed with `XIIGEN_RUNTIME_CONFIG_INVALID`,
logs a sanitized correlation-aware error, keeps `ready = false`, and prevents
router initial navigation. The Angular shell must not continue with default or
null `apiBaseUrl`, tenant resolution, auth, or feature flag values.

The file is generated from `hosting-targets.json` and environment-specific
deployment settings. It contains:

```json
{
  "apiBaseUrl": "https://tenant.example.com/api",
  "tenantResolution": "subdomain|path|header|single-tenant",
  "tenantIdHint": null,
  "features": {},
  "auth": {
    "tokenStorage": "memory",
    "refreshEnabled": true,
    "refreshMode": "preemptive-and-reactive",
    "preemptiveRefreshSkewSeconds": 30,
    "preserveReturnUrl": true
  },
  "correlationHeader": "X-Correlation-Id"
}
```

Angular environment files may contain only static build flags and the location
of the runtime config file. They must not contain secrets, tenant signing keys,
Vault tokens, or tenant runtime data.

Allowed environment file fields are:

```typescript
export const environment = {
  production: false,
  runtimeConfigPath: "assets/xiigen-runtime-config.json",
  buildVersion: "local",
  enableDebugTools: true
};
```

API base URLs, tenant ids, feature toggles that vary by tenant, auth settings,
tokens, secrets, Vault paths, and provider credentials are forbidden in
`environment.ts` and `environment.prod.ts`. The generator must reject any
environment file that includes those runtime values.

## Feature Flags

Runtime feature flags are consumed through `FeatureFlagService`, not by reading
the raw config object in components:

```typescript
export class FeatureFlagService {
  readonly flags: Signal<Record<string, boolean | string | number>>;
  isEnabled(key: string, fallback?: boolean): boolean;
  value<T extends boolean | string | number>(key: string, fallback: T): T;
  reload(config: XiigenRuntimeConfig): void;
}
```

Components and guards inject `FeatureFlagService`. Generated Angular code must
not import `environment` for tenant-varying features and must not directly
index `runtimeConfig.features` outside this service.

Feature flags are initialized once from `RuntimeConfigService` during app
startup. Runtime reload is not automatic in the first implementation; the only
approved reload path is an explicit `FeatureFlagService.reload(config)` call
from a platform admin/dev-tools action or test harness. Reload updates the
`flags` signal atomically. Flow components react through signal reads and do
not poll config files.

## HTTP Interceptors

Use functional interceptors:

- `authInterceptor: HttpInterceptorFn` adds `Authorization: Bearer <token>`
  when `AuthSessionService` has an in-memory access token.
- `tenantInterceptor: HttpInterceptorFn` adds `X-Tenant-Id` only when the
  server-side tenant resolution mode requires a header.
- `correlationInterceptor: HttpInterceptorFn` adds `X-Correlation-Id` from
  `CorrelationContextService` or creates one for the command/request.
- `authRefreshInterceptor: HttpInterceptorFn` performs one bounded refresh on
  401 when refresh is enabled; otherwise it clears session state and routes to
  login/denied.

`tenantInterceptor` reads `RuntimeConfigService.snapshot.tenantResolution`.
It adds the `X-Tenant-Id` header only when all of these are true:

- `tenantResolution` is `"header"`;
- `tenantIdHint` is present and non-empty;
- the request URL targets `apiBaseUrl` or a relative API URL owned by XIIGen;
- the request is not a third-party telemetry, asset, translation-bundle, or
  external provider request.

For `subdomain`, `path`, or `single-tenant`, the interceptor must not add
`X-Tenant-Id`; the server derives tenant scope from the approved resolution
source. A runtime config with `tenantResolution = "header"` and no
`tenantIdHint` fails schema validation before interceptors run.

JWT access tokens are stored in memory by default. Persistent token storage
requires a separate security ADR.

`AuthSessionService` is the only token source for interceptors:

```typescript
@Injectable({ providedIn: "root" })
export class AuthSessionService {
  readonly accessToken: Signal<string | null>;
  readonly refreshInProgress: Signal<boolean>;
  hasToken(): boolean;
  getAccessToken(): string | null;
  setSession(response: AuthLoginResponse): void;
  clearSession(reason: "logout" | "expired" | "refresh-failed"): void;
  refreshOnce(): Promise<boolean>;
}
```

Generated code must not read tokens from `RuntimeConfigService`, browser local
storage, session storage, cookies, or component state.

Refresh handling is single-flight and loop-safe:

1. `authRefreshInterceptor` catches a 401 only once per original request.
2. It marks the retried request with an internal `XIIGEN_REFRESH_RETRY` context
   token so the same request cannot trigger a second refresh loop.
3. If another refresh is already in progress, it awaits that in-memory promise
   instead of calling `/auth/refresh` again.
4. On refresh success, it updates `AuthSessionService` and retries the original
   request once.
5. On refresh failure, missing refresh token, or second 401 after retry, it
   clears the session and routes to login with the preserved `returnUrl`.
6. Refresh requests themselves are excluded from refresh interception.

## Auth Session Behavior

`AuthSessionService` stores access tokens in memory only. A browser refresh
clears the access token and forces re-auth unless a later ADR approves
persistent storage. Logout clears all in-memory token, user, role, and pending
refresh state.

Token expiry is detected by decoding the JWT `exp` claim when present and by
server 401 responses. The default refresh mode is `preemptive-and-reactive`:

- before a request, refresh once when the token expires within
  `preemptiveRefreshSkewSeconds`;
- after a 401, perform one bounded refresh when refresh is enabled;
- if refresh fails or loops, clear session state and route to login/denied.

`CanActivateFn` auth and role guards preserve the attempted URL as a
`returnUrl` query parameter whenever they redirect to login. After successful
auth, the shell returns to that URL only if the route still passes tenant, auth,
role, and context-role guards.

## Global Error Handling

The Angular shell registers `XiigenGlobalErrorHandler` as the application
`ErrorHandler`.

The handler records:

- correlation id;
- current route and flow id when available;
- active tenant id only when it is already public route context;
- sanitized error code/category;
- build version.

It must not log bearer tokens, refresh tokens, request bodies, PII, Vault
paths, raw tenant data, or generated code bundles. User-facing messages are
plain language and do not expose stack traces. Optional telemetry posts use the
same auth and correlation interceptors and must tolerate offline/failure
without breaking route activation.

When client telemetry is enabled, the only approved initial endpoint is:

```text
POST /api/telemetry/client-errors
```

If this endpoint is unavailable, returns 401/403/429/5xx, or the browser is
offline, the handler drops or bounded-buffers the sanitized event in memory and
continues route activation. It must not retry indefinitely and must not write
telemetry payloads to persistent browser storage.

## Lazy Loading

The platform shell lazy-loads each flow as a route array:

```typescript
{
  path: "flows/FLOW-XX-<slug>",
  canActivate: [
    configLoadedGuard,
    tenantGuard,
    authGuard,
    roleGuard,
    contextRoleGuard
  ],
  loadChildren: () => import("./flows/FLOW-XX-<slug>/routes")
    .then(m => m.FLOW_XX_ROUTES)
}
```

Inside a flow route array, leaf screens use `loadComponent`. Use
`loadChildren` at the flow boundary and `loadComponent` for leaf views. This
keeps generated packages consistent while allowing fine-grained screen loading.

Guard activation order is fixed and fail-closed:

1. `configLoadedGuard` awaits `RuntimeConfigService.whenReady()` and redirects
   to a configuration-error route on validation/load failure.
2. `tenantGuard` resolves tenant context from the approved runtime-config mode.
3. `authGuard` verifies an in-memory access token or redirects to login with
   `returnUrl`.
4. `roleGuard` checks canonical role snapshots for route policies.
5. `contextRoleGuard` calls the server/context-role resolver when the policy
   requires business-state-derived roles.

Routes may omit `roleGuard` or `contextRoleGuard` only when the auth policy
registry marks the endpoint/screen as not requiring those gates. Routes must
not put auth, role, or context-role guards before `configLoadedGuard`.

`tenantGuard` implementation:

- reads `RuntimeConfigService.snapshot.tenantResolution`;
- for `subdomain`, extracts the tenant label from the browser host using the
  hosting-target rules generated from `hosting-targets.json`;
- for `path`, extracts the configured path segment and normalizes it before
  route activation continues;
- for `header`, uses `tenantIdHint` from runtime config and relies on
  `tenantInterceptor` to emit `X-Tenant-Id` for API calls;
- for `single-tenant`, uses the configured `tenantIdHint`;
- rejects missing, ambiguous, or unsupported tenant mode with a `UrlTree` to a
  tenant-resolution error route.

The guard never reads tenant id from component state, arbitrary query strings,
or local storage. Server authorization remains the source of truth.

Subdomain extraction uses longest-suffix matching against generated hosting
targets. `hosting-targets.json` produces entries shaped like:

```json
{
  "tenantHostSuffix": "example.com",
  "reservedSubdomains": ["www", "api", "admin", "static"]
}
```

For a host, the guard finds the longest configured suffix that matches the
right side of the host. The tenant label is the DNS label immediately to the
left of that suffix. For `acme.example.com`, tenant label is `acme`. For
`northwind.eu.example.com` with suffix `eu.example.com`, tenant label is
`northwind`. Reserved labels and hosts with no label before the suffix fail
closed to the tenant-resolution error route.

## Flow Route Registration

Generated flow Angular routes are statically registered at build/generation
time from the route manifest, not discovered dynamically from tenant runtime
data in the browser. The shell owns:

```text
src/app/flow-route-registry.generated.ts
```

That generated file imports each flow route array by lazy boundary:

```typescript
export const XIIGEN_FLOW_ROUTES: Routes = [
  {
    path: "flows/FLOW-01-user-registration",
    canActivate: [configLoadedGuard, tenantGuard, authGuard, roleGuard],
    loadChildren: () => import("../flows/FLOW-01-user-registration/routes")
      .then(m => m.FLOW_01_ROUTES)
  }
];
```

The Angular shell includes `XIIGEN_FLOW_ROUTES` in the router configuration.
Tenant install/cascade operations can enable or disable flow availability
through feature/config metadata, but they do not inject arbitrary route code at
runtime. A flow package that lacks a generated `routes.ts` and manifest route
entry fails the Angular shell contract gate.

Shell route structure:

```typescript
// src/app/app.routes.ts
export const APP_ROUTES: Routes = [
  ...XIIGEN_PLATFORM_ROUTES,
  ...XIIGEN_FLOW_ROUTES,
  { path: "**", redirectTo: "/error/not-found" }
];
```

`bootstrapApplication` calls `provideRouter(APP_ROUTES, withEnabledBlockingInitialNavigation())`.
The flow registry is imported by `app.routes.ts`; `AppComponent` does not
manually compose routes.

`XIIGEN_PLATFORM_ROUTES` is defined in:

```text
src/app/platform-routes.ts
```

Initial contents:

```typescript
export const XIIGEN_PLATFORM_ROUTES: Routes = [
  { path: "error/config", component: XiigenConfigErrorComponent },
  { path: "error/tenant", component: XiigenTenantResolutionErrorComponent },
  { path: "error/not-found", component: XiigenNotFoundComponent },
  { path: "auth/login", component: XiigenLoginComponent },
  { path: "auth/denied", component: XiigenAccessDeniedComponent }
];
```

Health and telemetry endpoints are API routes, not Angular shell routes, and
are not part of `XIIGEN_PLATFORM_ROUTES`.

Every generated flow package exports exactly one named route array from its
`routes.ts`:

```typescript
export const FLOW_01_ROUTES: Routes = [ ... ];
```

The name is `FLOW_XX_ROUTES` with the two-digit flow id. Default exports and
alternative names such as `FLOW_01_ROUTES_ARRAY` are rejected by the Angular
shell contract gate.

Initial platform error/auth route URLs and components:

```text
/error/config   -> XiigenConfigErrorComponent
/error/tenant   -> XiigenTenantResolutionErrorComponent
/error/not-found -> XiigenNotFoundComponent
/auth/login     -> XiigenLoginComponent
/auth/denied    -> XiigenAccessDeniedComponent
```

Guards redirect only to these initial routes unless a later ADR extends the
platform route set.

`contextRoleGuard` resolves business-state-derived roles through the protected
platform auth endpoint:

```text
POST /auth/context-role/resolve
```

The request carries route policy id, flow id, resource/context id, policy
version, and current route params. It does not carry a free-form tenant id; the
server derives tenant scope from the authenticated request context. The guard
fails closed for 401, 403, 404, stale policy version, resolver timeout, or any
non-allow response.

## Acceptance Criteria

P-10 is not complete until:

- SSR is explicitly disabled or a later ADR replaces this decision;
- runtime config loads before guarded routes;
- runtime config is loaded by the application initializer before router
  initial navigation, not by a guarded-route resolver;
- Angular bootstrap uses only the runtime config initializer; token refresh,
  tenant resolution network calls, and context-role resolution are not
  bootstrap initializers;
- `RuntimeConfigService.ready` is an Angular `Signal<boolean>` with
  `whenReady(): Promise<XiigenRuntimeConfig>` for guards and interceptors;
- `RuntimeConfigService` is `@Injectable({ providedIn: "root" })` and flow
  code injects that singleton;
- feature flags are read through `FeatureFlagService`, not direct runtime
  config indexing in generated components;
- feature flag reload is explicit and atomic through
  `FeatureFlagService.reload(config)`;
- runtime config validates against `schemas/angular-runtime-config.schema.json`;
- `RuntimeConfigService.load()` uses the generated schema validator and fails
  closed with `XIIGEN_RUNTIME_CONFIG_INVALID` before route activation when the
  config is malformed;
- no tenant secret appears in Angular environment files;
- environment files contain only the approved static fields and runtime config
  path;
- functional interceptors inject auth, tenant, and correlation headers;
- tenant interceptor tests prove `X-Tenant-Id` is emitted only for
  `tenantResolution = "header"` with a valid `tenantIdHint` and only for
  XIIGen API requests;
- auth interceptors read and mutate token state only through
  `AuthSessionService`;
- token refresh behavior is tested for success, failure, and loop prevention;
- refresh tests prove single-flight refresh, one retry per request, refresh
  endpoint exclusion, and session clearing on failed refresh;
- memory-only token storage, page-refresh re-auth, logout clearing, and
  `returnUrl` preservation are tested;
- `XiigenGlobalErrorHandler` sanitizes logs and user messages and never emits
  tokens, PII, Vault paths, or request bodies;
- generated flow packages use `loadChildren` at the boundary and
  `loadComponent` for leaf screens.
- route declarations use guard order
  `configLoadedGuard -> tenantGuard -> authGuard -> roleGuard ->
  contextRoleGuard`, with role/context guards omitted only when the auth policy
  registry allows it.
- tenant guard tests prove subdomain, path, header, and single-tenant modes
  resolve only from runtime config and hosting-target rules;
- subdomain tests prove longest-suffix matching, reserved-label rejection, and
  missing-label rejection;
- shell route tests prove flow routes are generated into
  `flow-route-registry.generated.ts` at build/generation time and are not
  loaded from tenant runtime data in the browser.
- shell route tests prove `app.routes.ts` uses `APP_ROUTES`, imports
  `XIIGEN_FLOW_ROUTES`, and every flow package exports `FLOW_XX_ROUTES`;
- platform route tests prove `XIIGEN_PLATFORM_ROUTES` contains only the five
  initial shell routes above and excludes API health/telemetry endpoints;
- context-role guard tests prove it calls `POST /auth/context-role/resolve`
  without sending a tenant id and fails closed on all non-allow outcomes;
- guard redirect tests prove config, tenant, denied, login, and not-found
  failures route to the URLs/components listed above.

## Applies Before
- P-10 Angular shell scaffold.
- Any flow Angular package that calls the .NET API.
