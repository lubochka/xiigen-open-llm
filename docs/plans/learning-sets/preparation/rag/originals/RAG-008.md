# XIIGEN CAPABILITY GAP SIMULATION PROTOCOL
## How to Simulate XIIGen Running a Task — What Breaks and Where
## Version: 1.0 | Date: 2026-03-24
## Purpose: Map real capability gaps before planning any flow

---

# PART 1 — THE SIMULATION PROTOCOL

## How to run a simulation

A simulation is not "imagine if XIIGen could do this." It is a step-by-step
trace through what XIIGen **actually does** today when given a task, using the
actual engine components that exist. At each step, you ask:

```
Q1. What component handles this step?  (name the actual handler/service)
Q2. What input does it receive?        (exact fields, where they come from)
Q3. What does it produce?              (exact output shape)
Q4. What does it need that doesn't exist?  (the gap — named precisely)
Q5. What is the observable symptom?    (how failure appears to the user/operator)
```

A gap is confirmed only when Q4 has a specific answer. "It doesn't work" is not
a gap. "The rag-retrieve.handler queries by {patternType:'FLOW_DESIGN', domain:'X'}
but there is no registered pattern with domain='social-media-scheduling'" is a gap.

---

## The simulation trace format

For each task scenario, the trace has levels:

```
LEVEL N: [abstraction level name]
  INPUT:    what arrives at this level
  HANDLER:  which XIIGen component processes it (or NONE if missing)
  PRODUCES: what the component outputs
  NEEDS:    what is required that doesn't exist → GAP-N
  SYMPTOM:  what the operator/user observes when this fails
  VERDICT:  PASS | PARTIAL | BLOCKED | SILENT_FAILURE
```

`SILENT_FAILURE` is the worst verdict — the engine continues but produces
wrong output without signaling that anything is broken.

---

## The five simulation scenarios

Chosen to cover the widest surface of XIIGen's claimed capabilities:

```
SIM-A: the AI agent orchestration flow canonical — Canva C5 adapter (known, specified, planned)
SIM-B: the AI agent orchestration flow adaptation — F1 from C5 (adaptation from canonical)
SIM-C: Content pipeline — Scenario 6 from the big prompt (multi-modal, multi-platform)
SIM-D: Diet coaching app — Scenario 4 (conversational channel, multi-model, recurring)
SIM-E: Pascal migration — Legacy system redesign (arbitrary domain intake)
```

SIM-A is the "should work" baseline. If it breaks, everything after it also breaks.
SIM-E is the most ambitious. Gaps found in SIM-A that aren't fixed will compound in SIM-E.

# PART 2 — SIM-A: the AI agent orchestration flow CANVA C5 ADAPTER

**Task:** Generate the Canva Text Elements adapter (C5 canonical)
**Why chosen:** Most specified task in XIIGen's entire catalog. If this breaks, nothing is solid.

---

## A-L1: Task Router Level

```
INPUT:    "Generate C5 — Canva Text Elements Adapter"
HANDLER:  NONE — no task router exists
PRODUCES: nothing
NEEDS:    A component that receives a task description and routes it to the
          correct flow/handler combination. Currently every flow is initiated
          by a human typing the right session file. There is no
          POST /api/engine/task endpoint.
SYMPTOM:  Operator must manually identify which phase to run, which session
          file to load, and which POST endpoint to call. XIIGen cannot
          self-initiate from a task description.
VERDICT:  BLOCKED
```

**GAP-A1: No task intake router.**
XIIGen has `POST /api/engine/run` for specific task types and
`POST /api/engine/convergence` (planned). It has no general intake that
accepts a task description and routes it. Every task must be pre-decomposed
by a human into specific session files.

---

## A-L2: PortingDecisionGate (the porting-related implementation rule 1)

```
INPUT:    { capability: "Canva Text Elements", platform: "canva", ftId: "FT-C5" }
HANDLER:  PortingDecisionGate (planned in the AI agent orchestration flow Phase B — NOT YET BUILT)
PRODUCES: { decision: PORTABLE | NOT_PORTABLE, reason, constraints[] }
NEEDS:    The gate must know Canva's specific constraints:
          - No direct HTTP calls from adapter (Canva sandbox restriction)
          - Manifest.json required fields (appName, version, requiredScopes)
          - Review timeline: 2-4 weeks, rejections on: missing permissions,
            direct the programming interface calls, unminified bundle > 5MB
          NONE of this is in the retrieval system. The gate will produce a verdict based
          on generic FLOW_DESIGN patterns — missing the Canva-specific rules.
SYMPTOM:  Gate passes C5 with a generic PORTABLE verdict. The generated adapter
          makes direct HTTP calls (not through QUEUE FABRIC) because the
          Canva-specific prohibition was never in the gate's context.
          the thin-related implementation rule 2 violation — caught by arbiter, but only after generation.
VERDICT:  SILENT_FAILURE (gate passes, but with wrong constraints)
```

**GAP-A2: No external knowledge intake for platform constraints.**
The PortingDecisionGate's `rag-retrieve.handler` queries:
```json
{ "patternType": "PLATFORM_CONSTRAINT", "platform": "canva" }
```
Zero results — no such patterns exist. The gate falls back to generic
FLOW_DESIGN patterns, misses the sandbox HTTP restriction.

---

## A-L3: the programming interface Mapping Document (flow check 26)

```
INPUT:    { platform: "canva", capability: "text-elements", sdkVersion: "2.1.0" }
HANDLER:  NONE — flow check 26 requires this document to exist BEFORE code generation,
          but nothing in the engine produces it
PRODUCES: should produce: { endpoints[], methods[], parameters[], constraints[] }
NEEDS:    Something that reads https://www.canva.com/developers/docs/ and
          produces a structured the programming interface mapping. This requires external knowledge
          intake — reading a URL and converting it to structured data the
          genesis prompt can use.
SYMPTOM:  A human must write contracts/api-maps/canva/FT-C5.md manually.
          If skipped (no enforcement), the code generation station invents plausible method names:
          canva.addTextElement() instead of canva.ui.startLoading() + 
          appProcess.registerOnMessage(). The generated adapter calls methods
          that do not exist.
VERDICT:  BLOCKED (human required) or SILENT_FAILURE (if human step is skipped)
```

**GAP-A3: No mechanism to produce the programming interface mapping documents from external sources.**
flow check 26 is a gate check — it verifies the document exists. But nothing in the AI agent orchestration flow
Phases A-D creates the document. It must be authored by a human.

## A-L4: Adapter Generation — the code generation station Prompt Assembly

```
INPUT:    {
            taskTypeId: "T-[+1]" (AdapterCodeGenerator),
            genesisPrompt: "Generate a Canva app adapter for text elements...",
            stack: "canva-app",
            ragContext: [retrieved patterns]
          }
HANDLER:  the code generation station (exists, operational)
PRODUCES: canva-text-elements-adapter.ts
NEEDS:    The genesis prompt has Section 1 (neutral constraints) and Section 4
          (Canva-specific frame). Section 4 derives from stackCoupling.
          BUT: stackCoupling for "canva-app" stack was written as:
          implementationNotes: "See Canva Apps SDK documentation"
          This is a reference, not actual content. the code generation station receives a pointer to
          external documentation it cannot access, not the documentation itself.
SYMPTOM:  the code generation station generates a plausible adapter structure. All method names are
          invented. The adapter will compile (TypeScript accepts invented names
          as type errors, not parse errors, if typed as `any`). Tests that
          mock the Canva SDK will pass. Integration tests with actual Canva
          SDK will fail at runtime.
VERDICT:  SILENT_FAILURE (compiles, passes mocked tests, fails in production)
```

**GAP-A4: stackCoupling implementationNotes contain pointers, not content.**
The Section 4 generation frame says "see documentation" instead of containing
the actual SDK patterns. This is a documentation gap, not an architectural gap —
but it means every generated adapter is generated from incomplete context.

## A-L5: 5-Arbiter Consensus (the thin-adapter minimality rule through the thin-related implementation rule 3)

```
INPUT:    generated canva-text-elements-adapter.ts
HANDLER:  5-arbiter consensus (planned, not yet built as GenericNodeExecutor
          voting gate — GAP-CATALOG N2 from the AI agent orchestration flow v5)
PRODUCES: { scores: [s1..s5], verdict: PASS|FAIL, violations: [] }
NEEDS:    the thin-adapter minimality rule checks: "no business logic in adapter" — this check requires
          knowing what IS business logic vs what is glue code. Currently this
          distinction is defined in the iron rules text but not as a named
          check in the validate.handler catalog.
          the thin-related implementation rule 2 checks: "QUEUE FABRIC only" — this requires knowing what
          calls constitute QUEUE FABRIC calls vs direct HTTP. The check exists
          in the catalog (LEARNINGS N3) but is NOT YET ADDED to the engine.
SYMPTOM:  Arbiter runs without N2 (voting gate) and N3 (queue_fabric_only).
          An adapter that calls direct HTTP passes the arbiter. Only after
          Canva rejects the submission (2-4 weeks) does the violation surface.
VERDICT:  PARTIAL (arbiters run, but key checks missing)
```

**GAP-A5: Named arbiter checks defined in the AI agent orchestration flow v5 (N1-N4) not yet wired
into the engine.** This is documented in the AI agent orchestration flow's own gap catalog and is
known — but it means the arbiter runs in degraded mode for all 65 adapters.

## A-L6: Adaptation Delta — C5 to F1

```
After C5 generates successfully (with the gaps above noted):

INPUT:    { canonical: "C5 Canva Text Elements", target: "F1 Figma Site Generator" }
HANDLER:  NONE — no adaptation delta computation exists
PRODUCES: should produce: { deltaContext: [], unchangedIronRules: [], newIronRules: [] }
NEEDS:    A component that computes: "what is different between C5's platform
          context and F1's platform context, and what stays the same?"
          
          C5 → F1 differences:
          - Auth: Canva OAuth → Figma plugin token (different auth flow)
          - Sandbox: Canva apps sandbox → Figma plugin sandbox (different constraints)
          - Object model: Canva elements → Figma node tree (different shape)
          - Output: Canva UI the programming interface → Figma createFrame() + figma.root (different calls)
          
          C5 → F1 similarities (should NOT be regenerated):
          - QUEUE FABRIC pattern (identical)
          - @xiigen/plugin-sdk usage (identical)
          - FREEDOM config structure (identical)
          - Error handling pattern (identical)

SYMPTOM:  F1 is generated from scratch using C5 session files as reference.
          The operator must manually identify what's different and annotate
          the F1 session file. At scale (65 adapters), this is 64 manual
          delta analyses. The accumulated learning from C5 does not transfer
          automatically to F1.
VERDICT:  BLOCKED (manual human step required for each new adapter)
```

**GAP-A6: No adaptation delta computation.**
Every new adapter after C5 is either a full regeneration or a manual annotation
task. XIIGen cannot compute "what changed between these two platform contexts"
and apply only the delta.

# PART 3 — SIM-B: CONTENT GENERATION PIPELINE (Scenario 6)

**Task:** User speaks text → AI generates → schedules multi-platform posts
with images, video, audio, captions.

## B-L1: Task decomposition

```
INPUT:    "User recorded audio. Generate and schedule content across 5 platforms."
HANDLER:  NONE — same as SIM-A L1. No task router.
          But here the problem is deeper: even if a router existed, the task
          decomposes into sub-tasks that span multiple capability domains
          that XIIGen has never seen.

Expected decomposition:
  [audio-to-text, text-improve, content-plan, image-gen × N,
   video-gen × N, music-gen, voiceover, template-assemble × 5,
   caption-gen × 5, schedule × 5]

Match check against existing flow patterns:
  audio-to-text      → FLOW exists for this? NO. No ISpeechService.
  text-improvement   → FLOW exists? PARTIAL. AI pipeline exists, no domain context.
  image-generation   → FLOW exists? NO. No IImageGenerationService.
  video-generation   → FLOW exists? NO. No IVideoGenerationService.
  music-generation   → FLOW exists? NO. No IMusicGenerationService.
  voiceover          → FLOW exists? NO. No IAvatarVoiceService.
  template-assemble  → FLOW exists? NO. No platform template registry.
  caption-gen        → FLOW exists? PARTIAL. AI pipeline, no platform format rules.
  schedule-post      → FLOW exists? NO. No ISocialSchedulerService.

Result: 7 of 10 sub-capabilities have NO fabric interface.

SYMPTOM:  Without gap detection, the engine attempts to match all 10 against
          registered flow patterns. 7 match nothing. Engine either fails
          silently (skips them) or throws unhandled exceptions.
VERDICT:  BLOCKED
```

**GAP-B1: No gap detection in task decomposition.**
When a sub-task matches no existing pattern, the engine has no protocol.
It cannot emit: "GAP DETECTED: ISpeechService required, design session needed."
It cannot spawn a design session to create the missing interface.
The human must notice the gap and design the interface manually.

---

## B-L2: Fabric interface design — ISpeechService example

```
The operator notices audio-to-text is missing. Manually initiates design.

INPUT:    { capability: "audio-to-text", providers: [Whisper, AssemblyAI, Azure Speech] }
HANDLER:  planning session (human-driven)
PRODUCES: ISpeechService interface:
          transcribe(audioBuffer: Buffer, options: SpeechOptions): Promise<TranscriptResult>
          detectLanguage(audioBuffer: Buffer): Promise<LanguageCode>
NEEDS:    This is a design session — human-initiated, human-driven.
          What XIIGen SHOULD do: retrieve existing fabric interface patterns
          from the retrieval system, apply to new domain, produce draft interface, run through
          Q1-Q4 gate automatically, produce FREEDOM config keys for provider.
          What XIIGen DOES: human writes the interface from scratch. No retrieval
          of existing patterns. No automatic FREEDOM config generation.
          No automatic test stub generation.
SYMPTOM:  Correct interfaces are produced but slowly (one session per interface).
          With 7 missing interfaces, this is 7 separate planning sessions before
          any generation can start. The interfaces may be inconsistent
          (different naming conventions, different result types) because they
          were designed in separate sessions without a shared pattern.
VERDICT:  PARTIAL (produces correct output, but slow and potentially inconsistent)
```

**GAP-B2: Fabric interface design is not automated.**
XIIGen can generate code FROM fabric interfaces. It cannot generate fabric
interfaces FROM capability descriptions. The interface design step requires
a human planning session for every new capability type.

## B-L3: Multi-modal output routing

```
After interfaces exist, the pipeline runs. Multiple sub-tasks produce different output types:

Sub-task: image-generation
  INPUT:    { prompt: "...", style: "...", dimensions: "1080x1080" }
  OUTPUT:   image file (PNG/JPEG) — binary data

Sub-task: video-generation
  INPUT:    { frames: [], audio: buffer, duration: 3 }
  OUTPUT:   video file (MP4) — binary data, large

Sub-task: caption-generation
  INPUT:    { content: "...", platform: "tiktok", maxLength: 150 }
  OUTPUT:   text string

Sub-task: schedule-post
  INPUT:    { platform: "tiktok", assets: [image, video, caption], time: ISO }
  OUTPUT:   { postId: "...", scheduledAt: "..." }

HANDLER:  feedback.handler — stores results to Elasticsearch
PROBLEM:  feedback.handler stores to xiigen-flow-results index.
          This index holds JSON documents. Binary data (images, video) cannot
          be stored in Elasticsearch. The feedback.handler has no concept of
          blob storage (S3, Azure Blob, GCS) as an output destination.
          Large binary outputs have no storage path.
SYMPTOM:  Image generation result is a URL or a base64 string in Elasticsearch.
          For large video files, base64 encoding makes the search index document exceed
          the 100MB document size limit. The feedback.handler throws a storage
          error on the video sub-task. The entire pipeline fails at output storage.
VERDICT:  BLOCKED (binary output has no storage path)
```

**GAP-B3: No blob storage fabric interface.**
IBlobStorageService does not exist. feedback.handler stores everything to
Elasticsearch. Binary outputs (images, video, audio) cannot be stored in the search index
at production scale. No fabric interface abstracts S3/Azure Blob/GCS.

## B-L4: Platform-specific assembly — TikTok vs YouTube Shorts

```
INPUT:    {
            platform: "tiktok",
            videoFile: "s3://...",
            music: "s3://...",
            caption: "...",
            hashtags: ["#ai", "#content"]
          }
HANDLER:  should be a TikTok adapter (like the AI agent orchestration flow's canva adapter)
          but: no the AI agent orchestration flow equivalent exists for social platforms
          and: the AI agent orchestration flow is not yet executed (it's in pre-A state)

Platform-specific constraints for TikTok:
  - Max video: 60s at 9:16 aspect ratio
  - Audio: must be platform audio or original (licensed music blocked)
  - Caption: 2,200 chars max, first 200 visible without expand
  - the programming interface: requires business account, TikTok for Developers app approval
  - Upload the programming interface: POST /v2/post/publish/video/init (multipart, chunked)

None of this is in the retrieval system. Same as GAP-A2 for social platforms.

SYMPTOM:  Generated assembly code uses wrong aspect ratio (defaults to 16:9).
          Music file is passed directly (blocked by TikTok's content ID).
          Upload call uses wrong endpoint (the programming interface v1 deprecated).
          Content is blocked at upload. No error surfaced in XIIGen — failure
          happens on TikTok's servers after submission.
VERDICT:  SILENT_FAILURE
```

**GAP-B4: No platform constraint registry for social/deployment platforms.**
The same gap as GAP-A2 (platform constraints not in the retrieval system) but for a different
platform class. the AI agent orchestration flow covers marketplace plugins. Social platforms, video
platforms, notification platforms — none are registered.

## B-L5: Multi-model coordination — parallel AI calls

```
The content-plan sub-task requires calling 4 AI models in parallel:
  Model 1 (Claude): Overall content strategy
  Model 2 (GPT-4V): Visual style analysis
  Model 3 (Gemini): Platform-specific optimization
  Model 4 (DALL-E): Image prompt refinement

HANDLER:  IQueueService — enqueue 4 tasks, wait for all 4 to complete
PROBLEM:  The queue fabric handles individual job submission and polling.
          It has no "fan-out and gather" primitive — no way to say:
          "submit these 4 tasks, wait for ALL to complete, collect results."
          Current pattern: submit → poll every X seconds → get result.
          For 4 parallel tasks: 4 separate polls, no aggregation.
          
          The results need to be compared and synthesized:
          "given 4 model outputs, what is the consensus content plan?"
          This synthesis step has no handler in the current topology.

SYMPTOM:  Operator submits 4 tasks. Must poll 4 separate job IDs.
          Must manually collect 4 results and run a 5th call to synthesize.
          There is no "wait for all + synthesize" topology node.
VERDICT:  PARTIAL (fan-out works, fan-in + synthesis doesn't)
```

**GAP-B5: No fan-in / multi-result synthesis pattern.**
The queue fabric supports parallel task submission. It has no aggregation
handler that waits for N tasks to complete and feeds all N results to a
synthesis step. This pattern is required for every multi-model evaluation
scenario in the big prompt.

# PART 4 — SIM-C: DIET COACHING APP (Scenario 4)

**Task:** WhatsApp meal logging → AI calorie calculation → daily feedback loop.

---

## C-L1: WhatsApp inbound message

```
INPUT:    WhatsApp webhook: { from: "+972...", body: "ate 2 eggs, coffee, toast" }
HANDLER:  NONE — XIIGen has no IConversationalChannelService
PRODUCES: nothing
NEEDS:    A fabric interface that:
          (a) receives inbound messages from external messaging platforms
          (b) maintains conversation state across messages from the same user
          (c) can send replies back on the same channel
          
          This is fundamentally different from the queue fabric pattern:
          Queue: system initiates → waits for result
          Conversational: external user initiates → system processes → replies
          
          The difference: the trigger comes from OUTSIDE the system,
          on a channel the system didn't open.
SYMPTOM:  WhatsApp webhook fires. No handler registered. Request returns 404.
          WhatsApp marks the webhook as failed. After 72 hours of 404 responses,
          WhatsApp disables the webhook endpoint. User messages are silently dropped.
VERDICT:  BLOCKED
```

**GAP-C1: No conversational channel fabric.**
IConversationalChannelService does not exist. The current architecture has:
- IQueueService: async job processing (XIIGen-initiated)
- IAIService: model calls (internal)
- IDatabaseService: storage (internal)
No fabric interface handles external-initiated, stateful, bidirectional communication.
WhatsApp, Slack, SMS, push notifications — all require this pattern.

---

## C-L2: Parse "ate 2 eggs, coffee, toast" → structured meal log

```
INPUT:    { rawText: "ate 2 eggs, coffee, toast", userId: "...", date: "2026-03-24" }
HANDLER:  ai-generate.handler (exists)
          genesis prompt: "Extract food items and quantities from user message"
PRODUCES: { items: [{food: "eggs", quantity: 2, unit: "pieces"}, ...] }
NEEDS:    The the retrieval system context for this step should include:
          - User's dietary profile (restrictions, targets, previous logs)
          - Nutrition database patterns (what is a standard serving size?)
          - Language patterns for food quantity ("a cup of", "half a", "large")
          
          None of this exists in xiigen-rag-patterns.
          The user's dietary profile is not in any index (never stored).
          The nutrition database doesn't exist in any fabric.

SYMPTOM:  AI parses the message. Returns structured items — probably correctly
          for simple cases. Fails on ambiguous quantities ("a handful of nuts").
          Returns no caloric values because no nutrition database exists.
          The next step (calorie calculation) receives items with no caloric data.
VERDICT:  PARTIAL (parsing works, context is missing, caloric data absent)
```

**GAP-C2: No user state / session history store.**
Each user interaction must be processed with the context of that user's history
(dietary profile, previous logs, goals). This is not a the retrieval system pattern problem —
it is a user-scoped stateful context problem. No index, no interface, no
retrieval pattern exists for "give me everything known about user X that is
relevant to their meal logging interaction."

## C-L3: Recurring daily flow trigger

```
DESIGN:   Every day at 20:00 local time, send a feedback message to each user.
HANDLER:  ISchedulerService (defined in PATCH--fabric-interfaces, not yet implemented)
PRODUCES: scheduled job: { userId: "...", time: "20:00", flow: "daily-feedback" }
NEEDS:    ISchedulerService with:
          - Per-user timezone handling (20:00 is different for each user)
          - Recurring schedule (not a one-time delayed job)
          - Cancellable (user can pause notifications)
          - Survives restarts (persisted schedule, not in-memory)
          
          Current state: ISchedulerService is defined in a patch document.
          It is not implemented. The implementation notes reference
          "Bull/BullMQ or Action Scheduler" but Bull handles delayed jobs,
          not per-user recurring schedules with timezone support.
SYMPTOM:  No daily messages are sent. The scheduled trigger never fires.
          Users receive no feedback after logging meals.
VERDICT:  BLOCKED
```

**GAP-C3: ISchedulerService not implemented for recurring per-user schedules.**
The patch document defines the interface. No provider implements it.
The a task type reclassification (INCOMPATIBLE → IMPL_VARIES_WITH_PROVIDER) was decided
in the architectural session but not yet applied to contracts.

---

## C-L4: Multi-model analysis — several rounds

```
DESIGN:   Run meal log through Model A, B, C. Compare outputs. If agreement
          < threshold, run another round with disagreements as context.
HANDLER:  This is the same pattern as SIM-B L5 — fan-out + fan-in.
          But here it's iterative: results of round N feed into round N+1.
NEEDS:    A topology handler that:
          (a) runs N models in parallel (fan-out)
          (b) collects all N results (fan-in) — GAP-B5
          (c) evaluates agreement score
          (d) routes: if agreement >= threshold → proceed
                      if agreement < threshold → run another round with diff context
          
          This is a conditional multi-round loop with model output as loop state.
          No topology handler supports this pattern. route.handler can branch
          once. It cannot re-enter a previous node with accumulated state.
SYMPTOM:  The topology can run one round of multi-model analysis.
          If disagreement is detected, route.handler sends to a "low agreement"
          branch. That branch has no way to re-run the analysis with the
          disagreement context injected. It either fails or routes to a
          static fallback response.
VERDICT:  PARTIAL (one round works, iterative rounds blocked)
```

**GAP-C4: No iterative convergence loop in topology execution.**
Topologies are directed acyclic graphs — no cycles allowed in current design.
A loop that re-runs a node with accumulated state from previous iterations
is architecturally impossible. Every multi-round AI scenario requires this
pattern: diet analysis, content review, code generation rounds, arbiter consensus.

**Note:** The 5-arbiter consensus in the AI agent orchestration flow has the same gap — arbiters run
once in parallel, not iteratively. The arbiter is not a convergence loop.

# PART 5 — SIM-D: PASCAL MIGRATION (Scenario: legacy system redesign)

**Task:** Ingest Pascal accounting system → produce modern multi-tenant SaaS.

---

## D-L1: Intake — read Pascal codebase

```
INPUT:    pascal_accounting.zip (uploaded file)
HANDLER:  NONE — no intake handler exists
PRODUCES: should produce: { structure, intent, constraints, quality }
          extracted from the Pascal source code
NEEDS:    A component that:
          (a) reads Pascal syntax (procedure/function definitions, BEGIN/END blocks)
          (b) extracts business rules embedded in code comments and logic
          (c) identifies data structures (RECORD types, typed constants)
          (d) maps Pascal procedures to modern capability concepts
          (e) produces a structured representation in XIIGen vocabulary
          
          The AI ENGINE fabric (IAIService) can read Pascal if given the files
          as context. What doesn't exist is the handler that:
          - accepts a zip/directory
          - extracts and sequences the right files for analysis
          - submits them to IAIService with the right extraction prompt
          - stores the output in a form later phases can query
SYMPTOM:  Operator uploads the zip. Nothing processes it. Must manually read
          the Pascal code, identify the business rules, and encode them as
          iron rules in a new flow's REFERENCE-PLAN.md. The entire value of
          automated intake is lost.
VERDICT:  BLOCKED
```

**GAP-D1: No artifact intake handler.**
XIIGen can generate from context provided in prompts. It cannot ingest
arbitrary artifacts (zip files, PDFs, codebases, system diagram diagrams, drawio files)
and produce structured representations from them. Every intake task requires
human reading and manual encoding.

## D-L2: Gap detection — PASCAL-INVOICING has no pattern match

```
INPUT:    extracted Pascal procedures, matched against existing flow patterns
          RegisterUser → the user registration flow (a task type) pattern — match found
          ProcessOrder → the business onboarding flow adjacent — partial match
          GenerateInvoice → NO MATCH
              Pascal-specific: VAT by country, partial payment tracking,
              invoice balance invariant, PDF generation
HANDLER:  NONE — no gap detection component
PRODUCES: nothing
NEEDS:    When a procedure extracts to a capability with no existing flow
          pattern, the engine should:
          (a) confirm the gap is genuine (not a labeling mismatch)
          (b) spawn a design session with the Pascal business rules as context
          (c) produce a new flow plan for PASCAL-INVOICING
          (d) continue the migration pipeline after the gap is filled
SYMPTOM:  Without gap detection, the migration either:
          (a) silently skips INVOICING — partial system delivered
          (b) throws "no matching pattern found" — entire migration halts
          Neither is acceptable. The operator has no visibility into which
          capabilities were skipped or why.
VERDICT:  SILENT_FAILURE or BLOCKED depending on error handling
```

**GAP-D2: No gap detection and design session spawning.**
Same as GAP-B1 but now in the context of migration. An unmapped capability
must trigger automatic design rather than silent skip or hard stop.

## D-L3: Cross-level constraint propagation

```
Pascal audit rule discovered at D-L1:
  PROCEDURE RegisterUser:
    WriteAuditLog('USER_CREATED', result, tenant);  (* always — no exceptions *)

This must become an iron rule for the generated the user registration flow equivalent:
  IR: "Audit log write is mandatory. Must precede queue emit (the eighth architecture DNA pattern extension)."

HANDLER:  When does this propagation happen?
          Phase A (inject): seeds fixtures. No intake from Pascal.
          Phase B (generate): reads genesis prompt. Pascal context not there.
          
          The Pascal rule was discovered at D-L1. There is no mechanism to
          carry a discovery from intake through to the iron rules of generation.
          The genesis prompt for a task type says "the eighth architecture DNA pattern: store before emit" but doesn't
          say "also: audit log write is mandatory and precedes emit" because
          that constraint came from the Pascal source, not from XIIGen's existing
          patterns.
SYMPTOM:  Generated the user registration flow equivalent passes DNA checks. Passes arbiter.
          Missing: audit log write. At runtime: user registrations proceed
          without audit entries. Compliance requirement violated silently.
VERDICT:  SILENT_FAILURE
```

**GAP-D3: No cross-level constraint propagation.**
Constraints discovered at intake (L1) have no path into generation (L3).
The phases are isolated. What one phase discovers cannot automatically become
a requirement for a downstream phase unless a human manually adds it to the
genesis prompt.

## D-L4: Documentation output

```
DESIGN:   After generating the modern system, produce documentation comparing
          old Pascal system to new SaaS: what changed, how to use new system.
HANDLER:  ai-generate.handler (exists) with documentation genesis prompt
NEEDS:    The generator needs:
          (a) The Pascal system's original structure (from D-L1 output)
          (b) The generated system's structure (from the flows that ran)
          (c) A documentation genesis prompt for this comparison format
          
          Problem (a): D-L1 output is not stored in any queryable index.
          If it was, it would be in an ad-hoc session context, lost on compaction.
          
          Problem (b): The generated flows are in TypeScript files. Extracting
          their structure requires running the same intake process (GAP-D1)
          on the generated code.
          
          Problem (c): A documentation genesis prompt exists conceptually but
          has never been authored. No documentation domain patterns are in the retrieval system.

SYMPTOM:  Documentation step cannot retrieve the Pascal intake output.
          Falls back to generating generic documentation from the genesis prompt
          alone. Produces documentation that describes the generated system
          but does not compare it to the Pascal original.
VERDICT:  PARTIAL (documentation produces, but not the right documentation)
```

**GAP-D4: Intake output is not persisted across phases.**
D-L1 produces a structured representation of the Pascal system. This should
be stored in a queryable index (a flow-scoped working memory) so later phases
can retrieve it. Currently: no such index exists. Intake output lives only in
the session context of the intake phase.

# PART 7 — RESOLUTION PHASES

## Mapping gaps to resolution phases — in dependency order

The phases below are NOT flow numbers. They are capability delivery phases.
Each phase produces capabilities that unblock the next phase.

---

### PHASE ZERO: Foundation (no simulation can progress without these)

Capabilities delivered:
- Artifact intake handler (GAP-D1)
- Task router (GAP-A1)
- Intake output persistence — flow-scoped working memory (GAP-D4)

Why these first:
Every simulation hits GAP-A1 at L1. Every simulation that requires
reading an external artifact hits GAP-D1. Nothing in Phase 1+ can
run autonomously without these.

What "artifact intake handler" means concretely:
```
POST /api/engine/intake
body: { artifact: binary|url|text, type: ZIP|PDF|URL|CODEBASE|system diagram }
produces: {
  structuredRepresentation: { structure, intent, constraints, quality },
  storedAt: "working-memory::{tenantId}::{jobId}",
  extractionConfidence: 0.0-1.0,
  humanReviewRequired: boolean
}
```
Uses IAIService internally. One endpoint. Stores output in a new
flow-scoped working memory index queryable by subsequent phases.

---

### PHASE ONE: Gap Detection + Interface Design

Depends on: Phase Zero

Capabilities delivered:
- Gap detection in decomposition (GAP-B1)
- Design session spawning when gap detected (GAP-D2)
- Automated fabric interface design from capability description (GAP-B2)
- Cross-level constraint propagation (GAP-D3)

Why in this order:
Intake (Phase Zero) produces structured representations.
Gap detection compares representations against existing patterns.
When a gap is found, a design session must be spawnable automatically.
The design session produces a fabric interface, which requires automated
interface design to be reliable.

---

### PHASE TWO: New Fabric Interfaces

Depends on: Phase One (automated interface design)

Capabilities delivered:
- IBlobStorageService (GAP-B3) — providers: S3, Azure Blob, GCS
- IConversationalChannelService (GAP-C1) — providers: WhatsApp, Slack, push
- ISchedulerService implemented (GAP-C3) — providers: Bull recurring, cron, Action Scheduler
- Platform constraint population in the retrieval system (GAP-A2, GAP-B4) — for all registered platforms

Why in this order:
These interfaces are designed using the automated interface design from Phase One.
Without Phase One, each requires a manual planning session (still possible
but not automated). Platform constraint population is also a Phase One output —
the intake handler reads SDK documentation and populates the retrieval system patterns.

---

### PHASE THREE: Execution Patterns

Depends on: Phase Two (fabric interfaces must exist to test patterns against)

Capabilities delivered:
- Fan-in / multi-result synthesis topology handler (GAP-B5)
- Iterative loop topology handler (GAP-C4)
- Adaptation delta computation (GAP-A6)

Why in this order:
Fan-in requires multi-model calls via IAIService (exists) and result storage
via the working memory index (Phase Zero). Iterative loops require fan-in.
Adaptation delta requires intake representations (Phase Zero) to exist for both
the canonical and the target.

---

### PHASE FOUR: Context and State

Depends on: Phase Three (patterns must exist before context is wired in)

Capabilities delivered:
- User state / session history store (GAP-C2)
- stackCoupling content populated (GAP-A4) — for all registered platforms
- Arbiter checks N1-N4 wired (GAP-A5) — documented in the AI agent orchestration flow v5

Why last:
These are quality-of-output improvements. The system can operate without them
(with degraded output). Phases Zero-Three are blockers. Phase Four is quality.

# PART 8 — SIMULATION PROTOCOL REUSE

## How to run a new simulation

When a new scenario needs gap analysis, follow this protocol:

```
1. NAME the scenario (one sentence, specific input + expected output)

2. IDENTIFY the levels (usually 4-6 levels from task reception to output storage)

3. FOR EACH LEVEL:
   a. Write: INPUT — exact fields, where they come from
   b. Write: HANDLER — name the actual XIIGen component (or NONE)
   c. Write: PRODUCES — what the component outputs
   d. Write: NEEDS — what is required that doesn't exist (be specific)
   e. Write: SYMPTOM — what the operator/user observes when this fails
   f. Write: VERDICT — PASS | PARTIAL | BLOCKED | SILENT_FAILURE

4. ASSIGN a GAP-ID to each NEEDS item not already in the catalog

5. CHECK the gap dependency graph — does this gap already depend on an
   existing gap? If yes, it resolves when the upstream gap resolves.
   If no, add it to the catalog as a new entry.

6. ADD to the phase plan — which phase resolves this gap?
```

SILENT_FAILURE is the priority flag. A blocked engine is visible and fixable.
A silent failure ships to production and fails in the field.
