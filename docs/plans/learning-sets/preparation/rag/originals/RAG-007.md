# 2. HOW TO SIMULATE A RUN

## The trace format

For each scenario, produce a STEP TABLE. Every row is one step the
engine must execute to complete the scenario.

```
| Step | What must happen | Handler | Input available? | Output expected | Actual result | Gap? |
|------|-----------------|---------|-------------------|-----------------|---------------|------|
```

### Column definitions

**Step:** Sequential number. Each step is one discrete action.

**What must happen:** Plain language. What the engine needs to do at
this point to make progress toward the scenario goal.

**Handler:** Which existing XIIGen handler or service would execute this.
Options:
  - ai-generate.handler (calls an AI model)
  - validate.handler (checks conditions)
  - route.handler (branches based on condition)
  - rag-retrieve.handler (retrieves from the retrieval system)
  - feedback.handler (stores results + emits events)
  - score.handler (evaluates quality)
  - [fabric interface].method (calls a fabric service)
  - HUMAN (requires human intervention)
  - NONE (no handler exists for this action)

**Input available?:** For each piece of data this step needs, mark:
  - ✅ exists and accessible
  - ⚠️ exists but not accessible to this handler
  - ❌ does not exist

**Output expected:** What this step should produce for the next step.

**Actual result:** One of:
  - WORKS — handler exists, input available, output produced correctly
  - PARTIAL — handler exists but input incomplete or output degraded
  - BREAKS — handler doesn't exist, or critical input missing
  - WRONG — handler exists and runs but produces incorrect output

**Gap?:** If BREAKS or WRONG: which gap class (A-L) and a one-line
description of what specifically is missing.

## Trace rules

1. **Start from what the engine receives.** Not from what a human
   would prepare. If the scenario requires an EngineContract and no
   EngineContract exists, Step 1 is "produce EngineContract" and it
   will break immediately.

2. **Follow the actual handler chain.** Don't skip steps. If the
   topology says rag-retrieve → ai-generate → validate → route →
   feedback, trace each one. The gap might be in retrieve, not generate.

3. **Check EVERY input.** For each step, list what data it needs.
   Mark each piece ✅/⚠️/❌. A step can break because ONE input
   is missing even if five others are present.

4. **Don't assume fixes.** If Step 3 breaks, don't assume "well if
   we fixed that, Step 4 would work." Trace Step 4 with the broken
   input from Step 3. The cascade reveals compound gaps.

5. **Trace the LEARNING path too.** After the main flow completes
   (or breaks), trace: what training data was produced? What should
   have been produced? This reveals learning gaps separately from
   execution gaps.

## Depth levels

Not every scenario needs full depth. Use these levels:

**L1 trace (decomposition only):** Trace how the task decomposes into
sub-tasks. Don't trace execution of each sub-task. Use for GROUP B
scenarios to find decomposition and orchestration gaps.

**L2 trace (execution per sub-task):** Trace the handler chain for
each sub-task. Use for GROUP A and GROUP D scenarios where the
sub-tasks are known and the question is whether execution works.

**L2-TS trace (TypeScript service trace):** Use when the relevant handler
is a TypeScript service (`BootstrapCycleRouter`, `BootstrapArbiterPanelHandler`,
`AiDrivenRetrospectiveService`, etc.) rather than a bash session step.
Read the TypeScript source directly. For each service method, trace:
  1. What parameters does it receive?
  2. What TypeScript branches fire for this input?
  3. Does the code query the graph, or apply a hardcoded decision first?
  4. What is returned — and is it the correct value?

L2-TS traces require access to `server/src/fabrics/graph/planning/` source.
They are required for all GROUP E scenarios and for any GROUP A-D scenario
where a bash trace returns PARTIAL or SILENT_FAILURE with no clear cause.

**Key signal from L2-TS:** If a service applies a hardcoded decision before
querying the graph, that is a **Class J1 gap** regardless of how correctly the
Phase A bash seeding was done. The bash layer can be perfect; the TypeScript
layer can still override it.

**L3 trace (full depth with learning):** L2 plus trace what training
data is produced and whether it's correct. Use for A1 and A3
(canonical scenarios where the learning loop matters most).

## Two execution layers — which to trace

XIIGen planning logic has two layers. Always be explicit about which you are tracing:

**BASH LAYER** (SESSION-N.md scripts): curl commands, STATE.json updates, the search index writes.
  Trace by following the session file step by step.
  Gaps found here: missing steps, wrong field names, unverified assumptions.
  Use L1 or L2 trace depth.

**TYPESCRIPT LAYER** (`server/src/fabrics/graph/planning/`):
  `BootstrapCycleRouter`, `BootstrapArbiterPanelHandler`,
  `AiDrivenRetrospectiveService`, `AiDecisionPipelineService`.
  Trace by reading the TypeScript source.
  Gaps found here: hardcoded logic blocking graph reads, missing interface
  methods, uncalled persistence paths, wrong query field types.
  Use L2-TS trace depth.

**Critical implication:** A bash script that seeds an edge correctly can
fail silently if the TypeScript handler that reads that edge has a hardcoded
override. Always run GROUP E (L2-TS traces) before GROUP A (bash traces).
A BREAKS verdict in E1 (the search index mapping) or E3 (structural override) means
the TypeScript layer is routing wrong — bash trace results are unreliable.

**L2-TS Trace Verification Table:**

Every L2-TS trace must check these TypeScript entry points. The table below
lists what to verify at each. A failing entry in this table is a J-class gap.

| Entry Point | What to Verify |
|-------------|---------------|
| `BootstrapCycleRouter.route()` | Graph query fires BEFORE hardcoded boundary check; `${archetype}:SCORE_BRACKET:MACHINE_CONSTANT_INVERSION` override consulted first |
| `BootstrapArbiterPanelHandler.assemble()` | REQUIRES_MINIMUM_ARBITER + OPTIONAL_ARBITER + PROMOTED_ARBITER edges all queried; immutable check on key_principles |
| `AiDrivenRetrospectiveService.runR1()` | Return value written to xiigen-flow-lifecycle by caller; not silently discarded |
| `AiDecisionPipelineService.route()` | ROUTING_DECISION triple produced; curriculumTier set from tierMap |
| `feedback.handler.resolveCurriculumTier()` | Every archetype string used in any FLOW-XX contract appears in tierMap with correct tier value |
| `validate.handler.NAMED_CHECKS` | Every NAMED_CHECK_* exported from any contracts file is registered as a key in NAMED_CHECKS |

# 3. HOW TO DEFINE A GAP

## Gap definition format

Every gap found by simulation uses this format:

```
GAP ID:          [letter]-[number] (letter = gap class A-L, number = sequential)
NAME:            [short descriptive name, max 8 words]
FOUND IN:        [scenario ID where this gap was first observed]
ALSO HITS:       [other scenario IDs that hit the same gap]

STEP WHERE IT BREAKS:
  Scenario [X], Step [N]:
  Handler: [which handler was expected to run]
  Input needed: [what data was required]
  Input status: [which specific piece is ❌ or ⚠️]
  What happens: [BREAKS/WRONG — one sentence]

ROOT CAUSE:      [one sentence — what doesn't exist that should]

SYMPTOM vs ROOT:
  Symptom:  [what you observe — "adapter generation fails"]
  Root:     [what's actually missing — "no external SDK documentation intake"]
  Test:     [if root is fixed, does symptom disappear? yes/no]

CATEGORY:        [which of the 4 levels is affected]
  □ TOOL         — a fabric interface or external integration is missing
  □ SKILL        — a prompt, skill, or the quality judge station criteria is missing
  □ ORCHESTRATION — the topology model can't express this pattern
  □ ARCHITECTURE — the engine's fundamental model doesn't support this

UNBLOCKS:        [which other gaps become fixable once this is resolved]
BLOCKED BY:      [which other gaps must be fixed before this one can be]

FIX CLASS:       [what kind of work fixes this]
  □ CONTENT      — write a prompt, skill, or the quality judge station criteria (no code)
  □ INTERFACE    — define a new fabric interface + provider (code, follows pattern)
  □ EXTENSION    — extend existing handler/topology model (code, modifies existing)
  □ NEW HANDLER  — new handler type needed (code, new pattern)
  □ INFRASTRUCTURE — new the search index index, new service, new external integration
```

## Rules for gap identification

1. **One gap = one root cause.** If two symptoms have the same root
   cause, they are one gap with two manifestations, not two gaps.

2. **Test the root cause.** Ask: "if this root cause is fixed, do
   ALL manifestations of this gap disappear?" If not, there are
   two gaps, not one.

3. **Distinguish TOOL from ARCHITECTURE.** A missing fabric interface
   (IMessagingService) is a TOOL gap — it follows the existing pattern.
   A missing topology construct (fan-out/fan-in) is an ARCHITECTURE
   gap — the pattern itself doesn't support it.

4. **Don't create gaps for things that are planned.** If the meta-arbitration flow
   builds IFlowLifecycleService and a gap says "lifecycle the programming interface
   doesn't exist" — that's not a gap, it's a prerequisite. A gap
   is something NO current plan addresses.

5. **Every gap must be found by simulation.** No gap should be
   "I think we might need this." Every gap must trace to a specific
   step in a specific scenario trace where the engine breaks.

6. **Systemic gap promotion.** If two or more gaps share the same
   observable root (same missing constant, same event name string,
   same field name) but appear in different files or session steps,
   promote them to a single systemic gap with a "locations" array.
   Individual gaps that are actually one systemic gap must NOT be
   counted separately in blocking gap totals. Each systemic gap
   gets one GAP ID and one root cause, with all manifestation
   locations listed.

   Example: gap number 5 and simulation gap fourteen in the business onboarding flow — a task type event name
   appeared wrong in 3 locations but was one root cause (rc 3). The
   simulation initially counted them as two gaps. After promotion:
   one systemic gap, three locations, one fix.

## Gap class definitions (from your assessment, refined)

```
CLASS A: EXTERNAL KNOWLEDGE INTAKE
  The engine cannot read external artifacts and produce structured
  understanding from them. Includes: SDK docs, the programming interface specs, codebases,
  PDF specifications, system diagram diagrams, Figma designs.

CLASS B: RECURSIVE DECOMPOSITION
  The engine cannot take a complex task and produce a sub-task graph
  with dependencies. Includes: gap detection (sub-task has no match),
  design session spawning (new capability needed).

CLASS C: ADAPTATION DELTA
  The engine cannot compute what differs between a canonical pattern
  and a new target, and apply only the delta. Results in: full rework
  or wrong copy.

CLASS D: ON-DEMAND CAPABILITY DESIGN
  When a sub-task requires a fabric interface or capability that
  doesn't exist, the engine cannot detect this and design the
  missing piece before proceeding.

CLASS E: DYNAMIC CONTEXT ASSEMBLY
  Context for logical units is static (seeded at Phase A). Many tasks
  need context assembled at runtime based on what the specific
  execution requires.

CLASS F: CROSS-LEVEL CONSTRAINT PROPAGATION
  Constraints discovered at higher decomposition levels don't
  automatically become iron rules at lower levels. Includes:
  platform constraints, user preferences, existing system constraints.

CLASS G: CONVERSATIONAL CHANNEL
  Two-way stateful communication channels (WhatsApp, Slack, push)
  require a different execution pattern than request-response or
  async queue. The engine has no concept of this.

CLASS H: DEPLOY-TEST-FEEDBACK LOOP
  The pipeline ends at "generate code." Real use cases need:
  deploy → test in target environment → observe → feed back →
  regenerate → redeploy. This loop doesn't exist.

CLASS I: MULTI-MODAL OUTPUT
  The engine generates text (TypeScript, JSON, markdown). Real use
  cases need: images, video, audio, diagrams, platform-specific
  packages, deployed services.

CLASS J: PLANNING LAYER INFRASTRUCTURE
  The planning layer components (BootstrapCycleRouter,
  BootstrapArbiterPanelHandler, AiDrivenRetrospectiveService) have
  implementation gaps that prevent graph-first decisions from working
  correctly. These gaps are invisible to code generation simulations —
  the engine still generates code, but learning data is wrong or lost.
  Found by GROUP E scenarios only.

  J1 — HARDCODED OVERRIDE: TypeScript hardcodes a routing decision
       before consulting the graph. Seeded edges are ignored for
       specific input cases.
       Example: BootstrapCycleRouter returns STOP_STRUCTURAL before
       querying archetype override edges when score < 0.50.

  J2 — MISSING INTERFACE METHOD: A fabric interface lacks a method
       required by a generated service pattern. The genesis prompt
       cannot reference a method that doesn't exist.
       Example: IScopedMemoryService lacks sortedSetAdd/RangeByScore/
       Remove for FIFO queue patterns.

  J3 — UNPERSISTED LEARNING OUTPUT: A planning service computes
       learning outputs but no caller persists them. Data exists in
       memory during execution, then is lost after Phase F completes.
       Example: AiDrivenRetrospectiveService.runR1() result not
       written to xiigen-flow-lifecycle.

  J4 — MAPPING/RETRIEVAL MISMATCH: the search index index field mapping prevents
       term queries from matching seeded documents. Index exists, edges
       are seeded, queries return zero results with no error.
       Example: fromEntity field as text-analyzed instead of keyword.
       All graph routing silently falls back to hardcoded defaults.
```

CLASS K: SESSION FILE SCHEMA DRIFT
  Session file content references fields, event names, or data structures
  that have drifted from the actual engine interface. The session file was
  correct at authoring time but the engine schema changed, or the session
  file was authored against an assumed schema that was never verified.

  K1 — DpoTriple field name drift: session file uses `chosen.code` /
       `rejected.code` but the live DpoTriple interface has top-level
       `chosen: string` / `rejected: string`. SESSION-E gap item 08 gate
       permanently fails if it queries .code subfields.

  K2 — CloudEvent name drift: session file references an event name
       (e.g. "OnboardingBroadcastCompleted") but the contract events[]
       array defines a different string (e.g. "OnboardingBroadcastSent").
       Phase B emits an event that no downstream handler recognizes.

  K3 — Fixture field name drift: session file seeding commands write
       fields that don't match the actual the search index index mapping. Documents
       are stored but never retrievable by the queries that read them.

CLASS L: ARCHETYPE REGISTRATION GAP
  A new archetype is defined in engine contracts but not registered in
  one or more of the required engine registration points. The contract
  is real; the registration is missing. Results in silent fallback
  behavior (wrong tier, no enforcement, contract bypass).

  Registration points that must ALL be updated together:

  L1 — ContractArchetype enum: new value not added → contract
       references a string that doesn't exist in the type system.
  L2 — ENGINE_CONTRACTS bootstrap array: task type entry missing →
       engine doesn't know this task type exists at bootstrap.
  L3 — feedback.handler.resolveCurriculumTier() tierMap: archetype
       missing → curriculumTier resolves to null → V9-003 violation,
       the preference learning signal triple invisible to curriculum router.
  L4 — Topology wiring: RouteHandler, fan-in aggregator, or broadcast
       dispatcher not wired → flow execution skips the task type
       entirely with no error.

## When to add a new gap class

A new class (M, N, ...) is added ONLY when a simulation finds a break
that doesn't fit any of A-L. The break must be:
- Not a symptom of an existing class
- Affecting a different architectural layer than existing classes
- Found in at least 2 scenarios (not a one-off)

Class J was added from the user registration flow simulation findings (2026-03-27).
Four GROUP E scenarios each produced a distinct J-subclass gap.

Classes K and L were added from the business onboarding flow simulation findings (2026-03-27).
K covers three sub-classes of schema drift between session files and live
interfaces. L covers four registration points that must stay synchronized
when a new archetype is introduced.

# 4. SIMULATION EXECUTION ORDER

Run simulations in this order. Each group builds on what the
previous group revealed.

```
ROUND 0: GROUP E (planning layer correctness — NEW, run first)
  Run E1 through E9 at L2-TS depth.
  These MUST pass before any GROUP A-D simulation is reliable.
  A BREAKS verdict in E1 (the search index mapping) or E3 (structural override)
  invalidates all downstream simulation results.
  E9 (infrastructure index existence) runs FIRST — before E1.
  Expected: J-class gaps (hardcoded overrides, missing interface methods,
            unpersisted outputs, the search index mapping issues).
            K-class gaps (DpoTriple field drift, CloudEvent name drift).
            L-class gaps (archetype registration missing from one or more points).
  STOP after ROUND 0 if E1, E3, or E9 show BREAKS — fix the TypeScript layer
  and infrastructure before proceeding. Running GROUP A with a broken planning
  layer or missing indices produces misleading training data.

ROUND 1: GROUP A (designed-for scenarios)
  Run A1, A2, A3, A4 at L2/L3 depth.
  These SHOULD work. Gaps found here are in the existing design.
  Expected: few gaps, mostly TOOL or CONTENT class.

ROUND 2: GROUP D (the AI agent orchestration flow deep detail)
  Run D1, D2, D3, D4 at L2 depth.
  the AI agent orchestration flow has the most detailed plan — gaps are precisely locatable.
  Expected: gaps in Classes A, C, E (external intake, adaptation, dynamic context).

ROUND 3: GROUP B simple scenarios
  Run B1, B2 at L1 depth.
  The simplest product scenarios. Find decomposition and feedback gaps.
  Expected: gaps in Classes B, E, G (decomposition, context, feedback).

ROUND 4: GROUP B complex scenarios
  Run B3, B5, B6 at L1 depth.
  Full system generation, diet app, content pipeline.
  Expected: gaps in Classes D, G, H, I (on-demand design, channels, deploy, multi-modal).

ROUND 5: GROUP C cross-cutting
  Run C1, C2, C5, C6, C7 at L2 depth.
  These are capabilities needed by multiple scenarios.
  Expected: confirms and sharpens gaps found in Rounds 1-4.

ROUND 6: Remaining scenarios
  Run B4, B7, B8, C3, C4 at L1 depth.
  Fill remaining coverage.

After each round: update the gap catalog. Check if any new class (M+)
is needed. Check if existing gaps need splitting or merging.
```
