## Что предотвращает дублирование

Каждая новая сессия получает уникальный `agent-id`; один agent ID нельзя одновременно использовать в двух окнах. `next` под короткой межпроцессной блокировкой читает общее состояние, выбирает свободный домен и сохраняет claim с token и request. Пока claim действует, другому агенту этот домен не выдаётся. Если первый профиль создаёт ещё отсутствующую общую смысловую семью, её создание также резервируется; другой профиль ждёт сохранённые факты, вместо того чтобы придумывать другой сюжет под тем же F-ID.

Генерация моделью идёт вне блокировки. `progress`, `finish`, `resume`, `release` проверяют текущие owner/token. Повторный finish идемпотентен; другая сессия не может приписать результат себе. Повторное предъявление той же полной DPO-тройки внутри домена выявляется структурным завершением. Эти меры предотвращают конкретные операционные дубли; они не доказывают смысловую новизну каждой строки.

Системная файловая блокировка освобождается при завершении процесса, но **сохранённая claim не исчезает по таймауту**. Медленная модель не считается брошенной. Восстановление идёт по exact resume владельца. Явное освобождение выполняется сохранённой owner-командой при разрешённом продолжении сессии. Ручная правка JSON, удаление lock/state или присвоение чужого token не являются процедурами восстановления.

Область защиты: процессы, использующие этот координатор и один общий data root. Старый `batches.py` и разные локальные копии не входят в неё. Legacy request продолжается отдельно последовательно; новый runner прямо возвращает `LEGACY_NOT_COORDINATED`.

## Как обновляется прогресс

1. `next` записывает владельца, allocation, request и резерв семей.
2. Автор сохраняет полные строки и запускает выданный `progress`. В матрице появляется фактическое `authoring_rows_saved`: запись имеет уникальный назначенный pair ID и непустые разные chosen/rejected при непустом prompt. Полная metadata и число строк проверяются на finish; предметное качество этот счётчик не доказывает. Квота пока не засчитывается.
3. `finish` проверяет полную назначенную партию, записывает creation и увеличивает `draft_created_pairs` один раз. Owner/семейные reservations освобождаются.
4. `next` назначает следующую партию того же пула. Рабочий статус и качество отображаются раздельно.

Показать матрицу:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:/Users/lubao/Documents/xiigen/llm mvp/learning-sets/preparation/tools/create_campaign.ps1" -Action status -WorkRoot "C:/Projects/llm_mvp_core/learning-sets"
```

Если запись `status.json` отстала после сбоя, команда status восстанавливает её из авторитетного `state.json`. Не обнуляй прогресс и не копируй [status.template.json](campaign/status.template.json) поверх живого состояния. Шаблон содержит 24 домена и 217 тем с нулевым **плановым** счётом и стартовыми замечаниями; это не наблюдение работы на пользовательском компьютере.

## Домены и темы, требующие внимания

[quality-status-seed.json](campaign/quality-status-seed.json) содержит привязанные к domain/topic/profile замечания по уже существующим коммитам. При первом чтении координатор добавляет отсутствующие flag ID, не заменяя локальный progress и уже обновлённые решения. [Отчёт](verification/COMMITTED-CORPUS-ASSESSMENT-2026-10-26.md) отделяет прочитанные текстовые материалы, LFS pointers и старые аудиты, чей SHA совпал с текущим объектом. Неизвестное качество не объявляется плохим; совпавший аудит не выдаётся за новый построчный review.

| Статус флага | Основание | Действие автора |
|---|---|---|
| `needs_rework` | Указан конкретный подтверждённый дефект и затронутая область | Избегать этого дефекта в новых строках; старую попытку не переписывать без назначения |
| `needs_assessment` | Содержание не прочитано либо проверка покрыла только часть свойств | Не утверждать acceptance; продолжать CREATE_ONLY по назначению |
| `resolved` | Есть отдельное явное предметное основание закрытия конкретного замечания | Сохранить основание; новый finish сам по себе флаг не закрывает |

Для нового наблюдаемого замечания команда `flag` принимает обязательные `-AgentId`, `-FlagId`, `-Domain`, `-QualityStatus`, `-Reason`, `-Evidence` и необязательные `-Topic`, `-Profile`; также точный `-WorkRoot`. Значения — фактический домен, objective/topic, профиль и реальная ссылка на пару/файл/отчёт, не заглушки. Это запись известного факта, не новый цикл independent review. `needs_rework` имеет приоритет при сводке; если открытых флагов нет, отображается `not_established`, а не «качество доказано».

Reason internally in English. Do not output private reasoning or a chain-of-thought transcript. Краткие статусы и итог — по-русски; учебный текст — на языке назначенного профиля. Используй текущую выбранную китайскую модель Kiro без override. Не угадывай имя или версию модели; неизвестное происхождение обозначай `unknown`.

CREATE_ONLY: реальные кандидатные DPO-пары и материал семейств. Самопроверка смысла каждой составляемой строки входит в создание. Отдельный reviewer, checksum-гейты, acceptance, export/import, обучение и production CI в эту сессию не входят. `finish` проверяет структуру и назначенный объём, но не доказывает смысловую правильность или обучение.

После успешного `finish` сразу выполни выданный `next` и продолжай до квоты своего пула, без вопроса «продолжать?». Прямой NEXT/новый ID немедленно заменяет прежнее задание: не доделывай старый отчёт, ремонт или запуск. STOP прекращает действия, включая вызов release; сохранённая claim остаётся для явно разрешённого последующего resume/release. Реальный внешний блок сообщай точно, не выдавай его за DONE.

Если инструмент реально выполняется и вернул handle, прочитай документацию доступного инструмента и используй его штатный wait/resume до terminal. Зависимое чтение выполняй после завершения записи. Пустой stdout, раннее отсутствие файла и timeout транспорта не доказывают падение. Не запускай дубликат, не создавай цикл частого опроса, не придумывай API ожидания и не заканчивай работу вместо доступного ожидания.
