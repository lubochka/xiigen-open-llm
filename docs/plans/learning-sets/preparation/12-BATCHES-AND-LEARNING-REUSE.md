Большой сет собирается из небольших партий с понятным учебным содержанием. Сначала проверяется, что модель генерирует качественные пары одной темы; затем — что конкретный Student действительно учится на них. Скорость этих двух процессов измеряется отдельно.

## Порядок работы уже определён

`index.json` — единственный источник порядка карточек. `generation-queue.json` разворачивает его в отдельные задания по профилям; `GENERATION-QUEUE.md` содержит готовую команду для каждого. Прямой ID пользователя имеет приоритет. Старые ID сохраняются, новые темы добавляются после них. Это порядок подготовки, не предписание заново исполнить завершённые опыты.

Один запуск `prepare` получает одну тему, профиль, split и назначение семей. Новые переводческие карточки начинают с 10 кандидатов; остальные — с 25. После содержательного просмотра следующие партии обычно по 25, либо меньше при ограниченном контексте. Число задаётся **до генерации** в новом request; нельзя молча обрезать готовые пары. Старые карточки с пилотом 50 сохраняют его как две партии по 25. В переводческом дополнении первый десяток входит в последующий набор: добирать фактический объём, а не дублировать его при сборке.

| Этап | Что делаем | Что реально можно заключить |
|---|---|---|
| 10 или 25 кандидатов по карточке | CODEX выбирает материал; Chinese генерирует; CODEX проверяет каждую пару | Работает ли конкретный промпт и какие ошибки даёт генератор |
| 50 принятых | Непересекающиеся партии; после стартовых 10 добрать 40, после двух полных 25 уже 50; отбраковку добрать новым request | Есть маленький проверенный корпус, но обучение ещё не доказано |
| Минимальный учебный набор | Начальное назначение 100 семейных случаев TRAIN плюс независимые DEV/EXAM; достаточность калибруется на DEV | Есть ли усвоение у выбранного Student при достаточном бюджете |
| 1000 принятых на поток | Непересекающиеся shards, повторный review каждой партии, фиксированный учебный pilot | Можно сравнить объём/состав данных при одинаковой проверке |
| Дальнейший рост | Новый назначенный объём после полезного измеренного результата | Локальное улучшение по конкретным метрикам, не автоматическое преимущество для всех доменов |

100 семей — начальное назначение, не универсальная гарантия обучения. Если выбранная модель не усваивает минимальную компетенцию на DEV, сначала подобрать достаточный бюджет/родительское состояние и сохранить его. Запрещено продолжать серию заведомо пустых 0→0 опытов ради заполнения таблицы. При этом отсутствие роста точности не отменяет полезного ускорения настоящего обучения при сохранённом ненулевом качестве.

## Что менять между версиями генератора

Изменять один фактор: например, уточнение условия, вид hard negative, долю неоднозначных контролей, семейства раскладки или число классов маршрутизатора. Сохранять старую версию промпта, source slices и raw ответы. Исправление имени/ID не считается новой смысловой задачей. Условие должно содержать факты, позволяющие CODEX решить задачу без доверия генератору.

Для каждой партии считать requested/generated/accepted/rejected/tie, уникальные семьи сценариев, частоты дефектов, длины, направления/классы, время и токены генерации, время review, принятые пары в минуту. Цена — только если известен фактический тариф. Эти показатели описывают производство данных. Они не заменяют время обновления Student, число полезных ответов и память процесса обучения.

## Общие сценарии для языков и функций

Все направления одного перевода, его опечатки/раскладки, парафразы и исходный контекст получают общий `origin_family_id`. Для нескольких тематических карточек, использующих один сценарий, нужен явный family-plan: `schemas/family-plan.example.json`. При самостоятельных новых сценариях автоматическое назначение допустимо, но скрытые смысловые повторы должен найти CODEX.

`lexical_family_id` служит другой цели: связывает канон и ошибки одного слова. Например, физическая семья שלום объединяет ввод `שלום`, допустимую опечатку и проверенное отображение клавиш, но перевод greeting/peace выбирается по контексту. Нельзя ни разделять копии одного сценария по TRAIN/EXAM, ни объединять все независимые фразы с частым словом в один огромный split-group. Для специального экзамена на неизвестные слова назначается отдельная схема.

Примеры из карточек и `reference-examples*.jsonl` открыты генератору. Они остаются reference. Нельзя получить закрытый экзамен заменой имени персонажа в этих примерах. Независимые экзаменационные семьи создаются отдельно и не показываются генератору TRAIN.

## Минимальное честное сравнение обучения

В binding конкретного run должны быть существующие entrypoint/команда, получатель, поля данных, изменяемые веса/память, путь обычного ответа, хеши B1/данных и способы ожидания. Если adapter отсутствует, сохраняется `NOT_RUN`; вымышленный CLI не пишется. Подготовка данных при этом завершима отдельно.

Сравнить before/A/B на фиксированных независимых случаях, показать правильные ответы с знаменателем, время до первого правильного результата, реальное время обновления и память, качество после reload, регрессии. Объём обработанных токенов либо wall-time — заранее выбранная ось бюджета. Точки сохранения и отбор checkpoint используют DEV, не EXAM. Успех по одной полезной метрике показывается вместе с ухудшениями остальных. Результат записывается кандидатом; перенос кода решает Люба.

## Сквозной путь от запроса к домену

В [routing-e2e-reference.jsonl](schemas/routing-e2e-reference.jsonl) даны открытые сценарии формы будущей проверки. Это **не закрытый EXAM и не измеренные результаты**. Сырой запрос передаётся обученному router; выбранный domain/profile — обученной Unit; ответ проверяется по предметной задаче.

Нужно отдельно измерять маршрут, предметный ответ при правильном известном маршруте и полный ответ с фактически выбранным маршрутом. Иначе регрессия router маскируется хорошей Unit либо наоборот. Expected route хранится у оценщика, не во входе learner. Один router учится теме маршрутизации на разных классах; его TRAIN не является смешанным обучением переводу, SQL и UI.

Атомарный OR-ROUTE-01 выбирает один маршрут или clarify. Многошаговый запрос сначала требует отдельного согласованного planner/decomposer-контракта; нельзя самовольно добавить граф вместо одного route. Порядок кандидатов, имена проектов и формулировки варьируются внутри семейства проверки. OOD/unsupported/ambiguous учитываются отдельно.

## Работа с процессом и переход к следующей теме

Перед длинным запуском прочитать фактическую схему tools и сохранить handle. При running ждать тот же handle штатным wait/resume, не завершать раунд вместо доступного ожидания, не опрашивать один тул в пустом цикле и не запускать дубль. Terminal wrapper не заменяет terminal дочернего обучения. NEXT/конкретный ID запрещает возвращаться к старой задаче; STOP прекращает новые действия. Занятый каталог не удаляется: действующий run продолжается по его состоянию; новая попытка получает следующий ID версии.
