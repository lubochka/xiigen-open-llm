# Переводы и восстановление опечаток: примеры и простая самопроверка

**Назначение:** помочь автору сразу составить содержательно правильную DPO-пару. Это дополнение к текущему заданию на создание данных; оно не добавляет независимый review, blind-проверку, checksum-гейты, обучение или production CI.

В [машиночитаемом дополнении](translation-quality-lessons-2026-10-26.json) находятся **126 открытых образцов: 84 переводческих и 42 для восстановления текста**, а также 12 коротких разборов ошибок. Они добавляют **0** пар к производственной квоте. Не копировать их, не менять только имя или число и не считать производные новым независимым материалом. В выданное задание включаются примеры только его темы и языкового профиля; не нужно читать весь сборник для одной партии.

## 1. Как использовать в текущей партии

1. Прочитать назначенные домен, профиль, микроцель, количество и следующий шаг из текущего request. Восстановление опечатки и перевод после её восстановления — разные задачи ученика.
2. Взять назначенные исходные примеры и подходящий разбор из этого дополнения. Хороший и плохой ответы показывают **один** содержательный контраст; плохой способ авторинга находится отдельно.
3. Создать новый сюжет из разрешённого материала. В prompt ученика поместить каждый факт, без которого правильный ответ нельзя выбрать: контекст значения, карту клавиш, правила буквального идентификатора или явно указанный род.
4. Написать полный `chosen`; получить правдоподобный `rejected` с одной назначенной ошибкой. Обе стороны отвечают на одну задачу в одинаковом формате.
5. Во время написания выполнить короткую проверку ниже. Это часть составления примера. Сохранить пары в пути выданного request, выполнить его `finish` и сразу перейти к его `next`.
6. Продолжать до назначенной квоты. Прямой `NEXT` меняет текущую задачу; предыдущий отчёт больше не дописывается. Прямой `STOP` прекращает действия. Реальную недоступность входного материала нельзя скрывать выдуманными данными или статусом «готово».

**Language rule:** Use English for internal reasoning. Do not output private reasoning or a chain-of-thought transcript. Public checks are short, verifiable facts. Give progress in Russian; learner text follows the assigned profile. Use the Chinese model currently selected in Kiro without a model override.

## 2. Удаление: сравнить длину, затем воспроизвести операцию

| Ситуация | Правильное чтение | Простой способ проверки |
|---|---|---|
| `письмо → писмо` | Удаление `ь` с индексом 3, считая с нуля. | 6 → 5 code points; вставка `ь` обратно восстанавливает точное слово. |
| `письмо → пильмо` | Замена `с` на `л`, а не удаление. | 6 → 6; отличаются символы на позиции 2. |
| `market → maket`, указан индекс 3 | Удаление действительно было, но индекс неверен. | Удаление позиции 3 даёт `maret`; позиция 2 даёт `maket`. |
| `letter → leter`, указан индекс 2 **или** 3 | Оба индекса допустимы: удаляются одинаковые соседние `t`. | Оба действия дают ту же строку. Не требовать единственности индекса. |
| `Окно → Кно` | Кроме удаления изменён регистр. | Удаление позиции 0 даёт `кно`, а не `Кно`. |

Одного правила «на одну букву меньше» недостаточно. Оно ловит замену вместо удаления, но пропускает неверный индекс, изменение регистра и лишние правки соседних слов.

### Полное предложение важнее словарной формы

Хорошая конструкция:

- исходник: `Она взяла ручку.`;
- точная форма в исходнике: `ручку`;
- переставить соседние позиции 2 и 3: `рукчу`;
- повреждённый исходник: `Она взяла рукчу.`;
- обратная перестановка возвращает **всё** исходное предложение.

Плохая конструкция: взять лемму `ручка`, получить `рукча`, затем написать `Она взяла рукча.`. Сам обмен букв выполнен, но он не воспроизводит назначенную словоформу. Понадобилось бы ещё исправлять окончание.

**Небольшая проверка автора:** восстановить выделенный участок и сравнить всю строку с первоначальной. Вне выбранного вхождения должны сохраниться пробелы, регистр, артикли, окончания, предлоги и пунктуация. Если одинаковое слово встречается дважды, явно указать нужное вхождение; не заменять все совпадения сразу.

## 3. Различать виды повреждения

| Микроцель | Что должно быть верно | Что не подходит |
|---|---|---|
| Удаление одного code point | Длина уменьшена на 1; удаление указанной позиции даёт raw. | Замена при прежней длине. |
| Вставка одного code point | Длина увеличена на 1; удаление добавленной позиции возвращает canonical. | Добавление двух букв, даже если получилось привычное слово. |
| Замена одного code point | Длина прежняя; ровно одна позиция отличается. | Удаление плюс вставка со сдвигом остальной строки. |
| Перестановка соседних букв | Длина и состав прежние; обмен **двух соседних разных** символов даёт raw. | Несоседний обмен; обмен двух одинаковых букв, после которого строка не меняется. |
| Неверная раскладка | Весь выбранный фрагмент точно декодируется напечатанной картой. | Догадка по похожему виду слова; перестановка букв без соответствия карте. |
| Сохранение правильного слова | Вход уже правильный, никакое повреждение не назначено. | Создание «половины исправлений» из раздела с контрпримерами. |

Нельзя менять операцию в metadata, чтобы задним числом оправдать случайно написанный raw. Сначала задаётся микроцель, затем из точной формы строится её повреждение.

### Иврит и Unicode

В этом дополнении механические примеры используют **неогласованный иврит** и явно считают Unicode code points. Например, `שלם` содержит 3 code points, а `שָׁלֵם` — 6: три буквы и три комбинируемых знака. Количество видимых букв, UTF-8 bytes и code points — разные величины.

Не удалять огласовки, не менять конечные формы и не нормализовать Unicode незаметно. Для таких операций требуется назначенное правило. Простое `string.Length` в C# также нельзя автоматически приравнивать к количеству Unicode code points для произвольного текста за пределами BMP. У этих коротких буквенных примеров такой проблемы нет; будущий пример с emoji требует отдельного соглашения.

Хранить иврит в логическом порядке символов. Направление отображения не разрешает переворачивать строку.

## 4. Раскладка: карта видна ученику и действует только на выбранный фрагмент

[Локальная карта клавиш](../domains/translation/layout-fixture-v1.json) — учебная фикстура без Shift, CapsLock, dead keys и обещаний о любых мобильных клавиатурах. Её имя для иврита — `he-fixture`; не выдавать её за проверенный драйвер конкретной ОС.

Показательный пример:

```json
{
  "raw": "vnf,c",
  "canonical": "המכתב",
  "raw_to_canonical": {
    "v": "ה",
    "n": "מ",
    "f": "כ",
    ",": "ת",
    "c": "ב"
  }
}
```

Запятая внутри `vnf,c` — вход карты для буквы `ת`. Если удалить её как «пунктуацию», восстановление испортится. Проверка: прочитать все пять символов по порядку, получить `המכתב`, затем по обратной карте получить те же `vnf,c`.

**Другой контекст — другое разрешение.** В `Открой файл jryj.txt.` имя объявлено буквальным. Хотя `jryj` декодируется как `окно`, правильный результат нормализации сохраняет `jryj.txt`. Возможность преобразовать строку ещё не означает, что это нужно делать.

Не давать карту только в metadata: у ученика должен быть вход, достаточный для ответа. Не объяснять результат раскладки только тем, что контекст уже прямо называет предмет; проверка карты остаётся отдельным свидетельством.

## 5. Проверить факты всего перевода

Проверка выполняется после восстановления слова. Успешное восстановление не оправдывает изменения остальной фразы.

| Что сверить | Хороший контраст | Простая проверка |
|---|---|---|
| Кто действует и на кого | `Maya thanked David.` / `David thanked Maya.` | Записать две роли: благодарит Майя, благодарят Давида. Наличие тех же имён недостаточно. |
| Явно указанный род | `She is ready.` / `He is ready.` | Сохранить референта и согласование; не угадывать пол по профессии. |
| Владелец | `Her umbrella is here.` / `His umbrella is here.` | «Чей зонт?» Род предмета не определяет пол владельца. |
| Область отрицания | `Not all doors are locked.` / `No doors are locked.` | Две двери: одна заперта, другая нет. Первая фраза истинна, вторая ложна. |
| Состояние действия | `She has already repaired the lock.` / `She is still repairing the lock.` | Ремонт уже завершён или ещё идёт? |
| Порядок событий | `After the backup finished...` / `Before the backup finished...` | Что раньше: завершение копирования или удаление? |
| Разрешение и обязанность | `She may enter...` / `She must enter...` | Допустимо ли не входить? Контекст разрешения должен быть виден. |
| Числа с единицами | 3 бутылки **по** 250 мл / 3 бутылки **всего** на 250 мл | В первом случае общий объём 750 мл. Сам набор цифр не отличает ответы. |
| Идентификатор | `Report_Q4.csv` / `report_q4.csv` | Посимвольное совпадение имени; регистр и подчёркивание сохраняются. |

Не добавлять «главный», «новый», «настоящий» или другие уточнения, которых нет в исходнике и разрешённом контексте. Если перевод выбранного слова исправлен, но владелец стал другим, пара по-прежнему ошибочна.

Для неоднозначного источника не выбирать смысл из скрытой metadata. Либо в prompt уже есть различающий контекст, либо выполняется назначенный режим уточнения. Если цель — только исправление орфографии и правильное написание не зависит от смысла, уточнение значения не требуется.

## 6. Отдельный домен: восстановление исходного текста

Переводчик выдаёт текст на **целевом** языке. Нормализатор опечаток выдаёт исходный текст на **том же** языке, сохраняя все неповреждённые части. Это не новая квота на каждый язык: квота принадлежит выделенному домену, а языковые доли указаны в реестре.

Для нормализатора установлен один короткий контракт:

```json
{"action":"restore","text":"Она взяла ручку.","question":""}
```

- `restore`: единственное оправданное исправление применено; вопрос пуст.
- `preserve`: исходный текст сохранён совершенно точно; вопрос пуст.
- `clarify`: исходный текст сохранён; в вопросе на исходном языке названы неразличимые по контексту варианты.

Внутри JSON не должно быть объяснения способа генерации DPO, плана работы или private reasoning.

### Хорошее и плохое восстановление

Вход ученика сообщает одну соседнюю перестановку в названии письменной ручки:

```text
Она взяла рукчу.
```

Хорошо:

```json
{"action":"restore","text":"Она взяла ручку.","question":""}
```

Плохо:

```json
{"action":"restore","text":"Она взяла рукчу.","question":""}
```

Оба ответа одного формата. Ошибка второй стороны состоит в том, что объявленное восстановление не выполнено.

### Хорошее и плохое сохранение

Вход объявляет `form_id` точным идентификатором:

```text
Set form_id to 7.
```

Хорошо:

```json
{"action":"preserve","text":"Set form_id to 7.","question":""}
```

Плохо:

```json
{"action":"restore","text":"Set from_id to 7.","question":""}
```

Слова `form` и `from` похожи, но перестановка внутри идентификатора не разрешена.

### Хорошее и плохое уточнение

Вход: `She saw the bat.`. Условие сообщает ровно одну заменённую букву в `bat`; допустимые исходные слова — `cat` и `rat`. Другого контекста нет.

Хорошо:

```json
{"action":"clarify","text":"She saw the bat.","question":"Did she see a cat or a rat?"}
```

Плохо:

```json
{"action":"restore","text":"She saw the cat.","question":""}
```

Оба варианта исходного слова требуют одной замены и подходят к предложению. Выбор `cat` без контекста — догадка. Правильный ответ не должен выдавать её за восстановленный оригинал.

В JSON-дополнении есть **по два примера для каждого из семи узких заданий на каждом из трёх языков**: удаление, замена, соседняя перестановка, вставка, раскладка, сохранение, неоднозначность. Раздел сохранения содержит два явно обозначенных класса — правильное слово и буквальный идентификатор. Их квоты назначает request; наличие двух примеров не создаёт автоматической пропорции 50/50.

## 7. Семьи: один сюжет не равен одному номеру

У одного конверта под одной тетрадью есть согласованные EN/RU/HE тексты. Все шесть направлений относятся к одной **смысловой семье** этого сюжета и сохраняют её split.

Лексические семьи различаются по языку и смыслу:

```text
lex:en:envelope:postal_container
lex:ru:конверт:postal_container
lex:he:מעטפה:postal_container
```

Опечатка и неверная раскладка конкретной лексемы остаются в её лексической семье. Падежная форма и артикль сохраняются отдельно как точная форма из предложения. Служебный номер строки не доказывает ни общего сюжета, ни лексического родства.

Плохо: один origin у «окно открыто» и «хлеб на полке» только потому, что оба примера первые в файлах. Плохо также объявить перевод исходника новым независимым EXAM-примером. Новый ID не устраняет происхождение.

Метаданные семьи сами по себе не учат исправлять опечатку. Ученик должен действительно видеть повреждённый текст в prompt, а предпочтительная сторона — выполнять нужное восстановление или перевод.
