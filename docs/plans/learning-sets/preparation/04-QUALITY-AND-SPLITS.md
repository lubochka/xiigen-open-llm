# Качество данных и независимость проверки

> **Текущее поручение — CREATE_ONLY.** Смысловые требования к содержимому и семействам используются при авторинге. Процедуры отдельного review/oracle/приёмки/обучения ниже сейчас не запускаются и не блокируют создание. После записи draft текущий координатор выполняет выданный finish; результат сохраняется по `paths.creation_report` (в D1000 — `creation.json`), затем выполняется выданный next. Файл `report.creation.md` относится к прежнему batch-runner и не является обязательным результатом нового координатора. Полный договор: [20](20-CREATE-ONLY-AND-PATHS.md); схема строки: [dpo-candidate.schema.json](schemas/dpo-candidate.schema.json).

> Новая доменная кампания использует [17: контракт](17-CURRENT-PREPARATION-CONTRACT.md), [18: команды](18-BATCH-RUNBOOK.md) и `tools/create_campaign.ps1`/`campaign.py`. `tools/batches.py` обслуживает отдельно выбранные legacy requests и описанные ниже прежние процедуры приёмки. Обязательные hashes/profile receipts из прежних описаний не применяются к созданию; содержательное качество и native-контракт не ослабляются. Ниже сохранена предметная методика и явно оговорённая история. Упоминание `batches.py accept/export` не означает проверенной совместимости приёмки с новым `xiigen.domain-campaign-request.v1`.

## Прямой аудит пользователя и простая помощь автору

CREATE_ONLY задаёт границу действий **генератора**. Прямое поручение пользователя проверить уже созданные draft разрешает аудитору читать их и описывать дефекты сейчас. [Аудит25октября](24-GENERATOR-OUTPUT-AUDIT-2026-10-25.md) — открытая проверка с видимыми chosen/rejected и metadata: она не является blind-review и сама не выполняет accept, export, oracle или обучение. Это не новая стадия в очереди генератора.

Помощь автору — [хорошие и плохие примеры с простым счётом](prompts/TYPO-AUTHORING-EXAMPLES-RU.md) и [адресные примеры 26 октября](prompts/AUTHORING-SELF-CHECKS-2026-10-26.md). Например, `письмо` содержит 6 code points; удаление `ь` даёт `писмо` из 5. `пильмо` всё ещё содержит 6 и потому не является удалением. Затем верни ровно удалённый символ на его место: должны восстановиться исходное слово и регистр. Одна длина не обнаружит неверный индекс или дополнительную перестановку. Это самопроверка при авторинге, без отдельного отчёта, нового процесса или review-гейта; полной смысловой гарантии она не даёт.

## Уточнения 25.10.2026

Один objective не означает один класс. Вопрос/прямой перевод — классы одного TR10-CONDITIONAL; они сбалансированы 50:50 в каждой семье и партии. Разные routes и clarify — классы OR-ROUTE-INTENT. Guarded UPDATE и COUNT — разные навыки: они остаются раздельными.

`tools/sets.py` теперь отклоняет известные публичные семьи/точные prompts в DEV/EXAM, duplicate JSON keys, non-finite числа, неподтверждённые review и смешение objective. Код не схлопывает значимые пробелы. Эти проверки влияют на допуск реального входа обучения; они не объявлены измерениями обучения. Подмена family ID без анализа происхождения остаётся запрещённой, даже если автоматическая проверка не нашла совпадения.

При отдельно назначенной batch-приёмке языковое/исполняемое evidence относится к конкретным pair_id и проверяемой версии blind по [BATCH-REVIEW](prompts/BATCH-REVIEW-PROMPT-RU.md) и [02](02-DATA-CONTRACT.md). Нужны `status=completed`, method, detail_ru и предметный kind; `NOT_RUN` и отсутствующий flag не становятся PASS. Translation требует bilingual_review, code.* — execution. Для docs.* source_grounded допустим только у неисполняемого факта при depends_on_execution=false и назначенных source_refs; поведение/API/SQL/Angular или назначенный executable_oracle требуют execution с реальным результатом и существующими raw artifacts. Проверка JSON не распознаёт смысл сама; общий числовой self-score этого не заменяет. Эти будущие условия приёмки не запускаются генератором CREATE_ONLY.

## Что проверять до масштабирования

Хорошая DPO-пара требует ответа на четыре вопроса: хватает ли информации в условии; действительно ли chosen верен; действительно ли rejected хуже; ясно ли, какая одна ошибка делает его хуже. Синтаксическая валидность JSON не отвечает на эти вопросы.

| Проверка | Принять | Переработать / удержать вне TRAIN |
|---|---|---|
| Содержательный контраст | Отрицание, роль, зависимость, побочный эффект, версия или другое наблюдаемое различие | Два синонима, вкус проверяющего, искусственный бессмысленный ответ |
| Условие | Все нужные факты видны и обе стороны решают одну задачу | Скрытый callee, неизвестный диалект, неуказанный род, выдуманное свойство API |
| Отрицательная сторона | Естественный полный ответ с одной ошибкой | `[WRONG]`, объяснение плохого ответа вместо ответа, ошибка во всех местах |
| Язык | Правильный целевой язык и согласование с заданным контекстом | Невозможность проверить иврит, неразрешённая двусмысленность |
| Код/SQL | Заданный контракт выполняется на позитивных и граничных входах | Только компиляция без поведения, фиктивный тест, несовместимый диалект |
| Домен | Одна предметная тема и один профиль в пакете | Учить перевод и SQL в одной Unit под видом разнообразия |
| Маршрутизация | Все примеры учат выбору маршрута, включая отрицательные/неподдерживаемые входы | Одноклассовый TRAIN без основания для отказа, path/ID как ответный сигнал |
| Происхождение | Снимок проекта либо честно помеченная симуляция | Синтетика названа реальным проектом, старый `train_ready` принят без проверки |

Сильный контраст может отличаться одним словом и иметь высокое лексическое пересечение. Универсального запрета overlap>0.60 нет. Но механическое добавление «не» не гарантирует ни естественности, ни истинности: доказательство должно следовать из исходного смысла.

## Семейное разделение

TRAIN меняет состояние; DEV настраивает бюджет/температуру/порог/выбор состояния; EXAM используется один раз после фиксации решения. `reference` — публичные примеры автора; они не превращаются в закрытый экзамен. Исходный пример и все производные держатся в одном split. Это касается:

- переводов в обе стороны и через третий язык;
- опечаток, ошибочной раскладки и обратимого восстановления;
- одного исходного метода, его doc/code задач и переименованных копий;
- одного проектного сценария в разных подклассах оркестрации;
- вариантов порядка кандидатов маршрутизатора.

В текущей D1000 все назначенные строки имеют `split=train`: `campaign.py` задаёт это в request и проверяет при finish. DEV/EXAM эта кампания не создаёт. Распределение SHA-256 80/10/10 относится к прежней дорожке `sets.py`, а не к фактическому составу D1000; нельзя переносить уже увиденные TRAIN-семьи в EXAM ради получения пропорции. Для будущего отдельно назначенного DEV/EXAM сначала задаются новые, не показанные автору TRAIN семьи. Повторное использование смысловых семей под новым ID выявляется отдельной проверкой происхождения и near-duplicate review; один хеш строки этого не решает.

Не менять split после просмотра результатов. Не выбирать лучший checkpoint по EXAM. Если экзамен был показан генератору обучения или использован для настройки — отметить в отчёте `EXAM_CONTAMINATED`, считать его результат свидетельством разработки и назначить новые семейства для закрытого EXAM. Старый файл и результат сохраняются: не переписывать split внутри принятого shard. При сборке следующего снимка исключить загрязнённый экзаменационный shard из списка закрытой проверки.

### Семья токенов и семья сценариев

Каноническое слово, его опечатки и неверная раскладка имеют одну `lexical_family_id`. Значения различаются `sense_id`/контекстом, исходная строка сохраняется. Но все независимые предложения с этим словом не объединяются автоматически в один `family_id`: иначе частые слова связали бы почти весь корпус. Split объединяет производные одного исходного сценария. Для отдельной проверки новых слов CODEX заранее назначает split по лексемам и явно называет эту цель.

Нормализация не должна превращать имя переменной, SQL-идентификатор или намеренно иноязычный фрагмент в другое слово. Семья задаёт связь примеров для обучения, а не обязательную замену текста или равенство векторов. Проверяются clean/noisy/control группы; ambiguous случай требует контекста, не исправления по одному словарю.

## Неизменяемые части и версии набора

Новая дорожка принимает полную проверенную партию через `tools/batches.py accept`; предыдущие accepted-файлы явно передаются через `--against`. Сохраняются ссылки на исходные тексты, request и отдельное review. Старые строки не подаются снова как новые кандидаты: это создаст дубликаты и ошибочно увеличит их учебный вес. Исторические merge/catalog команды относятся к sets.py.

Для роста корпуса перечислить принятые партии одной темы/профиля и одной микроцели в `tools/batches.py export --inputs …`. Выбранные строки входят в снимок один раз; старый полный снимок не склеивается с уже включёнными в него партиями. Квоты задают execution-queue и scale-plan; checksum и старый compose не обязательны. Предыдущие снимки, исходные партии и review сохраняются. Точные команды — в [18](18-BATCH-RUNBOOK.md).

При сравнении размеров TRAIN сохранять один назначенный независимый DEV/EXAM с фактическими текстами и версией. Если меняется и состав проверки, назвать это отдельным фактором; не приписывать разницу одному лишь объёму обучения. Количество подготовленных строк само по себе не означает полезного изменения обучения; нужен отдельный валидный урок.

## Сбалансированность внутри темы

Классы и отрицательные контроли допустимы внутри одной темы. Для оркестрационного маршрутизатора тема — выбор маршрута: строки про перевод, SQL и неподдерживаемую задачу не обучают эти предметы. Для translation Unit материал других задач в TRAIN запрещён. Контроль отсутствия эффекта на других доменах проводится через отдельные экзамены, а не перемешивание учебных наборов.

Для каждой темы публиковать counts по положительным/отрицательным случаям, сложности, длине, ошибкам, направлению, семействам и источникам. Для routing включить supported, unsupported, ambiguous и конфликтные ограничения; назначить квоты до измерения. В атомарной OR-ROUTE-01 запрос, требующий нескольких предметных действий без одного определённого маршрута, служит контролем `clarify`: карточка не должна внезапно обучать графу шагов. Обучение многошаговой декомпозиции требует отдельной темы со своим входом и выходом, как указано в [05](05-LEARNING-AND-CHECKPOINTS.md). One-class TRAIN допускается только отдельной явно названной гипотезой, не как универсальный материал.

## Объективные проверки

Для C#/Angular фиксируется точная версия среды и видимый контракт. Для SQL фиксируются диалект и данные, включая NULL, дубликаты, отсутствие совпадения, пустую таблицу и нарушение транзакции. Выполнить chosen и rejected на одинаковых входах: ожидаемый контраст должен проявиться, а различия вне цели записываются. Документация проверяется по видимому code/call graph, а не по совпадению с формулировкой эталона. Перевод допускает эквивалентные варианты и проверяет смысл/отрицание/участников/числа; exact string match не единственный критерий.

Слепой review выполняет отдельная сессия проверяющего в её текущем профиле либо человек; наблюдаемая модель и метод записываются по BATCH-REVIEW, без требования определённого имени модели. Он уменьшает подсказку ярлыком, но не гарантирует отсутствия общих ошибок моделей; самопроверка китайского генератора его не заменяет. Показывать метод проверки. Для Hebrew морфологии/неоднозначных форм не назначать уверенность из воздуха; оставить `needs_language_review`, до приёмки не использовать. Не заменять содержательную проверку общим числовым score без rubric.

## Что считается успехом

Любое **измеренное** улучшение полезного показателя на валидном учебном опыте — успех по этому показателю, теме и профилю. Рост точности не обязателен. Например, одинаковое ненулевое качество при меньшем времени обучения — полезное улучшение. Рядом обязательны изменения остальных показателей и регрессии. Небольшой выигрыш на одном прогоне — наблюдаемый результат с неопределённостью, а не доказанная универсальная причина.

`0 правильных до → 0 после`, сдвиг loss/margin, прирост числа файлов, статическая проверка и запуск без урока не доказывают улучшения обучения. Если все содержательные ответы нулевые — `LEARNING_NOT_DEMONSTRATED`, а не скрытый успех от тысячных margin. Для вычислительной оптимизации необходим действительный ненулевой учебный результат в обоих сравниваемых плечах и измерение именно участвующего в обучении пути.
