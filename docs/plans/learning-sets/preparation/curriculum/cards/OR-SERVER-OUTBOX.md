## 5. Оси генерации и содержательная проверка

- **transaction:** not_started; in_progress; committed; aborted.
- **delivery:** not_sent; ack_unknown; broker_ack.
- **owner:** self; other.

В первой партии должны присутствовать все релевантные состояния из этих осей и близкие контроли с противоположным действием. Не требуется механическое равенство всех комбинаций; фактическое распределение классов записать в отчёте. Если целый класс отсутствует, не объявлять pilot содержательно полным.

- Commit состояния и ACK доставки различаются; ACK не выдан за успешную обработку потребителем.
- Повтор E сохраняет event_id; новая бизнес-операция не маскируется как retry.
- Наличие outbox не объявлено доказательством exactly-once или измеренного выигрыша обучения.
- Один решающий дефект; выбранный ответ следует из видимого prompt, а не из скрытых метаданных.
- Есть близкий контроль с обратным решением; нельзя выигрывать постоянным ожиданием, отказом или одним классом.
- Контрпример не выдан за новую измеренную строку и остаётся в семье исходного сценария.
- Набор не подменяет обучение роутингу предметным ответом и наоборот.

Не смешивать:

- Не смешивать с уроками SQL, настройкой брокера или реализацией клиента.
- Не обучать учебную модель скрытому детерминистическому правилу через metadata: контракт виден в prompt.

Невалидны два одинаково допустимых ответа, потеря решающего контекста, альтернативы с разными заданиями и отрицательный ответ с несколькими независимыми дефектами. Сохранить причину карантина; новая версия получает новый ID и `derived_from`.

## 6. Шесть полных reference-примеров

Ответы ученика не содержат рационализацию выбора. Объяснение и контрпример ниже предназначены автору и проверяющему. Контрпример принадлежит тому же открытому семейству и не может стать независимым EXAM.

### Пример 1: OR-SERVER-OUTBOX-REF-01

Семейство: `v3-ref.or-server-outbox.f01`.

**Вход:**

```text
Симуляция сервера. Нужно сохранить заказ D и сообщить событие E. Контракт: транзакция commit_document_and_outbox атомарно сохраняет D и pending-запись E; relay может публиковать E только после commit. Ни D, ни E ещё не сохранены. publish_first отправляет E до commit. Выбери JSON next_action из commit_document_and_outbox, publish_first.
```

**Предпочтительный ответ:**

```json
{
  "next_action": "commit_document_and_outbox"
}
```

**Правдоподобный ошибочный ответ:**

```json
{
  "next_action": "publish_first"
}
```

**Различающий факт:** Условие требует наличия устойчивого состояния до внешнего события; выбранная транзакция обеспечивает именно явно заданную атомарность.

**Контрпример / граница:** Если D и pending E уже подтверждённо committed, следующим действием может быть dispatch_outbox, а повторный commit не нужен.

### Пример 2: OR-SERVER-OUTBOX-REF-02

Семейство: `v3-ref.or-server-outbox.f02`.

**Вход:**

```text
Симуляция сервера. Транзакция D+outbox E вернула aborted; по контракту обе записи отсутствуют. Публикация допустима только по committed outbox. record_failure сохраняет terminal-ошибку попытки без публикации; dispatch_event публикует E сейчас. Повторный запуск этой попытки не разрешён. Верни JSON next_action.
```

**Предпочтительный ответ:**

```json
{
  "next_action": "record_failure"
}
```

**Правдоподобный ошибочный ответ:**

```json

```

**Различающий факт:** Aborted не оставляет committed-основания для события; событие не должно сообщать о несохранённом заказе.

**Контрпример / граница:** При подтверждённом commit и pending E публикация становится разрешённой.
