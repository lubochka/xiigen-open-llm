1. Background: What the Orchestrator Is and Why Phase Transitions Matter

1.1 The Nine-Node Pipeline

The LlmFromScratch project implements a dynamic-flow orchestration pipeline in pure C# without any external ML frameworks. The pipeline is a nine-node sequence that processes one source packet — a structured problem description — into a human-readable result.

The nine nodes are:

Node Role
Node 1 Domain Splitter: breaks the source packet into domain-tagged fragments
Node 2 Domain Translator: converts each fragment into a formal domain statement
Node 3 Scheme Planner: produces a step-by-step plan for the domain statement
Node 4 Domain Processor: executes each plan step
Node 5 Applier: applies the processed plan to produce concrete results
Node 6 Result Translator: converts formal results into natural language
Node 7 Arbiter Selector: chooses which review units should fire
Node 8 Arbiter Units: review results and produce accept/concern/reject verdicts
Node 9 Formatter: assembles the final human-readable output

The critical technical foundation is that the system does not process words directly. Every input passes through a semantic compiler that maps text to a 22-slot predicate vector. The 22 predicates are a fixed vocabulary:

NULL_GUARD   FAIL        ITERATE     HANDLE_ERROR  AWAIT
THROW        DECLARE     ASSIGN      CREATE        CALL
BRANCH       RETURN      GET_OP      VALIDATE_OP   CREATE_OP
UPDATE_OP    DELETE_OP   PROCESS_OP  CONVERT_OP    SEND_OP
LOG_OP       AUTH_OP

These predicates are the fixed contract between all units in the system. Domain labels (such as database-query-efficiency or api-contract) are attached to predicate vectors as metadata. Phase signatures (such as Phase 3 — Technical Design) are learned statistical patterns over predicate vectors, not fixed code structures.

1.2 Why Phase Transitions Are Needed

As of the start of the T34 experiment, the nine-node pipeline could process one source packet in isolation. It did not know that its output would become the input for a downstream phase of development work. It did not carry decisions, constraints, or knowledge gaps forward from one phase to the next.

A real development lifecycle has seven phases: UI/UX Definition, Functional Specification, Technical Design, Implementation, Testing, QA, and QA Automation. Each phase produces decisions that the next phase must respect. If the Technical Design phase decides that all services must inherit from BaseService, the Implementation phase must know about that decision and either enforce it or explicitly name it as an uncovered gap.

The experiments described in this report build and prove the mechanisms that allow the system to carry phase context forward and verify that downstream phases are consistent with what upstream phases decided.

Three structures need to be added to the architecture for this to work. They sit above and beside the nine-node pipeline:

  1. The Phase Context Packet — a structured artifact that every completed phase produces, capturing its decisions, inherited constraints, knowledge edges (named gaps), boundary markers, and rejected items.

  2. The Transition Gate — a verification unit that runs between two phases and checks whether the downstream phase's source packet is consistent with the upstream phase's context packet.

  3. The Phase Registry — a versioned topology that maps phase nodes, transition edges, continuity thresholds, and conformance tests. This is stored as data, not code, so that methodology changes do not require rebuilding the system.

2. T34 Experiment — Phase 3 to Phase 4 Transition Gate

2.1 What T34 Was Trying to Prove

T34 (code phase 24, experiment identifier T34-PHASE-3-TO-4-TRANSITION-GATE) was the first concrete test of the transition gate concept. It asked one specific question: given a real Phase 3 Technical Design context packet and a real Phase 4 Implementation source packet, does the transition gate correctly identify what was preserved, what was left as a named gap, and what was safe to pass despite appearing superficially problematic?

The Phase 3 source was the existing XIIGEN dynamic-flow architecture documents: - DYNAMIC-FLOW-ARCHITECTURE-PLAN-v1_0-DRAFT.md - DYNAMIC-FLOW-HIGH-LEVEL-DESIGN-AMENDMENT-v1.md - DECISIONS-LOCKED.md

The Phase 4 source was an existing implementation plan: - AUTONOMOUS-LEARNING-SESSION-PLAN-v1.0.md

The implementation plan described an eight-step autonomous learning cycle for the 16.AutonomousLearning project component.

Three specific scenarios were designed to test the gate's judgment:

Scenario T34-1: Stated-but-unenforced constraint. The Phase 3 design requires that all production services inherit from BaseService. The Phase 4 plan mentions BaseService in its dependency map but does not include a Gate B check or test assertion that would catch a service that omits the inheritance. Expected verdict: CONCERN (not BLOCK — the phase can proceed with this named gap, but the gap must be resolved before the phase output is accepted).

Scenario T34-2: Absent knowledge-edge acknowledgment. The Phase 3 design introduces a cross-phase context packet mechanism for carrying decisions between phases. This mechanism is not yet implemented. The Phase 4 plan does not mention this gap explicitly — it neither implements it nor marks it as out of scope. Expected verdict: CONCERN (the local component can proceed, but the plan must explicitly mark the gap as out of scope so it does not silently disappear).

Scenario T34-3: Superficial resemblance to a rejected item. The Phase 4 plan lists a fixed five-step implementation sequence (Phase 1 through Phase 5 build steps). The Phase 3 design explicitly rejected a static runtime pipeline as an architectural shape. A naive checker would flag the fixed sequence as reinstating the rejected item. Expected verdict: PASS — the fixed sequence is build-time implementation order, not runtime execution topology. Artifact types are different.

2.2 T34 Round A — Oracle Documents

Round A produced five oracle documents that defined the experiment before any code was written. These documents are the authority; the code must match them, not the other way around.

T34-SOURCE-BINDING-v1.md defined the upstream and downstream source documents and produced a complete upstream context packet. The context packet contained:

  • 6 decisions made (DCTX-01 through DCTX-06), including the locked decisions that the pipeline graph is data not code, that internal LLMs run before any external AI, and that arbiters are the hard acceptance boundary.
  • 7 constraints inherited (CSTR-01 through CSTR-07), including no external ML frameworks, StackDetector before normalization, StratifiedSplit for splits, the D-09 weight formula, and BaseService-style service inheritance.
  • 3 knowledge edges (KEDGE-01 through KEDGE-03), including the cross-phase context packet mechanism not yet implemented and the swappability judge not yet trained.
  • 2 boundary markers (BND-01, BND-02).
  • 4 rejected items (REJ-01 through REJ-04), including the static runtime pipeline as an architecture shape and external AI as ordinary control-path authority.

T34-TRANSITION-DOMAIN-MAP-v1.md defined the formal vocabulary for the four transition domains: constraint preservation, decision acknowledgment, knowledge edge continuity, and rejection preservation. For each domain it specified the formal statement shape, the key vocabulary, and the required phrasing for each of the three T34 scenarios.

T34-TRANSITION-FAILURE-TAXONOMY-v1.md defined six failure types (F1 through F6) with their observable signals and correct verdicts. The taxonomy established the critical distinction: F2 (stated but unenforced) produces CONCERN, not BLOCK. F3 (absent knowledge edge acknowledgment) produces CONCERN. F6 (superficial reinstatement with different artifact type) produces PASS.

T34-TRANSITION-HUMAN-RESULT-STANDARDS-v1.md defined what a technical lead must be able to read in the final human result: the transition verdict must be PASS WITH GAPS, five preserved constraints must be named, each concern must have a concrete remediation, and the build-time sequence must be explicitly distinguished from the rejected static runtime pipeline.

T34-TRANSITION-EXECUTOR-CONTRACT-v1.md specified the seven pass gates, the required metrics table, the required test names, and the required evidence output (JSON, Markdown, and Mermaid files).

2.4 T34 Round B — UML Diagram Changes

The T34 Round B manifest recorded that all four SVG diagrams were redrawn before the code was written, because the existing diagrams showed the wrong mental model. The corrections are explained below.

Diagram 1: dynamic_flow_runtime_uml.svg

What the diagram showed before correction:

The diagram represented the nine nodes as processing text or tokens directly. There was no semantic compiler at the front. There was no predicate packet as the fixed inter-unit contract. The diagram did not show a phase context compiler, a transition gate, a context packet store, or the continuous learning feedback path.

What the diagram shows after correction:

The diagram is organized into three horizontal lanes.

Lane 1 — Intake and Predicate Contract: - User / Document Input → Semantic Compiler → Predicate Packet

The Semantic Compiler maps all incoming text to the 22-slot predicate vector. The Predicate Packet is the fixed contract that every downstream node receives. No node sees raw words; every node sees predicate counts, domain tags, confidence scores, and dependency edges.

Lane 2 — Dynamic Flow Pipeline: The nine nodes appear in sequence: Topology Router → Sub-Phase Router → Domain Splitter → Domain Translator → Scheme Planner → Processor and Applier Arrays → Convergence Gate → Result Translator + Formatter.

Two new components appear after the pipeline: Phase Context Compiler and Transition Gate Unit. The Phase Context Compiler takes the complete predicate output of a phase run and produces a ranked set of predicate fragments (decisions, constraints, knowledge edges, boundaries, rejected items) for the next phase. The Transition Gate Unit receives the upstream carry-forward summary and the downstream source packet and produces PASS, PASS WITH GAPS, or BLOCK.

Arbiter Selector + Units and Knowledge Edge Path appear as the review layer that feeds the learning cycle.

Lane 3 — Registries and Learning: Flow Registry, Unit Registry, Dataset Registry, Decision Graph, Context Packet Store, Event Log, and Continuous Learning.

The Context Packet Store is a new registry that holds versioned phase predicate summaries. The dashed lines from the pipeline to the registries represent runtime lookups, not control flow.

3. P3 Experiment — Learning From Transition Failure

3.1 What P3 Was Trying to Prove

P3 (code phase 25, experiment identifier P3-LEARNING-FROM-TRANSITION-FAILURE) extended T34 by asking: what happens when the transition gate does block, and does the system learn the right lesson?

P3 ran three sub-experiments in sequence:

P3-C — Corrupted run. The Phase 3 upstream context packet is unchanged. The downstream domain packet set is corrupted by removing the BaseService packet (td06_base_service_constraint) entirely. No packet in the set carries or acknowledges BaseService. Expected verdict: BLOCK.

This simulates a downstream implementation plan that is completely silent about BaseService — not mentioning it even as a named gap.

P3-L — Learning cycle. The BLOCK finding feeds into the idle learning cycle. The cycle produces one FeedbackRecord naming BaseService as the dropped predicate, then derives one LearnedDiscriminator that encodes the specific boundary: entirely absent → BLOCK; present as concern → PASS_WITH_GAPS.

P3-V — Verification run. The original T34 domain packet set (all 10 packets including td06 with status concern) is run through the transition gate. The gate consults the discriminator registry, finds the discriminator inactive because td06 is present, and produces PASS_WITH_GAPS — the same result as T34. The discriminator did not over-generalize.

The key question that P3 answered was: does the learned discriminator correctly distinguish between "entirely absent" and "present but unenforced"? These two states look superficially similar (both indicate the constraint is not fully enforced) but have very different meanings. An entirely absent predicate means the downstream plan has no awareness of the constraint at all — it cannot possibly enforce what it does not know about. A present-but- concern predicate means the plan knows about the constraint and has explicitly flagged the gap.
