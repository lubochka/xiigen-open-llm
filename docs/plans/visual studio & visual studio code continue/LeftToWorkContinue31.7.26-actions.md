## §1. Человеческое резюме (простыми словами, без командных блоков)

Есть три линии работы (трека), и все три сходятся на одной общей кодовой базе.

- **Трек A** — дизайн-в-код (ветка `DesignToCode-clean`).
- **Трек B** — DPO-обучение (ветка `codex/dpo-implementation`).
- **Трек C** — расширения редакторов Visual Studio / VS Code и родственных хостов (ветка
  `orchestrator-extensions`, дальше «ветка расширений» или «OE»).

Общая база всех трёх треков = **КОПИЯ финализированной `main`**. «Финализированная main» — это главная
ветка уже ПОСЛЕ того, как в неё влиты Трек A и Трек B. По содержимому она совпадает с вершиной
`codex/dpo-implementation` по РАВЕНСТВУ ДЕРЕВЬЕВ: `tree(main 577c5fd65)` == `tree(codex c834c8809)` ==
`3ec02a4259e6` (проверено 02.08.2026). Это равенство СОДЕРЖИМОГО, а не предковость: между `main` и
ДВИЖУЩЕЙСЯ вершиной codex `merge-base --is-ancestor` даёт exit 1 в обе стороны (codex уходит
почасово). `c834c8809` — историческая вершина codex, чьё дерево влито в `main`; её берём для сверки
деревьев. База приколочена ПИНЕННОЙ вершиной по равенству деревьев, а не «предком».

**Что делает Трек C.** Он НЕ вливает ветку расширений в главную линию на месте. Он берёт КОПИЮ
финализированной `main` и накладывает на неё только полезную работу ветки расширений: первично
ОДНИМ контролируемым слиянием вершины OE с пофайловой развязкой (механизм (a), §5), альтернативно —
коммит за коммитом (механизм (b)). В ветке расширений над общим предком лежит **41 коммит**; эффективно переносить
нужно **38** (минус один пустой мерж-коммит, минус два коммита-близнеца — по одному из каждой пары);
из конфликтного набора реально трогать руками нужно **~10 файлов** (триаж M4). Старые ветки
`orchestrator-extensions` при этом замораживаются как архив (удаление — только по отдельной явной
отмашке Любы, это правило, а не вопрос).

**Масштаб — 6 репозиториев.** Сходимость охватывает не только ядро `llm_mvp_core`, но и 5 хост-репо
(3 smart-skills-хоста + `xiigen-platform` + `xiigen-flows`). У каждого — своя линия
`orchestrator-extensions`, которая портируется на копию его собственной финализированной `main`
(PART D).

**Ничего не исполняется до одного GO Любы.** Программа PART B/C/D не стартует, пока Люба не
подтвердит, что Треки A и B влиты в `main`, И не НАЗОВЁТ вершину финализированной `main` — это
значение обозначено `$PIN_FINAL_MAIN`; плюс отдельная механическая отмашка на материализацию копии
(`materialize_go`). Движение `main`, наблюдаемое на диске, само по себе гейт НЕ удовлетворяет: гейт
удовлетворяет ТОЛЬКО названная Любой вершина. Это записано как гейт (§3, §7), а не как вопрос.

**Честный счётчик.** Ревью Трека C — актуальное число независимых ревью-циклов ведётся в
`PLAN-REVIEW-FINDINGS-LEDGER.md` (на 02.08.2026: 10/10; авторская отметка на момент написания — 0/10).
Сборки, тесты и DPO-прогоны в этой программе не выполняются и не заявляются.

Дословный тезис: **все три трека делят общую кодовую базу (финализированную main) ДО начала любого

```

git -C "$V2" merge-base --is-ancestor $PIN_FINAL_MAIN origin/main                                                  # exit 0: финализированная вершина — предок текущей main (main движется почасово, поэтому не равенство)
git -C "$V2" merge-base --is-ancestor $CODEX_G1 $PIN_FINAL_MAIN                    # exit 0 ⇒ Трек B в базе
git -C "$V2" rev-list --right-only --cherry-pick --no-merges --count $PIN_FINAL_MAIN...$DTC_G2                    # == 0 ⇒ Трек A по cherry-эквивалентности (НЕ предковость) (--no-merges: мерж-коммит DTC cherry-эквивалентностью не сокращается — без флага даёт 1, с ним 0)
git -C "$V2"  merge-base --is-ancestor $PIN_FINAL_MAIN orchestrator-extensions-v2     # exit 0 ⇒ Трек C на базе
git ls-remote https://github.com/lubochka/claude-xiigen-smart-skills.git refs/heads/main refs/heads/orchestrator-extensions  # хост-пины
```

**Достижимость `$DTC_G2` (примечание к check 3, RC3-F02).** `$DTC_G2` должен оставаться ДОСТИЖИМЫМ
объектом: при retire G-2 использовать вариант G-2a (запушенный тег `archive/DesignToCode-clean-<дата>`),
а НЕ G-2b (удаление ветки) — иначе объект `$DTC_G2` в свежем клоне `$V2` недостижим и проверка выдаёт

Определения: `$CODEX_G1` — вершина `codex/dpo-implementation`, влитая в `main` на шаге G-1; `$DTC_G2`
— вершина `DesignToCode-clean`, замороженная на retire-шаге G-2. Обе называет Люба и фиксирует в
леджере до старта (codex движется почасово — нужна ПИНЕННАЯ вершина, а не «tip сейчас»).

Смысл: первая проверка приколачивает базу к названной Любой вершине. Вторая доказывает, что Трек B
