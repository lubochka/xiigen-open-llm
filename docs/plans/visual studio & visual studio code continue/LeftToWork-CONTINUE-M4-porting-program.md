встречаются в тексте ТОЛЬКО как цитаты неисполненной программы.

Термин «порт» (port) здесь = перенос полезной работы одной ветки на копию другой ветки без
слияния историй: мы берём КОПИЮ финализированной main и накладываем на неё эффективную работу
ветки расширений (orchestrator-extensions), не сливая ветки напрямую. Наложение выполняется ТОЛЬКО
в одноразовой копии (ветка `orchestrator-extensions-v2`); сама `main` при этом не меняется.
Первичный механизм (a) = контролируемое слияние вершины OE в копию с последующей пофайловой
развязкой по триажу §3; альтернатива (b) = наложение коммит за коммитом. Обе дают одну и ту же
поверхность порта; (b) применяется только если (a) даёт непригодную поверхность.

Шелл исполнения всех цитируемых команд: Git Bash (POSIX sh) на Windows; пути с пробелами — в
кавычках.

## §0. Человеческое резюме (плайн-русский)

Что делаем на уровне человека. Есть основная линия продукта (ветка `main`) и есть отдельная линия
работы над расширениями редакторов (ветка `orchestrator-extensions`, дальше «ветка расширений»
или «OE»). Мы НЕ сливаем их напрямую. Вместо этого, когда основная линия будет собрана начисто
(после того как в неё вольют сиблинг-работы A и B), мы делаем её КОПИЮ — отдельный клон по пути
`C:\Projects\llm_mvp_core-orchestrator-extensions-v2` с веткой `orchestrator-extensions-v2` — и
накладываем на копию только полезную работу ветки расширений: первично (a) одним контролируемым
слиянием вершины OE с развязкой по триажу, альтернативно (b) коммит за коммитом. Старые ветки orchestrator-extensions при этом
замораживаются как архив (удалять их можно ТОЛЬКО по отдельной явной отмашке Любы — это правило,
не вопрос).

Груз порта. В ветке расширений над общим предком лежит 41 коммит. Из них реально надо перенести
38. Вычитаем: минус 1 «пустой» коммит-слияние `1a283fd72` (он не несёт никаких изменений
содержимого — доказано в §3.a), минус 2 коммита-близнеца (в двух парах коммитов ровно один и тот же
патч продублирован; переносим по одному из каждой пары). Итого 41 − 1 − 2 = 38. Под первичным
механизмом (a) весь этот груз входит в копию ОДНИМ мерж-коммитом (история OE достижима вторым
родителем), а арифметика 38/близнецы/пропуск управляет НАПРЯМУЮ только альтернативой (b) «коммит за
коммитом».

Поверхность (сколько файлов «столкнётся» при наложении). Против локальной ноги ветки codex,
которую мы используем как прокси будущей финализированной main, поверхность = 34 файла с ручным
конфликтом содержимого (все типа content) плюс 49 файлов, где git сливает сам, но правки есть с
обеих сторон (их надо перепроверить после). Эти два числа (34 и 49) совпали с ожиданием
архитектора один в один.

Важное уточнение метода (находка этого цикла). У ветки codex и ветки расширений оказалось ДВА
общих предка (в терминах git — «merge-base»), а не один: `6624161be` и `54399063`. Это называется
«криcс-кросс» (перекрёстная история). Из-за этого простая проверка «что нового добавила ветка
расширений относительно ОДНОГО предка» показывает пусто для 24 из 34 конфликтных файлов — потому
что содержимое ветки расширений для этих файлов совпадает буква-в-букву с одним из двух предков, а
основная линия (codex) эти файлы уже развила дальше. Проще говоря: по этим 24 файлам ветка
расширений не несёт ничего нового, их правильная развязка — «взять сторону базы». Оставшиеся 10
файлов несут реальные новые изменения ветки расширений и требуют настоящего переноса. Метод и все
числа пересчитаны с учётом обоих предков (подробно в §2 и §3).

Что НЕ исполняется без двух отмашек Любы. Программа не запускается, пока Люба не даст две вещи:
(1) подтвердит, что сиблинг-работы A и B влиты в main, и НАЗОВЁТ вершину финализированной main —
это значение обозначено как `$PIN_FINAL_MAIN`; (2) даст отмашку материализации копии (та же отмашка
`materialize_go`, что зафиксирована в цикле M3). Движение `main`, которое я вижу на диске, само по

гейт (§5, §6), а не как вопрос к Любе.

Лицензия. Вся работа остаётся под AGPL-3.0. Файл LICENSE и заголовки AGPL-3.0 сохраняются как есть

## §3. Superseded-триаж (устаревание) — рецепт и пофайловая таблица

Слово «superseded» = «вытеснено»: сторона базы уже содержит (буква-в-букву) то, что добавила бы
ветка расширений, поэтому переносить нечего — берём сторону базы («resolve-to-base»). Никаких
заявлений о равенстве во время исполнения (runtime equivalence) не делается — только текстовая
проверка.

### Рецепт (двухстадийный)

**Стадия 1 (быстрая, токенами).**
1. Если файла нет в базе (`git cat-file -e $BASE:P` падает) → вердикт PORT-NEEDED (переносить), файл
   новый.
2. Иначе, если blob файла в OE равен blob в одном из ДВУХ предков (MB1 или MB2) → OE не несёт по
   этому файлу никакого чистого изменения; база (потомок предка) его уже развила → вердикт
   TEXTUALLY-SUPERSEDED (взять сторону базы). Это криcс-кросс-артефакт.
3. Иначе берём дельту `git diff <виртуальная-база>..$OE -- P` (`<виртуальная-база>` — MB1/MB2 —
   сегодняшние; на исполнении пересчитать против фактического `$PIN_FINAL_MAIN`), из добавленных строк выбираем до 5
   токенов (обрезка пробелов; пропускаем строки короче 12 непробельных символов, чистые
   скобки/пунктуацию и директивы `using`; предпочитаем идентификаторы/строковые литералы/коды
   ошибок). Каждый токен ищем в базе: `git grep -F -c -- "<токен>" $BASE -- P`.
   - все токены найдены (hit ≥ 1) → TEXTUALLY-SUPERSEDED;
   - ни один не найден (все 0) → PORT-NEEDED;
   - смешанно → AMBIGUOUS → Стадия 2.

**Стадия 2 (трёхсторонняя, для AMBIGUOUS).** `a` = виртуальная база, `b` = BASE, `c` = OE. Берём все
чистые добавленные строки `diff a c` (реальное новое от OE) и проверяем присутствие каждой в `b`
(база). Если ВСЕ присутствуют → SUPERSEDED-CONFIRMED. Если хоть одна отсутствует → файл =
PORT-NEEDED-CONFIRMED (правило: файл переносим, если хоть один ханк требует переноса).

Закрытый словарь вердиктов: TEXTUALLY-SUPERSEDED / PORT-NEEDED / SUPERSEDED-CONFIRMED /
PORT-NEEDED-CONFIRMED. Формулировка «runtime equivalent» не употребляется никогда.

Примечание об асимметрии рецепта (RC7-F01). Рецепт Стадии 1 асимметричен (мерил только «токены OE
отсутствуют в базе» — направление OE→база); классификация ОБЯЗАНА учитывать и обратную дельту
база→OE: файл с большой параллельной разработкой базы развязывается ПОХУНКОВО независимо от вердикта
Стадии 1 — целофайловый --theirs выбросил бы работу базы (напр. LiveLocalServerTests.cs: база 8014
строк vs OE 723; Machine.cs: база 3031 vs OE 1614).

### Строка честности (§3, дословно требуемая)

Вердикты — ТЕКСТОВЫЕ проекции против локальной ноги codex как прокси финализированной main; на фазе
ИСПОЛНЕНИЯ triage перегоняется против `$PIN_FINAL_MAIN` после гейта.
