## 2. Реальный retrieval consumer получает уже обученную policy

[TransformerEmbeddingKnnLogicalUnit.Train:97–165](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:97) строит EmbeddingModel с maxLen=min(64,ContextLen), вычисляет вектор каждого примера и добавляет его в HNSW (m8/efConstruction32/efSearch16). Здесь нет loss/optimizer/backward; Train означает построение памяти из примеров. При обычном [ExecuteAsync:181–208](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:181) query проходит тот же encoder, кандидаты ранжируются fusion scorer, возвращается **сохранённый example.Output**.

Существенное контрдоказательство более сильной версии «encoder не может учиться»: [DefaultLogicalCapabilityTrainer:658–675](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:658) берёт policyModel из teaching stack и передаёт её в ExecuteDpoTeachingAsync. После успеха **та же переменная policyModel** передаётся в [retrieval Train:963–969](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:963). Поэтому обновления разрешённых параметров через DPO logits могут изменить hidden states и последующие embeddings, хотя retrieval API не дифференцируем. Это source-возможность полезного переноса обучения, не измеренный здесь прирост качества.

Trainer подключён в [LogicalOrchestratorAssistant:474–497](C:/Projects/llm_mvp_core/15.OrchestratorModel/Logical/LogicalOrchestratorAssistant.cs:474); [TeachingSessionBuilder:354–366](C:/Projects/llm_mvp_core/15.OrchestratorModel/Logical/TeachingSessionBuilder.cs:354) включает его условием enableCapabilityTraining. Реальный запуск требует admission и остальных условий этого пути: наличие конструктора не означает, что каждый запрос обучает модель.

Подготовленный retrievalUnit регистрируется [на1125–1133](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:1125). [GeneratedCapabilityFlowFactory:7317–7335](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:7317) выбирает его при UseLearnedUnitWhenAvailable и наличии подходящей unit с trust не ниже Probationary; иначе возвращает UniversalNineNodeDevelopmentFlow. [GeneratedCapabilityFlow:7383–7396](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:7383) канонизирует query и вызывает unit; [метрики:7420–7430](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:7420) явно помечают retrieval_unit_selected=true и learned_unit_selected=false. [Финальный результат:7454–7466](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:7454) оформляет выбранный сохранённый output через CapabilityResultTranslator.

Это важное уточнение будущего micro35: kNN здесь **штатная часть generated-capability consumer**, а не автоматически «скрытая подмена» neural ответа. Исключение fallback допустимо для изоляции опыта, но исключение самого retrievalUnit сменило бы исследуемый consumer. Также registry-флаг isLearned=false не доказывает отсутствие предшествовавших DPO-обновлений policy. Ни этот флаг, ни метрика PASS сами по себе не устанавливают качество нового закона.

## 3. Plateau stop: реальный, но локальный контракт generated capability

[N35-CVG:11–19](<C:/Users/lubao/Documents/xiigen/llm mvp/design to code session/replanning/possibleDifs/35-NEW-GENERATED-CAPABILITY-DPO-LOSS-PLATEAU-STOP-2026-10-16.md:11>) правильно указывает связку DefaultLogicalCapabilityTrainer → LogicalDpoTrainingUnit → DpoConvergenceMonitor. Важно различать defaults трёх уровней:

| Уровень | Max steps / window / threshold |
|---|---|
| [Сам LogicalDpoTrainingRequest:465–467](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:465) | 1 /25 /0,002. Сам request не имеет defaults5/1. |

| [ExecuteDpoTeachingAsync:2284–2309](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:2284) | Явно передаёт max/window; threshold не передаёт и получает0,002 из request default. |

`dpo.max_steps` и `dpo.convergence_window_steps` разбираются как int и ограничиваются снизу1; [LogicalDpoTrainingUnit:586–589](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:586) разрешает max от1 до5. [Admission settings:696–710](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:696) отвергают нечисловой/отрицательный threshold и window<1. Верхний бюджет5 — существующий ограниченный контракт, не установленная ошибка.

В [цикле:1343–1390](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:1343) сначала выполняется **настоящий trainer.StepVector**, затем обновляется stepsTaken, и только на step%windowSteps==0 вызывается ShouldStop(lastMetrics.Loss). Это сравнение loss в концах интервалов, не среднее всех loss внутри окна. [DpoConvergenceMonitor:23–38](C:/Projects/llm_mvp_core/11.DPO/DpoConvergenceMonitor.cs:23) первым вызовом только запоминает loss; затем считает подряд два изменения с abs(delta)<threshold и возвращает stop. Равенство порогу не проходит; знак улучшения не учитывается: малый рост loss тоже может считаться стабильностью.

При предложенной helper последовательности [0,6931;0,6929;0,6927;…], window1/threshold0,002 дают stop после **третьего** обновления. Это прямое следствие предиката, а не полученный C# trace. Отсутствие двух стабильных изменений оставит до пяти шагов; window≥2 при max5 не успевает сделать три вызова monitor. Стандартный request с max1/window25 тоже не получает такого раннего stop.

Контроль threshold=0 математически отключает данный strict-inequality stop, но **DefaultLogicalCapabilityTrainer не читает metadata threshold**. Его нельзя испытать под вымышленным ключом, сохранив тот же caller. [Micro35:11–24](<C:/Users/lubao/Documents/xiigen/llm mvp/design to code session/replanning/possibleDifs/35-MICRO-DPO-CONVERGENCE-VS-DOMAIN-QUALITY-2026-10-16.md:11>) корректнее выбирает существующий параметр window1 против window5 при одинаковых max5/threshold0,002.

Stop predicate не измеряет новый правильный ответ, heldout law accuracy или retention. Но из этого не следует, что pipeline вообще не имеет других проверок: после DPO есть frozen-reference/state checks и [trust scoring:724–730](C:/Projects/llm_mvp_core/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs:724). Полный аудит этих gates сюда не входит. [DPO result:1421–1440](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:1421) возвращает фактическое DpoStepCount, последний loss/accuracy и state, без отдельного поля stop reason. Поэтому по одному DpoStepCount<5 без зафиксированных effective settings и trace нельзя доказать именно plateau.

## 4. Почему эти два свойства не объясняют RP01 автоматически

DPO оценивает [chosen/rejected log-probs:875–896](C:/Projects/llm_mvp_core/11.DPO/DpoTrainer.cs:875); обычный [LlmModel.Forward:226–241](C:/Projects/llm_mvp_core/03.TransformerModel/LlmModel.cs:226) проходит blocks/final norm/lm_head. Sentence pooling этому gradient path не нужен. Отдельный дефект таблицы Embedding из56 также не превращает замороженную базу RP01 в доказательство неработоспособности q/v LoRA.

Итак, delta к56/41 — два новых отсутствующих derivatives для возможного metric learning и конкретная короткая stop-policy generated-capability. Повторно используются established границы frozen embeddings, разрешённых trainable recipients и direct RP01 loop. Сохранённого runtime trace, где plateau сократил именно изученный RP01 либо где production contrastive loss пытался пройти через EmbedBatch, здесь нет. Польза дополнительных шагов и доменная цена раннего stop остаются открытыми.
