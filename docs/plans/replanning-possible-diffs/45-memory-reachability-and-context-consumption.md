Проверены три ограниченных механизма нового helper drop. **Ни один не установлен как причина плохих свободных ответов RP01.** Для HNSW найдено строгое условие, при котором сохранённый урок нельзя извлечь; для GraphRAG подтверждён ранний выход из сборки контекста, но ближайший найденный ответчик читает только его TokenCount; ProjectWiki Mode2/Mode3 действительно не читают текст выбранного chosen. Гипотеза о потере исправления с прежним PairId существенно сужена: текущий CLI использует ID, зависящий от содержания DPO-пары.

Новые уточнения относительно helper:

- При production `m=8` лимит степени на уровне 0 равен 16; предложенные 12 TRAIN vectors не могут воспроизвести reverse-prune уровня 0. Ниже приведён бумажный пример с 18 векторами и условием на уровень последнего узла — без запуска и без Python-эмуляции.
- `HnswIndex.Save/Load` сохраняет adjacency, но найденный capability restore **заново строит** HNSW через Train. Это разные способы восстановления.
- Даже wrapper `TransformerEmbeddingKnnLogicalUnit` не означает, что каждый потребитель использует retrieval: capability generation извлекает из него model/tokenizer и вызывает TextGenerator.
- В текущем sealed-DPO continuation изменение chosen/rejected меняет PairId; обычное повторение той же пары корректно пропускается. Смена ID не обеспечивает замещения старого урока и не устраняет нечувствительность Mode2 к chosen.

## 1. HNSW: урок в Count не обязательно достижим

[Add, строки 49–96](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:49) добавляет vector/id и соседей нового узла; каждый старый сосед получает обратную ссылку. При превышении `maxM` его список заменяется ближайшими к **старому** узлу через `SelectNeighbours`. На уровне 0 `maxM=2*m`, на верхних — m. Отброшенная ссылка не восстанавливается; требования оставить хотя бы одну входящую ссылку к новому узлу нет.

[Search, строки 99–110](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:99) стартует с entry point, проходит верхние уровни, затем вызывает SearchLayer уровня 0. [SearchLayer, строки 190–230](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:190) следует только по исходящим спискам посещённых узлов. Он не сканирует `_vectors` как запасной путь. Поэтому увеличение `efSearch` или `topK` не возвращает узел, до которого нет пути от начальной вершины поиска.

Это условие следует отличать от обычной приближённости ANN: при связном графе недостаточная ширина поиска тоже может пропустить ближайший вектор, но это другая причина. Нулевая входящая степень уровня 0 сама по себе также недостаточна, если узел стал entry point или доступен через верхние уровни. Строгий ниже пример исключает оба случая.

**Бумажный контрпример для настоящего m=8 — не выполненный опыт.** Пусть сначала добавлены 17 разных ID с одним ненулевым вектором `u=(1,0)`. При `efConstruction=32` или 64 и нижнем cap=16 уровень 0 до этого размера полный: очередной узел находит все прежние и ни у одного не превышается степень 16. Затем добавляется ID 18 с `v=(-1,0)`, причём его случайный уровень равен 0. Такой уровень допустим [RandomLevel, строки 156–161](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:156).

Новый узел выбирает 16 из 17 старых. Каждый из этих соседей уже имеет 16 старых соседей с cosine=1; новый даёт cosine=-1 и при pruning исключается. У нового остаются 16 исходящих ссылок, но ни одной входящей; верхних уровней у него нет, entry point прежний. Query=v должен иметь exact nearest равным новому ID с cosine=1, но графовый поиск его не посещает. Это доказательство возможности по source и заданным значениям; **не измерение частоты, не saved native receipt и не пример реальных encoder outputs**.

Отсюда существенная поправка к micro-design: при тех же production-параметрах и **не более 17** точек уровень 0 полный, поэтому предложенный ordinary pilot из 12 TRAIN vectors не различает данный reverse-prune. Даже если upper-level списки сокращались, конечный поиск из любой старой вершины получает всех соседей полного L0. Helper Python m=2/L0 на 11 Gaussian vectors остаётся отдельным сообщённым proxy-наблюдением. Его числа и native parity здесь не проверялись и не переисполнялись. Для m=8 нужен набор, на котором pruning достижим; размер сам по себе ещё не доказывает его вред.

## 2. GraphRAG: Results и переданный текст различаются, но caller важнее

[HybridRetriever.Retrieve, строки 29–43](C:/Projects/llm_mvp_core/08.GraphRag/HybridRetriever.cs:29) возвращает полный `merged` в Results и отдельно формирует ContextText. Ранжирование и topK применяются **до** сборки текста: [строки 82–85](C:/Projects/llm_mvp_core/08.GraphRag/HybridRetriever.cs:82). В [BuildContext, строки 88–105](C:/Projects/llm_mvp_core/08.GraphRag/HybridRetriever.cs:88) первый не помещающийся snippet вызывает `break`, поэтому следующие даже более короткие snippets не рассматриваются.

Проверка control flow на бумаге: при готовых formatted lengths 11990/30/5 и лимите 12000 после первой строки вторая вызывает выход; третья поместилась бы, но пропущена. Если первый snippet длиннее 12000, текст пустой. `AppendLine`-разделители не входят в `used`; `MaxTokens*4` и `ContextText.Length/4` используют длину строки, не BPE tokenizer. Это источник потенциального пропуска/ошибки бюджета; выбор `continue` вместо `break` сам по себе не гарантирует лучшего предметного контекста.

Найденный caller — [WikiContextRetriever, строки 76–103](C:/Projects/llm_mvp_core/42.ProjectWikiDomain/WikiContextRetriever.cs:76). Для вызова HybridRetriever нужны одновременно AllowSemantic, отсутствие принудительного lexical/reject route и ненулевой injected retriever. При его отсутствии остаются lexical EvidenceHits и warning fallback. [Фабрики, строки 16–35 и 40–64](C:/Projects/llm_mvp_core/42.ProjectWikiDomain/ProjectWikiDomainServiceCollectionExtensions.cs:16) по умолчанию получают `hybridRetriever=null`.

Адресный tracked C# поиск `HybridRetriever`, `RetrievalContext`, `SemanticContext`, `ContextText` не нашёл явного создания `new HybridRetriever`. Это ограниченный статический поиск: внешний DI, reflection или внешний caller не исключены. Найденные ProjectWiki validation-фабрики вызываются без третьего аргумента; RP01 simulation-call-chain к этому retriever не найден.

Более сильное ограничение установлено после caller: [ProjectLocalWikiOrchestrator, строки 67–83](C:/Projects/llm_mvp_core/42.ProjectWikiDomain/ProjectLocalWikiOrchestrator.cs:67) передаёт context в ProjectLocalWikiModelUnit. Тот выбирает top из **lexical EvidenceHits**, строит факты/цитаты по ним и читает из SemanticContext только TokenCount: [строки 26–59](C:/Projects/llm_mvp_core/42.ProjectWikiDomain/ProjectLocalWikiModelUnit.cs:26), [62–81](C:/Projects/llm_mvp_core/42.ProjectWikiDomain/ProjectLocalWikiModelUnit.cs:62). Advanced sections также используют EvidenceHits: [114–137](C:/Projects/llm_mvp_core/42.ProjectWikiDomain/ProjectLocalWikiModelUnit.cs:114).

Поэтому при одинаковых lexical hits замена пропущенного semantic текста не добавляет его закон в содержательную часть **этого** ответа. Могут отличаться напечатанное число semantic tokens и служебные признаки; mode также задаёт confidence 0.88 против lexical 0.82. При пустых lexical hits ответчик отказывается, даже если SemanticContext непуст. Это не доказательство, что GraphRAG бесполезен вообще: его текст доступен другим возможным consumers. Но обещать улучшение найденного ответа одним `break→continue` сейчас оснований нет.

Полезный уже существующий механизм здесь — предметный lexical evidence и цитаты; отсутствие semantic-text consumption его не отменяет. Эти сведения нельзя переименовать в neural-generated знание.

**Будущая проверка, не запуск.** Сначала зафиксировать реального потребителя ContextText, если такой появится в исследуемой ветке. Изолированно сравнить сборку на трёх formatted snippets и контрольном наборе, где всё помещается; измерить итоговый текст и фактическое число токенов pinned tokenizer. Для найденного ProjectLocalWikiModelUnit отдельный контраст должен удерживать lexical hits и менять только semantic text при одинаковом TokenCount: отсутствие смыслового изменения будет ожидаемым свойством текущего consumer. Эксперимент качества с другим model/prompt consumer потребует отдельного доказанного вызова, а не подстановки нового пути вместо существующего.

Однако текущий CLI continuation имеет другой identity contract:

1. [ContinueOrchestrationTrainingAsync, строки 3122–3158](C:/Projects/llm_mvp_core/27.TranslationDomain.Tools/Program.cs:3122) разрешает repository-owned DPO dataset, загружает machine и материализует новые пары. [Строки 3387–3394](C:/Projects/llm_mvp_core/27.TranslationDomain.Tools/Program.cs:3387) пропускают уже обученные **manifestPair.PairId**.
2. [MaterializeRepositoryOwnedOrchestrationTrainingPair, строки 3695–3711](C:/Projects/llm_mvp_core/27.TranslationDomain.Tools/Program.cs:3695) переносит `PairId=manifestPair.PairId`, chosen/rejected из DPO-пары; исходный ordinal PairId не становится ID нового урока.
3. [Manifest mapping, строки 1477–1489](C:/Projects/llm_mvp_core/14.ContinuousLearning/Training/RepositoryOwnedDpoDatasetManifest.cs:1477) пересчитывает identity и сопоставляет его с manifest. [FileDpoPairStore.ComputeIdentity, строки 2560–2599](C:/Projects/llm_mvp_core/14.ContinuousLearning/Feedback/FileDpoPairStore.cs:2560) включает Domain, Prompt, **Chosen и Rejected**, а также соответствующие provenance/authorship поля. Изменение chosen/rejected даёт другой ID при обычном предположении об отсутствии SHA256 collision; старые sealed bytes нельзя заменить и сохранить тот же валидный паспорт.

Следовательно, для этого проверенного CLI «исправление неизбежно блокируется прежним source ID» — неверное обобщение. Повтор того же content-ID является ожидаемой идемпотентностью. При законной новой ревизии ID меняется, но **старый урок остаётся рядом**: upsert/supersedes-контракт в рассмотренном store отсутствует. При одинаковом prompt/score выигрывает ordinal PairId, а не более поздняя ревизия. Для Mode2 эта конкуренция прежде всего меняет style_source; выбранный новый PlanText всё равно не потребляется. Для Mode1 полезный content consumer делает revision-selection вопрос содержательно значимым, но фактический wrong→right effect не измерен.

**Будущая проверка, не запуск.** Разделить два контракта: прямой API same-ID retry/changed-content и sealed CLI с новым content-ID. В каждом сохранять RowsTrained, IDs и payload до/после, selected ID и ordinary output; отдельно повторить после checkpoint restore. Для пары «старый ID/новый ID» не считать само увеличение Count исправлением: нужен выбранный актуальный урок. Для проверки именно revision semantics сначала использовать Mode1 либо payload/selection, чтобы независимая нечувствительность Mode2 к chosen не скрыла результат. Не удалять guard до определения требуемого version/supersedes-контракта.
