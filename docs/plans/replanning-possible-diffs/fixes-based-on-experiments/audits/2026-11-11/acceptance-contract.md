# Договор проверки переноса и экспериментального вывода — 11 ноября 2026

Область: новые работы по карточкам `fixes-based-on-experiments` и `experimets`, которые используют результат опыта для изменения продукта или для научного вывода. Это адресное усиление по установленным ошибкам, не новый приказ повторить все опыты. Принятый результат сохраняется в своей точной области. Каждое применение указывает конкретную карточку, попытку, исходник, получателя и бюджет.

## 1. Сначала утверждение и его настоящий потребитель

У каждой карточки отдельно зафиксировать: что изменяется в алгоритме; какую задачу решает пользователь; какая измеряемая величина должна измениться; через какой **обычный** caller она читается. В цепочке producer→выбор→guard→consumer→сохранённое состояние нет необъяснённых переходов.

Положительный результат компонента подтверждает только компонент. Для product claim обязательны фактический route hit, введённый фактор, выполненные guards и конечный ответ. Если scorer выбирает один вариант, а поздний guard может его отвергнуть, проверить случай «недопустимый winner + допустимый runner-up». Контроль только на полном покрытии эту границу не закрывает. Восстановление проверяется после первичного обычного чтения, а не заменяет его.

Не считать числовую уверенность модели независимым доказательством её правильности. Отдельно назвать источник gold, правило совпадения, constant/identity/replay baseline, отрицательный контроль и точную границу вывода. Детерминированный helper остаётся helper; его существование не означает обученный навык.

## 2. Смысл величины проверяется независимо от её носителей

| Величина | Независимое определение | Ошибка, которую нужно исключить |
|---|---|---|
| Cold score | Правильные фактические ответы необученного состояния на указанной панели | Называть это максимумом постоянного ответа |
| Constant-answer ceiling | Максимум правильных ответов одного фиксированного кандидата при том же scorer, с числителем и знаменателем | Сравнивать ceiling с другим файлом, где снова записан cold |
| Exact-pair overlap | В обучении были тот же input и та же target | Называть все неповторённые пары невиданными inputs |
| Input novelty | Input отсутствует во всех действительно предъявленных тренировочных входах | Проверять только различие target |
| Эпохи с обновлениями | Поэпоховый ledger фактических изменений | Приравнивать число ошибочных примеров к числу эпох |
| Resource delta | `(B−A)/A` для одной и той же метрики, работы, окна, процесса/сборки и панели | Делить delta компонента на несопоставимый общий расход с оснасткой |
| Полнота тестирования | Независимый discovery/case inventory сопоставлен по identity с результатами | Выводить полноту из суммы pass/fail/skip |
| Научный вывод | Вывод из пригодного измерения именно этого фактора | Считать warning по обязательному guard совместимым с SUPPORTED |

Сравнение двух JSON, порождённых одной формулой, подтверждает согласованность сериализации, но не правильность формулы. Отрицательный oracle должен различать смысл: смена только target не меняет input novelty; cold0 может сосуществовать с ceiling2/4;7 updates могут лежать в4 эпохах. Не изменять gold, чтобы скрыть нарушение продукта.

## 3. Владение попыткой и неизменность улик

До подготовки данных и первого Train выделить `run_id` и исключительное владение каталогом. Отсутствие tracked files в Git не доказывает свободное место. Существующая непустая, чужая или прерванная попытка сохраняется; повтор получает новый адрес или явный отказ. Создать marker атомарно с политикой отказа при существовании (`FileMode.CreateNew` или эквивалент), а не проверкой Exists перед обычной записью. Marker связывает исходный SHA, dirty delta, проект, конфигурацию, фильтр и время старта.

Все writers используют этот корень: JSON, snapshots, логи, TRX и terminal. Однократные артефакты не перезаписываются. Для намеренного append либо смены промежуточного состояния нужна отдельная owner-only операция; окончательный файл публикуется целиком через временный файл и атомарное переименование с явной политикой конфликта. Это не объявляется гарантией переживания отказа диска без отдельного требования и проверки.

`ResolvePath` не разрешает выход за пределы корня. Режим продолжения прерванной попытки отличается от нового запуска и проверяет identity исходника, попытки и уже законченных стадий. Cleanup не удаляет опубликованные, чужие и незавершённые доказательства. Даже обычный test helper, который пишет в фиксированный tracked путь, обязан участвовать в этом договоре; наличие общего sink само по себе не охватывает обходные writers.

## 4. Измерение, научный исход и окончание процесса — разные результаты

Тест пишет наблюдения и решение валидатора. До окончания runner общий результат остаётся `IN_PROGRESS`. Test body не может удостоверить literal «N/N passed», успешность сборки или реальный process exit. Если используется `verdict.ExitCode`, назвать его внутренним кодом валидатора.

После terminal процесса внешний владелец связывает command/handle/PID, source+assembly identity, process exit, полный stdout/stderr и raw TRX. Соседний упавший Fact, late assertion, testhost abort или отсутствие TRX не превращаются в успех ранее записанного отчёта. Отсутствующий terminal означает незавершённость, а не0 ошибок.

| Условие | Measurement outcome | Научный вывод | Runner terminal |
|---|---|---|---|
| Все обязательные инварианты соблюдены, эффект есть | VALID | Поддержан только названный эффект | Берётся из фактического runner |
| Измерение пригодно, полезного эффекта нет | VALID | Отрицательный/неподдержанный | Может быть нормальным успешным завершением |
| Нарушены доза, finite, equal-start, identity либо обязательный stage | INVALID или INCOMPLETE с причинами | Не выводится как SUPPORTED | Failure/incomplete, связанный с тем же запуском |
| Нет ошибочного примера для коррекции | NO_CONTRAST | Фактор коррекции не проверен | Наблюдаемый штатный исход; corrective Train=0 |
| Выполнение оборвалось до нужных arms/readouts | NOT_MEASURED для пропущенного | UNKNOWN | ABORTED/INCOMPLETE |

Нарушение, которое должен представить validator, не может быть перехвачено ранним assert до записи этого исхода. Если продолжать небезопасно, сохранить partial raw, фактический расход и именованную завершённую стадию; не дополучать цифры скрытым повтором обучения. Negative-path тест проходит через реальный executor→sink→external terminal, а не только Serialize заранее изготовленной receipt.

## 5. Полный расход и причинная граница

До запуска описать physical run, source rows, Train calls, Unit lesson calls, optimizer updates, epochs, flow observations, component queries, save/load и внешние вызовы. Main, setup-probe, control, mutation, rerun и restore имеют отдельные счётчики; общий total выводится из них. Цепочка Unit Tokenizer→Executor — одна цепочка чтения этих единиц; она сама по себе не является полным вызовом TranslationMachine/Orchestrator/Verifier. Нельзя переименовывать её в product Flow или дважды учитывать tokenizer как ещё одно такое чтение. Одинаковые hashes независимых переобученных объектов не делают повторные Train бесплатными.

Исправление арифметики по сохранённым raw не требует нового Train. Последующие научные сравнения получают новый паспорт и бюджет; в отчёте видно, что действительно исполнилось, что лишь запланировано и что заблокировано средой. Диагностический запуск не стирает стоимость прежнего.

Стоимость качества и механизма проверяется раздельно. Мутация отмены ускорения может законно оставить semantic-equivalence тест зелёным. Для заявления, что ресурсный выигрыш защищён от регрессии, нужен контроль, чувствительный к возврату затрат, при сохранённых ответах. Записывать повторы, разброс и область threshold; медиана и порог2×не доказывают отсутствие5%-регрессии и не охраняют все выбросы.

## 6. Обязательная адресная матрица применимости

Это профилактические дополнения, **не список доказанных дефектов каждого соседнего опыта**.

| Семейство | Что добавить к его собственной карточке |
|---|---|
| P48/P49 и neural probes | Finite/state/loss controls; отличие clipping diagnostic от оптимизируемого CE; source/model/attempt; whole-run terminal вне Fact |
| P49 и warm-start | Три disjoint группы overlap, сохранённые и потерянные IDs, подготовка в полной цене; +1 ответ не называется кривой ускорения |
| P50 и graph/flow | Guards участвуют во всех verdicts и exit; assigned node/output identity; budget; endpoint gain отдельно от monotonicity; bespoke restore отдельно от native unit |
| P52/P58 и correction | Cold/constant/Train-control отдельно; actual wrong response с происхождением; no-errors terminal; достижимая запись invalid; полный setup/control расход |
| P54, P60/P64 и top-k/cascade | Selection и admission проверены совместно; lawful runner-up не теряется; ordinary route и fallback наблюдаемы; ресурсные окна сопоставимы |
| Wiki/retention/route identity | Активная редакция отделена от истории; same-owner state; параметры/metadata/ответы отдельны; update-count не эпоха; public gate не internal acquisition |
| Cache/restore | Все constructor families; warm same-owner hit→restore/rollback→miss; rejected-before-mutation отдельно от failure-after-begin; optimizer/RNG сравниваются по полям |
| Batch inventory и QA | Известный solution scope; явные маршруты новых классов; discovery vs executed cases; partial fix не пересчитывает full baseline |

## 7. Приёмочный пакет одного ремонта

Достаточный пакет содержит конкретный source+dirty delta, точный изменённый owner/caller, предыдущий и новый наблюдаемый ответ/исход, независимый oracle, positive+negative/retention, чувствительную мутацию, фактический бюджет, build/discovery/test identity, полный terminal и исходные raw. Где используется checkpoint — показать его load тем же назначенным API без Train, и отдельно продолжение обучения, если оно входит в claim.

Не все строки требуют дорогого нового опыта. Численные формулы, классификация overlap, file ownership и порядок terminal можно проверять малыми независимыми fixtures. Научный и продуктовый результат при этом не подменяется инфраструктурным PASS.

Исторические данные не переписываются: correction хранит исходный path+hash+JSON pointer, новую формулу/вывод и основание. Card, registry, report и общий вывод получают согласованное **датированное** состояние. Если giant carrier не прочитан полностью, отдельный supplement явно помечается так и включается в карту ссылок; это не означает, что весь carrier прошёл аудит.
