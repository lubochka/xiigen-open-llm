## Актуальные находки и снятые формулировки

### EW-01. Непубликованная попытка не имеет исключительного владельца

**Статус:** подтверждено чтением текущего исходника; нативная демонстрация в этом аудите не выполнялась. Это остающийся дефект, уже отмеченный 10 ноября.

`ExperimentEvidenceSink.cs`: `ForDeclaredDirectory` (примерно 137–165), `IsPublishedEvidenceDirectory` (252–284), `WriteTextExactly` (169–188), `WriteBytesExactly` (230–245), `ResolvePath` (194–209).

Причина — смешение двух вопросов: «лежит ли папка в Git?» и «свободна ли она для нового запуска?». При доступном Git и нуле отслеживаемых файлов код признаёт папку свободной, даже когда в ней уже есть результаты прерванного/первого запуска. Затем записывает через `File.WriteAllText`/`WriteAllBytes`, то есть поверх существующего файла. Два последовательных либо параллельных `ForDeclaredDirectory` с одним незакоммиченным адресом разрешают одинаковый корень. Коллизии GUID для проявления этого дефекта не нужны.

При отслеживаемой папке штатное перенаправление уже работает; четыре теста приёмника проверяют перенаправление, отказ, новую свободную папку и сохранение содержимого. Эти полезные проверки нельзя снимать или называть приёмник отсутствующим. Однако среди них нет существующей незакоммиченной папки, двух владельцев одной попытки, перезапуска после сбоя и согласованного внешнего результата запуска.

Ремонт должен до подготовки/обучения выделить исключительное владение попыткой, а не ждать первого `WriteEvidence` через `Lazy`. Чужая или незавершённая папка должна сохраняться как улика и вызывать отказ либо новый адрес. Для намеренного продолжения нужен отдельный проверяемый режим с идентичностью попытки и границей продолжения.

Правильная модель — два независимых результата: измерения конкретного опыта и итог тестового запуска. Отказы более ранней подготовки и assertions требуют отдельного внешнего завершения попытки. Ошибка возникает, когда эта промежуточная запись одновременно изображает терминальный успех runner.

### BG-01. Узкая причина сторожа исправлена, новая очередь классов осталась

**Статус:** починка подтверждена текущим исходником и независимым пересчётом исторической цепочки fix→reverse mutation→restore. Остаток 119 текущих положительных фильтров проверен статически.

Не отменять текущий смысл охраны `new_test_class_without_strong_batch_signal`. Для 119 классов нужно определить семейство, ресурсные ограничения и первое совпадение в `batches.tsv`, затем проверить discovery и отсутствие лишних владельцев. Добавление всех в старую weak snapshot или широкое совпадение, которое превращает остаток в фиктивно явную семью, скроет проблему.

### BG-02. Условия резервного обхода шире, чем описано комментарием

**Статус:** условный риск текущего кода, не вновь воспроизведённый дефект нормального корневого решения.

В `TestSuiteBatchManifest.cs:2007–2016` fallback включается по `declaredProjects.Count == 0`. Комментарий приравнивает это к отсутствию `.sln`, но `ReadSolutionDeclaredProjectFiles:2020–2062` также возвращает пустой список, если `.sln` существует, но его записи не распознаны или все пути `.csproj` исчезли. Тогда опять запускается широкий рекурсивный обход, в том числе чужих копий. В карточке надо разнести «явный синтетический режим без решения» и «решение есть, но непригодно». Последнее должно давать диагностический отказ, а не расширять область молча. Для текущего здорового `.sln` принятая починка остаётся действующей.

Тексты ниже — подготовленные вставки в договоры/карточки; в исходные ветки этим worker не внесены. Они не редактируют skills и не реализуют продуктовую починку.

### Вставка 1. Владение и сохранность каждой попытки

**Целевые документы:** `fixes-based-on-experiments/04-evidence-and-novelty.md`; общий экспериментальный договор `experimets/03-metrics-and-reporting.md`. Ссылку на общий договор добавить в P48/P49/P52/P58 и остальные исполняемые карточки, создающие улики.

> До подготовки данных и первого шага обучения запуск получает отдельный `run_id` и исключительное владение каталогом попытки. Нулевое число файлов в Git не доказывает свободный каталог. Непустой каталог, уже открытая попытка и чужой маркер владельца не перезаписываются; повтор выбирает новый адрес либо явно завершает работу с диагностикой. Владение выделяется атомарно созданием маркера с отказом при существовании (`FileMode.CreateNew` или эквивалент), а не проверкой `Exists` перед обычной записью. Маркер содержит идентификатор попытки, исходный SHA/dirty delta, конфигурацию, проект/фильтр и время старта. Ошибка после получения владения сохраняет попытку; автоматическое удаление каталога в cleanup не разрешено.
>
> Все writers используют одно выделенное место: показатели, снимки состояния, stdout/stderr, TRX, отчёт и окончательный статус. `ResolvePath` не разрешает выход за пределы корня попытки; выдача пути не считается разрешением перезаписать чужой файл. Однократные артефакты создаются без overwrite. Если журнал намеренно дописывается либо owner обновляет промежуточное состояние, такая операция задаётся отдельно; окончательный артефакт публикуется только после целой записи временного файла в том же каталоге и атомарного переименования с нужной политикой конфликта. Это гарантия согласованной видимости, не заявление о сохранности при отказе диска без отдельного требования и проверки.

### Вставка 2. Измерения и терминальный результат запуска

**Целевые документы:** `fixes-based-on-experiments/03-test-and-execution-contract.md`; `experimets/46-qa-execution-test-repair-and-fresh-results-2026-11-03.md`; ссылки из `experimets/cards/P48-weighting-curriculum.md`, `P49-probe-warm-start.md`, `P52-semantic-annotation.md`, `P58-feedback-learning.md`.

> Приёмник в тесте пишет результат измерений: выполненное обучение, конечность состояния, численные наблюдения, научный вывод и причины отказа. До завершения runner общий статус остаётся `IN_PROGRESS`; тест не пишет собственные literals «N/N passed», код выхода процесса либо успешность сборки. Численный `verdict.ExitCode` при необходимости называется кодом валидатора, а не фактическим process exit.
>
> Окончательный статус создаёт внешний владелец запуска после terminal процесса. Он связывает команду, handle/PID, build identity, process exit, целиком сохранённые stdout/stderr, сырые TRX и фактические результаты всех выбранных случаев. Late assertion, провал соседнего Fact, авария testhost и отсутствие TRX не превращаются в успех уже записанных измерений. Аварийный/прерванный запуск получает `ABORTED`/`INCOMPLETE` с причиной; `PASSED` допустим лишь при фактическом успешном terminal и согласованных требуемых результатах. Повтор после любого из этих исходов создаёт отдельную попытку. Отчёт читает этот окончательный документ; если его ещё нет, прямо пишет «итог запуска ещё не получен».

### Вставка 3. Полнота, счётчики и честное сужение приёмки

**Целевые документы:** те же договоры исполнения; будущая карточка устранения остатка batch inventory.

> Перед запуском сохраняются независимо полученный состав discovery, единица счёта (метод, параметризованный case, класс или проект), фильтр и сборка. После запуска сверяются идентичности ожидаемых и наблюдённых случаев. Арифметика `passed + failed + skipped = total` доказывает согласованность записанных строк, но не полноту охвата. `NotExecuted` и skipped не считаются выполненными проверками; расхождение XML Counters и строк сохраняется как расхождение. При аварии runner и неизвестном остатке итог описывается как зарегистрированная выборка и нижняя граница отказов. Исторический частичный ремонт не пересчитывает полный baseline вычитанием числа закрытых падений.
>
> Для ремонта guard сохраняются те же имена случаев до/после и при обратной мутации. Переход 36→15 принимается только как закрытие установленной причины с 21 проверкой, сменившей исход; оставшиеся 15 и их причины остаются открытыми. Текущие новые классы получают явный маршрут в `batches.tsv` без расширения неизменяемого baseline слабых классов. Корневое решение является независимым источником области; отсутствие, синтаксическая непригодность и пустой состав решения различаются. Резервный рекурсивный обход допустим только в явно заданном синтетическом режиме.

| Сценарий | Что должен показать ремонт |
|---|---|
| Повтор обычного запуска для отслеживаемой попытки | Старые hashes неизменны; новые файлы в отдельной попытке |
| В назначенной папке уже есть незакоммиченные файлы | Все прежние байты сохранены; отказ или новый адрес |
| Два процесса одновременно получают один адрес | Владение получает только один; второй не пишет в его файлы |
| Сбой между измерением и последним assertion | Измерения сохранены, окончательный статус не PASSED |
| Основной Fact завершился, соседний Fact упал | Report не сообщает буквальный N/N успех |
| TRX отсутствует, повреждён или runner оборвался | `INCOMPLETE`/`ABORTED`; полнота UNKNOWN, не «0 ошибок» |
| Прерванная попытка и новый запуск | Отдельные run ID и папки; первая улика не удалена |
| Здоровая численная P48/P58 и испорченный численный контроль | Validator остаётся чувствительным; жизненный цикл не скрывает ни валидные, ни отказные данные |
| `.sln` существует, но не даёт пригодных project paths | Диагностический отказ без подхвата вложенных копий |
| Явный синтетический корень без `.sln` | Разрешённый fixture работает; режим не подменяет область реального репозитория |

Эти сценарии не требуют нового длительного обучения для каждой ветки: владение и terminal проверяются небольшими тестами инфраструктуры с управляемым процессом. Для исходных опытов нужен адресный нативный повтор после фактической реализации; полный suite необходим только в объёме текущего договора приёмки, а не как замена различающим сценариям.
