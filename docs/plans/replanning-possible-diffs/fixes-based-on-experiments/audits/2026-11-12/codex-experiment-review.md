### Две важные границы чисел

**P48:** одинаковые итоговые 12/16 не означают одинаковые ответы. Между плечами отличаются **6 из 16 ответов**. Поэтому переносить равенство score на тождество поведения нельзя. В текущем test source перед двумя плечами есть ещё один настоящий `TrainStep` для градиентного оракула: 4 800 arm steps + 1 oracle step = **4 801 шаг выбранного основного Fact**. Это вывод по исполнению исходника, не новый runtime counter. [Источник](https://github.com/lubochka/llm_mvp_core/blob/dcb931773147267c8864a532351d22b4c351265b/Tests/ExperimentFixes/P4801WeightingCurriculumCeilingTests.cs#L461-L518).

## 2. Текущие замечания и конкретная приёмка ремонта

### E01 / прежний F06: P52 продолжает писать неверный предел

Сейчас writer использует `cold.Count(row => row.AnswerCorrect)` внутри `предел_постоянного_ответа`. На фактической панели cold=0, а два варианта правильного ответа встречаются по два раза, поэтому лучший неизменный ответ даёт 2/4. Код и сохранённая ошибка совпадают; это **подтверждение открытого замечания**, не новая находка. [Строки writer](https://github.com/lubochka/llm_mvp_core/blob/dcb931773147267c8864a532351d22b4c351265b/Tests/ExperimentFixes/P5201RejectedAnnotationAddressArmsTests.cs#L488-L518).

Ремонт: вывести answer ceiling из той же панели и того же сравнения OrdinalIgnoreCase, которым оцениваются answers; tense ceiling посчитать отдельно из gold tense. Cold score оставить самостоятельным наблюдением. Новую сводку привязать к историческому input hash, не перезаписывая frozen attempt-0002 и не повторяя обучение ради переименования.

Приёмка: fixture cold=0/4, answer ceiling=2/4; вариант gold histogram 3+1 даёт 3/4; одинаковый ответ для всех gold даёт 4/4; пустая панель даёт явный отказ, а не случайный ноль. Изменение cold answers при неизменном gold не меняет ceiling.

### E02 / прежний F07: P49 путает новый input и новую пару

В `ComputeOverlap` обе численные меры вычисляются, но текстовая классификация выбирается только по совпадению пары. Ветка `inputAndTarget == 0` называет входы незнакомыми, хотя они могут полностью совпадать с TRAIN и отличаться только target. В текущем корпусе строка e-t1=(0,1) имеет знакомый cold input 0, обучавшийся с target 3. [Текущий helper](https://github.com/lubochka/llm_mvp_core/blob/dcb931773147267c8864a532351d22b4c351265b/experiments-v2/RP01-MICRO/P4901/src/FinitenessGovernedVerdict.cs#L239-L268).

Ремонт: три взаимоисключающие группы — exact pair seen; input seen/target new; input unseen. Указывать TRAIN-набор конкретного плеча. Отдельно сохранить старые цифры и дату корректировки словесного вывода.

Приёмка на текущем EXAM: cold **2+1+1**, warm **4+0+0**. Контроль: изменение только target у виденного input не увеличивает число unseen input. Full accuracy, recall и novel-input score публикуются отдельными строками. Новое обучение для этой арифметической правки не требуется.

### E03 / прежний F10: возвращаемая loss и используемый gradient описывают разные функции

У `ProbeNeuralNetwork.TrainStep` reported loss ограничена снизу вероятностью 1e-7; gradient остаётся unclipped softmax cross-entropy. На logits [0,-20] и target=1 получается probability 2.0611536181902033e-9, reported loss **16.11809565095832**, stable CE **20.000000002061153**. Производная clipped loss в этой области равна нулю, используемая target-компонента gradient приблизительно **−0.99999999794**. Это самостоятельный scalar counterexample; C# здесь не запускался. [Источник](https://github.com/lubochka/llm_mvp_core/blob/dcb931773147267c8864a532351d22b4c351265b/35.ExperimentsV2/Core/ProbeNeuralNetwork.cs#L71-L110).

Ремонт: вычислять loss устойчивой формулой log-sum-exp из logits, согласованной с gradient; диагностический cap, если нужен отображению, не подменяет training objective. Приёмка должна включать saturated logits, обычную область и finite differences по всем обучаемым блокам, с именованным dtype/tolerance. Оракул P48, проверяющий W2 одного шага в обычной области, не закрывает эту saturation-границу.

### E04 / прежний F11: WC01 делает 14 полных эпох без обновлений

Источник каждый раз обходит 18 эпох; нулевой update epoch не останавливает цикл. Новый replay, повторяющий метод прежнего аудита, воспроизвёл snapshot: 4 активные, **14 полностью пустых** эпох. Это исправляет применимость фразы из пользовательского списка «11 из 18»: здесь речь о другой точно указанной fixture, а не об универсальном результате всех запусков. [Train](https://github.com/lubochka/llm_mvp_core/blob/dcb931773147267c8864a532351d22b4c351265b/42.ProjectWikiDomain/ProjectWikiRequestRoutingTrainableModel.cs#L58-L99).

В текущем детерминированном алгоритме после полной эпохи без обновлений состояние остаётся тем же; повтор того же порядка входов снова ничего не изменит. Ремонт может остановить следующий цикл по счётчику реальных updates, сохранив максимальный cap. Нельзя назначать глобально «четыре эпохи» по одной fixture.

Приёмка: точное сохранение weights/predictions на этой fixture, набор с более поздним достижением zero-update, набор без zero-update до cap и пустой TRAIN с явным договором. Считать presentations/updates/epochs раздельно. Дополнительную native экономию времени/allocations измерить отдельно; здесь она не оценена.

### E05 / прежний F13: P58 нужен полный счёт основного Fact

Текущий основной Fact один раз обучает setup-probe, затем каждое из трёх плеч повторяет setup и подаёт коррекцию. Статически достижимая цена main: **24 + 3×24 + 3×3 = 105 TrainOnExample**. Read path: cold/setup 16, TRAIN-control 16, три EXAM 24, всего **56**. «24 setup и 3 corrective на плечо» допустимо как локальный бюджет, но не как полная цена опыта. [Setup и TRAIN-control](https://github.com/lubochka/llm_mvp_core/blob/dcb931773147267c8864a532351d22b4c351265b/Tests/ExperimentFixes/P5801CorrectiveLessonCounterExampleArmsTests.cs#L610-L652).

Ремонт: run-local счётчики main setup, arm setup, corrections, model reads и instrument controls. Все итоговые числа получать из фактических операций. В отдельных Facts и полном test class свои итоги, не приписываемые main. Приёмка должна находить добавленный скрытый setup-call и нулевую коррекцию, когда ошибочной строки нет; внешний terminal обязан сохранять отказ, если ранний assert прерывает путь. Последняя проблема относится к F04 и разбирается root.

Их несовпадение с новым source не доказывает, что исправление отсутствует, и не разрешает переписать исторические файлы. Новая опубликованная попытка должна указать source/dll/run identity и сопоставимый фактический output. [Текущий ceiling](https://github.com/lubochka/llm_mvp_core/blob/dcb931773147267c8864a532351d22b4c351265b/Tests/ExperimentFixes/P5801CorrectiveLessonCounterExampleArmsTests.cs#L252-L324).

Проверка фактических model bytes, импорт текущим продуктом и полнота отрицательных guards остаются отдельными вопросами; эта таблица их не закрывает.

## 4. Требования, которые нужно перенести в остальные карточки

1. **Назвать измеряемый объект и знаменатель.** Отдельно ответ, адрес урока, пригодность rejected, TRAIN recall, novel input, whole-product cost и helper cost. Не подставлять cold score в ceiling.
2. **Фиксировать отношение к TRAIN конкретного плеча.** Изменение метки, sourceId или имени проекта не делает фактический input новым.
3. **Учитывать все вызовы.** Подготовка, numeric oracle, controls и повтор setup входят в полный расход. Локальные counts сохраняются отдельными полями.
4. **Различать source fix и наблюдение.** Исправленный writer, старый frozen output и новый native run — три разных состояния.
5. **Не заменять ограничения метрики общей оценкой.** Полезный address gain сохраняется даже при нулевом answer delta. Recall не называется generalization, а одинаковый score не называется одинаковыми ответами.
6. **Привязывать перенос к текущему caller.** Старый portable script проверяет свой pin; совпадение 8 из 9 blobs не делает весь расчёт актуальным.

Последний пункт проверен здесь непосредственно: старый `recompute_product_measurements.py` закреплён на 55cfd9d; у текущего `TranslationPhraseCompositionPlanner.cs` blob **8e4485b** вместо **44398e8**. Его прежний общий manifest нельзя молча объявить текущим. P54/current helper/wiring проверяет родитель отдельно; настоящий пакет не подменяет эту проверку старой Python-моделью planner.
