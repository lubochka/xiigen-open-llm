## Как чинить тест и когда передавать проблему архитектору

Назначенный исполнитель переноса/QA **обязан собирать продукт и проект тестов, выполнять выбранные проверки, исправлять технические fixtures и неправильные ожидания по независимому договору**. Запрет на runtime исследователю не переносится на него. Общие правила [QA46](../../../experimets/46-qa-execution-test-repair-and-fresh-results-2026-11-03.md) и [120](../../120-executor-context-and-test-repair-contract-2026-11-02.md) сохраняются.

1. Отделить build, discovery, setup, Act, assertion, teardown и внешний timeout. Назвать input/expected/actual и договор, а не только строку падения.
2. Техническую ошибку разрешённого задания исправить и повторить адресную проверку. Нельзя менять gold по actual, добавлять Skip, ослаблять границу или исключать класс ради зелёного счётчика.
3. Если тест требует несуществующего обучения, спорной схемы, нового научного фактора или смены пользовательского контракта — передать архитектору конкретный недостающий вход/решение. Не вшивать ответ и не доучивать при Load. Это не повод запрещать все остальные разрешённые проверки.
4. В эскалации сохранить команду, source/DLL, fixture, полный журнал, failing identity, договор и два ограниченных варианта. Архитектор принимает решение об изменении контракта; routine test repair повторного разрешения не требует.

Поручение заранее включает необходимые read-only чтения кода/дифа/свойств файлов, поиск callers и разбор XML наряду с build/test. Не создавать случайный запрет на диагностику только потому, что её команда не попала в пример запуска. Явный пользовательский закрытый список и запрет чтения секретов сохраняются; реальные значения окружения с секретами не выводятся. Для проверки override нужны известные искусственные значения, не дамп окружения машины.

Временные мутации выполняет один назначенный исполнитель при исключительном владении общей сборкой. Независимый reviewer не запускает конкурирующую сборку в том же bin/obj: чтение результата не требует её, а новый runtime прогон получает согласованное окно. Вторая модель/новый worktree самостоятельно не выбираются. Это координация общего ресурса, а не запрет переносов; после освобождения окна назначенное исполнение продолжается.

### Временное ожидание общего ресурса и возобновление

Поручение переноса/QA включает сборки, discovery, тесты и доказательное исправление теста. Документная сессия автора этой правки не выполняет их и не накладывает свой запрет на исполнителя. Текущее R01 ведёт существующий владелец; второй worker для той же работы не назначается. Фактические owner/handle/пути берутся из живой передачи исполнителя, а не выдумываются из названия карточки.

| Состояние | Что записать и сделать | Когда продолжать |
|---|---|---|
| Общие выходы заняты | `WAIT_RESOURCE`; ID, owner, invocation, полная команда/handle, PID и start identity, пересекающиеся абсолютные пути, место raw/terminal и способ наблюдения | Дождаться terminal существующего процесса, проверить освобождение именно этих путей, переснять source и выполнить назначенный build/test без нового разрешения |
| Владелец или исход процесса неизвестен | Назвать неизвестное; восстановить invocation через существующий launcher/session и terminal. Mtime, одинаковое имя процесса и исчезнувший worker сами по себе не доказывают исход | После установленного исхода и освобождения; не удалять чужой claim, не убивать процесс и не начинать дубликат для выяснения результата |
| Предложены отдельные выходы | Карта абсолютного csproj/config/TFM/RID на restore/assets, obj, bin, generated/copy/publish, raw/TRX, включая весь ProjectReference | Только при доказанной непересекаемости; одинаковые `MSBuildProjectName` требуют различения по полному пути проекта. Иначе последовательное окно |
| Source изменён во время или после сборки | Сохранить compiler-input manifests до/после, реальные DLL hashes/load paths и raw; установить принадлежность binary | Неизменная доказанная DLL остаётся evidence своего снимка. Новый конечный source требует собственной приёмки; неопределённая identity понижает только соответствующую область |

Перед сборкой согласовать короткое окно без записи в затронутые compiler inputs, включая untracked glob-входы. После сборки проверить снимок ещё раз; отсутствие изменений tracked Git diff не доказывает неизменность всех входов. При мутационном контроле возврат исходника и конечная свежая проверка обязательны. Одновременные сборки не аннулируют автоматически обе истории: сначала проверить пересечение выходов и фактическую DLL identity.

Переносы сохраняют приоритет. Ожидаемое долгое ожидание разрешает только уже назначенную независимую работу в её прежнем бюджете; оно само по себе не назначает PRIMARY, новое обучение или новый фактор. Если условие освобождения доступно в этой сессии, дождаться его и продолжить, а не завершать работу отчётом о временной занятости.

## Путь результатов и повторный запуск

R01 должен согласовать существующий launcher и sink, не заводить третий независимый координатор. Root выделяется атомарно **на invocation**, до fixture/setup; static Lazy на тип не является политикой новой попытки. stdout/stderr/TRX, scientific raw и progress имеют одного владельца и разные правила записи. Raw/final неизменяемы; progress, если нужен, имеет явно разрешённое обновление. После seal запись запрещается, в том числе обходным caller.

Для следующего F03-слайса выбрать первый свободный номер внутри `artifacts/fbe/AUDIT-F03-ATTEMPT-OWNERSHIP/` атомарным claim; 0001/0002 сохраняются. Проверка `Test-Path` без исключительного захвата не резервирует каталог. Старые results и чужой `review-2` не перезаписывать и не удалять. Одна проверка не должна молча создавать отдельный постоянный root на каждый внутренний шаг: вложенные случаи принадлежат одному invocation и именуются в manifest. Политика удаления доказательств не вводится этим заданием; бытовая уборка не является лечением роста каталогов.

До claim проверить доступность назначенных команды/host и путь; после claim сохранить даже незавершённый исход. Ошибка каталога и ошибка записи файла имеют разные диагностические стадии. Для отказа прав не менять ACL пользовательского репозитория: сначала законная изолированная test fixture/управляемый native seam. Если настоящая ACL-ветвь не выполнена, указать это; соседний IOException не доказывает её прохождение.

## Ожидание в текущем Codex

Если `exec_command` вернул `session_id`, продолжать `write_stdin` с этим же ID до фактического завершения. Если внешний `functions.exec` вернул `Script running with cell ID`, продолжать `functions.wait` с этим cell ID: он не является PID дочернего процесса. Использовать ограниченное ожидание до60 секунд и короткие содержательные обновления, не пустые запросы и не частый опрос файлов. Ни одно из этих уведомлений само по себе не подтверждает timeout/смерть child. После восстановления сессии сначала связать прежний invocation, PID/start и сохранённый terminal; новый запуск не является способом узнать исход прежнего.
