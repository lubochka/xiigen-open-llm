# Аудит переноса экспериментов в продукт — 12 ноября 2026

## Решение

**Серия переносов содержит подтверждённый прогресс, но общая приёмка реализации остаётся открытой.** Готовый допустимый planner ещё не подключён к обычному caller; часть guards не управляет окончательным verdict; неверные потолки/новизна и неполная цена опыта сохраняются у конкретных writers. Дополнительно доведён до обычного GeneratePlanAsync конкретный механизм: урок чужого flow повышает уверенность выбранного flow, у которого собственного подтверждения нет.

Выполнены свежая проверка исходников, численные пересчёты сохранённых опытов, сверка позднего FIX-P56, независимый review и реальные изменения **девяти существующих документов/карточек в двух репозиториях**. Подготовлен [адресный план десяти работ](codex-repair-plan.md) с владельцами кода, сохраняемыми контрактами, отрицательными контролями и границами приёмки. Продуктовые исправления этим документным пакетом не реализованы.

Дата каталога соответствует 12 ноября в Asia/Jerusalem; промежуточная проверка времени — 11 ноября22:52UTC. Исходный срез core: **dcb931773147267c8864a532351d22b4c351265b**; planning: **405e7e5bcfc245c4f68980175e57912dfd108b96**. Новые commits ниже изменяют документы и переносимые аудиторские скрипты; состояние производственного кода остаётся указанным срезом.

## 1. Что добавил этот проход

### 1.1. Допуск маршрута может подтвердить урок другого маршрута

Условие выведено из актуальных Train, classifier, TryGround, body lookup, обычного facade и composer. Две пары A=(FLOW-01,alpha), B=(FLOW-02,beta); запрос `beta FLOW-01`. С одной A свой nearest score равен0 и результат уходит в Mode2. После добавления B выбранной остаётся A, но global nearestB даёт1/3, confidenceA становится29/30≈0.966667, и выводится тело A. A и её собственное свидетельство не менялись.

Правильная фильтрация тела по выбранному FlowRef уже существует и здесь не нарушена. Проблема раньше неё — принадлежность свидетельства уверенности. Старый текст карточки48 прямо требовал сохранить global lookup на этом шаге. Поэтому исправлена постановка: новый отдельный контроль требует своего witness; прежний body-only FIX-IM сохраняет приёмку.

Это **новый конкретный контрпример в уже известной соседней границе B12**, не новый универсальный класс ошибок. Историческая доска уже просила foreign negative, но не задавала этот положительный чужой witness. Выполнено9 аналитических случаев на6 pinned исходниках; native C# run отсутствует. Формула confidence не объявляется измеренной вероятностью правильности. [Полная трасса, расчёт и приёмка](codex-flow-confidence-review.md).

### 1.2. Поздний FIX-P56 получил отдельную проверку доказательств

Он действительно идёт через public training, ordinary orchestrator, SaveCheckpoint и LoadCheckpoint свежего объекта. Новый пересчёт проверил19blobs,4TRX,36строк трёх receipts: имена и IDs тестов, counters, фактические adapter/text,12stage×case строк в каждой расписке и размер её собственного snapshot.

Сохранённые исходы:2/2pass; на mutant3pass/2fail; после восстановления5/5; после ремонта writer5/5. Ровно два ожидаемых теста падают на мутации. Узкий результат по целому слову в signature branch поддержан доказательствами. При этом mutation удаляет весь word-comparison loop и грубее прежнего Contains; S2 различает исходный substring bug, S4 его не различает. Это ограничение уже было исправлено автором и в новом аудите не переоткрывается как новая ошибка.

Same-process fresh object не называется независимым процессом. Отсутствие phrase-map в панели не подтверждает его admission; общий gain N60 с false-accept регрессией этим пакетом не принят. [Разбор и пересчёт](codex-product-review.md#2-fix-p56-узкий-обычный-путь-подтверждён-сохранёнными-доказательствами).

### 1.3. У F03/B05 установлен ещё один writer, который не обеспечивает исключительность

P56 теперь пишет в отдельный timestamp+PID subdirectory; два поздних опубликованных запуска не столкнулись. Но static Lazy хранит путь на весь загруженный тип, Directory.CreateDirectory допускает существующий каталог, File.WriteAllText заменяет имя. Два invocation в одном процессе получают тот же root. Это source-level остаток владения попыткой, без утверждения о реально наблюдённой новой потере файлов. Добавлен конкретный writer в R01; accepted защита корневых frozen файлов сохраняется. [Кодовая причина](codex-product-review.md#3-f03b05-имеет-ещё-одного-конкретного-writer-fix-p56).

### 1.4. Найдена и исправлена неоднозначность будущего опыта

Planning N35 задавал три домена по два дополнительных heldout prompts, затем называл «все3extra». Датированная поправка фиксирует **6 уникальных heldout строк**,3×2. Это ошибка постановки/счёта, не ошибка фактического обучения: native опыт этой карточки не объявлялся выполненным. Вместе с численностью усилены support/UNMEASURED и запрет подстановки general score вместо отсутствующего security score.

## 4. Что уже работает и почему это сохранено

- **PlanAdmissible уже реализован.** Остаток — подключение обычного потребителя и его приёмка, а не ещё одна реализация алгоритма.
- **FIX-P56 имеет содержательный ordinary-path пакет.** Его ограниченный positive/negative и saved-load результат выдержал новый пересчёт.
- **P58 исправляет ceiling в текущем producer.** Старые frozen metrics не являются основанием снова требовать эту же source-правку.
- **P48/P49 уже учитывают non-finite состояние** в актуальных проверенных validators; это не закрывает другие смысловые ошибки метрик.
- **FIX-IM уже ограничивает body выбранным flow.** Новый confidence defect не отрицает этот перенос.
- **Вынос Wiki Featurize и узкий batch-copy fix имеют прежнюю принятую область.** Resource mutation Wiki оставаласьgreen, а15inventoryfail остались; условия расширения названы отдельно.

Перечень фиксирует основания сохранения узких результатов, а не выдаёт общую повторную приёмку всех затронутых подсистем. Наличие опубликованного теста не означает, что он исполнялся в этой сессии.

## 6. Метод, навыки и ограничения

Работа использовала канонические project skills из `docs/skills`: архитектурную классификацию для owner/caller/state boundaries, phase-planning и plan-review для зависимостей/доз/приёмки, code-examination для цепочки вызовов, prompt-patch-authoring для конкретных исполнительских договоров, experiment-design/test-integrity для oracle/novelty/бюджетов, qa-session-type/debug-session/test-failure-triage/bug-to-tests для различения продукта, fixture, контракта и среды, human-readable-architecture-audit для человеческого объяснения последствий. Автоматизированная QA этой сессии — реальные portable rechecks hashes/identities/numeric outcomes и readback публикаций.

Полное чтение всех многотысячных AGENTS/CLAUDE и всего skill stack **не заявляется**. Прочитаны применимые разделы; experiment-design, test-failure-triage и bug-to-tests прочитаны целиком, у остальных отмечен выборочный охват. Наличие файла в локальном дереве не считается его прочтением. Навыки и AGENTS не редактировались. Один независимый агент работал последовательно; вложенных агентов не было.

Независимый reviewer проверил численный пакет и новый flow counterexample, затем root product packet и добавленные карточки/план. По ревью исправлена формулировка N33: «один arm» могла запретить законное A/B; теперь внутри rate одно окно/arm, а между A/B разные arms с одинаковыми границами измерения. В R03 явно сохранён уже имеющийся GetOrchestratorAsync().RunAsync вместо возможности понизить проверку до прямого Execute. В R05 разделены derived Train0 и native приёмка изменённого writer с фактическим ledger. Уточнён порядок сохранения S-AB до ожидаемого failingassert. Проверка не заменяется числом формальных кругов review.

Выполнены Python-пересчёты трёх пакетов; source blobs проверялись до/после. Локальное извлечение через patch первоначально меняло концы строк; до расчётов источники восстановлены точными GitHub bytes и прошли Git blob SHA. Это исправление нашего чтения, удалённые raw не менялись. Источники пакетов пересекаются, поэтому41+19+6 не объявляются66разными файлами.

**Не выполнено:** native build/test/Train/Predict/Flow/Load — в среде отсутствуют dotnet и PowerShell; повтор всех опытов/всей очереди; свежий full-suite baseline; runtime memory/latency A/B; полное восстановление/перепроверка заявленных6201повреждённых бинарных artifacts; проверка всей матрицы языков и всех publication-coordinator failures. Сообщение пользователя о6201файле сохраняется как отдельная историческая работа, новое независимое число в этом аудите не получено.

Приватные репозитории читались/публиковались GitHub API; branch updates выполняются с expected SHA, без force.
