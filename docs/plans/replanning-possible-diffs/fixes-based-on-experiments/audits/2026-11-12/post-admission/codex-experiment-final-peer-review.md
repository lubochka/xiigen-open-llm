## Замечание ER-FINAL-01: вычислительный порядок R09

В просмотренном R09 предложено `max(logits) + log(sum(exp(logits−max))) − logit_target`. Как вещественная формула это правильно. Если выполнить её слева направо в используемом C# float, прибавление маленького log-слагаемого к большому max теряет это слагаемое до последующего вычитания.

Различающий пример с тем же целевым классом1: logits `[100000000,100000000]`. Правильная CE равна ln2≈0,69314718. Последовательное float32 округление написанного порядка даёт0. Порядок `(max−logit_target) + log(sum(exp(logits−max)))` даёт0,6931471824645996.

Выполненный самостоятельный арифметический контроль, без C# запуска:

```python
import math, struct
f32 = lambda x: struct.unpack('f', struct.pack('f', x))[0]
m = f32(100000000.0)
log_sum = f32(math.log(f32(2.0)))
written_order = f32(f32(m + log_sum) - m)  # 0.0
reordered = f32(f32(m - m) + log_sum)      # 0.6931471824645996
```

**Адресная поправка:** назвать безопасный вычислительный порядок с предварительным `max−target`; добавить common-shift control `[0,0]` и `[1e8,1e8]`, одинаковый target, CE≈ln2 в заранее выбранной tolerance. Проверка `[0,-20]` остаётся отдельным saturation control. Это не новая научная доза и не изменение цели `p−y`; это уточнение численного исполнения уже назначенного ремонта. Автор уведомлён. Остальные выводы этого review от устранения замечания не зависят.
