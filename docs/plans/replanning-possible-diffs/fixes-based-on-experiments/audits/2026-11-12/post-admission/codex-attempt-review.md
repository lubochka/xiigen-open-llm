## 2. Точная причина утраты единственного владельца

[`ExperimentEvidenceSink`](../../../../../../../Tests/ExperimentFixes/ExperimentEvidenceSink.cs), строки 139–149, 169–179 и 251–268: фабрика спрашивает только об отслеживаемых файлах. При нуле возвращает тот же каталог. `WriteTextExactly` создаёт недостающие каталоги и заменяет целевой файл. Два независимых вызова фабрики могут оба завершиться успешно до первой записи; дальнейшая последовательность «A записал → B записал» теряет содержимое A. Даже гонка по времени для этого контрпримера не нужна. Уже существующий untracked файл также не меняет результат успешного Git-запроса.

Fallback при недоступном Git отличается: строки 271–288 считают непустой каталог опубликованным. Поэтому нельзя обобщать дефект на любой непустой каталог и любой способ запуска. Нужна именно доступная Git-проверка с нулём tracked files, либо два ещё пустых адресата до записи.

[`ExperimentEvidenceSinkTests`](../../../../../../../Tests/ExperimentFixes/ExperimentEvidenceSinkTests.cs), строки 54–212: четыре Facts проверяют перенаправление опубликованной попытки, отказ для неё, свежий unpublished каталог и точность байтов. Они не проверяют occupied untracked, два фабричных вызова, жизнь owner handle, закрытую попытку и проигравшего владельца до setup. Поэтому их сохранённый PASS нельзя читать как защиту от конкурирующих writers. При этом сами четыре свойства полезны и должны остаться зелёными после ремонта.

[`TranslationRequiredWholeTermOrdinaryPathTests`](../../../../../../../Tests/ExperimentFixes/TranslationRequiredWholeTermOrdinaryPathTests.cs), строки 234, 255, 516, 549–586: timestamp+PID вычисляется один раз для загруженного типа. Для повторного вызова того же имени файла в этом типе адрес снова совпадает; `CreateDirectory` существующий путь принимает, `WriteAllText` заменяет файл. **Не утверждается, что обычный xUnit уже повторил один Fact внутри процесса или что два последних опубликованных запуска столкнулись.** Это проверенный source-level остаток договора, а не сообщение о новой наблюдённой потере результатов.

## 4. Итог процедуры не вычисляется внутри измеряющего теста

[`P5801CorrectiveLessonCounterExampleArmsTests`](../../../../../../../Tests/ExperimentFixes/P5801CorrectiveLessonCounterExampleArmsTests.cs): ранние проверки обучения и наличия ошибочной строки стоят в 661–675, `DecideReceipt` — в 697–698, status/report — в 901–908, последняя проверка — в 913–914. Внутренний документ отражает решение этого валидатора. Он не знает будущий исход записи report, соседнего Fact, fixture teardown, процесса и TRX. При no-contrast путь завершается до полного status; уже записанные setup/train-control не надо стирать или переименовывать в успешную полную попытку.

[`Learn07RollbackRunnerTests`](../../../../../../../Tests/Learn07RollbackRunnerTests.cs), строки 108–111, уже честно пишет `ExitCode:null` для in-process probes. Прежнее замечание «любой такой writer подставляет нулевой exit» здесь было бы устаревшим. В то же время строки 39–41 выбирают общий фиксированный artifact root, 168–173 публикуют report/validation/parent-review/state patch, а проверки артефактов выполняются после этого, в 175–176. Последний assertion ещё может упасть. Подпись `ACCEPTED_FOR_PHASE_COMMIT_WITH_LIMITATIONS` — локальное содержимое документа; она не должна закрывать внешнюю приёмку.

Внешний итог должен привязать фактический exit процесса, полный required-test inventory, полученные IDs/кратность, SHA исходников и assembly, команды и хеши stdout/stderr/TRX. При late-failure полезный raw остаётся, но внешний результат — FAILED/INCOMPLETE, а не ноль из inner JSON. Техническая валидность, научный отрицательный результат и допуск продукта остаются разными полями.

## 5. Два узких контрпримера к отчётности и описи

### 5.1. Missing TRX

В [`summarize-test-batches.ps1`](../../../../../../../tools/test-batches/summarize-test-batches.ps1) missing-file fallback присутствует и для leaf (409–414), и для batch (536–541). Состояние из journal отдельно решает, увеличивать ли OpenCount и ReadableBatchCount (548–560).

Фикстура: одна строка `COMPLETED_GREEN`, `total=1`, `passed=1`, остальные нули; путь TRX отсутствует. Перевод именно этих ветвей на Python даёт `passed=1`, `OpenCount=0`, `ReadableBatchCount=1` при `trx_exists=false`. Нужно сохранить журнал как вторичный источник, но пометить его `JOURNAL_ONLY/NOT_PROVEN_RAW` и не повышать readable/accepted. Существующий self-check с настоящими синтетическими TRX и timeout leaf (749–786) эту missing-TRX комбинацию не проверяет.

### 5.2. Empty solution fallback

[`TestSuiteBatchManifest.cs`](../../../../../../../Tests/TestSuiteBatchManifest.cs), строки 2007–2016: рекурсивный fallback выбран по `declaredProjects.Count == 0`. Reader 2020–2057 не отличает отсутствие решения от присутствующего решения без подходящих существующих `.csproj`; отсутствующие объявленные проекты просто пропускает.

Файловые фикстуры подтверждают две разные ситуации: без `.sln` широкий поиск нужен синтетическим тестам; с пустым `.sln` или единственным объявлением отсутствующего проекта он снова включает `artifacts/foreign-copy/Foreign.csproj`. Непустое корректное решение выбирает только объявленный проект — положительное исправление сохраняется. Контрпример доказывает ошибку candidate enumeration, **не текущую порчу канонического solution, не дополнительный запуск чужого проекта и не новое число провалившихся native tests**.

Минимальный план: вернуть отдельные сведения `solution found`, объявленные пути, отсутствующие пути и ошибки разбора. Для real solution отсутствие пригодных проектов означает диагностический отказ/неполную опись. Synthetic fallback включается явным параметром для синтетического корня. Новые assertions не ослабляют список настоящих проектов.

```bash

```

Получено 11 записей наблюдений, объединённых в восемь сценариев C1–C8. C8 содержит четыре варианта решения. C1–C4 и C8 — файловое исполнение переведённых ветвей; C5 — только положительный reference control исключительного создания; C6 — настоящий Python child, который пишет inner exit=0 и завершается exit=7; C7 — перевод конкретной PowerShell-ветви. Это **не 11 C# tests, не новая приёмка launcher и не результат ремонта**. Исходники и их SHA перечислены в JSON; Train=0.

Сам генератор расписки создаёт выходной файл исключительно, до запуска проб, и отказывает при уже существующем файле. Ошибка после захвата оставляет незавершённый файл, который не следует принимать за законченную JSON-расписку.

## 7. Приёмка следующего ремонта

В порядке, достаточном для этой находки:

1. Восстановить один run context существующего executor; захватить owner до fixture/setup/model call; определить все writer roots и правила закрытия. Прямая xUnit команда должна получить этот же контекст либо явно отказать до работы.
2. Добавить native инфраструктурные cases без модели: occupied untracked root; два владельца одного адреса; повтор внутри одного host; sealed/abandoned attempt; отказ writer после захвата; оба способа сохранения bytes и обход через `ResolvePath`; неверный/выходящий за root путь. У проигравшего все setup/Train counters равны нулю; прежние хеши неизменны.
3. На искусственном child проверить полный успех, поздний assertion/ненулевой exit, timeout/abort, missing TRX, missing required test и incomplete teardown. Перечень expected IDs фиксируется до запуска, а вывод составляется из результатов того же child/assembly.
4. Подключить FIX-P56 и существующего потребителя общего sink к этому же пути. Использовать разрешённый ограниченный regression после проверки инфраструктуры; исторические PRIMARY не повторять ради отчёта. Отдельно исправить fixed artifact writer Learn07.
5. Проверить три inventory случая: нет решения в явно synthetic режиме; пустое/испорченное real solution; корректное решение с foreign-copy рядом. Первый и третий — законные контроли, второй — диагностический отказ без расширения охвата.
6. Провести проверку на итоговой сборке и записать полный terminal. Пока native cases не исполнены, статус — план ремонта и source-level подтверждённый остаток.
