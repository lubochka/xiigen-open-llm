## Профилактика для остальных карточек

Каждая применимая карточка должна ответить на вопросы ниже своим содержанием. Вставка общей фразы «соблюдать качество» не заменяет ответа.

1. **Где результат станет наблюдаемым?** Именовать реальный вход, получателя, запись состояния и consumer. Правильная метка без правильного конечного ответа закрывает только метку. Правильный FlowRef без правильного PlanText не закрывает план.
2. **Какой дефект обнаружит отрицательный пример?** Для исправления порядка admission/cap — годный кандидат после нескольких негодных; для UTF-8 — граница внутри многобайтного символа; для shifted window — ровно граница окна и на один токен больше; для metadata carrier — одноразовая последовательность и неверный тип. Контроль должен ломать обещанный механизм, не только отсутствие метода.
3. **Что случится на следующем действии?** Добавить, исправить, повторить, продолжить после restore. Поведение replace/append, конфликт цели, dedup и active revision описать отдельно. Не расширять каждую локальную карточку до всей платформы.
4. **Что считается тем же состоянием?** Помимо весов — tokenizer, RNG, индексы, словари, schema, learner/receiver identity и версия, если они определяют ответ. Копия объекта и свежая загрузка с диска — разные доказательства.
5. **Можно ли получить этот результат без изучаемого механизма?** Constant/majority baseline, нулевое пересечение признаков, постоянная проекция, одинаковые кандидаты и target leakage. Проверять фактический вход модели, не имена переменных.
6. **Что означает EXAM?** Поимённо проверить пересечение с TRAIN по входу и цели, семье/проекту при соответствующем обещании. Exact recall полезен и должен называться прямо. Для generalization нужно независимое множество и заранее зафиксированный oracle.
7. **Был ли учебный этап численно и операционно исполнен?** Attempted/completed updates, изменение состояния, finite guard, terminal outcome. Конечность каждого участвующего плеча должна управлять действительностью сравнения, а не только печататься в отчёте. NaN означает численный отказ уже начатого обучения; ноль updates — отдельный исход; неизмеренный ресурс — не ноль. Отрицательный контроль повреждает только одно плечо при успешном втором.
8. **Откуда ожидание?** Независимый договор/данные/математический oracle. Actual предыдущего запуска не становится gold автоматически. Любой ремонт теста объясняет, почему ошибся тест или implementation.
9. **Можно ли прочитать результат в новом процессе?** Назвать API и payload; Train при readback равен нулю; нормализация gold не восстанавливает отсутствующий learned state. Reflection в опыте не выдаётся за native import.
10. **Сможет ли следующий запуск уничтожить доказательство?** Входные artifacts неизменяемы, output root уникален, публикация отделена от вычисления, исходники и сборка привязаны к попытке.

## Как усилен промпт исполнителя

Вместо «реализуй карточку, запусти тесты, добейся зелёного» постановка должна содержать самостоятельные поля:

> Проблема и наблюдаемый эффект. Проверенный source и состояние существующей приёмки. Конкретный owner и место вызова. Данные и независимый oracle. Positive/negative и следующий шаг жизненного цикла. Допустимые изменения и всё ещё открытые продуктовые решения. Полный бюджет и output root. Именованный набор проверок и критерий terminal outcome. Что нельзя утверждать по полученному результату.

Задание на аудит документов не содержит скрытого разрешения нового Train. Задание на назначенный кодовый ремонт включает необходимые локальные проверки и исправление fixture по независимому договору; исполнитель не останавливается за повторным разрешением на каждый такой шаг. Если текущий код уже исправлен, он сохраняет принятую область и проверяет только открытый остаток.

## Применённые принципы навыков

Таблица перечисляет использованные принципы и их источники; она не означает, что каждый большой файл прочитан целиком или что загружен весь каталог. Точный объём чтения независимой части, включая частичное чтение `test-integrity` и полученные, но не полностью прочитанные большие документы, указан в `experiment-review.md`, §7. Принцип навыка не заменяет доказательство исполнения его проверок.

| Направление | Проектные источники | Применение в этой поставке |
|---|---|---|
| Архитектура | `human-readable-architecture-audit`, `architectural-decision-testing`, `learning-path-audit` | Причинная цепочка и границы consumer, активная цель, существующее решение о месте contracts; не объявлять API работающим продуктовым путём |
| Планирование и проверка | `plan-self-validation`, `task-slice-golden-rule`, `plan-execution-feedback` | Отдельные открытые остатки, зависимости и бюджеты; история сохранена; действие не замещено одной записью статуса |
| Код | `code-examination`, `claim-verification` | Символ и ветвление прочитаны; blob проверен; вывод из кода не называется выполненным тестом |
| Эксперименты | `experiment-design`, `improvement-measurement`, `score-interpretation` | Исправленная производная отделена от фактора; overlap, ceiling и gained/lost; проценты и п.п. различены |
| QA / automation / debug | `qa-session-type`, `test-integrity`, `test-failure-triage` | TRX разобраны по именам и stack; писатель receipts включён в тестируемую границу; native UNRUN явно сохранён |
| Промпты | `prompt-patch-authoring` | Причина ошибки преобразована в конкретное исполнимое условие, с положительным и отрицательным примером |
| Коммуникация | `human-communication-GLOSSARY`, human-readable audit | Тема обучения, механизм, получатель и измерение различены; выводы выражены через пользовательский результат |

Общие примеры из навыков не являются разрешением добавлять произвольные данные, API, новые модели или всеобъемлющую учебную программу. Нужная глубина задаётся конкретным дефектом и обещанием карточки.
