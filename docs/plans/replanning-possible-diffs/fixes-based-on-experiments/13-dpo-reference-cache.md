При этом chosen NLL слегка ухудшился одинаково в A и B: `0.0002897947 → 0.00029096575` для первой строки и `0.00030099385 → 0.0003021206` для второй. Это общий BEFORE→AFTER эффект двух DPO-шагов, а не ухудшение, вызванное кэшем. Это teacher-forced чтение **тех же двух TRAIN-строк**, Generate=0; перенос на свободные ответы и held-out качество не измерен. Raw не содержит полного побайтового сравнения финальных весов/AdamW/RNG: равенство сохранённых метрик не повышать до доказанного равенства всего состояния.

Измеренный выигрыш памяти действителен по этой оси; роста accuracy для успеха не требуется. Один фиксированный A→B без прогрева/перестановки не устанавливает устойчивое ускорение. Нельзя из этого результата объявлять универсальный выигрыш на потоке уникальных пар, где попаданий мало.

### Дефект инструментирования, который нельзя перенести

В B `step1Timing.PolicyForward` и `step2Timing.PolicyForward` содержат `StartedCalls=2`, `CompletedCalls=4`, `IncompleteCalls=-2`. ReferenceForward у B за два шага записан как 6 completed, причём второй шаг имеет 2 completed за 0,1853 мс. Это несовместимо с трактовкой каждого счётчика как отдельного фактического модельного Forward. Исторический raw сохраняется без исправления; его нельзя использовать как строгий oracle числа проходов. **Текущий продуктовый timing корректен:** в `11.DPO/DpoTrainer.cs:878–889` каждый reference/policy helper уже имеет собственную пару Begin/Complete. Дефект относится только к исторической инструментированной B-копии. При переносе cache сохранить эти границы и не копировать ошибку B; отдельного ремонта существующего timing этот план не назначает.

Источник контракта: [`DpoStepVectorTiming`](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/11.DPO/DpoStepVectorTiming.cs) и [`DpoStepVectorTimingTests`](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/Tests/DpoStepVectorTimingTests.cs#L29). `Complete` вызывается только для действительно начатого и завершённого helper; `CompletedCalls <= StartedCalls` всегда.

## Продуктовый получатель и замкнутые решения

Фактический путь: [`StepVectorCore`](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/11.DPO/DpoTrainer.cs#L832) → `CaptureBatch`/admission → `AcquireMutationPermit` → `ExecuteWithPublication` → два `BatchLogProbs(_reference, ...)` → policy chosen/rejected → backward → AdamW. В существующих строках879/882 повторяются именно эталонные likelihood, потребляемые DPO objective. Кэш не выбирает chosen/rejected и не оценивает их внешнее качество.

| Решение | Точный первый перенос |
|---|---|
| Владелец | Один `DpoTrainer`, private cache; никакого static/global/session-wide хранилища. Новый тренер всегда пустой. |

Кэш не входит в checkpoint и не восстанавливается с диска. **Уточнение фазовой границы (29.10, раздел 4 плана 95).** Это не blanket «любая ошибка очищает всё», а три разные фазы. (i) Отказ допуска **до** мутации — несовпадение профиля, `RequireAllowedState`, отсутствующий или несовпавший continuation proof — происходит раньше любого изменения и прогретый cache не трогает: очищать там нечего и нельзя, иначе отклонённый вызов молча обесценивал бы чужую законную память. (ii) Успешная ветвь очищает cache **после** завершения разрешённого импорта и **до** возврата `true`: с этого момента тренер продолжает другое состояние, и прежние ответы эталона ему больше не принадлежат, даже если сам эталон не менялся. (iii) Сбой **после** начала восстановления очищает cache прежним откатом `RestoreContinuationState`, отдельной очистки не добавляется. Границы (i) и (ii) разделяет именно допуск: до него прогретое состояние неприкосновенно, после него оно недействительно. |
| Потоки | Изменения cache находятся внутри существующей критической секции policy mutation. Не добавлять параллельное обучение одним trainer. |

Ключ не должен заново хэшировать полный reference на каждом lookup. `DpoProjectLoraRecipient` уже фиксирует `_referenceHash` при Capture; предоставить внутреннюю immutable identity для cache. **Existing `RequireValid` с проверкой frozen reference не ослаблять**: экономия reference Forward не разрешает убирать защитную проверку. Не использовать `GetHashCode`, только уже проверенный точный digest/ordinal equality. Привязка tokenizer в cache не заменяет текущий validation contract и не создаёт новую независимую authority.

Изменяемые при реализации файлы: `11.DPO/DpoTrainer.cs`; новый внутренний `11.DPO/DpoReferenceScoreCache.cs`; при добавлении отдельной статистики — `11.DPO/DpoStepVectorTiming.cs`. Это ось теста, не отключение admission. Для legacy recipient cache всегда отключён.

Сохранение уже корректного инструментирования: Begin/Complete `ReferenceForward` обрамляет **каждый фактический** вызов `BatchLogProbs`; cache hit не вызывает эту фазу. Для двух разных пар в шаге1: ref4/policy4/backward4/optimizer1. Для тех же пар в шаге2: ref0/policy4/backward4/optimizer1, cache hits2. Отказавший helper даёт started-only и не получает выдуманную длительность завершения.

Для `ThirdPair_EvictsOldestOfTwoWithoutChangingScores` и material-части `ChangedMaterialOrTokenizer_DoesNotReusePriorEntry` назначается один tiny run по реальному [DpoStepVectorTimingTests](https://github.com/lubochka/llm_mvp_core/blob/2297566a5c07b564031337c2b5d4187ca10ca729/Tests/DpoStepVectorTimingTests.cs): V256/C8/H8/L1/Q2/KV1/FF16, q/v LoRA rank2/alpha4/dropout0, seed73 и streams `tiny.policy`/`tiny.reference`, tokenizer `Train("fixture",256)`. Это инженерная проверка производного кэша внутри учебного шага, не самостоятельное доказательство приобретения навыка и не новая TRAIN-строка LC H512.

Три точных `(prompt, chosen, rejected)`:

- pA=`("a","b","cc")` и pB=`("d","ee","f")` — существующие две пары tiny fixture;
- pC=`("a","bb","cc")` — заранее назначенный valid changed-material input: другой chosen при прежнем prompt, в том же допустимом profile. `DpoExactPairMaterial.CreateBatch` и существующий test admission строят реальный digest, ручная подмена hash запрещена.

Один trainer с capacity2 получает по одной паре в каждом StepVector: **pA → pB → pA → pC → pA**, steps1–5. Состояние FIFO: `[A] → [A,B] → [A,B] → [B,C] → [C,A]`. Один hit не переставляет A; итог hits1/misses4/stores4/evictions2. Бюджет этого run: **5 optimizer updates, 8 reference + 10 policy = 18 Forward, 10 Backward**, без дополнительных readout/Generate и без H512 acquisition. Обе named проверки читают одну immutable квитанцию `artifacts/fbe/FIX-LC/attempt-0001/resources/tiny-lifecycle.json`; повторять пять steps для каждого assert нельзя. State/score correctness основного кэша уже покрывает H512 parity; маленький companion проверяет смену материала и eviction, не объявляет measured learning accuracy.

`GetOrCompute` — планируемый внутренний метод нового `DpoReferenceScoreCache`, вызываемый StepVector **после** его admission/recipient checks; factory возвращает только целую пару scalar scores. Half-pair и различие tokenizer-key проверяются прямыми contract calls к этому же объекту, с0model Forward/Backward/updates. Они дополняют native learning test, не подменяют его. У tiny V256 обучение другого корпуса до того же vocab256 не создаёт автоматически иной tokenizer; такой тест не должен утверждать проверенный новый key. Материал с иной tokenizer identity, несовместимый с захваченным execution profile, остаётся отдельным **отказом до cache hit**, а не ожидаемым допустимым miss.

Restore и publication rollback использовать только через существующие proof-bearing fixtures из `DpoTrainerOptimizerStateHandoffTests`, с их реальными continuation identities и отдельными receipts. У `TimingTests.Trainer` continuation proof равен null: `TryRestoreContinuationState` после step5 на этом owner недопустим; этот tiny run не расширяется ложным restore. Новый owner имеет пустой cache, но одно это не доказывает same-owner restore. `DpoTrainer` не реализует IDisposable; не назначать несуществующий `trainer.Dispose()`.
