## 2. FIX-IL: совместить допуск длины с владельцем SFT

**Основание:** [N63IL/results-after-fix](../../../../experiments-v2/RP01-MICRO/N63IL/results-after-fix/report.md): A отказал до mutation, B выполнил 200 SFT updates и изменил TRAIN `3/42→4/42`. Снижение NLL и ухудшение Pos.cs остаются в прежнем плане. Первоначальная попытка с duplicate SourceId не является учебным результатом.

Native `IncrementalTrainer.Capture/TrainAsync` сначала материализует и проверяет все последовательности `Prompt + LF + Response`; [проверка длины](../../../../14.ContinuousLearning/Training/IncrementalTrainer.cs) до update сохраняет атомарный отказ. Product helper остаётся **`SupervisedContextAdmission`**, уже назначенный прежним IL; не создавать конкурирующий `SupervisedTrainingAdmissionPlanner` или второй publisher.

Планируемый `CodeDocumentationSupervisedContinuationCoordinator` владельца MC получает явно именованный **`BoundedSupervisedBatchV1`** профиль. Он дополняет одноурочный MC-профиль, не меняет его default. В профиле закреплены `maxSubmitted=300`, `maxAcceptedUpdates=200`, dataset/source identity, parent/tokenizer/context, scheduler policy и сохранённые настройки IL. Эти значения — пределы данного server-owned профиля, не константы длины для всех моделей. Клиентский prompt не может их менять.

Последовательность назначения:

1. До A реализуется необходимый MC SFT-only owner и механический bounded-profile seam с прежней политикой **`RejectWholeBatch`**. Это отдельная common-предпосылка, одинаковая для A/B; её review не засчитывает полезность IL. Выбранный профиль и оба лимита входят в immutable intent. Никаких фиктивных DPO-пар для открытия SFT.
2. Сначала проверяются provenance/уникальность SourceId/валидность всех submitted rows, включая будущие deferred. Проверка `maxSubmitted` предшествует любому model call.
3. На A полный список из 300 строк достигает строгой проверки контекста и даёт `TRAINING_EXAMPLE_CONTEXT_EXCEEDED`. **Проверка квоты accepted updates выполняется после проверки контекста**, иначе A упадёт по другому основанию и не воспроизведёт фактор. На B `SupervisedContextAdmission` отделяет 100 длинных строк до строгого trainer и передаёт 200 допустимых.
4. В обеих руках после валидации фактически исполняемого списка проверяется `count <= maxAcceptedUpdates`. Список из 300 допустимых коротких строк обязан отказать до первого update; нельзя молча взять первые 200. Это один zero-training contract case, не новый учебный набор.
5. В native transaction сохраняются исходный ordered batch digest, решение по каждой строке, admitted digest и **фактические** updates. Deferred не помечаются обученными. MC exact-parent/acceptance/publication/retry остаются единственным владельцем.

Основная учебная проверка остаётся из прежнего IL: два `IncrementalTrainer.TrainAsync`, A=0/B=200 updates, 200 training Forward/Backward и 20 диагностических Forward; готовый PA01 parent step1000→1200, без повторных 1000 шагов. Их существующий spy проверяет список из 200 и deferred100; новый zero-training case квоты входит в тот же `AdmissionContracts` Fact. Число конечных подслучаев этого Fact становится **8 вместо 7**; других новых processes/fit нет.

**Два разных native пути.** Изолированный учебный `CaptureLearning` вызывает строгий `IncrementalTrainer.TrainAsync` с test-only `IIncrementalTrainingSessionFactory`, восстанавливающей полный PA fixture; A передаёт300, B200 после настоящего admission helper. Product wiring отдельно использует SFT-only sibling `IncrementalTrainer.TrainSupervisedTransactionAsync` владельца MC и canonical tiny parent; repository-owned DPO transaction не заменяется фиктивной парой, private PA manifest не импортируется как product grant. Для shifted profile:

- Полный material сохраняет все T IDs/targets/masks и свой исходный digest. В `Forward` policy **и** reference поступает prefix длины T−1.
- Capacity проверяется по T−1 против `min(policy.ContextLength, reference.ContextLength)`, T≥2. Scoring row i предсказывает полный target i+1; последняя цель остаётся учтённой. Rank/shape проверяются до обращения к `Dimensions[1]`.
- Loop bound для shifted readout/backward — число доступных logits rows, ограниченное `fullTargetCount−1`; нельзя сохранить старый `logitsT−1` и потерять последнюю цель второй раз. Legacy full-input loop сохраняется.
- Execution profile и ключ reference-cache включают convention и execution length. Один material digest сам по себе не различает две вычислительные постановки. Existing cache LC не может вернуть full-input receipt как shifted receipt; content admission при этом не получает новую семантику текста.
- Старые public/default overloads остаются legacy до явного выбора нового профиля. Старый capacity test `DpoExactPairMaterialTests` не переписывается на success; новый profile проверяется отдельно. Если меняется constructor/deconstruct, сохранить прежние формы вызова.

**Eligibility и совместимость с уже принятыми факторами.** `ExactShiftedInputV1` применим только при LoRA dropout0 и у policy, и у reference. Для ненулевого dropout causal prefix не доказывает равенство RNG draws/траектории после удаления позиции: сохраняется legacy full-input `T≤C`, а `T=C+1` отказывает до Forward. Профиль определяется проверенным recipient, не prompt. Если FIX-PD уже принят, T — valid full length каждой стороны, а не padded width. Если FIX-NH уже принят, logits имеют R выбранных rows; scoring/backward используют сохранённую original-row map → target/mask `i+1`. Требование `logitsRows==T−1` относится только к обычной полной голове; выбранные rows не сокращают causal hidden prefix. Эти условия расширяют назначенный descriptor22, не создают второй профиль/кэш.

В `ScTensorContracts` сохраняются **6** заранее назначенных случаев. Case `TargetRowCount` включает обе convention и проверку их различия в profile/cache key; случай «последняя цель отличается от предпоследней» проверяет ненулевой последний gradient. В тех же TargetRowCount/invalid-input cases проверить выбранную row-map и отказ nonzero-dropout на границе без Forward. Это расширение assertions на тех же tensors, не дополнительная модельная проверка.

<a id="fix-rpe"></a>
**FIX-RPE.** У существующего frequency builder нет observer для надёжной отмены ровно в середине cache miss. ## 6. FIX-SVD: точные native тесты и граница математического вывода

Владелец уже назначил `FitFixedTraining`/`EvaluateFixedPanel` в [E10SvdPmiEmbedding.cs](../../../../34.Experiments/Experiments/E10SvdPmiEmbedding.cs).
