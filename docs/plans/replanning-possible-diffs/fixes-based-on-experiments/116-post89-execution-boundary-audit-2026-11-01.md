## 3. RF02: подписанные дополнительные входы не проверяются перед процессом

**Owner:** [New-RunBinding.ps1](https://github.com/lubochka/llm_mvp_core/blob/c4d05a27963fc3edb59f5f75bb097a1fc9936654/experiments-v2/_runners/run-binding/New-RunBinding.ps1), `New-RunBinding` и `Invoke-BoundRun`. Helper SHA256: `fbc67b2faff30f4574046637021f19f8c278b7add7cd7feda6cb2d3276a4663a`.

При подготовке helper принимает RequiredDataPaths, OptionalDataPaths и ExtraSourcePaths. Все группы получают fingerprints; extra также записывается в state. Перед child перечитываются source closure, project/import identities, required inputs, assembly/runtime/deps и arguments. **Optional inputs и extra_sources в этой фазе не перечитываются.** Неизменившийся путь аргумента не обнаруживает изменившееся содержимое файла.

Проба использует настоящий неизменённый `Invoke-BoundRun` и его настоящий запуск `dotnet`. Binding вручную сформирован на входе фазы 6, а маленький Reader читает три текстовых файла; он не использует модель. Это намеренно узкий контрпример к prelaunch contract, не имитация результата Reader.

| Случай | Наблюдение успешной версии harness |
|---|---|
| Все bytes прежние | Child exit0, прочитаны BEFORE |
| Изменён extra source | Child exit0, прочитан EXTRA_AFTER — дефект |
| Изменён существующий optional | Child exit0, прочитан OPTIONAL_AFTER — дефект |
| Ранее отсутствующий optional появился | Child exit0, прочитан OPTIONAL_APPEARED — дефект |
| Изменён required input | DATA_CHANGED_AFTER_BUILD доchild — положительный контроль отказа |
| Изменён linked source fingerprint | LINKED_SOURCE_CHANGED доchild — положительный контроль отказа |

Optional drift уже обсуждался в 103§6.б: у конкретного P20caller metrics перенесли в required. Этот ремонт сохраняется, но не закрывает общую API-границу. `extra_sources` — отдельно проверенный здесь остаток; абсолютная новизна во всём проекте не утверждается. Статический Test-RunnerContract проверяет форму вызова, а не эти изменения содержимого.

**Минимальный ремонт RF02d:** определить все реально потребляемые входы, перепроверять их before launch, а для позднего чтения обеспечить immutable snapshot/owned handle. Изменение, исчезновение и появление optional — разные контроли; missing→missing и unchanged — допустимые positive controls. Полный путь New-RunBinding→Invoke на поддерживаемой платформе проверяется отдельно. Существующие RF02 effective ProjectReference properties и legacy-terminal admission остаются самостоятельными обязанностями по 114.

Первая версия нашего Reader имела ошибочный deps manifest `{}`: четыре child завершились 134 до чтения файлов. Эти данные сохранены и не считаются доказательством consumer bytes. После ремонта только audit harness четыреchild прочитали файлы и завершились 0. Независимый reviewer проверил оба набора; [validator](../../../../experiments-v2/_audits/2026-11-01-post89-execution-boundary-audit/validate_binding_evidence.py) читает только сохранённые state/terminal/stdout/fingerprints, требует exact six cases и явно возвращает `product_pass=false`.

## 5. P89: точность вывода и правильный перенос

[effective-p89.json](../../../../experiments-v2/_audits/2026-11-01-post89-execution-boundary-audit/effective-p89.json) связывает вывод с 11 исходными JSON через SHA256/Git blob. Это отдельное вычисленное уточнение, а не исправление исторического raw.

| Поле | Исходный PRIMARY | Сохранённое фактическое исполнение |
|---|---|---|
| Обучающий vector |60 единиц, Signal2 |60 слотов,5 активных, Signal1.0833334≈13/12 |
| Optimizer start |Импорт moments/step400 |Свежий DPO, step0; донорская линия по весам |
| Stop threshold/window/max |.002/1/5 |.002/1/5 |
| Обновления A/B |Предел 5 наarm |3/3; monitor false,false,true в обоих |
| Ответы |Проверка качества/retention |2/4 общих и 1/2EXAM до/после без изменения |
| Расход |Лимиты future recipe |6updates,16generation,16scoring forwards; training forward/backward не измерены |

На записанных десятичных числах weighted deltas равны.00022650/.00022655, unscaled —.00020910/.00020916. При фактическом threshold.002 обе последовательности дают ту же остановку. Достаточный интервал для различия на сохранённом трёхточечном префиксе — `.00020916 < threshold <= .00022650`; это арифметическое условие по округлённым records, **не наблюдение дальнейшего выполнения доstep5 и не 40%экономии**. Фактически сэкономленных updates здесь 0.

Оракул `weighted = Signal * (weighted / Signal)` проверяет согласованность деления, но не независимый расчёт немасштабированной потери. Для heterogeneous batch нужен сумматор до индивидуального Signal. Например, при α=(.5,.5), s=(1,2), loss=(.2,.8): weighted=.9, unscaled=.5, но `.9/mean(s)=.6`. Этот чистый арифметический контрпример включён в P89 и план; он не требует обучения.

На закреплённом текущем source `DpoTrainer` масштабирует вклад VectorSignal, а `LogicalDpoTrainingUnit.ExecuteAsync` передаёт `lastMetrics.Loss` в ShouldStop. **Продуктовый перенос unscaled monitor ещё не выполнен.** Он должен сохранить прежнюю weighted метрику для совместимости, не менять gradient/update, добавить явную unscaled величину и проверить настоящий consumer, включая разные Signalв одномbatch. RF10 устраняет недостижимость наблюдений; правильный масштаб наблюдаемой величины — другая обязанность.
