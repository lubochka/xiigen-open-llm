### Какой перенос ещё не обоснован

Сравниваемый старый метод — [E50DomainGraphClosure.BuildEdges](../../../../../35.ExperimentsV2/Experiments/E50DomainGraphClosure.cs):86–100 в `35.ExperimentsV2`. Там направление действительно задаётся `i < j` и `edges.Add((i,j))`. Это экспериментальный consumer; из этого не следует, что весь продукт строит графы такой эвристикой.

В текущем проекте 21 уже существуют другие, разные по полномочиям пути: `LogicalRegistryDynamicGraphProjector.Project`:97–138 читает transitions реестра, строит и валидирует topology; `DeterministicDynamicGraphTopologyBuilder.BuildDynamicTopology`:22–82 проверяет предложенную topology и бюджет; `DynamicGraphEdgeFlow` заявляет learned target handoff, а `EdgeAuthorityDecision` уже содержит `OrderedTargets`. В этой работе прочитаны соответствующие фрагменты, но полный путь от сырого пользовательского текста до исполнения всех этих компонентов не прослежен. Поэтому новый глобальный графовый router не назначается. Первый будущий архитектурный шаг — выбрать один настоящий consumer существующей системы и показать, где именно он читает обученный порядок; до этого перенос в продукт условный.

### Аналитический контрпример к фразе «позиционные признаки не нужны»

Сохранённая S1 без позиционных предикатов дала 12/12. Это факт панели. Но `report.md`:128 и генерирующая его строка `Program.cs`:1501 объясняют его тем, что BPE сохраняет порядок благодаря соседству слияний. Такое общее объяснение не выдерживает чтения кода:

1. [RegexSplitter.cs](../../../../../01.Tokenizer/RegexSplitter.cs):16–21 выделяет отдельные словесные chunks, в том числе с ведущим пробелом.
2. [BpeTokenizer.Encode](../../../../../01.Tokenizer/BpeTokenizer.cs):125–134 выполняет `ApplyMerges` **внутри каждого chunk**, затем соединяет списки токенов.
3. `KnnLogicalUnit.Vectorize`:438–469 суммирует количества токенов в 32 ячейки первой половины вектора. Порядок списка токенов далее не сохраняется. Без предикатов вторая половина пуста.

Аналитическая пара, **не выполненный probe**:

```text
x = please review code then implement change
y = please implement change then review code
gold(x) = review→implement
gold(y) = implement→review
```

У x и y совпадает мультимножество chunks: `please`, ` review`, ` code`, ` then`, ` implement`, ` change`. Для одного фиксированного tokenizer сумма количества его токенов совпадает независимо от перестановки chunks. Следовательно, при пустых предикатах `V(x)=V(y)`, включая нормализацию и последующее хеширование в 32 ячейки. Детерминированный reader одной и той же обученной памяти не может различить такие входы; на сбалансированной паре с разными правильными маршрутами его потолок — **1/2**. Это математическая граница представления; фактическое поведение нового прогона здесь неизвестно.

Исходный успех P50 не аннулируется. Снимается более широкий вывод о ненужности признаков порядка. В частности, разные формы `review/reviewing`, первый chunk без ведущего пробела и прочие особенности короткой панели могут давать различия без представления общего порядка. Конкретный вклад каждого такого признака не измерен.

### Будущий ограниченный учебный рецепт: только предложение

Это новая проверка границы, а не повтор исторического P50 ради статуса. Её запуск требует отдельной прямой авторизации. Номер карточки назначает родитель; этим review новая executable карточка не создаётся.

**Одинаковая основа A/B:** настоящий `KnnLogicalUnit<string, OrderedRoute>`, `dimensions=64`, `k=1`, `confidenceFloor=0`, одинаковый порядок учебных текстов, один и тот же алгоритм BPE и его настройки, одинаковая политика `KnnAnswerSnapshot.FromCopy`, один обычный `ExecuteAsync`. Не менять расстояние, score, HNSW, gold, пороги или graph adapter между плечами. Два независимых fit одинакового корпуса обязаны записать одинаковое описание tokenizer; отсутствие доступного native export не обходить reflection или повторным обучением под видом restore.

**Единственный фактор:** A передаёт пустые `PredicateIds`; B передаёт уже существующую функцию `PositionalPredicates` из P5001:1068–1074 — `W{позиция}_{слово}`. Она читает только входной текст, не `GoldRoute`, `GoldSteps`, RowId, Kind, ожидаемый класс или имя файла. Нельзя добавлять score «review должен быть первым». Хеш-коллизии предикатов возможны; B заранее не обещается 2/2.

TRAIN из десяти строк, ровно в таком порядке:

| ID | Текст | Правильный маршрут |
|---|---|---|
| u1 | `review code then implement change` | review→implement |
| u2 | `inspect code then implement change` | review→implement |
| u3 | `review module before editing it` | review→implement |
| u4 | `inspect module before editing it` | review→implement |
| u5 | `implement change then review code` | implement→review |
| u6 | `implement change then inspect code` | implement→review |
| u7 | `edit module before reviewing it` | implement→review |
| u8 | `edit module before inspecting it` | implement→review |
| p1 | `please review code then implement change` | review→implement |
| p2 | `please implement change then review code` | implement→review |

EXAM из шести строк: прежние e1 `review code before implementing change`, e2 `inspect code before implementing change`, e3 `implement change before reviewing code`, e4 `implement change before inspecting code` с прежним gold; дополнительно h1 `kindly review code then implement change` → review→implement и h2 `kindly implement change then review code` → implement→review. h1/h2 не передавать обучению.

Оба плеча получают p1/p2, поэтому A является обученным положительным контролем: при обычной выдаче одного из двух присутствующих маршрутов оно способно на 1/2, а не сравнивается с пустым состоянием 0→0. У p1/p2 в A совпадают векторы; для h1/h2 действует та же аналитическая граница. Перед сравнением сохранить нормализованные признаки и поиск actual neighbour ID — без запуска отдельного surrogate вместо native learner.

Учебная приёмка раздельна: (а) воспроизводится ли измеренный порядок на исходных e1–e4; (б) сохранены ли ответы u1–u8; (в) различаются ли выученные p1/p2; (г) есть ли перенос на h1/h2. Для заявления о новом полезном различении требуется B лучше A на назначенной паре при фактически выполненном Train; `0→0`, более красивый score и одинаковое число верных с потерянной старой строкой не подходят. Успех на p1/p2 означает сохранение обученных различий; обобщение требует отдельно h1/h2. Если B не выигрывает, сохранить отрицательный результат и не менять oracle.

**Бюджет:** основной A/B — 2 native fit по 10 уроков = 20 уроков; после fit по 10 контрольных и 6 экзаменационных `ExecuteAsync` = 32 вызова. До fit — по 6 записей `NO_TRAINED_UNIT`, итого 12 холодных наблюдений и 0 native вызовов. Только EXAM запускает графы: 12 графов / 24 вызова узлов. Обязательный отдельный отрицательный контроль C: ещё 1 fit / 10 уроков, меняются только ярлыки p1/p2, затем 4 `ExecuteAsync` на p1/p2/h1/h2; дополнительных графов и узлов 0. Полная верхняя граница — **3 fit, 30 уроков, 36 native запросов, 12 холодных наблюдений, 12 графов, 24 вызова узлов; DPO/SFT/teacher=0, retry=0**. Отрицательный контроль должен обнаруживать чувствительность к обученным ярлыкам в той части панели, где B действительно различает ответы; неизменная метрика записывается как незакрытый контроль, не обходится новой пробой вне бюджета.

Ресурсы мерить у одинаковых границ native fit/read для A/B; сохранять elapsed, allocation и отдельный retained/peak показатель, если измерен. Общий пик последовательного процесса нельзя выдавать за A/B peak. Если будущая карточка обещает сохранённый старт, до запуска ей отдельно нужен реализованный native loader; текущий рецепт этого обещания не делает.

## 3. P51: тема обязана различать известные ответы, но не становится доказательством обобщения

Тема обучения — перевод; задача — выбор значения `bank` в EN→RU по уже заданному `TopicDomain`. Получатель — `ExecutorUnit` направления EN_RU, внутренняя точная память. Это **новый конкретный кандидат корректности ключа** относительно просмотренных планов, не новый вид обучаемой архитектуры.

Три урока: `(bank, finance, банк)`, `(bank, river, берег)`, `(file, general, файл)`. Экзамен содержит те же три известные пары и `(bank, unknown)`, где gold — отказ. Отложенных известных переводов нет. После обучения A хранит `bank→берег`, `file→файл`, B — три разных адреса. Результат B классифицируется как `memory_reuse / correct-answer integrity`, **не acquisition-generalization**.

| Метрика на сохранённой панели | Холодное | A | B |
|---|---:|---:|---:|
| Верные исходы / 4 | 1 | 2 | 4 |
| Неверный известный перевод | 0 | 1 | 0 |
| Ложное принятие неизвестной темы | 0 | 1 | 0 |
| Верные учебные контроли / 3 | Не измерено | 2 | 3 |
| Разных адресов после трёх записей | 0 | 2 | 3 |

В `arms.arm_a.exam_answers` E1 возвращает «берег» вместо «банк», E4 также «берег» и `FALSE_ACCEPT`. В B E1 — «банк», E4 — `[EN_RU:BOOTSTRAP] bank`, `bootstrap-en_ru`. Sмена тематических ярлыков двух уроков уменьшает B с 4/4 до 2/4. Копия с выключенным фактором совпала с A на этой панели. Эти свидетельства поддерживают измеренную корректность адреса и отказа именно здесь.

Текущий код ещё использует source-only ключ: [TranslationTrainedUnits.cs](../../../../../27.TranslationDomain/TranslationTrainedUnits.cs), `ExecutorUnit.TrainOnExample`:413–415 — `NormalizeMapKey(input.SourceText)`; `Execute`:264–268 читает этот ключ, хотя получает `topicDomain`. Экспериментальная реализация `BuildExactKey` находится только в [P5101/Program.cs](../../../../../experiments-v2/RP01-MICRO/P5101/Program.cs):115–123.

**Пробелы приёмки нового переноса:**

- В B `NO_TOPIC_MATCH` на строках 138–146 только записывает наблюдение. Выполнение продолжается через phrase/word/KNN. Native `TrySelectKnnCandidate`:333–360 не получает тему, и обычный EN_RU путь ограничивается общими словами. `SourceTokenSimilarity`:962–973 требует минимум два общих содержательных слова. Поэтому однословный `bank` не доказывает отказ для многословного источника. Это конкретный открытый сценарий, а не уже исполненный контрпример.
- A обучается и вызывается через `TranslationMachine`; B использует `CopyArm.Train` и прямой `TranslationRoutingFlow.ExecuteAsync` (`Program.cs`:783–817). Измеренные 60.7491 → 12.7096 мс и 290856 → 275208 allocated bytes не являются доказанным ускорением одного и того же продуктового пути. Последовательный heap 670472 → 833168 байт увеличился примерно на 24.3%, но измерен на разных накопленных состояниях процесса; его также нельзя объявить чистой ценой фактора или спрятать как отсутствие регрессии. Peak 45723648 байт общий; CPU по плечам не измерен.
- Native `ExecutorUnit.ExportCheckpoint/ImportCheckpoint`:484–535 сохраняют `ExactSourceMap` без схемы тематического ключа. ## 4. P52: полезна диагностика разметки, рост перевода не измерен

Тема — перевод RU→EN, различение прошедшего и настоящего времени. В каждом плече две пары дают шесть native unit lessons через `TranslationMachine.TrainStructuredBatchAsync`; меняется источник rule tags при создании уроков. Потребитель ответов настоящий: `GetOrchestratorAsync → RunAsync → TranslationRoutingFlow → TrainedTranslationAdapter`.

Сохранённые фактические ответы e1/e3 `Он проверил файл[.]` → `He checked the file`; e2/e4 `Он проверяет файл[.]` → `He checks the file`. Точный источник: [TranslationStructuredBatchBuilder.BuildGeneralBatch](../../../../../27.TranslationDomain/TranslationStructuredBatchBuilder.cs):94–110 дописывает `BuildRuleTags(pair.Rejected)` в signature и в правильный `TokenizerOutput`; `BuildRuleTags`:434–441 читает именно rejected. Сначала назначить семантику поля и проверку согласованности с базовым tokenizer; это допустимый диагностический перенос без заявления об улучшенном переводе.

Будущая ограниченная учебная приёмка диагностического переноса: обе прежние пары, по 6 native unit lessons на A/B, передаваемые в `TrainStructuredBatchAsync`; читать `SemanticTokenizerUnit.Tokenize` обеих учебных строк после Train (2 на плечо), сохранять actual signature. Никаких дополнительных fits ради получения чувствительности финального ответа. Если полная согласованность не достижима из-за нынешней unconditional PAST-ветки, диагностический перенос не принимается как полный, а исходный measured gain tags остаётся сохранённым.
