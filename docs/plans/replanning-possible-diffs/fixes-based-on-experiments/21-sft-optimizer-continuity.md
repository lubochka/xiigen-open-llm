## 1. Задача, тема и измеренное основание

Тема — документация кода; профиль — краткое английское описание порядка аргументов C#-метода. Получатель — LoRA q/v модели `rp01-csharp-small/v1`, H512, не kNN и не маршрутизатор. ### 2.2. Полный вызываемый путь

`Program.MapCodeDocumentationSupervisedContinuation → Endpoint.ExecuteAsync(selector) → Coordinator.ExecuteAsync → Configuration.ResolveGrant → SFT admission + FileSupervisedTrainingTransactionStore.OpenOrCreate → IncrementalTrainer.TrainSupervisedTransactionAsync → ProductionSupervisedTrainingStepExecutor.Execute → Trainer.TrainSupervisedNextTokenStep → Forward/CE/Backward/ClipGradNorm → AdamW.Step → CompleteCandidate → PublishSupervisedNext → strict v3 load в новой сессии`.

Новый coordinator зарегистрировать в startup DI рядом с existing continuous-learning composition; отдельный `CreateRepositorySupervisedStartRequest` получает только уже проверенный grant. Отсутствующий SFT profile оставляет маршрут недоступным с typed `SFT_CONTINUATION_NOT_CONFIGURED`, без модели/обучения. ## 3. Закрытые решения о допуске, состоянии и совместимости

### 3.1. Вход и право на конкретный урок

Startup profile содержит `operationKind=SupervisedOnly`, `continuationMode=NewSftEpoch|ResumeSft`, exact domain/design-pattern/model/version/runtime identity, sealed SFT dataset manifest hash, ordered row IDs/content hashes, target mode/framing, expected cursor, один следующий урок и его weight/LR budget, exact parent manifest/weights hash и основание разрешения источника. Для следующего урока отдельный startup grant связывается с фактически опубликованным parent; неизвестный будущий hash не заполняется догадкой. Тест ниже открывает новый host с таким вторым grant. Каталог не выдаёт wildcard permission на любые файлы или родителя «latest».

Начальный bounded profile допускает только явно проверенные локальные SFT lessons с точными source IDs/content hashes в разрешении оператора. `TrainingSourceProvenance.BuildManifest/Combine` проверяет и сохраняет происхождение по существующему контракту; это не доказательство согласия владельца источника. Новый admission отдельно сопоставляет каждую строку с exact разрешённым источником/контентом и неизменяемым manifest, проверяет domain, row order, framing и лимит1урок/вызов. У отсутствующего/неподходящего разрешения — `SFT_SOURCE_ADMISSION_REQUIRED` до создания обучающей сессии. Новые внешние teacher-generated rows этим профилем не принимаются: их отдельная legal-teacher цепочка не заменяется ручным SourceId. Ни research authority, ни DPO lease, ни `ROOT_B0_FIRST_UPDATE` не выдают SFT admission.

Sealed `lessons.jsonl` содержит exact prompt/response/domain/weight/SourceId/CapturedAt и фиксированные row IDs в учебном порядке. Manifest фиксирует bytes/hash/row count, source manifest, material framing, target mode и неизменяемую последовательность row IDs; конкретные expected/next cursor принадлежат grant/candidate, sealed dataset при продвижении не переписывается. Snapshot и bounded digest используют те же полевые значения, что проверка SFT examples в `IncrementalTrainer`, с отдельным version prefix `xiigen.supervised-only-example-batch.v1`; существующий DPO supervised-batch digest не переименовывается. Исполнитель не смешивает темы и не создаёт материал по EXAM.

### 3.2. Режим, родитель и отказ при конфликте

`ColdStartPolicy=Denied`: модель читается из совместимого canonical parent. Явный `NewSftEpoch` может начать SFT с weights-only v1/v2 parent и fresh SFT optimizer; его первый accepted урок создаёт v3. `ResumeSft` требует полный совместимый v3 SFT bundle. Старый weights-only checkpoint не превращается в продолжение и не дополняется пустыми moments. Этот выбор задаёт новый SFT profile; прежний TP1/DPO профиль продолжает прежнее поведение.

Перед `BeginMutation`, attach/import и любым Execute проверить exact bound parent против текущего canonical latest compatible checkpoint, SFT provenance/cursor, неизменённые target mode/framing/optimizer settings и `operationKind=SupervisedOnly`. При intervening DPO/иной mutation или scheduled DPO в выбранной операции вернуть `SFT_CONTINUATION_INTERLEAVED_MUTATION_UNSUPPORTED`; при смещении parent — `SFT_CONTINUATION_PARENT_CONFLICT`. Новый путь не забирает, не переставляет и не подавляет DPO queue; DPO request остаётся DPO request. Проверка не выдаёт глобальной гарантии о чужой очереди: атомарное владение child slot и повторная проверка exact parent при acceptance/publication запрещают записать устаревшую ветку при конкурентном изменении. Конфликт `parent.Step+1` не обходится переименованием, поиском свободного номера или продолжением на другом parent. Для повторного selector coordinator сначала открывает его exact transaction: уже опубликованный terminal receipt проверяется и возвращается до проверки допуска к новой mutation; иначе собственный child ошибочно сделал бы повтор «устаревшим». Accepted-but-unpublished transaction возобновляет только собственную publication без Train; её parent/child slot проверяется по сохранённому reservation descriptor, а новая transaction требует bound parent==latest перед любым update. Собственная reserved child leaf/staging не считается чужим занятым slot: допускается только тот же durable owner и те же принятые bytes. Чужой child или действительно сместившийся parent дают typed conflict.

Если MC и MS позднее выбраны вместе, target mode/framing входят в continuation identity. `ResumeSft` не переключает `AllTargets→ResponseTargets` с прежними moments. Смена цели требует явно назначенного `NewSftEpoch`; измерения комбинированного product route здесь нет. Historical MS A/B использует test-only восстановленный donor как заданный фактор и не разрешает такую смену в production resume.

### 3.3. Запись, восстановление и publication

1. **Независимые объекты.** Проверить bytes/identity без мутации → создать независимую session → окончательно attach/load adapters → построить stable keyed bindings и проверить keys/dimensions/settings → атомарно импортировать optimizer → восстановить RNG → первый Execute. Build не импортирует moments до attachment. Ошибка не запускает fresh fallback и не возвращает частичную сессию как результат.
2. **Собственный SFT candidate.** SFT store получает typed address под `training-artifacts/models/{domain}/{designPattern}/{modelId}/{modelVersion}/sft-transactions/{transactionId}/`. Уникальная create-new transaction leaf владеет `candidate.lora`, `optimizer.bin`, `rng.json`, `continuation.json` и их staging files; path/address создаёт новый sibling в `RepositoryOwnedTrainingArtifactLayout`, с validated slug/transaction identity. Эти короткие имена допустимы только внутри собственной leaf, не в shared root. Повторный selector переоткрывает ту же проверенную leaf; конфликт не выбирает новое имя. Сохранить create-new/write-through, bounded paths/record, same-handle hash, flush и полное повторное чтение принятого набора. Candidate envelope связывает accepted adapter hash с base/parent, SFT dataset/source/cursor, optimizer/RNG hashes/lengths/settings/step и mode/framing. `CompleteCandidate` допускается только после полного комплекта; это собственный SFT transaction, не `DpoTransactionDomain`.
3. **Полный checkpoint.** `PublishSupervisedNext` принимает только этот accepted SFT handle и session-bound SFT manifest. Он независимо проверяет exact parent, accepted identity и child slot; пишет full model, те же optimizer/RNG bytes и отдельный published envelope. `candidateAdapterSha256` и `publishedWeightsSha256` имеют разные поля. Ссылка на hash candidate envelope связывает обе границы; moments из текущего случайного optimizer не пересоздаются.
4. **Версия manifest.** Новая `repository-owned-model-checkpoint-manifest-v3-sft-continuation` содержит `trainingKind=SupervisedOnly`, обязательную `SupervisedDatasetManifest`, parent lineage и typed `SupervisedContinuation`. Это отдельный request/read/write/validate branch; DPO manifest у SFT update не фабрикуется. Верхний manifest связывает hashes/lengths `sft-continuation.json`, `sft-optimizer.bin`, `sft-rng.json` в canonical checkpoint leaf. В continuation — weights identity, optimizer/RNG hashes, domain/model/tokenizer/runtime config/topology/LoRA keys/settings, cursor, mode/framing и `schedulerPolicy=NewSession`; рекурсивного self-hash нет. v1/v2 bytes/omission/constructors остаются прежними. Loader/discovery/latest selection понимают v3 и её SFT validator; не вызывают DPO dataset validator для SFT provenance, не пропускают повреждённый latest ради старого «подходящего» parent. Retained factory передаёт полный проверенный SFT descriptor.
5. **Две шкалы шагов.** Repository checkpoint — `parent.Step+1`, не AdamW step1000. `Trainer._supervisedStep` остаётся session-local scheduler. Измерение при constant LR0.001 не доказывает продолжение произвольного scheduler. `DpoTrainer` сохраняет свой отдельный optimizer; DPO writers/`DpoTrainingPublicationBundle` не используются как SFT sidecars.

Повтор уже опубликованной transaction возвращает тот же manifest. Reservation связывает transaction/candidate hash, parent, child step и фиксированный createdAt; сохранённые owned staging files проверяются и продолжаются по этой записи, а не по одному совпадению пути. Собственная частично записанная child leaf не запускает новый Train или выбор следующего номера. Полный кандидат после сбоя publication сохраняется; частичный комплект не становится accepted. Publication не успешна по одному наличию weights. При stale parent/занятом child slot возвращается точный конфликт, candidate не переучивается и чужие файлы не удаляются.
