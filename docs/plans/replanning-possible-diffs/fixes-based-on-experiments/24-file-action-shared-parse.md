## 2. Почему это новое дополнение

[required-changes](../required-changes.md#kh-cost-01) уже содержит краткого кандидата и числа. В существующих планах 10–23 нет переноса общего дерева в настоящий `TrainFileActionKnn`, его native learning regression и согласования с FIX-NKU. Этот документ добавляет именно их.

[FIX-NKU](10-nku-do-while-label.md) меняет учебную **метку** do-while. FIX-KHC меняет только **повторный разбор**. Это разные факторы. Не включать `DoStatement` в KHC-правку, не менять список признаков, k, distance, приоритет меток или порог допуска. Если FIX-NKU уже принят и внесён отдельно, сохранить его в обоих сравнительных вариантах и записать фактический source SHA; исторические KHC-числа остаются историческими. Набор KHC использует `for`, не `do-while`.

## 3. Точная правка и настоящий получатель

Проверенные файлы продукта:

1. [`12.SemanticCompiler/Prediction/FileActionKnn.cs`](https://github.com/lubochka/llm_mvp_core/blob/213f0c9b0568384632ab6bb5a67c57d6f17b3df9/12.SemanticCompiler/Prediction/FileActionKnn.cs#L11-L104). Добавить `using Microsoft.CodeAnalysis;` и публичные перегрузки `Label(SyntaxNode root)` и `FeatureVector(SyntaxNode root)`. Перенести в них существующие тела после `ParseText(...).GetRoot()` без изменения семантики. Строковые методы сохраняются и делегируют, каждый со своим прежним `ParseText(source).GetRoot()`.
2. [`12.SemanticCompiler/SemanticCompilerFacade.cs`](https://github.com/lubochka/llm_mvp_core/blob/213f0c9b0568384632ab6bb5a67c57d6f17b3df9/12.SemanticCompiler/SemanticCompilerFacade.cs#L193-L203). Только в `TrainFileActionKnn` после существующего фильтра пустых строк один раз разобрать каждый source, затем передать **один и тот же root** обеим перегрузкам. Оставить исходный порядок Features → Label и условие `examples.Length >= 4`.

Планируемая форма участка:

```csharp
.Select(source =>
{
    var root = CSharpSyntaxTree.ParseText(source).GetRoot();
    return (Features: ActionLabelGenerator.FeatureVector(root),
            Label: ActionLabelGenerator.Label(root));
})
```

Это пример будущей правки, не уже внесённый код. Новый контракт root-перегрузок — переданное неизменяемое дерево того же исходника с теми же parser options. Тело не должно заново разбирать текст или мутировать дерево. Не вводить глобальный AST-cache: дерево живёт только при подготовке одной строки и не сохраняется в памяти kNN. Для существующих строковых вызовов, включая `Label((string)null!)`, сохраняется прежний маршрут обработки; новые перегрузки не являются поводом изменить старые ошибки или обработку пустого текста.

Связь с обучением и выдачей результата проверена непосредственно:

`TrainFileActionKnn → подготовленные Features/Label → FileActionKnnPredictor.Train → _train → Predict → SemanticCompilerFacade.PredictFileAction → CompilationResult.PredictedFileAction`.

`Train` действительно заменяет сохранённую таблицу; `Predict` голосует по трём ближайшим примерам. Читатель вызывается через [Compile](https://github.com/lubochka/llm_mvp_core/blob/213f0c9b0568384632ab6bb5a67c57d6f17b3df9/12.SemanticCompiler/SemanticCompilerFacade.cs#L153-L172), а [guard](https://github.com/lubochka/llm_mvp_core/blob/213f0c9b0568384632ab6bb5a67c57d6f17b3df9/12.SemanticCompiler/SemanticCompilerFacade.cs#L326-L333) требует C#, `UseFileActionKnn=true` и минимум четыре строки памяти. Замена двух разборов одним находится **до настоящего обучения**, а проверяемый ответ берётся **после него**. Наличие нового overload само по себе не учебный тест.

Разметка уроков и извлечение AST детерминированы; предсказание использует обученную таблицу. Эти роли показываются отдельно. `ClassifyDomain` в этом facade использует keyword path, поэтому успешный `Compile` не называется доказательством обученного выбора домена. Остальные вызовы парсера в `Compile`, structural/method KNN и других проектах этим опытом не покрыты и не оптимизируются попутно.

## 4. Фиксированные данные, состояние и адреса

Единственный источник — поля `inputs.train`, `inputs.exam`, `prepared`, `answers` у raw A/B выше. Перед переносом проверить совпадение inputs двух плеч. Будущие файлы тестового набора:

- `Tests/Fixtures/ExperimentFixes/v1/Khc01/train.json` — ровно K1–K6 и их `source` из raw A, порядок сохранён;
- `Tests/Fixtures/ExperimentFixes/v1/Khc01/exam.json` — ровно KQ1–KQ4, source и независимый gold из raw A;
- `Tests/Fixtures/ExperimentFixes/v1/Khc01/historical-prepared.json` — шесть исходных меток/векторов, для сравнения состояния;
- `Tests/Fixtures/ExperimentFixes/v1/Khc01/manifest.json` — исходный commit, пути, SHA-256 реальных исходных bytes и назначение полей; EXAM gold доступен только scorer.

Это **планируемые** новые файлы. Не превращать опубликованные результаты в изменяемый working directory. Исходный runner имел несовпадение путей карточки/команды: raw лежит в `experiments-v2/RP01-MICRO/KHC/results`, отчёты — в `docs/plans/replanning-possible-diffs/experimets/results/2026-10-20/KH-COST-01`. Будущий исполнитель использует именно эти адреса, не ищет альтернативу.

TRAIN — одна тема, две допустимые группы одной задачи: K1–K3 с `for`, K4–K6 без цикла. EXAM — новые имена/числа в тех же двух семействах. Gold: KQ1/KQ2 = ADD_METHOD, KQ3/KQ4 = ADD_LOOP. Запрещено вычислять gold через `Label(examSource)`, подсказать ожидаемую метку learner или добавлять третью тему. Constant baselines обеих меток равны 2/4, отказ — 0/4.

У `FileActionKnnPredictor` и этого facade **нет проверенного checkpoint API**; нейронный H512 donor к ним неприменим. Здесь разрешён именно минимальный cold acquisition: подготовка шести строк и один Train на экземпляр. Повторное обучение нужно для измеряемого перехода подготовки; загрузка готовой таблицы исключила бы сам фактор из опыта. Все последующие assertions читают один immutable receipt и уже подготовленный экземпляр своей стороны, не обучают его заново. Сохранённый `historical-prepared.json` — ожидаемая таблица, а не притворный native checkpoint. Не добавлять production persistence ради этой правки и не называть повторный `Train(savedRows)` холодным восстановлением без обучения.

## 5. Обучающий регрессионный тест и бюджет

Новый файл: `Tests/FileActionPreparationLearningTests.cs`. Новый test-only fixture: `Tests/ExperimentFixes/FileActionPreparationFixture.cs`. Ни один сейчас не реализован. Они используют обычный project reference на настоящий `SemanticCompiler`, не Compile Include старых экспериментальных копий и не копию алгоритма в тестах.

Основной тест `SharedParse_LearnsBothFamiliesThroughFacade` получает режим A/B только для подписи отчёта, **не для выбора другого алгоритма внутри learner**. Сначала его один раз выполнить с нативным кодом до правки; затем тот же тест один раз с нативным кодом после правки. Каждый процесс создаёт новый facade с `UseFileActionKnn=true`, `UseRegexPreprocessor=false`, `UseMethodKnn=false`, `UseStructuralKnn=false`. Флаги фиксированы одинаково и убирают влияние необязательных соседних predictors; `Compile` остаётся реальным.

**Сопутствующий путь Compile учтён явно.** Он вызывает `RememberCompiledSource → EnsureGrammarMaskFilter → GrammarMaskFilter.Train → NgramPredictor.Train` даже при отключённых method/structural flags. В основном A/B это 16 обновлений E05-таблицы на 16 Compile, вне измеряемого интервала; отдельный E05 результат не оценивается. Входы EXAM попадают в собственный накопитель E05, но не в `_fileActionKnn._train`: перед fit FileAction TrainingSize обязан оставаться0, после —6. По [GrammarMaskFilter.cs](https://github.com/lubochka/llm_mvp_core/blob/213f0c9b0568384632ab6bb5a67c57d6f17b3df9/12.SemanticCompiler/Prediction/GrammarMaskFilter.cs#L16-L32) и проверенному facade эти состояния раздельны. Нельзя представить побочные грамматические обновления как обучение FileAction на EXAM либо использовать их output как его ответ. Новый тест наблюдает именно FileAction-таблицу через test-only fixture; существующий reflection-подход к `_fileActionKnn` в E13E14FeatureFlagTests допустим для проверки размера, не для подмены состояния.

На сторону: четыре `Compile(KQ)` до fit → один `TrainFileActionKnn(K1…K6)` → те же четыре `Compile(KQ)` после. Измеритель охватывает только подготовку + fit в `TrainFileActionKnn`; сериализация, readout и сборка вне него. Зафиксировать wall, CPU, `GC.GetAllocatedBytesForCurrentThread` и peak процесса с отдельной подписью. Отдельный прогрев и retries до красивого числа не назначены. Первые четыре native Compile естественно инициализируют Roslyn/E05, поэтому их нельзя объявить нулевой предысторией или обещать точное повторение исторического cold wall time; A и B получают одинаковую предысторию.

Ожидаемый учебный контракт: до fit все `PredictedFileAction=null`; после — точный gold 4/4, каждая семья 2/2, выше constant 2/4. Ответ нельзя брать напрямую у разметчика. Source experiment использовал собственный Query-guard над копиями predictors, **не полный native Compile**; новый тест проверяет именно этот ранее не покрытый потребитель. Если native Compile не даёт требуемые ответы, это обнаруженное расхождение consumer/preprocessing, а не разрешение подменить его историческим Query.

Основной A/B FileAction: **2 fit, 12 предъявлений учебных строк, 6 уникальных TRAIN, 16 Compile (8 before + 8 after)**. Ноль neural/DPO/SFT updates, ноль внешних вызовов. Assertions обучения и ресурсов разделяют эти два receipts, а не запускают ещё два A/B.

**Порядок добавления кода тестов:** до A создать только `SharedParse_LearnsBothFamiliesThroughFacade` и helper, использующие уже существующие APIs. Метод `RootOverloads_PreserveTrainingLabelsAndFloat32Features` и все обращения helper к новым SyntaxNode-перегрузкам добавить и компилировать только после product overload patch и завершения основного B. Иначе даже отфильтрованный baseline A не соберётся из-за отсутствующего API. Затем этот отдельный контрактный тест сравнивает шесть строковых результатов с root-результатами по побитовым float32 и исходным меткам. Он имеет **0 Train и 0 Compile**; отвечает за материал, который передаётся в настоящий learner. Несколько граничных значений — пустой текст и синтаксически неполный C# — проверяют прежний строковый контракт; не считаются дополнительными обучающими результатами.

Пути новых receipts: `artifacts/fbe/FIX-KHC/attempt-0001/A/learning.json`, `B/learning.json`, `comparison.json`; тестовые логи — `A/tests/`, `B/tests/`, `contracts/tests/`. Тестовый fixture использует `XIIGEN_FBE_KHC_ARM=A|B`, проверяет отсутствие готового terminal результата и пишет только свой назначенный файл через CreateNew. Существующая папка — повод прочитать её статус, не удалить её и не запустить завершённую сторону повторно. Сравнение создаётся один раз после двух terminal receipts; source SHA и build identity каждого native плеча записываются отдельно.

После переноса **не требовать точного исторического времени или процента экономии от unit test**. Функциональные assertions проверяют сохранённое обучение/материал. Новые allocations/wall/CPU сообщаются отдельно по тем же областям: отсутствие воспроизведённой экономии запрещает объявлять её доказанной в новом native consumer, но не позволяет скрыть исторический локальный успех. Новый замер не повторяют автоматически.

## 7. Связь с промптом и доменом

Основная проверка KHC заканчивается настоящим `CompilationResult.PredictedFileAction` для C# source. Общий обучаемый путь «промпт → тема → receiver» остаётся [FIX-E2E](20-prompt-domain-e2e.md). KHC не создаёт нового domain selector, не выбирает маршрут по C# keyword и не включает `UseFileActionKnn` всем пользователям.

При отдельно выбранной совместной интеграции к существующим E2E receipts добавляется проверка отсутствия вызова `TrainFileActionKnn` и изменений памяти file-action у невыбранных translation/orchestration/Wiki handlers; **0 новых Train и 0 новых запросов**. Это проверка изоляции уже обученного результата, не новое успешное обучение router. Положительный prompt→C#-action endpoint/FlowRef этим опытом не доказан и в каталог FIX-E2E автоматически не добавляется. Для выбранного C# consumer здесь задан локальный positive через Compile; результат общей маршрутизации нельзя подменить этим локальным тестом.
