## 1. P02: смысловой ремонт применён частично

Первичные файлы: [DpoMetrics](../../../../11.DPO/Models/DpoMetrics.cs), [действующий builder](../../../../experiments-v2/RP01-MICRO/P0201/src/PreferenceSeparationReport.cs), [Program](../../../../experiments-v2/RP01-MICRO/P0201/Program.cs), [тесты](../../../../Tests/PreferenceSeparationReportTests.cs), [report](../../../../experiments-v2/RP01-MICRO/P0201/results/attempt-0001/report.md), [сохранённый test log](../../../../experiments-v2/_runners/Run-PreferenceSeparationTests.log).

**Подтверждено в source:** `DpoMetrics.cs:39–69` теперь различает долю улучшившихся относительно reference пар и правильные ответы; `ReferenceRelativeImprovementRate => Accuracy` помечен JsonIgnore. Это alias прежнего измерения, не изменение DPO. Историческая JSON-квитанция не расширяется новым сериализуемым полем. Тесты builder действительно используют тот же файл, который включён в host; сохранённый log сообщает `Test Run Successful`, `Total tests:103`. Это результат сохранённого чужого запуска, не новые103 проверки этой сессии.

**R28-M1, подтверждённая ошибка writer.** `Program.cs:441` по-прежнему записывает в `metric_definitions.accuracy_field_in_step_metrics`: «хранит долю шагов». На самом деле одна квитанция содержит долю пар этого шага; StepVector использует нормированные веса с нижней отсечкой0,01. В `PreferenceSeparationReport.cs:294` остался аналогичный комментарий «это и есть историческое поле Accuracy». Последняя правка поправила общий текст, но не эти поверхности. Тест `SerializedReportCarriesAllThreeNamesAndTheirDefinitions` проверяет отдельный builder, а не весь объект, который создаёт Program; потому эта ошибка не обнаруживается его assertions.

**R28-M2, разный знаменатель остаётся разной величиной.** Обозначим m[t,i] запас пары i шага t, w[t,i] её нормированный вес. Тогда:

- доля улучшившихся пар одной квитанции: `R[t] = Σ_i w[t,i] · 1(m[t,i]>0)`;
- доля шагов с положительным средним запасом: `S = mean_t 1(Σ_i w[t,i]·m[t,i]>0)`;
- среднее долей квитанций: `A = mean_t R[t]`;
- доля улучшившихся пар конечной панели и фактические правильные ответы — ещё два отдельных измерения.

У одного шага с равными весами и запасами`[+1,−3]` R=0,5, S=0. Это математический контрпример, не новый модельный запуск. Поэтому значение из `Build(...stepRewardMargins)` нельзя считать агрегированием исторического Accuracy. На P02 S и A совпали из-за однородных знаков внутри каждого шага; исправление be1 это честно признаёт. Но текущие документы03/69/78 называют report key `reference_relative_improvement_rate` «каноническим» для S, тогда как одноимённый native alias означает R. Новый общий договор должен указывать единицу наблюдения, веса, фазу и aggregation либо давать разным величинам разные имена. Исторические0,750/1,000 сохраняются вместе со своими определениями.

**R28-W1, прежний незакрытый дефект.** `Program.cs:546` возвращает `ArmResult(...,0d)`, `:500` пишет `wall_ms_arm_b_sft=armB.SftWallMs`; тип`:695` не допускает null. Нельзя повторять12 оплаченных updates ради исправления обозначения неизвестного времени.

Улучшение по наблюдаемому DPO-интервалу примерно1,504% сохраняется; оно не становится трёхкратным усилением градиента, финальной post-update оценкой или улучшением accuracy. Поправка отчёта не превращает предварительные SFT-уроки в универсальную политику.

## 2. P08: изменение пока осталось в эксперименте

Адресный source/raw audit выполнил `/root/p08_transfer_audit`; его [пакет](reviews/2026-10-27-p08-generation-transfer-source-audit.md) содержит исходные строки и ограничения.

Нужно различать три участка: настоящую SFT-подготовку; A/B выбор токена по полученным logits; A/B через два выбранных TextGenerator. В P08 первые два выполнены, третий не доказан: TextGenerator с выбранными sampler создаётся, но A/B ответы получаются прямым вызовом sampler. Обычный greedy TextGenerator в программе действительно вызывался; это не закрывает A/B consumer. Созданный объект и доступный constructor не равны вызванному consumer.

Текущий [Sampler.cs](../../../../09.Inference/Sampler.cs) при topK>0 выбирает одну ветку, а topP обрабатывает через else-if. Последовательное отсечение в B реализовано только в P0801. На T1 вероятность gold выросла0,86879754→1, support2→1; у остальных3 строк распределения не улучшились, actual correct2/4 в обеих руках. Это полезный локальный эффект по вероятности, а не успех одного уменьшения support. E1 gold уже отсутствует в top-k. Неизменный argmax не доказывает бесполезность stochastic policy, но и не доказывает общее улучшение выдачи.

Report:126 говорит, что sampler-изменение «не даёт и не может давать» эффект скорости/памяти. Это необоснованное обобщение: sampler costs не измерены, B добавляет sort/softmax/cumsum. Правильный статус ресурса — NOT_MEASURED.

**Статический край, не измеренный новый результат:** `Sampler.MultinomialSample`, строки89–98, выбирает первый i с `r<=acc`. Для вероятностей`[0,1,0]` и допустимого r=0 возвращается id0 с нулевой вероятностью. Например, logits`[0,3,1]`,topK=1,temperature>0 дают support{id1}, но эта граница выбора его нарушает. Экспериментальный B копирует этот край. Будущий контроль использует `after.json → rows[id=T1].logits`,temperature1,topK1,topP1,draw0: единственный допустимый id43, старое условие возвращает id0. Это отдельный контроль от исходного K2/p0,6; дополнительный нейронный проход для сохранённых logits не требуется.

**Конфликт рецепта:** P08/P09 называют «exact response masks» для учебного участка H64-RD, но фактически используют native `TrainSupervisedNextTokenStep` по полной последовательности prompt+response. Response positions здесь относятся к readout; это не response-only SFT loss. Исправить описание, сохранив фактический donor objective и отсутствие LF; не менять обучение задним числом ради текста карточки.
