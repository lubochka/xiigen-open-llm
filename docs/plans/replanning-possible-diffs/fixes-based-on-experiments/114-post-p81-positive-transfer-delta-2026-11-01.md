### Source parity: почему это тот же фактор, и что ещё проверить

Текущий native сокращатель **не отбрасывает** реальные lambda kinds как `?`: [MethodKnn.cs](../../../../12.SemanticCompiler/Prediction/MethodKnn.cs):213 применяет `kind.EndsWith("Expression", StringComparison.Ordinal) => kind[..^10]`, поэтому получаются `SimpleLambda` и `ParenthesizedLambda`. [Копия P84](../../../../experiments-v2/RP01-MICRO/P8401/src/E13LambdaFamilySeam.cs):15–22,108–139 использует тот же Body walk и сокращатель. [Raw panel-0-features](../../../../experiments-v2/RP01-MICRO/P8401/results/attempt-0001/panel-0-features.json) показывает0 mismatches с тогдашним native по8 методам. Все формы этого корпуса блочные; текущая P83 ветка ExpressionBody их обход не меняет. Это целевая source-проверка, не заявление о новом выполненном native Compile.

Точные raw bags текущих M: F1=`{Add,NumericLiteral,Ret,SimpleLambda}`, F2=`{Add,NumericLiteral,Ret,ParenthesizedLambda}`, F3=`{Add,Ret,ParenthesizedLambda}`, F4=`{NumericLiteral,Ret}`. B заменяет только два lambda имени на `Lambda`. Отсюда аналитически:

| Пара | A distance | B distance |
|---|---:|---:|
| F1,F2 | .4 | 0 |
| F1,F3 | .6 | .25 |
| F1,F4 | .5 | .5 |
| F2,F3 | .25 | .25 |
| F2,F4 | .5 | .5 |
| F3,F4 | .75 | .75 |

С тремя копиями каждой оставшейся формы nearest class получает3 из5 голосов. Поэтому ожидаемый Q-readout на исключённых E1–E4: A=`Loop,Guard,Loop,Loop` (1/4), B=`Loop,Loop,Loop,Loop` (2/4). Это объяснение raw результата и будущий oracle, **не измерение будущего native facade**. Для каждого из трёх retention controls собственная форма присутствует тремя exact-zero соседями; единственное межформенное zero совпадение B — F1/F2, обе имеют gold Loop. Следовательно минимум3 из5 голосов правильны, а12/12 controls на arm достижимы без изменения k/tie. Arity probe `(x,y)=>x+1` в этот TRAIN/query набор не входит; его известное схлопывание не доказывает ошибку этих controls.

До любого Train обязателен native source/feature parity gate обеих собранных версий: закрепить hashes и единственный diff, извлечь F1–F4/E1–E4 нативным `MethodExtractor.Extract`, сверить точные bags, FileId/IndexInFile, target gold-происхождение и ожидаемые расстояния. Gold остаётся внешней константой, не feature. Проверка C# prefix и двух дополнительных pure probes занимает не более40 отдельных Extract calls:8 источников×2 варианта prefix×2 arms=32; arity/async×2 prefix×2 arms=8. Это явно назначенная подготовка, **0 Train/0 Compile**; внутренние Extract при последующем Train/Compile считаются отдельно в receipt. Если bags отличаются, нельзя объявлять historical numbers native результатом или ослаблять oracle: остановиться до расхода10/80/64 и вернуть exact mismatch. Все дальнейшие feature assertions используют эти извлечённые данные, без повторных скрытых calls.

## Точный корпус, без выбора исполнителем

Источник — [P8401/Program.cs](../../../../experiments-v2/RP01-MICRO/P8401/Program.cs):72–100. Каждая строка TRAIN — отдельный файл с двумя соседними методами M→N и одной допустимой парой. Gold закреплён буквально; не вычислять ожидаемый ответ через тестируемый CanonicalType.

| F1 | `class A{Func<int,int>M(){return x=>x+1;}void N(){for(int i=0;i<2;i++){}}}` | Loop |
| F2 | `class B{Func<int,int>M(){return (x)=>x+1;}void N(){for(int i=0;i<2;i++){}}}` | Loop |

Для настоящего `Compile` **одинаково** добавить `using System;\n` перед каждым TRAIN/query source как явный C# marker. Проверить до обучения, что method KindBag от этого не меняется; Parse/DetectStack — подготовка, не обучение. C#-маркер не является уроком и не может содержать gold. Если native DetectStack или Compile отвергает fixture, остановить qualification с исходной ошибкой; не подбирать новые строки, пока не изменён план. Компилированность самостоятельного C# приложения этими fixtures не обещается.

Обязательные pure controls без Train/Compile: unary twin; arity probe `class P{Func<int,int,int>Probe(){return (x,y)=>x+1;}}`; no-lambda F4/E4; async edge `class E{async Task<int>Edge(){await T();return 1;}}`.
