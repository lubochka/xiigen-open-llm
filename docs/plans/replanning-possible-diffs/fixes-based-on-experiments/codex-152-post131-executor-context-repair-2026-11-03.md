## Что должен предъявить исполнитель ремонта

1. Названный ID очереди, текущую фазу, фактически перечитанные AGENTS/CLAUDE и полный применимый стек120. 2. Для каждого затронутого проекта: конкретный build, исходники/DLL, discovery ожидаемых имён и TRX той же сборки. Кодировка/компиляция/setup/assert — разные стадии. Падение технической команды ремонтируется внутри наряда; спорное изменение требования передаётся архитектору с input/expected/actual/log, а не с просьбой заново разрешить тесты.
3. Для saved reanalysis: неизменные input bytes, отдельный новый output, фактический verifier и outer exit; Train/Predict/Flow/Load0. Положительный пакет и адресная порча различаются на нужной границе. Если producer archive недоступен или новая checker сборка не проверена — точный NOT_PROVEN/UNRUN, без фиктивного PASS.
4. Отдельно: достоверность процедуры, научный результат и продуктовая приёмка. Любое измеренное полезное улучшение — успех именно этой метрики/профиля; остальные изменения показываются рядом. Документный ремонт не меняет admission/HOLD по ресурсным ухудшениям и не объявляет новый выигрыш точности.
