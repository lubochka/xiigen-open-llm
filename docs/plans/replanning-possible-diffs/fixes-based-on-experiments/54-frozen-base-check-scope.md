## Действующее уточнение после P102 — Сохранность одной попытки не устанавливает виновника старого повреждения

**Проверка `POST102-FIX-FBC`. WRONG.** Before/after hash одинаковый, значит этот writer никогда не портит файлы; меньший набор hashes сохраняет полноту проверки.

**CORRECT.** Оптимизация сравнения не сокращает обязательное множество base tensors/bytes. Совпадение доказывает сохранность только в названном наблюдавшемся окне; причинная атрибуция повреждения требует отдельного воспроизведения.

**Адресная приёмка.** Контроль изменяет любой обязательный element вне прежней sampled области и должен быть обнаружен. Ресурсный счёт сравнивает одинаковое окно и включает все попытки. Canonical files не портить ради доказательства; use isolated fixture. R03 отдельно защищает consumed inputs.

Применять [единый контекст40](../experimets/40-effective-executor-context-2026-11-02.md) и [адресный план121](121-post102-addressed-repair-plan-2026-11-02.md): актуальные роли навыков, один рабочий оценщик, ordinary consumer и реакция на test/report failure. ## 3. Математическое основание и точная граница сложности

Для двух `float[]` одинаковой длины обозначим `bits(x_i)` 32-битное представление элемента. Старый предикат равен

`E(x,y) = (|x|=|y|) ∧ ∀i bits(x_i)=bits(y_i)`.

Преобразование четырёх байтов одного `float` в его 32-битный рисунок взаимно однозначно. В одном процессе byte order обеих сторон одинаков. Поэтому

`E(x,y) ⇔ |bytes(x)|=|bytes(y)| ∧ ∀j bytes(x)_j=bytes(y)_j`.

Здесь нет арифметики с float: сохраняются различие `+0/-0`, payload/sign NaN, infinities и все нормальные/subnormal значения. Это сильнее числового равенства и не допускает tolerance. Разные длины дают false у обоих предикатов; fallback сохраняет прежнее поведение для массива, чей byte length не помещается в Span<int-length>. Никакого предположения о том, что «NaN всегда равны», нет.

Пусть `M` — число float базы, `R` — число float эталона, `P` — число именованных параметров, `K` — объём их ключей/shape metadata. Старое сравнение базы обходится в `Θ(M)` с LINQ iterator/delegate на элементах и `O(P)` объектов перечисления за проход всех массивов; spans также требуют `Θ(M)` читаемых данных и `O(1)` дополнительной памяти на один массив. Удаляется слой перечислителей/делегатов; возможная SIMD-обработка является свойством конкретного runtime, а не обещанной векторизацией или новым асимптотическим порядком.

**Весь `RequireValid` не становится O(1)**: остаются hash эталона `Θ(R+K)`, поиски `SingleOrDefault`/allowlist порядка `O(P²)` и прежние структуры/проверки. Верхняя оценка остаётся `O(M+R+K+P²)` на вызов; при `C` вызовах — множитель `C`. Число вызовов этим планом не сокращается. Из этой формулы нельзя вывести процент выигрыша wall/CPU, пропорциональный размеру модели, или экономию всего обучения. Она доказывает эквивалентность и объясняет возможное уменьшение постоянного множителя; величину проверяет отдельная native A/B квитанция.
