## RF03. Вердикт P30 следует назначенному сравнению

<!-- OWNER-CONTEXT-120 --> **Самопроверка выбранного раздела:** METRIC по договору120 во входе файла; собственные source/caller/данные/доза и negative+positive этой строки обязательны. **Алгоритм.** У evaluator должны быть явные assigned alpha A/B, идентичность panels/candidate IDs, фактическая score formula и observable: top1, ranking или другая заранее выбранная метрика. Сначала проверить полноту/finite значения и tie policy. Затем вычислить predictions этого observable при назначенных alpha. Не считать `!strictDominance` настоящим пересечением. Если изучается весь интервал alpha, пересечения score lines и смена победителя на интервале считаются отдельно от эффекта двух actual arms. Tie-only row, unchanging ordinal winner, ненаблюдавшаяся смена ниже top1 и недостаток candidates имеют разные причины отсутствия evidence.

**Приёмка:**

- A=(1,1), B=(1,1): permanent tie, `NOT_INFORMATIVE_FACTOR_PANEL`, actual top1 не меняется.
- A=(2,2), B=(1,1): strict dominance, тот же вывод, valid control работы вычислителя.
- A=(2,0), B=(0,2) при alpha0/1: смена winner, informative для top1.
- Та же пара при одинаковых alpha A=B или при двух alpha по одну сторону crossing: фактор назначенного A/B не различим.
- Empty/NaN/incomplete panel: invalid evidence с причиной, не positive и не scientific null.

На старых observations создать отдельную versioned correction с input hashes. Не переписывать report, который описывал первоначальное исполнение. `transfer-status.json` R7 изменять только после этой приёмки.

## Исполнительное задание для каждой работы

Перед началом назвать RF-ID и текущий SHA целевых файлов, прочитать его evidence и затронутые карточки. Если адресный owner уже исправлен новым коммитом, сравнить его конкретную приёмку с этим требованием и снять только действительно закрытый остаток. Не повторять весь старый аудит из-за движения соседней документации.

1. Записать один failing counterexample и один valid control до правки; для сложной транзакции — перечисленные late failure boundaries.
2. Назвать producer→typed input→state owner→ordinary reader→observable и migration policy там, где меняются keys/state.
3. Реализовать минимальный адресный repair, сохранив уже принятые positive behaviors. Не добавлять второй обходной путь с hardcoded gold.
4. Снять после правки те же наблюдения, execution summary и actual operation counts. Report reconstruction использует0 Train; unit mutation test и новый scientific training не смешиваются.
5. Перед DONE сверить **опубликованную** вершину, реальный diff и receipts. Указать отдельно code implemented, native acceptance, consumer integration, useful effect, state restore. Никакой один флаг не заменяет остальные.

Проверка плана: у каждой строки есть owner, вход/отказ, observable, positive control, запрещённая подмена результата и критерий завершения. Существующие scientific recipes не получают нового запуска от этой таблицы. Публикация плана не публикует продуктовую реализацию и не меняет исходные raw.
