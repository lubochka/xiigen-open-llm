## S01. Проверяющий P104 должен увидеть испорченные данные

**Владелец:** `experiments-v2/RP01-MICRO/P10401/Program.cs`, условия2.4/3.5/4.1/4.4, `AddCheck`, сериализованные acceptance receipts. **Причина:** четыре ветки отвечают `false` по имени порчи, а удержание допускает любые два шага.

**Выбранное устройство.** Чистый evaluator принимает типизированные данные/receipt и frozen expectations. Enum мутации, ожидаемый исход и название теста ему не передаются. Отдельный mutator меняет копию наблюдения. Сохраняются hashes исходного/испорченного входа, неизменного evaluator, точная причина отказа. Неожиданное исключение получает статус HARNESS_ERROR, а не ожидаемого обнаружения дефекта.

**Адресные случаи.** Для2.4 удалить прежний ответ, затем заменить два шага на неправильные: проверять полный ordered payload, lesson identity и один state lineage; правильная длина не спасает. Для3.5 смешать native и synthetic counts; evaluator проверяет разложение. Для4.1 удалить admissible subset из receipt. Для4.4 сохранить только отказы, но подставить положительный lawfulAccepted. Для1.4 изменить реальный gateDescriptor, а не локальный bool. Остальные условия рассматриваются отдельно, не принимаются числом17.

**Приёмка.** На сохранённых честных rows остаются lawful2/5→4/5 и correct3/5→5/5. Все перечисленные реально испорченные receipts отвергаются по ожидаемой причине. Для потребителя B добавить отдельный future native witness: API возвращает payload выбранного непервого lesson, ordinary executor исполняет его ordered steps; замена payload на rank1 падает. Этот witness не подменять `trained_corpus_row`.

**Стоимость и восстановление.** Первое исправление — только replay сохранённых данных, Train=0 и native model reads=0. Паспорт node calls исправляется на observed12 native +10 synthetic;16 не является нижней границей. Сбой report не разрешает повторить обучение. Оригинал attempt-0002 остаётся неизменным, corrected acceptance ссылается на его hashes.

## S03. Закрыть обход через сохранённое подтверждение качества

**Владелец:** `ProjectWikiRequestRoutingTrainableModel.HasPassedEvaluationGate`, `FromSnapshot/ToGateEvidence`, `ProjectWikiRequestRoutingUnit.ExecuteAsync`; DTO в `ProjectWikiDomainModels.cs`.

**Решение:** единый валидатор проверяет finite всех трёх сравниваемых observations и соответствующих thresholds до сравнений. Другие числовые поля gate, если они используются как активные ограничения, входят в ту же схему валидации; неприменимые поля не становятся доказательством. Отсутствующее/неизмеренное evidence даёт NeedsSecondPass и причину с точным полем. Никакого clamp Infinity до1, подстановки0 или снижения действующих0.95/1.0/0.85. Отдельно проверить соответствие сохранённых thresholds версии политики; finite само по себе не означает разрешённый порог.

**Контрпример:** finite biases `[.1,.5,.05,0,…]`, empty token weights, хороший gate. По одному заменить RouteAccuracy, WrongAnnotationRate, AverageConfidence на NaN/+Infinity/-Infinity; затем каждый threshold на nonfinite. Приёмка проходит через входной snapshot обычного Unit и проверяет `CanStartTargetRunner=false`, конечную наружную confidence и именованную причину. Хороший snapshot сохраняет Selected. Для каждого законного порога — below/at/above там, где диапазон метрики позволяет; точность не требует невозможного значения выше1.

**Красная проверка:** удалить finite validation именно gate evidence, оставив новые guards оценок; +Infinity witness снова разрешает маршрут. Эта порча должна ломать новый тест. Проверка только private helper или отражением без Unit не закрывает конечного потребителя. Модели не обучаются; fixture имеет явные коэффициенты и не называется выученной способностью.

## S04. Разделить смысловой ключ и происхождение учебной пары

**Владельцы:** `TranslationMachine` и builder структурированного урока; `SemanticTokenizerUnit.TrainOnExample/Tokenize`; `ExecutorUnit.TrainOnExample/Execute/TrySelectKnnCandidate`; `VerifierUnit`; checkpoint serialization/import в `TranslationTrainedUnits.cs` и `TranslationUnitContracts.cs`.

**Архитектурное решение принято для плана.** `PAIR` — учебное происхождение, не семантика и не разрешение ослабить source floor. Смысловой ключ хранит pattern/concepts и проверенные RULE-сегменты; provenance хранит pair ID отдельно. Обновляются все производители и читатели ключа, versioned checkpoint и миграция. Точный состав изменяемых полей перечисляется из кода перед реализацией, затем проверяется полнота по call sites. Это детализация выбранного договора, не перенос выбора архитектуры на исполнителя.

**Политика допуска:** известная семантика сохраняет существующий0; обычная EN_RU без неё —0.60. Наличие PAIR никогда не переключает эти основания. Миграция старого checkpoint извлекает только PAIR-сегмент, сохраняя следующие RULE. Коллизии одинаковых semantic keys с разными payload выявляются до публикации всей новой памяти; конфликт не разрешается порядком dictionary и не приводит к частично изменённому live state. Исходный checkpoint сохраняется. При несовместимости — диагностический отказ миграции, без Train и без восстановления старой привилегии.

**Почему другие варианты отвергнуты:** односторонний strip расходится с writers; обрезка хвоста уничтожает полезный RULE; сохранение bypass для legacy оставляет дефект; падение порога для всех меняет договор вместо ремонта идентичности. Инвариант «один смысл с другим номером урока даёт то же решение» достаточен для этого выбора; отдельное решение владельца только из-за старого OPEN не требуется.

**Приёмка:** одинаковый текст/семантика с разными PairId; нет/есть PAIR; RULE после PAIR; genuine semantic concept; unknown concept; similarity ниже/на/выше.60; legacy checkpoint и конфликт миграции. Путь фиксирует early-return/KNN. Проверить ordinary TranslationMachine и verifier после fresh import: новый смысл читается, требуемые термины сохраняются, baseline exact/phrase/word ответы удержаны. Реальная порча возвращает проверку `Contains("|PAIR:")`, и метаморфный тест падает. Сначала восстановить/опубликовать исходники существующего диагностического теста отдельно от default compile; журналы сами по себе не воспроизводимы.

## S05. Исправленный смысл должен согласовываться с ролями каждого слова

**Владелец:** `TranslationSemanticTokenizer.ClassifyPos/DetermineRole/BuildRuleTags`; тип исправленной аннотации и её применение в `SemanticTokenizerUnit`. **Граница:** это отдельная причина от S04; один ремонт не считается доказательством другого.

**Решение:** вернуть целостный semantic result: Pattern, Signature, Tokens, Roles, Lemmas, RuleTags согласуются. Коррекция не может менять только заголовок, оставляя противоречащие роли незаметными; поддержанные token-level исправления сохраняются и импортируются вместе, а недостающие наблюдения явно маркируются. В исходном классификаторе известная сущность не становится глаголом только из-за последней `л`; imperative и passive/tense различаются по объявленному поддержанному разбору. Не заменять это списком двух ожидаемых готовых ответов и не заявлять универсальную русскую морфологию.

**Проверка:** «проверь файл»/«файл проверен», пунктуационные варианты, перестановка, отрицание и незнакомое слово. Первые две сохранённые строки задают известный failure witness; дополнительные fixture checks не расширяют автоматически учебную панель P106. Проверяются роли конкретного токена, полный смысл и направление перевода, а не наличие ACTION/OBJECT где-либо в signature. Для неподдержанной морфологии — явный unknown без fabricated tense. Обычный tokenizer, semantic unit, TranslationMachine/verifier и свежий импорт проверяются раздельно. Удаление поправки POS возвращает «файл=VERB» и ломает приёмку.

## S06. Импортированное качество должно проходить тот же порог

**Владелец:** `OrchestrationPlanMachine.CreateImportedEvaluationGate`, `ImportAsync`, **`ImportCheckpoint`**, `LoadCheckpointAsync` и местная оценка; обычный `ExportAsync` и строители checkpoint/manifest refs. `ImportCheckpoint` копирует готовый `LastEvaluationGate` в обход первого helper, поэтому ремонт одного helper не закрывает задачу.

**Выбранная политика:** один существующий порог .75 и один finite guard для local/import. Eval-ссылки сохраняют происхождение и проходят прежнюю проверку baseline-unverified, но не повышают0.1 до пройденного gate. Нулевой sample count legacy импорта означает отсутствие переданного счётчика, не нулевую размерность реально выполненного экзамена. Схема evidence отделяет это состояние от измеренного0; старые исходные exports не переписываются.

**Сохранённый флаг:** `PassesGate=true` не является достаточным доказательством. Оба import-входа вызывают общий валидатор evidence до выдачи принятого gate. Честный низкий результат с `PassesGate=false` и отсутствие gate допускаются как непроверенное состояние. Противоречащий checkpoint (`PassesGate=true`, accuracy .1/nonfinite) отклоняется с точной причиной **до изменения live state**. Нельзя просто скопировать флаг и сбросить только SemanticQualityClaimed. Экспорт не восстанавливает доверие по одному старому bool.

**Приёмка:** .1 и .749 не получают пройденный gate, .75 и законное конечное значение выше проходят при корректных остальных полях; NaN/±Infinity и baseline-unverified refs не получают доверенный gate. Для accuracy диапазон[0,1] проверяется отдельным контрактом, не смешивается с generic finite score. Проверить обе цепочки: LearningMachineExport→ImportAsync→ExportAsync и checkpoint bytes→LoadCheckpointAsync→ImportCheckpoint→ExportAsync. Подменить в реальном checkpoint accuracy на .1 при PassesGate=true; после отказа прежние state/ответы остаются, новых eval refs нет. Реальная порча возвращает `>0` либо прямое присваивание LastEvaluationGate, и соответствующий witness падает. Это исправление согласованности существующего договора, не утверждение о случившемся плохом импорте.
