## Что исправлено и что ещё требует работы

Последние коммиты закрывают несколько конкретных дефектов, но не всю цепочку переноса опыта в обычный продуктовый вызов. Новая немасштабированная потеря уже читается обоими сторожами сходимости; HNSW проверяет уровни соседей и максимальную глубину; дополнительные входы запуска повторно сверяются перед дочерним процессом. Эти работы нельзя снова назначать как отсутствующие.

Сохраняются другие границы: обычное декодирование может скрыть неизвестный номер токена; среднее по шагам обучения названо конечным результатом и участвует в двух порогах публикации; переводческая партия может частично изменить живую память до отказа; поиск завершает уровень и ограничивает кандидатов до полного допуска обычного читателя. Кандидат фильтра из P101 допустим только для его однотокенного ASCII-контракта: глобальное правило `tokenId < 128` в байтовом словаре исключило бы русские, ивритские и другие многобайтовые ответы.

**Действующий план:** [118-post101-addressed-repair-plan-2026-11-02.md](118-post101-addressed-repair-plan-2026-11-02.md). **Изменённые карточки:** [119-post101-card-hardening-and-coverage-2026-11-02.md](119-post101-card-hardening-and-coverage-2026-11-02.md). Предыдущие 113–116 сохраняют исторические доказательства; их OPEN/DONE и прежний NEXT относятся к указанным там срезам. Ниже каждому выводу назначен собственный уровень подтверждения.

## 2. Существенные открытые границы переноса

### A101-01. Исправление конца ответа не устраняет молчаливую потерю токена

В [BpeTokenizer](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/01.Tokenizer/BpeTokenizer.cs) `EosToken` теперь равен `null`, а [TextGenerator](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/09.Inference/TextGenerator.cs) берёт специальный конец ответа только из явного `verifiedEosToken`. Это правильный отдельный перенос коммита `3194310941c4`.

Однако `Decode` по-прежнему заменяет неизвестный ID на `Array.Empty<byte>()`. Проверка допустимости IDs в генераторе включена только для detailed-пути. Следовательно, обычный `Generate` и прямой `Decode` не получили того же договора. В сохранённом P99 восемь вставок неизвестного ID не меняют видимый правильный текст; все восемь должны быть видимы вызывающему как отказ/ошибка декодирования, а не как дословно правильный результат. Искусственная модель с несовпадающими vocab 2048/336 показывает достижимость обычного пути; это не измерение частоты в обученной эксплуатации.

**Исправление и приёмка:** A101-R1 — единая проверяемая граница декодирования, явный unknown ID и его позиция, отказ до публикации частичного ответа; обычный и detailed-пути; положительные контроли корректной композиции байтов. Совпадение финальной строки с gold само по себе недостаточно.

### A101-02. Однотокенный фильтр P101 нельзя переносить на весь UTF-8

[P101 Program](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/experiments-v2/RP01-MICRO/P10101/Program.cs) выбирает допустимые однотокенные ответы байтового словаря условием `tokenId < 0x80`. В назначенном опыте ответ — один ASCII-оператор. В обычном тексте `Я` кодируется байтами `[208,175]`, `א` — `[215,144]`, `🙂` — `[240,159,153,130]`; каждый полный поток корректен, но такой фильтр исключает все его байты. Это доказуемая граница кандидата, **не внесённая регрессия текущего Sampler**.

**Исправление и приёмка:** A101-R2 — сначала определить контракт потока и terminal-политики. Валидность проверяется по накопленному UTF-8-префиксу и законченному ответу, а не по самостоятельной декодируемости каждого токена. Проверить русский, иврит, emoji, разрезанный многобайтовый символ, неверную последовательность и конец на незавершённом префиксе. Ни глобальный ASCII-whitelist, ни скрытая дополнительная генерация за пределами maxTokens не назначаются этим аудитом.

### A101-03. Поля Final в отчёте Wiki содержат среднее траектории

[ProjectWikiDpoMetricRunner](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/42.ProjectWikiDomain/ProjectWikiDpoMetricRunner.cs) собирает метрики `StepMany`, затем вычисляет `sum(metric * PairCount) / sum(PairCount)`. Вес по числу пар корректен; прежнее подозрение о смешивании масштабов этим вычислением не подтверждается. Но среднее записывается в `FinalLoss`, `FinalAccuracy`, `FinalRewardMargin` из [модели отчёта](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/42.ProjectWikiDomain/ProjectWikiDomainModels.cs). Метрики шага описывают вычисление до обновления; среднее траектории не измеряет конечный checkpoint.

Поля реально прочитаны порогами [CrossStackBusinessFlowGraphTrainingPipeline](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/42.ProjectWikiDomain/CrossStackBusinessFlowGraphTrainingPipeline.cs) и [ManifestPublisher](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/42.ProjectWikiDomain/CrossStackBusinessFlowGraphManifestPublisher.cs); также они расходятся по отчётным адаптерам. Это не только неудачное название поля. При равных весах accuracy `[1,1,1,0]` даёт среднее 0.75, а `[0,0,0,1]` — 0.25: порог среднего может решать противоположно последнему измерению. Это арифметические свидетели при остальных фиксированных допусках, **не утверждение о найденной исторической неправильной публикации**. Даже последняя метрика шага ещё не заменяет новое чтение конечного состояния.

**Исправление и приёмка:** A101-R3 — отдельные trajectory mean, last-step-pre-update и final-state-evaluation; конечное состояние читается на фиксированных TRAIN/EXAM без новых обновлений. Явно выбрать метрику для каждого потребителя. Сохранённые старые Final нельзя без миграционной пометки переименовать в «измеренный финал».

### A101-04. RF01: отказ партии возможен после частичной записи

[TranslationMachine](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/27.TranslationDomain/TranslationMachine.cs) предварительно проверяет синтаксис JSON, затем обучает живые units и только после этого оценивает held-out. Валидный JSON `42` вместо ожидаемого `ExecutorInput` проходит синтаксический просмотр, но может упасть при десериализации после записи первого правильного урока. Ошибка позднего held-out имеет ту же границу. Это статический контрпример по актуальным владельцам, не новый native run.

**Исправление и приёмка:** сохранить RF01, выбрать staging всей изменяемой партии и единственную публикацию после typed validation, обучения и held-out. Проверять memory/history/readiness/version/answers сразу после отказа и до любого restore. Отдельные случаи: неверный тип поздней строки, ошибка trainer, отмена, поздний held-out и конфликт версии. Старый синтаксический guard оставить как полезную раннюю проверку.

### A101-05. RF06: два разных преждевременных завершения поиска

В [TranslationUnitContracts](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/27.TranslationDomain/TranslationUnitContracts.cs) `Take(k)` предшествует `ApplyCandidatePredicate`: пять непригодных результатов могут скрыть шестой пригодный. Кроме того, cascade завершает full-tier при source threshold 0.35, тогда как [обычный EN→RU исполнитель](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/27.TranslationDomain/TranslationTrainedUnits.cs) позже требует 0.60. Кандидат 0.50 закрывает full-tier, затем отбрасывается вызывающим; пригодный prefix 1.00 не посещается. Одной перестановки targetPredicate перед Take недостаточно.

**Исправление и приёмка:** полный допуск обычного читателя должен участвовать в завершении tier и cap. Logical aliases одного урока не считаются независимыми голосами. Нужны два отдельных отрицательных свидетеля и сохранение приоритета действительно пригодного full-tier. Обычный executor должен получить результат без обхода через exact/phrase/wordmap.

### A101-06. RF02: rehash уже сделан, идентичность фактически прочитанных bytes ещё отдельная задача

[New-RunBinding](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/experiments-v2/_runners/run-binding/New-RunBinding.ps1) теперь сверяет required/optional/extra входы перед child. Сохранённый тест с настоящим дочерним Reader подтверждает чтение объявленных байтов в своей fixture; checker malformed claims тоже исправлен. Эти изменения полезны и не требуют повторной реализации.

Остаются интервал между проверкой и чтением, а также MSBuild instance identity: очередь source closure хранит path/depth, visited привязан к пути, evaluation явно передаёт Configuration, но не полный набор effective ProjectReference properties. Два экземпляра одного проекта с разными свойствами не равны одному пути. Полная цепочка New-RunBinding→MSBuild→child не подтверждается ручной phase6fixture. На данном срезе обнаруженные обычные callers ещё не предъявляют непустых optional/extra; риск API не выдаётся за доказанную порчу прошлых опытов.

**Исправление и приёмка:** RF02d-residual — выбранный immutable snapshot/owned-handle договор до consumption; RF02a — keyed evaluated instance `(path, effective properties)`; RF02b/c — семантический допуск terminal и полный учёт попыток. Отдельно удержать уже пройденные unchanged/missing/changed controls.

### A101-07. Остатки обычных потребителей

**RF05a:** zero-overlap guard маршрутизатора уже работает в исходнике. Невзвешенное голосование k5 всё ещё может отдать точный CODE_Q далёкому большинству; по семи seed-урокам source-derived расчёт даёт 4/7, а перестановка меняет спорный выбор. Это не новая native accuracy. Нужны явное правило точного совпадения/конфликтов, все семь controls и trace ordinary wrapper до его confidence; static seed-память не равна всей архитектуре learned routing.

**P98 producer→consumer:** `BpeTokenizer.Train` возвращает размер/причину завершения, но [BuildTokenizer обычного trainer](https://github.com/lubochka/llm_mvp_core/blob/3194310941c428ef9a5e643c4dc9d7ad7d15447e/18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs) пока игнорирует результат. Нельзя утверждать, что его конкретный корпус обязательно недобирает 512; подтверждён разрыв наблюдаемости, а не конкретный отказ этой обучающей строки. Недостижимый запрос допустим для маленького корпуса: требуется честный outcome и выбранная политика, а не универсальное исключение.

**P83:** основной expression-body extractor исправлен. Scoped target с отдельным Body-only договором — отдельное расширение; оно не отменяет сделанный перенос. Ordinary caller acceptance с реальной assembly ещё не закрывается структурными component tests.

## 5. Исправления точности объяснений

1. **Потеря с индивидуальными масштабами.** Для весов `(0.5,0.5)`, loss `(0.2,0.8)`, Signal `(1,2)` получаются weighted0.9, unscaled0.5, ложное деление0.6. Ошибка0.1/0.5 = **20%**, а не40%. Числа в oracle верны; ошибочна его словесная строка и повтор в `required-changes.md`/`docs/projects/11-dpo.md`. Текущие документы исправлены; исторический oracle-output сохранён с этой поправкой. Корректность новой формулы UnscaledLoss этим не опровергается.
2. **P101 objective parity.** Writer сравнивает product.Loss с copy.Loss, хотя копия умножает её на13/12. По всем пяти checkpoints product.Loss совпадает с copy.UnscaledLoss до сохранённой точности; четыре остальные поля тоже совпадают. Поэтому корректный вывод — «сверка objective metrics подтверждена по тем же величинам; сверка gradients/updates с native Step не выполнена». Нельзя превращать это в полную аттестацию копии или переписывать исторический false без отдельной hash-bound correction.
3. **P101 причинность оптимизатора.** `mean(abs(w_end-w_start))/steps` — среднее конечное смещение на число шагов, не средний размер отдельного шага. При движениях `+1,-1` первая величина0, вторая1. Одни endpoints не доказывают подавление вторым moment и смену знака gradient. Это допустимые гипотезы, которым нужен отдельный контроль; ради объяснения старого отчёта новое обучение не назначается.
4. **P93 одноклассовая DEV.** Эмпирическая доля успехов определена и равна1; монотонная константа1 имеет Brier0 на этой панели. Неопределённой остаётся польза различения ошибок и переносимость калибровки на ошибки. Формулировка «эмпирическая вероятность не определена» слишком сильна. Записанный отказ учить PAV не подменяется новым fit.
5. **P100 частота и JIT.** «Примерно47%» в объяснении двухкандидатного распределения — расчётная вероятность, а не измеренная частота неудач. По сохранённым logits вероятность byte182 составляет примерно46,0–46,1% при названных настройках; это не наблюдаемая частота. В P96/P97/P100 различие первого/следующего timing не доказывает JIT как единственную причину: нужны прогрев и порядок измерения. Сохранённые времена остаются фактом своего протокола; причинная атрибуция понижается до предположения.

Исправления являются новой квалификацией над неизменными первичными данными. Исторические отчёты, stdout, model weights и optimizer/RNG файлы не переписываются. Для будущего writer correction содержит target digest, предыдущий вывод, новый вывод и точное основание; не превращает выводимое число в непосредственно измеренное.

## 6. Состояния, бюджет и обычный читатель

P101 действительно начал с записанного optimizer400 и дошёл до500; P89 фактически начал с0. Общая папка S0 или слово restore не доказывают равенство optimizer/moments/scheduler/RNG. Для P101 дополнительное чтение repair согласуется с main по пяти recorded weight hashes, token IDs, текстам и logits `+/-`; это проверка сохранённых свидетельств, не новая загрузка бинарных файлов этим аудитором.

Полный расход включает подготовительные Fit, контрольные запросы, неудачные builds, повторные чтения и diagnostic calls. Например, P94 имеет основные node calls4/6 и дополнительные1/2, а P99 —6 BPE Train при исходном плане4. Эти расходы видимы в raw и не должны исчезать из summary; записанное изменение задания не объявляется самовольным только из-за расхождения с первоначальным числом. В P94–P97 отдельный BPETrain словаря-двойника виден в программе и описании, но не во всех общих budget-таблицах: memory_fits корректен для KNN-памяти и не обозначает все learner calls. Нужны отдельные строки parent memory fit, вложенный BPETrain и дополнительный twin BPETrain без двойного счёта независимых программ. «Не измерено», «выведено из структуры», «измерено» остаются разными источниками числа.

Проверка learned-state должна доходить до предметного результата: для Unit — typed множество и ассоциации; для Flow — исполненное отношение; для Graph — записанное sink-состояние. Одинаковый ответ тривиального правила не отменяет реальность обучения, но ограничивает доказательство его необходимости/преимущества. Статический отказ в illegal graph не становится приобретённым нейросетевым навыком.
