## Целостность IDs и атомарный импорт редакции — уточнение 11 ноября 2026

Дополняет уже опубликованный 11 ноября проект active revision; принятый узкий FIX-RET сохраняется. Source OrchestrationKnnStore.Add молча игнорирует повтор PairId, тогда как PromptFlowGroundingModel.Train далее строит fresh weights. Поэтому новый revision-контракт нельзя ограничить наличием MemberPairIds: возможна несогласованность нового target с ранее сохранённой парой. Это проверенная граница проекта ремонта, без заявления о новом native отказе ordinary batch caller.

**До любых изменений** owner проверяет immutable PairId→canonical payload. Точный повтор возвращает явный идемпотентный результат без второй дозы/новой revision. Повтор ID с другой target, prompt, mode или FlowRef отказывает до записи weights/pairs/revision; легальная смена цели получает новый lesson ID и новый RevisionId по правилу карточки. Не удалять dedup guard.

Import строит отдельный candidate и до публикации проверяет уникальность ID, все ссылки members, согласованность их FlowRef/mode/нормализованной target с revision и schema. Conflicting duplicate, missing member, чужой mode/target или неоднозначная legacy history оставляют прежнее состояние целым. Проверка ссылки без проверки payload недостаточна.

Новые отрицательные контроли: B повторно использует ID A; identical duplicate; checkpoint с двумя разными payload одного ID; member с правильным ID, но неправильным body/mode/FlowRef; failure перед публикацией candidate. Повтор ID с изменённым payload отвергается до Train; сохранение нормального A→B1→B2 приобретения проверяется по существующему отдельному бюджету, не маскируется структурными Train=0 тестами. [План](audits/2026-11-11/repair-plan.md) и [review](audits/2026-11-11/followup/final-review.md).

## Уточнение действующего договора — аудит 11 ноября 2026

Основание: `llm_mvp_core@009bf226174441fa0fbf0336e74ad2f2b7174d92`. Это дополнение к карточке, а не заявление о выполненном ремонте. Принятый узкий FIX-RET и его сохранённые результаты остаются историческим положительным основанием. Ниже назначена следующая конкретная граница: исправление цели, затем новый парафраз этой исправленной цели. Нативный запуск в настоящем аудите не выполнен.

### Что именно остаётся неверным

В `PromptFlowGroundingModel.Train`:25–38 сравнение идёт со **всеми** прежними уроками того же FlowRef. `CanAccumulateCompatibleInputFeatures`:202–243 отвергает накопление, если хотя бы одна старая положительная цель отличается. Поэтому последовательность «старая цель A → исправление B с признаком beta → совместимый парафраз B с признаком gamma» оставляет только gamma. Старая A навсегда запрещает накопление признаков новой B. Это не повторное отсутствие объединения: объединение через max уже реализовано и принимается для своего совместимого набора.

Вторая сторона того же состояния: `FindLearnedPair`:154–168 ограничивает поиск FlowRef, но не активной редакцией тела. Сохранение правильного маршрута само по себе не гарантирует чтение актуального плана. `OrchestrationKnnStore`:48–59 выбирает первый результат при равенстве по PairId; переименование PairId не должно возвращать устаревшую цель.

### Выбранная форма ремонта

Владельцем остаётся существующий `PromptFlowGroundingModel` внутри `OrchestrationPlanMachine`; новые отдельные обучатели, teacher, классификатор и точная таблица готовых ответов не вводятся. Детерминированное сравнение целей — служебная проверка совместимости состояния, а не доказательство семантического понимания.

Предлагается **новая** типизированная запись `ActiveFlowTargetRevision` с полями `FlowRef`, `RevisionId`, `ChosenFlowRef`, `ExpectedRouteMode`, `NormalizedPlanText`, `MemberPairIds`. Имена обозначают проектируемый контракт, не существующий API. `RevisionId` — идентификатор смены принятой цели; совпадение содержания определяется тем же явным кортежем и той же нормализацией пробелов, которыми пользуется текущий код. Hash/PairId не используются как оценка качества.

1. При первом уроке создать активную редакцию. При совпадении кортежа с активной редакцией объединить **только** входные признаки этой редакции через max, как в принятом FIX-RET, и добавить PairId в её состав.
2. При действительном исправлении цели начать новую редакцию и свежие входные признаки. Старые пары оставить в истории, но исключить из допуска накопления и выбора исполняемого тела. Не объединять признаки A с B.
3. `FindLearnedPair` получает уже выбранный FlowRef и выбирает тело только среди `MemberPairIds` его активной редакции. Если такой пары нет, возвращает отсутствие доказанного learned body; вызывающий код использует свой явный fallback. Предсказанный FlowRef не добавлять к входным признакам запроса.
4. Сохранение/загрузка состояния переносит веса, пары и активную редакцию вместе. Расширить существующий checkpoint-контракт в его владельце; назначить версию схемы и проверку ссылочной целостности. Новый DTO не должен жить только в тесте или рядом с реальным состоянием.
5. Для старого checkpoint допускается восстановить редакцию автоматически, только если у FlowRef ровно одна совместимая группа целей. Если групп несколько и в снимке нет надёжного порядка принятия, не угадывать «последнюю» по PairId, имени файла или порядку JSON: вернуть явное состояние неоднозначности и отсутствие доказанного active body. Если вызывающий код использует существующий Mode2 fallback, явно сохранить причину перехода; его семантическая безопасность этим дополнением не доказана. Для продолжения обучения нужен явно выбранный актуальный снимок/повторный ввод принятой цели; старые байты не перезаписывать.

### Проверки, которые действительно различают ремонт

Основной владелец тестов — существующий `Tests/ExperimentBasedPromptFlowRetentionTests.cs`; соседние проверки тела маршрута из карточки48 должны читать тот же контракт. Следующие сценарии — **предлагаемые**, их исполнение не заявляется:

| Сценарий | Обязательное наблюдение |
|---|---|
| A → B1 → B2 при одном FlowRef | После B2 доступны входные признаки B1 и B2; признаки A не возвращаются; тело соответствует B |
| Совместимые B1/B2 в обратном порядке | Состав признаков одинаков; ни один парафраз не теряется из-за порядка |
| Старый PairId сортируется раньше нового, затем ID переименованы | Исполняемая редакция не меняется от лексикографического порядка ID |
| Save → новый объект Load без Train | Редакция, положительные чтения и отрицательный контроль сохраняются вместе |
| Load → следующий совместимый B3 | Продолжается B, а не заново A; доза обучения явно учтена |
| Старый неоднозначный checkpoint A+B без порядка | Нет молчаливого выбора старого тела; причина неоднозначности видна |
| Отключено ограничение по редакции | Должен покраснеть именно тест актуального тела; совпадение только количества пар недостаточно |

Учебный сценарий сохраняет уже предложенный бюджет: **5 одноэлементных batches = A + конкурирующий маршрут C + B1 + B2 + B3**. Пять состояний для чтения: после A/C, после B1, после B2, после Save/Load без Train, после B3. На каждом — те же пять заранее заданных запросов: парафразы B1/B2/B3, маршрут C и отрицательный запрос; итого25 readouts,1 save,1 load. Ожидания каждого состояния фиксируются до исполнения; будущий B3 до своего урока не считается усвоенным только по названию запроса. Прежние9 тестов сохраняют отдельный исторически назначенный расход.

Переименование ID и неоднозначная legacy-схема проверяются отдельно с Train=0; их вызовы import/load и чтения раскрыть отдельно, не спрятать в25 научных чтениях. Проверка **обратного порядка B1/B2 через настоящий Train** требует второй самостоятельной попытки с теми же5 одноэлементными batches,25readouts,1save/1load; вместе два порядка стоят10batches,50readouts,2save/2load. Импорт заранее объединённого словаря не заменяет эту проверку. Мутационные прогоны также имеют собственный полный расход. Если нужен новый научный набор сверх названного, сначала отдельно назначить его дозу. Не снимать уже действующие отрицательные проверки совместимости и no-leakage.

### Соседняя граница пустого/неподтверждённого соседа

`OrchestrationKnnStore.Jaccard`:69–78 сейчас даёт 1.0 двум пустым наборам. Текст из одной пунктуации может быть непустой строкой и иметь пустые tokens. Сам поиск также не исключает нулевое пересечение. Пустая лексическая информация не является подтверждением маршрута. Это отдельная строка ремонта общего store/caller, не основание снизить threshold текущего learned grounding. До изменения зафиксировать различие: сходство empty/empty, отсутствие соседа, слабый сосед и разрешённый fallback. Проверить обычный Mode2 caller, пустые/пунктуационные запросы, положительный непустой пример и отрицательную пару другого маршрута; не заявлять нативную достижимость только по формуле Jaccard.

**Условие приёмки:** source и checkpoint одного кандидата, сборка/discovery/назначенные тесты той же DLL, положительные и отрицательные чтения через обычного потребителя, мутация фильтра активной редакции, полный учёт дозы и финальный результат runner. Python-модель предиката из аудита объясняет дефект, но не заменяет эту приёмку.

## Приёмка и состояние обучения: аудит 28 октября

Панель должна сохранять точное множество уникальных RowId, Kind и gold. Контрпример P05: [T1,T2]→[T1,T1] имеет тот же размер, но прячет потерянный урок. Контрпример P11: 2/4→2/4 скрывает E1 gain и E2 loss; constant-answer baseline считать отдельно. 1→0 после настоящего обучения остаётся валидной регрессией. Сдвиг весов сам по себе не квалифицирует результат, PARTIAL и нулевой назначенный Train не закрывают учебную цель.

Применимость: FIX-RET. Контроль отчёта: точная панель, настоящий учебный этап, терминальное завершение и выполненные обязательные проверки — отдельные поля; успех одной оси не равен общему допуску. Требования по [плану88](88-gradient-warmup-transfer-repair-plan-2026-10-28.md) добавляются к исходному рецепту, не меняют исторические результаты и не назначают повтор обучения. Проверки сохранённого receipt используют raw уже выполненного обучения; новая самостоятельная программа обязана содержать назначенный Train. Если нужен новый вызов модели, сначала явно назначить полный бюджет, а не скрывать его в диагностике. Это профилактическая применимость, не установленный дефект каждого данного исходника. STOP/NEXT и ожидание исходного process handle из карточки сохраняются.

## 1. Измеренная причина и полезный результат

Тема — оркестрация: выбор выученного плана. Получатель — `PromptFlowGroundingModel` внутри `OrchestrationPlanMachine`. Это обучение памяти с извлечением, а не LoRA/нейронный DPO. Лабораторные имена LAB-A/LAB-B обозначают два разных плана, не две руки опыта и не два предметных домена.

После двух общих уроков обе руки отвечали на прежний запрос RQ1 правильно. Затем третий урок дал другой парафраз **того же** LAB-A. Контроль заменил входные признаки LAB-A; изменение сохранило прежние признаки и добавило новые по максимуму на каждый токен.

| Проверка | Контроль до→после | Изменение до→после |
|---|---|---|
| RQ1: прежний запрос, маршрут и полное тело плана | верно → неверно (чужой LAB-B) | верно → верно |
| RQ2: новый парафраз | неверно → верно | неверно → верно |
| RQ3: конкурирующий план | верно → верно | верно → верно |
| RQ4: отрицательный запрос | верно → верно | верно → верно |
| Итог правильных | 3/4 → 3/4 | 3/4 → 4/4 |
| Входные признаки двух маршрутов | 8 → 8 | 8 → 12 |

Агрегат 3/4→3/4 скрывает потерю RQ1: поэтому retention измеряется по переходу конкретного задания. Общий обученный старт обеих рук имеет одинаковый смысловой hash `5856573d504f...`. Полный ответ проверяется по `RouteMode`, `FlowGrounding.FlowRef`, верхнему `FLOW_REF` в результате и телу плана после нормализации пробелов; одного идентификатора недостаточно.

Источники: [A/raw-answers.json](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/experiments-v2/RP01-MICRO/N61-MODE1/results/RETENTION-M1-01/A/raw-answers.json), [B/raw-answers.json](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/experiments-v2/RP01-MICRO/N61-MODE1/results/RETENTION-M1-01/B/raw-answers.json), [состояния B](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/experiments-v2/RP01-MICRO/N61-MODE1/results/RETENTION-M1-01/B/states.json), [manifest с точной проекцией](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/experiments-v2/RP01-MICRO/N61-MODE1/results/RETENTION-M1-01/B/manifest.json), [отчёт](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/experiments-v2/RP01-MICRO/N61-MODE1/results/RETENTION-M1-01/report.md).

Цена — рост входного словаря, в этом наборе на четыре токена. Одноразовые latency/alloc/peak наблюдения противоречивы и не превращаются в норматив производительности. Противоречащие исправления, save/load, wrapper `GetOrchestratorAsync`, plugin и реальное исполнение flow исторически **не проверялись**. Успех по удержанию остаётся успехом по этому показателю и теме; остальные оси и регрессии всегда рядом.

## 2. Куда переносить и как ограничить

В [PromptFlowGroundingModel.cs:17–24](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/42.ProjectWikiDomain/PromptFlowGroundingModel.cs#L17) `Train` после `_knn.Add(pair)` безусловно делает `_weights[pair.FlowRef] = BuildWeights(pair)`. Именно эта запись стирает предыдущий входной словарь. Настоящий потребитель — [OrchestrationPlanMachine.GeneratePlanAsync:60–132](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/42.ProjectWikiDomain/OrchestrationPlanMachine.cs#L60): `TryGround → FindLearnedPair → RenderLearnedFlowPlan`.

План измеренного ядра: вычислить свежие веса, для совместимого парафраза того же flow объединить **только** `InputFeatureWeights`: для каждого ключа без учёта регистра `max(old,new)`; отсутствующий ключ трактовать как отсутствие, не вычитание. Все остальные поля `OrchestrationFlowGroundingWeights` остаются из свежего `BuildWeights`. Не менять KNN, confidence, query text, deduplication PairId, tokenizer и composer в этом срезе.

### Совместимый парафраз и исправление — разные операции

Опыт доказал пользу для двух согласованных формулировок одного плана. Он не разрешает сделать union общей политикой исправлений.

При переносе нужен узкий, проверяемый допуск накопления: `Mode1LearnedFlowGrounding`, тот же непустой `FlowRef`, тот же `Chosen.FlowRef`, тот же `ExpectedRouteMode` и то же нормализованное `Chosen.PlanText` у накопляемых уроков. Источник, PairId и формулировка prompt могут различаться — так было в опыте. Сравнение положительных целей выполняется **только при обучении** и не передаёт gold в inference.

Это предлагаемый защитный слой интеграции, а не новый измеренный выигрыш. Конкретная реализация: перед `_knn.Add(pair)` прочитать существующие пары этого FlowRef из `ExportPairs()`; если их положительные цели совместимы и старые веса есть — применить max; иначе выполнить прежнюю замену `BuildWeights(pair)`. Новая приватная функция `CanAccumulateCompatibleInputFeatures` — **запланирована, пока отсутствует**. В ней нельзя вводить семантические эвристики по словам запроса. Старое поведение при смене тела плана сохраняется; прежние KNN-пары не удаляются. Корректность разрешения противоречащих уроков этим не заявляется: это отдельная незакрытая задача, не дополнительный кандидат данного пакета.

## 3. Одна подготовка и точное продолжение

Порядок исходных уроков: `00-b` (LAB-B, “validate payment receipt email”), `10-a1` (LAB-A, “validate payment approval ledger”), `20-a2` (LAB-A, “check invoice consent journal”). Единственный источник полных DTO и EXAM — [experiments-v2/RP01-MICRO/N61-MODE1/Program.cs:133–168](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/experiments-v2/RP01-MICRO/N61-MODE1/Program.cs#L133): `BuildLessons`, `BuildExam`, `Pair`. Файлы в `35.ExperimentsV2/Experiments/Rp01Micro/N61Mode1/RETENTION/B/` содержат вариант learner, не авторские DTO.

У обоих LAB-A-уроков `Chosen.PlanText` буквально одинаков: `Validate approval, then persist the ledger.`; `RejectedText` одинаков: `Persist the ledger before validating approval.`. `Pair` задаёт обоим `Mode1LearnedFlowGrounding`, `Chosen.FlowRef=FlowRef=LAB-A`, `ExpectedRouteMode=LearnedFlowGrounding`. Следовательно предложенный compatibility guard **пропускает именно измеренное накопление** 10-a1→20-a2, хотя SourcePath/SourceBundleId/PairId различаются. Нормализация только whitespace: `string.Join(" ", text.Split((char[]?)null, StringSplitOptions.RemoveEmptyEntries))`, как [исходный scorer:314–315](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/experiments-v2/RP01-MICRO/N61-MODE1/Program.cs#L314). Нельзя приводить регистр или менять содержание positive, чтобы провести несовместимый урок. Сам измеренный max находится в [B/PromptFlowGroundingModel.cs:17–39](https://github.com/lubochka/llm_mvp_core/blob/4f35cb71b3db482bfe7ebe611c652c78d89d5db1/35.ExperimentsV2/Experiments/Rp01Micro/N61Mode1/RETENTION/B/PromptFlowGroundingModel.cs#L17).

Будущие файлы: `Tests/Fixtures/ExperimentFixes/v1/RETENTION-M1-01/lessons.json`, `exam.json`, `s0.checkpoint.json`, `provenance.json`. Общий S0 — результат первых **двух** native уроков. Существующий `states.json` содержит наблюдения, но сам по себе не объявляется готовым загружаемым checkpoint. Поэтому один producer создаёт S0 через настоящий `OrchestrationPlanMachine.ExportCheckpoint/SaveCheckpointAsync`; после fresh load проверяет RQ1/RQ3/RQ4 и сохраняет квитанцию. Все продолжения читают этот S0. Если совместимый полносоставный S0 уже зарегистрирован по [общему договору](02-learning-state-and-fixtures.md), производить его повторно запрещено. Новые отчёт и ресурсы — `artifacts/fbe/FIX-RET/attempt-0001/`; журналы тестов — `tests/`, затраты — `resources/`.

В S0 входят pairs, weights, PairIds и версия схемы; ни EXAM, ни эталонные ответы не добавляются к обучению. После restore третий урок предъявляется ровно один раз. В исходном опыте budget — 3 Train/8 Generate/3 Export на руку; будущая общая подготовка разделяет два общих урока и один урок продолжения, не выдаёт сохранённые counters за новые updates. В этом алгоритме нет optimizer/RNG: их отсутствие пометить N/A, не создавать фиктивные файлы.

## 5. Порядок и поведение исполнителя

Этапы: fixture/S0 → перенос max для совместимых парафразов → поштучное обучение → native save/load/continuation → wrapper из [E2E-плана](20-prompt-domain-e2e.md). На каждом этапе фиксируется конкретная недостающая проверка; статический просмотр не называется выполненным обучением. Сроки/повторные прогоны не расширяются из-за желания получить PASS.

Исполнитель — текущая default-модель сессии без override; native learner — указанная память. Скилы: `intent-to-plan-SKILL.md`, `phase-planning-SKILL.md`, `plan-review-SKILL.md`, `generated-code-review-SKILL.md`, `test-integrity-SKILL.md`, `human-communication-GLOSSARY.md` в `docs/skills`. Отчёт по-русски: RQ1 retention и RQ2 acquisition отдельно, затем другие ответы, размеры, стоимость и ограничения. Если понадобятся новые DPO, пары создаёт внешняя открытая китайская модель; выбор и оценку делает CODEX с `astra 6 ultracode`. Исторический simulation не получает задним числом такую provenance.

Любое измеренное улучшение полезного показателя — успех именно по нему и теме, даже без роста accuracy; регрессии не скрываются. STOP/NEXT немедленно прекращает действия прежней карточки: никаких дописываний её отчёта, тестов, commit или cleanup. Коротко сообщить уже известное состояние; при NEXT перейти к точному назначенному ID из [реестра](01-registry.md), при STOP больше ничего не запускать. Полные роли skills, русский шаблон отчёта и ожидание — в [общем контракте](03-test-and-execution-contract.md). Ждать тот же живой handle до exit/deadline, не заканчивать ход с вымышленным отказом, не повторять launch из-за тишины. Существующие эксперименты и raw не удалять и не подменять.
