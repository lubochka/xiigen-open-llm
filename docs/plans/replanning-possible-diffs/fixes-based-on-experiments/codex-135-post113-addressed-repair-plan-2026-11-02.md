### Исторический вариант устройства до публикации CAS

Этот раздел сохраняет исходное проектное решение. После9c2167f действующий выбор — существующий CAS с сохранным отказом и приёмкой по139/R117-03, а не повторная замена его writer gate. Ниже не самостоятельное новое назначение.

У каждой TranslationMachine один gate записи, общий для всех entrypoints, способных публиковать состояние. Захват происходит **до чтения версии-основы**; staged training/import, финальная проверка отмены и publication входят в одну транзакцию писателя. Номер новой версии назначается под тем же gate по текущему опубликованному номеру. Чтение RunAsync не берёт этот gate: оно один раз получает неизменный holder и завершает запрос на нём. Для текущих синхронных Task-returning mutation методов достаточно локального monitor; если реализация вводит await внутри транзакции, нужен единый async-compatible gate, а не monitor через await. Все call sites используют один выбранный механизм, вложенный повторный захват/публикация через другой путь исключены.

Это устраняет потерю A в расписании `capture(A,v7) → capture(B,v7) → publish(A,v8) → publish(B,v8)`. После ремонта B начинает с опубликованного A и получает v 9 либо явно отказывается до своей мутации по выбранному cancellation/contract. Учебный callback не повторяется автоматически. CAS с молчаливым повторным Train отвергнут: он способен увеличить учебную дозу; CAS с потерянным результатом без отражения отказа также непригоден. Один общий lock вокруг всех inference отвергнут: уже имеющийся snapshot reader позволяет не останавливать обычные ответы на время обучения.

EvaluateAsync измеряет фиксированный holder за пределами долгого writer gate. Receipt всегда содержит **measured state identity/version**, набор оценки и его hash. При записи результата берётся короткий тот же gate: если текущий holder соответствует измеренному, метрика публикуется вместе с этой принадлежностью; если уже опубликован другой, результат возвращается как измерение прежней версии (`STALE_FOR_CURRENT_STATE` — предлагаемый новый именованный статус), а AccuracyAfterLastBatch новой версии не меняется. Не называть этот статус существующим API до реализации. Новый native query или повторная оценка автоматически не назначаются. Версию публикации метаданных и identity обученного состояния различать, если первая возрастает без изменения второй.

## 4. R03 — конечные численные значения и независимый допуск

**Исправляет:** N05. **Владелец:** `P11001/src/NumericOutputVerifier.cs::Verify`, producer tolerance в `src/ScalarProjectionOracle.cs` и finalizer `Program.cs`. Область ремонта — численная приёмка, не оптимизация kernel.

До вычитания проверять конечность каждого expected/actual и tolerance, совпадение shape, конечный неотрицательный tolerance. У нуля свой положительный случай; при нулевом expected относительная ошибка выводится по зафиксированной существующей формуле, а принятие определяется тем же абсолютным/смешанным договором, что назначен заранее. Переполнение самого `actual−expected`, absolute/relative error либо расчёта tolerance также даёт именованный numeric-invalid; вычисленная Infinity не становится неограниченным разрешением. Числа не обрезать и не заменять нулём.

Один evaluator получает честные сохранённые массивы и их копии: finite +1; NaN actual; +Infinity/−Infinity actual; NaN expected; NaN/+Infinity/negative tolerance; форма с пропущенной координатой. Все неподходящие случаи должны дать отказ до вычисления итогового PASS; честный finite и допустимый zero-error проходят. Мутация проверяющего «вернуть прежний comparison без finite» должна снова показать ложный допуск и быть обнаружена набором.

Независимый oracle сохраняет полные координаты и способ получения tolerance; нельзя пересчитать expected из B или поднять tolerance после ошибки. В текущем saved JSON полные weights/tolerance не сохранены, поэтому replay может доказать конечность и известные ошибки, но **не восполнить** отсутствующую полную native oracle-проверку. Эта граница остаётся в новой receipt. Контроли массивов не создают Train, Forward или повторного benchmark.
