## 1. Что улучшилось и что этим не доказано

Тема обучения — **программирование**, профиль — следующий тип метода в C#. Получатель — `MethodKnnPredictor`, память — пары соседних методов одного файла. Проверяется сохранение уже обученной памяти при следующем непригодном наборе.

T1 содержит один файл с пятью методами: образуются четыре учебные пары. После настоящего Train обе руки отвечают `Loop` на все четыре закреплённых запроса. T2 содержит четыре разных файла по одному методу: пригодных пар нет. A допускает T2 по числу методов и вызывает Train, который сначала очищает память. B считает пары до Train и оставляет старую память при отказе.

| Состояние | A: допуск по числу методов | B: допуск по числу пар |
|---|---|---|
| Q0, до T1 | 0 пар; 0/4, все null | 0 пар; 0/4, все null |
| Q1, после T1 | 4 пары; 4/4 `Loop` | 4 пары; 4/4 `Loop` |
| T2: методы / пары | 4 / 0; Train вызван | 4 / 0; Train не вызван |
| Q2, после T2 | 0 пар; 0/4, все null | 4 пары; 4/4 `Loop` |
| Удержано относительно собственных правильных Q1 | 0/4 | **4/4** |

Это полезное измеренное удержание, основанное на ненулевом результате после T1. Постоянный ответ `Loop` тоже дал бы 4/4: **различение классов и обобщение на новые структуры не доказаны**. Связь с настоящим обучением установлена отдельно: пустая память → Train(T1) → четыре пары и ответы → разное поведение памяти после Train/admission(T2). Тест не должен подменять эту цепочку постоянным ответом.

Источники: [raw A](https://github.com/lubochka/llm_mvp_core/blob/c8b0d8a029ce721ecd906d3ff747e740b524be23/experiments-v2/RP01-MICRO/KHE/results/arm-A.json), [raw B](https://github.com/lubochka/llm_mvp_core/blob/c8b0d8a029ce721ecd906d3ff747e740b524be23/experiments-v2/RP01-MICRO/KHE/results/arm-B.json), [runner](https://github.com/lubochka/llm_mvp_core/blob/c8b0d8a029ce721ecd906d3ff747e740b524be23/experiments-v2/RP01-MICRO/KHE/Program.cs), [отчёт](https://github.com/lubochka/llm_mvp_core/blob/c8b0d8a029ce721ecd906d3ff747e740b524be23/experiments-v2/RP01-MICRO/KHE/results/report.md), [кандидат](https://github.com/lubochka/llm_mvp_core/blob/c8b0d8a029ce721ecd906d3ff747e740b524be23/experiments-v2/RP01-MICRO/KHE/results/candidate.md).

## 2. Точное место изменения и настоящий потребитель

Изменяется только [`12.SemanticCompiler/SemanticCompilerFacade.cs`, `TrainMethodKnn`:179–190](https://github.com/lubochka/llm_mvp_core/blob/c8b0d8a029ce721ecd906d3ff747e740b524be23/12.SemanticCompiler/SemanticCompilerFacade.cs#L179-L190). После прежнего извлечения методов вместо `allMethods.Count >= 4` считать **те же** соседние пары, которые принимает [`MethodKnnPredictor.Train`:127–139](https://github.com/lubochka/llm_mvp_core/blob/c8b0d8a029ce721ecd906d3ff747e740b524be23/12.SemanticCompiler/Prediction/MethodKnn.cs#L127-L139):

```csharp
var eligiblePairs = 0;
for (var index = 0; index < allMethods.Count - 1; index++)
{
    if (allMethods[index].FileId == allMethods[index + 1].FileId &&
        allMethods[index + 1].IndexInFile == allMethods[index].IndexInFile + 1)
        eligiblePairs++;
}
if (eligiblePairs >= 4)
    _methodKnn.Train(allMethods);
```

Это форма будущей правки, не внесённый код. Соседство означает соседние позиции **исходного списка**, одинаковый FileId и последовательный IndexInFile. Не сортировать/группировать методы, не создавать пары через границу файлов, не превращать KindBag в последовательность, не менять извлечение, ошибки пустых файлов или предел `short.MaxValue`. `_pairs.Clear()` остаётся внутри прямого `MethodKnnPredictor.Train`: контракт этого низкоуровневого метода не меняется. При отклонённом наборе facade просто не вызывает его.

В B тот же assertion требует Q1=4/4, Q2=4/4 и неизменные четыре пары. Другой compile/load/failure или Q1=0 не считается нужным воспроизведением. Сегодня этот тест ещё не запускался.

Method-память от них не обучается: Q0 должен оставить TrainingSize=0. EXAM попадает в накопитель E05, но не в `_methodKnn._pairs`; ответ и метрики E05 не используются для оценки MethodKnn. Эти затраты вне таймера TrainMethodKnn, но входят в стоимость полного теста.

Ресурсный интервал — ровно каждый вызов `TrainMethodKnn(T1)` / `(T2)`; отдельно allocations текущего потока, wall, CPU и whole-process peak.
