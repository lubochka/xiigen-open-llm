Native direct chain: `TrainFromSource → ParseText → Extract(cached) → Train → _training`, затем `PredictFromNode → Extract(public uncached) → Predict`.

Consumer chain: `SemanticCompilerFacade.TrainStructuralKnn → per-file Extract(cached) → one batch Train`, затем на **том же** facade `Compile → PredictStructuralNextTokens → PredictFromNode → CompilationResult.PredictedNextTokens`. Это действительные writers/readers памяти, не проверка наличия файла. Consumer не получает выигрыша, если изменить только `TrainFromSource`: facade его не вызывает.

**Критический запрет:** не заменить цикл фасада на `foreach (source) predictor.TrainFromSource(source)`. `Train` очищает `_training`, поэтому такой перенос оставит только последний файл. Не добавлять переход последнего узла одного файла к первому узлу другого. Сохранить ограничение числа файлов `short.MaxValue`, k=5, stable сортировку соседей, majority/tie break и threshold10. Не менять `DistanceTo`, `%200`, `SyntacticRoleMapper`, default feature flags или другие kNN.

Кэш не хранится в поле predictor/facade, static/global dictionary, checkpoint или registry. После подготовки таблицы остаются только числовые `StructuralVector` и `NextToken`; ссылки на SyntaxNode и целые деревья не превращаются в обученную память. Сохранить поддержку независимых экземпляров; конкурентный Train одного predictor этим планом не вводится.

## 3. Математическое основание и приоритет

**Проверенное математическое обновление.** [Дополнение исходной карточки на858e984](https://github.com/lubochka/llm_mvp_core/blob/858e98452abdcbca43971bb00f749417ea659991/docs/plans/replanning-possible-diffs/experimets/cards/AST-SIB-CACHE-01.md#book-math-ast-sibling-cache) теперь связано с [§2.5 книги, PDF97–100](https://github.com/lubochka/xiigen-planning/blob/0c5c0b2b9222cf1d0b94d0b5ed62b7480570b351/llm%20mvp/math-theory/giansalvo-transformer-vol1/source/0093-0100-ch02-encoder-cost-and-matrix-structure.md#section-2-5). Из книги используется раздельный учёт стоимости стадий; следующая оценка для AST выведена по самому коду и не является теоремой книги о kNN. Это уточнение доказательной базы уже положительного AST01, не новый эксперимент или причина повторять его.

Пусть у родителя p есть dₚ детей, и в обучение попало mₚ этих детей. Старый алгоритм для каждого ребёнка снова строит список длины dₚ и ищет индекс. Работа sibling-части составляет O(Σ mₚdₚ); если участвуют все дети широкого родителя, его вклад O(dₚ²). Кэш один раз перечисляет dₚ детей и делает mₚ ожидаемо постоянных dictionary lookups: O(Σ dₚ + Σ mₚ). Словари удерживают O(Σ dₚ) элементов до конца обработки дерева. Это оценка **sibling-части**, не всего learner: разбор, обход предков/глубины и поиск ближайших соседей остаются прежними.

В суммах учитываются только родители, для которых mₚ>0; исключённый последний descendant не требует вычислять ещё не запрошенную группу. «Ожидаемо» относится к lookup хеш-таблицы, а не к обещанному времени C# обучения. Условия сохранения результата уже проверяются назначенными§5 assertions: неизменное дерево и node identity, прежний порядок/cap255, одинаковые полные learned rows, один batch Train фасада после всех файлов. Новые standalone benchmarks, fits или отдельный математический PASS не добавляются. Приоритет KHC→AST→N60 и доменная граница C# остаются прежними: положительные allocations подкреплены этим ограниченным выводом, но снижения числа уроков или роста semantic accuracy он не доказывает.

Для фиксированного immutable дерева список детей имеет прежний порядок. Для ребёнка с ordinal i обе реализации дают `PositionInParent=min(i,255)` и `SiblingCount=min(dₚ,255)`. У root — `(0,0)`; прежний отсутствующий-index fallback — position0. Все остальные координаты вычисляются прежним кодом. Следовательно, при тех же узлах и fileId равны vector rows, next-kind labels и порядок пар. При том же k, расстоянии и tie-break равны ответы на одинаковые queries. Это условное доказательство эквивалентности **подготовки учебной памяти**, а не доказательство общей точности модели.

`SiblingCount` сейчас не участвует в `DistanceTo`; `PositionInParent` участвует с весом0,3. Нельзя удалять count на этом основании: он входит в сохранённое свидетельство состояния, а такой redesign не проверен данным фактором. `%200` может объединять разные SyntaxKind; сохранность кодека не устраняет его коллизии.

Поэтому FIX-AST получает приоритет среди измеренных затрат обучения после FIX-KHC: есть положительные per-arm данные, приобретение ненулевых ответов и объяснение устранения повторной квадратичной работы. Это не основание вытеснить первые пункты реестра, сохраняющие optimizer/память и правильные учебные метки.

Граница применимости: Roslyn C# AST и те же extraction rules. Для переводов, POS-порядка, SQL/TypeScript, LoRA, tokenization и domain selector результат не измерен. На очень маленьком дереве стоимость словарей может перевесить экономию; адаптивный порог и другой cache layout сюда не добавляются без собственного положительного опыта.

### 5.2. Три assertions на готовых квитанциях

1. `NativeProfilesPreserveLearnedStateAndReportCost`: A/B каждого direct профиля имеют одинаковые11-field rows в прежнем порядке, SHA и16post outputs; отдельные before/after counts совпадают с§1. Scorer считает B−A для allocations/time/CPU, сообщает все ухудшения. Нет обязательного процента ускорения или требования роста accuracy. Любой измеренный полезный выигрыш признаётся **по своей оси/профилю**; если нового выигрыша нет, корректность может пройти, но новый resource success не заявляется.
2. `FacadeKeepsAllFilesAndLearnedReadout`: A/B содержат одинаковые9228 tuples и совпадающие28 outputs; первые16 имеют настоящий ненулевой AFTER при пустом BEFORE. Сравнить full tuple list с конкатенацией direct rows: narrow FileId0 + wide с **только** заменой metadata FileId0→2. Это ловит last-file-only, потерянный пустой слот, лишний cross-file successor и другой порядок. Копии tuples используются только scorer, не loader модели. Правильный результат должен содержать более одного предсказанного compact ID; constant-output не считается достаточным покрытием.
3. `LearnedVectorsKeepSiblingBoundarySemantics`: читать rows уже обученных direct профилей, включая wide позиции254/255/256 и count>255, и сравнить с зафиксированным uncached публичным oracle из того же source; cap255, соседские роли, FileId, прочие поля и порядок должны совпасть. Root `(0,0)` проверить отдельным extraction-only read публичного и нового internal overload вне Train, через test reflection с новым cache; это контракт **того же** writer§2. Две независимые parse-копии одного текста проверяются отдельно, без переиспользования cache между деревьями. Это0Train/0Predict и не отдельный «успех обучения».

Третий assertion не нуждается в переобучении: все необходимые реальные learned rows уже сохранены. Если внутреннего overload нет или его сигнатура другая, тест сообщает контрактный дефект, не создаёт аналог learner внутри Tests. Для составных полей expected берётся из сохранённого A и публичного неизменённого extraction, а не из изменённой cache-ветви B. Глобальное static хранение AST запрещено самим местом lifetime в§2 и проверяется code review; не вводить нестабильный GC/WeakReference timing-test.

Canonical row serialization совпадает с AST01 Program:11decimal fields в порядке `AstNodeType,Parent1Type,Parent2Type,Parent3Type,PositionInParent,SiblingCount,DepthInMethod,ScopeDepth,FileId,SyntacticRole,NextToken`, separator comma, LF, UTF-8 без BOM. Для exact direct inputs ожидаются digests§1; новый facade digest вычисляется из фиксированной конкатенации scorer§5, не объявляется историческим measurement. По окончании assertions `resources/comparison.json` объединяет **существующие** receipts без нового Train. Человеческий `report.md` — в корне attempt, на **русском**: основание → реальные before/after → per-profile B−A всех измеренных ресурсов → state/readout parity → facade path → регрессии/неизмеренное → actual counts → files/tests → ограниченный кандидат.

## 8. Ожидание, конфликты и прямой переход

Использовать фактическую default-модель сессии, без выбора другой модели или reasoning override. Перед tools прочитать их предоставленные schemas. Для `exec_command` с живым session_id — `write_stdin` с тем же ID; для `functions.exec`, вернувшего `Script running with cell ID`, — `functions.wait` с тем же cell. В другой среде использовать документированный wait исходного запуска. Ожидания порциями≤60секунд с содержательной progress-связью; не завершать ход словами «жду», пока работа жива. Не запускать polling-loop, второй waiter, дублирующий процесс или новый отчётный скрипт ради ожидания. Отсутствующий ещё файл не означает failed run.

При несовпадении current source с закреплённым baseline сначала определить конкретный diff в двух target methods; сохранить уже принятые независимые исправления одинаково в A/B, не откатывать их и не подменять native A source-copy. Если тот же cache уже внедрён, прочитать его receipt и выполнить только ещё назначенную проверку без повторного переноса/обучения. Противоречие, меняющее causal factor, фиксируется как конкретный blocker выбранного сравнения, без самостоятельного выбора другой карточки.

**STOP/NEXT действует непосредственно в этой карточке и промпте.** При STOP прекратить новые действия. При прямом назначении следующего ID немедленно перейти к нему: запрещено продолжать старую задачу, дописывать ей отчёт, чинить код/тесты, делать commit, cleanup или повторный запуск «перед переходом». Назвать только фактически подтверждённое состояние/живой handle, не придумывать завершение процесса. Старые эксперименты и результаты не удалять/не перезаписывать. Следующий ID читать из01; сейчас после FIX-AST идёт FIX-HNQ, но актуальное прямое указание пользователя имеет приоритет.

## 9. Связь с prompt → домен → реальный получатель

[План20](20-prompt-domain-e2e.md) уже задаёт learned selection, typed handoff, native recipient, отрицательные случаи и cold restart. AST01 не обучал outer selector. Его `SyntaxKind`, cached ordinal и C# marker не могут выбирать тему или подменять learned FlowRef.

При интеграции выбранных планов сохранить прежние три topic-профиля E2E и fixed budget:0новых queries/0новых fits ради FIX-AST. На тех же translation/orchestration/Wiki запросах trace/state изоляции должен показывать отсутствие StructuralKNN Train и отсутствующий structural recipient, если он не выбран существующим каталогом. Успех FIX-AST не даёт оснований автоматически добавить четвёртый C# handler или запускать его обучение из prompt dispatcher. Прямое native подтверждение writer→reader проводится§5 через настоящий facade.

Проверка cold restart существующих selector/recipients сохраняется по20. У StructuralKNN пока нет native persistence, поэтому его cold restore нельзя объявить пройденным по AST01 или переобучить незаметно при restart. Такой новый lifecycle требует отдельного обоснованного плана; локальный cache вообще не является состоянием обучения и не сохраняется. Это ограничение downstream-оптимизации, а не незавершённое проектирование уже описанного общего prompt→domain пути.
