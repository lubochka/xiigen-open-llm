## Q22. Как превратить исправление выданного перевода в урок

Осталась доставка в обычном потоке. Взять исходный запрос, реальный ответ переводчика и проверенное исправление из того же обращения. На границе [InternalFirstAiSupport](../../../../22.AgentAlgorithms/Pipeline/InternalFirstAiSupport.cs) связать эту тройку с вернувшей ответ единицей. Передать её существующему [TranslationCorrectionLearningAdapter.DeliverAsync](../../../../27.TranslationDomain/TranslationCorrectionLearningAdapter.cs). Адаптер вызывает `TrainStructuredBatchAsync`. Его отдельная приёмка записана в `2814c376bd0`. Нижний раздел R34-FB описывает первоначальное проектирование этого адаптера.

Взять подготовленное состояние на восьми уроках [P4201 и его вопросы e5/e7](../../../../experiments-v2/RP01-MICRO/P4201/Program.cs). Записать выданный ответ до исправления, доставить исправление обычным способом и прочитать ответ той же единицы. Для Анны ответ сохраняет «не открыла окно», для Бориса — «не открыл дверь». Указать, какая строка отправлена на обучение и что получилось при повторе. После доставки эти строки показывают усвоение исправлений. Варианты перевода оцениваются по смыслу. Исполнитель прекращает этот срез, когда видны обычный вызов, получатель и результат доставки.

Для следующего урока EN→RU у Kimi есть [одна строка со сменой области отрицания и поручение автору независимого вопроса](codex-158-learning-sets-transfer-coverage-2026-11-04.md#q22-data). Предложенный автором плохой ответ служит примером для разметки. В урок по фактической ошибке записывают то, что действительно выдала модель по этому запросу.

## Подлинность квитанции и одновременный повтор — уточнение 11 ноября 2026

Уточнение проектируемого исправления F09/B10, опубликованного выше по времени в этом файле. Новые receipt types сами по себе не доказывают происхождение. Выбранный механизм — **предлагаемый server-owned immutable каталог issued/verification records у существующего владельца TranslationMachine**. Обычный producer регистрирует фактически выданный answer и захваченные request/direction/topic/receiver/state; trusted verification producer регистрирует связанный результат. Caller передаёт opaque IDs; adapter получает canonical payload из каталога и сверяет его. Присланный caller typed record либо строка provenance не являются авторитетным свидетельством.

После lookup/authenticity и проверки canonical payload атомарно занять ключ ReceiptId+LessonId **до Train**. Владелец ключа хранит payload fingerprint и состояние IN_PROGRESS/COMMITTED. Одновременный идентичный запрос получает существующий task/IN_PROGRESS либо committed outcome, но не делает второй Train. Тот же ключ с иным payload отвергается. Простой lookup→Train→CAS не защищает физическую дозу: два запроса могут одновременно увидеть miss; CAS ограничит публикацию, но не уже выполненное обучение.

Committed duplicate возвращается до stale-проверки новой доставки. Только новый владелец выполняет captured state/version admission и существующий conditional Train/CAS. Исход и trained state публикуются совместно. После load учитывается только совместно сохранённый checkpoint; неизвестный исход аварии до durable save остаётся UNKNOWN_COMMIT_STATE, автоматический retrain запрещён. Этот протокол не обещает exactly-once через недоказанное crash окно.

К существующим source-echo, forged-third-text, чужим request/state/receiver и rejected=verified добавить simultaneous identical duplicate и conflicting-payload duplicate; наблюдать фактический Train counter, а не только один published state. Для одного принятого урока оба конкурирующих запроса дают суммарно одну дозу. Такая проверка использует одну из двух уже назначенных корректирующих доз бюджета 8+2: два adapter delivery по одной issued/verification receipt, одна corrective Train dose; дополнительных flow/verifier calls для второй доставки нет. Дополнительный scientific Train не скрывается под тестом идемпотентности. Искусственный counting trainer проверяет владение отдельно и не доказывает product acquisition.

Это исправление **плана и постановки**, не уже подключённые registry/claim APIs. [План §3.3](audits/2026-11-11/repair-plan.md), [независимый review](audits/2026-11-11/followup/final-review.md).

**После отказа.** Claim имеет явные terminal состояния REJECTED_BEFORE_TRAIN, FAILED_AFTER_TRAIN и UNKNOWN_COMMIT_STATE наряду с COMMITTED. Ошибка либо CAS conflict после затраченного Train не освобождает ключ как новый. Повтор того же ключа возвращает сохранённый исход без автоматической второй дозы; иной payload по тому же ключу по-прежнему запрещён. Инфраструктурный failure-after-Train контроль использует counting trainer calls=1 и real learner calls=0. Native Unit failure path, если он нужен, получает отдельную заранее объявленную дозу; это не скрытый одиннадцатый урок сверх 8+2. Новая попытка после разбора требует отдельной явно учтённой доставки, а не скрытого retry. Стойкость этой записи к crash до durable save остаётся вне заявленной гарантии.


**Restore authority.** Поскольку canonical lookup предшествует committed duplicate lookup, тот же согласованный checkpoint обязан переносить canonical issued/verification records, необходимые для всех committed keys, вместе с state/outcome/fingerprint. Import проверяет полные ссылки и payload до атомарной публикации. Эти records восстанавливаются из доверенного сохранения владельца; произвольный caller JSON не получает права заполнить authoritative registry. При отсутствии подтверждённой записи duplicate получает UNKNOWN_RECEIPT без Train, а не автоматическую новую доставку. Outstanding uncommitted receipt после load также не разрешает скрытый retry.

## Уточнение действующего договора — аудит 11 ноября 2026

Срез: `llm_mvp_core@009bf226174441fa0fbf0336e74ad2f2b7174d92`. Действующий `TranslationCorrectionLearningAdapter` уже существует; старые абзацы о «будущем файле» ниже описывают состояние 30 октября. Узкий принятый перенос R34-FB не снимается. Настоящее дополнение задаёт ремонт **происхождения фактически выданного ответа**, который не был доказан строковыми проверками.

### Почему сравнение со source недостаточно

`TranslationCorrectionLearningAdapter.BuildLesson`:160–186 требует непустой `ActualRejectedAnswer`, непустую строку `VerificationProvenance`, затем отвергает равенство rejected с verified и с SourceText. Первая проверка равенства по-прежнему нужна: одинаковые chosen/rejected не задают исправление. Вторая делает недоказанный вывод о происхождении: если реальный ответ системы был эхом исходного текста, корректный урок отвергается; если подставлен выдуманный текст, отличный от source и verified, одни эти проверки подмену не обнаружат.

Сейчас `DeliverAsync` передаёт допущенный урок в существующий `TrainStructuredBatchAsync` и проверяет доставку получателю. Это не автоматическое доказательство, что supplied rejected был получен от данного запроса и данного состояния. Не объявлять этот путь обучением DPO: текущий Executor учится на принятом ответе, а rejected служит контекстом/следом происхождения.

### Конкретный договор на границе вызова

Предлагаются **новые** записи `TranslationIssuedAnswerReceipt` и `TranslationVerificationReceipt`; это проектируемые типы, не найденный API. Первая связывает `ReceiptId`, `RequestId`, `SourceText`, `Direction`, `TopicDomain`, `ReceiverUnitId`, `StateId`, `ActualAnswer`. Вторая связывает `VerificationId`, `IssuedReceiptId`, `VerifiedCorrectAnswer`, `VerifiedAnswerConfidence` и ссылку на фактическую проверку. Хеш текста может проверять целостность, но не заменяет доверенного автора квитанции.

Выбранный владелец квитанции выдачи — `TranslationMachine.InlineTranslationOrchestrator.RunAsync`:2113–2175. Он один раз разрешает опубликованную версию:2127, получает ответ `flow.ExecuteAsync`:2149, добавляет версию к результату:2157–2165 и возвращает фактический `FinalHumanResult`:2171. Создавать квитанцию следует после `flowResult.IsSuccess`, **включая low-confidence/эхо**, из захваченного request/result/version, а не из произвольной строки caller. Требование verdict=Passed/TRANSLATED здесь неверно: `TranslationRoutingFlow`:84–126 возвращает Ok и для `TRANSLATION_LOW_CONFIDENCE`, а именно такой ответ может требовать коррекции. Разрешённое направление берётся из фактического flow, а receiver — из того же назначенного направления существующей единицы. `StateId` должен включать identity состояния, не только номер, который может повториться после импорта. Имеющийся `TranslationAtomicJsonWriter.CanonicalStateIdentity` — кандидат для вычисления при публикации/импорте, без повторного расчёта всего checkpoint на каждом чтении.

Предлагаемая передача: внутренняя typed-квитанция выдачи → проверяющая сторона с неизменённым actual → связанная квитанция проверки → адаптер. Lookup квитанции по непрозрачному ReceiptId проверяет её происхождение; возможность caller самому создать запись с любым actual запрещена. Журнал квитанций является служебным состоянием происхождения, не новой памятью переводов. `InternalFirstAiSupport` из исторического плана не объявляется уже подключённым producer или действующим callback обучения. Внешнюю проверку не вызывать без отдельного существующего разрешения и бюджета.

`BuildLesson` проверяет связь квитанций, точное совпадение запроса/направления/темы/получателя/версии состояния и rejected с сохранённым actual. Все отказы происходят до изменения обучаемого состояния. Затем используется существующий `TranslationLearningExample` и тот же `TrainStructuredBatchAsync`, без параллельной памяти исправлений. Истинное source-echo допускается только при подтверждённой квитанции; неподтверждённый source, подменённый другой ответ, чужой receiver или stale state отвергаются. Общая проверка rejected≠verified остаётся.

Producer и typed-handoff пока не реализованы; не заменять их `VerificationProvenance="verified"`. Текущий ручной адаптер можно характеризовать только в пределах его существующего входного договора. Порядок доставки проектируемого журнала обязателен:

1. Проверить подлинность квитанций и весь неизменённый payload.
2. Найти committed outcome по ReceiptId+LessonId. Точный повтор возвращает сохранённый исход без Train **даже после перехода current state к следующей версии**. Конфликт того же ключа с другим payload отвергается.
3. Только для новой доставки проверить captured StateId/version и выполнить условное обучение. Передать уже имеющийся `expectedStateVersion` в `TranslationMachine.TrainStructuredBatchAsync`:415–424 (сейчас adapter:274–276 его не передаёт). Дополнить проверкой StateId тот же read-once admission:446–458 до подготовки staged copy. Завершающий `TryPublishVersion`:219–239 и вызов:669 сохраняются как CAS-защита от изменения версии между проверкой и публикацией; автоматического retrain после конфликта нет.

Ключ, fingerprint payload и committed outcome должны входить в ту же атомарно публикуемую версию и тот же export/load checkpoint, что обученное состояние. Гарантия отсутствия второй дозы ограничена живым процессом и загрузкой **уже совместно сохранённого** state/outcome. Текущий `TryPublishVersion` — CAS в памяти; он не делает отдельный `SaveCheckpointAsync` долговечным commit. Окно аварии после CAS до сохранения остаётся `UNKNOWN_COMMIT_STATE`: автоматический повтор Train запрещён, требуется восстановление по принятому checkpoint и журналу попытки. Полная exactly-once гарантия через такой сбой требует отдельного durable commit/recovery протокола и здесь не заявляется. Stale новая доставка получает именованный отказ/требование повторной проверки до записи.

### Проверки и учебная граница

Использовать существующий `Tests/TranslationCorrectiveLearningTests.cs` и его текущие сценарии, дополнив независимым отрицательным контрактом. Названия ниже описывают предлагаемые проверки; они ещё не выполнены:

| Проверка | Ожидаемый результат и защита от ложного зелёного |
|---|---|
| Фактический ответ равен source, verified отличается, квитанции совпадают | Один допустимый урок принят; прежний отказ по одному равенству source должен быть различён |
| Фактический ответ иной, но caller подставил source | Отказ до Train; состояние и число принятых уроков не меняются |
| Caller подставил третий текст, не равный ни source, ни gold | Тот же отказ; неравенство строк не служит происхождением |
| Подменены request, направление, тема, receiver либо state | Именованный отказ по конкретной связи; нет записи в другую единицу |
| Actual равен verified | Исправление не создаётся, прежний guard сохранён |
| Повтор одной квитанции | Тот же исход без второго Train в живом процессе и после load совместного checkpoint; crash до save даёт UNKNOWN_COMMIT_STATE, без автоматического retrain |
| Положительные 8 retention + 2 исправления и fresh-load | Старое учебное наблюдение сохраняется, corrected rows честно считаются обученными, не held-out |

Структурные отрицательные проверки выполняются до Train и не добавляют учебную дозу. Для уже назначенного учебного сравнения сохранить 10 уроков (8+2), 60 flow calls, **8 вызовов проверяющего**, 2 save и 3 load; вложенные вызовы раскрыть. Это не число Fact-методов. Внешний teacher/DPO/SFT остаются 0. Если выбранный wiring требует дополнительного научного опыта, выделить его явно, без повторного использования старого результата как доказательства нового producer.

**Приёмка:** связанный обычный producer→verifier→adapter→receiver; independent expected/actual; отсутствие записи на отрицательном случае; прежнее удержание и restore; мутация связи actual/receipt действительно краснит свой тест; итоговый runner terminal принадлежит текущей сборке. До подключения producer и такого запуска исправление происхождения остаётся открытым. Настоящий аудит изменяет описание карточки, а не продуктовый адаптер.

Решение о repeat delivery следует из отдельного договора lesson ID, не из текстовой дедупликации. R34-CA сохраняет свою область экспериментального consumer и не получает продуктовый статус из исправления R34-FB.

## Порядок, исполнитель и предел завершения

Сначала восстановление и реальные открытые блокеры101/102, затем R34-FB и узкие исправления105. R34-CA становится продуктовой работой после указанного связывания consumer; не останавливать ради него разрешённые готовые исправления. Чужой общий router или новая библиотека данных для этого не назначены.

Для каждого будущего изменения перечитать применимые AGENTS/CLAUDE и навыки `architect-behavior-classifier-SKILL.md`, `planning-session-startup-SKILL.md`, `plan-review-SKILL.md`, `generated-code-review-SKILL.md`, `prompt-patch-authoring-SKILL.md`, `output-readability-gate-SKILL.md`, `human-communication-GLOSSARY.md` в `docs/skills`. Исполнитель сохраняет свою модель по умолчанию; эти планы не выбирают за него иной платный сервис. Отчёт на русском: до/после, полезный показатель и тема, все ухудшения, реальные уроки/вызовы, ресурсы, что осталось открытым, какие исходники изменены.

Любое измеренное улучшение полезного показателя считается успехом именно показателя и темы; рост точности для этого не обязателен. Для общего переноса применять правило пользователя: прежде >5% улучшения без >5% ухудшения остальных осей, кроме CPU; явная логическая целостность диагностики/сохранения/правильного ответа имеет отдельное основание. Меньший полезный эффект не терять. Неизмеренную ось не объявлять отсутствием регрессии.

**Обязательное поведение:** не продолжать предыдущую задачу после прямого указания перейти к следующему ID; не расширять бюджет ради красивого итога и не запускать новую программу при команде остановиться. При долгом разрешённом запуске сохранять process handle и ждать terminal outcome штатным блокирующим ожиданием, отрезками до60с для связи с пользователем. Не завершать раунд словами «жду», не объявлять процесс мёртвым из-за отсутствия файла и не создавать конкурирующие polling-процессы. Повтор после технического отказа — новая attempt-папка, прежняя сохранена. В текущем этапе запуск не разрешён этой карточкой: она описывает будущую приёмку.
