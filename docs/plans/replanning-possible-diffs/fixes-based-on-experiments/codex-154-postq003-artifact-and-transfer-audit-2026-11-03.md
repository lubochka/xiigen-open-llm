## 3. F154-02 — 19 путей адресуют текст merge-конфликта вместо checkpoint

Для каждого пути независимо собран текст из двух исходных LFS pointers: заголовок LFS, `<<<<<<< HEAD`, at187 OID/size, `=======`, original OID/size, `>>>>>>> e235f0971d6172f020822d42c61fe34a2819f9f8`, с LF и конечным LF. Его длина **289 байт**, SHA256 **точно равен опубликованному current LFS OID во всех19 случаях**. Это проверка content identity конкретных bytes, а не догадка по небольшому размеру.

Полный текст, paths, hashes и границы доказательства: [conflict-content-identity.json](../../../../experiments-v2/_audits/postq003-2026-11-03/codex-conflict-content-identity.json). Например P6801/A адресует `99eebd05c8efcef59377c289aa854dcbb608f90f46c3a1986cebca109c5cf5cf`,289; original —320620 bytes. Для выбранных P68/P69/P78 histories изменение связано с merge `7dfaeab72ca40e3045a11449167c2a5cceddd51a`; для P68 отдельно прочитаны оба parent pointers. Первое появление каждого из19 paths всей историей коммитов здесь не аттестовано.

**Предел:** backing objects с LFS server в этой сессии не скачивались; их доступность и native Load не проверены. Подтверждено, что current pointers задают content identity конфликтного текста. Обычный поиск `<<<<<<<` по отслеживаемому Git-файлу может пройти: снаружи лежит корректный LFS pointer, конфликт находится в адресуемом содержимом.

**Условие ремонта:** для19 путей восстановить точные original payload, проверить настоящий тип/структуру и EOF, source→staged pointer→опубликованный pointer→fresh materialized readback. Отрицательный контроль использует корректный внешний LFS pointer, адресующий конфликтный текст; он должен отказать до публикации обученного состояния. Известная потеря bytes и конфликт — разные причины, не одна универсальная текстовая замена.
