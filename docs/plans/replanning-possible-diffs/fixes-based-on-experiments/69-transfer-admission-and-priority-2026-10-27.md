## 1. Как применять критерий

Успех исследования и допуск переноса — разные поля. Любое измеренное полезное улучшение сохраняется как успех именно этого показателя и профиля, даже если другой показатель ухудшился. Но готовность переносить механизм определяется всей панелью ниже.

| Класс | Условие | Следующее действие |
|---|---|---|
| P1-L · логическая ошибка | Есть точный путь ошибки диагностики/сохранения/восстановления и независимый ожидаемый результат | Адресный ремонт и проверка контрпримера; нельзя под этим названием менять весь обучающий алгоритм |
| P1-M · крупный измеренный выигрыш | Хотя бы один полезный показатель улучшен строго больше5%; прочие проверенные показатели не ухудшены больше5% | План переноса только проверенного профиля, с исходными контролями и ресурсным receipt |
| P2-M · малый измеренный выигрыш | Положительный выигрыш не превышает5%; нет существенной встречной регрессии | Сохранить кандидат; приоритет точности, времени обучения, памяти, диска, загрузки/записи |
| CONDITIONAL · доказательств недостаточно | Полезный сдвиг есть, но необходимый контроль или ресурс не измерен / oracle ненадёжен | Подготовленный план допустим; утверждение «все критерии переноса выполнены» недопустимо. Закрыть конкретный пробел, не повторять всю кампанию |
| HOLD · встречная регрессия | Измерено ухудшение больше5% вне исключения CPU | Не включать общий default. Сохранить успех и ограничение, не переименовывать отрицательный контроль и не удалять строку |

Расчёт по умолчанию — относительная величина: для «больше лучше» `gain=(B−A)/abs(A)`, для «меньше лучше» `gain=(A−B)/abs(A)`. Ухудшение считается с противоположным знаком. Для accuracy/F1 дополнительно показать исходные counts/denominators и разницу в процентных пунктах. Строго5% не является «более5%». Это явная расчётная конвенция плана, а не утверждение, что пользователь отдельно назначила относительный способ для каждого показателя.

При A=0 относительная величина не определена: показывать 0→N, знаменатель, абсолютный прирост/п.п.; не писать бесконечные проценты и не обходить контроль0→0. Для signed margin с нулём/сменой знака сравнивать исходные значения и смысл метрики, а не автоматически ранжировать её по проценту. Статистическую значимость из порога5% не выводить; число seed/пар и неопределённость остаются рядом.

**Исключение CPU узкое.** Даже большой рост CPU-time не исключает кандидат. Он не оправдывает рост RAM, allocations, checkpoint/disk bytes, падение accuracy или ухудшение времени load/save. Wall time при конкурирующей нагрузке не выдаётся за CPU-time. Если сравнение времени обучения смешивает CPU и ожидание/IO, сохранить оба показателя и причину; не придумывать CPU-долю.

Неизмеренный показатель — `NOT_MEASURED`, не нулевая регрессия. Нельзя объявлять отсутствие любых ухудшений по одному accuracy или общему счётчику процесса. Требуемые метрики определяются изменяемым механизмом: для конструктора/восстановления особенно важны фактический выбор, изоляция, RAM/allocations, размер сохранённого состояния и load/save. Новые ограничения не требуют бессмысленно измерять все существующие метрики проекта для каждого локального изменения.

## 4. Порядок подготовки и тесты

1. Сохранить первыми учебные блокеры U1/U2[68](68-transfer-repair-followup-plan-2026-10-27.md). Исправление неверного oracle не отменяет положительное основание уже внесённого механизма.
2. Уточнить диагностические receipts U7/U8 и KDP/KDR. Для unit-проверки уже завершённого опыта не повторять Train; такой unit не называется новым учебным экспериментом. Каждая новая экспериментальная программа по-прежнему содержит реальный учебный участок по[36](../experimets/36-diagnostic-learning-programmes.md).
3. Дальше FIX-KDP, затем E2E-KDR по74 с настоящим prompt→learned route→checkpoint+principles→domain answer→update→fresh restore. Полезный профиль не распространять на непрошедшие RU/HE route или нейтральные C#/EN функции.
4. Перед следующим переносом старого ID применить этот критерий к его сохранённому receipt. Общий исторический порядок в реестре не является доказательством допуска каждой строки по новым порогам. Например MC21 содержит рост peak и ухудшениеD4, KS содержит allocations1112→2136B: их нельзя автоматически назвать безопасными из-за роста accuracy. Проверить область измерения и относительную регрессию; не скрывать её исключением CPU.

Тест допуска должен отдельно проверять: ровно5%/чуть больше5%; отсутствие знаменателя; отсутствие ресурса; CPU-only рост; рост disk/RAM при улучшении accuracy; новая ошибка отдельной строки при неизменном aggregate; `attempted` против `completed`; task-correct против answer-correct; TopProfile против CanSelect. Использовать копии уже полученных receipts, не дополнительные Forward ради проверки арифметики.

Математика поддерживает выбор механизма (например корректный denominator, разложение рейтинга, строгая связь update count и stage), но не отменяет измеренную регрессию. «Нет статистически значимого ухудшения» и «не измеряли ухудшение» — разные утверждения. Для маленьких панелей рядом с процентами всегда counts.
