## 3. M02 — неправильный тест байтов может лишить генератор русского текста

В новом [AnswerReadingRejectsIncompleteCharacterIdentifiersTests](https://github.com/lubochka/llm_mvp_core/blob/3cd2f26ced57da3acc4cd8a860c716a6bdac8a1e/Tests/ExperimentFixes/AnswerReadingRejectsIncompleteCharacterIdentifiersTests.cs#L144-L217) каждый token ID обязан отдельно пройти `Encode(Decode([id])) == [id]`. Это требование передаётся общему sampler, которому неизвестны tokenizer, уже выбранный префикс и оставшаяся длина ответа.

Однако [BpeTokenizer](https://github.com/lubochka/llm_mvp_core/blob/3cd2f26ced57da3acc4cd8a860c716a6bdac8a1e/01.Tokenizer/BpeTokenizer.cs#L235-L253) декодирует объединение байтов всех токенов. Для базового словаря256:

| Корректный ответ | Байты-токены | Каждый отдельный ID проходит round-trip? | Весь ответ корректен? |
|---|---|---|---|
| ж |208,182|нет|да|
| é |195,169|нет|да|
| 🙂 |240,159,153,130|нет|да|

Все эти контрпримеры исполнены в Python как проверка кодека и точной заявленной формулы. Это не запуск C# генератора. Одиночный фильтр оставляет128 ASCII bytes:182 незаконен в начале символа, но необходим после208.

**Выбранный ремонт:** развить уже существующий118/A101-R2 и124/S14. Корректность принадлежит последовательности и её состоянию в `TextGenerator.GenerateCore`. Допуск учитывает bytes конкретного tokenizer, текущий префикс, EOS и конец бюджета; неизвестный ID и незаконный префикс отклоняются. Чистый числовой sampler не получает глобального запрета ID≥128. Однотокенный случай проверяется через generator с `maxNewTokens=1`.

Положительные проверки — кириллица, двух-/трёх-/четырёхбайтные символы и BPE merges; отрицательные — чужой ID, continuation в начале, неполный последний символ, отсутствие допустимого кандидата. Ресурсный договор запрещает скрытые дополнительные Forward и Draw. Подробный совместимый API и порядок фильтрации — в M02 плана127.

Это ошибка **нового договора приёмки**. В проверенном текущем продукте такого ASCII-фильтра ещё нет.

## 4. M03 — PAIR-тест закрепляет несогласованную миграцию и ложное чтение после загрузки

[Новые тесты](https://github.com/lubochka/llm_mvp_core/blob/3cd2f26ced57da3acc4cd8a860c716a6bdac8a1e/Tests/ExperimentFixes/TranslationPairTailSignatureLearningTests.cs#L29-L43) требуют убрать PAIR только при чтении и оставить его в хранимом `TokenizerSignature`. Это расходится с124/S04: provenance пары хранится отдельно, semantic key имеет одну согласованную версию у writer, tokenizer, executor, verifier и loader. Иначе `_requiredTermsBySignature` остаётся записанной под одним ключом, а `Verify` ищет другой; обязательные слова могут перестать проверяться.

Ещё одна независимая ошибка — [SavedLesson…AfterImport](https://github.com/lubochka/llm_mvp_core/blob/3cd2f26ced57da3acc4cd8a860c716a6bdac8a1e/Tests/ExperimentFixes/TranslationPairTailSignatureLearningTests.cs#L253-L283). Тест импортирует target и проверяет re-export, но затем создаёт третий `SemanticTokenizerUnit`, снова обучает его и читает именно его. Такой результат не подтверждает использование загруженного состояния target.

**Выбранный ремонт:** согласовать тестовые ожидания с единой версией S04. После импорта запрос проходит через `target.GetOrchestratorAsync()` и его `RunAsync(LogicalOrchestratorRequest)`, без нового Train. Наблюдаются настоящий `FinalHumanResult`, `OverallVerdict` и метрики `adapter_id`/`confidence`; runtime Signature в этом API не выдумывается. Пример должен действительно зависеть от загруженной карты, не завершаться ранним exact/phrase ответом. Сохранный re-export вместе с намеренно выключенным reader обязан дать провал behavioral проверки.

PAIR не должен менять смысловой допуск; RULE после PAIR сохраняются. Коллизия canonical keys с разными payload отклоняется до публикации памяти. Неверный перевод без обязательного термина отвергается обычным verifier и после миграции.

## 6. M05 — P66: точность результата сохраняется, наблюдатель и общий расход требуют ремонта

[Независимый пересчёт](../../../../experiments-v2/_audits/2026-11-02-postmerge-audit/experiment-review.md) сохранил главный вывод: исключение похожих строк скрывает отрицательные смысловые контрасты. Видимые отрицания A0/2→B2/2; точность общего экзамена у обоих0/2, диагностической панели B0/4. Все ответы2/6 правильны только на точных дубликатах уроков. Это улучшение диагностической видимости, не качества перевода.

**Выбор источника не равен посещению ветки.** `Program.cs:841–855` назначает `KNN_NOT_REACHED`, если финальный adapter ID не содержит `-knn`. Но `TranslationTrainedUnits.cs:288–303,349–389` допускает выполненный поиск с последующим отказом кандидатов и fallback. Из шести исторических ответов достоверно известно, что KNN не выбран. Был ли он вызван на каждой строке, без соответствующей трассы не измерено.

**Расход.** `pairSimilarityEvaluations=12` правильно считает admissions:6 строк×2 урока. Затем исходник делает24 вызова той же функции для решётки,2 для ручного оракула и1 для границы. Итого39 прямых вызовов хозяина;12 и1 записаны отдельными полями,26 контрольных обращений не выделены в общей ведомости. Это source-derived count, не инструментированный runtime замер и не весь вложенный расход модели/Flow. Обвинение в дополнительном незаконном обучении из него не следует.

**Время.** Карточка назначает600 секунд сборке,1200 исполнению,1800 всей попытке. Запускатель использует неограниченное ожидание build и `Start-Process -Wait`, не реализуя эти пределы. Исторический запуск162 секунд +1,79 секунды уложился. Неисправен будущий путь зависания, а не задним числом этот результат.

Ремонт M05 разделяет attempted/eligible/selected/final source, вводит счёт у самого callable с категориями admissions/grid/oracle/edge и исполняемый общий deadline. Нужны controls «поиск вызван, все кандидаты отвергнуты», «один дополнительный вызов увеличил ledger», «зависший дочерний процесс завершён с timeout, результаты сохранены, новый Train не начат».
