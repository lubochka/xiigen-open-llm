## Добавочная приёмка DYN-RU — точный бюджет после уточнения30.10

Это новая **не выполненная** проверка композиции, а не ещё один алгоритм ранжирования. Использовать RU/S01–S04 и E01–E08 из [общей fixture](../experimets/cards/KNN-DOMAIN-PRINCIPLES-01-fixtures.md), строки71–74/79–86. Первичные [RU-уроки](../../../../experiments-v2/RP01-MICRO/KDP01/results/attempt-01/shared/v1/RU/S0/examples.jsonl) и соседние `model.bin`, `tokenizer.json` в той же S0-папке существуют; это адрес подготовленного состояния, не доказательство product Capture с каталогом. Проверенные исторические RU числа: retention4/4; пустое ранжирование5/8, `ru.time-frame/v1`8/8, исправлены E02/E07/E08 без потерь.

A статически составляет каталог `ru.time-frame/v1`; B динамически получает **те же** functions/IDs/versions/weights/Evaluate/порядок и создаёт тот же `KnnCandidatePrincipleCatalog`. На каждом плече настоящий `TransformerEmbeddingKnnLogicalUnit<string>.Train` с четырьмя уроками на одинаковых квалифицированных frozen model/tokenizer. Затем4 retention+8 EXAM чтений. В **обоих** плечах обязательны4/4 и8/8; одинаковые ошибки не достаточны. Нельзя подменять обучение B созданием `WithCandidatePrinciples` или выбирать иной checkpoint/teacher.

Добавка: **2 успешных Train,8 предъявлений прежних уроков,24 ExecuteAsync,0 новых уникальных уроков,0 DPO/SFT/neural updates**. Она добавляется к основной программе, а не прячется внутри её исходного бюджета. Общий потолок при совместном исполнении: **15 успешных Train /113 предъявлений /≤984 чтения**; прежние5 empty-Train отказов учитываются отдельно, то есть всего≤20 вызовов Train. Старые no-op/unknown/foreign/reversed контроли остаются в исходной программе; новых fits для них эта добавка не разрешает. Путь результатов — новая свободная attempt-папка runner этого плана с отдельным разделом DYN-RU; прежние результаты не перезаписываются. НомерQ не создаётся: это приёмка существующего FIX-KDP.

Сравнить отдельно catalog/setup, native Train, их суммарное время до готовности обученной единицы и inference. Исторические KDP/KDR содержат whole-run timing, **не сопоставимый native Train A/B**; не выдавать их за допуск скорости динамического варианта. Одна малая пара может остаться неточной из-за JIT/порядка/шума: тогда качество сохраняется как установленный результат, скорость — CONDITIONAL, без автоматических повторов и без обещания ускорения. Расширение на другие профили или повторные fits требует заранее назначенного бюджета. Новое условие пользователя не позволяет ссылкой на CPU exception скрыть ухудшение обучения этой композиционной ветки.

**Неактивный callback не обязательно нейтрален:** текущий `KnnCandidatePrinciples.cs::Rank`, строка355, использует `var share = catalog.Count == 0 ? 0.0 : 1.0 / catalog.Count;`. Добавление даже неактивной функции уменьшает долю остальных; суммарная поправка ограничена±0.20. Это установленная семантика, не новый доказанный дефект и не результат эксперимента. Поэтому динамическая пара сохраняет состав/количество функций; добавление no-op — отдельное изменение политики, а не допустимая скрытая «чистка». Полный configured restore остаётся открытым: `TeachingRegistryPersistence.Capture` явно отказывает каталогу, и DYN-RU не объявляет эту границу закрытой.

**Новое условие пользователя30.10 — динамическая композиция:** разрешены динамический массив функций, исправления ошибок и упрощение динамического кода при отсутствии ухудшения качества и скорости обучения. Для переноса, основанного именно на такой композиции/упрощении без отдельного измеренного выигрыша, это самостоятельная ветка допуска. Она не требует выдумать рост accuracy, но требует сопоставить настоящие native Train и качество на той же учебной программе. Общее исключение для CPU не заменяет это условие о скорости обучения. Setup/catalog construction, обучение и inference измеряются отдельно; нулевой Train при `WithCandidatePrinciples` не означает бесконечную скорость обучения.

**Действующий API вместо второго интерфейса:** `18.CapabilityTraining/KnnCandidatePrinciples.cs` уже содержит негeneric `IKnnCandidatePrinciple` (`Descriptor`, `Evaluate(KnnPrincipleQuery,KnnPrincipleCandidate):KnnPrincipleScore`) и `KnnCandidatePrincipleCatalog.Create(string profile,IReadOnlyList<IKnnCandidatePrinciple>)`. `18.CapabilityTraining/LlmIngredientLogicalUnits.cs` уже принимает `KnnCandidatePrincipleCatalog? candidatePrinciples=null` в Train и имеет `WithCandidatePrinciples(catalog)` — view на той же обученной модели/tokenizer/index/examples, без повторного Train. Динамически полученный массив направлять через этот каталог. У `21.AgentInfrastructure/Logical/KnnLogicalUnit.cs` другой контракт, textSelector/answerSnapshot; создавать в нём параллельный ranker ради названия «массив» не требуется.

Для будущей приёмки использовать существующие KDP01/KDR01 fixture; бюджет динамической пары указан отдельно в DYN-RU выше и не меняет задним числом исходные расходы основной программы. Проверить actual answer по каждой строке, чтение выученного состояния и новый урок только выбранному получателю. Не заменять одинаковый native Train в двух плечах сравнением Train(A) с созданием view(B). При недостаточной сопоставимости качества либо времени допуск остаётся условным; дополнительные повторы требуют отдельного заранее назначенного бюджета. Исторические числа не являются измерением новой динамической компоновки.

**Адресное усиление30.10:** [104–106](104-late-learning-evidence-audit-2026-10-30.md) не создают второго общего конструктора. В E2E этого owner развести выбор домена/модели и контекст внутри выбранной модели: тема finance/river у переводчика не обязана становиться отдельным доменом. ## Действующее уточнение после P102 — Тема обучения и общий механизм не задают один глобальный tiebreak

**Проверка `POST102-FIX-KNN-DOMAIN`. WRONG.** Новый MethodKnn tie fix можно внедрить в любой доменный retrieval, а название класса доказывает тему обучения.

**CORRECT.** Домен — предметная тема, task/language/profile и механизм указаны отдельно. Constructor state и native обученные readouts этой карточки проверяются своим call path; MethodKnn voting, D08 predicates и keyword classifier имеют разные contracts.

**Адресная приёмка.** Удержать разные темы и реального recipient через native constructor/train/execute. Q127 позиционный factor не переименовывается в исправление этого transfer. Общий helper допустим лишь при доказанном одинаковом contract; проверить actual consumer и отсутствие swallowed failures, не только созданный объект.

Применять [единый контекст40](../experimets/40-effective-executor-context-2026-11-02.md) и [адресный план121](121-post102-addressed-repair-plan-2026-11-02.md): актуальные роли навыков, один рабочий оценщик, ordinary consumer и реакция на test/report failure. Это ограничивает вывод и усиливает приёмку; исходные factor, доза, fixed panel и порядок сохраняются. Исправление saved evidence не является новой PRIMARY, а наличие этого блока не разрешает запуск. Исторические указания ниже действуют только в своей исходной области; при противоречии бюджета/фактора требуется адресное решение до исполнения.

```text
final_i  = native_i + .20*(1/m)*Σ(a_ij*w_j*clip(s_ij,-1,1))
a_ij = 0 при Applicable=false, иначе1; веса остальных не перенормируются.
```

В измеренных каталогах все w_j=1. Поэтому добавка каждому кандидату принадлежит[-.20,.20], разность добавок двух кандидатов≤.40. Если native gap строго>.40, этот профиль не может перевернуть пару. Это локальное доказательство ограничения, не эмпирическая гарантия качества. При native gap≤.40 функция всё равно может выбрать неверного: CS E07/E08 имеют gaps≈.3957/.3925, но синтаксические признаки предпочитают неверный candidate. Для RU/HE/OR полезные gaps значительно меньше; математика объясняет возможность, а сами fixed rows доказывают наблюдённый эффект.

Измеренный контракт должен сохранять weights=1 и catalog versions. Экспериментальный constructor:109 проверяет NaN/negative, но допускает positive Infinity и произвольные большие веса; при них bound.20/.40 неверен. Будущий product API для этого профиля принимает только finite веса назначенной схемы, finite scores, уникальные IDs, известные версии и matching profile/scope. Обобщённая система произвольных weights — отдельная постановка, а не этот перенос. Метки Applicable=false, score0 и successful check различаются.

Ответ остаётся Output выбранного сохранённого примера; функции не добавляют candidates и не пишут ответ. Query/gold/exam ID не поступают callback как оракул. Frequency имеет право читать только счётчики обучающего состояния, не exam answers. Для default пустой массив не пересчитывает confidence; raw scores для router не заменяются округлённой confidence.

Router: profile score=max native candidate score среди примеров этого профиля; второй score берётся из **другого** профиля. Допуск — top≠CLARIFY AND top≥.35 AND gap≥.05, с отдельным whitelist разрешённой binding. Tie-break — deterministic ExampleId. Order invariance функций проверяется на outputs/scores, а не на длине списка; canonical descriptor order закрепляется для float summation.

## 7. Метрики принятия и порядок работ

Каждый кандидат сравнивается со своей baseline на одинаковом корпусе, train state, graph и route decisions. Качество: overall task outcome, actual-answer correctness, admitted coverage, conditional correctness, lawful refusals, acquired lessons, retained answers, cross-profile writes, restore equality; missing≠0. Для ресурсов: per-arm wall latency p50/p95, allocations и peak memory при одинаковом числе полезных calls, serialized state bytes; отдельно CPU и фактические embedding/Forward counts. Whole-run KDP/KDR timings для этого не подходят.

Приоритет1 по пользе: хотя бы одна назначенная метрика улучшается строго>5%, остальные измеренные метрики не ухудшаются>5%; даже значительный рост CPU сам по себе не исключает перенос. Ровно5% и полезное≤5% — приоритет2 при тех же ограничениях. Для нулевого baseline относительный процент не вычисляется: показать абсолютную дельту и denom. Восстановление/полномочия/верный answer являются также жёсткими контрактами: новая неправильная строка, запись в чужой профиль или restore mismatch не маскируются средним улучшением. Для tiny панели одной ошибки достаточно, чтобы это было явно видно.

Порядок будущих slices:

1. Исправить qualification/restore/accounting oracle и добавить доказательные counterexamples из §5. Исторические reports не переписывать как заново выполненные; новый corrected result хранить отдельно.
2. Добавить opt-in native ranker API и пустую совместимую ветвь; прямые RU/OR tests, HE с незакрытой квалификацией отдельно. Нейтральные функции не продвигать.
3. Добавить immutable binding/manifest/index restore и native selected-profile writer; positive/negative state tests.
4. Подключить learned router и registry к разрешённой ProductHost композиции, выполнить experiment-based и E2E portions одного bounded cycle.
5. Сопоставить per-profile quality/resources с порогами. До сравнительных данных ресурсы остаются NOT_MEASURED и полного TRANSFER_QUALIFIED нет. Результат и ухудшения записать в общий реестр родителем.

Назначение документа — **план недостающего переноса и ремонта доказательств**. Он не означает, что код внедрён, что все пять профилей работают, что свойства saved state доказаны побайтово, или что текущие tests зелёные. Измеренные RU/HE/OR улучшения сохраняются с точными границами; математика объясняет их механизм и не заменяет отсутствующие product/resource evidence.
