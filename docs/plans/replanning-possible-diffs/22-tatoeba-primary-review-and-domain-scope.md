## Как оценщик может принять потерю смысла

[TatoebaPilotLoopRunner.cs](../../../27.TranslationDomain/TatoebaPilotLoopRunner.cs):1439–1461 выставляет ProductMatch при подходящем алфавите, отсутствии bootstrap/source-copy/лишнего отрицания и exact match либо similarity ≥0.50. Similarity, 1481–1488, — доля различных содержательных слов эталона, найденных в ответе. Это одностороннее совпадение, не полнота передачи смысла и не точность всех слов ответа.

WordRegex, 113, берёт буквы, поэтому число не входит в это сравнение. StopWords, 115–134, включают `not`, `не`; `HasExtraNegationJunk`, 1491–1495, отклоняет увеличение числа отрицаний, но не уменьшение. Из формулы следуют допустимые контрпримеры: потерянное отрицание; подмена одного из четырёх содержательных слов; сохранённое слово «доступ» при «разрешён» вместо «запрещён». Это логические примеры по коду, не результаты новых вызовов.

У метода есть действующий внутренний consumer: 704–738 получает реальный ответ orchestrator, считает RuntimeProductAccuracy и использует его в PassesTarget; 403–424 обновляет best observed accuracy и выбирает дальнейшую ветку. Значит, это не только неиспользуемая вспомогательная формула. Однако targeted `git grep TatoebaPilotLoopRunner.RunAsync` нашёл tracked вызовы в Tests, а среди остальных tracked файлов без Markdown/JSON/TXT точного вызова не найдено. Внешний launcher или исторический запуск этим не исключён. Привязки к нынешнему RP01 Student runner здесь нет.

### Доменное ограничение алфавита

В 1498–1507 для `ru` требуется кириллица без латиницы, для любого другого языка — латиница без кириллицы. В 1531–1538 направление EN_HE явно возвращает `he`. Поэтому правильный ответ только еврейскими буквами не удовлетворяет проверке. Смешанный корректный перевод с именем/кодом тоже может не пройти жёсткое правило для русского. Частота таких случаев и фактический EN_HE вызов не измерены. Предметно правильный перевод и алфавитная чистота требуют разных критериев.

## Какая часть словаря действительно обучается

В 1162–1247 алгоритм для каждой пары предложений перебирает все source words × все target words, считает совместную встречаемость, confidence и specificity, затем выбирает лучший target. Есть фильтры minimum support, .60 confidence, .45 specificity и .15 margin с дополнительным условием support. Это содержательные ограничения шума; нельзя утверждать, что любое совпадение автоматически принимается. Но они не устанавливают смысловое соответствие конкретных слов.

В 1249–1328 фразы тоже выбираются по общим строкам корпуса, coverage/specificity и близости длины. Фразовый путь **не содержит того же runner-up margin rejection**, что словарный: после фильтров выбирается первый кандидат; равные scores разрешаются support, длиной и алфавитным порядком. Поэтому неопределённость словарной и фразовой индукции нельзя считать одинаково обработанной.

Связь с обучением прослежена: 747–768 формирует эти maps, `ToTrainReadyPair` 1127–1159 помещает их в аннотации `[AGREEMENT]`/`[PHRASE]`, builder создаёт Unit examples, затем вызывается `TrainStructuredBatchAsync`. Это прямой путь переноса статистического предположения в обучаемую память. Ошибочных maps реального корпуса здесь не подсчитано.

### Дополнительная условная граница: один ключ без направления

`InduceLexicon` возвращает `Dictionary<string,string>` с ключом source word. Ключи частот и кандидатов в 1164–1195 не содержат source/target language; направление используется только для извлечения ContentWords. `InducePhraseMappings` также группирует по source phrase, без направления. `ToTrainReadyPair` применяет общие maps по наличию слова/фразы, не по языку target.

Если входная совокупность содержит, например, один английский source для разных target languages, эти статистики могут конкурировать в одной записи. Если корпус строго однонаправленный, этот риск не активен. Мы не установили, что сохранённый действительный pilot смешивал направления. Это новое уточнение области применимости, а не утверждение о произошедшей порче checkpoint. Fresh runner в 150,273–277 берёт первые TrainSetSize строк общей коллекции и передаёт их вместе; явного разбиения по направлению в этом вызове нет.

## Восстановление: реальный условный риск и уже имеющаяся защита

[TranslationCheckpointCache.cs](../../../27.TranslationDomain/TranslationCheckpointCache.cs):16–50 адресует объект по path/schema/mtime/length. При внешней замене байтов с сохранением размера и времени возможен прежний cache hit. Это особое условие; не свидетельство обычной неверной загрузки.

Runner 184–210 действительно возвращает cached Machine; 642–668 после успешного save вызывает Invalidate и Store. Штатное сохранение не забывает обновить cache. При этом Store хранит ссылку на живой Machine, а loop state — отдельное сохранённое описание. Доказательство расхождения после незавершённого изменения потребовало бы конкретного caller/сбоя; такой runtime receipt здесь отсутствует. Не переносить этот cache на DPO checkpoint owner с другим контрактом.

## Различающие будущие проверки, без исполнения

1. Для scorer: небольшой заранее размеченный набор полных и испорченных переводов; настоящий BuildRowResult сравнивается с отдельной предметной оценкой. Сначала это проверяет соответствие формулы, не улучшение обучения. Чтобы проверить влияние на loop, потом отдельный matched контраст меняет только gate, сохраняя поток пар, порядок и consumer; отслеживаются выбранные уроки и правильность на неизменном независимом наборе.
2. Для lexicon: одно направление, те же предложения; сравнение сохранённых associations с заранее заданным alignment. Затем выключить только индуцированные word maps, оставляя phrases/exact/KNN постоянными. Отдельно исследовать phrase tie, не менять оба механизма одновременно.
3. Для language scope: те же lawful источники в EN→RU и EN→HE, сравнить раздельную и объединённую индукцию при фиксированной оценке каждого направления. Само наличие неверной общей записи не равно ухудшению: exact/phrase пути могут её скрыть; нужен наблюдаемый использованный map и итоговый ответ.
4. Cache имеет меньший приоритет: воспроизведение специально созданного same-stamp replacement не объясняет реальный RP01 без свидетельства такого writer. Сначала искать существующий receipt/действительный вызов, а не запускать ещё одно обучение.

Helper proxy percentages относятся к намеренно подобранным синтетическим случаям, не к доле ошибок проекта и не к нашему эксперименту. Причинное влияние на качество каждого домена остаётся будущей экспериментальной проверкой. Никаких новых runtime запусков этим документом не совершено и не разрешено.
