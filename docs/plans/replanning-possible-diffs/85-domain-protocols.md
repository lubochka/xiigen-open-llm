## Обязательные правила для карточки и любого её промпта

**Найти tool и дождаться своей операции — обязанность исполнителя.** До выдачи команды прочитать [контракт31](experimets/31-tool-discovery-and-wait.md) и указанные там реальные skills/references; по каталогу текущей среды найти launch и wait/resume/status, прочитать их схему и сохранить provider, handle, start time, H/R и deadline. Не выдумывать Kiro API по Codex-примеру, не просить пользователя выбирать инструмент или запускать команду вместо исполнителя.

**Ожидание не равно бесполезному polling.** Одна выдача entry; затем штатный bounded wait/resume того же session/cell/process ID до terminal exit или исходного experiment deadline. Нормальный wait можно повторять при silent/running. Два быстрых неблокирующих чтения без прогресса требуют перейти в wait; если он неисправен/ответы противоречат — независимое чтение H/R/claim/exit и своего PID+start. Не вводить Start-Sleep в занятый терминал. Предел одного ожидания≤60с — не предел эксперимента; yield/RPC timeout не доказывает exit/kill/нулевой расход. После диагностики живой процесс продолжают ждать. Отсутствие log не доказывает, что запуска не было. Не выдавать entry заново «синхронно на25минут», не подбирать results-NN, не удалять claim/partial, не сокращать TRAIN/steps до двух минут ради tool. При UNKNOWN сохранять неизвестный расход и разбирать существующий запуск. STOP/NEXT Любы немедленны.

**Без действительного обучения задача не выполнена.** До исполнения в рецепте должны быть точные original файл/метод, learner→изменённое состояние→consumer, TRAIN/EXAM, назначенный before и конечный бюджет достаточного учебного набора. Для retention/restore требовать показанный навык до вмешательства; для acquisition допустим cold start с проверкой приобретённого поведения. Updates, loss, hash и случайный верный токен сами по себе не доказывают навык; частичное token learning не объявлять целым ответом/правилом. Unit/BPE обязаны действительно обучать память/правила и читать полученное состояние. Restore/consumer допускает доказанно обученный артефакт без повторного обучения ради счётчика.

**0 → 0, отсутствие обучения или неполное A/B — не завершение эксперимента.** Раздельно записать execution_status, learning_validity и hypothesis_status; при невалидности учебная цель OPEN. Сохранить сырые свидетельства и продолжить разрешённое исправление постановки, а не только написать «невалидно» и отчитаться об успехе. Не искать другой checkpoint/модель/host, не менять seed/фактор, не увеличивать steps до PASS: точный исправленный рецепт назначает автор карточки до новой попытки. Старые опыты не удалять. Поздняя ошибка сохранения не обнуляет состоявшиеся updates; неизвестное число — null, невыполненное плечо — «не измерено».

Любое полезное измеренное улучшение в **валидном учебном сравнении** — успех своей метрики/домена; рост accuracy необязателен, регрессии рядом. Диагностика невалидной постановки не закрывает учебную цель. Default-модель исполнителя без override; точные H/R/entry ниже. Отчёт — русский R/report.md. Текущая правка документов не разрешает runtime. Прямые STOP/NEXT Любы немедленны и при открытой цели.

## Общая рубрика качества

До опыта для каждого случая записать 2–4 проверяемых смысловых пункта и отдельно критическое противоречие. Оценка случая — доля выполненных применимых пунктов; итог домена — среднее сначала внутри семейств, затем между семействами. Пункты, которые неприменимы, исключаются из знаменателя, а не становятся бесплатными баллами. Состав и веса фиксируются заранее.

Эта рубрика для новых опытов; она не заменяет scorer уже начатой кампании. Помимо частичного балла показывать полные решения, критические ошибки и приобретения/потери. Можно иметь полезный частичный прирост при прежнем числе полностью правильных задач.

## D01. Документирование и понимание C#

**Смысл результата:** ответ верно объясняет поведение конкретного метода, а не повторяет красивый общий шаблон.

**Минимальные различия:** `x < limit` против `x <= limit`; `s == null` против `s.Length == 0`; `a - b` против `b - a`; значение возврата 0 против 1; исключение против допустимого результата; порядок двух операций с побочным эффектом. В качестве содержательного случая можно взять метод, возвращающий `s is null ? 0 : s.Length`: отдельно оценивать ветку null и обычную длину. Для `<`/`<=` обязательно значение на границе.

**Контроли:** одинаковое поведение с другим именем переменной; одинаковая форма кода с изменившимся условием; пограничные null/пустая строка/равенство. Для переполнения заранее назвать checked/unchecked и тип, иначе gold неоднозначен.

**Материал:** для проверки токенов достаточно 3 контрастов без обучения. Для малого L начальный проект — 8 учебных смысловых случаев, 4 DEV и 8 проверочных из иных источников или композиций; это бюджет пилота, не гарантия обнаружения эффекта. Нельзя строить TEST только переименованием TRAIN. Если вопрос касается общего префикса DPO, менять только способ обучения префикса, не одновременно размер набора и базу.

**Метрики:** правильные смысловые пункты и критические ошибки; preference отдельно; время до заданного смыслового уровня, токены, RAM. При сравнении исходной/тёплой базы стоимость её подготовки учитывается отдельно и в полной стоимости сценария.

**Промпт:** «Для P-ID сравни A/B на D01. Зафиксируй семантику выбранных методов и проверки null/границы/порядка. Покажи обе стороны каждой пары после настоящей токенизации и маскирования. После разрешённого L получи собственные ответы Student, оцени ветки поведения отдельно. Сохрани переименованный контроль и новый смысловой контраст. Не заменяй вывод обученного Student эталонным описанием».

**Хорошо:** ответ правильно различает `<` и `<=` на равенстве. **Плохо:** «выполняет проверку значения» засчитывается как объяснение обеих противоположных веток.

## D02. Анализ C# и структурные правила

**Смысл результата:** классификатор или память выбирает правильный класс/правило по структуре кода и контексту проекта. Здесь не обязательно генерировать текст.

**Различия:** одинаковый AST с иной семантически значимой константой; порядок операторов; два файла с одинаковым именем узла; одинаковый локальный фрагмент в разных enclosing contexts; rare class; ошибка security против только форматирования.

**Контроли:** форматирование и переименование без изменения смысла; другой проект с тем же классом; пограничная неоднозначная категория. Разделять TRAIN/TEST по проекту или исходному семейству, если заявляется перенос между проектами. Зафиксировать реальные label IDs, не выдумывать их из имени папки.

**Метрики:** macro-F1 и confusion matrix с support каждого класса; число неверно заблокированных корректных решений; стоимость retrieval/обучения памяти; ошибки на новых проектах отдельно от знакомых. Редкий класс с нулевым support не получает вымышленный идеальный балл.

**Промпт:** «В P-ID/D02 восстанови смысл меток и реальный структурный input. Сравни выбранное представление/правило на тех же случаях, удерживая split и порядок. Начни с трёх структурных контрастов. При L-memory отдельно покажи прирост от добавленных уроков. Положительный исторический результат не объявляй ложным из-за дефекта, который отсутствовал в его сохранённом split».

**Хорошо:** улучшилась классификация ранее ошибочных случаев другого проекта. **Плохо:** точность выросла из-за попадания вариантов одного файла в обе части.

## D03. SQL

**Смысл результата:** запрос или объяснение соответствует результату над заданными таблицами. Эквивалентные запросы допустимы, совпадение текста не требуется.

**Различия:** NULL и трёхзначная логика; `<`/`<=`; INNER/LEFT JOIN с отсутствующей строкой; COUNT(*)/COUNT(column); WHERE/HAVING; отрицание; порядок сортировки. Контрольные таблицы заранее содержат и обычные, и различающие строки: например одна строка с NULL, чтобы варианты COUNT различались.

**Контроли:** переименование столбца; дубликаты; пустая таблица; одинаковое множество строк при разном порядке, если ORDER BY отсутствует. Заранее назвать SQL dialect и bag/set semantics.

**Категории:** S — вручную заданные маленькие таблицы и ожидаемая логика; C — настоящий SQL/представляющий компонент; L — только при существующем разрешённом обучаемом SQL-пути; U — настоящий его consumer. Симуляция ответа сервера не доказывает работу SQL-маршрута.

**Промпт:** «Для P-ID/D03 закрепи dialect, схему и таблицы, на которых A/B дают разные результаты. Оцени истинность ответа по строкам, NULL и кратности, не по текстовому сходству. Найди реальный consumer. Если его пока нет, ограничь вывод выбранным уровнем C/S и подготовь точный недостающий интерфейс; не создавай второй trainer».

**Хорошо:** различены COUNT(*) и COUNT(nullable) на реальной различающей таблице. **Плохо:** оба запроса проверены только на данных без NULL и объявлены равнозначными.

## D04. EN→RU

**Смысл результата:** сохранены участники, действие, отрицание, обязательность, количество и связи предложений. Красота формулировки вторична.

**Различия:** `Alice follows Bob`/`Bob follows Alice`; `must`/`may`; `not`/утверждение; singular/plural; местоимение с однозначным контекстом; связанное прилагательное/существительное; фраза через пунктуацию и границу clause. Для gender-контраста давать контекст, который действительно задаёт пол/род; не применять универсальное правило «после женского слова всё женское».

**Контроли:** допустимый синоним; изменение только пунктуации без изменения отношений; неизвестное слово; два возможных референта. Неоднозначный референт не превращается в однозначный gold задним числом.

**Материал:** отдельно узнавание сохранённой фразы, новая композиция знакомых частей, новый смысловой случай. В проверке памяти нужный ответ/композиция должен быть достижим её заявленным механизмом. В нейронном пути реальные generated answers, не копия chosen. EN→RU и RU→EN имеют разные наборы и отчёты.

**Промпт:** «В P-ID/D04 оцени сохранность роли действующего лица, объекта, отрицания и модальности по заранее заданным пунктам. Проследи язык входа, direction key, найденные слова/фразы и verifier до окончательного ответа. Для кода уверенности покажи raw и итоговое значение, но не считай их смысловой точностью. Для UTF-8 сохрани bytes до декодирования и место повреждения».

**Хорошо:** исчезновение `not` считается смысловой ошибкой даже при красивом переводе. **Плохо:** совпадение нескольких русских слов даёт высокий quality, хотя участники действия перепутаны.

## D05. RU→EN

**Смысл результата:** тот же набор смысловых отношений, но другой фактический вход, язык, история и направление.

**Различия:** «Анна следует за Борисом»/обратные роли; «не должен»/«может не»; порядок слов при сохранении ролей; русские падежи; контекст для местоимения; новое исправление старой ошибочной пары. Английский вход, помеченный RU→EN, не является положительным опытом перевода из русского.

**Контроли:** буквальный повтор уже принятого урока; содержательное исправление с похожими словами; нерелевантная история другого направления. Для history admission показать три исхода раздельно: точный дубль, новый смысл, исправление прежней ошибки.

**Промпт:** «В P-ID/D05 проверь реальный русский source и ключ направления. Сравни A/B на одном содержательном исправлении, точном дубле и уроке другого направления. Измерь полезность допуска: изменился ли правильный ответ после принятия урока, а не только счётчик записей. Старый верный урок должен остаться доступным. Не засчитывай EN→RU-проверку как RU→EN».

**Хорошо:** новое отрицание в исправлении принято и сохранено в английском ответе. **Плохо:** история отвергает его по совпадению слов, а отчёт считает это успешной дедупликацией.

## D06. Морфология, части речи и связи

**Смысл результата:** контекст определяет роль слова и связи между словами, включая роль в другой части предложения.

**Различия:** «они стали работать» и «из стали»; один токен в разных синтаксических ролях; прилагательное, связанное с конкретным существительным; межфразовое местоимение; неизвестное словарю слово с достаточным контекстом. Нужны явно записанные gold role/связь, а не только приблизительное сходство вектора.

**Контроли:** известный словарный случай, неоднозначный без достаточного контекста и новый контекст того же слова. Разделять качество исходного POS/parse, качество представления и качество конечного решения. Неверная POS-гипотеза не должна автоматически становиться жёстким запретом корректного кандидата.

**Промпт:** «В P-ID/D06 сравни решения на одном слове в двух контекстах. Зафиксируй части речи, зависимость и референт отдельно, затем покажи, какие из этих полей реально использовал consumer. Проверь полезность выученной памяти и фиксированного правила при одинаковом входе. Не считай увеличение размерности доказательством сохранения смысла».

**Хорошо:** правильная роль обусловлена контекстом и улучшает связанный перевод/решение. **Плохо:** точная метка на TRAIN выдаётся за перенос на новый контекст.

## D07. Намерение и выбор домена

**Смысл результата:** выбран нужный разрешённый маршрут, а решение внутри этого маршрута полезно пользователю.

**Различия:** C#-код в просьбе объяснить, исправить или перевести комментарий; SQL внутри естественного языка; неизвестный intent; одинаковая лексика с разной целью; multi-intent. Истинная цель задаётся сценарием, не именем helper-файла.

**Контроли:** однозначный известный домен; неоднозначный запрос с допустимым уточнением; неизвестный домен. Считать exact routing accuracy недостаточно: отдельно измерять качество после маршрута, false rejection и стоимость лишних вызовов.

**Промпт:** «В P-ID/D07 передай одинаковые наблюдения двум политикам выбора. Покажи фактическое условие выбора и consumer, не только название router. Измерь верность маршрута и итогового решения. Для hybrid сравни фиксированную и обученную политику на тех же сохранённых состояниях; не обучай четыре новых состояния, если нужны только четыре варианта получения ответа».

**Хорошо:** новый маршрут улучшил итоговый ответ с известной ценой дополнительных вызовов. **Плохо:** router стал увереннее, но downstream не использует выбранный домен.

## D08. Трасса, Unit, Flow и многошаговая задача

**Смысл результата:** не теряются необходимые действия, их порядок, связи входов/выходов и условия выполнения.

**Различия:** проверить доступ перед записью/после записи; несколько выходов одного Unit; зависимость второго шага от первого; одинаковые действия в разных episode; реальная remediation против общей шаблонной фразы; обучение с частично принятым batch.

**Контроли:** перестановка независимых действий; зависимые действия с изменённым порядком; отказ посередине и восстановление; чужой output object с изменением после добавления в память. Контрольный отказ задаётся только в разрешённом изолированном будущем опыте, не в рабочем процессе.

**Промпт:** «Для P-ID/D08 проследи исходную пару → подзадачи → входы Unit → изменённое состояние → обычный ответ. На каждой границе сохрани смысловое различие chosen/rejected. Сравни одну конкретную границу A/B. Если учебный текст заменился шаблоном типа ошибки, покажи это отдельно от качества trainer. Для восстановления проверь и отсутствие двойного применения, и наличие нового полезного решения».

**Хорошо:** после урока исправился порядок зависимых действий и это дошло до конечного Flow. **Плохо:** count Unit вырос или JSON успешно сохранён — значит многошаговое обучение успешно.

## D09. Ответ по источникам и графу знаний

**Смысл результата:** найдено нужное свидетельство и оно действительно повлияло на правильный ответ; нерелевантные сведения не подменили источник.

**Различия:** значимый факт после обрезаемого префикса; факт только в metadata; два документа с одинаковым началом и разными отношениями; valid/stale/empty seeds; связь через два узла; новая подтверждённая поправка к старому факту.

**Контроли:** вопрос без ответа в корпусе; нерелевантное добавление в пул кандидатов; смешанные valid/stale seeds; source contradiction с заранее заданным правилом разрешения. Оценить retrieval recall@k по gold evidence и конечный grounded answer отдельно.

**Промпт:** «В P-ID/D09 используй маленький корпус с заранее указанными источниками ответа. Сравни только выбранное свойство prefix/index/seed/fusion. Покажи фактический ContextText и кто его потребил. Если он никому не передаётся, не приписывай продукту результат retrieval. Скорость поиска и число правильных ответов измерь раздельно».

**Хорошо:** нужный поздний факт стал доступен и изменил ошибочный ответ. **Плохо:** вернулся непустой список узлов, поэтому ответ объявлен обоснованным.

## D10. TypeScript/Angular — условный структурный перенос

Упоминание этого домена в новых помощниках не подтверждает готового обучающего маршрута. Сначала назвать настоящий parser/consumer и сделать C на трёх контрастах: порядок проверка→вызов, optional/nullish поведение с заранее названной версией языка, синхронный/асинхронный порядок. Переносить смысл вопроса E13, а не Roslyn kind names. Для Angular отдельно фиксировать, проверяется ли TypeScript-код или template binding; это разные входы.

**Промпт:** «Для P-ID/D10 установи конкретную языковую версию и путь. Дай два семантически равноценных синтаксиса и один близкий, но иной по поведению. Покажи, сохраняет ли настоящее представление различие и использует ли его consumer. Если пути нет, верни ограничение применимости, не создавай весь домен ради эксперимента».

**Хорошо:** корректность выбора на настоящем TS AST с известной стоимостью. **Плохо:** успешный C# ExpressionBody опыт объявлен доказательством Angular.

## D11. Иврит и английский — каждое направление отдельно

Этот профиль применяется только при найденном реальном языковом пути. Первые смысловые контрасты: отрицание, субъект/объект, число, род при достаточном контексте, сохранение имени и количества. Явно заданные участники устраняют неоднозначность. Проверять реальные Unicode-токены и target language; латинская транслитерация не заменяет правильный иврит, если контракт требует иврит.

**Промпт:** «Для P-ID/D11 выбери ровно HE→EN либо EN→HE. Зафиксируй три контраста с проверенным языковым gold и разрешёнными вариантами. Раздельно измерь сохранность смысла, грамматические согласования и повреждения кодировки. Русскую морфологическую эвристику не переносить; роль/референт должны следовать именно из этого входа».

**Хорошо:** сохранены отрицание и роли в конкретном направлении. **Плохо:** латинские слова в ответе засчитаны как успех EN→HE либо успех EN→RU объявлен переносом без измерения.

## D12. Испанский и английский — каждое направление отдельно

Первый пилот только после подтверждения consumer: утверждение/отрицание, разные действующие лица, единственное/множественное число, явно различённое время и модальность. Допустимые пропуски выраженного субъекта и варианты перевода заранее задаются языковым gold, а не правилом совпадения строк. Неоднозначный исходник получает несколько допустимых интерпретаций либо исключается из узкой причинной панели до опыта.

**Промпт:** «Для P-ID/D12 выбери ES→EN либо EN→ES, зафиксируй контрасты и допустимые грамматические варианты. Сравни один механизм на тех же входах; покажи смысловую правильность и цену по времени/памяти. При отсутствии нужного языкового пути ограничь результат C/S и явно отметь, что обучение домена не проверено».

**Хорошо:** разные корректные формулировки получают одинаковый смысловой балл. **Плохо:** правильный синоним объявлен ошибкой из-за несовпадения с одним эталоном.

## Поперечные механизмы: не дополнительные домены

### M1 / MM. Общая память и типизированный Unit

Применять P16–P25 и P60–P64 к одному реально используемому payload из D01–D09. Минимально: один урок, его перефразировка, отрицательный контраст; затем добавление нерелевантного урока и исправления. Проверить отсутствие потери старого полезного решения, алиасов и изменения хранимого Output через внешнюю ссылку. Для immutable string и mutable object выводы различаются. Не объявлять generic bug активным в домене без конкретного типа.

**Промпт:** «Назови фактический TInput/TOutput и вызов. Проверь один урок до/после, устойчивость к нерелевантному добавлению и мутации внешнего объекта. Отдельно посчитай память, качество retrieval и качество итогового ответа».

### M2 / PT. Нейронное ядро и предобучение

Применять P01–P14, P68, P75–P78 к D01, D03, D04 или D05 с реальным tokenizer/state. Сначала C на маленьком тензоре/последовательности при численной ошибке; L нужен только для вопроса о приобретённом поведении. Различать embedding, projection, q/v-LoRA и выходной слой. Смена vocabulary требует смысловой совместимости IDs, одинаковая размерность недостаточна.

**Промпт:** «Сопоставь разрешённые параметры, границы ответа, длину и mask с текущим consumer. Для конкретного P-ID отдели finite-difference/component correctness от обучения. Не переносить старый checkpoint в иной словарь. Измеряй скорость на одинаковой работе, а sample efficiency — на одинаковой целевой способности».

### M3 / DC. Преобразование материала в обучаемые структуры

Применять P06–P07, P13–P14, P18, P26, P39, P48 и P70 только к реальному material→Unit/Flow/vector контракту выбранного домена. Начать с сохранности одного значимого отрицания, оператора, роли или порядка. Finite отказ на внешнем публичном helper не равен пропуску NaN в штатном builder: проверять фактический вход.

**Промпт:** «На одном исходном смысле покажи каждое представление после преобразования и точное различие двух сторон. Проверь его сохранность до получателя обучения. Если вход штатно отклонён до подозреваемого участка, зафиксируй защиту и не объявляй обход воспроизведённым».

## Продолжение между доменами и выбор архитектуры

Для вопроса о забывании взять состояние после D01, сохранить его, затем обучить разрешённый D04. Старый D01-экзамен не менять. Показать новые приобретения D04, потери D01 и полную стоимость. Обратный порядок — отдельный будущий вопрос, не обязательная третья кампания.

Для каждого домена итоговая таблица должна содержать: применённую архитектуру, полезный показатель, цену, условия применимости и неопределённость. Общий победитель не назначается. Например, память может быть лучшей по стоимости на повторяющихся известных ситуациях, а другой путь — по новым композициям. Это результат, который помогает выбирать архитектуру по задаче.
