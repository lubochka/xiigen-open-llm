# Повторное использование уроков: ранжирование ещё не означает изменение обучения

Дата: 2026-10-16. Фаза: `READ_ONLY_RESEARCH`. Прочитаны исходники и материалы помощников; новые вычислительные проверки, обучение и изменения кода не выполнялись. Снимок core: `32ac6e741ce4cfb2dd8ac024716e470f8d0f18f7`.

## Что удалось уточнить

Находка помощников о границе «три или четыре старых урока» действительно соответствует коду отбора. Но предложенное исправление порядка трёх уроков **может вообще не менять DPO-вход**: следующий компонент снова сортирует их по дате. Кроме того, JavaScript-проверка помощника использует другую формулу, чем проверяемый C#-класс. Поэтому её числа нельзя считать численным воспроизведением продуктового ранжирования.

Эта находка относится к capability-training и создаваемому retrieval Unit. Наличие такого класса не доказывает его участие в уже завершённом RP01 Main500.

## 1. Где существует граница по числу кандидатов

[ReplayFusionRanker.cs:13](../../../18.CapabilityTraining/ReplayFusionRanker.cs#L13) принимает `topK=3`. При `manifests.Count <= topK` возвращается исходный порядок без вычисления релевантности (строки 18–21). При большем количестве считаются BM25 и пересечение наборов токенов, затем выбирается первая тройка (23–37).

Реальный вызывающий участок [DefaultLogicalCapabilityTrainer.cs:1870](../../../18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs#L1870) передаёт кандидатов, предварительно упорядоченных по убыванию даты, и использует три места. Таким образом:

- при трёх доступных уроках отбор не исключает ни одного из них;
- при четырёх уроках меняется не только порядок: один урок уже может не попасть в тройку;
- добавление четвёртого урока также меняет корпус для BM25. Это не чистое изменение одного переключателя ранжирования.

## 2. DPO повторно сортирует эту тройку

[AutonomousLearningReplayMixer.BuildPreferences](../../../18.CapabilityTraining/LogicalExperimentOptimizations.cs#L152) вычисляет число replay-пар, затем применяет `OrderByDescending(CreatedAtUtc).Take(replayCount)` (171–175). Второй overload делает то же самое (182–210). Затем выполняется фиксированное перемешивание, а не новая оценка релевантности (253–266).

Для **одних и тех же трёх manifest с различными датами** принудительное ранжирование вместо раннего возврата не изменит выбранные этим mixer пары и их порядок. Это следует из цепочки сортировок; runtime-прогон не проводился. При одинаковых датах нужно отдельно учитывать устойчивый порядок сортировки. При изменившемся составе тройки данный вывод уже неприменим.

Следовательно, улучшение `law-relevant@1` в отдельно вызванном ranker не доказывает улучшения обучения. Сначала нужно сравнить точные ID и хеши материала, фактически поступившего в DPO. В протоколе помощника уже предусмотрен вывод `ORDER_ONLY_NOT_CAUSAL`; чтение downstream-кода делает эту оговорку необходимой для его R1.

## 3. Ветка kNN имеет другой контракт порядка

Нельзя переносить предыдущий вывод на всю capability-систему. [BuildKnnTrainingCorpus](../../../18.CapabilityTraining/DefaultLogicalCapabilityTrainer.cs#L3467) берёт все выбранные replay-manifest в обратном порядке и добавляет текущие ветви. [GeneratedCapabilityKnnCorpusProjector](../../../18.CapabilityTraining/GeneratedCapabilityExecutableManifestProjector.cs#L333) сохраняет этот порядок в собственном массиве и хеше. [TransformerEmbeddingKnnLogicalUnit.Train](../../../18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L98) добавляет векторы в HNSW последовательно в том же порядке.

Поэтому принудительная перестановка той же тройки может изменить порядок вставки в индекс, даже если DPO-материал остался тем же. Это ещё не доказательство изменения ответа: при исполнении Unit запрашивает кандидатов и заново ранжирует их, с развязкой равных итоговых оценок по `ExampleId` ([175–243](../../../18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L175)). Требуется различать состав памяти, порядок её построения, найденных кандидатов и окончательный ответ. Последовательность вставки сама по себе не является приростом качества.

## 4. Ошибка соответствия в предоставленном proxy

В прочитанном `31-MICRO-REPLAY-SCORE-AND-ORDER-SOURCE-PROXY.mjs` лексическая оценка делится на максимальный BM25 среди кандидатов: `l/maxLex`. Но [ReplayFusionRanker.cs:27](../../../18.CapabilityTraining/ReplayFusionRanker.cs#L27) складывает **сырой** BM25 с другими компонентами:

`0.45 × Jaccard + 0.35 × BM25 + 0.20 × Jaccard`.

Нормализация на максимум есть в **другом** классе — [TransformerEmbeddingKnnLogicalUnit.ScoreCandidates:233](../../../18.CapabilityTraining/LlmIngredientLogicalUnits.cs#L233). Это два разных потребителя. Proxy фактически смешал части их формул. Его заявленное ограничение про упрощённые ASCII-корни не покрывает это дополнительное различие.

Сохранённый JSON proxy прочитан как результат помощника. Мы его не пересчитывали. Даже если конкретный победитель на сконструированном примере совпадает, общая численная эквивалентность продукту не доказана. Исправлять файл помощника или запускать его в этой фазе не требуется; расхождение сохранено здесь для будущего исполнителя.

Дополнительно R2 в proxy и fixture использует `topK=1` и два кандидата. Это допустимая отдельная проверка scorer, но реальный capability-вызов с `topK=3` на двух кандидатах попадает в ранний возврат. Текст native-протокола предлагает для R2 минимум четыре кандидата; эти две постановки нельзя объединять в один результат.

## 5. «Структурная» составляющая действительно повторяет пересечение токенов

В `ReplayFusionRanker` строка 29 буквально задаёт `pattern = vector`, где `vector` — Jaccard нормализованных слов, а не transformer-вектор и не отношения между аргументами. Поэтому веса 0.45 и 0.20 здесь складываются в 0.65 одного признака.

Для C# порядок аргументов, для SQL стороны соединения, для EN→RU действующее лицо и объект действия могут менять правильность при одинаковом наборе слов. Это предметные причины проверить представление. Однако замена на равенство всей строки, используемая в одном proxy, ещё не реализует законы домена и не доказывает обобщение на новые формулировки.

## Как проверить позднее — без запуска сейчас

1. Зафиксировать одну разрешённую коллекцию manifest, даты, `topK`, запросы и источник токенизации. Отдельные панели: три кандидата; четыре и больше; одинаковые даты как пограничный случай.
2. Для панели трёх кандидатов сравнить исходный и принудительно отсортированный список, затем **точные DPO-пары после mixer**. Если они совпали, не запускать два одинаковых обучения ради различия `top1`.
3. Отдельно сравнить упорядоченный kNN-корпус, вставку, найденные ID и итоговый ответ. Не приписывать изменение retrieval работе optimizer.
4. Для структурной гипотезы использовать минимум четыре кандидата в реальном вызывающем пути и заранее выбранное различие конкретного домена. Менять один признак; сохранить BM25, остальные веса и набор данных.
5. Считать предметную правильность ответа, сохранение прежних решений, долю выбранных допустимых уроков и стоимость. При неизменных входах/ответах записать отсутствие обнаруженного влияния, а не «исправленное обучение».

Это описание будущей проверки, а не разрешение или поручение запустить её.
