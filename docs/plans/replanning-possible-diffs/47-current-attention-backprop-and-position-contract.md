## Локальная математика backward

| Участок | Проверенное свойство и точная граница |
| --- | --- |
| Reshape/Transpose | Attention [323–352](C:/Projects/llm_mvp_core/03.TransformerModel/Layers/CausalSelfAttention.cs:323) использует TensorOps, а не новый detached Tensor. [Transpose:707–783](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:707) переносит градиент обратной перестановкой тех же осей; [Reshape:887–916](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:887) восстанавливает исходную форму. Перестановка `[B,T,heads,D] ↔ [B,heads,T,D]` согласована. |
| RoPE | [RotaryEmbedding:32–72](C:/Projects/llm_mvp_core/03.TransformerModel/Layers/RotaryEmbedding.cs:32) формирует угол `(offset+t) / theta^(2i/D)`. [TensorOps:1276–1364](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:1276) вращает split-half пару `i, D/2+i`: `y1=c*x1−s*x2`, `y2=s*x1+c*x2`; backward даёт `dx1=c*g1+s*g2`, `dx2=−s*g1+c*g2`. Это транспонированная матрица того же вращения. |
| Константы RoPE | [OuterProduct:1184–1207](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:1184), [Cos/Sin:1088–1116](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:1088) возвращают detached tensors. В данном caller их аргументы — созданные позиции и фиксированные частоты, не q/v или trainable theta. Отсутствие их производных не обрывает x-gradient: ApplyRotaryEmbedding сам связывает результат с x. |
| GQA | [RepeatInterleave:1211–1274](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:1211) повторяет каждую KV-head подряд четыре раза по оси 1; backward складывает все соответствующие upstream-вклады через `+=`. Нужна сумма, а не среднее: один исходный K/V участвует в четырёх query-heads. |
| QKᵀ и PV | [Attention:263–291](C:/Projects/llm_mvp_core/03.TransformerModel/Layers/CausalSelfAttention.cs:263) вычисляет `P=softmax(mask(QKᵀ/√D))`, `O=PV`. В [MatMul:593–700](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:593) attention-операнды имеют одинаковые `B*heads` ведущие матрицы, поэтому `batch % bBatchSize` выбирает соответствующую матрицу без коллизии. Производные соответствуют `dV=PᵀdO`, `dP=dOVᵀ`, `dQ=dSK/√D`, `dK=dSᵀQ/√D`. Это managed TensorOps/SimdOps path, а не доказательство о другом native attention backend. |
| Causal mask | [TensorOps:1367–1452](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:1367): ordinary mask использует `past=0`; разрешены столбцы `j≤row`. Forward пишет `−∞` выше диагонали; backward копирует только разрешённые координаты. У masked scores gradient нулевой. |
| Softmax | [TensorOps:789–883](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:789): вычитание max по последней оси, нормировка exp; backward `dx_i=p_i*(g_i−Σ_j p_j*g_j)`. В данном causal caller каждая строка имеет хотя бы self key; при конечных немаскированных scores строка не состоит целиком из `−∞`, и знаменатель положителен. Утверждение не покрывает NaN/Infinity, уже пришедшие до softmax. |

**Контрограничение RoPE:** для нечётного `D` этот kernel обрабатывает только `2*floor(D/2)` координат; последняя координата результата и её градиент остаются нулевыми. Это не универсальное сохраняющее норму вращение нечётномерного вектора. Такое прежнее поведение прямо закреплено в [LoraTests:573–636](C:/Projects/llm_mvp_core/Tests/LoraTests.cs:573). У RP01 `D=64`, поэтому это не найденная причина его качества. Нельзя переносить вывод о корректности на нечётные размеры без отдельного контракта.

Здесь не найдено ни утраты одной из KV-групп, ни усреднения вместо суммы, ни перепутанного знака RoPE backward, ни backward через запрещённые будущие позиции. Изменение 16 LoRA tensors само этого не доказывало; приведённые формулы — отдельное контрдоказательство простому предположению о разорванном или очевидно неверном attention-gradient. Оно всё ещё не заменяет численную проверку композиции на actual материале.

## Cache, absolute positions и первое решение

[LlmModel.ForwardWithCache:156–199](C:/Projects/llm_mvp_core/03.TransformerModel/LlmModel.cs:156) один раз читает uniform past length до цикла blocks и передаёт **одинаковый** offset каждому слою. Он не берёт уже увеличенную длину layer 0 как offset layer 1. После всех слоёв проверяется общая ожидаемая длина. При исключении внутри вычисления cache очищается.

В [cached attention:173–248](C:/Projects/llm_mvp_core/03.TransformerModel/Layers/CausalSelfAttention.cs:173) проверяются длина конкретного слоя и предел контекста. Новый chunk получает RoPE positions `past ... past+chunkLength−1`. В cache добавляются уже повёрнутые K и обычные V с исходными **двумя** KV-heads; старые K повторно не вращаются. GQA-repeat выполняется после чтения накопленных K/V. [MaskWithPast:1384–1421](C:/Projects/llm_mvp_core/00.TensorCore/Core/TensorOps.cs:1384) требует `keyLength=past+queryLength` и допускает `j≤past+row`. При одном новом query доступны все накопленные keys; при chunk длины больше 1 будущие позиции внутри chunk остаются закрытыми.

[KvCache:89–143](C:/Projects/llm_mvp_core/09.Inference/KvCache.cs:89) хранит snapshots, а [AppendAlongSequence/DetachedSnapshot:242–270](C:/Projects/llm_mvp_core/09.Inference/KvCache.cs:242) правильно дописывает временную ось отдельно для каждой ведущей B/KV матрицы. `DetachedSnapshot` создаёт tensor без `RequiresGrad` и без предков. Это относится и к текущим K/V первого prefill. **Если такой путь использовать для обучения, K/V-gradient был бы потерян. Но найденные DPO callers используют обычный Forward, поэтому это условный риск неправильного caller, не наблюдаемый дефект RP01 training.** Нельзя также объявлять весь cached forward глобальным no-grad: отсоединяются cache snapshots, а не произвольные остальные операции.

[TextGenerator:182–242](C:/Projects/llm_mvp_core/09.Inference/TextGenerator.cs:182) создаёт новый cache на запрос, выполняет prefill всех prompt IDs, берёт его последнюю строку logits и только затем выбирает первый токен. Для следующего решения выбранный токен передаётся через cached forward. Последний токен/EOS уже не прогоняется, отсюда корректная проверка бюджета `promptCount+maxNewTokens−1`. Ошибка только последующего decode не объяснила бы неверные logits первого решения; возможное отличие empty-cache prefill от обычного Forward нужно проверять отдельно.

Cache может влиять на свободное продолжение через сохранение истории и absolute positions, но не обновляет learned weights. Совпадение значений полного и cached forward математически ожидаемо при dropout 0 и одних параметрах. Побитовое совпадение всех режимов здесь не доказано: длины матриц и порядок float-редукций могут различаться. У почти равных лидирующих logits даже малая допустимая численная разница требует отдельно учитывать запас до второго кандидата.

## Минимальная будущая различающая проверка — не исполнена

Только после отдельного прямого разрешения на исполнение: зафиксировать один фактический RP01 checkpoint с ненулевыми q/v A/B, конфигурацию, tokenizer и пять точных token IDs. Сначала сравнить logits полного ordinary Forward с empty-cache prefill, затем с cached разбиением той же истории `2+2+1`, на соответствующих абсолютных позициях. Не выбирать новый токен между ветками: одинаковая история отделяет ошибку cache/position от расхождения sampling. Заранее задать абсолютный/относительный допуск и отдельно записать запас top-1 до top-2. Совпадение ослабит эту гипотезу о свободном ответе; расхождение уже первого prefill локализует иной участок, чем расхождение только поздних chunks.

Отдельная короткая derivative-проверка продолжает именно открытый вопрос 41: на **обычном uncached** attention с теми же `Q/KV=8/2`, `D=64`, короткой последовательностью и фиксированным upstream сопоставить analytic gradient и central finite difference выбранных координат q/v A/B при ненулевом B. Она должна включать reshape → RoPE → repeat → mask → softmax → PV, а не только отдельный оператор. Для B=0 нулевой A-gradient ожидаем и не является свидетельством поломки. Это локальная численная проверка, ещё не доказательство правильности всего weighted exact-v2 loss или улучшения свободного текста. Никакой runner для этих предложений не создан.
