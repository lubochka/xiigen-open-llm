## Что подтверждает код

[BpeTokenizer.Train](C:/Projects/llm_mvp_core/01.Tokenizer/BpeTokenizer.cs:42) начинает словарь с 256 отдельных байтов. Merged token тоже содержит байты, не обязательно полный Unicode scalar. [Decode](C:/Projects/llm_mvp_core/01.Tokenizer/BpeTokenizer.cs:87) соединяет байты известных token IDs и вызывает `Encoding.UTF8.GetString`. Неизвестные IDs игнорируются, но detailed генератор отдельно проверяет диапазон выдаваемых IDs.

[TextGenerator](C:/Projects/llm_mvp_core/09.Inference/TextGenerator.cs:212) добавляет выбранный token, останавливается по EOS или maxNewTokens и затем декодирует весь список. Проверки завершённости UTF-8 scalar в stop-условии нет. Поэтому конец на первом байте многобайтового символа возможен. Это обоснованное условие, а не измеренная частота.

В RP01 [общий вызов](C:/Projects/llm_mvp_core/14.ContinuousLearning/Training/CodeDocumentationStudentGeneration.cs:72) передаёт verifiedEosToken=null. Случайный старый EOS ID не является объяснением этого конкретного detailed пути. Условие о неизвестном ID также не надо смешивать с валидным byte-token, оказавшимся неверным продолжением другого байта.

## Что пока невозможно восстановить из этих receipts

Они содержат counts, stopReason и уже декодированный текст, **не полный список generated token IDs или bytes**. U+FFFD мог появиться из replacement decoding неверной последовательности или быть непосредственно выдан как кодировка этого символа. По строке после декодирования эти случаи не различить. Повторно закодировать строку в UTF-8 и успешно проверить её — не проверка исходных generated bytes: информация уже потеряна.

Внутренние U+FFFD не объясняются только обрывом последнего scalar. Для C# near-022 конец с U+FFFD совместим с tail-гипотезой, но не доказывает её; там остаются также внутренние U+FFFD. Для восьми ENRU ответов нет наблюдаемого replacement в конце. Следовательно, **tail completion не является достаточным объяснением их состояния или предложенным исправлением всего качества**.

Полностью прочитаны [UTF8 finding](<C:/Users/lubao/Documents/xiigen/llm mvp/design to code session/replanning/possibleDifs/33-NEW-UTF8-DECODER-CUTOFF-2026-10-16.md>) и [чужой proxy JSON](<C:/Users/lubao/Documents/xiigen/llm mvp/design to code session/replanning/possibleDifs/33-MICRO-UTF8-PROXY-RESULT-2026-10-16.json>). JSON показывает четырёхсимвольный набор с усечённым первым байтом. Это локальная иллюстрация replacement decode, не .NET/Student/доменные ответы; Python здесь не запускался.

В будущем при отдельном разрешении сначала сохранять raw IDs и соответствующие vocab bytes, отличать invalid interior от incomplete trailing sequence и literal U+FFFD. Для контроля заморожены checkpoint, tokenizer, prompt и sampling. Один byte-token не равен одному символу; merged token не равен одному байту. Обещание «добавить максимум три байта» требует реального контракта выбора продолжения: следующий выбранный моделью token может содержать много байтов либо не быть допустимым continuation. Простое принудительное подставление нужных байтов меняет генерацию и не считается обучением.

Сначала нужен ответ, **где нарушилась последовательность**, затем отдельный вопрос, меняется ли предметный смысл. Уменьшение числа `�` без правильных ответов — исправление представления, не доказательство приобретённой способности. Нового обязательного запуска для объяснения уже прочитанных данных этот отчёт не назначает.
