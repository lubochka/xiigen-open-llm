# Граница ответа и декодирование: какие новые замечания относятся к RP01

Дата: 2026-10-16. READ_ONLY_RESEARCH. Core `259c61769c3c`, planning `959e3eb11c95`. Чтение исходников; никаких повторных генераций, численных proxy или native проверок.

## Подтверждённая граница обучения

В нынешнем exact-DPO обучаются токены самого ответа, но не отдельный символ «ответ закончен». [DpoExactPairMaterial.cs](../../../11.DPO/Models/DpoExactPairMaterial.cs), строки 30–46 и 64–78, соединяет отдельно закодированные prompt и response. `Tokens :171–176` не добавляет ещё один target; `Mask :178–181` ограничивает маску длиной исходного ответа.

В [CodeDocumentationStudentGeneration.cs](../../../14.ContinuousLearning/Training/CodeDocumentationStudentGeneration.cs), строки 61–74, вызывается `GenerateDetailed` с `verifiedEosToken: null`. Это осознанное согласование с нынешними manifest, в которых не объявлен настоящий EOS. [TextGenerator.cs](../../../09.Inference/TextGenerator.cs), строки 213–249, в таком режиме завершает ответ по бюджету токенов. Следовательно, этот DPO-этап сам по себе не обучает специальному сигналу остановки.

Это дополнительная грань уже известной темы EOS, **не новая независимая причина**, которую следует прибавить к числу остальных ошибок. Нет оснований возвращать старый последний BPE merge ID в качестве EOS: обычный словарный токен не становится границей ответа от такого переименования.

## Чего это не объясняет автоматически

Теоретически полезный короткий ответ мог бы быть испорчен продолжением до лимита. Но сохранённые C# и ENRU ответы, разобранные в [14](14-data-quality-and-evaluation-alignment.md), не дали подтверждения такой полезной способности. Нулевой полный балл сам по себе не доказывает ни «правильный префикс был», ни «остановка несущественна».

Дешёвый **будущий** дизайн сначала оценивает уже сохранённые полные тексты по заранее заданным смысловым пунктам и отделяет неверное начало от вредного продолжения. Если требуется новый опыт, правило остановки задаётся до просмотра gold и не использует правильный ответ как подсказку. Добавление обучаемого EOS требует отдельного контракта tokenizer/checkpoint; оно не является заменой обучения смыслу и грамматике.

## TopK/TopP: реальное свойство кода, но другая ветка

[Sampler.cs](../../../09.Inference/Sampler.cs), строки 20–38: при `temperature<=0` сразу выбирается argmax. При положительной температуре `topK>0` выбирает TopK, а TopP находится в `else if`. Значит, два ограничения сейчас не комбинируются. Это расхождение с ожиданием совместного фильтра требует сначала установить обещанный контракт потребителя, а не автоматически объявить любой такой API неверным.

В `TopKFilter :42–55` сохраняются все значения не ниже k-го порога, поэтому равные логиты могут оставить больше k кандидатов. Это source-свойство без проведённого sampling опыта.

[Текущая конфигурация обычной C# генерации](../../../config/code-documentation/generation-v1.json) задаёт temperature=0, topK=0, topP=1. Прочитанный RP01 экзамен тоже использовал greedy режим. Эти conditional sampling-вопросы поэтому **не объясняют его нынешний отрицательный результат**. Они остаются отдельным вопросом для будущих режимов генерации и других потребителей.

## Пропуск неизвестного токена: защита нынешнего пути

[BpeTokenizer.Decode](../../../01.Tokenizer/BpeTokenizer.cs), строки 87–91, заменяет неизвестный ID пустым набором bytes. В общем вызове это способно скрыть несоответствие словаря. Но `GenerateDetailed` сначала валидирует canonical tokenizer (`TextGenerator :173–190`), а затем каждый полученный ID (`:230–231`). Нельзя переносить риск неподробного пути на нынешний проверенный RP01 consumer без факта обхода этих защит.

Это не доказывает качество декодированного языка. Разрешённый словарный ID, корректная маска и отсутствие исключения — инженерные свойства; смысл ответа измеряется отдельно.

## Как учтены материалы помощников

Первично сверены claims DS26-01/02/03 из `26-INDEPENDENT-STOP-TARGET-AND-SAMPLER-2026-10-16.md` и decoder-ветка N23-C из `23-INDEPENDENT-AUDIT-SHAPE-DECODER-AND-LEARNING-2026-10-16.md`. Их численные shadow/proxy и предложенные 256-token запуски не выполнялись. Shape-mismatch cosine — другой участок, этим документом он ещё не проверен. Подтверждённое отсутствие stop-target сохраняется как вопрос текущего контракта; sampler и неизвестные ID отделены как условные риски других режимов.
