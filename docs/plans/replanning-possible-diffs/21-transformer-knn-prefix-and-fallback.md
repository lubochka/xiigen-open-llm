## Для человека

В одном гибридном Unit нейросеть видит только начало запроса. Условие в конце длинного текста может не попасть в его нейросетевой вектор. Но утверждение «одинаковые первые 64 токена всегда дают одинаковый итоговый embedding» слишком сильное: есть запасная ветка, которая считает токены по всему тексту. Кроме того, итоговый выбор использует полный текст ещё в одном, лексическом канале. Эти пути надо различить до попытки исправлять качество.

Это не установленная причина бессвязных ответов RP01: его проверенный serving path получает модель и tokenizer через `GetServingRuntime`, затем вызывает TextGenerator, а не описанный здесь `ExecuteAsync`. Разделение consumers разобрано в [12](12-student-update-to-generation-path.md).

## Первичные доказательства и поправки

1. [LlmIngredientLogicalUnits.cs](../../../18.CapabilityTraining/LlmIngredientLogicalUnits.cs):98–115 создаёт EmbeddingModel с `Math.Min(64, model.Config.ContextLen)`. [EmbeddingModel.cs](../../../05.Embeddings/EmbeddingModel.cs):77–83 кодирует текст и оставляет первые `_maxLen` ID. В этой ветке нет окон или особого сохранения завершающего предметного условия.
2. Там же, 31–44: `ForwardHidden → MeanPooling → Normalize → EnsureNonZeroUnitVector`. Последний вызов нельзя пропустить при выводе об одинаковых vectors.
3. Там же, 49–73: если norm больше `1e-6`, возвращается нейросетевой вектор; иначе кодируется **полный исходный текст**, token counts складываются в координаты `tokenId % vector.Length`, затем нормируются. Это детерминированный запасной способ построения признаков. Он может различить suffix, который не видела нейросеть, но не сохраняет порядок токенов и допускает совпадения координат. Для пустого encoded текста есть отдельный string-hash fallback.
4. Следовательно, условное равенство при одинаковых первых 64 ID относится к нейросетевой ветке при одинаковом состоянии и режиме вычисления. Для конечного embedding нужно установить, какая ветка реально сработала. Частота fallback и наличие длинных значимых suffix в настоящем корпусе пока не измерены.
5. [LlmIngredientLogicalUnits.cs](../../../18.CapabilityTraining/LlmIngredientLogicalUnits.cs):181–191 передаёт query vector в HNSW, затем полный `request.Input` в ScoreCandidates. В 217–294 лексическое и структурное сравнение используют весь текст, но свою нормализацию. Она теряет некоторые языковые/операторные различия — [15](15-memory-growth-fusion-and-bpe.md).
6. Уточнение helper-предположения о «правильный сосед не попал в небольшой top-k»: в этом caller запрашивается `topK = _examples.Count`. [HnswIndex.cs](../../../06.VectorSearch/HnswIndex.cs):99–110 устанавливает `ef >= topK`; 190–222 обходит достижимые соседние вершины. Это не обычный маленький shortlist. Полнота достижимости графа здесь не доказана, поэтому нельзя ни гарантировать все записи, ни приписывать потерю правильного кандидата малому k без actual candidate IDs. Даже при полном пуле усечённый vector меняет один член fused score и способен менять ранжирование.

### История изменения

`git show 04330ca05bd8d9894e3d837f2b9272ae845ca9a0 -- 05.Embeddings/EmbeddingModel.cs` показывает добавление полного `EnsureNonZeroUnitVector` 6 мая 2026. Коммит назван wiring canonical experiment implementations. Предыдущая версия возвращала только результат pooling/normalization. Это конкретный исторический переход от исключительно нейросетевого признака к условной смеси двух способов представления, а не доказанная деградация. Поздний прочитанный diff этого файла относится к лицензии.

Гипотеза для архитектуры: улучшение в историческом kNN могло частично обеспечиваться запасным token-count представлением, а его результат затем приписывался только нейросетевому encoder. Для этого пока нет связанного положительного raw receipt с зафиксированной веткой. Этот файл не объявляет найденным тот самый успешный механизм «из матрицы в функцию».

## Малый будущий опыт — только проект

Сначала на существующем immutable checkpoint и memory проверить несколько пар текстов двух доменов: один значимый контраст до границы и тот же тип контраста после неё. Настоящие первые 64 ID должны совпадать у suffix-пары; визуально одинакового текстового начала недостаточно. Записать норму до fallback, использованный способ embedding, token IDs, candidate IDs, vector/lexical/pattern scores, итоговый ответ и предметную правильность.

Для отдельного сравнения длины изменить только 64→128 и заново построить все vectors этой ветки, сохранив memory/weights/tokenizer/fusion. Не смешивать этот контраст с отключением fallback. Если fallback активен, его вклад исследуется отдельным matched сравнением, иначе два изменения не дадут причины.

Раздельные выводы: потеря neural-признака; её компенсация другим каналом; изменение ответа; изменение правильности. Одинаковый результат при разных vectors опровергает влияние на выбранной панели, но не доказывает универсальную ненужность хвоста. Улучшение только на одном домене не переносится автоматически на другой. Никакой из этих операций здесь не запускался.
