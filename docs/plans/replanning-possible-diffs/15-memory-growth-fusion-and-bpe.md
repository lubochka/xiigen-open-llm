## Что важно для архитектуры

В системе есть как минимум два разных kNN-получателя. `TransformerEmbeddingKnnLogicalUnit` выбирает сохранённый ответ по transformer-вектору, лексике и структурной метке. `KnnLogicalUnit` заново строит BPE и хешированный вектор из учебного корпуса. Это не изменение LoRA и не доказательство того, что отдельный RP01 `TextGenerator` использовал эти механизмы.

## М-01. Шкала оценки старого ответа зависит от остальных кандидатов

Прямой источник: [LlmIngredientLogicalUnits.cs](../../../18.CapabilityTraining/LlmIngredientLogicalUnits.cs), строки 169–294. `ExecuteAsync` получает ANN-кандидатов, затем вызывает `ScoreCandidates`. Лексическая оценка каждого кандидата делится на **максимальную лексическую оценку в текущем пуле**. Итог: `0.45 × vector + 0.35 × normalizedLexical + 0.20 × pattern`. Возвращается сохранённый `example.Output`.

Поэтому добавленный кандидат может уменьшить лексический вклад всех прежних кандидатов, даже если сам не победит. Это конкретная зависимость формулы, а не предположение об исчезнувших весах. Однако изменение формулы ещё не доказывает переворот ответа на реальном корпусе: нужны фактические кандидаты и их исходные оценки. Числа из helper-прокси не являются измерениями XIIGEN.

Отдельно `ComputeBm25LikeScore:256–270` использует длины и document frequency **всего** `_examples`. Новый урок способен изменить исходный lexical score старых примеров и без попадания в ANN-пул. Нельзя смешивать два воздействия: изменение BM25-корпуса и изменение знаменателя fusion.

История по `git blame`: нормировка появилась в `d8322d1f5ea` 5 мая; нынешние три веса — в `c8dde8d038e` 7 мая. Это унаследованный механизм, а не найденная новая ошибка октябрьского RP01. Сравнение с исходным успешным E34 описано отдельно в [09](09-domain-functions-and-sibling-branches.md).

**Будущая короткая проверка, не запущена.** Сначала сохранить один настоящий запрос, его старые кандидаты и разложение оценок. Добавить один заранее выбранный предметно посторонний пример; энкодер и старые векторы оставить прежними. Для локализации отдельно сравнить оценку при неизменных старых lexical scores и при их пересчёте. Основной результат — сменился ли законно правильный старый ответ, какой член формулы вызвал смену, можно ли убрать её фиксированной шкалой без потери полезного нового урока. Отрицательный результат: меняется шкала, но ответы и предметная правильность не ухудшаются. Исправлять все три компонента одновременно нельзя.

## М-02. Неизвестная структура получает бонус совпадения

`ClassifyPattern:288–293` возвращает `UNKNOWN`, когда `NormalizeRoots` не дал токенов. В `ScoreCandidates:227–229` равенство двух таких строк даёт тот же бонус `0.20`, что установленное структурное совпадение.

Причина предметной зависимости видна в [TrainingVectorBuilder.cs](../../../23.SemanticCompilerAdapter/TrainingVectorBuilder.cs):104–134: нормализатор выделяет только `[a-z]`, отбрасывает короткие корни и ряд слов, включая `after` и `before`. Для чисто русского/ивритского текста этот лексический канал пуст. Числа и операторы C#/SQL тоже не представлены в нём. Transformer-вектор при этом остаётся отдельным каналом: вывод «вся система потеряла Unicode/операторы» неверен.

Если все кандидаты имеют `UNKNOWN`, бонус общий и **не меняет порядок**. Но `ExecuteAsync:195–204` превращает fused score в возвращаемую confidence, поэтому число может выглядеть увереннее без дополнительного знания структуры. Если часть кандидатов имеет известную метку, бонус уже может изменить порядок. Дальнейшее решение потребителя по confidence в этой части исследования не прослежено.

**Будущая проверка.** Один фиксированный пул с известными и неизвестными структурами; отдельно полностью неизвестный пул. Единственный фактор — выдавать ли структурный бонус при `UNKNOWN`. Сохранить выбранный ответ, confidence и предметную правильность. Для EN/C#/RU/HE результаты разделять. Не заменять отсутствие разбора универсальным запретом на ответ.

## М-03. Лексическая обработка повторно обходит всю память

Для каждого ANN-кандидата `ComputeBm25LikeScore` заново токенизирует весь корпус для average length; для каждого совпавшего query-token снова проходит корпус при подсчёте document frequency. Верхняя структура затрат зависит от `кандидаты × размер памяти × совпавшие слова`, а не только от количества возвращённых соседей. `ExecuteAsync:185` запрашивает `topK = _examples.Count`; реальное число полученных ANN-кандидатов неизвестно.

Это установленная повторная работа в коде, **не измеренное время**. Она не объясняет автоматически прежние 5 часов 43 минуты другого RP01 lifecycle. Будущая проверка — сравнить кэширование только corpus-статистик с текущим расчётом при побитово/численно эквивалентных оценках и том же ответе; измерять tokenization/scoring отдельно. Нового энкодера или обучения для этой гипотезы не требуется.

## М-04. Новый корпус заново определяет BPE-признаки старых уроков

Прямые источники: [KnnLogicalUnit.cs](../../../21.AgentInfrastructure/Logical/KnnLogicalUnit.cs):125–153,265–299; [BpeTokenizer.cs](../../../01.Tokenizer/BpeTokenizer.cs):42–68,526–538,568–573; [RegexSplitter.cs](../../../01.Tokenizer/RegexSplitter.cs):16–21.

`KnnLogicalUnit.Train` конкатенирует все inputs через `Environment.NewLine`, учит новый BPE с vocab 320, затем строит весь индекс. `BpeTokenizer` выбирает наиболее частую пару через `MaxBy(Value)` без явно заданного вторичного порядка; ID назначаются последовательно с 256. `Vectorize` складывает счётчики по `tokenId % tokenTierWidth`. Поэтому порядок строк, равные частоты и новый текст могут изменить соответствие между фрагментом текста и координатой.

**Существенное уточнение к helper.** Другие ID сами по себе не доказывают изменение расстояний. Если произошло только согласованное взаимно однозначное переименование координат, cosine остаётся прежним. Здесь риск связан также с изменением разбиения, частот и modulo-коллизий. Нужны реальные векторы и ранги; одного факта `ID changed` недостаточно для вывода «знание потеряно».

`Environment.NewLine` добавляет различие CRLF/LF в учебные байты. Regex допускает whitespace-чанки. Это основание проверить воспроизводимость словаря, но не доказательство ошибки Windows или различия качества на данном корпусе.

**Будущая проверка.** На одном маленьком предметном наборе отдельно менять порядок строк и добавлять один новый урок; сравнить с тем же дополнением при замороженном прежнем BPE. Начать с exact cosine по полученным native-векторам, чтобы случайный HNSW не стал вторым фактором. Сохранять разбиение, merge-table, коллизии, соседей и правильность ответа на тех же новых запросах. Если меняются только ID, а расстояния/ответы прежние, это воспроизводимость артефакта, не обнаруженная потеря способности.
