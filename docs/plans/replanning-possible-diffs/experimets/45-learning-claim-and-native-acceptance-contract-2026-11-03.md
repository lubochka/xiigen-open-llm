## Сначала установить, что именно проверялось

**Уточнение области QA по прямому указанию Любы:** [договор46](46-qa-execution-test-repair-and-fresh-results-2026-11-03.md) обязателен вместе с этим документом. Назначенный аудит кода, перенос, приёмка и ремонт тестов включают необходимые сборки, запуск и обоснованную адаптацию тестов по уже утверждённому договору. Слово «аудит» не означает исследовательский запрет. Этот документ был написан в документной задаче; её ограничение не наследуется исполнителем нового QA-поручения. Реально действующий технический deny не обходят, но и не объявляют вечным после снятия.

Различать три утверждения: «такой ответ наблюдался у данной сборки», «усвоен предъявленный учебный материал» и «конструкция перенесена на новые примеры». Для последнего нужны отдельные отложенные примеры; для усвоения — настоящий обученный старт, назначенные уроки и до/после. Отсутствие уроков отрицания не опровергает обучаемость отрицанию. При этом ответ «do not delete the file → удали файл» остаётся наблюдённой потерей смысла: его нельзя объявить правильным или удалить.

В P125 закреплены восемь утвердительных уроков. Его проверка восстановления может быть действительной в собственной области. Вывод о неудачном **обучении отрицанию или вопросам** на этом наборе некорректен. Исправляется именно вывод/предусловие теста, а не исходные ответы, gold или метрики. Дополнительный опыт — [обучение отрицанию P131](cards/P131-negation-training-contrast.md).

Новый ожидаемый ответ выводится из независимого требования, а не из фактического выхода продукта. Если тест проверяет обязательный отказ на неподдержанном вводе, отсутствие соответствующих уроков не делает этот контракт отказа недействительным.

## Решение архитектора после падения

| Что установлено | Решение | Что запрещено |
|---|---|---|
| Исходник не компилируется | Исполнитель исправляет назначенную типовую/интерфейсную поломку, собирает проект и тестовый проект, затем запускает проверки | Сужать long до int, исключать файл из сборки, подставлять старую DLL и объявлять текущий код исправным |
| Проверяемый контракт нарушен на корректном входе | Сохранить различающий тест; исправить причину в назначенном слое; выполнить red/green и соседние проверки | Ослаблять gold, tolerance, вход, assertion, Skip или набор обнаруженных тестов ради зелёного итога |
| Предусловие учебного теста отсутствует: модель этому не обучалась | Сохранить наблюдение и назвать TEST_DESIGN_GAP. В назначенном регрессионном тесте можно исправить изолированный fixture до уже утверждённой учебной предпосылки и повторить тест. Для новой научной гипотезы, иной программы/дозы или вывода об общем обучении оформить отдельный опыт с бюджетом, как P131 | Встраивать словарное исключение, ручной ответ, детектор do not или новый семантический guard только ради прохождения теста; незаметно превращать исправление fixture в новую научную кампанию |
| Ожидание теста действительно неверно по независимому контракту | Назвать источник ожидания и минимальную правку теста; применить уже данное разрешение в его области, иначе передать конкретное решение владельцу | Принимать текущее поведение продукта за эталон; просить одобрение на всё исправление без конкретного решения |
| Неисправна среда/запускатель или ещё нет доказательства | Передать точную ошибку и состояние исходного процесса; исправить инфраструктуру в назначенной области | Называть отсутствие файла после мгновенного чтения «опыт не запустился», запускать вторую копию или заканчивать работу вместо ожидания |

Архитектор возвращает исполнителю: класс причины, нарушенное предусловие/контракт, конкретный файл и метод, разрешённый слой ремонта, сохраняемый отрицательный контроль и команды повторной приёмки. Если причина ещё не установлена, он задаёт один ограниченный диагностический шаг; не выпускает неопределённое «почини тесты». При недостатке учебного свидетельства архитектурная гипотеза остаётся гипотезой до отдельного опыта.

## Обязательная сборка и проверки при разрешённой реализации

1. До изменения записать HEAD и локальную дельту, затронутые проекты/потребители, точные команды и ожидаемые имена тестов. При изменении публичного типа, например int→long, включить все прямые потребители и тестовый проект. Непроверенный старый тестовый бинарник не является базой.
2. После изменения **реально собрать** затронутые проекты и тестовый проект в одной указанной конфигурации. Затем **реально выполнить** назначенные целевые, интеграционные и регрессионные проверки. Если общий набор входит в условия приёмки, выполнить и его. Не заменять назначенную проверку чтением исходника или наличием файла теста.
3. `--no-build` допустим только после успешной сборки именно этого состояния/конфигурации, с записью идентичности запускаемой сборки. Build exit0 без исполнения тестов не закрывает приёмку. Test exit0 при нуле обнаруженных тестов тоже не закрывает её.
4. Сохранить команду, cwd, конфигурацию, HEAD+хеш локальной дельты, project/reference closure, DLL/PDB identity, время начала/конца, exit code, полный журнал и результат тестового раннера с числом обнаруженных/исполненных/пропущенных проверок. Проверить, что новые имена действительно обнаружены и выполнены.
5. При разрешённом запуске дождаться исходного task/session handle ограниченными блокирующими ожиданиями. Не использовать частый повторный запуск, частый опрос одного файла или финальное «жду» вместо ожидания. Прямой STOP/NEXT пользователя имеет приоритет; состояние остановленного шага остаётся честно записанным.
6. Если сборка/тест падает или исходный процесс не доходит до терминального состояния — эскалировать архитектору пакет ниже. До решения статус реализации **не принят**. Слово UNRUN честно описывает промежуточное состояние, но не позволяет закрыть поручение реализации или приёмки.
7. После принятого ремонта снова выполнить необходимые проверки на финальном состоянии. Предыдущий зелёный журнал после следующей правки недостаточен. `git add --all` выполнить по прямому правилу пользователя; staging/commit/push не заменяют приёмку. Сохранить неудачные попытки.

Для переводческих переносов затронутый продукт — `27.TranslationDomain/27.TranslationDomain.csproj`, продуктовые проверки — `Tests/LlmFromScratch.Tests.csproj`. Для нового host P131 отдельно назначены сборка актуального продукта/host и собственные проверки `P13101/Checks/Checks.csproj` по его карточке. Продуктовая приёмка29 проверок ниже относится к уже назначенному ремонту продукта и не добавляется скрытым хвостом к бюджету P131; она не разрешает новый Train или повтор P125. Конкретные фильтры задаёт карточка/автор ремонта до исполнения. Если фильтр, проекты либо бюджет не указаны, архитектор дописывает их; исполнитель не угадывает и не объявляет работу принятой. Не требовать повтора всей научной кампании для обычной компиляционной ошибки.

**Различение фаз:** только явно документное/исследовательское поручение может ограничиться чтением и честным «не запускалось». Назначенный аудит кода/QA и ремонт включают исполнение необходимых проверок; их нельзя объявлять документными для обхода приёмки. Новый научный опыт остаётся отдельным назначением. Полная таблица навыков, исправления тестов, свежести TRX и команд — в46.

Не делать тест молча зелёным, не прятать невалидность в конце отчёта и не передавать пользователю обязанность самому собрать проект.

## Хорошие и плохие примеры

- **Хорошо:** «P125 восстановил свой сохранённый результат. Отрицанию его не учили; утверждение об усвоении не измерено. Наблюдённый опасный перевод сохраняется. P131 отдельно добавляет четыре отрицательных урока».
  **Плохо:** «Добавим do not→не в продукт и тест пройдёт» либо «негативный пример невалиден, значит перевод безопасен».
- **Хорошо:** «После исправления int→long build прошёл; перечисленные новые тесты обнаружены и выполнены. Вот журнал финального SHA/дельты».
  **Плохо:** «По исходнику всё верно; тесты написаны; закрываем перенос» либо запуск старой Debug DLL вместо сломанного текущего проекта.
- **Хорошо:** «Запоминание 0/4→4/4, перенос на другие глаголы 0/4→0/4: успех запоминания, обобщение не показано; остальные изменения перечислены».
  **Плохо:** «Нет обобщения — никакого полезного улучшения» либо «4/4 в TRAIN доказывает общий перевод отрицаний».

## Навыки, отчёт и граница переноса

Перед каждым новым заданием заново и полностью читать local/canonical AGENTS, CLAUDE и основной список [120, §1](../fixes-based-on-experiments/120-executor-context-and-test-repair-contract-2026-11-02.md): архитектура, планирование, проверка плана, исполнение/проверка кода, prompt engineering, человеческая коммуникация. Для этой задачи обязательны также experiment-design, test-integrity, test-failure-triage и bug-to-tests. Использовать их для проверки решения, а не только перечислить файлы.

Любое измеренное полезное улучшение — успех по показателю и профилю; рядом показать все ухудшения. Допуск к переносу отдельно следует правилу пользователя: значимый выигрыш >5%, затем малый выигрыш, при отсутствии значимой регрессии других полезных показателей; исключение относится к CPU. Прямые логические ошибки диагностики/сохранения/восстановления рассматриваются адресно. Непроведённый P131 не даёт разрешения на новый продуктовый семантический механизм.


## Проверяемый результат и полнота исполнения — дополнение 12 ноября 2026

Основание — [численная проверка P48/P49/P50/P52/P58/WC01](../fixes-based-on-experiments/audits/2026-11-12/codex-experiment-review.md) и [проверка обычного переноса](../fixes-based-on-experiments/audits/2026-11-12/codex-product-review.md). Существующие требования нативной приёмки остаются. Ни свежий Python-пересчёт, ни commit документа не заменяют запуск продукта.

**Три носителя результата различаются явно:** immutable raw конкретного старого run; текущий producer; производная исправленная сводка. Исправленный P58 writer не делает старую расписку новой, а старая схема не опровергает уже выполненную правку writer. Для пересчёта без обучения указывать input hash, алгоритм/версию вычисления и отдельный output; raw не заменять. Скрипт отказывает при несовпадении хотя бы одного закреплённого input blob. Совпадение восьми из девяти файлов не даёт права считать весь расчёт свежим.

Для каждой метрики фиксировать объект, RowId set, числитель, знаменатель и сравнение ответа. Cold accuracy, constant-answer ceiling, input-function ceiling, TRAIN recall, address accuracy и ordinary answer accuracy — разные поля. Новизна определяется по фактическому input конкретного плеча: exact pair seen / input seen with target new / input unseen. При пустой или отсутствующей подгруппе вывод UNKNOWN/UNMEASURED, без подстановки нуля либо результата другого домена. Равные итоговые scores не означают одинаковых ответов.

**Полная цена исполнения** включает main setup, arm setup, controls, gradient oracle, corrective lessons, model readouts и restore. Пример: текущий P48 main имеет 4800 arm TrainStep + 1 oracle TrainStep; текущий P58 main — 105 TrainOnExample и 56 readouts. Это статический счёт названных Facts, не runtime-показание полного test class. Новый reporter считает реальные вызовы и выдаёт local/whole-run totals отдельно; дополнительные проверки не прячутся за словом «диагностика».

**Конечный статус — у внешнего исполнителя:** inner PASS не равен whole-run PASS. Build/discovery/setup/train/assert/restore/finalizer имеют собственные фактические исходы. После раннего exception, отмены или abort сохраняется неполный результат и уже выполненная доза; crash может не позволить самому test process записать finally, поэтому внешний runner обязан отличать отсутствие terminal от успеха. Недоступный запуск не меняет статус на PASS.

**Владение evidence начинается до работы:** один invocation получает атомарно захваченный run handle; непустой незавершённый каталог не становится свободным лишь потому, что git ещё не отслеживает его. Все writers используют этот handle. Неизменность опубликованных файлов и исключительное владение новой попыткой проверяются отдельно, без нового обучения.

Эти пункты добавляют точность существующим карточкам. Они не назначают массовый повтор опытов: исправление вычислимой сводки использует сохранённые строки, обычный regression имеет собственный бюджет, новая научная гипотеза — свой заранее определённый опыт.
