## Сначала выбрать средство запуска и ожидания

Исполнитель обязан пользоваться доступными skills/референсами и находить инструменты самостоятельно, а не спрашивать пользователя, каким тулом ждать или запускать команду. Это поиск средств выполнения **уже назначенного** рецепта, не выбор другого host, Student, модели агента, датасета или эксперимента.

1. Прочитать доступный в текущей сессии каталог инструментов: уже объявленные tools и их descriptions; если есть discovery/tool-search, искать по возможностям `process execution`, `wait/resume`, `process status/output`, `filesystem read`. Использовать реальное имя discovery API из текущей среды, не выдумывать `list_tools`/`tool_search`. Метаданные из инструкции тула — первичный источник о его параметрах.
2. Прочитать схему выбранного launch и wait/status: возвращаемый ID, признак незавершённой операции, terminal exit, длительность ожидания, отмена и судьба процесса после timeout. Найденная подсказка или имя инструмента без схемы не доказывают эти свойства. Если метаданных недостаточно, прочитать конкретный локальный reference; не обходить все skills повторно и не устанавливать новый плагин/SDK ради ожидания.
3. **До выдачи команды** выбрать ровно один поддерживаемый способ: асинхронный запуск с handle и bounded wait/resume; либо документированный синхронный запуск, если его лимиты действительно покрывают разрешённую операцию и требования отзывчивости. Если провайдер не сохраняет процесс после timeout, не использовать его для долгой операции, полагаясь на retry. Выбрать уже доступный provider, поддерживающий такой запуск; при отсутствии — назвать точный неподдерживаемый контракт после проверки доступных средств.
4. В уже назначенном журнале/отчёте сохранить `tool_wait_binding`: provider и имена tools, откуда прочитана схема, поле handle, ongoing/terminal markers, смысл timeout/yield, точные H/R/entry, момент выдачи и experiment deadline. После запуска дописать фактический handle и известные PID/start time. Отдельный новый result-root для этой записи не нужен. Модель исполнителя — default сессии, без override.

Умение найти tool не разрешает запустить опыт в исследовательской фазе. В нынешнем поручении выполняется только чтение источников и правка карточек.

## Одна выдача; ожидание и результат в том же задании

`NOT_ISSUED → ISSUED(handle) → WAITING → TERMINAL(exit) → READ_RESULT → REPORT`.

**ISSUED и WAITING не являются основанием закончить ход.** После ответа «running» следующий шаг — штатное ожидание исходного handle, а после terminal — чтение результата. Финальный ответ «запустил, жду уведомления / доложу потом» обрывает работу и запрещён. Краткое необходимое сообщение о состоянии идёт в commentary с продолжением ожидания в том же активном ходе. Не повторять сообщения «жду» на каждом timeout и не задавать вопрос «продолжать ли ждать».

- Launch — ровно один раз. Сохранить **тот ID, который вернул этот provider**. Session ID, exec cell ID, terminal ID и OS PID не взаимозаменяемы; PID также проверяется по времени создания.
- При running/yield/частичном stdout использовать документированный блокирующий/event wait/resume **того же handle**. Выбирать наибольший поддерживаемый интервал в пределах60секунд и оставшегося experiment deadline, чтобы не тратить вызовы на мелкие интервалы. Если после реального ожидания ответ running, продолжать тот же wait. Тихий этап без stdout нормален.
- Два одинаковых быстрых неблокирующих status/read подряд — сигнал прекратить этот способ и перейти в настоящий wait. Это предел аварийной диагностики, **не инструкция регулярно опрашивать дважды**. Мгновенная ошибка, невалидные аргументы или пустой ответ не являются ожиданием: прочитать схему и сменить неисправный способ наблюдения. Нормальные блокирующие wait не ограничены двумя.
- При неисправности канала один раз выполнить конечную независимую диагностику из контракта30, затем вернуться к ожиданию живой операции. Не перезапускать entry и не обнулять deadline. Не вводить Start-Sleep в занятый терминал.
- После terminal-события сразу получить статус/exit исходной операции и прочитать назначенные raw/stdout/stderr. Если провайдер завершает дочернюю задачу отдельно от внешнего wrapper, проверить именно назначенную цепочку по binding. Уведомление об окончании вспомогательного waiter не доказывает завершение опыта. Затем составить назначенный отчёт с раздельными execution/learning/hypothesis statuses; ожидание не подменяет проверку обучения.
- Прямой STOP/NEXT Любы имеет немедленный приоритет. При доказанном внешнем блокере или вынужденном прерывании не объявлять успешное завершение: указать INCOMPLETE и точный handle/известное состояние/отказ. Не обещать автоматическое продолжение, которого среда не гарантирует. Само отсутствие stdout или полезной параллельной работы блокером не является.

### Auto-notification не заменяет ожидание

Фраза инструмента «you will be notified» сообщает о событии, но сама по себе не подтверждает, что после final модель возобновится и прочитает результат. До запуска прочитать документированный способ **получения и обработки** этого события в текущей сессии: штатный event wait/resume либо поддерживаемая приостановка и продолжение активной задачи. Технический yield такого механизма не равен финальному пользовательскому отчёту. Не утверждать «уведомление вооружено, поэтому это не остановка» без подтверждённого continuation-контракта.

Если инструмент запрещает poll файла или sleep, соблюдать запрет. Не обходить его циклом Bash/PowerShell, новым фоновым waiter, timer→status polling или вторым monitor. Утверждение «блокирующего инструмента нет» требует проверки реального каталога, deferred discovery и подходящего reference; не придумывать названия API. Если ни один доступный механизм не позволяет наблюдать завершение и продолжать работу, до запуска выбрать другой **уже доступный** поддерживаемый launch/wait provider. Если операция уже выдана — сохранить её handle, использовать разрешённый канал наблюдения; при доказанной невозможности честно обозначить конкретный блокер и INCOMPLETE. Не выдавать это за «тихое ожидание», не повторять запуск и не просить пользователя выполнить его заново.

### Ожидание не создаёт новой работы и нового расхода

Во время WAITING выполнять только штатное ожидание, необходимую конечную диагностику его отказа и обработку новых указаний Любы. **Не придумывать себе работу:** не писать pair-summary-report.py, новые manifest/receipts, дополнительные анализаторы или документацию; не переходить к другим карточкам и не запускать агентов «пока ждём». Наличие требования к итоговому отчёту не разрешает создавать новые инструменты в это время. Если подготовка конкретного артефакта уже явно включена в рецепт, выполнить её в назначенной фазе; использовать существующие средства чтения после terminal. Обычная тишина во время реального wait — правильное поведение.

Не создавать фоновые bash/PowerShell-loop waiters, периодические monitors/watchdogs, оповещения каждые N шагов или расписания пробуждений. Замена монитора вторым фоновым waiter сохраняет ошибку, если исполнитель снова завершает ход. Остановка лишнего наблюдателя сама по себе не завершает ожидание исходного опыта; не путать его ID с run handle. Не останавливать и не перезапускать опыт ради удаления наблюдателя. Эти прямые указания Любы имеют приоритет над историческими рекомендациями о heartbeat/watchdog или «полезной работе параллельно»; не требуется менять skills или AGENTS.md.

## Три разных предела времени

| Предел | Что он означает | Что нельзя заключать |
|---|---|---|
| `yield_time` / длительность одного wait | Когда инструмент возвращает управление, возможно с живым handle | Что процесс завершился или его надо запустить снова |
| RPC/transport/tool timeout | Канал вызова перестал ждать; судьба дочернего процесса определяется схемой provider | Что Train не начинался, процесс убит или нужно выбрать `results-02` |
| Experiment/phase deadline карточки | Максимальное время уже назначенной работы, включая её объявленные этапы | Что его можно обнулить новым handle либо сократить TRAIN до двух минут ради удобства tool |

После timeout проверить собственный handle/PID/exit и прямые файлы. Если tool документированно убивает процесс при timeout, подтвердить terminal состояние; если семантика неизвестна, сохранить `OUTCOME_UNKNOWN`, не объявлять never-started. Новый25-минутный синхронный запуск не является продолжением старого background run. Перейти к другому каналу **наблюдения** того же процесса можно; повторить entry под видом диагностики нельзя.

Terminal exit и существующий результат проверяются вместе. Partial JSON, file existence, completed build, пустой log или atomic claim не подтверждают успешного обучения. Ошибка канала чтения не доказывает «файлы отстают на десятки минут»; утверждать внутренний cache bug или жёсткий2-минутный лимит без референса/наблюдения нельзя. Нужны факты: command issue time, handle, фактический elapsed, stage, exit, direct filesystem metadata и источник сообщения об ошибке.

## Точная привязка для инструментов Codex этой сессии

Это прочитанные схемы текущих tools, **не** Kiro API и не доказательство их доступности у другого исполнителя.

| Что вернул инструмент | Чем продолжать | Обязательное ограничение |
|---|---|---|
| `exec_command`: `session_id`, процесс ещё работает | `write_stdin` с тем же `session_id`, пустым `chars` и поддерживаемым `yield_time_ms` не более60000 | Пустой ввод ожидает/читает; не посылать launch/Start-Sleep в stdin работающего процесса |
| `functions.exec`: `Script running with cell ID ...` | `functions.wait` с тем же `cell_id`, ожиданием не более60000ms | Только после такого ответа; не передавать ему process session_id и не повторять исходный exec |
| Действующий research worker | `collaboration.wait_agent` с ограниченным timeout, затем прочитать пришедший packet/status | Timeout ожидания не означает завершение worker; не запускать второго при действующем лимите одного |
| `clock.sleep` существует в каталоге | Не выбирать его вместо доступного process wait | Timer не сообщает terminal-состояние; запрещён при provider no-sleep и не оправдывает timer→status polling |

Для `exec_command` поле `yield_time_ms` ограничивает первое ожидание, а возврат `session_id` означает необходимость продолжения через `write_stdin`. Ни отсутствие stdout, ни ранний возврат с session_id не означают остановку. Для `functions.wait` prerequisite прямо указан в схеме: только `Script running with cell ID ...`. Эти различия надо прочитать **до**, а не угадывать после запуска.

5. После фактически выданной операции обещать «теперь запущу синхронно» без установления судьбы прежней. Нельзя повторно запускать команду только для получения более удобного вывода.

При настоящем внешнем блокере указать конкретный provider/tool/операцию, прочитанную семантику, фактический отказ и исчерпанные доступные read/wait альтернативы. Обычный выбор инструмента и ожидание исполнитель выполняет сам. Отчёт — русский в назначенном R/report.md, с раздельными execution/learning/hypothesis statuses по контракту30.
