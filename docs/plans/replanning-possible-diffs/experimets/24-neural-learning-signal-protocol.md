## Общая формула: вся response, полный vocabulary, без усечения первым byte

Основание: [native Evaluate:956](C:/Projects/llm_mvp_core/11.DPO/DpoTrainer.cs:956), [shift/mask:1033](C:/Projects/llm_mvp_core/11.DPO/DpoTrainer.cs:1033), [DpoBatch](C:/Projects/llm_mvp_core/11.DPO/Models/DpoBatch.cs), [SFT host Observe:142](C:/Projects/llm_mvp_core/experiments-v2/RP01-MICRO/LEARN-SANITY-PROBE/Program.cs:142). Последний применим буквально только к одно-byte `+`/`-`; ниже задан общий ответный контракт, не копирование `Bytes(answer)[0]`.

1. **DPO:** использовать уже подготовленные и скопированные `ChosenIds`/`ChosenResponseMask`/`ChosenMask` конкретной пары. Не создавать новый admission, не вызывать повторный Prepare/Save/Load/hash tokenizer ради панели. Response weight позиции j — произведение двух исходных masks. Отсутствующая response mask у этих exact карточек — ошибка протокола; не заменять полнострочной маской. В TS01 A0/B0 читать после единственного назначенного Prepare и до StepVector; Prepare-cost уже закончился. В остальных DPO — после обычной подготовки уроков. B trim/head оптимизации действуют в training; diagnostic читает обычный полный causal Forward одинаково в обоих arms.
2. **SFT canonical BPE:** использовать joint native IDs `Encode(Prompt+LF+Response)` при обычной подготовке каждого указанного урока, затем удерживать их неизменными. Прочитать **уже назначенный** tokenizer JSON `Vocab` (base64 bytes по token ID), как в [MASK](cards/E-SFT-RESPONSE-MASK.md). Cumulative pieces должны восстановить strict UTF-8 joint bytes. Ответ начинается с `UTF8ByteCount(Prompt)+1`. Diagnostic weight токена = доля bytes токена, попавшая в response; prompt/LF weight=0. Это только одинаковая readout маска, не изменение training objective, не новый MASK_BOUNDARY_CROSSING gate для STATE/ORDER. Исходное правило отказа crossing в MASK-факторе сохраняется. **Отдельная RMS byte-ветка:** исходный sign learner обучается на `UTF8(Prompt+Answer)` БЕЗ LF; каждый ID — byte, response-start=`UTF8ByteCount(Prompt)`. Не добавлять разделитель: это изменило бы проверяемый контекст. Для сохранённых N63I/N63R scorer contracts служат только историческим описанием: ничего не добавлять и не пересчитывать моделью. Не выдавать эти разные диагностические denominators за одну и ту же метрику между карточками.
3. Каждый readout row даёт **один** `model.Forward(tensor, training:false)`. DPO full ids имеют форму `[1,T]`, logits `[1,T,V]`; target `ids[i+1]` оценивается по logits row i, i=0..T−2, weight=mask[i+1]. SFT вход — IDs без последнего token, как в native Trainer; targets сдвинуты на один. Target weights выровнены по тем же исходным IDs. Не добавлять второй Forward вызовом EvaluateAverageNextTokenLogProbability после уже полученных logits. В будущем N63C заменить тело existing scorer readout так, чтобы **из одного и того же forward** вернуть и прежний score, и новые поля; число вызовов не меняется.
4. На каждой позиции с weight>0: argmax полного V, tie выбирает меньший token ID; `gold_rank=1+count(logit>gold_logit)`; stable `NLL=max+log(sum(exp(logit−max)))−gold_logit`. Все значения finite. Выводить raw per-position predicted/gold/rank/weight и weight-normalized mean NLL/rank. **Существующий scorer сохранить буквально, включая знак и разрядность. N63I:** исходный double Score, Math.Exp/Math.Log, responseSum/denominator и уже положительный loss — без преобразования во float. **N63C:** native ComputeTargetLogProbs использует MathF/float; сохранить mask weights, denominator и accumulation order. Его результат — mean logP; прежний NLL = МИНУС этот scalar, margin=chosen−rejected. В новое NLL поле писать положительный NLL, не сам отрицательный logP. Получить logits один раз, сохранить прежнее значение и добавить rank/exact. Для новых standalone диагностических рядов stable double вычисление описано формулой выше и помечается отдельной диагностической метрикой. `teacher_forced_response_exact` истинен только при совпадении всех оцениваемых gold IDs. Это teacher-forced token/response показатель, не свободная autoregressive генерация. Rank1 при tie не равен exact. Mask sum0, invalid IDs, shape или nonfinite — `INVALID_LEARNING_READOUT`, не ноль и не новый набор данных.
5. Observer не меняет model, optimizer, RNG, dropout или cache settings. Не вызывать training:true, backward, ApplyOptimizer, restore или неявный Train в diagnostic. Если конкретный фактор добавит сохраняемый inference cache, его бесплатное наполнение readout до TRAIN недопустимо: такой новый фактор требует отдельной авторской правки. Текущие активные DPO факторы не являются LFT frozen-transpose cache; будущий результат LFT старым протоколом не обновляется.

## Заранее заданный вердикт и бюджет

До/после каждого arm показать TRAIN meanNLL, meanGoldRank, top1 counts и whole teacher-forced response exact; EXAM отдельно. Если правильных response-токенов/ответов нет ни до, ни после, учебный вердикт — `LEARNING_VERDICT_INVALID_ZERO_TO_ZERO`: снижение NLL/rank записывается как наблюдение, а не усвоение урока или сохранение навыка. Измеренные механические и ресурсные результаты сохраняются отдельно с прежними ограничениями сопоставимости. Если есть ненулевое правильное поведение, назвать его точную единицу: отдельные токены, целые ответы или условное правило. Ухудшения других строк/метрик рядом; нет автоматического вывода «алгоритм сломан» и нового обучения до PASS.

Для sign exact сообщить constant-sign baseline 1/2 на каждой сбалансированной двухстрочной панели. Сохранённый sanity `+,+` на TRAIN и `−,−` на EXAM этот baseline не превысил: learned conditional sign rule не доказано. Улучшение NLL/rank и полезная экономия ресурсов остаются самостоятельными ограниченными результатами. Для других карточек не переносить sign baseline или заключение об обученности другой модели.

В каждом raw и русском report явно разделить `actual_optimizer_updates`, `training_forward/backward`, `diag_train_forward`, `existing_exam_forward`, Generate и resources. Новая панель не называется бесплатной, не включается в число updates и не маскируется словом «проверка». Старые числовые бюджеты — авторские рецепты, а не установленный Любой предел. Её требование — минимальный набор с измеримым реальным обучением. Точные старт/данные/schedule карточки сохраняются: acquisition и resource измерение не требуют заранее обученного checkpoint. Retention/restore вывод требует положительного before именно перед вмешательством; без него RETENTION_NOT_ESTABLISHED. Дополнительная общая подготовка требует отдельного точного авторского назначения и счёта, здесь она не добавляется. Произвольно увеличивать steps, менять модель/данные или копировать чужую кривую исполнителю нельзя. Сохранённые попытки и отдельные уже выполненные probes не расширяются и не запускаются повторно.

## Защита от скрытого повторного обучения

Подготовка до запуска хранит source/data manifests и study blueprint только в назначенном host/source-root; **не** создаёт result-root ради паспорта. Result-root и его create-new study.json принадлежат единственной execution chain после раннего absence check/host claim и до learner/Train. Если прежний полный runner сам создаёт results/study, wrapper не делает это второй раз. Таким образом первая разрешённая команда не отвергает собственную преждевременную подготовку как старый результат.

До build проверить result-root, затем в назначенном host-root атомарно открыть `execution.claim` через FileMode.CreateNew с ID, result-root и временем. Claim сохраняется при ошибке и не удаляется ради перезапуска. Если путь существует — `ALREADY_STARTED_NO_RERUN`, без build/Train и без третьего каталога. Этот claim принадлежит единственной внешней команде, управляющей заданными A/B; дочерние arms его не переоткрывают. Внутри каждого нового arm-out до загрузки learner/Train создать собственный `training.claim` с CreateNew. Claim-файлы — явные будущие файлы малого host, не модификация продукта; создать их при подготовке этой документации нельзя. Если карточка уже имеет более строгую эксклюзивную блокировку **до** любых runtime effects, сохранить её и записать эквивалентность, не строить второй launcher.

Полностью записать/закрыть script перед запуском; зависимые операции не распараллеливать. Если процесс уже выдан, наблюдать тот же ID до exit; при неизвестном исходе `PROCESS_OUTCOME_UNKNOWN`, никакого restart. Отсутствие stdout и поздний CreateNew не доказывают отсутствие Train. Скрипты старого sanity не исправляются этим документом и не исполняются повторно. При немедленном stop/переходе не задерживаться ради этих файлов или отчёта; сохранить уже известный статус.
