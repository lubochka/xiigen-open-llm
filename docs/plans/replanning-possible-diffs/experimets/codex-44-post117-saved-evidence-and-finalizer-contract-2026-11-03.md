Для уже записанного PRIMARY первым действием является анализ существующих raw/state/receipt. Новый запуск ради исправления отчёта, JSON, verifier, индекса или пропущенной квитанции не назначается.

## 2. Назвать весь путь и границу доказательства

Карточка до изменения содержит конкретные producer → преобразование → learner/state → ordinary reader → restore reader с именами методов/файлов. Для source-linked host перечисляется, какие продуктовые `.cs` включены в ту же assembly; доступность internal проверяется по compile graph. Отдельный host не объявляется full-product build/DI/interface acceptance.

Сохранённый ожидаемый журнал и actual export имеют разные роли. Hash доказывает только те bytes, которые фактически хешировались. Считать записи недостаточно: сравнить exact IDs/keys, source/target, owner/namespace, порядок и кратности согласно schema. LFS pointer/OID — ссылка на bytes, не их новое прочтение. Поведение после восстановления оценивается новой машиной без Train, если такой native срез отдельно назначен.

## 3. Проверяющий должен отвергать конкретную подмену

У каждого обещания своя пара: honest positive и минимальная corrupt version с заранее заданным исходом. Испорченный материал идёт через тот же рабочий verifier, а не через отдельную демонстрационную ветку. Когда отказ — ожидаемое поведение, raw false означает успешный negative control лишь после сравнения с expected.

Обязательные правила:

- Actual, expected и tolerance имеют строгий тип, конечность и предметный диапазон; NaN и бесконечность не проходят из-за особенностей сравнения. Нельзя чинить провал расширением tolerance.
- Состав панели/owners/documents/channels задаётся independently expected keyset. Проверяются пропущенные **и лишние** элементы, duplicate IDs, exact cardinality и соответствие ID/данных. `Math.Min` не доказывает полное сравнение.
- Provenance связывается с фактически потреблёнными bytes и trusted identity своего объекта. Для переходов P116/E09/E43 это project+file+position обоих концов; для corpus snapshot — document ID/content и применимые tokenizer/revision; для DPO — actual material и реально переданные final preferences. Не требовать несуществующие project/position у другого владельца. Claimed hash/revision не является своим собственным доверенным эталоном.
- Corpus/state identity кодируется однозначно: length-prefix или строгая canonical schema, а не неэкранированный separator внутри пользовательского текста.
- Негативный пример должен достигнуть защищаемой ветви. Early refusal до создания кандидата не доказывает поздний CAS; different signature не доказывает same-cell guard; неизвестный кандидат не доказывает threshold на существующем.
- Один zero/constant baseline не заменяет предметный результат. Полный output, отрицание, время, роли и язык оцениваются по неизменному gold; path reached и confidence не являются точностью ответа.

Копируемая карточка называет собственные controls, а не только ссылается на эти общие правила.

## 4. Независимость включает подготовку, а не только финальную память

В ledger данных перечислены все стадии, которые чему-либо приспосабливаются: tokenizer/vocabulary, normalizer, encoder fit, выбор параметров, materialization, KNN, DPO, cache. У каждой есть разрешённый TRAIN/DEV/TEST split и actual consumed identity. Экзамен, увиденный tokenizer.Train, нельзя назвать полностью невиданным только потому, что его нет в финальном KNN corpus.

Обнаруженная историческая утечка сужает допустимый вывод; она не оправдывает смену gold или повтор старого PRIMARY. Чистый A/B расчёт стоимости при общей подготовке может оставаться полезным. Legacy материал без достаточной lineage помечается NOT_EVALUATED по этой оси; новый запрет всего обучения не выдумывается.

## 5. Единый итог из обязательных свидетельств

Список required check IDs задан доверенным назначением до чтения receipt. Каждый результат имеет expected/observed/verdict и ссылку на свидетельство. Missing, duplicate, unknown или failed mandatory check запрещает научный VALID. Не принимать receipt, которая сама выбрала удобный список обязательных проверок.

Разделять поля:

| Поле | Что оно утверждает |
|---|---|
| execution | Процесс и его стадия действительно завершены, исход известен |
| measurement_validity | Все обязательные проверки измерителя и материала выполнены |
| budget_status | Весь фактический расход соотнесён с исходными лимитами |
| hypothesis_status | Имеется ли ожидаемый полезный эффект, иной эффект или отрицательный результат |
| transfer_status | Что именно подтверждено в настоящем продуктовом consumer/restore |

Process exit0 не заменяет остальные поля. Законный отрицательный научный результат сохраняется и может считаться завершённым опытом; гипотезу не обучают до PASS. Честный локальный выигрыш при нарушенном budget описывается вместе с нарушением, а не стирается.

У каждого mandatory check есть отдельная чистая проверка: false, missing и unknown меняют общий verdict; honest positive остаётся успешным. «Всегда VALID» обязан провалить эту приёмку.

## 6. Receipt, стадии и дерево процессов

JSON должен иметь object root, обязательные типы и допустимые значения. `null`, array/string, `terminal="false"`, неверные source/attempt/stage и успешный build вместо run не допускаются. Свидетельство terminal принадлежит исходному handle/attempt. Повторный вход возвращает доказанный прежний исход и не перезапускает опыт по отсутствию красивого отчёта.

Ожидание/сроки следуют контракту31 и реальному tool API. Проверять дедлайн после синхронного завершения недостаточно. Остановка дерева и доказательство его завершения различаются: root.HasExited не доказывает потомков; ошибка наблюдения = UNKNOWN. Dummy child+grandchild и отказ observation проверяются отдельно, без модели. Живой запуск ожидается по исходному handle; новые waiter/PRIMARY не создаются.

## 7. Расход и позднее исправление

Сумма включает все physical attempts, warmup, calibration, retention, diagnostic instances и model/learning calls в helper. Обучить временную память для fingerprint — тоже обучение этой памяти. Отдельная категория implementation-control не делает вызов бесплатным. Neural steps и memory Learn учитываются раздельно, но оба учитываются.

При позднем сбое сохранить actual state/receipt и реальные счётчики; исправлять validation/report на этих данных. Saved-only режим не получает Train/Execute callbacks. Нет actual state — точный NOT_OBSERVED, а не реконструкция под видом измерения. Старые cap/PRIMARY/gold не расширяются задним числом.

## 8. Как записывать результат и перенос

Для каждой метрики: сохранённые до/после, знаменатель, единица, gained/lost, источник, причинная граница. Примеры этого аудита: P115156→4 — lexical calls, не вся inference; P1163→0 — незаконные пары, а +1control ещё включает replay; P1170→1 — достижимость памяти, при3/5 exact и пропущенном «сейчас».

Product `SOURCE_IMPLEMENTED`, исходник теста, исполненный native PASS и принятый restore — разные состояния. Не повторять уже написанный CAS/zero filter/schema fix; проверять его собственный оставшийся контракт. Все ненаблюдавшиеся native проверки остаются UNRUN.

## 11. Что делать, когда проверка падает

Сначала сохранить конкретный вход, ожидаемый исход, фактический исход, ошибку и версию кода. При документном поручении это анализ уже сохранённых свидетельств и план ремонта; команды ниже не назначают исполнение. При прямо разрешённом ремонте выполняются только назначенные проверки, с ожиданием исходного процесса до терминального состояния по договору31.

| Что обнаружено | Правильное действие | Что не считается исправлением |
|---|---|---|
| Тест вызывает удалённую или другую перегрузку | Сверить интерфейс, действующий метод и все call sites; назвать точный вызов для исправления. Например, версия оценки Translation передаётся в EvaluateAtVersionAsync; обычный EvaluateAsync сохраняет интерфейсный контракт | Добавить необязательный аргумент в интерфейсный метод лишь ради старого теста или объявить отдельный source-linked host доказательством сборки продукта |
| Правильный отрицательный контроль отвергнут | Сравнить наблюдение с независимым ожиданием. Для повреждённой расписки expected acceptance=false и observed acceptance=false означают пройденный контроль | Требовать, чтобы все исходные bool были true |
| Проверка видит повреждение, но общий результат успешен | Проследить verifier → итог → Run/Main → exit.json → runner/receipt; связать отказ с пригодностью и исходом приёмки. Исполнение процесса и научный результат остаются отдельными полями | Добавить warning, новую колонку отчёта или локальный assert, оставив внешнее принятие успешным |
| Новый корректный контракт делает старое ожидание неверным | Назвать изменённый договор и независимое основание нового ожидаемого значения; сохранить отрицательный контроль старого дефекта | Переписать expected из actual, снизить threshold/tolerance, Skip или удалить проблемную строку |
| Сломалась неизменная продуктовая гарантия | Чинить код владельца; старый правильный тест сохранить | Ослабить тест, чтобы он совпал с регрессией |
| Измеритель или fixture ошибочны | Исправить конкретную формулу/вход; сохранить прежний raw и датированную поправку; заново вычисляемый вывод пометить как derived | Объявить пересчёт новым ускорением или обучением, менять gold |
| Поздний сбой сериализации, отчёта, сборки или инструмента | Разделить стадии и actual counters. Сохранённое обучение не повторять; при ремонте отчёта работать без Train/Execute. Отсутствующее состояние обозначить NOT_OBSERVED | Выбрать новую results-NN, повторить все updates или сделать нулевыми уже потраченные вызовы |
| Проверка вообще не достигла нужной ветви | Указать ранний отказ и недостающий различающий вход; использовать только назначенный контроль, будущий runtime оставить UNRUN | Назвать ранний stale-entry отказ проверкой позднего CAS или exact ответ проверкой KNN |

Обязательная проверка после разрешённого ремонта: честный случай остаётся принятым; собственный повреждённый случай отвергается; отсутствие обязательного наблюдения не даёт успеха. Затем проверяется соответствующий обычный потребитель и, если назначено, загрузка. Число тестов не заменяет эти исходы. Источник теста означает «проверка написана»; слова «упал/прошёл» требуют сохранённого результата исполнения именно этой версии.

Это конкретные условия будущей приёмки соответствующих владельцев. Они не расширяют обучающую панель, не требуют всех чужих fixtures в каждом опыте и не объявляют уже исполненными новые проверки. Новый контроль с моделью требует собственного заранее назначенного бюджета. Чистая проверка связанного с обучением измерителя не обязана сама обучать модель, но не называется новым учебным экспериментом.
