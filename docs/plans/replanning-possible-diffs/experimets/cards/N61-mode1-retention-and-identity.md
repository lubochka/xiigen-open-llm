## Обязательные правила для карточки и любого её промпта

**Найти tool и дождаться своей операции — обязанность исполнителя.** До выдачи команды прочитать [контракт31](../31-tool-discovery-and-wait.md) и указанные там реальные skills/references; по каталогу текущей среды найти launch и wait/resume/status, прочитать их схему и сохранить provider, handle, start time, H/R и deadline. Не выдумывать Kiro API по Codex-примеру, не просить пользователя выбирать инструмент или запускать команду вместо исполнителя.

**Ожидание не равно бесполезному polling.** Одна выдача entry; затем штатный bounded wait/resume того же session/cell/process ID до terminal exit или исходного experiment deadline. Нормальный wait можно повторять при silent/running. Два быстрых неблокирующих чтения без прогресса требуют перейти в wait; если он неисправен/ответы противоречат — независимое чтение H/R/claim/exit и своего PID+start. Не вводить Start-Sleep в занятый терминал. Предел одного ожидания≤60с — не предел эксперимента; yield/RPC timeout не доказывает exit/kill/нулевой расход. После диагностики живой процесс продолжают ждать. Отсутствие log не доказывает, что запуска не было. Не выдавать entry заново «синхронно на25минут», не подбирать results-NN, не удалять claim/partial, не сокращать TRAIN/steps до двух минут ради tool. При UNKNOWN сохранять неизвестный расход и разбирать существующий запуск. STOP/NEXT Любы немедленны.

**Не завершать ход на ожидании и не придумывать работу.** ISSUED/WAITING → штатный блокирующий/event wait исходного handle → terminal/exit → чтение назначенных raw → отчёт. Финальное «жду уведомления / доложу потом» до результата запрещено; обещание auto-notification не доказывает возобновление. Не создавать фоновый waiter/monitor/watchdog, циклы polling, progress-события каждые N шагов, summary scripts, manifests или другую работу «пока ждём»; не запускать агентов или следующую карточку. Обычное ожидание не требует заполнения паузы работой. Соблюдать provider no-poll/no-sleep. Проверить настоящий wait/continuation в каталоге до launch; при отсутствии доказать конкретный блокер, сохранить handle и INCOMPLETE, без выдуманного API или relaunch. STOP/NEXT Любы немедленны. Полный порядок и исключения — [контракт31](../31-tool-discovery-and-wait.md).

**Без действительного обучения задача не выполнена.** Для каждой новой экспериментальной программы, включая diagnostic/reader/restore, обязателен назначенный реальный учебный участок: original файл/метод, learner→изменённое состояние→обычный consumer, точные TRAIN/EXAM, before/after и конечный бюджет. Сохранённый обученный S0 является стартом, но не заменяет этот участок. Для retention/restore навык проверяется до вмешательства; для acquisition допустим cold start с приобретением поведения. Ноль обновлений допустим у отдельного контрольного плеча или reader после общего Train, но не у всей новой программы. Unit/BPE действительно обучают память/правила; neural updates=0 у них не означает отсутствие native Train. Updates, loss, hash и случайный верный токен сами по себе не доказывают навык; 0→0 не является учебным результатом, частичные токены не объявляются целым ответом. Исторический безучебный receipt сохранить; его повтор получает отдельный назначенный рецепт по оригиналу и новый output, а не считается завершённым новым опытом. Уже выполненный учебный участок этой же попытки не повторять ради счётчика после сбоя отчёта; продолжить его сохранённые stages. Отдельная unit-проверка готового receipt не является новым экспериментом обучения. Полный охват карточек и адресные рецепты — [37](../37-full-catalogue-learning-coverage.md).

**0 → 0, отсутствие обучения или неполное A/B — не завершение эксперимента.** Раздельно записать execution_status, learning_validity и hypothesis_status; при невалидности учебная цель OPEN. Сохранить сырые свидетельства и продолжить разрешённое исправление постановки, а не только написать «невалидно» и отчитаться об успехе. Не искать другой checkpoint/модель/host, не менять seed/фактор, не увеличивать steps до PASS: точный исправленный рецепт назначает автор карточки до новой попытки. Старые опыты не удалять. Поздняя ошибка сохранения не обнуляет состоявшиеся updates; неизвестное число — null, невыполненное плечо — «не измерено».

Любое полезное измеренное улучшение в **валидном учебном сравнении** — успех своей метрики/домена; рост accuracy необязателен, регрессии рядом. Диагностика невалидной постановки не закрывает учебную цель. Default-модель исполнителя без override; точные H/R/entry ниже. Отчёт — русский R/report.md. Текущая правка документов не разрешает runtime. Прямые STOP/NEXT Любы немедленны и при открытой цели.

Полный конечный порядок диагностики и критерии: [контракт30](../30-failure-recovery-and-learning-validity.md). При конфликте со старым текстом ниже действует этот блок.
**Состав данных ограничивает вывод.** До запуска автор задаёт точные TRAIN/EXAM/CONTROL, покрытие классов, роли отрицательных примеров, семьи/пересечения и конкретный контроль постоянного ответа. Одноклассовый TRAIN и выигрыш на его единственной метке не доказывают различение маршрутов; updates/confidence не заменяют этот контроль. Разные опыты не устанавливают причину регрессии состава данных. Измерять любой исход, не предписывать ухудшение; набор и budget исполнитель не меняет сам. Полное обязательное правило — [состав данных и допустимый вывод](../32-training-set-and-inference-contract.md).

**Сохранённый учебный результат используется без повторного выбора.** В уже разрешённой фазе исполнения пригодные сохранённые веса/обученное состояние имеют приоритет: восстановить их и продолжить назначенный опыт, не спрашивая «A: использовать результат или B: обучить заново». Поздняя ошибка проверки, сериализации или отчёта сама по себе не основание повторять Train. Сначала прочитать актуальные receipts и установить, не выполнены ли recovery/плечи уже; состоявшуюся работу не переиздавать. Проверять только необходимую для следующего шага совместимость и учебную квалификацию, используя имеющиеся данные; недостающие показания получать лишь по явно ограниченному recovery-рецепту, без optimizer updates и без притворного восстановления отсутствующих moments/RNG. Если пригодность доказана, выбрать reuse автоматически. Если объективно отсутствует необходимое состояние, назвать конкретный технический пробел; не предлагать повторное обучение «для чистоты», не просить пользователя снять guard и не выдавать размер файла/падение loss за доказательство выученного навыка. Текущая документная фаза запусков не разрешает.

**Реализация не отменяет контракт.** «Код не читает RNG/optimizer/проверку» означает отклонение, а не разрешение его игнорировать. До следующего model call исправить реализацию в уже разрешённом scope либо применить только явно назначенный в карточке совместимый режим восстановления; не придумывать исключение, не просить снять guard и не переносить weights-only DPO-исключение на SFT continuation.

Оценщик получает raw `OrchestrationGenerationResult` **после** `GeneratePlanAsync`. Для положительного задания он проверяет одновременно:

1. `RouteMode == LearnedFlowGrounding`, classifier/boundary и ожидаемый `FlowGrounding.FlowRef`.
2. Upper-case строку `FLOW_REF=...` в блоке, созданном `SerializeChosen`, отдельно от нижнего `flow_ref=...`.
3. Тело после следующей строки `TITLE=...`: оно должно совпасть с заданным ниже Chosen body после нормализации только пробелов/переносов.

Совпадение flow ID без правильного тела не считается правильным ответом. В этой узкой задаче ожидается воспроизведение выученного плана; рубрика не заявляет языкового обобщения или исполнения этих действий. Gold не передаётся в learner, classifier, retrieval или renderer.

Для отрицательного запроса правильны `RouteMode == Mode2Generalization`, отсутствие `FlowGrounding` и отсутствие выданного блока `FLOW_REF=LAB-A/LAB-B`. Не требовать сочинения правильного плана резервного копирования от необученного Mode2. Ошибка `OperationResult` — отдельная ошибка пути, не допустимый fallback.

```csharp
public OrchestrationTrainingPair? FindNearest(
    string prompt, PairMode? mode = null, string? flowRef = null)
    => FindNearestWithScore(prompt, mode, flowRef)?.Pair;

public OrchestrationNearestPair? FindNearestWithScore(
    string prompt, PairMode? mode = null, string? flowRef = null)
{
    var promptTokens = Tokenize(prompt).ToHashSet(StringComparer.OrdinalIgnoreCase);
    return _pairs
        .Where(pair => (mode is null || pair.Mode == mode) &&
            (flowRef is null || string.Equals(pair.FlowRef, flowRef, StringComparison.Ordinal)))
        .Select(pair => new OrchestrationNearestPair(
            pair,
            Jaccard(promptTokens, Tokenize(pair.Prompt).ToHashSet(StringComparer.OrdinalIgnoreCase))))
        .OrderByDescending(item => item.Score)
        .ThenBy(item => item.Pair.PairId, StringComparer.Ordinal)
        .FirstOrDefault();
}
```

1. `static async Task<int> Main(string[] args)` принимает ровно `--contrast RETENTION|IDENTITY --arm A|B --output <absolute-new-directory>`. Проверяет соответствие аргументов AssemblyMetadata. При существующем output отказывает, ничего не затирая.
2. `BuildLessons(contrast)` создаёт только перечисленные typed пары. `BuildExam(contrast)` возвращает только таблицу query/gold этой карточки. Данные зашиты literal-строками в runner; `SourcePath` содержит `simulation`, без имени teacher-модели. Никаких внешних авторов/загрузок.
3. Создать ровно `new OrchestrationPlanMachine()` для выбранного плеча. Чужую сборку другого плеча не загружать. Начальные размеры/IDs должны быть пустыми; записать `ExportCheckpoint`.
4. RETENTION: два раза `await machine.TrainOrchestrationBatchAsync(singlePairBatch)`; проверить `IsSuccess`, записать возвращённые RowsTrained/TrainedPairIds; snapshot A0/B0; четыре `await machine.GeneratePlanAsync(query)`; третий такой Train; snapshot A1/B1; четыре Generate. IDENTITY: после empty snapshot три Generate; два Train; final snapshot; три Generate.
5. В каждом ответе сохранить полный `OperationResult` и `OrchestrationGenerationResult`, не только verdict. Native `.Value` читать только после `IsSuccess`. Счётчики принадлежат wrapper вокруг этих вызовов, не берутся из написанного заранее ожидаемого числа.
6. `Grade(result, gold)` работает после ответа по рубрике выше. Не вызывать `EvaluateAsync`: он использует другую рубрику и изменяет `_lastEvaluationGate`. Не вызывать дополнительный nearest/Generate для отчёта. Выбранное тело/FlowRef берутся из уже полученного PlanText; source PairId сопоставляется с сохранённым Chosen. Если нескольким PairId соответствует одинаковое тело, записать все совпавшие IDs, а не выдумывать единственный выбранный PairId. В RETENTION это касается `10-a1` и `20-a2`.
7. Snapshot сериализовать обычным `System.Text.Json` с `OrchestrationPlanJsonOptions.Standard`; raw сохраняется целиком. Для отдельного semantic hash исключить только `ExportedAtUtc`, сортировать ключи maps/списки identities; численные значения, pairs, version и progress не исключать. В IDENTITY semantic state должен совпасть A/B; в RETENTION до третьего урока — тоже, после него различия input weights ожидаемы.
8. Записать через `FileMode.CreateNew`: `raw-answers.json`, `states.json`, `training-receipts.json`, `costs.json`, `run-receipt.json`; manifest копируется в новый output без перезаписи. `run-receipt` включает фактические args, assembly path, PID, timestamps, counts и completion. При ошибке сохранить `failure.json` и уже полученные данные, return 1; никакого автоматического retry или трактовки ошибки как 0%.
9. После двух выбранных плеч подготовить один человеческий `report.md` из этих JSON без новых вызовов learner/consumer. Полная таблица 16 либо 12 ответов и все costs обязательны; дополнительные исполнения для красивой статистики не предусмотрены.

Малые функции `BuildLessons`, `BuildExam`, `Grade`, `MeasureAsync` и создание JSON — заданный glue runner. Они не меняют модель, не подставляют gold и не имитируют native learning. Фиксированная проекция источников и этот glue — весь объём подготовки; не редактировать `.csproj` проекта 35, dispatcher, продуктовые классы или общие навыки. Отсутствие готового Program сейчас — работа подготовки, а не требование Любе найти команду.

## Измерения и человеческий отчёт

`MeasureAsync` измеряет только выбранный настоящий Train либо Generate: `Stopwatch` wall time и разность `Process.TotalProcessorTime` на границах вызова. Снимки `GC.GetTotalMemory(false)` подписать **managed heap**, `Process.WorkingSet64` — **текущий working set**, `Process.PeakWorkingSet64` после raw-save — **наблюдаемый peak процесса этого плеча**, включая startup/JIT/сохранение до этой точки. Это не peak конкретного Train.

Не использовать `GetAllocatedBytesForCurrentThread` через произвольный `await` без доказанной привязки потока. Если нужны allocation bytes, для этого фиксированного runner использовать дельту `GC.GetTotalAllocatedBytes(precise: true)` вокруг вызова и явно подписать process-wide managed allocations с overhead; не смешивать её с RSS. Никакого `GC.Collect`, прогрева или повторов. Однократные значения могут оказаться неразличимыми; это честная граница измерения, не запрет признавать локальный полезный эффект.

Нативное поле `CpuMs` в этом writer содержит elapsed `TickCount64`, а `PeakRamMb` — snapshot managed heap. Сохранять его как native-reported value, но для CPU/RAM выводов использовать явно названный измеритель. Переименование поля само не является speedup. Время serialization, snapshot/hash и процесса записать отдельно; не суммировать полный процесс со своими вложенными этапами.

| Срез | Контроль до → после | Изменение до → после |
|---|---|---|
| Каждый ответ, его body/FlowRef/route и правильность | Не измерено | Не измерено |
| Retention RQ1; acquisition RQ2 / IQ1; сохранение LAB-B | Не измерено | Не измерено |
| Wrong learned acceptance на отрицательном запросе | Не измерено | Не измерено |
| Wall/CPU настоящих Train и Generate, по вызовам | Не измерено | Не измерено |
| Managed allocations, heap snapshots, RSS, process peak | Не измерено | Не измерено |
| KNN rows, unique FlowRef, input feature keys, JSON bytes | Не измерено | Не измерено |
| Нейронные слои и optimizer | 0 → 0 | 0 → 0 |
| Уровни: machine / grounding model / KNN / composer; Flow wrapper | Те же 4 компонента, wrapper 0 вызовов | Те же 4 компонента, wrapper 0 вызовов |

Структура не растёт в число «нейронных слоёв» из-за большего числа ключей. Для retention цена merge — возможный рост feature keys/bytes; для identity — дополнительная фильтрация кандидатов. Любая другая полезная измеренная ось также признаётся по своему смыслу.

**GOOD, иллюстрация без измеренных чисел:** «В RETENTION новый урок дошёл до Train. В контроле старый запрос начал получать план LAB-B, а merge сохранил LAB-A; при этом таблица признаков стала больше. Новый парафраз и отрицательный запрос показаны рядом». Или: «В IDENTITY обе обученные памяти одинаковы, но один consumer читает чужое body; фильтр исправил доставку уже усвоенного approval-плана. Это не изменение LoRA».

**BAD:** «KnnSize вырос — значит навык удержан»; «исправили напечатанный FlowRef — значит ответ правилен»; «память стала больше, поэтому полезного результата нет»; «CpuMs меньше — доказано меньше CPU»; «нужны ещё 200 повторов для допуска».
