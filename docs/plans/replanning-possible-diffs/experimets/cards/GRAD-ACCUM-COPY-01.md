## Обязательные правила для карточки и любого её промпта

**Найти tool и дождаться своей операции — обязанность исполнителя.** До выдачи команды прочитать [контракт31](../31-tool-discovery-and-wait.md) и указанные там реальные skills/references; по каталогу текущей среды найти launch и wait/resume/status, прочитать их схему и сохранить provider, handle, start time, H/R и deadline. Не выдумывать Kiro API по Codex-примеру, не просить пользователя выбирать инструмент или запускать команду вместо исполнителя.

**Ожидание не равно бесполезному polling.** Одна выдача entry; затем штатный bounded wait/resume того же session/cell/process ID до terminal exit или исходного experiment deadline. Нормальный wait можно повторять при silent/running. Два быстрых неблокирующих чтения без прогресса требуют перейти в wait; если он неисправен/ответы противоречат — независимое чтение H/R/claim/exit и своего PID+start. Не вводить Start-Sleep в занятый терминал. Предел одного ожидания≤60с — не предел эксперимента; yield/RPC timeout не доказывает exit/kill/нулевой расход. После диагностики живой процесс продолжают ждать. Отсутствие log не доказывает, что запуска не было. Не выдавать entry заново «синхронно на25минут», не подбирать results-NN, не удалять claim/partial, не сокращать TRAIN/steps до двух минут ради tool. При UNKNOWN сохранять неизвестный расход и разбирать существующий запуск. STOP/NEXT Любы немедленны.

**Не завершать ход на ожидании и не придумывать работу.** ISSUED/WAITING → штатный блокирующий/event wait исходного handle → terminal/exit → чтение назначенных raw → отчёт. Финальное «жду уведомления / доложу потом» до результата запрещено; обещание auto-notification не доказывает возобновление. Не создавать фоновый waiter/monitor/watchdog, циклы polling, progress-события каждые N шагов, summary scripts, manifests или другую работу «пока ждём»; не запускать агентов или следующую карточку. Обычное ожидание не требует заполнения паузы работой. Соблюдать provider no-poll/no-sleep. Проверить настоящий wait/continuation в каталоге до launch; при отсутствии доказать конкретный блокер, сохранить handle и INCOMPLETE, без выдуманного API или relaunch. STOP/NEXT Любы немедленны. Updates, loss, hash и случайный верный токен сами по себе не доказывают навык; 0→0 не является учебным результатом, частичные токены не объявляются целым ответом. ## Непосредственная связь с обучением

[DpoTrainer.StepVectorCore][step] делает policy forward обеих сторон, [BackwardLogProbs][backward] запускает `logits.Backward`, backward-функции слоя вызывают [TensorOps.AccumulateGrad][accum], затем один AdamW update. При первом поступлении градиента текущий метод создаёт внешний `ToArray`; [Tensor constructor][ctor] передаёт массив в [TensorStorage][storage], который делает ещё один `ToArray`. Поэтому это затраты каждого достигнутого первого вклада в autograd, включая промежуточные узлы двух policy-графов; не только две начальные logits-матрицы.

**Гипотеза:** удаление внешней копии в этом месте уменьшит allocated bytes одинакового учебного перехода, сохранив независимое владение массивом градиента, порядок его накопления, значения weights и learning readout. Выигрыш по wall-time или peak RAM не обещается.

### Почему тот же градиент можно получить дешевле: сохранённый результат AGC1

**Дополнение от 22.10.2026.** Ниже объяснён уже опубликованный [результат AGC1][pass8-agc-report]. Прежние формулировки паспорта о будущем выполнении сохранены как историческая спецификация; этот математический разбор не назначает новый запуск и не меняет очередь.

**Пример для студента.** Несколько проверяющих прислали списки числовых поправок к работе. Вы складываете их, чтобы получить итоговое исправление. Первый список раньше переписывался дважды, хотя для дальнейшей работы достаточно одной собственной копии. Если убрать лишнее переписывание, остальные поправки прибавляются в прежнем порядке, итог остаётся тем же, а работы с памятью становится меньше.

**Математика книги.** В [§9.5–9.6, печатные с. 284–285 / PDF с. 320–321][pass8-agc-book] обратный сигнал собирается из путей вычислительного графа. Для feed-forward блока книга записывает

$$
\frac{\partial L}{\partial y_m}=g_mW_2^\top D_mW_1^\top,
\qquad
\frac{\partial L}{\partial W_2}=r_m^\top g_m.
$$

Здесь $g_m$ — входящий сигнал ошибки, $W_1,W_2$ — матрицы блока, $D_m$ — маска активных ReLU, $r_m$ — их выход. [Proposition 9.6][pass8-agc-chain] выводит первую формулу по правилу цепочки; следующий текст указывает, что вклады в параметры суммируются по токенам и элементам batch. Книга объясняет, какие числа должны получиться; число физических копий массива — вопрос реализации.

**Наш вывод для накопителя.** Обозначим входящие в один узел вклады через $g_k$; это общая запись для объяснения кода, а не отдельная формула книги:

$$
G=\sum_{k=1}^{K}g_k,\qquad G_1\leftarrow g_1,\qquad G_k\leftarrow G_{k-1}+g_k\quad(k\ge2).
$$

Если $C$ копирует массив без изменения чисел, $C(C(g_1))$ и $C(g_1)$ имеют одинаковые значения. Именно внешнюю копию убрали между [A][pass8-agc-a-code] и [B][pass8-agc-b-code]: одна исполняемая строка отличается, ещё две строки — поясняющие комментарии. [Конструктор Tensor][pass8-agc-tensor] по-прежнему передаёт данные в [TensorStorage][pass8-agc-storage], где выполняется `Data = data.ToArray()`. Поэтому у градиента остаётся собственный массив; ветвь последующего `+=` и порядок сложения не изменены. Это объяснение относится к прежнему последовательному выполнению без конкурентной записи в исходный массив.

**Почему это может экономить время.** На тот же градиент и тот же учебный результат требуется меньше копирований и выделений памяти. Конкретная экономия секунд зависит также от GC, прогрева и прочей работы процесса. Это измеренный успех по стоимости одного update; уменьшение числа уроков или ускорение сходимости не измерялись. [Подготовка старта][pass8-agc-prep] отдельно потребовала 1000 SFT updates и 2 281 350,2736 мс: это узкое запоминание одной строки о постфиксном инкременте. DPO начинался со свежего оптимизатора, шаг 0 → 1, без импорта SFT-моментов. Отложенной выборки и свободной генерации в этом результате нет.
