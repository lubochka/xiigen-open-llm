## Обязательные правила для карточки и любого её промпта

**Найти tool и дождаться своей операции — обязанность исполнителя.** До выдачи команды прочитать [контракт31](../31-tool-discovery-and-wait.md) и указанные там реальные skills/references; по каталогу текущей среды найти launch и wait/resume/status, прочитать их схему и сохранить provider, handle, start time, H/R и deadline. Не выдумывать Kiro API по Codex-примеру, не просить пользователя выбирать инструмент или запускать команду вместо исполнителя.

**Ожидание не равно бесполезному polling.** Одна выдача entry; затем штатный bounded wait/resume того же session/cell/process ID до terminal exit или исходного experiment deadline. Нормальный wait можно повторять при silent/running. Два быстрых неблокирующих чтения без прогресса требуют перейти в wait; если он неисправен/ответы противоречат — независимое чтение H/R/claim/exit и своего PID+start. Не вводить Start-Sleep в занятый терминал. Предел одного ожидания≤60с — не предел эксперимента; yield/RPC timeout не доказывает exit/kill/нулевой расход. После диагностики живой процесс продолжают ждать. Отсутствие log не доказывает, что запуска не было. Не выдавать entry заново «синхронно на25минут», не подбирать results-NN, не удалять claim/partial, не сокращать TRAIN/steps до двух минут ради tool. **Не завершать ход на ожидании и не придумывать работу.** ISSUED/WAITING → штатный блокирующий/event wait исходного handle → terminal/exit → чтение назначенных raw → отчёт. Финальное «жду уведомления / доложу потом» до результата запрещено; обещание auto-notification не доказывает возобновление. ## Самостоятельные сравнения

<a id="s-1"></a>
### P24.1 — Count<=topK bypass ranking

A current Count<=topK shortcut, B Rank для всех counts: те же 3 manifests; затем отдельный fourth irrelevant. First ID, returned set и downstream order sensitivity. Если получатель использует все order-invariant, quality effect неприменим.

<a id="s-2"></a>
### P24.2 — Lexical vector против настоящего frozen embedding

**A:** current vector=Jaccard normalized roots. **B:** предложенный read-only hook получает EmbeddingModel(model, tokenizer, maxLen=min(64, ContextLen)).Embed(query) и .Embed(manifest.TrainingText) из одного frozen checkpoint/tokenizer; vector=clamp(cosine,0,1). Это тот embedding owner, который создаётся в TransformerEmbeddingKnnLogicalUnit.Train, но его подключение к ReplayFusionRanker пока CONDITIONAL. **Pattern в B остаётся старым lexical Jaccard**, а не копией нового vector; lexical coefficient.35, vector.45, pattern.20, pool, attestation, tie и topK3 неизменны. Все query/document embeddings одной версии. Противоположный закон с тем же bag против lexical-distant верного закона; exact/unique-token control; zero embedding и различие только после 64tokens — края. Улучшение ranking не доказывает actual retry gain без того же ordinary Flow.

<a id="s-3"></a>
### P24.3 — Pattern-копия lexical vector против независимого order/scope признака

**A:** pattern=lexical Jaccard. **B:** pattern=1 только при равенстве заранее заданного order/scope signature query и manifest, иначе 0; vector и lexical остаются прежними. Signature — ordered signed relations, например C# [(validate, input),(persist, input)] против обратного порядка; SQL predicate binding ON(right.active) против WHERE(right.active); перевод subject=Anna, verb=follows, object=Boris против role swap. Для controlled-input стадии эти структуры задаются открытыми входами обеих сторон; parser quality не измеряется. Для ordinary стадии требуется реальный extractor из source, без gold labels/hidden TEST metadata. При missing/unknown signature B использует старый pattern как явный fallback, не hard veto. Контроль — одинаковый закон с переименованием имен по заранее заданному role binding; edge — ambiguous referent/unknown parse. Это отдельная интервенция от embedding в.2.

<a id="s-4"></a>
### P24.4 — Score shortlist gate

**A:** существующий cutoff shortlist. **B:** убрать только score cutoff и передать тот же ordered candidate list к следующему существующему limiter; ranking/topK/attestation/data неизменны. На frozen DEV зафиксировать candidate чуть ниже текущего cutoff и lawfulgold, low-scorewrong — отрицательный контроль. Считать coverage, wrongaccepted, latency, числорассмотренных candidates; addedcandidate сам по себе не gain.

<a id="s-5"></a>
### P24.5 — ReplayMixer повторно сортирует по времени

A ReplayMixer повторно CreatedAt-sort, B сохраняет полученный selected order при той же accepted set. Equal timestamps tie и downstream unordered consumer — controls.

<a id="s-6"></a>
### P24.6 — Top-3 aperture к DPO или KNN recipient

**A:** top3 replay manifests. **B:** top5 при одном frozen lawful pool≥6 и одном ranking. Отдельно показать какие IDs попали в DPO replay и BuildKnnTrainingCorpus. Primary budget DPO: одинаковые processed examples и optimizer updates; фактические unmasked tokens и wall time измеряются отдельно, поскольку длины заменённых пар различаются. Не усекать ответы ради равенства: новый набор замещает доли прежнего по заранее зафиксированной round-robin схеме; retention цену показать. Для памяти число принятых entries может расти: это явная цена расширения памяти, а не эффективность нейронных вычислений. Контроль — pool≤3; края — 4–5 записей и важная шестая запись за пределом top5. Если обоим получателям хватает top3, эффект не ожидается.

<a id="s-7"></a>
### P24.7 — Вложенный KnnExamples переносится отдельно от manifest shortlist

A — BuildKnnTrainingCorpus берёт одну пару каждого selected manifest. B — при том же selected set дополнительно разворачивает только уже аттестованные KnnExamples этих manifests, с dedup по stable ExampleId+content hash и отказом при конфликте. Непроверенные вложенные записи не обходят admission. Student weights, DPO список и encoder прежние; index каждой ветви согласован со своим corpus. Old-law case опирается на вложенный урок, отсутствующий во внешней паре; manifest без вложений — контроль. Цена размера/latency отдельно; нет допустимого nested provenance — CONDITIONAL.

<a id="s-8"></a>
### P24.8 — Предел 256: полный отказ против проверяемого bounded snapshot

A — текущий InvalidReplay при 257 admissible manifests. B — предложенный bounded snapshot: до online выбора отдельный streaming validator проверяет все 257 и сохраняет полный digest/receipt, online selector читает top3 из этого validated snapshot без повторной неограниченной загрузки. Нельзя просто Take256 до проверки или снять proof gate. One invalid late entry должен блокировать snapshot;256 и empty pool — controls. Это новый архитектурный кандидат, CONDITIONAL до validator/snapshot contract. Считать admission correctness, legitimate lesson availability, validation time/memory, не заранее обещанное качество.

<a id="s-9"></a>
### P24.9 — Coverage законов внутри одного DomainTag

A — top3 общего rank. B — round-robin по заранее известным разрешённым SubPhaseId группам, внутри каждой прежний rank, общий top3; порядок групп фиксируется до экзамена по TRAIN coverage, не gold. Один редкий старый закон и много частых одного закона в том же фактическом DomainTag; не смешивать SQL/C# без общего owner. Контроль одна группа; edge больше трёх групп означает неизбежную потерю coverage. Считать old/new law retention и среднее качество вместе с ценой полезного rank.

<a id="s-10"></a>
### P24.10 — Старый Unit доступен обычному router

A — обычный запрос при штатной регистрации старых Units. B — тот же router и все состояния, но один разрешённый old Unit исключён из candidate registry только в изоляции; остальные candidate IDs прежние. Это ablation доступности, не сравнение старого checkpoint с новым как одинаковых моделей. Old-law query должен иметь trace выбранного recipient; unrelated query — контроль. Если старый Unit не выбирался, no contrast. Результат отделяет потерю знания нового Unit от потери способности всей системы.
