## Что это означает для обучения

В переводческом пути есть две разные возможности потерять полезный урок. Первая — разные записи одного слова превращаются в разные ключи, а иногда разные слова сливаются. Вторая — правильный перевод с сохранённым идентификатором отбрасывается языковым фильтром. Отдельно обнаружен риск неверной оценки ответа: счётчик `ProductMatch` проверяет признаки, но не равнозначен правильному переводу.

Эти механизмы относятся к структурированным переводческим Unit и отдельному переводческому runner. Их участие в уже измеренном нейронном RP01 не установлено. Нельзя объяснять ими его 0/3 или 0/4 без цепочки вызовов.

## 1. Смысловой ключ зависит от формы Unicode и заглавной Ñ

Источник: [TranslationTrainedUnits.cs](../../../27.TranslationDomain/TranslationTrainedUnits.cs), `NormalizeMapKey`, строки 1008–1028; выбор exact/phrase/word/kNN в строках 263–288.

- Перед приведением к нижнему регистру `LooksLikeUtf8Mojibake` считает символы `Ð`, `Ñ`, `Ã` признаком испорченной кодировки. Но Ñ бывает обычной испанской буквой.
- При срабатывании используется другая очистка: удаляется пунктуация по краям отдельных слов. В обычной ветке удаляются все символы, кроме букв, цифр, `_`, `$` и пробелов.
- Каноническая нормализация NFC отсутствует. У `sí` и `si` с отдельным комбинируемым ударением могут получиться разные ключи; комбинируемый знак обычная фильтрация удалит, сближая второй вариант с `si`.

Следствие по исходнику: внешний вид и регистр входа могут менять точное сопоставление, хотя предполагаемый языковой смысл не меняется. Это не доказательство фактического промаха во всех путях: совпадение по phrase/word/kNN может скрыть потерю exact-ключа. Для испанского различие `sí/si` предметно значимо; для C# и RU→EN это не универсальный критерий.

Будущий ограниченный опыт: записать один корректный урок и предъявить NFC/NFD, Ñ/ñ и контрольный вариант без соответствующих букв; сохранить ключи и реально выбранную ветку. Сначала измерить существующее поведение, затем отдельно сравнить предлагаемую канонизацию. Не менять остальные правила очистки в той же паре вариантов. **Не запускался.**

## 2. EN→RU: ASCII-идентификатор может быть принят одной веткой и отвергнут другой

Источник: тот же файл, строки 924–960 и 991–1005.

Для строгого EN→RU-кандидата одновременно требуются кириллица и отсутствие ASCII-латиницы. Для phrase-кандидата требование отсутствия латиницы не используется. Проверка копирования отдельно исключает `CODE_IDENTIFIER`, но это исключение не отменяет строгий запрет ASCII-латиницы.

Поэтому сохранённые `HTTP`, `Task`, имя API или кодовый идентификатор могут мешать одному пути принятия корректного русского объяснения. Нельзя обобщать это до «EN→RU всегда отбрасывает идентификаторы»: порядок поиска и более мягкая phrase-ветка являются контрдоказательствами такой формулировке. Проверка латиницы ограничена A–Z/a–z, а не всем латинским письмом.

Будущий опыт: один и тот же допустимый перевод с защищённым идентификатором и без него, с трассировкой exact/phrase/word/kNN и конкретного reject-предиката. Домен — технический EN→RU; контроль — обычное предложение. Оценивать сохранность значения и идентификатора, а не только кириллицу. **Не запускался.**

## 3. ProductMatch измеряет ограниченный набор признаков

Источник: [TranslationProductHeldOutRunner.cs](../../../27.TranslationDomain/TranslationProductHeldOutRunner.cs), строки 149–179, 339–362, 594–644.

`ExactMatch` вычисляется отдельно и не входит в `ProductMatch`. Последний использует отсутствие bootstrap, required/forbidden markers, письмо, копирование и опциональные списки emoji/имён. Пустой список для `.All` даёт истинный результат. `Bleu1` здесь — доля совпавших слов фактического ответа без штрафа за его краткость; `ChrF1` — пересечение счётчиков символов без порядка. Перестановка действующего лица и объекта поэтому может не проявиться в этих счётчиках.

Свежая дополнительная граница: при `runtime.IsSuccess == false` в `actual` помещается `ErrorMessage`, но сам флаг успеха не входит в `ProductMatch`. Из исходника следует возможность проверять текст ошибки как перевод. Реальный ошибочный ответ, прошедший приёмку, в этой работе не найден; это условный кандидат, зависящий от текста ошибки и настроенных маркеров.

При этом runner явно возвращает `PassesPromotionGate = false`: его `PassesGate` нельзя выдавать за разрешение публикации. Поиск имени класса во всех tracked C# дал только его файл и `Tests/TranslationDomainTests.cs`. Это ограничивает доказанный потребитель; не доказывает отсутствие внешнего вызова.

Будущий опыт: правильный перевод, перестановка ролей, потеря отрицания, отсутствие emoji при пустом/заполненном `EmojiMarkers`, отдельно ошибка runtime. Сравнить текущие поля и заранее определённую смысловую оценку. Не обучать модель ради проверки арифметики gate. **Не запускался.**

## 4. Поправка к присланному Python proxy: emoji даёт другую ChrF1 в C#

Помощник сохранил для `actual = Hello`, `expected = Hello 🙂` значение `ChrF1 = 1`. Его [Python proxy](C:/Users/lubao/Documents/xiigen/llm%20mvp/design%20to%20code%20session/replanning/possibleDifs/28-PRODUCT-HELDOUT-SCORER-PROXY.py) перебирает Unicode-символы и удаляет символ категории `S`. C# в строках 633–644 перебирает `char`, то есть отдельные UTF-16 единицы. 🙂 состоит из двух surrogate-единиц; они не являются `char.IsSymbol`.

Статическое следствие для именно этого примера: у `Hello` 5 учитываемых единиц, у `Hello 🙂` — 7, пересечение — 5. Поэтому ожидаемая C# `ChrF1 = 2 × 1 × (5/7) / (1 + 5/7) = 5/6`, примерно 0.8333, **а не 1**. Это расчёт по исходнику и контракту .NET, не выполненный native-замер. Категории `IsSymbol` и особенности `Char` описаны в [Microsoft Char.IsSymbol](https://learn.microsoft.com/en-us/dotnet/api/system.char.issymbol?view=net-10.0) и [Microsoft CharUnicodeInfo.GetUnicodeCategory](https://learn.microsoft.com/en-us/dotnet/api/system.globalization.charunicodeinfo.getunicodecategory?view=net-10.0).

Поправка не отменяет проблему `EmojiPreserved`: при пустых `EmojiMarkers` он остаётся true, а `ProductMatch` не зависит от `ChrF1`. Она отменяет конкретное численное доказательство, будто этот C#-счётчик совсем не видит данный emoji. Ещё одно различие proxy: Python `\w` включает `_`, тогда как C# tokenizer здесь использует `\p{L}\p{N}` и апостроф. Proxy нельзя считать побитовой копией реализации.
