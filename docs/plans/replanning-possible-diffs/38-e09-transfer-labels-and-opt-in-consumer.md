## Что подтверждено

Commit `27ae03266ae2f7300d63e915795c0ff62369fa67` от 07.05.2026 прямо называется переносом E09/E10 structural KNN в production. Он добавляет `12.SemanticCompiler/Prediction/StructuralKnn.cs` и удаляет экспериментальные predictor/extractor. Это реальная связь через Git, а не совпадение названий. Само по себе это ещё не искомое доказательство истории «неудачная матрица стала очень успешной функцией kNN».

В parent `f8a41b76b26b7de4c53aecb845661d37837d686c`, `35.ExperimentsV2/Core/StructuralKnnPredictor.cs:25–35`, голоса ближайших собираются в Dictionary, после чего берётся MaxBy без явного числового tie-break. В [нынешнем predictor](../../../12.SemanticCompiler/Prediction/StructuralKnn.cs:150) при равенстве числа голосов выбирается меньший NextToken (`ThenBy(group.Key)`). Это новая фиксированная политика при равенстве, но частота и вред таких решений в настоящих запросах не измерены. Порядок Dictionary старого runtime нельзя объявлять предметным предпочтением.

[E09 BuildTokenVectors](../../../35.ExperimentsV2/Experiments/E09StructuralKnn.cs:107) строит отдельный sorted kindMap для каждого файла. Голое число старой метки не имеет универсального значения между файлами. Новый [NodeTypeId](../../../12.SemanticCompiler/Prediction/StructuralKnn.cs:98) — SyntaxKind%200; TrainFromSource использует его для следующего узла (124–141). Это иной codec, не автоматически ошибка: собственные train/query могут быть согласованы. Реальные collisions modulo200 в корпусе здесь не вычислялись.

## Дополнительная проверка фактического включения

Helper правильно требует настоящего caller. Он найден в [SemanticCompilerFacade](../../../12.SemanticCompiler/SemanticCompilerFacade.cs:206): TrainStructuralKnn агрегирует пары по нескольким C# исходникам и обучает память при ≥10 парах. Этот путь использует тот же NodeTypeId для target; он не восстанавливает прежние локальные kindMap labels. Нельзя утверждать, что production целиком лишён обучения kNN.

Но [PredictStructuralNextTokens](../../../12.SemanticCompiler/SemanticCompilerFacade.cs:298) возвращает пустой результат, если выключен UseStructuralKnn, stack не CSharp либо TrainingSize<10. [Опция](../../../12.SemanticCompiler/SemanticCompilerOptions.cs:15) по умолчанию false. Метод Compile вызывает predictor (157) и записывает его прогноз в CompilationResult; существование этого выхода ещё не означает применение его к пользовательскому ответу.

Адресный `git grep` по tracked C# нашёл внешние вызовы TrainStructuralKnn и явные присваивания UseStructuralKnn=true **только в Tests/E09E10FeatureFlagTests.cs**. Поиск свойства PredictedNextTokens также нашёл лишь объявление, присваивание в facade и эти Tests; обычный потребитель прогноза не найден. Это ограниченный source search: внешняя сборка, reflection и иные способы конфигурирования им не исключены. Но для RP01 пока нет положительного доказательства, что эта обученная функция включена, наполнена примерами и использована в ответе. Это более близкий практический вопрос, чем немедленная замена tie-break.

Дополнительная граница state: TrainStructuralKnn с <10 новых пар не вызывает Train и не очищает старую память (224–225), тогда как прямой TrainFromSource на пустом тексте очищает её (126–129). Это разные контракты методов; ошибку реального клиента не наблюдали. При будущей проверке обязательно указать, какой именно API использовался.
