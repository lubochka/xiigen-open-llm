## С-01. Обновлённые q/v-LoRA читаются и полным forward, и генерацией с cache

**Что подтверждено.** В просмотренном пути нет отдельной inference-модели, игнорирующей adapters. [LlmModel.cs](../../../03.TransformerModel/LlmModel.cs):153–199 и :219–241 используют одни `_tokenEmbedding`, `_blocks`, `_finalNorm`, `_lmHead`. Различается способ обработки последовательности, а не владелец этих параметров.

[CausalSelfAttention.cs](../../../03.TransformerModel/Layers/CausalSelfAttention.cs):140–168 вызывает `ForwardProjection` для q/k/v/o в полном пути; :194–246 делает то же в cached. Общий dispatch :251–259 вызывает установленный adapter, если он есть. [LoraLinear.cs](../../../10.LoRA/LoraLinear.cs):112–125 в обоих случаях вычисляет `base(x) + Scaling * (dropout(x) @ Aᵀ) @ Bᵀ`; `Scaling=Alpha/Rank` задан в `10.LoRA/LoraConfig.cs:17`. Отдельного cached scaling в прочитанном коде нет.

**Разрешённый recipient.** [DpoTrainer.cs](../../../11.DPO/DpoTrainer.cs):190–226 связывает AdamW только с adapter parameters по identity; :230–254 проверяет установленную топологию, frozen base и независимый frozen reference. [CodeDocumentationSimulationDpoExperiment.cs](../../../14.ContinuousLearning/Training/CodeDocumentationSimulationDpoExperiment.cs):130,160 получает этот recipient и создаёт `CreateForProjectLora`. Сохранённые results ниже показывают изменение 16 adapter-тензоров и неизменность 39 base-тензоров. То есть embedding, base q/k/v/o, FFN, нормы и output head не обучаются отдельно этим DPO; они всё равно участвуют в обоих forward. Это ограничение области адаптации, не доказанная причина плохого ответа.

Полный policy forward в DPO использует `training:true` (`DpoTrainer.cs:1014–1029`), reference/scoring — false; cache использует false. Однако RP01 runner в :110–111 **отклоняет `LoraConfig.Dropout != 0`**. Поэтому общая гипотеза «обучение и generation различаются из-за LoRA dropout» не объясняет этот принятый путь. Нельзя переносить этот вывод на другие runners с ненулевым dropout.

**Классификация.** Source counterevidence против простого LoRA bypass, другого head или другого scaling. Численная эквивалентность full/cache на конкретных C50/C100 этим ещё не доказана. Статус — REUSE существующих owners; причинный эффект оставшихся различий требует будущего отдельного сравнения.

**Позиции и маска.** Full attention использует RoPE от offset 0; cache — `positionOffset` из уже накопленной длины (`CausalSelfAttention.cs:148,219–225`). ## С-06. Что остаётся между изменением вероятностей и правильным ответом

На данном материале локализован наблюдаемый разрыв: сохранённое изменение LoRA → изменение cached prefill logits **есть**; правильная собственная последовательность на малых проверенных панелях **не показана**. На единственной записанной первой позиции delta logits порядка .011 не сменила лидера с исходным top1–top2 gap .369. Это объясняет устойчивый выбор **той позиции**, не всех остальных ответов.

Остаются конкурирующие причины: численный full/cache decode drift; недостаточная пригодность frozen base для языковых/программных закономерностей; ограниченная область q/v adaptation; слабый или однообразный контраст данных; objective, улучшающий относительную likelihood без нужного token-rank/sequence gain. Ни одна из них не выделена этим source-reading как единственная причина. Количество changed tensors не различает их. Отсутствие learned EOS может влиять на завершение ответа, но не объясняет само по себе неверный первый token.

В этом участке **не найден новый исторический neural donor**, одновременно имеющий сохранённое подтверждённо изменившееся состояние, пригодную исходную базу и сопоставимую свободную оценку. Старые успехи specialized memories/functions из [09](09-domain-functions-and-sibling-branches.md) и [10](10-historical-function-transfer-and-learning.md) не переименовываются в такой donor. Поиск качества данных и соответствующих исторических neural состояний остаётся открытым; это не вывод, что их не существует.

### Один будущий различающий фактор: full forward против chunked cache на тех же сохранённых token IDs

**Только проект; не выполнен и не назначен к запуску этим документом.** Он проверяет узкую гипотезу исполнения Student, прежде чем менять обучение. Домен — EN→RU prompt, уже сохранённый в paired first-decision; consumer — `LlmModel` под `TextGenerator`. Это не новый тест качества C# или универсальный verdict по всем доменам.

Входы уже существуют: 50 `promptTokenIds` из C50-completed.json; C50 SHA `6f4d0284ea823ba99932b0f28576855c14205703115b48c983c7a9f03749179b`; C100 SHA `3acb5a9080d0454942c261eca4c1b886aab011db83729947509be4463785fab5`; tokenizer SHA из С-03. До будущего выполнения следует закрепить bytes/hash обоих completed receipts и проверить совпадение их prompt IDs. Сегменты назначены заранее: первые **42** tokens — prefill, следующие **8** — по одному. Новых строк, labels или токенизации не требуется.

- На каждом checkpoint A вызывает `Forward(all50, training:false)`; B вызывает `ForwardWithCache(first42, fresh KvCache)` и затем восемь single-token calls с оставшимися **теми же** сохранёнными IDs. Единственный меняемый фактор внутри пары — full/chunked execution. C50 и C100 являются двумя отдельно отчётными состояниями, не дополнительным вмешательством.
- Reuse: production checkpoint import из `SimulationEnRuContinuation.OpenStudent`/существующего host loader; public `LlmModel.Forward`, `ForwardWithCache`, `KvCache`. Образец выравнивания absolute positions уже есть в `CacheAwareForwardTests.cs:32–48`. Будущему более дешёвому исполнителю потребуется минимальный diagnostic caller; текущий runner сам full/cache comparator не предоставляет. Не переписывать attention, tokenizer или маски.
- Бюджет проекта: **20 model forward calls всего** — 2 full, 2 prefill, 16 decode; 0 optimizer/DPO/Teacher calls. Стены времени не обещаются. Это teacher-forced replay prompt IDs, а не восемь собственных ответов модели; TRAIN/heldout обучение не проводится, prompt не становится новой обучающей строкой.
- До оценки закрепить tolerance, предлагаемый начальный FP32 критерий `abs(A-B) <= 1e-4 + 1e-4*max(abs(A),abs(B))` для всех сравниваемых logits. Это проектный порог, не уже доказанная точность. Отдельно сохранять max absolute/relative delta и top1 каждого выровненного окна; несовпадение top1 при почти равных лидерах не скрывать общей tolerance. Сравнивать prefill позиции 0…41 и decode 42…49 с соответствующими строками full.
- State control: до/после неизменные keyed tensors/checkpoint bytes, отдельный fresh cache для каждого состояния, одинаковые inference flags. Сохранять source/config/checkpoint/recipe hashes, token IDs и raw logits в новом изолированном output; не менять старые receipts. Повтор по той же recipe — replay, не новое обучение и не доказательство cold optimizer restore.
- **Отрицательно для cache-гипотезы:** обе пары укладываются в заранее установленный порог и имеют одинаковые top1 на всех сравнениях. Это ослабляет конкретную гипотезу на 50-token prefix и восьми decode позициях, но не доказывает parity на длинных контекстах или рост смыслового качества.
- **Положительный диагностический сигнал:** устойчивое превышение порога или существенное расхождение top1 при совпадающих inputs/state. Он требует локализации первого расходящегося layer/position в отдельном будущем задании; ещё не доказывает, что исправление улучшит ответы. Если hashes/IDs/import не совпали — INVALID_SETUP, а не cache verdict. Не менять threshold после просмотра результата.

Условный минимальный ремонт зависит от этого разграничения: если parity соблюдён, сохранить текущие forward/cache owners и исследовать data/base/objective; если найдено расхождение, исправлять конкретный position/mask/append consumer с matched replay. Сейчас нет достаточного основания менять эти реализации. Верность полного forward относительно математики Transformer — также отдельный вопрос: согласие двух путей само по себе её не доказывает.
