## Проверенная передача материала

[Indexer:28–51](C:/Projects/llm_mvp_core/08.GraphRag/Indexer.cs:28) выбирает RawText, иначе Signature, иначе Name. Непустой RawText исключает остальные поля из embedding-текста. Name/type/filePath сохраняются metadata, Signature отдельно там не хранится. Если RawText уже содержит существенное различие, потери нет; если различие только в Signature, входы encoder могут совпасть.

[EmbeddingModel:22–46](C:/Projects/llm_mvp_core/05.Embeddings/EmbeddingModel.cs:22) получает внешний encoder/tokenizer и maxLen, по умолчанию512. [Tokenize:77–99](C:/Projects/llm_mvp_core/05.Embeddings/EmbeddingModel.cs:77) оставляет первые maxLen BPE IDs; [LocalSearch:29–52](C:/Projects/llm_mvp_core/08.GraphRag/LocalSearch.cs:29) и [GlobalSearch:37–61](C:/Projects/llm_mvp_core/08.GraphRag/GlobalSearch.cs:37) используют этот embedder. Одинаковые усечённые входы при одинаковом состоянии и обычной ненулевой ветке не несут отличия хвоста. Из этого не следует одинаковый конечный ответ: graph edges, сохранённые узлы и другие потребители могут различаться.

[EnsureNonZeroUnitVector:49–74](C:/Projects/llm_mvp_core/05.Embeddings/EmbeddingModel.cs:49) при слишком малой норме добавляет счётчики ID из **полного текста**, сгруппированные modulo hiddenDimension, и нормирует. Это иной, детерминированный путь; он способен сохранить часть хвоста, пропущенного encoder. Счётчики добавляются к существующему vector, а не к явно заново обнулённому массиву: для малого, но ненулевого исходного vector это не строго чистый bag-of-IDs. При специально нулевом vector предложенная формула proxy уместна. Путь не возвращает признак fallback, частота его срабатывания в реальной работе неизвестна. Пустая строка отдельно не проверена: T=0 может отказать раньше.

Правильный исследовательский вопрос — полезна ли конкретная политика представления в данном домене. Детерминированный fallback не становится бесполезным только из-за отсутствия LoRA; но его полезность нельзя приписывать изменению обученных параметров.

## Непустой результат при отсутствии действующих seeds

[PersonalisedPageRank:66–116](C:/Projects/llm_mvp_core/07.GraphEngine/PageRankCalculator.cs:66) при непустом графе возвращает список **всех** node IDs, отсортированный по рангу. Пустой seedSet даёт нулевой teleport; отсутствующие в graph IDs тоже не получают teleport. Однако список IDs не отфильтровывается по положительному рангу. GlobalSearch берёт topK этого списка; [HybridRetriever:62–105](C:/Projects/llm_mvp_core/08.GraphRag/HybridRetriever.cs:62) принимает результаты и может включить их текст независимо от нулевого score.

Source-условие помощников подтверждено: непустой graph плюс пустой индекс или только устаревшие index IDs может дать snippets действующих graph nodes без действующих vector seeds. [BruteForceIndex:23–29](C:/Projects/llm_mvp_core/06.VectorSearch/BruteForceIndex.cs:23) допускает пустой результат, но в непустом индексе возвращает topK без порога релевантности. Поэтому «нет seeds» не эквивалентно «не найдено смыслово подходящее знание»: неподходящий кандидат с существующим ID тоже считается seed. Guard на непустоту не заменяет предметную проверку применимости.

## Две поправки к будущему опыту

**Первое: valid seed не исключает нерелевантное дополнение.** В том же сохранённом контрольном JSON validSeedControl возвращает B первым, затем A/C с нулевыми рангами. Это согласуется с C# return-all→Take(topK). Guard «есть хотя бы один valid seed» оставляет такое дополнение. Считать его полным решением ложного контекста нельзя; вопрос минимального positive score/достижимости/предметной релевантности — отдельный будущий фактор, а не незаметное расширение текущего A/B.

**Второе: удаление stale IDs меняет веса смешанного набора.** Helper-протокол одновременно требует фильтровать invalid seeds и обещает неизменность при наличии хотя бы одного valid seed. В source seedWeight=1/seedSet.Count. Для набора `{valid B, missing X}` удаление X меняет вес B с1/2 на1; меняется и danglingShare. Поэтому обещание точного совпадения верно для полностью valid контроля, но не для смешанного списка. В будущем нужны отдельные случаи empty, stale-only, all-valid, mixed-valid/stale. Либо guard только запрещает нулевой validCount, сохраняя исходный непустой набор, либо явно исследуется также перенормировка. Нельзя назвать оба варианта одним неизменным вмешательством.

Для prefix arm `firstN→head+tail` фиксировать настоящий maxLen и branch fallback, перевекторизовать документы и запросы согласованно. Для metadata arm удерживать тексты короче cutoff. Замена нулевого encoder ненулевым в диагностике fallback показывает ветвление, но не является доказательством пользы обучения. Влияние на C# overload, SQL schema или EN→RU отрицание оценивается только у реально читающего контекст потребителя, с правильными отказами и потерянными полезными ответами отдельно.
