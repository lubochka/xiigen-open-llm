# E25/E26: успешная предметная память и другой алгоритм под тем же названием

16 октября 2026. READ_ONLY_RESEARCH, продолжение поиска исторических положительных механизмов. Источники прочитаны в core `0eccbdc3c4efb90adf1d699806cbfa9f5610998d` и в историческом `0c23a17b72de7730dde27acafc7f65b29bf85de7`. Запусков нет. Это ещё не установленный точный случай, который Люба помнит как перенос из неудачной матрицы в успешную функцию kNN.

## Основное обнаружение

Для E25 сохранён положительный результат **34,38% → 87,5%** классификации синтаксического порядка. В эксперименте действительно использовались обучающие примеры и kNN по соседним частям речи. Но `SemanticCompiler29.PatternClassifier`, который сейчас даёт structural bonus в transformer-kNN, не содержит этой памяти: он присваивает части речи по коротким спискам слов и применяет фиксированные условия. В его комментарии осталась ссылка на +154,6% из другого алгоритма.

Это конкретное расхождение переноса, а не возражение против детерминированных алгоритмов вообще. Правила могут быть полезны. Однако результат обученного kNN не подтверждает качество заменивших его правил.

[E25PatternClassifier.cs](../../../35.ExperimentsV2/Experiments/E25PatternClassifier.cs):20–47 создаёт POS-последовательности, делит 80/20, вызывает `Train(train)` и сравнивает `PredictByRules` с kNN. Его [исходник](../../../12.SemanticCompiler/Translation/PatternClassifier.cs):34–86 хранит train, считает Jaccard по **POS-биграммам**, берёт k=3 и голосует по меткам восьми структур.

Исторический `35.ExperimentsV2/Infrastructure/SentencePatternClassifier.cs@0c23a17b72:29–81` содержал тот же существенный путь train → POS-bigram distance → top3 → label vote. Позднее `dcc1a5c206` удалил дубликат и добавил alias. Есть небольшое различие untrained fallback: в старом файле возвращался `IMPERATIVE_V`, в нынешнем проекте 12 — `PredictByRules`. Обученный эксперимент до Predict заполняет память; нельзя выдавать тексты двух классов за полностью идентичные.

**Границы успеха.** Генератор `:89–113` выбирает из фиксированных POS-шаблонов, иногда вставляет ADJ, затем перемешивает. Случайное разделение не отделяет целые шаблонные семейства. Точное пересечение созданных train/validation последовательностей здесь не восстанавливалось. Это реальный успех выбранного представления на данной синтетической задаче, а не проверка всех языков или качества перевода целого предложения. Комментарий «95% technical prompts» не имеет подтверждающего корпуса в прочитанном генераторе.

## К-02. Что попало в production-класс и fusion

[SemanticCompiler29.PatternClassifier](../../../29.SemanticCompiler/Translation/PatternClassifier.cs):24–65 принимает слова. `InferPos` различает только action-word, structure-word и всё остальное как NOUN. `Train`, learned state и kNN в нём отсутствуют. Есть фиксированный выбор SVO/SOV/IMPERATIVE; вопросительные варианты и TOPIC_OV из E25 не представлены.

В ветвлении есть дополнительное сужение: условие `firstVerb == 1 && tags[0] == 10` недостижимо при данном `InferPos`, который возвращает только 7/8/3. При `firstVerb == 0` не может быть существительного до глагола; следовательно, предусмотренный return `VSO` в этой реализации не достигается. Это вывод из прочитанного кода, не выполненный test case.

Оба production-файла появились уже в таком виде в commit **`0c23a17b72…` от 1 мая**, названном «full E01–E27 pipeline». Адресный diff к HEAD показывает только license headers. Сообщение commit о 877 тестах — историческое заявление автора, не подтверждение переноса исследованного алгоритма и не наш запуск.

Нынешний фактический consumer найден: [LlmIngredientLogicalUnits.cs](../../../18.CapabilityTraining/LlmIngredientLogicalUnits.cs):213–214 создаёт именно **SemanticCompiler29** classifier; `:288–293` подаёт ему `TrainingVectorBuilder.NormalizeRoots`, а `:227–238` превращает равенство меток в бонус .20. То есть роль тоже изменилась: эксперимент выбирал синтаксическую метку по POS; production использует грубую метку как один признак сходства сохранённых ответов. Качество этого преобразования отдельно не измерено найденными E25 receipts.

Прочитанный [SemanticCompilerPipeline.cs](../../../29.SemanticCompiler/Pipeline/SemanticCompilerPipeline.cs):18–87 состоит из AST/stack/domain/normalizer/family/logic stages; вызова E25/E26 внутри его `Compile` нет. Название «full pipeline» в commit не заменяет этого вызова. Другие внешние consumers нельзя исключить одним просмотром pipeline.

**Будущая небольшая проверка, не выполнена.** Сначала на одинаковых заранее заданных POS-структурах сопоставить preserved learned classifier, его rule baseline и production rules; не добавлять в это сравнение ошибку извлечения POS из текста. Затем отдельным фактором проверить настоящий text→POS и использование метки в неизменном fusion-пуле. Считать ошибки структуры и правильность выбранного ответа раздельно. Смена label без улучшения ответа — только промежуточный эффект. Для запроса C# структура должна учитывать соответствующий закон/AST, а не автоматически заимствовать SVO из перевода.

## К-03. E26 тоже не совпадает с одноимённым production-словарём

Сохранённые [E26 1 мая](../../../35.ExperimentsV2/results/E26-CONTEXTUAL-DICTIONARY/results/run-2026-05-01-003.json) и [7 мая](../../../35.ExperimentsV2/results/e01-e53-tier4-20260507-190227/E26-CONTEXTUAL-DICTIONARY/results/run-2026-05-07-004.json) показывают .4 → 1.0 на **15** случаях, из них 6 hard. Значения tier3/tier4 не увеличивают панель: [E26ContextualDictionary.Run](../../../35.ExperimentsV2/Experiments/E26ContextualDictionary.cs):20–64 не использует tier для создания новых случаев. `BuildTestCases:70–98` проверяет русские технические слова «поток», «запрос», «вернуть» и соседние POS.

В namespace ExperimentsV2 класс [Infrastructure/ContextualDictionary.cs](../../../35.ExperimentsV2/Infrastructure/ContextualDictionary.cs):29–113 заполняется `BuildDefault` таблицей значений и левых/правых POS-контекстов. Поиск выбирает ближайшую запись, затем приоритет. Поле k есть, но `TranslateWithContext` возвращает первую запись после сортировки — голосования нескольких соседей здесь нет. Это полезный контекстный словарь; данный runner не доказывает приобретение новых значений из DPO.

А [SemanticCompiler29.ContextualDictionary](../../../29.SemanticCompiler/Translation/ContextualDictionary.cs):21–60 — отдельная статическая таблица **null/record/request** с сигналами SELECT/WHERE/csharp/http и первыми четырьмя context-словами. У неё нет отдельного левого/правого POS-контекста, добавления учебных entries или подбора соседей. Слова, представление и задача изменены, хотя комментарий ссылается на «+150%».

Адресный `git grep` по tracked C# нашёл конструирование contextual dictionaries проекта 12 и experiments, но не `SemanticCompiler29.ContextualDictionary`; текущий pipeline его тоже не вызывает. Это ограниченный отрицательный поиск, не доказательство отсутствия reflection/external consumer. Для RP01 связь с ним не установлена.

**Будущий малый контраст.** На одном выбранном домене проверить влияние отдельно заданных левого/правого контекстов на неоднозначное слово: без контекста, с прежним POS-memory и с нынешней статической таблицей при одинаковых cases. Предварительно определить общий контракт и закрытый gold; прямо считать неподдерживаемые слова, не приравнивая fallback к правильному переводу. Новое обучающее изменение требуется только для вопроса о приобретении значения, а не для повторной демонстрации заранее заполненного словаря.
