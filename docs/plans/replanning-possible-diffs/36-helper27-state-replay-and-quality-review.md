## 1. Replay: различаются входы DPO и нового retrieval Unit

### Действующая цепочка

Реальный верхний caller существует: после первого orchestrator run и найденных knowledge edges `AdaptiveLogicalOrchestrator` вызывает `TrainAndRegisterAsync`; без trainer или без knowledge edges этот путь не выполняется ([470–518][orchestrator-caller]). В текущем trainer inventory проходит через `SelectAndValidateReplaySnapshot`, затем итоговые preference rows передаются в DPO, а выбранные replay manifests отдельно используются при создании KNN ([490–543][trainer-replay-call], [662–675][trainer-dpo-call], [952–969][trainer-knn-call]).

Активный selector сначала отбирает тот же `domainAdapterTag`, проверяет snapshot shape, соответствие topology и replay attestation. Лимит 256 проверяемых кандидатов — не окно replay из 256 примеров: превышение/недопустимый кандидат приводит к ошибке. Только после проверок выбранный набор сокращается до **трёх** newest manifests либо top3 fusion ranking ([1781–1880][replay-select]; константа 256 — строка 53). Поэтому «сначала последние десять» не описывает текущий основной путь. Более старый/неподходящий same-domain manifest может иметь значение для admission до top3, а не только для качества replay.

`ComputeCurrentRepeatCount` ограничивает число повторов текущих строк диапазоном 1–3; наличие replay поднимает минимум до 2. Mixer целится в долю старых строк 0,30, вычисляет число через округление и ограничивает наличием manifests. Затем он **снова сортирует выбранные manifests по `CreatedAtUtc`**, беря нужное число ([128–178][replay-mixer]). Если fusion ранее поставил старый релевантный manifest первым, recency-sort может исключить его из DPO, хотя он остаётся среди top3 для KNN. `TryProject16ReplayMix` лишь переставляет уже полученные строки; оно не возвращает исключённые примеры ([253–266][replay-shuffle]).

Конкретный вывод из формулы, **не выполненный опыт**: при одной текущей branch, одном классе и трёх выбранных legal manifests вес равен `4/(1×4)=1`, repeat после минимума равен 2; DPO получает две текущие строки и `round(2×0,30/0,70)=1` replay-строку. KNN получает по одной верхнеуровневой строке каждого из трёх manifests плюс текущую registration plan. `BuildKnnTrainingCorpus` не разворачивает историческое поле `manifest.KnnExamples`; используются `TrainingText`, `OutputText`, predicates/domains каждого выбранного manifest ([3467–3507][knn-corpus]). Это доказанное различие состава явной памяти, не измеренная разница знаний.

Новый Unit действительно имеет потребителя: `GeneratedCapabilityFlow.ExecuteAsync` компилирует вход, вызывает переданный retrieval Unit, а затем передаёт `unit.Output` в translator итогового результата ([7351–7460][generated-flow]). Метрики этого flow прямо обозначают `retrieval_unit_selected=true`, `learned_unit_selected=false`. Это осмысленный retrieval-путь, а не доказательство neural free generation. Существование flow не доказывает, что конкретный будущий запрос выберет именно его: при проверке качества нужно записать фактический выбранный Unit/flow и окончательный ответ.

### Контрдоказательства широкому выводу «старая память потеряна»

Parent checkpoint выбирается отдельно по inventory/registry, а не по этим трём replay rows ([624–645][parent-selection]). `BuildTeachingStack` сохраняет parent policy path и загружает parent tokenizer; DPO request получает этот path ([2314–2371][parent-stack], [2284–2295][dpo-parent-request]). Parent artifacts проверяются по provenance и hash ([1806–1889][parent-validation]). Следовательно, отсутствие примера в явном replay не означает отсутствие его влияния в parent state. Здесь не доказана ни степень сохранения старых весовых знаний, ни маршрутизация ко всем ранее зарегистрированным Unit. Top3 может быть сознательным budget; его несоответствие требованиям нельзя объявлять без зафиксированного контракта и экзамена retention.

Историческая разница проверена через `git show`: в **8f20ceb8a9bfbadab2ad309226c47dd76e714548** caller действительно вызывал `FindReplayManifests`, а helper брал latest10 и затем top3; результат шёл в DPO и KNN ([180–218][historical-replay-call], [282–290][historical-knn], [590–607][historical-replay-select]). В текущем tracked C# search `FindReplayManifests` обнаружен как legacy helper/wrapper, основной caller использует новый selector. Это ограниченный поиск статических ссылок, не доказательство отсутствия внешнего/reflection caller.

Полезный исторический результат сохранён без обесценивания: JSON E43 содержит `retention_accuracy 0.3226 → 0.3978`, `replay=177`, oldPairs=465, newPairs=414 ([result, 5–17][e43-result]). Source сравнивает **заново построенный** bigram-count словарь на новых парах со словарём на новых + части старых; один checkpoint последовательно не доучивается. Старый validation set одинаков, Evaluate выбирает most frequent next-token ([26–55][e43-design], [89–109][e43-metric]). Это позитивное свидетельство полезности сохранения старых примеров для данного частотного механизма. Оно не измеряет forgetting при DPO/LoRA и не устанавливает лучший budget для capability trainer. Binary именно исторического запуска отдельно не аттестован.

**Минимальный будущий различающий опыт, не запускать по этому документу.** Сначала зафиксировать четыре уже legal manifests одного домена, одну current branch и одинаковый old-family-disjoint exam. В диагностике membership записать admission, top3, DPO replay IDs, KNN corpus IDs и parent checkpoint. Для причинного сравнения менять ровно один фактор: recency-sort после fusion либо окно явного KNN corpus; остальное, включая родительское состояние и examiner, оставить одинаковым. Нужны фактически выбранный flow, final answer, old/new correctness и abstention. Membership mismatch сам по себе не является ухудшением качества; отсутствие эффекта на обычном consumer опровергает широкое объяснение для этого набора.

## 2. Mutable checkpoint cache: условный разрыв RAM и durable state

`TranslationCheckpointCache` хранит `TranslationMachineLoadResult` по absolute path/schema/mtime/length. `TryGet` возвращает сохранённый объект, `Store` не клонирует его ([16–50][cache]). В `TatoebaPilotLoopRunOptions` cache по умолчанию **null** ([15–25][cache-default]). При hit runner получает `loadedCheckpoint.Machine`, при miss загружает диск и сохраняет тот же result в cache ([184–213][cache-load]). Далее обычный `TrainRowsAsync` меняет machine до `SaveLoopCheckpointAsync` ([224–251][cache-mutate-first], [444–475][cache-mutate-next]).

`SaveLoopCheckpointAsync` создаёт новый cursor/loop state, вызывает save, при неуспехе бросает исключение и **не достигает** `Invalidate/Store`; эти операции стоят после успеха ([642–669][cache-save]). Сам save при cancellation возвращает failure; запись идёт через temporary file и replace, ошибки возвращаются как `CHECKPOINT_WRITE_FAILED` ([552–605][machine-save]). Отката уже изменённого machine в этих путях нет.

Следовательно, если C0 загружен в cache, затем machine изменён и save не дошёл до replace, следующий run **в том же живом процессе с тем же cache** может получить новое содержимое machine и старый cursor, при неизменном ключе файла C0. Это условный source-сценарий, не зарегистрированный runtime incident. В него нельзя подставлять полный process crash: после гибели процесса RAM alias исчезает. Успешный save обновляет cache; `Cache=null` читает диск; изменившийся file-stamp даёт miss. Same-size/same-mtime rewrite — отдельная ранее отмеченная проблема ключа, её нельзя считать новым доказательством alias-сценария.

**Граница caller.** `git grep` по tracked `*.cs` с исключением `Tests/**` нашёл declaration cache, optional field runner и внутренние ссылки, но не production construction `TranslationCheckpointCache` и не внешний вызов `TatoebaPilotLoopRunner`. Это отсутствие в конкретном tracked search, а не утверждение об отсутствии untracked/external клиентов. Не установлено, что cache включён в RP01 или в пользовательском pilot. Фактический ordinary output зависит от состояния machine, но влияние несогласованного cursor/machine на качество пока не измерено.

Это развитие уже записанного [отчёта 22](22-tatoeba-primary-review-and-domain-scope.md), где mutable alias и слабый file-stamp key отмечались. Новое уточнение — точный save-failure промежуток и требование same-process reuse; это не ещё один независимый cache bug и не потеря полей сериализатором.

**Минимальный будущий различающий опыт, не запускать по этому документу.** Один проверенный C0, один retained cache, один разрешённый структурный lesson. После мутации вызвать контролируемый отказ до file replace. Сопоставить следующий cache load и cold disk load: полное learned state, cursor, training identities и одинаковые ordinary ответы. Контроль — успешный save; отдельный контроль — новый процесс/новый cache. Первичный результат — divergence durable/RAM state; неправильный ответ признаётся последствием только при наблюдении на одинаковом запросе.

## 3. Readiness после batch без применённых уроков

В `TrainStructuredBatchAsync` проверяется непустота batch, но не наличие trainable rows. `trainedUnits` создаётся заново, цикл пропускает `HeldOut` и неизвестный UnitId, а затем `_hasStructuredTraining = trainedUnits.Count > 0` заменяет историческое значение ([89–145][structured-train]). Поэтому nonempty heldout-only batch после успешного обучения устанавливает false. Unknown-unit-only batch также устанавливает false, хотя `RowsTrained` считает все `!HeldOut` и может быть положительным. Эти два счётчика описывают разные события.

Название «любой no-op» было бы чрезмерным: известный trainer добавляется в `trainedUnits` после вызова независимо от того, изменил ли он память. Повторный идемпотентный известный урок или trainer, вернувшийся без изменения данных, сам по себе не приводит к этому сбросу. Empty batch и pre-cancelled call отвергаются до присваивания.

Реальное следствие флага — `EvaluateAsync`: при false перевод вообще не вызывается; результат имеет accuracy=0 и negative gate, при этом `RowsEvaluated` равно числу заявленных items ([148–200][structured-evaluate]). Флаг экспортируется и импортируется вместе с остальным checkpoint ([282–300][structured-export], [339–358][structured-import]). Но память KNN/maps/rules здесь не очищается. Обычный `GetOrchestratorAsync` возвращает `_flow` без проверки флага ([653–659][ordinary-orchestrator]); ordinary adapter также не проверяет его. Поэтому source поддерживает **ложный отрицательный сигнал готовности/evaluation**, а не автоматическую потерю способности отвечать.

**Что делают найденные callers.** Tatoeba `TrainRowsAsync` строит batch с `heldOut:false` ([747–770][tatoeba-train]); `TranslationProductHeldOutRunner` также обучает отдельный train batch, затем отправляет product cases обычному orchestrator ([309–333][product-heldout]). CLI initial/continue использует `BuildTranslationContinueExample`, где `HeldOut:false` ([4677–4694][cli-example]). Эти callers не доказывают достижимость heldout-only reset в штатном ходе.

Особенно важен контрпример **Batch029**: runner действительно создаёт `heldOutBatch`, но в `TrainStructuredBatchAsync` передаёт **trainBatch**; heldout-переводы оценивает через обычный orchestrator ([161–193][batch029-caller]). `heldOutBatch.Examples.Count` попадает в отчёт, тогда как `UnitAccuracyAfter` берётся из результата training ([238–269][batch029-report]). Таким образом, само присутствие `UnitExamplesHeldOut` не доказывает ни сброс readiness, ни запуск трёх Unit-heldout метрик из следующего раздела. Runtime product/exact accuracy там имеет отдельного потребителя; его нельзя обесценивать дефектом непройденного scorer path.

Связь с [отчётом 19](19-unit-state-identity-and-partial-learning.md): это иной эффект относительно partial batch mutation/identity, но общая тема честного состояния. Наблюдение no-op batch на живом RP01 не получено. Для isolated Student DPO/free generation прямой caller не установлен.

**Минимальный будущий различающий опыт, не запускать по этому документу.** На одинаковом обученном A сравнить отсутствие нового вызова с nonempty heldout-only B. Не менять learned state и eval items. Записать `HasStructuredTraining`, unit-memory digest, ordinary ответы, `EvaluateAsync` и фактическое число переводов внутри evaluation. Второй отдельный контраст — unknown-unit-only B; не смешивать его с первым. Стабильные ordinary ответы при изменившемся gate означают сбой контрольного сигнала, а не ухудшение перевода.

## 4. Unit-heldout metrics: три разные границы достоверности

Вход в эти метрики — `TranslationMachine.MeasureHeldOutAccuracy`: группировка по UnitId и среднее **по группам Unit**, а не по всем отдельным примерам ([662–672][unit-average]). Для применения выводов к run сначала требуется установить, что именно эти heldout rows дошли до scorer. Отдельный product-heldout экзамен не становится недействительным только из-за существования этого API.

### Verifier оценивается только на отрицательном классе данного builder

`BuildGeneralBatch` создаёт verifier input из `rejectedCandidate`, chosen verifier output имеет `Pass=false`; positive verifier example на `pair.Chosen` здесь не создаётся ([128–141][builder-verifier]). `QualityVerifierUnit.MeasureAccuracy` сравнивает только `result.Pass == expected.Pass` ([1150–1170][verifier-accuracy]). На наборе только таких строк гипотетический always-reject получил бы 100%; это аналитическое свойство метрики, не результат запущенного proxy и не поведение текущего verifier.

Контрпример: пустой настоящий verifier без learned rules не находит issues и возвращает `Pass=true` ([1052–1091][verifier-rules]); на negative-only set он получил бы 0, а не гарантированные 100. Поэтому верный вывод — протокол не проверяет принятие правильных ответов, а не «весь verifier accuracy поддельный». Hand-authored/balanced heldout, содержащий `Pass=true`, уже не имеет описанной одно-классовости.

### Tokenizer сверяется со своей Pattern-разметкой и пропускает Signature

Builder сам вычисляет base `TranslationSemanticTokenizer` sequence и записывает его Pattern в expected output; Signature при этом может получить `PAIR`/rule tags ([92–115][builder-tokenizer]). Scorer вызывает trained tokenizer, но сравнивает **только Pattern** ([164–184][tokenizer-accuracy]). Нетребующий исправлений base tokenizer совпадёт со своей Pattern-разметкой; такой score не измеряет семантическую верность независимо от автора labels. Совпадающий Pattern при неправильном Signature также засчитывается.

Signature значим для продукта: tokenizer умеет learned exact/pattern corrections ([88–140][trained-tokenizer]); обычный adapter использует именно этот tokenizer и язык request, затем executor и verifier ([117–139][ordinary-adapter]). KNN cascade ищет full/prefix/structure signature с source guard ([246–265][signature-consumer]). Но это ещё не измеренная порча ответа: для выбранных данных signature может совпадать, а phrase/word/fallback paths могут изменить результат независимо от данной ошибки метрики.

### Verifier-scoring меняет и язык, и tokenizer instance

`QualityVerifierUnit.MeasureAccuracy` создаёт **новый base** `TranslationSemanticTokenizer` и всегда вызывает его с `"ru"` ([1155–1166][verifier-accuracy]). Это отличается от ordinary `TrainedTranslationAdapter`, который получает trained semantic tokenizer и `request.SourceLanguage` ([124–126][ordinary-adapter]). Поэтому дополнительное уточнение к helper — scorer обходит learned tokenizer corrections, а не только выбирает неверный язык для EN/HE/ES.

Эффект условен: на конкретном source смена `ru/en` может не менять sequence; learned correction может отсутствовать; фактическое verifier-правило может использовать marker, а не signature. В частности, issue `translated quality marker`, создаваемый этим builder, специально исключён из signature-правила в `TrainOnExample`, но может добавить source-marker rule ([1095–1145][verifier-train]). Нельзя всем строкам builder приписать обязательную поломку signature lookup. Адресный source-контраст есть; размер bias и его знак требуют независимого exam.

## 5. Адресная сверка N26: направление coverage и polarity

**N26.03, direction metric.** При отсутствии heldout `AccuracyAfter` вычисляется не из переводов, а через `MeasureUnitCoverage`. Список required жёстко равен SemanticTokenizer + **ExecutorRuEn** + QualityVerifier ([674–684][unit-coverage]). Полный batch из этих трёх ролей для EN_RU, использующий ExecutorEnRu вместо ExecutorRuEn, получает `2/3`, а такой же RU_EN — `1`. Это арифметический вывод из source, не выполненный переводной опыт. Batch только из executor имеет другие значения; нельзя распространять 2/3 на любой EN_RU batch. Если смешанный batch содержит и RU_EN executor, данное ограничение не проявляется.

Эта величина не подтверждает accuracy ни в одном направлении; RU_EN=1 означает покрытие трёх адресов. Batch029 действительно публикует `UnitAccuracyAfter` из train result и использует прирост при `MeetsAccuracyTargets`, но одновременно проверяет отдельные product accuracy/bootstrap rate ([238–269][batch029-report]). Сам Batch029 — RU_EN; из него нельзя вывести фактическое EN_RU занижение. `TranslateForEvaluationAsync` отдельно задаёт `ru→en` ([686–704][evaluation-direction]); это другой direction seam, а не объяснение формулы coverage.

**Будущий различающий опыт:** два заранее разрешённых трёхролевых train batch для RU_EN/EN_RU с одинаковой структурой и одинаковым независимым exam по соответствующему направлению. Сравнить coverage, число реально обученных ролей и ordinary correctness раздельно. Не менять одновременно количество ролей и язык; не использовать coverage как gold качества.

**N26.02, polarity.** `Verify` проверяет присутствие required terms через `Contains`, для source-marker допускает любой из списка, а для concept rules тоже проверяет наличие target substring ([1052–1091][verifier-rules]). Если единственное релевантное условие — наличие «процесс», то «Процесс запущен» и «Процесс не запущен» обе удовлетворяют этому условию. Whole-word matching устранило бы часть substring ошибок, но само по себе не различило бы отрицание, роль или модальность. Это подтверждённая семантическая граница терминного фильтра, не утверждение, что verifier уже вернул конкретную ложь пользователю.

Обычный consumer действительно вызывает verifier, но окончательное принятие зависит также от candidate confidence; phrase-map с confidence≥0,85 допускается и при verifier failure ([124–139][ordinary-adapter]). Verifier не создаёт неправильный candidate: для реального ущерба нужно показать появление такого candidate, его путь принятия и final answer. Это уточняет, а не дублирует ранее разобранный marker OR/signature AND и phrase bypass.

**Ограничение авторского fixture.** Прочитанный `26-MICRO-VERIFIER-POLARITY-FIXTURE-2026-10-16.json` явно задаёт domain `EN_RU imperative-to-result` (строка 6). Его «Start the process» → «Процесс запущен» с `lawful_by_source=true` (11–20), как и «Enable the alarm» → «Сигнализация включена» (41–50), меняет команду на утверждение выполнения. Аналогичная смена есть у approve/send. Такие labels допустимы только при отдельно заданной задаче acknowledgment/result с нужным контекстом; они **не являются валидным gold обычного EN_RU перевода** по одной исходной команде. `lawful_by_source=true` и статус frozen не делают авторский oracle независимым. JSON прочитан, не исполнен и не изменён.

**Будущий различающий опыт:** отдельно сохранить задачу acknowledgement, если она действительно нужна, и отдельно подготовить translation exam с независимой проверкой gold. Для «Start the process» положительный перевод — например, «Запустите процесс»; близкий отрицательный — «Не запускайте процесс». Не обучать на этих exam candidates и не подменять исходный чужой fixture. При одном и том же required noun сравнить Verify, confidence/path и final ordinary output; доказательство ограничить тем потребителем, который реально прошёл проверку.
