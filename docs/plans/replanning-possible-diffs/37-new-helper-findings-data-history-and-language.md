## 1. Расписание C#500: фактическая группировка подтверждена, обязательность стратификации уточнена

[Генератор данных](../../../.kiro/xiigen-slices/work/results/RP01-astra-synthetic-dev-csharp-500-20261015/materialize_dataset.py:230) сортирует записи по SHA256 prompt. Комментарий строк231–232 требует отдельного stratified schedule. Однако [manifest](../../../.kiro/xiigen-slices/work/results/RP01-astra-synthetic-dev-csharp-500-20261015/dataset-manifest.json), поле `consumer_contract.schedule`, требует зафиксировать размер batch, число шагов, parent/reference/optimizer/RNG и бюджет; **само слово stratified и обязательный способ балансировки там отсутствуют**.

[Исполнитель](../../../14.ContinuousLearning/Training/CodeDocumentationSimulationDpoExperiment.cs:106) читает строки, готовит их в том же порядке (114–119), затем берёт последовательные десятки и сохраняет их IDs перед StepVector (175–186). Статистика всех500 сохранённых строк пересчитана без запуска trainer: SHA256 `c78a620a01cd2ab1d35962eb3521a9e87ee51deeedc325dfc809112b0e035935`; 40/50 десяток имеют повтор шаблона, минимум6 разных шаблонов, среднее8.4, максимум3 строки одного шаблона; первые две десятки содержат9 и8 шаблонов.

Это расхождение комментария автора с реализованным расписанием. **Называть его нарушением всего frozen experiment contract нельзя по одному комментарию.** Дополнительное чтение нашло [frozen runtime manifest](../../../.kiro/xiigen-slices/work/results/RP01-simulation-main500-execution-20261015/frozen-runtime-manifest.json): batchSize10, maximumUpdates50, epochs1, pairs500, точный hash набора и исходников. [canonical-input-binding](../../../.kiro/xiigen-slices/work/results/RP01-simulation-main500-execution-20261015/canonical-input-binding.json), записанный до MAIN, прямо сохраняет `schedule, training texts, record order ... unchanged`; [issued command](../../../.kiro/xiigen-slices/work/results/RP01-simulation-main500-execution-20261015/native-main.issued.json) использует этот hash и10/50. То есть поздняя рекомендация балансировки не может задним числом подменить исполненный frozen порядок. Полная человеческая история утверждения здесь не восстанавливалась.

Смешивание по хешу само по себе не доказано хуже стратификации. Различие группировки меняет агрегированный gradient и траекторию optimizer; направление пользы неизвестно. Повторы шаблона внутри batch не равны повторному незаконному применению одной и той же пары.

Будущий отдельный опыт: одинаковое множество20 принятых пар и два update в каждом плече; меняется только разбиение/порядок. Начальные состояния, tokenizer, параметры и независимая оценка фиксируются заранее. Набор по-прежнему имеет16 шаблонов, а не20 независимых семейств. Улучшение likelihood без улучшения собственного ответа — отдельный исход. Этот опыт не запускался.

## 3. E48: полезный промежуточный выигрыш сохранился под итоговым FAIL

[Исходник E48](../../../35.ExperimentsV2/Experiments/E48DomainBootstrapper.cs:26) выбирает первые60% файлов как source, остальные как target. Ближайший домен не вычисляется. Созданная `warmSrcNet` (43–45) дальше не используется; на каждой точке бюджета заново создаётся warm-сеть и повторяется source training (66–77). Это настоящие вызовы learner в историческом алгоритме, но не save→load перенос готового checkpoint.

[Сохранённый May1 JSON](../../../35.ExperimentsV2/results/E48-DOMAIN-BOOTSTRAPPER/results/run-2026-05-01-001.json) сообщает final0.3036→0.3036, `passed=false`; в notes при N56 есть cold14% и warm34%, при N112 —30% и34%. Положительный сигнал при малом target-бюджете не следует выбрасывать из-за конечного равенства.

Уточнение знаменателя: `newVal=57` — число предикатов. [ProbeNeuralNetwork.Evaluate](../../../35.ExperimentsV2/Core/ProbeNeuralNetwork.cs:112) оценивает56 соседних переходов. Это не57 независимых доменных задач. `scaling_signal=1.375` — сохранённый численный относительный прирост; строка `effGain=+1381%` ненадёжна как метрика из-за форматирования. Из округлённых14%/34% нельзя восстанавливать точный эффект. Стоимость warm source включена в enhanced; отдельно созданная неиспользуемая warmSrcNet находится до обоих таймеров.

Будущий контраст должен различать: source training как дополнительные вычисления; полезность конкретного source; исправность сохранения/загрузки. Нельзя одновременно менять все три и объявлять результат эффектом restore. Для качества нужны одинаковые целевые случаи и измерение по нескольким бюджетам; для restore — тождество состояния до/после без нового обучения. Эти проверки только предложены.

## 4. E44/E45: отрицательный результат измеряет не только вес или curriculum

[E44V2](../../../35.ExperimentsV2/Experiments/E44DatasetWeighterV2.cs:40) сначала применяет [StratifiedSplit](../../../35.ExperimentsV2/Infrastructure/StratifiedSplit.cs:23) к отдельным predicate IDs. Baseline снова перемешивает объединённые IDs и обучает новые соседние пары; enhanced идёт раздельно по general/security, повторяя security-переходы10раз (48–72). Меняются сами пары, порядок и число updates. `weighted_f1` — формула0.7×security accuracy+0.3×general accuracy, не F1 из precision/recall.

[Архив E44](../../../35.ExperimentsV2/results/E44V2-DATASET-WEIGHTER/results/run-2026-05-01-001.json) действительно отрицательный:0.1663→0.0039; general predicates6, security875. Это нельзя переименовать в успешный опыт, но нельзя и приписать падение исключительно усилению security. [E45V2](../../../35.ExperimentsV2/Experiments/E45CurriculumOrganizerV2.cs:27) определяет easy/hard порядком файлов; baseline перемешивает токены до построения переходов, enhanced сохраняет внутригрупповое соседство. [Его архив](../../../35.ExperimentsV2/results/E45V2-CURRICULUM-ORGANIZER/results/run-2026-05-01-001.json):0.3623→0.3478. Старый E29V2 имеет родственную проблему, уже разобранную в [24](24-e29-pair-value-and-probe-objective.md).

Сначала фиксировать исходные пары переходов и разделять целые источники; затем менять только weight либо порядок предъявления. Иначе эксперимент сравнивает разные задачи. Это содержательное объяснение, почему старый FAIL не запрещает идею последующего обучения или kNN, но точная историческая связь с запомнившимся пользователю matrix→function donor ещё не установлена.

## 5. E49/E50: полезная графовая эвристика и неверная трактовка устойчивости

[E49](../../../35.ExperimentsV2/Experiments/E49OrchestratorExpander.cs:37) сравнивает «нет зависимости» с Jaccard по фиксированным predicate profiles. [Архив](../../../35.ExperimentsV2/results/E49-ORCHESTRATOR-EXPANDER/results/run-2026-05-01-001.json) содержит0.6→0.8667: это9→13 правильных из15 решений о связях, а не13 успешно решённых пользовательских задач. Пять из шести предсказанных рёбер правильны. Параметры здесь не обучаются; полезность предметной эвристики не отменяется.

[E50](../../../35.ExperimentsV2/Experiments/E50DomainGraphClosure.cs:39) получает baseline и enhanced из **одной** траектории: средний delta и последний delta. Первый delta<.05 записывает closureRound без отмены. [Архив](../../../35.ExperimentsV2/results/E50-DOMAIN-GRAPH-CLOSURE/results/run-2026-05-01-001.json) сохраняет D3=0%, D4=100%, финальный≈7.14%, но `passed=true`. Финал не выполняет абсолютный критерий5%; +75.22% не является эффектом альтернативного обучающего алгоритма.

Дополнительное объяснение из исходника: профили уже введённых доменов и pairwise threshold неизменны, BuildEdges только добавляет возможные связи с новым доменом. Прежние пары этим алгоритмом не переоцениваются. Поэтому снижение относительного delta при растущем знаменателе не доказывает, что система выучила устойчивый граф. Это source-вывод, не новый replay.

В [нынешнем DynamicDomainGraph](../../../17.DynamicDomains/DynamicDomainGraph.cs:10) closure означает достижимость в предоставленных переходах; `OrchestratorExpander` ищет bridge-пути (70–118). Это другая функция. Ранний stop E50 не объявляется действующим стопом RP01. Будущий опыт должен сначала показать реального потребителя и сравнить законные выбранные связи на одной панели; temporal stability и полезность графа оценивать раздельно.

## 6. RU→EN: правило расширения памяти способно само создать неверную запись

[FrequencyQuoteMapBatchBuilder](../../../27.TranslationDomain/TranslationFrequencyQuoteMap.cs:44) не читает `GrammaticalRole`, хотя поле есть во входе; переводом слова назначается последнее слово TargetPrefix (132–139). [Executor.TrainOnExample](../../../27.TranslationDomain/TranslationTrainedUnits.cs:424) добавляет gender-alternate для всех WordMappings без проверки роли, а [DeriveGenderAlternateForm](../../../27.TranslationDomain/TranslationTrainedUnits.cs:774) смотрит лишь на окончание `-л/-ла` и длину. [AddWordMapping](../../../27.TranslationDomain/TranslationTrainedUnits.cs:744) перезаписывает contextual и surface map.

Следовательно, условная последовательность корректных уроков «пил→drank», затем существительное «пила→saw» может записать искусственное «пил→saw». Это не показанный пользовательский ответ: exact/phrase/kNN могут вернуть другой путь. Поиск имени **правильного** класса по tracked C# нашёл BuildBatch caller только в Tests/TranslationDomainTests.cs:1493. Это ограничение достижимости найденного авторского маршрута, не доказательство отсутствия любого внешнего/динамического caller. Само расширение WordMappings имеет более широкий вход — любые уроки Executor с такими mappings.

`BuildRejectedCandidate` (142–155) возвращает исходный текст, если marker пуст, не найден либо удаление даёт пустоту. Тогда текстовая chosen/rejected разница теряется, хотя JSON confidence/annotations различаются. Нельзя принять разный JSON за сохранённое предметное противопоставление. SourcePrefix/TargetPrefix не доказывают alignment конкретного слова.

Будущий малый опыт: два порядка тех же корректных уроков, trace выбранной ветки, сохранённая WordMapping и новый перевод без exact-source подсказки. Отдельно проверять авторскую пару на text-tie. Это не повод жёстко запретить все окончания `-ла`: нужна роль конкретного слова и отдельное измерение полезного gender transfer.

## 7. EN→RU: проверка схожести теряет полярность и лицо, но есть узкий защитный закон

[TranslationKnnStore](../../../27.TranslationDomain/TranslationUnitContracts.cs:194) исключает not/no и личные местоимения из content words. Дополнительный [Executor source guard](../../../27.TranslationDomain/TranslationTrainedUnits.cs:962) делает сходное исключение и требует минимум общих content tokens. Он реально вызывается в [TrySelectKnnCandidate](../../../27.TranslationDomain/TranslationTrainedUnits.cs:333). Поэтому это два слабых фильтра, а не два независимых доказательства деградации.

Контрдоказательство общему «отрицание всегда теряется»: [TranslationMemorySourceLaw](../../../27.TranslationDomain/TranslationMemorySourceLaw.cs:19) проверяет исходный текст простых copular clauses до similarity и отклоняет противоположную полярность того же субъекта/предиката/времени. Для «do not approve…» он возвращает Unknown, который сам по себе не является запретом. Пары могут также попасть в разные signature buckets; exact/word/phrase paths способны ответить раньше. Неправильный фактический ответ в этой работе не получали.

Будущее сравнение: те же уже выбранные кандидаты с совпадающими content words; отдельно supported copular и неподдержанные action clauses, смена лица и отрицания. Считать не только отказ от плохого соседа, но и сохранение правильных ответов. Unknown нельзя без измерения превратить в универсальный отказ.

## 8. Размерность cosine: условный дефект, не найденная причина RP01

[Distances.CosineSimilarity](../../../06.VectorSearch/Distances.cs:10) идёт по длине первого массива без проверки второго; [BruteForceIndex](../../../06.VectorSearch/BruteForceIndex.cs:23) вызывает эту формулу. [HnswIndex](../../../06.VectorSearch/HnswIndex.cs:49) хранит переданный vector, а Load (134–151) восстанавливает массивы без общего dimension/encoder binding. Короткий query может проигнорировать хвост indexed vector, длинный — выйти за границу. Это свойство исходника; helper JS не запускался повторно.

В [KnnLogicalUnit.Vectorize](../../../21.AgentInfrastructure/Logical/KnnLogicalUnit.cs:265) длина явно задаётся dimensions; mismatch в актуальном RP01 не предъявлен. Version drift encoder при одинаковой длине — другая проблема. Будущий первый шаг здесь — установить фактические dimensions и encoder identity у одного настоящего consumer; без несовпадения этот риск не объясняет наблюдавшееся падение.
