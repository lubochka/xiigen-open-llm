## 1. Левая фраза, а не порядок уроков

TryComposeFromPhraseMappings сортирует фразы по длине, затем идёт слева направо и берёт первую совпавшую **в текущей позиции**. Глобального сравнения разбиений предложения нет. Для `close user session`, фраз `close user → закрыть пользователя`, `user session → сеанс пользователя` и отдельных слов `close`, `session` левое совпадение закрывает первые два слова. Другая фраза уже недоступна. Полное покрытие токенов совместимо с `закрыть пользователя сеанс`. Перестановка этих двух уроков не меняет позиции совпадения: исправление исходной гипотезы helper об «очерёдности уроков» обосновано. [Сортировка и обход](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:811), [порог покрытия](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:847).

Покрытие означает число сопоставленных токенов, а не сохранение связей или смысловую корректность. В общем случае допускаются и два фразовых span с покрытием от 0.50. Контрограничения: full exact-query вернётся раньше; не каждое перекрытие ошибочно; предложенный правильный перевод требует человеческого gold и контекста. Полезный механизм сохраняется: выученные фразы действительно составляют ответы для нового полного source. Опыт должен различать качество разбиения при одинаковых mappings, а не объявлять любые composition-успехи фиктивными.

На конечном пути неправильная фраза может быть принята даже при Verifier.Pass=false: phrase-map с confidence ≥0.85 имеет отдельное разрешение; сам Executor выставляет 0.86. Поэтому verifier нельзя считать универсальным предохранителем композиции. [Confidence ветки](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:270), [условие адаптера](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationDirectionAdapters.cs:128).

## 2. `can't` и `can`: два различных фильтра

Первый SourceTokens использует regex слов, отбрасывает односимвольные куски и low-information слова. Поэтому в ASCII-примере `we can't ship the package` отрицание распадается на `can` и отброшенное `t`; после stop words остаётся тот же набор `{can, ship, package}`, что у положительного source. Для низкоинформативной сигнатуры первый порог 0.35 не защищает этот случай. [Regex/stop words](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationUnitContracts.cs:192), [cascade](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationUnitContracts.cs:246), [SourceTokens](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationUnitContracts.cs:308).

Второй, ordinary EN_RU фильтр работает иначе: NormalizeMapKey удаляет апостроф внутри слова, оставляя `cant`. Здесь наборы уже различны, но shared=2 и overlap/queryCount=2/3 удовлетворяют требованиям shared≥2 и similarity≥0.60. Это **не одинаковая токенизация двух фильтров**. [Порог ordinary](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:234), [вторая similarity](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:962), [нормализация](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:1008).

Source-law содержит полезный veto противоположной полярности, но только для узкого шаблона `the/a/an … is/was [not] …`. Для `can't ship` возвращается UNKNOWN, который не исключает кандидата. Это следует из C# шаблона и фильтра, а не из строки UNKNOWN в JS proxy. [Закон](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationMemorySourceLaw.cs:19), [исключается только Contradiction](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationUnitContracts.cs:268).

Условный конечный путь ошибки существует: одна положительная EN_RU запись, отсутствие ранних exact/phrase/word результатов, совместимый кириллический target и verifier без подходящих правил. Это пока source prediction, не наблюдение корпуса. Контрпример обобщению «отрицание нигде не обучаемо»: разрешены standalone mappings `cant→не`, `not→не`, `cannot→не`; применимые mappings или обученное правило могут изменить путь. [Допуски](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:587).

## 3. `->`: потеря разделителя и скрытый exact-source

NormalizeMapKey выбрасывает не буквенно-цифровые символы, кроме `_`, `$` и whitespace. Внутри слова `delete->archive` становится `deletearchive`; при отдельных токенах `delete -> archive` пустой `->` удаляется, и phrase matcher видит соседние `delete`, `archive`. Эти варианты нельзя смешивать: гипотеза ложной смежности относится к **отдельному разделителю/пробелам**, как в helper fixture. [Нормализация](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:1008), [фильтрация токенов](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:804).

Есть дополнительная маскировка: если урок имеет SourceText=`delete archive`, его exact-key совпадает с query=`delete -> archive`. Тогда ответ выдаёт **exact-source раньше phrase-map**. Требование helper «не обучать буквальный delete -> archive» недостаточно для изоляции phrase-path. Надо исключить полный **нормализованный** exact-key; например, изучать ту же PhraseMapping из другого полного source. [Запись exact-key](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:413), [ранний lookup](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:266), [helper work order](<C:/Users/lubao/Documents/xiigen/llm mvp/design to code session/replanning/possibleDifs/30-MICRO-NATIVE-CAUSAL-PILOTS-AND-CODEX-EXECUTOR-WORK-ORDER-2026-10-16.md:60>).

Это реальная неоднозначность source-нормализации; смысловой ущерб зависит от домена. В DSL/операторной записи `->` может быть существенен. В обычном переводе декоративный разделитель иногда допустимо игнорировать. Сам факт преобразования строки не назначает правильный перевод операторной конструкции и не доказывает снижение качества всех punctuation-примеров.

## 4. Обычная kNN-ветка есть только у EN_RU

При наличии хотя бы одного не-UNKNOWN concept **или** `|PAIR:` в signature исполнитель вызывает kNN с minimumSourceSimilarity=0 для любого направления. Иначе ordinary-попытка предусмотрена только для EN_RU и требует 0.60. Для нейтральных `large/big garden window` базовый английский tokenizer создаёт NOUN-токены без concept; raw store может вернуть EN_ES соседа, а обычный Execute до этой kNN-ветки не дойдёт. [Ветвление](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:279), [базовая классификация](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationSemanticTokenizer.cs:260), [pattern](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationSemanticTokenizer.cs:351).

Это **асимметрия доступности механизма**, а не доказательство, что снятие gate улучшит остальные направления. Similar source может менять смысл (`large`/`small`); параметр 0 у semantic/PAIR ветки не отменяет внутренних .35/.25 source-aware порогов cascade. Ранние exact/phrase/word paths работают и в других направлениях. Обученный tokenizer также может заменить signature/pattern и изменить ветвление. [Коррекции tokenizer](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:89), [cascade](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationUnitContracts.cs:246).

В helper слишком широко сказано, что `null/true/false` одинаково включают semantic path. Все три получают POS=TECH_TERM, однако ResolveConcept присваивает NULL_LITERAL только `null`; для обычных английских `true/false` здесь остаётся UNKNOWN. CODE_IDENTIFIER и PAIR дают другие возможные входы, но требуют собственного фактического токена/signature. [Различие POS и concept](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationSemanticTokenizer.cs:269), [ResolveConcept](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationSemanticTokenizer.cs:295).

Положительная ES-запись может попасть в выдачу EN_HE. Записи одного bucket сохраняют порядок добавления, фильтрация предшествует Take(k), ранжирования по качеству/языку нет. Это не полноценная проверка ни Hebrew, ни Spanish, ни English. Target guard вызывается уже после выбора cascade и его top-5. ## N33: отдельный дефект filtered ordinal, с важным контрпримером

N33 совпадает с обнаруженным при сравнении N30 proxy замечанием: phrase matcher фильтрует пустые normalized tokens, но при переходе к word-map берёт `tokens.Tokens[i]` из **исходного** массива. После удалённого punctuation-only токена индексы расходятся; Math.Min не восстанавливает соответствие. Это конкретная ошибка source-сопоставления, независимая от жадного выбора фразы. [Фильтрация](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:804), [обращение по неверному ordinal](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:837).

При RU_EN phrase `проверь→check`, word maps `проверь→check`, `файл→file`, отсутствии normalized exact-key: `— проверь файл` позволяет phrase выполнить первый шаг, а затем повторно взять исходное `проверь` вместо `файл`. `check check` набирает coverage=1, проходит RU_EN script/copy guard и может дойти до конечного ответа. Здесь source-прогноз ошибки конкретен; runtime не проверен.

Но `проверь — файл` даёт другой исход: phrase-ветка набирает лишь .5 и отказывается, после чего **TryComposeFromWordMappings обходит исходные токены**, находит обе word maps, имеет mapped=2, ratio=2/3≥.5 и может вернуть `check file`. Поэтому сохранённые proxy-счётчики «2/4 correct accepted → 4/4» относятся к изолированной phrase-функции, не ко всей Machine. В исправном downstream verifier-free примере средняя пунктуация уже может быть исправлена текущим fallback. [Полный word-map обход](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:366), [порядок Execute](C:/Projects/llm_mvp_core/27.TranslationDomain/TranslationTrainedUnits.cs:264).

Два исправления будущего work order N33: unit-обучение вызывается через **TrainStructuredBatchAsync**, а не legacy TrainBatchAsync; запрещать в обучении нужно общий normalized exact-key всех четырёх вариантов, а не только буквальный source с тире. Иначе early exact lookup маскирует именно этот дефект. Сохранение original index не решает отдельно операторную смежность N30: для неё требуется определённая семантика разделителя, а не только согласованные индексы.

## Минимальные будущие различающие проверки — не исполнены

Один замороженный structured checkpoint и независимые малые fixtures; все проверки сначала подтверждают активный adapter/caller и отсутствие конкурирующего exact-key. Менять по одному условию. Сохранять исходные и normalized tokens, signature/keys, порядок кандидатов, выбранный AdapterId, промежуточный candidate, verifier и FinalHumanResult; число raw hits отдельно от правильных конечных переводов.

|---|---|
| Левая композиция | Те же mappings и query при двух порядках уроков; отдельно сравнить оба допустимых разбиения по заранее проверенному gold. Равенство двух текущих outputs опровергает именно lesson-order объяснение, а не доказывает correctness. |
| Contraction | Положительный source и `can't` при одном positive lesson; отдельный negative lesson/word-map служит контролем обучаемости. Проверить оба фильтра и конечный adapter; получить независимый polarity gold, не назначать любой abstain качественным переводом. |

Сначала доказать недоступную ветку текущего source; затем, только при отдельной авторизации изменения, сравнивать альтернативный gate. Raw recall не принимать за точность. |
| Shared memory | Одинаковые собственные EN_HE уроки, отличие только в добавлении чужого EN_ES lesson; зафиксировать одинаковые key и порядок записей. Ни один из этих протоколов не реализован и не запущен. Для переноса пользы в RP01 сперва нужен отдельный контракт: какие сохранённые уроки/данные должны попасть в нейронный training recipient и как его free answers будут оцениваться. Подмена этого вопроса улучшением словарного Flow не закрывает нейронный результат; полезные memory/composition-успехи при этом остаются самостоятельным результатом своей ветки.
