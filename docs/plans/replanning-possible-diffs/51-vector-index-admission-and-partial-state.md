## 1. Add не атомарен; разные направления mismatch дают разные исходы

[HnswIndex.Add:49–65](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:49) сначала добавляет vector, ID, metadata, выбирает случайный уровень и добавляет пустые списки связей. Только затем [68–96](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:68) выполняет cosine/search и двустороннее связывание. `Count` — это `_vectors.Count`, не число успешно интегрированных уроков. Нет проверки dimension, finiteness или rollback. Первый Add вообще завершается до какого-либо сравнения координат.

[Distances.CosineSimilarity:10–20](C:/Projects/llm_mvp_core/06.VectorSearch/Distances.cs:10) итерирует `a.Length` и читает `b[i]`; равенство длин не проверяется. Это асимметрия: длинный первый аргумент вызывает выход за границу короткого второго, а короткий первый аргумент молча игнорирует хвост второго, включая его вклад в норму.

## 3. Nonfinite admission и сериализация — разные границы

HNSW и BruteForce не отказывают в NaN/Infinity ни при Add, ни при Search. Cosine не проверяет finite координаты/результат; проверка `denom<1e−9` не ловит NaN. Один сохранённый `[NaN,0]` и query `[1,0]` достаточны для возвращаемого NaN score без вопроса о сравнении нескольких кандидатов. С `[+Infinity,0]` тот же путь получает `Infinity/Infinity`. Это вывод по арифметике source, не результат native запуска.

Не следует называть порядок NaN в .NET просто «неопределённым»: [HnswIndex.ScoreDesc:182–188](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:182) явно использует `Single.CompareTo`, а затем ID. По [контракту Single.CompareTo](https://learn.microsoft.com/en-us/dotnet/api/system.single.compareto?view=net-9.0) NaN сортируется ниже чисел; NaN/NaN сравниваются равными. При этом отдельные обычные `<`/`>` в обходе HNSW не являются finite-validation. Это не semantic abstain и не гарантия корректного ранжирования/достижимости при повреждённых координатах. Смешанный многоточечный outcome здесь не исполнялся.

[MeanPooling:19–55](C:/Projects/llm_mvp_core/05.Embeddings/MeanPooling.cs:19) получает hidden values, усредняет и нормирует. [EmbeddingModel.EnsureNonZeroUnitVector:49–74](C:/Projects/llm_mvp_core/05.Embeddings/EmbeddingModel.cs:49) полезно восстанавливает нулевой/слишком малый embedding через токены, но не является finite guard: для NaN обе проверки нормы не дают отказа, а деление не устраняет NaN. Штатные свежие массивы устраняют найденный alias-сценарий, но сами по себе не доказывают численную пригодность embedding. **Фактический nonfinite output encoder и прохождение всех более ранних production guards в этом пакете не установлены.**

В реальном transformer consumer [Search/ScoreCandidates:181–196](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:181), [217–243](C:/Projects/llm_mvp_core/18.CapabilityTraining/LlmIngredientLogicalUnits.cs:217) нет отдельного отказа по finite score: vector score проходит Clamp и смешивается с lexical/pattern score. Это точный потенциальный получатель плохого значения, но не наблюдение, что он уже получил его на реальном запросе.

**Save ограничивает часть этой гипотезы.** [HnswIndex.Save:115–131](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:115) копирует текущие координаты в List, затем вызывает `JsonSerializer.Serialize(data)` без custom options, после этого пишет `.tmp` и делает Move. Для .NET 9 проверена первичная цепочка [SingleConverter.Write](https://github.com/dotnet/runtime/blob/v9.0.0/src/libraries/System.Text.Json/src/System/Text/Json/Serialization/Converters/Value/SingleConverter.cs#L22) → [Utf8JsonWriter.WriteNumberValue](https://github.com/dotnet/runtime/blob/v9.0.0/src/libraries/System.Text.Json/src/System/Text/Json/Writer/Utf8JsonWriter.WriteValues.Float.cs#L23) → [ValidateSingle](https://github.com/dotnet/runtime/blob/v9.0.0/src/libraries/System.Text.Json/src/System/Text/Json/Writer/JsonWriterHelper.cs#L78): nonfinite вызывает исключение. Следовательно такой Save не доходит до File.WriteAllText/Move; он не заменяет существующий target checkpoint. Память индекса от этого не откатывается. Это source-предсказание стандартного сериализатора, а не проверка установленного runtime/диска.

Для **конечных** несовпадающих размеров, изолированной ghost-записи и изменённых через alias координат JSON-валидация не обеспечивает целостность индекса. Save сохраняет текущие vectors/IDs/graph; [Load:134–151](C:/Projects/llm_mvp_core/06.VectorSearch/HnswIndex.cs:134) восстанавливает их без общей проверки dimensions, связности и согласованности полей. Он создаёт новые массивы: прежний внешний alias на original float[] не переходит в загруженный экземпляр, но уже изменённые координаты остаются в snapshot. Сам Load также не содержит явного finite guard; все возможные внешние malformed JSON representations здесь не исследовались.

[BruteForceIndex.Save/Load:32–36](C:/Projects/llm_mvp_core/06.VectorSearch/BruteForceIndex.cs:32) вообще выбрасывают `NotImplementedException`. Его alias/NaN пример — in-memory доказательство, не свидетельство cold restore. Наличие `.tmp`/Move в HNSW защищает порядок записи файла, а не атомарность Add и не семантику уже сохранённого состояния.

## 5. Малый будущий различающий протокол — только предложение

Запуск требует отдельного прямого разрешения пользователя. Никакого runner/теста/копии proxy для него не создано. Проверки можно ограничить тремя независимыми механическими случаями, без обучения нейросети:

1. **Атомарность/shape:** на current HNSW отдельно два направления mismatch из таблицы; фиксировать exception, Count, IDs, размеры, entry/levels/edges до/после, затем результат прямого Save/Load. В контрольной ветке отвергать неправильную длину до Add. Для первого случая достаточно Count/graph — subsequent valid Add не нужен для доказательства мутации и внёс бы RNG-различие. Если всё-таки сравнивать последующее качество, сначала фиксировать уровни/исходный граф, а не выдавать иной random rebuild за эффект исправления.
2. **Alias:** двумерный BruteForce-контраст исходный buffer против копии, одна внешняя запись после Add, одинаковые query/IDs. Проверить выбранный ID и координаты; не смешивать этот эффект с HNSW reverse-prune. Для фактического production влияния отдельно предъявить caller, который действительно сохраняет и меняет тот же массив. Без него результат останется свойством API.
3. **Nonfinite:** singleton index/query с одной заранее названной NaN/Infinity координатой; отдельно admission/Search и Save. Guard-контроль отвергает вход до мутации. Ожидаемое различие — RAM принимает nonfinite, стандартный HNSW Save его не пишет; нельзя заранее обещать successful poisoned restore. Проверка malformed finite dimensions относится к пункту 1, а не к NaN.

К доменной оценке переходить только после найденного affected caller/сохранённого состояния: один frozen corpus, encoder/tokenizer identity, тот же вызванный flow, выбранный example ID и обычный output; сравнить правильность и отказ на нескольких затронутых примерах.
