# A2 — Hybrid architectures / continual learning / catastrophic forgetting / edge distillation

**Trend.** Current research pushes continual (lifelong) learning to counter catastrophic forgetting, edge/on-device distillation, and hybrid architectures that keep learning after deployment.

**How this project relates.** LlmFromScratch approaches this space with a real from-scratch low-rank adapter mechanism wrapped in two continual-learning pipelines. `10.LoRA` provides genuine from-scratch low-rank adapters so a base model can be extended without full retraining (it is in the verified-trained list). `14.ContinuousLearning` and `16.AutonomousLearning` supply the surrounding pipeline plumbing — codebase indexing, feedback / DPO-pair routing, an idle detector, replay mixing, and a promote-only-if-improved gate — for per-project incremental and idle-time training. The whole stack is pure C# with no cloud dependency — that is the edge / on-device angle.

**Where in the code.** `14.ContinuousLearning/Pipeline/ContinuousLearningPipeline.cs:22` (the per-project cycle: index -> cache -> feedback DPO pairs -> train -> register); `14.ContinuousLearning/Training/IncrementalTrainer.cs:55` (the actual LoRA/DPO gradient step is not wired to a live model here — the trainer records the intended `{domain}.lora` path and returns); `16.AutonomousLearning/Pipeline/AutonomousLearningPipeline.cs:24` (idle detection, before/after evaluation and a promote-only-if-improved gate, delegating the same `IncrementalTrainer`); `10.LoRA/LoraApplicator.cs:17` (`LoraApplicator.Apply` freezes the base parameters and returns LoRA adapters for the attention layers — a real from-scratch mechanism).

**Orchestration.** Continual learning is itself pipeline-driven: `ContinuousLearningPipeline` and `AutonomousLearningPipeline` are the orchestrators, and trained adapters are held per domain by an in-memory `DomainModelRegistry` (`14.ContinuousLearning/Registry/DomainModelRegistry.cs:14`). Publishing and re-loading accepted checkpoints through `25.ModelServer` (`IModelRepository`) is the project's model-server contract, but these two pipelines are not wired to it — that is a separate path that is not yet connected.

**Honesty boundary.** LoRA is a real, implemented from-scratch mechanism (in the verified list: DpoTrainer, LoraApplicator, Trainer, TranslationMachine). The continual / autonomous pipelines (`14.ContinuousLearning`, `16.AutonomousLearning`) provide the pipeline plumbing; the actual incremental / idle-time training step is not yet wired to a live model — it records the intended adapter path rather than running the gradient update — and the pipelines are not connected to `25.ModelServer`. So this answer does not claim more than the verified list: it is real low-rank machinery plus honest continual-learning scaffolding, not a solved lifelong-learning system and not a claim that the continual loop trains end-to-end today.
