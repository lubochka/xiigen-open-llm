## Что именно должно стать зелёным и почему

Прицельный прогон фильтром `FullyQualifiedName~TestSuiteBatchInventoryGuard`
поднимает **весь класс — 61 проверку** (подсчёт меток `[Fact]` = 61), а не только
36. Поэтому честное ожидание такое:

1. **61 из 61 зелёная.** Из них 36 — именно те, что названы в уликах полного
   прогона `artifacts\fbe\FULL-SUITE-20261110\attempt-0001\failures-all-501.md`
   (36 поимённых строк класса). Они падали с исключением
   `Test project has no TargetFramework: ...\.kiro\...\Tests\LlmFromScratch.Tests.csproj`,
   потому что сканер объявлял тестовым проектом хранилища однострочную заготовку
   из каталога результатов работ владельца. После сужения области такие копии в
   опись не попадают, исключение не бросается.
2. Остальные 25 проверок класса работают на синтетических корнях без файла
   решения. Они были зелёными и обязаны остаться зелёными: для корня без решения
   код идёт по прежней ветке полного обхода. Если покраснеет хоть одна из них —
   правка задела синтетическую ветку, и это отказ.
3. Ключевое числовое ожидание внутри проверки
   `ActualRepositoryInventoryMatchesCheckedInSnapshot`
   (`Tests\TestSuiteBatchInventoryGuardTests.cs:470`): `report.Projects.Count == 3`.
   Предсказываю ровно 3, потому что решение объявляет три проекта с пакетом
   тестового набора (`Tests\LlmFromScratch.Tests.csproj`,
   `Tests\DesignConversion.ModelActivation.Tests\...`,
   `Tests.ApiDashboardWpf\...`), а четвёртый объявленный служебный проект

   в решении не объявлены, поэтому в опись больше не попадают — без них счёт и
   равен трём.
4. Отчёт сторожа обязан быть без проблем (`AssertNoProblems`): раз в описи ровно
   три объявленные сборки, проблемы `batch_manifest_unknown_dll` и
