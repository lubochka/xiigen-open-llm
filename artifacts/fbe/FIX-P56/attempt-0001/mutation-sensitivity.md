# Доказательство чувствительности: что покраснело при удалении правила

Назначение: строка очереди переносов «обязательное слово проверяется целиком»
(строка работ 24, устойчивое имя `FIX-P56`), попытка `attempt-0001`.

Зелёный прогон без доказанной чувствительности не доказывает ничего. Поэтому из
продукта было временно удалено одно утверждение правила, и измерено, что именно
покраснело.

## 1. Что именно удалено

Файл: `C:\Projects\llm_mvp_core\27.TranslationDomain\TranslationTrainedUnits.cs`.
Удалённое утверждение — цикл сравнения обязательных слов с словами кандидата по
одной и той же позиции, внутри метода проверки целого слова. В живом дереве до
мутации оно занимало строки 1560–1571:

```csharp
            // Compare every required word against the candidate word at the same offset.
            for (var offset = 0; offset < requiredWords.Count; offset++)
                // Letter case is ignored so an upper-case "READY" still satisfies "ready".
                if (!string.Equals(
                        candidateWords[start + offset],
                        requiredWords[offset],
                        StringComparison.OrdinalIgnoreCase))
                {
                    // This offset is not a match: stop comparing it and try the next one.
                    matches = false;
                    break;
                }
```

**Честная оговорка о слове «строка».** Наряд требовал убрать ровно одну строку
правила. Фактически удалено одно **утверждение**, занимавшее 12 физических строк
вместе со своими комментариями. Удалить одну физическую строку так, чтобы
продукт собрался и чтобы различие проявилось именно на контрпримерах, нельзя:
удаление одной физической строки внутри этого утверждения оставляет цикл без
тела и даёт ошибку сборки, а удаление других одиночных строк правила
(например проверки пустого требования на строке 1548) на панели этой приёмки
вообще ничего не меняет, то есть не различает дефект.

Почему выбрано именно это утверждение: без него переменная совпадения остаётся
истинной, и правило объявляет требование найденным для любого кандидата, у
которого слов не меньше, чем в требовании.

**Поправка 11.11.2026: мутант не равен прежнему выражению и слабее его.** В
первой редакции здесь стояло «это и есть возврат к прежнему поведению
„обязательное слово ищется куском текста“». Это строго неверно. Прежнее
выражение требовало, чтобы буквы требования хотя бы присутствовали в кандидате;
мутант не требует и этого — он принимает любого кандидата достаточной длины в
словах, даже если ни одной буквы требования в нём нет. То есть мутант — более
грубое ослабление, чем исходный дефект, и он доказывает зависимость утверждений
от удалённого кода, но не воспроизводит прежнее поведение продукта.

Из этого следует, какая строка панели что именно различает:

- строка S2 (`ReadyFlag already` при требовании `ready`) несёт различение «кусок
  против целого слова»: буквы требования в кандидате есть, и прежнее выражение
  приняло бы его ошибочно;
- строка S4 (`null is already` при требовании `is ready`) этого различения **не
  несёт**: `is ready` не является куском текста `null is already`, поэтому
  прежнее выражение отказало бы и без правки. На мутанте она краснеет, то есть
  зависимость от удалённого кода у неё есть, но прежний дефект она не
  воспроизводит.

Это рассуждение по коду, а не исполненное измерение: прогона прежнего выражения
против панели обычного пути в этой попытке не было. Копия прежнего выражения
измеряется только на прямой панели соседнего уже принятого файла проверок, где
его исход записан как 3 из 4 и 2 из 4.

## 3. Что покраснело на мутанте

Прогон 5 из журнала команд: сборка код возврата 0, прогон код возврата 1,
`Failed: 2, Passed: 3, Total: 5`, каталог результатов
`Tests/TestResults/fix-p56-run02-mutant`.

**Упало ровно то, что было записано в ожиданиях до прогона.**

Новая проверка обычного пути — упала на контрпримере:

```text
Failed TranslationRequiredWholeTermOrdinaryPathTests.OrdinaryConsumerPath_RequiredTermIsCheckedAsWholeWords
  Assert.Equal() Failure: Strings differ
  Expected: "bootstrap-ru_en"
  Actual:   "executor-ru_en-exact-source"
  at ...TranslationRequiredWholeTermOrdinaryPathTests.cs:line 316
```

По-человечески: без правила целого слова продукт **принял обычным путём заведомо
неверный перевод** — тот, где обязательное слово стоит только куском внутри
другого слова. Ответ пришёл из точной памяти исполнителя вместо отказа и
заготовки.

Соседняя уже принятая проверка прямого контроля — упала на главной строке
фактора:

```text
Failed TranslationRequiredWholeTermLearningTests.CandidateArm_LearnedTermMustMatchWholeWords_AndSurvivesFreshLoad
  основная панель после урока, строка P2 «already» (ГЛАВНАЯ СТРОКА ФАКТОРА:
  выученное слово стоит куском внутри другого слова): ожидалось отказ, получено принято
```

## 4. Что осталось зелёным на мутанте и почему это правильно

Три проверки остались зелёными, и каждая по своей причине:

- предусловие оснастки — оно измеряет подписи разбора и правила целого слова не
  касается вообще;
- базовое плечо соседнего файла — оно намеренно утверждает только те исходы,
  которые обязаны держаться и до правки, и после неё;
- плечо-опровержение соседнего файла — оно прогоняет копию прежнего выражения
  поиска куска текста и утверждает, что та даёт 3 из 4 и 2 из 4; от продуктового
  кода это утверждение не зависит.

## 6. Чего это доказательство не даёт

Оно доказывает, что утверждения новых проверок действительно зависят от
удалённого утверждения правила, и что соседний прямой контроль зависит от него
же. Оно не доказывает отсутствия регресса в остальных областях проекта: полный
набор проверок этим нарядом не запускался. Оно не измеряет качество обучения.
