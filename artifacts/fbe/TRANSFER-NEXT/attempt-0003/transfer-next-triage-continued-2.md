**Что это.** Третий читающий проход по очереди переносов удачных опытов. Два прежних прохода лежат
рядом и прочитаны мной целиком:
`artifacts/fbe/TRANSFER-NEXT/attempt-0001/transfer-next-triage.md` (467 строк) и

## 0. Якорь состояния реестра и предупреждение: файл реестра правится параллельно

Все адреса строк ниже верны для **точного состояния файла**
`docs/plans/replanning-possible-diffs/fixes-based-on-experiments/01-registry.md`
**размером 792 178 байт, время изменения 12 ноября 2026, 13:17:56**.

Это не формальность. По ходу моей работы файл реестра **изменился под мной**: в начале прохода он
имел 791 228 байт, таблица работ начиналась строкой 147, первый пункт квалификации стоял на строке
321. Сейчас — 792 178 байт, таблица работ со строки 149, первый пункт квалификации на строке 323.
Все адреса в разделе пунктов квалификации сдвинулись на **плюс две строки**.

Последствие, которое обязан назвать: **адреса строк в двух прежних проходах уже частично
недействительны** — например первый проход ссылается на «строку 146» для порчи двоичных
доказательств и «строку 195» для оценщика порчи, второй — на «строку 229» для порога загрузок.
Эти числа были верны для своего состояния файла и не верны для нынешнего. Поэтому каждый адрес в
этом файле я привязываю к якорю выше, а не к имени файла вообще.

Измеритель сдвига проверен на положительном и отрицательном примере: заголовок пункта
квалификации 30 ищется поиском по строке — найден на 787; прямое чтение строки 787 даёт тот же
заголовок (совпало); прямое чтение строки 785, которую давал прежний поиск, даёт другой текст
(расхождение опознано). То есть сдвиг установлен двумя независимыми приборами, а не выведен из
одного.

### 1.2 Что я дополняю

**Главное дополнение.** Второй проход честно назвал 33 непросмотренные строки и их адреса. Я
проверил эти списки поиском по рабочим именам: **ни одна из двенадцати строк, разобранных в
разделе 3 этого файла, не упоминается ни в одном из двух прежних проходов ни разу** — ноль
попаданий по каждому из двенадцати рабочих имён в обоих файлах. То есть этот проход не повторяет
прежние, а закрывает их белое пятно.

**Второе дополнение.** Прежние проходы отсеивали строки по одному обязательному признаку —
закрепляет ли карточка доисходный отпечаток испорченного пути. Это верный, но недостаточный
отсев: он не проверяет, **существует ли названный перенос в коде уже сейчас**. Я добавил второй
обязательный отсев — чтение живого кода по адресу из колонки состояния. Он и дал семь
противоречий раздела 2.

**Третье дополнение.** Сдвиг адресов строк реестра (раздел 0) прежними проходами не наблюдался,
потому что они работали до правки.

**Четвёртое дополнение.** Незакрытый перенос общих настроек чтения учебного JSON: каталог
доказательств `artifacts/fbe/FIX-JO/attempt-0001/` содержит только наблюдение о выделениях и
текстовый указатель на доказательства — **ни красного прогона до правки, ни зелёного после**, в
отличие от соседнего каталога `artifacts/fbe/FIX-NG/attempt-0001/`, где лежат оба и ещё две
регрессии. Незакрытый перенос опаснее ненач атого: он выглядит сделанным.

### 1.3 С чем я не согласен — один пункт, с причиной

**Не согласен с достаточностью отсева «карточка не закрепляет доисходный отпечаток — значит строка
не блокирована».** Второй проход вывел из этого признака, что шесть живых сестёр «ноябрьским
фактом не блокированы», и перешёл к выбору кандидата. Признак верный, но он отвечает только на
вопрос о порче двоичных доказательств. Он **ничего не говорит** о том, перенесена ли работа уже.
Моя проверка показывает цену этого пробела: пять строк, которые по тексту реестра выглядят
открытыми и по признаку закреплений не блокированы, в действительности уже стоят в продуктовом
коде. Если бы отбор опирался только на прежний отсев, они попали бы в первую очередь — и перенос
дал бы ровно те мусорные коммиты, которые запрещены.

Это несогласие не отменяет ни одного конкретного вывода прежних проходов: их пять исполнимых строк
и один проверенный кандидат лежат в исходниках опытных прогонов и в файле
`42.ProjectWikiDomain/OrchestrationPlanMachine.cs`, и второй проход там прочитал живой код лично
(его раздел 2.5). Несогласие касается только правила отсева, которое они применяли к остальной
очереди.

## 4. План переноса чистого кандидата, исполнимый без изобретения

Перенос по этому плану в текущем наряде **не выполняется**: сборки и прогоны запрещены до чистого
окна, и сам перенос придёт отдельным нарядом.

### 4.1 Какой порядок обхода требует карточка — дословно

Карточка `29-matmul-right-gradient-locality.md`, строка 95:

> Изменить порядок циклов `batch → inner → column → row` на `batch → row → inner → column`; перед
> внутренним `column` один раз прочитать `aValue = a.Data[aOffset + row*aCols + inner]`.

Там же приведено само накопление, которое обязано остаться прежним:

```csharp
gradB[bOffset + inner * bCols + column] +=
    aValue * result.Grad.Data[resultOffset + row * bCols + column];
```

Строка 102 карточки перечисляет, что обязано сохраниться: «Для каждой ячейки B последовательность
суммирования по batch/row сохраняется. Сохранить `bBatch = batch % bBatchSize`, offsets, shape,
`AccumulateGrad`, gradA, forward SIMD и cancellation. Не добавлять parallel reduction, новую
формулу, транспонирование/кэш весов или экспериментальную `GradBExperimentTelemetry` в production».

### 4.2 Какой порядок стоит сейчас

Живой код `00.TensorCore/Core/TensorOps.cs`, строки 702–704, прочитаны лично:

```csharp
for (int inner = 0; inner < aCols; inner++)
for (int column = 0; column < bCols; column++)
for (int row = 0; row < aRows; row++)
```

Элемент левой матрицы читается внутри самого глубокого цикла, то есть заново на каждую тройку
«внутренний индекс, столбец, строка».

### 4.3 Точное место правки

Файл `00.TensorCore/Core/TensorOps.cs`, ветвь «если правая матрица требует градиента» внутри
функции обратного прохода умножения матриц: объявление массива градиента на строке 695, цикл по
партиям со строки 696, смещения на строках 698–701, тройной цикл на строках 702–704, тело
накопления на строках 705–708, передача накопленного градиента на строке 712. Правка касается
строк 702–708 и добавляет одно чтение перед внутренним циклом по столбцам. Ни одна другая ветвь
функции не меняется.

### 4.4 Различающая проверка — честный ответ, а не удобный

**Поведенческой проверки, которая падала бы против текущей логики и проходила после правки, у этой
работы не существует, и это свойство самой работы, а не пробел плана.** Основание прямое: правка
сохраняет формулу, смещения и порядок суммирования по партиям и строкам для каждой ячейки —
значит числа до и после совпадают **побитово**. Любое утверждение о числах по построению зелёное в
обеих руках. Карточка это признаёт сама, строка 198: «Oracle задан независимо от нового порядка
циклов», и три назначенных ею проверки — «точная целочисленная арифметика».

Поэтому называю ровно то, что эти три проверки доказывают и чего не доказывают, и чем их дополнить.

**Что три назначенных карточкой проверки действительно закрывают — зияющий пробел покрытия.**
Карточка, строка 171, прямо пишет про существующую проверку обратного прохода: «Сохраняет gradA; в
текущем тесте B не trainable, поэтому он один **не покрывает gradB**». То есть сегодня у расчёта
градиента правой матрицы покрытия нет вовсе, и перенос пошёл бы в непокрытый код. Три проверки из
карточки (новый класс `Tests/ExperimentFixes/GradBLocalityContractTests.cs`) закрывают именно это,
с независимо выведенным ожидаемым:

| Проверка | Вход и независимое ожидаемое, дословно по карточке |
|---|---|
| Неоднородный верхний градиент против аналитического результата | A=[[1,2,3],[4,5,6]] без градиента; B=[[2,-1],[0,3],[-2,4]] с градиентом; верхний G=[[1,2],[3,4]]. Ожидаемое gradB=[[13,18],[17,24],[21,30]] |
| Оба градиента сохраняют накопление | те же A/B/G, обе стороны с градиентом. После одного свежего обратного прохода gradA=[[0,6,6],[2,12,10]], gradB как выше. На втором свежем выходе с теми же листьями и тем же G, без обнуления, оба градиента ровно удваиваются |
| Пакетный правый градиент сохраняет привязку партии | A[2,2,3], B[2,3,2], G[2,2,2] с полными значениями из карточки. Ожидаемое gradB: прежняя первая матрица / [[13,-13],[14,-14],[15,-15]]; gradA: прежняя первая / [[1,1,-5],[-2,-2,10]] |

**Чем заменяется различающая проверка — две вещи, обе измеримые.**

Первое: **чувствительность к поломке вместо чувствительности к переносу.** Три проверки выше
обязаны падать против **испорченного** индексирования. Назначенная мутация, по смыслу карточки
(строка 203: «Если B падает на прежнем независимом expected — чинить indexing/accumulation в
назначенной ветви»): заменить в теле накопления `bOffset + inner * bCols + column` на
`bOffset + column * bRows + inner`. Против такой мутации первая проверка обязана дать не
[[13,18],[17,24],[21,30]], а другую матрицу, и упасть. Если она не падает — проверка бессмысленна,
и это выясняется до переноса, на неизменённом коде. Это и есть единственная различающая величина,
доступная здесь: различение правильного индексирования от неправильного, а не старого порядка от
нового.

Второе: **ресурсная панель двух рук как носитель заявленного выигрыша.** Карточка задаёт
двухстадийный прогон (`Tests.Support/ExperimentTransfer/Run-NativeAB.ps1`, стадии `Baseline` и
`Candidate`) с измерением времени, процессорного времени и выделений вокруг двух настоящих шагов
обучения, и требует точного совпадения квитанций обеих рук по носителям, чтениям, потерям,
именованным числам и состоянию оптимизатора. Совпадение квитанций — доказательство, что числа не
поехали; расхождение панели — доказательство, что выигрыш есть.

**Прямая оговорка карточки, которую обязан перенести без смягчения** (строка 162): «Исторический
участок −62% не измеряется этим новым whole-step timing и не становится CI порогом. CI проверяет
обучение/parity; будущий receipt честно показывает все resource deltas, включая отсутствие
выигрыша». То есть 62,59% из пункта квалификации 30 — выигрыш ядра в прежнем измерении, и новая
панель может его не воспроизвести; это допустимый исход, а не повод ослабить оракул.

**Решение, которое не моё.** Если требование «проверка, падающая против текущей логики» для этого
класса переносов обязательно без исключений, то единственный способ его выполнить — написать
проверку, чувствительную к порядку циклов, то есть подогнанную под новую реализацию. Это прямо
запрещено правилом «нельзя подгонять ожидаемое под код». Поэтому выбор между «принять
чувствительность к мутации плюс ресурсную панель» и «не переносить работы этого класса вовсе» —
решение родителя-архитектора, а не моё.

### 4.5 Решение родителя-архитектора от 12 ноября 2026 и пять условий его действия

Вопрос из раздела 4.4 отдан родителю-архитектору и решён им: **принято «чувствительность к
поломке плюс ресурсная панель», работы этого класса переносятся.** Основание названо как правило,
а не как уступка: правило проекта требует от проверки падения против прежней или заведомо
сломанной логики **либо равноценного опровержения**. Для переноса, который по построению даёт
побитово те же числа, равноценное опровержение — ровно два факта: проверки падают против
сломанного индексирования (значит они не пустые) и квитанции двух рук совпадают дословно (значит
равенство чисел доказано, а не предположено).

**Пять условий, без которых решение не действует.**

1. **Проверки приходят первыми, до переноса, и их чувствительность доказывается на неизменённом
   коде.** Новый класс проверок делается независимо от переноса, потому что он закрывает зияющий
   пробел: карточка сама признаёт, что у расчёта градиента правой матрицы покрытия сегодня нет
   вовсе — существующая проверка обратного прохода держит только левый градиент, так как правая
   матрица в ней не обучаемая. Порядок исполнения: новый класс проверок зелёный на текущем коде →
   названная мутация индексирования (`bOffset + inner * bCols + column` заменяется на
   `bOffset + column * bRows + inner`) делает их красными → откат мутации → только потом
   перестановка циклов → те же проверки снова зелёные. Так «различающей проверки нет»
   превращается в «сеть безопасности поставлена заранее».
2. **Если хоть одна из трёх проверок не краснеет против названной мутации — она пустая, и её
   усиливают до переноса, а не после.** Это уже случалось в слайсе второго исполнителя: там
   проверка раннего захвата сама создавала то, что проверяла, и выяснилось это только мутацией.
3. **Равенство чисел доказывается, а не предполагается.** Квитанции обеих рук обязаны совпасть
   дословно по носителям, чтениям, потерям, именованным числам и состоянию оптимизатора. Любое
   расхождение — стоп и доклад; перенос не делается.
4. **Ресурсная панель — отчёт, а не гейт.** Никакой порог по времени не становится условием
   приёмки. Причина конкретная: на этой машине параллельно работает другая сессия, которая
   запускает свои сборки, поэтому измерения времени загрязнены. Панель обязана приложить проверку
   занятости машины и назвать условия измерения. Отсутствие выигрыша — допустимый исход; его
   показывают честно и ни в коем случае не используют как повод ослабить оракул. Оговорка карточки
   про исторические минус 62% остаётся без смягчения, как перенесена в разделе 4.4.
5. **Допуск к переносу стоит на историческом измерении карточки** — минус 62,59% и минус 60,67% по
   ядру при плюс 0,00086% выделений, — и это измерение уже отвечает критерию хозяйки. **Новая
   панель есть доказательство честности, а не повторная квалификация: исторические 62% ею заново
   не подтверждаются, и заявлять это запрещено.**

**Граница этого решения, записана дословно по требованию родителя-архитектора:**

> оно действует ТОЛЬКО для переносов, про которые доказано, что выход побитово тот же, и доказано
> совпадением квитанций, а не рассуждением. Для любого переноса, способного изменить выход,
> поведенческая различающая проверка обязательна. Писать проверку, чувствительную к порядку
> циклов, запрещено — это подгонка под реализацию, и тут я с тобой полностью согласен.

### Пометка 12.11.2026, вечер (исполнитель): моя ошибка в разделе 3.2, прежний текст сохранён

**В чём ошибка.** Я посчитал оставшиеся места создания настроек и сделал из их
