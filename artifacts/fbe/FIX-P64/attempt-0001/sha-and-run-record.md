## Применение `git restore`

Применяла РОВНО ОДИН раз, одной командой на два файла:

    git restore -- 27.TranslationDomain/TranslationUnitContracts.cs \
                   27.TranslationDomain/TranslationTrainedUnits.cs

Зачем: снять красный на неизменённом опубликованном коде тем же окончательным
исходником проверок. Перед этим мои правленые файлы были скопированы в
единственный разрешённый временный каталог
`artifacts/fbe/FIX-P64/attempt-0001/tmp`, после красного прогона возвращены
оттуда обычным копированием (не `git restore`), а временный каталог удалён в том
же ходе с проверкой чтением. Равенство восстановленного кода опубликованному
подтверждено двумя способами: `git diff --stat` по каталогу продукта дал пустой
вывод, и побайтовое сравнение с `git show HEAD:<путь>` совпало.

Других записывающих команд `git` не было: ни `add`, ни `commit`, ни `push`, ни
`checkout`, ни `reset`, ни `branch`, ни `merge`, ни `rebase`, ни `tag`, ни
`stash`.

## Дословный вывод прогонов не переписывался

В четырёх файлах `*.log` сохранён дословный вывод запускателя проверок, включая
возвраты каретки (323, 4, 69 и 26 байт соответственно). Я их намеренно не
нормализовала. Проверено, что при публикации они сохранятся как есть:
`core.autocrlf` = `false`, свойство `text` для этих путей не задано
(`git check-attr -a` даёт `text: unset`), поэтому байты уйдут в коммит без
преобразования.

Мои собственные текстовые улики — наоборот, чистые: во всех файлах `.md` и
`.txt`, которые написала я, возвратов каретки ноль, последний байт ровно один
перевод строки, предпоследний переводом строки не является, строк с хвостовыми
пробелами ноль. Счёт делался по сырым байтам (`tr -dc`, `od`), а не поиском по
тексту, потому что поиск в этой оболочке срезает возврат каретки и даёт ложный
ноль.
