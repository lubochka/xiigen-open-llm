## Что именно предсказывается

Проверяется не предсказатель напрямую, а БОЕВАЯ дорога обычного фасада:
обучение через `SemanticCompilerFacade.TrainMethodKnn`, затем обычная компиляция

результата компиляции.

Прочитанный механизм, на котором построено предсказание:

1. `SemanticCompilerFacade` создаёт предсказатель с ПЯТЬЮ соседями
   (`12.SemanticCompiler/SemanticCompilerFacade.cs`, строка 46).
2. Фасад отвечает, только если признак включения истинен, стек — C#, и обучено
   не меньше ЧЕТЫРЁХ пар (там же, строка 370).
3. Запрос фасада — ПОСЛЕДНИЙ извлечённый метод исходника (`extracted.Value[^1]`,
   строка 377), тогда как уже принятая приёмка предсказателя берёт ПЕРВЫЙ.

   последний и первый — один и тот же метод. Это утверждается проверкой явно.
4. Голос в `MethodKnn.Predict`: сначала число голосов, затем НОВОЕ правило
   «меньшее расстояние до ближайшего соседа внутри группы», и только потом
   порядковое сравнение имени метки.
5. Обучающая панель даёт по одной паре на файл, то есть четыре пары и четыре
   РАЗНЫЕ метки — голос выходит РОВНЫМ, по одному голосу на метку.

# ДОПОЛНЕНИЕ ПОСЛЕ ПЕРВОГО НАБЛЮДЕНИЯ — сработал названный заранее риск

## Что наблюдалось дословно

Код возврата прогона: 1. Случаев обнаружено 3, выполнено 3, прошло 0, упало 3.
Сообщение об ошибке у всех трёх: `No predicates extracted`. Падение произошло

ДО того, как дело дошло до сравнения меток.

## Классификация причины по навыку разбора падений

Это **не** дефект продукта в разрешении равного голоса и **не** неверный эталон
ответа. Это недостижимость проверяемой ветви из-за слишком бедного входа —
отдельный класс «мёртвый guard требует достижимого входа».

Прочитанный механизм причины, по живому коду, а не по догадке:

1. `SemanticCompilerFacade.Compile` на четвёртом шаге вызывает
   `LogicExtractor.Extract(source)` и при его отказе прекращает компиляцию
   (`12.SemanticCompiler/SemanticCompilerFacade.cs`, строки 147–150).
2. `LogicExtractor.Extract` возвращает отказ `No predicates extracted`, когда после
   отображения не осталось ни одного известного признака
   (`12.SemanticCompiler/Compression/LogicExtractor.cs`, конец метода `Extract`).
3. Причина пустоты — порог в `SemanticTokenizerPipeline.Level3Tokens`:
   `return result.Count >= 4 ? result : Level2Tokens(csharpSource);`
   (`12.SemanticCompiler/Compression/SemanticTokenizerPipeline.cs`, строка 62).
   Исходники панели дают меньше ЧЕТЫРЁХ разборных признаков, поэтому вместо
   признаков дерева возвращаются словесные токены второго уровня, которые
   в таблице признаков не отображаются ни во что известное и отбрасываются.

## Самостоятельная находка о достижимости боевой дороги

**Четыре экзаменационных исходника восемьдесят пятого опыта, поданные в обычный
фасад как есть, НЕ доходят до предсказания метода вообще.** Их отбраковывает
гораздо более ранний страж признаков. Это факт о боевой достижимости панели
опыта, а не о правиле разрешения ничьей. Он сохраняется в доказательствах и
передаётся архитектору отдельной строкой.

## Правка входа, а не ожидания

| Что | Значение |
|---|---|
| Что НЕ меняется | эталонные ответы `Guard`, `Guard`, `Loop`, `Loop` и контрольный `Loop`; число соседей; панель обучения; политика разрешения ничьей; продуктовый код |
| Что меняется | только ИСХОДНИК ЗАПРОСА: перед панельным методом добавляется ведущий метод-носитель признака, чтобы страж признаков пропустил исходник |
| Источник договора для правки | договор входа исполнителя, раздел 6, пункт 3: «Для мёртвого guard дать достижимый input»; навык целостности тестов, режим отказа номер два (достижимость ветви) |
| Старое ожидание | панельный исходник из одного метода доходит до предсказания через обычный фасад |
| Новое ожидание | панельный исходник доходит только в сопровождении метода-носителя признака; ИЗМЕРЯЕМЫЙ метод и его эталон при этом не меняются |
| Почему это не подгонка | ожидаемый ОТВЕТ продукта не изменён ни в одном случае; изменён только вход, который прежде не добирался до проверяемой ветви |

Почему метод-носитель не искажает измерение, и как это доказывается самой проверкой:

- запрос фасада — ПОСЛЕДНИЙ метод исходника, а носитель ставится ПЕРВЫМ,
  поэтому измеряется по-прежнему панельный метод;
- набор признаков считается у каждого метода по его собственному телу, поэтому
  добавление соседнего метода набор панельного метода не меняет;
- проверка утверждает это ЯВНО: набор признаков последнего метода нового
  исходника сравнивается с набором признаков того же метода, извлечённого из
  исходного панельного исходника из одного метода, и они обязаны совпасть;
- обучение идёт через `TrainMethodKnn`, который вызывает извлечение методов
  напрямую и стража признаков вообще не проходит, поэтому обученные пары
  этой правкой не затронуты.

Носитель признака выбран по безусловному текстовому правилу самого извлекателя:
при наличии в тексте подстроки `== null` признак охраны по пустой ссылке
добавляется независимо от пути разбора дерева, поэтому отказ по пустому набору
исключён.
