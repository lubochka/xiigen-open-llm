# Блокер: принятый родительский комплект шага 1000 не проходит собственную расписку

> **ТЕКУЩЕЕ СОСТОЯНИЕ: БЛОКЕР ЗАКРЫТ.** Всё, что ниже, — исторический разбор на
> момент обнаружения. Координатор проверил историю указателя файла весов и
> установил: расписки ВЕРНЫ, испорчены байты. Укорочение на один байт внесено
> коммитом `187b54b8844` от 2 ноября («local bin files»); до него коммит
> `8734c4e7de7` держал указатель на объект `ba8ec8c2…` размером 43500 байт.
> Подлинные объекты нашлись локально, байты восстановлены и сверены —
> `10-weights-restore-evidence.txt`. Минимальная проверка наряда после этого
> выполнена: потеря 4,8934336, шаг оптимизатора 1000 → 1001. Поэтому гипотеза
> «устаревшие расписки» из раздела ниже **опровергнута**, а вариант А из
> раздела «Два ограниченных варианта» — **исполнен**. Остальные повреждённые
> тем же классом пути намеренно не ремонтировались.

Минимальная проверка наряда остановилась ДО обучения, на восстановлении
родителя. Это дефект хранения артефактов, а не моей правки: загрузчик падает
раньше, чем создаётся обучающий цикл, и падает на сравнении хэша файла, а не на
градиенте.

## Откуда взялись нынешние байты

Три файла байт в байт совпадают между собой:

```text
bundle_equals_experiment_before_reserialization = True
bundle_equals_donor = True
```

- комплект родителя: `…/checkpoints/000002/weights.bin`, время записи 01.11.2026 15:01:50
- назначенный донор: `experiments-v2/RP01-MICRO/RESTORE-MINIMAL-SET/results/trained-weights.bin`, 43499 байт, 01.11.2026 15:02:48
- пересериализация модели из самого опыта: `experiments-v2/RP01-MICRO/SEXP01/results/attempt-0001/A/before.weights.bin` и `.../B/before.weights.bin`, 43499 байт, тот же хэш

Исходный опыт шёл 23 октября; подмена датирована 1 ноября. Похоже, что 1 ноября
и донор, и полезный файл принятого комплекта были перезаписаны результатом
пересериализации модели (43499 байт), а манифест остался прежним (43500).
Это объяснение по временам и совпадению байт, а не доказанный умысел.

## Состояние в хранилище: объявленных байт нет нигде

Содержимое отслеживаемого файла в последней публикации — указатель крупного
файла, и он указывает на ту же испорченную длину:

```text
version https://git-lfs.github.com/spec/v1
oid sha256:5696e6b532e86b03ab2332098f018fa1e0c26260287d3388a56aa7483b0f8392
size 43499
```

Поиск по всему дереву (`*weights*.bin` с длиной 43499 или 43500) не нашёл НИ
ОДНОГО файла длиной 43500 байт и ни одного с хэшем `ba8ec8c2…6e0e`.
`git status` для этого пути чист — то есть испорченный вариант и есть
опубликованное каноническое состояние.

Признаки правки переводов строк исключены: `git check-attr` даёт
`text: unset`, `diff: unset`, то есть файл помечен двоичным и перевод строк его
не менял.

Вывод по хранению: принятое состояние родителя шага 1000 **не материализуется
по хэшу** из текущего дерева. По стоячему правилу проекта указатель крупного
файла без подкладывающего объекта с нужным хэшем не является сохранённым
артефактом модели.

## Почему это не моя правка

1. Отказ выдан до создания обучающего цикла: загрузчик сравнивает хэши файлов
   задолго до первого вызова модели и до конструктора `Trainer`.
2. Текст отказа — `SFT_PARENT_SEALED_MISMATCH Payload hash mismatch: weights.bin`,
   это сравнение байт файла, а не вычисление градиента.
3. Моя правка касается только закрытого метода обратного прохода в
   `04.TrainingLoop/Trainer.cs`; она не читает и не пишет артефакты комплекта.
4. Испорченные байты датированы 1 ноября 2026, за 12 дней до этой работы.

## Два ограниченных варианта для архитектора

**Вариант А — восстановить байты родителя и повторить проверку без изменений.**
Нужны подлинные 43500 байт с хэшем `ba8ec8c2…6e0e` из источника вне этого
дерева (другая опубликованная копия, объект крупного файла из истории, резервная
копия донора). После восстановления моя оболочка проверки запускается той же
командой без правок. Эта работа пишет в запечатанный комплект и в каталог
обучающих артефактов — она за границей моего наряда, я её не выполнял.

**Вариант Б — выполнить тот же один шаг обучения из другого начального
состояния и честно назвать отличие.** В дереве есть принятый комплект номер 1
(`checkpoints/000001`, роль «свежая необученная база», шаг оптимизатора 0). Один
шаг обучения с учителем из него доказал бы ровно то, что требует карточка по
существу: шаг проходит по изменённому обратному проходу, потеря конечная, шаг
оптимизатора сдвигается на единицу (0 → 1, а не 1000 → 1001). Но это отступление
от буквы карточки, которая назвала именно шаг 1000, и загрузчик по своему
правилу выбирает комплект с максимальным номером принятия, то есть сам на
комплект номер 1 не встанет. Без слова архитектора я этот вариант не выполняю.

Третьего варианта в границах моего наряда нет: менять загрузчик, менять
запечатанный комплект, подгонять манифест под испорченные байты или объявлять
проверку пройденной — запрещено.

## Дополнение после проверки варианта Б: дефект системный, вариант Б тоже закрыт

Я проверил чтением, цел ли базовый комплект, чтобы вариант Б был проверенным
фактом, а не предположением. Он тоже сломан, и тем же способом.

| Комплект | Роль, шаг | Объявлено в его манифесте | Фактически на диске |
|---|---|---|---|
| `repos/A/.../checkpoints/000001` | свежая необученная база, шаг 0 | 43500 байт, `9bdc12d70fad4c4a0aa8b4125b00a41d824e89fc2f22a12f726bf15a54c6c098` | 43499 байт, `0ae4789953de72fc7dde47ab1935ade62d60bb0c158522ec1e6ddadb893fb743` |
| `repos/B/.../checkpoints/000001` | свежая необученная база, шаг 0 | 43500 байт, `9bdc12d7…c098` | 43499 байт, `0ae47899…fb743` |
| `repos/B/.../checkpoints/000002` | ввезённый обученный снимок, шаг 1000 | 43500 байт, `ba8ec8c2…6e0e` | 43499 байт, `5696e6b5…8392` |

То есть **все принятые комплекты этой семьи опытов в обоих хранилищах** держат
файл весов ровно на один байт короче объявленного, и у каждого свой
несовпадающий хэш. Ни один из них не пройдёт проверку загрузчика. Значит в
дереве нет ни одного родителя, из которого можно выполнить минимальную проверку
наряда, — ни шаг 1000, ни шаг 0.

Единственный файл весов этой топологии, который совпадает со своей распиской, в
дереве не найден вообще: поиск по всем `*weights*.bin` не дал ни одного файла
длиной 43500 байт.

Наиболее вероятное объяснение по наблюдаемым фактам: манифесты запечатаны
прежней записью контрольной точки (43500 байт), а все файлы на диске записаны
нынешней записью (43499 байт) — то есть формат контрольной точки продукта
изменился ровно на один байт, и запечатанные расписки от этого устарели. Это
объяснение по совпадению длин и по тому, что пересериализация модели в самом
опыте даёт те же 43499 байт; доказанным фактом я его не называю.

Следствие для вариантов: **вариант Б закрыт тоже.** Остаётся только вариант А —
восстановить подлинные байты (или признать расписки устаревшими и перепечатать
комплекты по отдельному решению архитектора). Любая перепечатка расписок меняет
смысл приёмки прошлых опытов, поэтому это решение владельца продукта, не моё.
