  ок     тип договора получен — ожидалось True, получено True

Панель 2. Жёсткость связи: задал любое имя — читается одна величина.
  ок     настоящее имя есть — ожидалось True, получено True
  ок     псевдоним есть — ожидалось True, получено True
  ок     у псевдонима нет собственного хранилища — ожидалось 0, получено 0
  ок     по умолчанию настоящее имя истинно — ожидалось True, получено True
  ок     по умолчанию псевдоним читает то же — ожидалось True, получено True

Панель 3. Установка при создании через каждое из двух имён.
  ок     договор собран отдельной сборкой — ожидалось True, получено True
  ок     потребитель, использующий СТАРОЕ имя, собирается — ожидалось True, получено True
      задал новое -> новое=False, старое=False

  ок     задал новое — старое читает то же — ожидалось False, получено False
  ок     задал старое — новое читает то же — ожидалось False, получено False
  ок     задал новое ложь — прочиталась ложь — ожидалось False, получено False
  ок     задал старое ложь — прочиталась ложь — ожидалось False, получено False

Панель 4. Выражение изменения и равенство записи.
  ок     изменение через новое имя видно старым — ожидалось False, получено False
  ок     изменение через старое имя видно новым — ожидалось False, получено False
  ок     равенство записи не различает путь установки — ожидалось True, получено True
  Равенство опирается на хранилище, а у псевдонима его нет, поэтому
  удвоения в равенстве и свёртке не возникает.

Панель 5. Потребитель старого имени получает ПРЕДУПРЕЖДЕНИЕ, а не ошибку.
  ок     сборка потребителя старого имени УДАЁТСЯ — ожидалось True, получено True
  ок     и выдаёт предупреждение об устаревании — ожидалось True, получено True
      предупреждений об устаревании: 6
      текст: 'Flags.UseConfidenceFloor' is obsolete: 'Старое имя обманывало: это не минимум уверенности, а заказ урока. Используйте UseLowConfidenceLessonSignal.'
  Это и есть ответ на главный вопрос пути (Г): двадцать замороженных
  хозяев опытов продолжают СОБИРАТЬСЯ, получая предупреждение вместо
  ошибки, и доказательная база не теряется.

Панель 6. Счёт имён в открытом списке не меняется.
  ок     имён в списке столько же, сколько настоящих признаков — ожидалось 3, получено 3
  ок     в списке стоит НОВОЕ имя — ожидалось True, получено True
  ок     псевдонима в списке НЕТ — ожидалось False, получено False
  Список написан вручную, поэтому псевдоним в него просто не вносится:
  счёт остаётся прежним, и проверки, закрепляющие счёт, не падают.

Панель 7. Чувствительность: порча пересылки обязана быть поймана.
  ок     подстановка порчи изменила текст — ожидалось True, получено True
  ок     порченый договор собирается (порча тихая) — ожидалось True, получено True
      порченый: задал новое -> новое=False, старое=True
      порченый: задал старое -> новое=True, старое=False
  ок     порча поймана: задал новое, старое РАСХОДИТСЯ — ожидалось True, получено True
  ок     порча поймана: задал старое, новое РАСХОДИТСЯ — ожидалось True, получено True
  Порча — это ровно та болезнь двух живых имён, которую мы искали:
  обе записи имеют своё хранилище, и вызывающие расходятся молча.
  Сверка её ловит, значит зелёный результат панели 2 что-то значит.
